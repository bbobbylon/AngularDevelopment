A component's fields are its own — a parent cannot reach inside a child and set one, and a child cannot reach up and read one off its parent. An input is the one door Angular builds between them. Modern Angular's input() function returns a read-only signal on the child's side, so the connection stays reactive for as long as both components are alive.

A child declares size = input(0) — no transform. The parent writes the plain attribute size="42", no brackets. Ask the child for size() + 1, and the register doesn't ring up 43. 

size = input(0);
<app-counter size="42" />
size() + 1;   // '421'
size = input(0, {{ '{' }} transform: numberAttribute {{ '}' }});
<app-counter size="42" />
size() + 1;   // 43

The mechanism

A bound value crosses the template boundary as text — nothing decides otherwise for you.

'42' + 1 is '421'. Not a bug in your math — a bug in what size() was ever holding.

The problem

How does data get into a component you don't control?

Say a parent renders <app-badge /> somewhere in its template. The parent has a signal called theme; the badge needs to know its value to pick a colour. Nothing about JavaScript's ordinary rules makes that easy — Badge is a separate class, with its own fields, and nothing links one class's fields to another's just because one happens to render the other.

Before you scroll: could Badge's class simply reach up and read theme straight off its parent — the way a method might read a sibling field on the very same class?

It can't. A component's fields are private to it in every way that matters here — there is no ambient path from child back to parent, and Angular has no interest in inventing one. What Angular gives you instead is a single, deliberate channel built for exactly this job: an input.

The mental model

An input is a function parameter.

Here's the mental model worth carrying: an input is a function parameter. A component is a function that returns UI, and its inputs are the arguments. That framing buys you more than it looks like it should — input.required<T>() is a parameter with no default, input(0) is one with a default already filled in, transform is coercion at the boundary, and "don't mutate an object you were handed" is advice you already follow with ordinary function arguments.

The one place the analogy breaks down: a function is called once and is done. An input can change while the component is still alive — and reacting to that without a callback of your own is the one job signals exist to do.

A component is a function; its inputs are the arguments. input.required<T>() is a parameter with nothing to fall back on. input(0) is one with a default already filled in. And a transform is exactly what it sounds like in a plain function too — coercion, run once, right at the door.

Deriving

Reacting to inputs with computed() — no ngOnChanges required.

Because inputs are signals, you derive from them with computed() the same way you would derive from any other signal: 

readonly initials = computed(() => this.label().slice(0, 2).toUpperCase());

The trap, fixed

Transforms fix what strings break.

A transform coerces the bound value before it ever reaches the signal — Angular ships booleanAttribute and numberAttribute, and you can hand it any pure function of your own:

Signal inputs are read-only from inside the component — only the parent sets them (use model() for two-way). And don't read an input in the constructor: bindings aren't applied yet, so a required input throws there. Read it in ngOnInit, a computed, or the template.

Under the hood

Inputs are reactive consumers, not passive properties.

A signal input isn't a plain property that Angular happens to set. When the parent's binding produces a new value, Angular writes it into the input signal, which notifies every computed and view that read it — exactly like any other signal. That's why deriving with computed() "just works" and why ngOnChanges is unnecessary: the reactivity graph already knows who depends on the input. It also means an input read is only tracked where you actually call label(); untouched inputs cost nothing.

Exam pitfalls

Five ways this bites in an exam.

  • Reading a required input in the constructor throws. Bindings aren't applied yet at construction — read it in a computed, ngOnInit, or the template.
  • Inputs are one-way and read-only inside the child. You can't label.set(...) on an input; use model() for two-way binding.
  • The string-attribute coercion trap. Without booleanAttribute, disabled="false" passes the string 'false' — which is truthy — so the child looks disabled. The transform fixes it.
  • Alias confusion. With {{ '{' }} alias: 'large' {{ '}' }} the template binds [large] but the field is big. Bind the alias, read the field.
  • Mutating an object input in the child. You share the parent's reference — mutating it is a hidden two-way channel and breaks OnPush assumptions. Treat inputs as immutable.

Before you go

Four things to remember.

  • Think of it as a function parameter: input.required<T>() has no default, input(0) has one, and transform is coercion at the door.
  • Data only flows one way — down. The parent's binding is the only thing that ever writes into an input; the child reads it with () and never sets it.
  • Derive from an input with computed() instead of ngOnChanges — no string keys to typo, no guard to forget.
  • Never read a required input in the constructor — bindings land after construction, so it throws. And never trust an unaliased boolean or number attribute without a transform.
