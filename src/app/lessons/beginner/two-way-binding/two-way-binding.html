Property binding sends data down. Event binding sends events up. Two-way binding is what happens when one value has to travel both ways at once — and it turns out to be nothing more than those two bindings, glued together by one naming rule the compiler enforces for you. This page goes from the exact expansion, through model()'s emission rules and the failure mode that catches almost everyone who splits the banana without reading this far, down to [(ngModel)] and the decorator-era pattern it replaced.

The problem

A binding that only points one way has a gap.

You already know both halves. [value]="count" sends a value down into a child. (click) or a custom (somethingHappened) sends an event back up. Between them they cover almost everything — except the one case where a child owns a piece of UI whose whole job is to propose a new value for something the parent holds: a stepper, a text field, a toggle. Wire that by hand and you write the same pair of bindings, with the same pair of names, on every single one.

Angular's answer is two-way binding: one piece of syntax that is secretly the exact two bindings you already know, written once. Before the next section shows you the mechanism, try to build it yourself.

You've written [value]="count" and (valueChange)="count = $event" separately before. If Angular offered you one piece of syntax that meant both, at once, what do you think it would look like — and why would the event's name have to be valueChange specifically, rather than anything the component author felt like calling it? There's a live comparison two sections down to check yourself against.

The mental model

Two-way binding is a banana in a box.

That's Angular's own name for [(x)], and it's a joke about the punctuation that happens to be exactly right about the mechanism. ( ) — a banana — sits inside [ ] — a box. There is no third kind of binding hiding in here: it's the two you already know, glued together.

The gluing rule is strict, and it's worth saying before you see the code: whatever you name the input, the output must be named the same thing plus the literal word Change. Not close — exact. That isn't a style guideline. It's how the compiler finds the other half of the pair.

Banana in a box. [(x)] is [x] (the box, always down) plus (xChange) (the banana, always up) — one rule, enforced by the compiler, never something you have to remember to follow by hand.

The mechanism

It's just sugar — here's the exact expansion.

The compiler rewrites [(x)]="expr" into a property binding plus an event binding, and the write-back is signal-aware: when the bound expression is a WritableSignal, Angular calls .set($event) on it instead of attempting a plain assignment — which is also exactly why you bind [(value)]="count", the signal itself, and never count(), a call expression with nothing to assign back into.

The API

model() builds you the pair.

model() declares an input/output pair in one line: an input named value and an output named valueChange, wired together and compiler-checked. The returned ModelSignal is writable from inside the child — .set() / .update() — and every child-side write emits on the output automatically. The rule most people get wrong on the first try, and the one the bubbles above just rehearsed: parent-side writes do not emit valueChange. Only writes that originate inside the child do.

Because model() is just an input + output pair, you are never forced into the full sugar. All three usages below are legal on the exact same child: full two-way [(value)]="x", one-way [value]="x" (the child's own writes stay local, nothing flows back out), or listen-only (valueChange)="onChange($event)" with no input bound at all.

The trap

Splitting the banana — and what happens when you say no.

Because [(x)] is only sugar, you can always drop back to the explicit pair and put logic between the child's proposal and your own state — clamping, validating, or dispatching to a store instead of assigning directly. This is the pattern for rejecting a value the child suggested.

parent's clamped = {{ clamped() }} child shows {{ ref.value() }}

The second pill reads straight off the child itself, through #ref — it is not the parent's number, it's a second, independent witness.

Keep stepping past 10. The parent's pill stops dead at 10 — it's clamped, as promised. Now check the other pill, the one reading straight off the child. Does it agree?

It doesn't, and it won't again until you step back down through 10. Here's why. The parent's [value] binding is an ordinary binding slot — exactly the kind the Change Detection lesson dissects — and Angular pushes a new value through it only when a fresh read genuinely differs from what's parked in that slot. Once clamped() settles at 10, every further proposal clamps back down to… 10. The slot never sees a difference, so the write into the child is skipped entirely — not because model() is buggy, but because a binding that looks unchanged is never pushed. Meanwhile the child's own value is a writable signal with a mind of its own: inc() updates it directly, with no dependency on what the parent's slot thinks. The two numbers are free to disagree for as long as you keep clicking.

Naming the failure: a split-banana "no" from the parent does not undo the child's own write — it only stops the parent's copy from moving. Any child built on model() keeps a local copy that a rejected proposal cannot roll back, which is exactly why "the child asks, the parent decides" is only half the story.

Fixes, best first:

  1. Give the child nothing to disagree with you about. Swap model() for input() + output() inside the child (see the decision below) — a component with no writable field of its own has no state that could ever drift from the parent's.
  2. Force an actual rewrite. Route the rejection through a genuinely different value first, then the real one, on two separate passes, so the binding's own equality check sees two real changes instead of one silent no-op. Fragile, and rarely worth it next to option 1.
  3. Make the disagreement visible instead of silent. A quietly-reverted number is the wrong UI anyway — emit a validation state the child can render (a shake, a red border, a disabled button) rather than a write that appears to simply not have happened.

Choosing the right tool

model() isn't always the right call.

Fix number one above is a decision that applies far more often than just "the parent might say no". Angular gives you four shapes for a value that crosses a component boundary, and picking the wrong one is what produces bugs like the one you just watched.

Picking the right tool for a value the child needs
What you need Reach for
The child only ever displays the value input() — no output at all, nothing to propose
The parent owns the state; the child proposes changes it might reject input() + output() — the exact shape the clamp demo needed, with no local copy to desync
The child needs its own editable draft that resets whenever the input changes input() + linkedSignal() — see Advanced Signals
The value is genuinely shared and live on both sides, with no rejection to worry about model() — what every demo on this page has used so far

One API note while you're choosing: a model() input supports { alias }, the same as input(), but not a transform. If you need to coerce what comes in — numberAttribute, a custom mapper — that's one more argument for the input() + output() shape instead.

A common confusion

model() is not forms integration.

The two get mixed up because they solve adjacent problems with similar-looking syntax. They are not the same tool, and only one of them ever plugs into a <form>.

model() gives you exactly one thing: an input/output pair with a compiler-checked naming contract. It works on any standalone component and needs nothing imported to use.

It also knows nothing about forms. It cannot be driven by [(ngModel)], formControlName, a Validator, or read back dirty / touched / disabled state — none of that machinery exists for it.

ControlValueAccessor is the interface NgModel and FormControl actually talk to. Implementing it — writeValue, registerOnChange, registerOnTouched, optionally setDisabledState — is what makes your component usable as <my-input [(ngModel)]="x"> or [formControlName]="x".

In exchange, it inherits the whole forms machinery for free: validators, dirty/touched tracking, disablement.

Two-way binding for native controls

Native inputs don't have a valueChange — that's what ngModel is for.

A raw <input> has no valueChange output, so [(value)] on one does nothing useful. FormsModule supplies NgModel — exactly the ControlValueAccessor the last section named, already written for you and pre-wired to every native control type. [(ngModel)] desugars to [ngModel] + (ngModelChange), the identical rule as any other banana.

"Clear (from code)" calls text.set('') directly — no typing involved. In this browser tab it lands in the field before the next paint, so it looks instant.

The write-back is scheduled, not instant. A programmatic write like text.set('') changes the signal immediately, but the <input> element's own DOM value doesn't update until the next change-detection pass reaches this binding — the same scheduling story as the Change Detection lesson, just applied to a form control instead of a <p>. A running app gets that pass for free before the next frame paints. A component test does not: call fixture.detectChanges() (or await stability) before asserting on the input's DOM value, or the assertion reads the stale text and the test lies about passing.
Because these are signals, [(ngModel)]="text" binds directly to the text signal — Angular writes via .set(), no getter/setter boilerplate. ngModelOptions.updateOn accepts 'change' (default), 'blur', or 'submit' — the same knob reactive forms expose, useful when per-keystroke updates trigger expensive work.
Two errors everyone hits once. Forgetting to import FormsModule produces NG8002: Can't bind to 'ngModel' since it isn't a known property of 'input' — the directive simply isn't in the template's scope. An ngModel inside a <form> must carry a name attribute (it registers with the parent NgForm under that name), or use [ngModelOptions]="{ standalone: true }" to opt out of registration entirely.

The compiler's rule

What can sit on the left of [(x)]?

Angular writes back into your expression, so the target of [(x)]="expr" must be something you could legally put on the left of = — or a writable signal. The compiler checks it at build time, not at runtime:

What compiles, and why
Binding Verdict
[(value)]="count" (WritableSignal) Signal-aware — compiles to count.set($event).
[(value)]="user.name" (plain property) Plain assignment — compiles to user.name = $event.
[(value)]="count()" A call expression — nothing to assign to. Bind the signal, not its value.
[(value)]="user().name" Reading through a signal call — the write target isn't assignable. Copy to a local writable signal, or split the banana.
[(value)]="total" (computed) computed() is read-only — there's no .set() to call.
[(value)]="a || b" Arbitrary expressions aren't assignment targets.

Before model()

The decorator-era pattern — @Input + @Output.

You will read this in every pre-v17 codebase, and it clarifies why the naming contract exists — before model(), you built both halves by hand and kept them in sync yourself:

model() against the pattern it replaced
model() (modern) @Input + @Output (legacy)
Declaration one line, pair generated two members, names must align by hand
Child updates it value.set(v) — emits automatically set the field and remember to .emit(v)
Read in child value() — reactive, works inside computed() plain field — needs ngOnChanges to react to parent writes
Required + alias model.required(), { alias } @Input({ required: true }), alias kept in sync by hand on both sides
The suffix is exactly Change. model() enforces that at compile time. The legacy pattern only enforces it by convention — get the name wrong (valueChanged, onValueChange) and the banana just quietly stops working, with no error pointing at why.

Traps that show up in exams

Four more ways this bites in practice.

  • Mutation doesn't propagate. Two-way binding syncs assignments. Bind an object and mutate one of its properties, and no input fires and no event emits — the identical rule as every other binding in the app. Prefer immutable updates, or bind primitives.
  • (ngModelChange) is not (change). ngModelChange emits the parsed value on every model update; the native change event fires on the DOM's own schedule (text inputs: on blur) and hands you a raw Event, not a value.
  • Template-driven and reactive forms don't mix on one control. Putting [(ngModel)] on a control that already has a formControlName is an error — pick one system per control, even inside an otherwise-reactive form.
  • A missing name doesn't always fail the same way. An ngModel with no name attribute fails loudly inside a <form> (NgForm can't register it), but works fine standalone outside one — so the same typo can pass in a quick test and break the moment the field moves into a real form.

Questions from the back row

Before you go

Six things to remember.

  • [(x)] is sugar for [x] + (xChange) — the suffix is a hard compiler contract, not a naming convention you have to police yourself.
  • model() builds the pair for you and emits only on child-side writes — a parent's write updates the input silently, or every two-way binding would loop.
  • Bind the signal itself, never its call — count, not count(). The compiler enforces assignability at build time, before the app ever runs.
  • Splitting the banana lets a parent reject a value, but a rejected write can still desync a model()-based child — you watched it happen. Reach for input() + output() whenever the parent might say no.
  • model() is component-to-component only; it is not forms integration. Only a real ControlValueAccessor plugs into [(ngModel)] or formControlName.
  • [(ngModel)] adapts native controls through that same accessor. Remember FormsModule, a name inside a <form>, and that its DOM write is scheduled, not synchronous — the thing a test has to wait for.
