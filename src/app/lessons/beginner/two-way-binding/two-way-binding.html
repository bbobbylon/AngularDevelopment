Two-way binding keeps a value in sync in both directions: the view updates the data and the data updates the view. The syntax is the "banana in a box": [(x)] — brackets (property binding) inside parentheses (event binding). This page goes from the sugar down to the emission rules, interception patterns, and the traps — all one idea from different angles: two pipes, glued together.

The mental model

Two pipes, glued together — not a mirror.

The intuitive picture of two-way binding is a mirror: change either side and the other matches, symmetrically. That picture is wrong, and it's exactly wrong in the way that trips people up. A better one: [(x)] is two separate pipes, fused by syntax, not by behaviour — an inbound pipe ([x], parent → child) and an outbound pipe ((xChange), child → parent). Water only leaves the outbound pipe when the child pours something into it. The inbound pipe filling up — a parent's write — never spills over into the outbound one.

Hold onto that image. It explains why a parent's write is silent (it only ever uses the inbound pipe), and it is literally what "splitting the banana" means later in this lesson: you unglue the two pipes and put a valve on the outbound one.

[(x)] is two pipes glued together: [x] flows IN, (xChange) flows OUT. Fusing them with banana-in-a-box syntax doesn't turn them into one wire — water only leaves the outbound pipe when the child pours it in.

The mechanism

It is just sugar — the exact expansion.

The compiler rewrites [(x)]="expr" into a property binding plus an event binding whose name follows a strict contract: the output must be named xChange — the input's name with the literal suffix Change. There is no configuration for this; it is a naming convention baked into the compiler.

The suffix is exactly Change — capital C, no d, no on prefix. model() generates it automatically; if you ever hand-roll the legacy @Output() pair yourself, one typo here breaks the banana with no compiler error pointing at it.

The emission rule

What model() actually creates — and when it emits.

model() declares an input/output pair in one line: an input named value and an output named valueChange. The returned ModelSignal is writable from inside the child (.set() / .update()), and every child-side write emits on the output. The subtle rule most people get wrong: parent-side writes do NOT emit valueChange — the event only fires for changes that originate in the child. Two very different paths, side by side:

Clicking + / − inside the stepper logs a valueChange emission. "Set to 42 from parent" updates the input silently — no event, exactly the right-hand path above.

Because model() is just an input + output pair, all three usages are legal: full two-way [(value)]="x", one-way in [value]="x" (child changes stay local), or listen-only (valueChange)="onChange($event)".

Taking control

Splitting the banana: intercept, validate, clamp.

Because [(x)] is sugar, you can always unglue the two pipes and put logic between the child's emission and your state. This is the pattern for validation, clamping, confirmation dialogs, or dispatching to a store instead of assigning:

Live — parent clamps every write to 0…10

clamped = {{ clamped() }}

Try stepping past 10 or below 0 — the child asks, the parent decides. The child still works unmodified; the policy lives where the state lives.

Form controls

ngModel — two-way binding for form controls.

Native form elements have no valueChange output, so [(value)] on a raw <input> does nothing useful. FormsModule provides the NgModel directive, which adapts each control type (text, checkbox, select, radio) to the two-way contract via a ControlValueAccessor. [(ngModel)] desugars to [ngModel] + (ngModelChange) exactly like any other banana — same two pipes, a different provider on the inside.

Live — one directive, every control type

text = "{{ text() }}" ({{ text().length }} chars)

blurText = "{{ blurText() }}" — only updates on blur

framework = "{{ framework() }}"

agree = {{ agree() }}

Since these are signals, [(ngModel)]="text" binds directly to the text signal — Angular writes via .set(), no getter/setter boilerplate. The blur demo shows ngModelOptions: updateOn accepts 'change' (default), 'blur', or 'submit' — the same knob reactive forms expose, useful when per-keystroke updates trigger expensive work.
Two errors everyone hits once: (1) forgetting to import FormsModule produces NG8002: Can't bind to 'ngModel' since it isn't a known property of 'input' — the directive simply doesn't exist in the template's scope. (2) An ngModel inside a <form> tag must have a name attribute (it registers with the parent NgForm under that name), or use [ngModelOptions]="{ standalone: true }" to opt out of registration.

The compiler's rule

The assignability rule — what compiles, what doesn't.

Angular writes back into your expression, so the target of [(x)]="expr" must be something you could put on the left of = (or a writable signal). The compiler enforces it:

Binding Why
[(value)]="count" (WritableSignal) ✓ Signal-aware: compiles to count.set($event).
[(value)]="user.name" (plain property) ✓ Plain assignment: user.name = $event.
[(value)]="count()" ✗ A call expression — nothing to assign to. Bind the signal, not its value.
[(value)]="user().name" ✗ Reading through a signal call: the write target isn't assignable. Copy to a local writable signal or split the banana.
[(value)]="total" (computed) ✗ computed() is read-only — no .set() to call.
[(value)]="a || b" ✗ Arbitrary expressions aren't assignment targets.

Where this bites

Pitfalls that show up in exams and code review.

  • Mutation doesn't propagate. Two-way binding syncs assignments, not mutation. If you bind an object and mutate its properties, no input fires and no event emits — same rule as every other binding. Prefer immutable updates or bind primitives.
  • @for loop variables aren't assignable. [(ngModel)]="item" inside a loop fails — the loop variable is a snapshot, not a storage location. Bind to a property of the item ([(ngModel)]="item.name") instead.
  • The suffix is exactly Change. An output named valueChanged or onValueChange silently breaks the banana — the compiler finds no matching output for the desugared binding and nothing connects.
  • (ngModelChange) ≠ (change). ngModelChange emits the parsed value on every model update; the native change event fires per DOM rules (text inputs: on blur) and hands you a raw Event.
  • Template-driven vs reactive: [(ngModel)] is the entry point to template-driven forms. Mixing it onto a control that already has a formControlName is an error — pick one system per control.

Questions from the back row

Before you go

Recap — five things to remember.

  • Two pipes, glued together: [x] flows in, (xChange) flows out. The suffix is a hard compiler contract — always input-name + Change.
  • model() generates the pair; it emits on child writes only, never on parent writes — that asymmetry is what keeps the loop from closing.
  • Bind the signal itself, never its call — the target must be assignable.
  • Split the banana whenever a write needs interception (clamp, validate, dispatch).
  • [(ngModel)] adapts native controls via ControlValueAccessor; remember FormsModule, name-in-forms, and ngModelOptions.updateOn.
