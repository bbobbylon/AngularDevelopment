A component is more than one constructor call. Angular creates it, wires up its inputs, builds its view, checks it over and over as your app runs, and eventually throws it away — and at each of those moments you can ask to run your own code. That's a lifecycle hook: implement the matching method, name it exactly right, and Angular calls it for you. This page puts the whole sequence on screen, live, so you watch it happen instead of memorising a list.

A parent's ngAfterViewInit cannot fire until every child underneath it has already reported ready, which means the child's own ngAfterViewInit — step three above — has to happen before the parent's, step four. Creation runs outside-in because a parent has to exist before it can render a child; readiness runs inside-out because a parent's view is never "complete" while something inside it still isn't.

Construction runs outside-in — the frame goes up before there are rooms, and a room can't be built before the floor it sits on. Sign-off runs inside-out — each room gets inspected, then the floor, then the whole building, because a floor isn't finished while a room on it is unfinished. A component's lifecycle is both of those, running in the two opposite directions this page just drew.

The mechanism

A hook is just a method Angular calls by name.

There's no EventEmitter or observable hiding underneath a lifecycle hook. Angular's change-detection tree walk simply invokes instance.ngOnInit(), instance.ngDoCheck() and so on directly, in a fixed order, on every component that has a method by that exact name. Here's the actual child component the demo below is built on, read line by line — and, further down, the same handshake as a conversation instead of a picture.

That same tree walk is what explains the ordering from the analogy above. Angular checks components top-down — a parent creates and initialises its children while rendering its own template, which is why a child's ngOnInit always runs before its own ngAfterViewInit. But the "view ready" hooks fire bottom-up: a parent's view isn't complete until every child's view is, so children report in first.

No dispatcher, no subscription. The tree walk calls instance.ngOnInit() the same way it would call any other method on the object. Implementing OnInit only catches a typo at compile time — it's erased at runtime. Name the method ngOnInit and Angular calls it; the interface is optional. SimpleChanges comes from Angular's binding-diff machinery, which only tracks decorator @Input()s. A signal input() never appears in it. Fires on every change-detection pass reaching this component — a click on an unrelated button counts. That's what makes it expensive by nature.

The full order

Seven hooks, four moments.

The picture and the quiz at the top covered how a parent and child interleave. This is the other ordering fact — the one inside a single component, from birth to destruction.

CID, then Content, then View, then Destroy. Changes, Init, DoCheck — then the content pair, then the view pair, then destroy. Content always comes before View.

Reference: every hook, and when it fires
Hook When it runs
ngOnChanges Before init and whenever an @Input changes (gets a SimpleChanges).
ngOnInit Once, after the first ngOnChanges. Do your setup here.
ngDoCheck Every change-detection run. Use sparingly — it fires a lot.
ngAfterContentInit Once, after projected content (ng-content) is initialised.
ngAfterContentChecked After every check of projected content.
ngAfterViewInit Once, after the component's view & child views are ready.
ngAfterViewChecked After every check of the view & child views.
ngOnDestroy Just before Angular destroys the component. Clean up here.

The famous trap

Setting your own binding inside a view hook.

Avoid changing a bound property inside ngAfterViewInit/...Checked (or ngDoCheck) after a template has already read it this pass — that's exactly what triggers NG0100. Defer the write instead: a signal, or queueMicrotask.

The modern replacement

Increasingly, you don't reach for most of these.

Most of these hooks existed to work around the lack of reactivity. With signals, ngOnChanges usually becomes a computed, and ngOnInit is often just a field initialiser.

Two hooks remain genuinely necessary: ngOnDestroy for manual cleanup a signal can't do for you — a setInterval, a ResizeObserver, a third-party chart instance — and the afterNextRender / afterEveryRender family for work that needs the real browser DOM. Everything else here is worth recognising for exams and for reading pre-signals code, even where you'd no longer reach for it yourself.

Questions from the back row

Before you go

Five things to remember.

  • A hook is a plain method Angular calls for you — no event, no subscription. Name it exactly right (ngOnInit, not OnInit) and it fires.
  • Creation runs outside-in, "ready" runs inside-out. A parent's ngOnInit always beats its child's; a child's ngAfterViewInit always beats its parent's.
  • ngOnInit for setup, ngOnDestroy for cleanup — ngOnChanges reports decorator-@Input changes only, never a signal input().
  • ngDoCheck runs on every change-detection pass, app-wide. Put almost nothing in it.
  • Prefer signals & DestroyRef in new code where you can — but know all seven hooks anyway, because most existing Angular code and most interview questions still use them.
