Angular gives you several ways to drive an element's classes and inline styles from data — from single-toggle bindings to whole objects, plus the older ngClass / ngStyle directives. They all merge rather than replace, which is the one fact that explains almost everything on this page.

Bind the identical object to [class] and to [ngClass]. Re-render both 100 times with nothing about the classes ever changing. One of them does zero extra work after the first pass. The other does two hundred. 

[ngClass]="{{ '{' }} active: isOn() {{ '}' }}"
// own ngDoCheck(), own differ,
// runs on EVERY pass, unconditionally
[class]="{{ '{' }} active: isOn() {{ '}' }}"
// ONE compiled instruction
// skipped once the object reference repeats

The problem

An element already has a class. You bind another one in. What survives?

Here's the assumption almost everyone brings from plain JavaScript: setting el.className replaces whatever was there before. Angular's class and style bindings are not that. They look similar enough that the wrong mental model survives right up until it produces a bug nobody can explain in code review.

A <div> starts with a static class="card shadow". You add a [class] binding that turns on active whenever a signal called isActive() is true — and right now, it's true. Before you scroll any further: does the final class attribute still have card and shadow on it, or has the new binding wiped them out? There's a full walkthrough with the answer further down the page.

The mental model

Angular is a stack of transparencies on an overhead projector.

Picture the old classroom projector. The static class="box" is the bottom sheet, drawn once and never erased. Every binding you add lays another transparent sheet on top of it — [class] one sheet, [class.box--active] another. Nobody wipes anyone else's sheet clean — you see everything at once, stacked.

That single picture answers both of the questions people get wrong here. Why does class="box" survive a [class] binding that never mentions it? Because the binding is a different sheet. And when two sheets both draw box--active, which one do you see? The stack has a fixed order, and the per-class binding always sits on top.

Bindings layer — they never replace. Static class, then [class] maps, then [class.x] on top. If a class you didn't expect is still there, something below is still drawing it.

The mechanism

Every sheet is its own compiled instruction.

Your template doesn't run through some generic "apply the classes" function at runtime. Each binding source is compiled, ahead of time, into its own small instruction that the renderer calls on every check. That's the whole reason one binding can never clobber another's classes: there is no single className string being rebuilt from scratch every pass. There are several small instructions, each one responsible for its own sheet, and a differ patching only what actually moved.

The default tool

Toggling a single class or style.

[class.name]="bool" toggles one class. [style.prop]="val" sets one style — and you can append a unit, like [style.width.px] or [style.width.%]. This is what you reach for when you already know the class or property name at author time, which is most of the time:

Where this bites

That suffix is doing more work than it looks like it is.

Drop the unit suffix and nothing complains — which is precisely the problem. The binding still runs, the value still gets set, and the browser just quietly throws it away. 

<div [style.width]="8">

// setProperty('width', '8')
// → invalid CSS, dropped by the browser
<div [style.width.px]="8">

// setProperty('width', '8px')
// → 8 pixels wide

The data-driven tool

Binding many classes or styles at once.

Reach for the [class] / [style] map when the set of classes isn't known until runtime — a status that could be any of several values, for instance:

Bound classes merge with the static class attribute — they don't replace it. When two bindings target the same class/style, the more specific one wins (e.g. [class.box--active] beats a key inside [class]), and !important is honoured in style strings.

The legacy tool

NgClass & NgStyle: same jobs, an older engine.

The ngClass and ngStyle directives predate the bindings above. They still work and accept strings, arrays or objects — but for new code the native [class] / [style] bindings are usually clearer and faster.

The reference

Five syntaxes, and when to reach for each.

Syntax Binds Value Use for
[class.name]="expr" one class boolean the class name is known at author time — the default choice
[class]="expr" many classes object / array / string the set of classes is data-driven
[style.prop]="expr" one style property value already a complete string one property, e.g. a colour
[style.prop.unit]="expr" one style property bare number Angular never infers units — supply one here
[style]="expr" many style properties object several properties driven by one binding
ngClass / ngStyle same jobs as [class]/[style] object / array / string legacy code only — needs an import, runs a runtime differ

Where this bites

Pitfalls that show up in exams & code review.

  • Thinking [class] wipes the static class. It doesn't — bound and static classes merge. Same for [style].
  • Forgetting the unit suffix. [style.width]="8" sets an invalid width: 8; use [style.width.px]="8" or bind a full string like "8px".
  • Reaching for ngClass/ngStyle in new code. The native [class]/[style] bindings are faster and need no import.
  • Fighting specificity. When [class.active] and a key inside [class] target the same class, the specific binding wins — don't set the same class from two places.
  • camelCase vs kebab-case. In binding syntax use camelCase ([style.fontSize.px]); inside a bound object either spelling works, since the key there is just a string handed to setProperty.

Questions from the back row

Before you go

Four things to remember.

  • [class.x] / [style.x] toggle or set a single thing — reach for these first, they're the cheapest to update.
  • [class] / [style] accept objects/arrays/strings for many at once.
  • Style bindings support unit suffixes like .px and .% — a bare number with no suffix is silently invalid CSS, not an error.
  • Bound classes/styles merge with static ones, and collisions resolve by binding kind — the per-class form always beats a map. ngClass/ngStyle still work but are legacy.
