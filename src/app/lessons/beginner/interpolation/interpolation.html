Interpolation — the {{ '{{' }} … {{ '}}' }} syntax — is how a component's data becomes text on the page. Angular runs the expression inside, turns the result into a string, and keeps that string in sync every time it checks the view. That sounds like "just print this value", and mostly it is — but the exam (and your future self debugging a blank field) cares about three things underneath it: exactly which expressions are legal in there, how expensive a call inside it can quietly get, and what happens the moment the value is null or a whole object instead of a string.

The problem

You have a value in your class. How does it get onto the screen?

Say your component holds first = signal('Grace'). Somewhere in the HTML you want the actual text "Grace" to show up, and you want it to stay correct if first ever changes. Plain HTML has no way to do that — <p>first</p> would print the four letters f-i-r-s-t, not the value the signal holds. You need a piece of syntax that means "stop, this part isn't literal text — go read a value out of the component and put that here instead."

Before the next section names it: is that syntax a one-time stamp — Angular reads the value once when the page loads and writes it into the HTML — or does it stay live, somehow reading the value again later? Commit to an answer. Most people guess "stamp", because that is how printing a value normally works. The real answer is the more useful half of this whole lesson.

The mental model

Angular cut a peephole in the door between your template and your class.

Picture your component as a room, and the template as the hallway outside it. {{ '{{' }} first() {{ '}}' }} is a small round peephole drilled straight through the door. Put your eye to it and you see whatever is on the other side right now — not a photo taken once, an actual live look. Walk away and look again in five minutes and you see whatever is true then. Nobody has to fetch you a new photo; the hole was never showing a photo in the first place.

That one image explains both halves of this topic at once. It stays live because looking through a hole is not a photograph — there is nothing to go stale. And it only ever accepts an expression, never a statement — a look, never a reach — because a peephole physically cannot do anything but show you what's there. You cannot post a letter through it, flip a switch through it, or reassign a value through it. If you want to change something on the other side of the door, you need an entirely different mechanism — an event binding, two lessons from now.

A look, never a reach. {{ '{{' }} … {{ '}}' }} reads a fresh value on every check — that's the "look" — and only ever a single expression, never an assignment or a statement — that's why it can't "reach" back and change anything.

The mechanism

Every single check does the same three things, in order.

"Live" is not magic — it is Angular re-running a small, fixed routine every time it checks this view, whether or not anything actually changed. Zoom in on one {{ '{{' }} … {{ '}}' }} and this is the whole routine:

Angular re-runs the expression fresh, every reachable check — there is no "skip it, nothing changed" shortcut built into a plain {{ '{{' }} … {{ '}}' }} itself. Whatever comes out gets coerced to text. A number becomes digits, null/undefined become an empty string, and a plain object becomes [object Object] — more on that below. The new string is diffed against what was painted last time. The real DOM is untouched unless that string is actually different — which is what keeps "runs every check" from meaning "expensive every check".

That last point is also where the restriction from the peephole analogy earns its keep in practice. Because an expression can only read, Angular is free to re-run it as often as it likes without worrying that doing so might change something — a read has no side effects to worry about. A plain method call inside {{ '{{' }} … {{ '}}' }} re-runs on every reachable check, no matter how unrelated the trigger was. Put anything non-trivial behind computed() or a pure pipe instead — both cache until their real inputs actually change.

The boundary

Six things that look reasonable and none of them compile.

Back to the peephole: a look can never become a reach. Every line below tries to write, construct, mutate, chain, reach for something ambient, or sneak in an operator that doesn't mean what it means in plain JavaScript.

Keep interpolation expressions simple and fast. They run on every change-detection pass that reaches them, so avoid heavy work or anything with side effects — move that into the component class, a computed(), or a pure pipe.

Pitfalls

Six ways this bites people who already understand it.

  • Expensive method calls. They run on every reachable change-detection pass — prefer computed() or a pure pipe, proven live above.
  • Interpolating into a property attribute. value="{{ '{{' }} x {{ '}}' }}" always yields a string; use [value]="x" to keep the real type.
  • Objects silently print as [object Object]. Use | json while debugging, or interpolate a specific field instead of the whole thing.
  • Side effects. No assignments or increments in an expression — Angular may evaluate it many times per second, so it has to be pure.
  • | is always the pipe operator inside a template — never bitwise OR, even though it's legal JavaScript everywhere else.
  • A missing value doesn't look like anything. null/undefined render as an empty string, not an error — the self-test above is the whole reason this one makes the list.

Questions from the back row

Before you go

Five things to remember.

  • A look, never a reach. {{ '{{' }} … {{ '}}' }} re-reads a fresh value on every check — that's what keeps it live — and only ever accepts a single expression, never a statement — that's why it can't write anything back.
  • Three steps, every time. Evaluate, stringify, then write to the real DOM only if the string actually changed. The first two always happen; the third is what keeps "runs every check" cheap.
  • A method call is not free. It re-executes on every reachable change-detection pass, no matter how unrelated the trigger was — proven live in the run-counter demo. computed() and pure pipes memoize by tracking their real dependencies; a plain method cannot.
  • null, undefined and objects all stringify differently — nullish values quietly become '', and a plain object becomes [object Object]. Neither one throws, which is exactly why both are worth memorising.
  • It's for text, not properties. Bind DOM properties with [prop] to keep their real type; reach for interpolation only when text is genuinely what you want on the page.
