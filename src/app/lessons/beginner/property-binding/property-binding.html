Property binding — [property]="expr" — writes to a DOM object's live property, one-way, on every single check. It looks close enough to setting an HTML attribute that most people never learn the difference exists — until the day disabled="false" refuses to enable a button, or [colspan] silently does nothing where [attr.colspan] works. This page draws the line for real: what a DOM property actually is, when Angular reaches for a raw attribute instead, and the handful of places that difference bites you in an exam or a code review.

The problem

You wrote disabled="false". It's still disabled.

No Angular anywhere — plain HTML: <button disabled="false">Save</button>. Every instinct says that button should be enabled. It is not, and it never will be, no matter what you type between those quotes. HTML boolean attributes don't read their value at all — they only ask one question: is the attribute there? disabled="false" is there. So is disabled="". So is bare disabled. All three disable the button, because presence is the entire test.

That much is old news to most people by the time they meet Angular — a famous-enough gotcha that it stops being surprising. What's not old news, and what this page is really about, is that Angular's own binding syntax has a version of the exact same trap, and it's far easier to walk into by accident, because it looks like you fixed it.

Hold your answer to the button above, and add one more guess to it: does wrapping the value in Angular's own binding syntax — [attr.disabled]="isDisabled()", where isDisabled() is a real TypeScript boolean — behave any differently? Most people assume yes, because now it's "really" a boolean, not a string. Hold that guess. There's a live demo further down built to break it.

The mental model

The sticker on the box, the gauge on the dashboard.

An appliance ships with a spec sticker printed once, at the factory — "Rated 120V", stuck to the box. The same appliance also has a live gauge on its own control panel, showing what's actually happening right now. At the moment you unbox it, the two agree: someone read the sticker and set the gauge to match. From then on they lead separate lives. Turning the dial moves the gauge. The sticker doesn't know, can't know, and was never built to know — it is paper, not instrumentation.

An HTML attribute is the sticker: text sitting in your markup, parsed once when the element is created. A DOM property is the gauge: a live field on the actual JavaScript object the browser is using right now. Angular copies the sticker onto the gauge at creation — that's the one moment they're guaranteed to agree — and after that, property binding only ever touches the gauge.

Printed once, live always. The attribute is the label Angular read when it built the element; the property is what's actually true about it right now. Before you reach for either syntax, ask which one you're trying to change.

The mechanism

[prop]="expr" writes straight to the live object.

Property binding is one-way — class to view, never the reverse — and it runs on every check, not just at creation. Compare that with the "printed once" sticker: a property binding is the opposite of a sticker, by design.

The attribute side

Some things exist only as attributes.

A handful of things — ARIA, colspan, SVG attributes, your own custom data-* — have no matching camelCase DOM property Angular can write to by default. For those, drop into [attr.*] explicitly:

Aside: HTMLTableCellElement secretly does expose a camelCase property, colSpan — so [colSpan]="span()" would technically also work. It's taught as attribute-only because that's what exams expect and because the general rule — "no matching camelCase property → use [attr.*]" — genuinely holds for ARIA and most SVG attributes. Don't assume every lowercase attribute lacks a camelCase twin — check when in doubt.

The trap

Brackets don't turn a string back into a boolean.

Here's the twist the opening napkin promised. [attr.disabled]="false" looks fixed — it's a real binding, reading a real boolean, not a hardcoded string in the markup. It has exactly the same bug as disabled="false", for exactly the same reason: a bound boolean still gets stringified before it reaches the DOM. ɵɵattribute only calls removeAttribute for null or undefined — you saw that on the last line of the snippet above. Every other value, false very much included, becomes a present, non-empty attribute string, and presence is disability.

A custom element exposes no disabled property at all — only the attribute. You write [attr.disabled]="isDisabled()", where isDisabled() is a plain boolean, currently false. Enabled, or disabled? Commit to an answer — then press the toggle below and watch the middle button specifically.

Live — one signal, three different bindings

All three read the exact same disabled signal from the demo up in The mechanism. Toggle it a few times: A follows correctly, C follows correctly too — and B just sits there, permanently disabled, no matter what the signal says. That's not a bug in the demo. That's String(false).

[attr.*] compares presence, not truthiness. Only null or undefined triggers removeAttribute — every other value, false included, gets stringified and stays on the element.

Component inputs

The same brackets, aimed at your own component.

[prop]="expr" isn't limited to native DOM elements. On a component tag, the compiler checks the binding against that component's own declared inputs — at build time, not by guessing at runtime.

The error you'll see constantly

Can't bind to 'x' since it isn't a known property of 'y'.

This is, by a wide margin, the most common Angular compile error — and it is a property-binding error:

NG8002: Can't bind to 'count' since it isn't a known property of 'app-badge'.

Four causes produce it. In order of how often they're the actual reason:

The component (or RouterLink, FormsModule, your own child) isn't in this component's own imports array. Standalone components only see what they explicitly list. The name is typo'd, or it was never actually turned into an input with input() / @Input(). The compiler checks by exact name, not by convention. You're on a native element and the property genuinely doesn't exist — ariaLabel isn't a thing on a plain <span>. Switch to [attr.*]. A real Web Component (<my-widget>) Angular has never heard of. Add CUSTOM_ELEMENTS_SCHEMA to the component's schemas, or write a thin Angular wrapper.

Its sibling error, NG8001, is the same complaint about an element instead of a binding — 'app-avatr' is not a known element — usually a misspelled selector or a component missing from imports entirely. One rule tells them apart: NG8002 names a binding; NG8001 names a tag.

The security boundary

Not every property gets sanitized the same way.

Property binding is also a security boundary: Angular ships a built-in table of trust-sensitive tag+property pairs, and any binding that matches one is routed through the DomSanitizer before it ever reaches the DOM — not opt-in, and not something you can accidentally skip. What does vary is what "sanitize" means, because it depends on which of three contexts the value lands in:

the three sanitization contexts, and what each one does when it's unhappy
Context Example On an unsafe value
URL <img [src]>, <a [href]> Sanitizes silently — strips dangerous schemes like javascript:, keeps the rest.
HTML [innerHTML] Parses it as markup and strips anything unsafe — <script> tags, event-handler attributes — keeping the safe remainder.
RESOURCE_URL <iframe [src]>, <script [src]> Throws. A resource URL can load and run arbitrary code, so there's no safe stripped-down version to fall back to.
Concatenating untrusted strings into the DOM by hand — el.innerHTML = userComment — bypasses all three of these contexts entirely. Go through a binding; every full sanitization context, plus the bypass methods and when it's actually legitimate to reach for one, gets the deep treatment in Security.

The traps

Five more ways to get bitten.

every one of these compiles clean and fails quietly — nothing shows up in the console
The mistake What actually happens
Passing a number as a string size="48" binds the string '48'; [size]="48" binds the number.
Reaching for [attr.*] where a property already exists Costs you live-state behaviour for no reason. Reserve it for ARIA, colspan, SVG, data-*.
Hand-concatenating untrusted HTML or URLs Bypasses the sanitizer entirely — see The security boundary above. Always go through a binding.
Expecting null to blank a property On [attr.*] it removes the attribute; on a plain property it stores the literal null.
Assuming no lowercase attribute has a camelCase twin Some do — colspan/colSpan, readonly/readOnly, tabindex/tabIndex, maxlength/maxLength. [attr.*] is only strictly required when no DOM property exists at all.

Questions from the back row

Before you go

Six things to remember.

  • Property binding writes to the live object, one-way, on every check. Attribute binding writes to the markup's frozen string state — a different instruction, a different DOM call, a different null rule.
  • Booleans always stringify. [attr.disabled]="false" sets the attribute to the string "false" — present, so the button stays disabled. Only null/undefined triggers removeAttribute.
  • Reach for [attr.*] only when there's no DOM property — ARIA, colspan, SVG, data-*. Everywhere else, the property reflects live state and the attribute doesn't.
  • [x]="48" and x="48" are not the same value. Brackets make it a real expression — the number 48. No brackets makes it the string '48', which strict templates will catch on a typed input.
  • NG8002 means the binding, not the tag. Work the four causes in order: not imported, misspelled or undeclared, no such DOM property, or an unregistered custom element.
  • Sanitization is automatic and keyed to context — URL, HTML and RESOURCE_URL each behave differently, and you opt out of it explicitly or not at all.
