Property binding — [property]="expr" — sets a DOM property (or a component input) from a component value. It is one-way: data flows from the class into the view. The hard part isn't the syntax; it's that a property and its same-named attribute are two different things that only start out in sync.

The mental model

A shipping label vs. what's actually in the box.

The intuitive assumption is that an attribute and its same-named property are just two spellings of the same thing. They're not, and the label-and-box picture makes the difference concrete. An attribute is the label printed on a box at ship time — disabled="true" in your HTML source. It's fixed, readable from outside without opening anything, and it's exactly what "View Source" reads. A property is what's actually inside the box right now — the DOM node's live, in-memory state. Someone can open the box and swap the contents — click a button, type into a field — without ever reprinting the label.

Most of the time the label matches the contents, because the attribute is what initializes the property when the element is created. The moment the box is opened and repacked, though, the label stops being trustworthy — and reading the label instead of opening the box is precisely the mistake the DevTools predict above was built around.

Attribute = the label printed on the box at ship time. Property = what's actually inside it right now. Reading the label after the box has been opened and repacked tells you nothing about the current contents.

The default tool

Binding DOM properties.

[prop]="expr" writes straight onto the DOM node's live property — the box's contents, not the label. This is what you want almost every time you bind something:

[disabled]="false" genuinely clears the disabled state. The plain HTML attribute disabled="false" would NOT — attribute presence is all that matters there, and the string "false" is still present. Property binding sets the live property, which is what you almost always want.

The exception

When there's no box to open — attribute-only bindings.

A few things have a label with no corresponding box contents at all — no live DOM property backs them. ARIA, colspan, SVG-specific attributes, and custom data-* all fall here. For those, [attr.*] is the only correct tool:

The reference

Property vs attribute vs interpolation.

Syntax Sets Value type Use for
[prop]="x" live DOM property / component input the real type of x almost everything
[attr.name]="x" HTML attribute stringified; null removes it ARIA, colspan, SVG, data-*
prop="{{ '{{' }} x {{ '}}' }}" attribute → often reflected to property always a string plain text attributes only

Under the hood

Two different DOM calls, not two spellings of one call.

The template compiler (Ivy) turns every [prop]="expr" and [attr.name]="expr" into an update instruction baked into the component's generated update function — one reason Angular templates are fast: no runtime parsing of your markup, only pre-compiled function calls that run on each check. The two kinds of binding take genuinely different paths from expression to DOM:

  • Component inputs are resolved at compile time, not by string-matching at runtime. When the compiler sees [user] on <app-avatar>, it looks up AvatarComponent's input metadata and emits a binding that targets that exact input — which is also how the compiler catches a typo'd input name as a build error instead of a silent no-op.
  • Sanitization is keyed on the specific tag + property pair. Angular ships a built-in table of "trust-sensitive" combinations (<img [src]>, <a [href]>, [innerHTML] on any element, and more). A matching binding routes the value through DomSanitizer before it ever reaches setProperty — not opt-in, only deliberately bypassable with bypassSecurityTrust*.
  • Not every sanitization context fails the same way. <img [src]>/<a [href]> (URL context) and [innerHTML] (HTML context) both sanitize silently — a dangerous value is just stripped, no error, nothing on screen explaining why. [src] on an <iframe> or <script> is a third context — RESOURCE_URL — and there Angular throws instead of sanitizing, because there's no safe way to guess what a loaded document or script is allowed to do. The only way to supply a RESOURCE_URL value at all is DomSanitizer.bypassSecurityTrustResourceUrl(), and only once you've verified the value is genuinely trusted — the Security lesson covers this in full.
  • Aside — colspan secretly does have a camelCase property. HTMLTableCellElement exposes a real DOM property called colSpan that reflects the colspan attribute, so [colSpan]="span()" would technically also work. It's grouped with the attribute-only examples above because most learners (and most exams) expect [attr.colspan] — don't assume every lowercase attribute with no obvious property is attribute-only; when in doubt, [attr.*] is always safe.

The error you'll actually see

NG8002: the most common template error in Angular.

Every demo on this page assumes the binding target already exists. NG8002 — Can't bind to 'x' since it isn't a known property of 'y' — is what Angular tells you the moment it doesn't, and the message is worth memorizing because it always comes down to one of four causes:

Cause Fix
The component/directive that declares the input isn't in this component's imports array Add it to imports: [...]
The input name is misspelled, or was never declared with input()/@Input() Fix the spelling, or add the input on the target component
The DOM property genuinely doesn't exist on that element Use [attr.*] instead — see the section above
It's a native custom element Angular doesn't recognize Add CUSTOM_ELEMENTS_SCHEMA to the component's schemas
NG8002 vs. its sibling NG8001. NG8001 ('x' is not a known element) fires on the tag itself — a missing component import, a typo'd selector. NG8002 fires on a binding on an otherwise-recognized element. Exams like to pair the two: the same root cause, a missing import, produces one error code or the other depending on whether the problem is the tag or one of its bindings.

Where this bites

Pitfalls that show up in exams & code review.

  • disabled="false" still disables. Attribute presence is what counts — use [disabled]="false" to actually enable.
  • Passing a number as a string. size="48" binds '48'; [size]="48" binds the number.
  • Using [attr.*] where a property exists. Prefer the property; reach for [attr.*] only when there's no DOM property.
  • Binding untrusted HTML/URLs. Angular sanitizes [innerHTML]/[href]/[src]; hand-concatenating into the DOM bypasses that — don't.
  • Expecting null to blank a property. On [attr.*] it removes the attribute; on a property it sets the literal `null`.
  • Checking DevTools' HTML source instead of the live property. The value attribute in the markup typically stays frozen at whatever it was initially — inspect the property (DevTools' "Properties" tab, or el.value in the console) instead.
  • Assuming every lowercase attribute has no camelCase property counterpart. Some do (colspan/colSpan, readonly/readOnly, tabindex/tabIndex); [attr.*] is only strictly required when no DOM property exists at all.

Questions from the back row

Before you go

Recap — six things to remember.

  • Attribute = the label, property = the box's contents. The attribute initializes the property once; after that they can drift apart.
  • Prefer property binding — it reflects the live state, not just the initial markup.
  • Use [attr.name]="expr" only when there is no matching DOM property.
  • Binding null/undefined to [attr.*] removes the attribute entirely — a property binding just stores the literal null.
  • Component inputs are resolved at compile time — a typo'd input name is a build error, not a silent no-op.
  • Checking DevTools' markup for a live value is reading the label, not opening the box.
