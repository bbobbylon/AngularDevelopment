Property & Attribute Binding

Property binding — [property]="expr" — sets a DOM property (or a component input) from a component value. It is one-way: data flows from the class into the view.

Binding DOM properties

Live

Bound image source:

<button [disabled]="disabled()">Save</button>
<img [src]="url()" [alt]="caption()" />

Line-by-line

Code What it does & why
[disabled]="disabled()" Calls the disabled signal (invoking it with () reads its current boolean value) and writes that value straight onto the button element's live .disabled property — not the disabled attribute. Every time the signal changes, Angular re-runs this binding and assigns the new value via the renderer (conceptually el.disabled = value). Because it's a real property assignment, the button's interactive state flips instantly, with no attribute string parsing involved.
[src]="url()" src is one of a handful of properties Angular treats as security-sensitive. Before the value reaches the DOM, it is routed through the DomSanitizer's URL security context, which strips dangerous schemes like javascript:. This happens automatically for every [src] binding — you don't opt in, and you can't accidentally opt out except by using bypassSecurityTrustUrl explicitly.
[alt]="caption()" A second, independent property binding on the same element — proof you can stack as many [prop]="expr" bindings as an element has properties. alt is a plain string property with no sanitization pass, used here purely for accessible descriptive text.
[disabled]="false" actually removes the disabled state. With the plain HTML attribute disabled="false" the button would still be disabled, because attribute presence is what matters. Property binding sets the live DOM property, which is what you almost always want.

Property vs attribute

HTML attributes initialize the DOM; properties are the live state. Most things you bind are properties. But a few things (ARIA, colspan, SVG, custom data-*) exist only as attributes — for those use [attr.*]:

@if (span() === 1) { }
spans {{ span() }} column(s) second

aria-label set via [attr.*] 

<td [attr.colspan]="span()">...</td>
<span [attr.aria-label]="label()">...</span>

Line-by-line

Code What it does & why
[attr.colspan]="span()" The attr. prefix tells Angular to compile this as an attribute binding, not a property binding: it stringifies span() and calls setAttribute('colspan', String(span())) on the element. If span() ever evaluated to null/undefined, Angular would call removeAttribute('colspan') instead — the attribute disappears entirely, which is a behavior [prop] bindings don't have (a property bound to null just stores the literal null).
[attr.aria-label]="'rating ' + span() + ' of 5'" ARIA attributes have no DOM property equivalent at all — there is no element.ariaLabel you could bind with plain [prop] syntax (well — there actually is an experimental ariaLabel reflection in very new browsers, but it isn't reliable enough to depend on), so [attr.*] is the only correct tool here. The expression concatenates a live string every time span() changes, and the attribute is re-stringified on each change.

Binding to component inputs & shorthand

The same [prop] syntax passes values into a child component's inputs — the compiler checks the input exists and its type matches: 

<app-avatar [user]="currentUser()" [size]="48" />   // [size]="48" binds the number 48
<app-avatar size="48" />                            // without [], "48" is the string '48'
<img bind-src="url()" />                            // canonical form of [src]

Line-by-line

Code What it does & why
[user]="currentUser()" Because <app-avatar> is a component, not a native element, the compiler resolves [user] against AvatarComponent's own @Input()/ input() metadata at compile time (with strict templates on — the default in this app's tsconfig style). If there's no user input, or currentUser()'s type doesn't match the input's declared type, that's a build error, not a silent runtime no-op. At runtime the value is written straight onto the child's input (a signal set() for a signal input, or a plain field assignment for a decorator input).
[size]="48" Everything inside [ ]="…" is a real TypeScript expression, evaluated in the component's context — so 48 here is the number 48, not text. This is true for component inputs exactly the same way it's true for native DOM properties.
<app-avatar size="48" /> No brackets means this is a plain HTML attribute, so Angular passes the literal string '48'. If the size input is typed number, strict template type-checking flags this as an error at build time; without strict mode it silently becomes a string where a number was expected — a classic "why is my math broken" bug and a favorite exam trap.
bind-src="url()" The canonical, non-bracket spelling of property binding — bind-src="expr" is 100% equivalent to [src]="expr". It exists for template environments where square brackets in markup are awkward (some server-side templating pipelines, very old tooling); you'll almost never see it in real Angular code, but an exam question can absolutely ask you to recognize it.
Property binding is also a security boundary: Angular sanitizes values bound to risky properties like [innerHTML], [href] and [src], stripping javascript: URLs and scripts. Concatenating untrusted strings into the DOM yourself bypasses that — don't.

Under the hood

The template compiler (Ivy) turns every [prop]="expr" and [attr.name]="expr" into an update instruction baked into the component's generated update function — one of the reasons Angular templates are fast: there's no runtime parsing of your markup, only pre-compiled function calls that run each check. 

{{ underTheHoodSample }}
  • Property bindings call setProperty, not setAttribute. [disabled]="disabled()" compiles to roughly ɵɵproperty('disabled', ctx.disabled()), which — after a strict-equality check against the previous value avoids redundant work — hands off to the Renderer2, which does the equivalent of el.disabled = value directly on the DOM node object. The disabled HTML attribute in the markup is never touched.
  • Attribute bindings call setAttribute / removeAttribute. [attr.colspan]="span()" compiles to roughly ɵɵattribute('colspan', ctx.span()), which stringifies the value and calls setAttribute — or removeAttribute when the value is null/undefined. This is the exact mechanism behind "binding null to [attr.*] removes the attribute."
  • Component inputs are resolved at compile time, not by string-matching at runtime. When the compiler sees [user] on <app-avatar>, it looks up AvatarComponent's input metadata (collected from its @Input() decorators or input() calls) and emits a binding that targets that exact input — which is also how the compiler can catch a typo'd input name as a build error instead of a silent no-op.
  • Sanitization is keyed on the specific tag + property pair. Angular ships a built-in table of "trust-sensitive" combinations (<img [src]>, <a [href]>, [innerHTML] on any element, [style] in some cases, and more). When a binding matches one of those, the compiled instruction routes the value through DomSanitizer for that SecurityContext (URL, HTML, RESOURCE_URL, …) before it ever reaches setProperty. This is not opt-in — you can't accidentally skip it, only deliberately bypass it with bypassSecurityTrust*, which you should treat as "I personally vouch this string is safe."
  • Aside — colspan secretly does have a camelCase property. HTMLTableCellElement exposes a real DOM property called colSpan (capital S) that reflects the colspan attribute, so [colSpan]="span()" would technically also work. It's grouped with the "attribute-only" examples above because most learners are taught (and exams often expect) [attr.colspan], and because the general rule — "no matching camelCase DOM property → use [attr.*]" — is genuinely true for ARIA and most SVG attributes. The lesson: don't assume every lowercase-attribute-with-no-obvious-property case is attribute-only; when in doubt, [attr.*] is always safe, and a real property binding is only wrong if the property doesn't exist.

Pitfalls that show up in exams & code review

  • disabled="false" still disables. Attribute presence is what counts — use [disabled]="false" to actually enable.
  • Passing a number as a string. size="48" binds '48'; [size]="48" binds the number.
  • Using [attr.*] where a property exists. Prefer the property; reach for [attr.*] only when there's no DOM property.
  • Binding untrusted HTML/URLs. Angular sanitizes [innerHTML]/[href]/[src]; hand-concatenating into the DOM bypasses that — don't.
  • Expecting null to blank a property. On [attr.*] it removes the attribute; on a property it sets the literal null.
  • Checking DevTools' HTML source instead of the live property. [value]="url()" updates the input's live .value property, but the value attribute in the markup (what "View Source" / outerHTML shows) typically stays frozen at whatever it was initially — that's expected, not a bug. Inspect the property (DevTools' "Properties" tab, or el.value in the console), not the attribute, when you're debugging a property binding.
  • Assuming every lowercase attribute has no camelCase property counterpart. Some do (colspan/colSpan, readonly/readOnly, tabindex/tabIndex, maxlength/maxLength); [attr.*] is only strictly required when no DOM property exists at all — true for ARIA and most SVG-specific attributes.

Exam corner

Why does disabled="false" still disable the button?
It's an attribute — presence alone disables. Bind the property: [disabled]="false" sets the live DOM property to false.
When do you need [attr.*] instead of [prop]?
When there's no matching DOM property — ARIA (aria-*), colspan, SVG attributes, custom data-*.
[size]="48" vs size="48" on a component input?
The first passes the number 48; the second passes the string '48' (no brackets = literal attribute string).
You bind [value]="url()", but the browser DevTools "Elements" panel still shows the old attribute value. Is the binding broken?
No — this is expected. [value] writes to the live DOM property, and the value attribute in markup generally does not auto-update to reflect it. Check the actual property (DevTools "Properties" tab, or inputEl.value in the console) instead of the HTML source.
Does [colSpan]="n" (camelCase, no attr.) work on a <td>?
Yes — HTMLTableCellElement has a real colSpan DOM property that reflects the colspan attribute, so a plain property binding works. It's still common (and usually clearer) to write [attr.colspan], but exams sometimes test whether you know the camelCase property secretly exists.

Key takeaways

  • [prop]="expr" sets a DOM property or component input, one-way.
  • Prefer property binding; it reflects the live state, not just the initial markup.
  • Use [attr.name]="expr" when there is no matching DOM property.
  • Binding null/undefined to [attr.*] removes the attribute.
  • Under the hood, property bindings compile to a setProperty-style instruction and attribute bindings to a setAttribute/removeAttribute one — different instructions, which is why their null handling differs.
  • Sanitization on [src]/[href]/[innerHTML] is automatic and keyed on the specific tag + property; it isn't something you opt into.
