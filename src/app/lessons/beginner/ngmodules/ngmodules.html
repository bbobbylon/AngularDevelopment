You've never once written an @NgModule in this app — every lesson before this one has been standalone. But for roughly eight years, from Angular 2 to the version most production codebases were still shipping in 2023, @NgModule was the only way to wire an Angular app together, and it's still what you'll read on the certification exam, in most existing jobs, and in every tutorial published before 2023. This page is a translation guide: what an NgModule actually does, the two entirely separate jobs it was quietly doing at once, and exactly how each piece maps onto the standalone code you already know.

The problem

Nothing in this app has an @NgModule. Something still had to do its job.

Here's a rule that has never once changed, standalone or not: a template cannot use a component, directive or pipe that hasn't been registered somewhere. Angular's compiler checks every element and attribute against a known list before it will let your app build at all. Today, a standalone component builds that list itself — its own imports array on @Component. Before 2023, a component couldn't do that. Something else had to register it on the component's behalf.

That something was the NgModule. And once you see it as a registration mechanism rather than a mysterious wrapper, the two questions worth actually answering fall out on their own:

  • What exactly counts as "registered", and who gets to decide? (declarations, exports, imports)
  • Registering a template is one thing — is that the same system that hands a component its services?
Every component, directive and pipe has to be registered somewhere before a template can use it — always true, standalone or not. If a component genuinely isn't registered anywhere, what do you think Angular does with a template that tries to use it: render it as a plain unrecognised tag, silently skip it, or refuse to build the app at all?

The mental model

An NgModule is a box with two separate doors.

Picture every NgModule as a sealed box. Whatever a module declares lives inside that box, and it lives there permanently — exactly one box may declare any given class. From outside, the box is opaque by default: nothing else in the app can see in.

Two separate doors change that, and a component only crosses from one box to another if both are open. The box that owns the component has to open an exports door outward — "you may use this." And the box that wants to borrow it has to open an imports door inward — "give me what you're offering." Open only one, and nothing moves. Nothing errors either — the component simply stays invisible, which is exactly what makes the bug so hard to spot later.

Declare once. Export to share. Import to borrow. Every NgModule question about "why can't I see this component" is really a question about which of those three steps got skipped.

Scaling up

Big apps split into feature modules. Three roles show up in almost every one.

Feature modules are lazy-loaded by the router, so their code downloads only when a user actually visits them. forChild, not forRoot, is the tell that you're reading a feature module rather than the root.

Once an app has more than a couple of feature modules, three roles appear on their own, whether or not anyone planned them:

Bootstraps the whole app — the only module with a bootstrap bucket — and imports BrowserModule. Standalone's bootstrapApplication replaces both jobs at once. Declares and exports reusable components, pipes and directives so every feature module can import it. Never put a singleton service here — five lazy-loaded importers means five instances. Services and one-off things (a nav bar) meant to exist exactly once, imported only by AppModule. Protected by a runtime guard, since nothing else stops a second import.

That guard is worth reading in full, because the two decorators in it show up nowhere else in this curriculum and answer a real exam question on their own.

providedIn: 'root' on the individual services makes this entire guard unnecessary — which is exactly why you'll only ever meet it in code written before that became the default recommendation.

Under the hood

An NgModule was quietly doing two people's jobs.

The compiler and the injector are separate systems inside Angular, checking separate things, and an @NgModule file was the one place that fed both of them at once — which is exactly why it felt like one mechanism instead of two.

The compiler half you've basically already lived: every "is not a known element" you've fixed by importing something IS this system, whether the class doing the importing was a module or a standalone component. Angular's compiler resolves each component's compilation scope — the set of directives, components and pipes its template is allowed to reference — from the owning module's declarations plus whatever its imports re-expose, entirely before the app runs. That's why an undeclared or unexported component fails at compile time rather than at runtime: the compiler already knows exactly what's visible where, before a single pixel is painted.

It's the injector half that hides a genuine surprise. An eagerly imported NgModule doesn't get an injector of its own at all — its providers flatten straight into the same root injector as everything else, so there's no surprise there. A lazy-loaded feature module is the exception: because the router instantiates it separately, after the app is already running, it gets its own environment injector, entirely separate from the compilation-scope question above.

Starting up, and mixing both worlds

Two bootstraps, one running app.

// main.ts
platformBrowserDynamic().bootstrapModule(AppModule);

Boots the whole app from one NgModule. AppModule pulls in BrowserModule, which is where DOM support actually comes from — importing it a second time from anywhere else throws at startup. 

// main.ts
bootstrapApplication(App, {{ '{' }}
  providers: [provideRouter(routes), provideHttpClient()],
{{ '}' }});

One function, one component, and a flat providers array instead of a chain of modules. BrowserModule's job now happens automatically — the browser platform is simply what bootstrapApplication targets.

They interoperate, and it goes both ways: pull an old module's providers into a standalone app with importProvidersFrom(SomeModule), and drop a standalone component or directive straight into an NgModule's imports array. The one direction that never works is a standalone component in declarations — you'll see exactly why in the quiz below.

Common mistakes

Five ways an NgModule app breaks quietly.

what it looks like, and the fix
Mistake What actually happens
Declaring a component in two modules Type X is part of the declarations of 2 modules. Each declarable belongs to one module — export it and import that module instead.
Using a component but forgetting to export it Importers can't see non-exported declarables. Add it to exports.
*ngIf / pipes fail in a feature module You forgot to import CommonModule — only BrowserModule in the root re-exports it.
forRoot() called in a feature module Use forChild() instead. Every duplicate call adds a fresh providers array — see the quiz above.
Providing a service in SharedModule Every lazy module that imports it gets its own instance — accidental duplicates. Prefer providedIn: 'root'.

Three more, specifically the ones written to catch you on an exam:

  • declarations may only contain components, directives, and pipes — services and other modules never go there (services go in providers, modules go in imports).
  • BrowserModule may only be imported by the root module — importing it a second time from a feature module throws at startup. Feature modules that need *ngIf/pipes import CommonModule instead.
  • A component declared in an NgModule can't be dropped straight into a standalone component's imports array — only standalone components, directives, pipes, or whole NgModules belong there.

Questions from the back row

Before you go

Six things to remember.

  • An NgModule was always doing two separate jobs at once — deciding what a template may use (compile-time) and deciding who provides a service (DI, at runtime). Standalone components split those apart: imports on @Component replaces the first, providedIn replaces the second.
  • Declare once, export to share, import to borrow. A class belongs to exactly one module; being usable elsewhere always needs both a door out and a door in — miss either and the class is invisible there, with no error to point at the gap.
  • Since Angular 19, standalone is the default — a plain @Component() cannot go in declarations at all. Old-tutorial code needs standalone: false added by hand before it compiles.
  • forRoot()/forChild() are just static methods that return a providers array (or don't). Nothing stops you calling forRoot() twice except discipline — which is exactly why the CoreModule guard exists, and exactly what providedIn: 'root' makes unnecessary.
  • A lazy-loaded module gets its own injector, so a provider registered there — not at the root — is duplicated once per lazy chunk that imports it.
  • The two worlds interoperate: importProvidersFrom() pulls an old module's providers into a standalone app, and a standalone component can be dropped into an NgModule's imports — never its declarations.
