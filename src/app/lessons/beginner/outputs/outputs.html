An output is how a child tells its parent that something happened, without ever reaching into the parent to make anything happen itself. The modern output() function creates a typed emitter; the parent listens with event-binding syntax, (outputName)="handler($event)". Everything below is really one idea told a few different ways: a child announces, and the parent decides.

The problem

Something happened inside the child. Now what?

A star got clicked inside a <app-rating> component, three levels deep in your page. The parent needs to know. But the child has no reference to the parent, no idea what the parent will do about it, and — if it is any good as a reusable component — no business knowing either. So how does the message get out?

The tempting wrong answer is to just hand the child a way to reach back in — a callback function, a shared object, a reference to the parent itself. That works, once. It also means the child can now only be used inside a parent shaped exactly like the one you wrote it for. Outputs exist to solve this without paying that price.

The rating child further down this page needs to tell its parent "someone picked 4 stars." Would you rather it called a method the parent handed it directly, or just announced what happened and let the parent decide what happens next? Which one still works if you drop that same child onto a screen its author has never seen?

The mental model

An output is a doorbell, not a door.

The child can ring it — "someone picked four stars" — but it cannot walk in and rearrange the furniture. What happens next is entirely the parent's decision, and the child neither knows nor cares. That is what makes the child reusable in a screen it was never designed for: it has no opinion about the consequences of its own events.

Data flows down through inputs. Events flow up through outputs. Nothing ever goes the other way.

The payoff

Inputs and outputs are two halves of one contract.

output() is emit-only by construction — no .subscribe(), nothing can push a value in from outside. The one-way contract is enforced by the type, not just by convention.

Name outputs for the event (saved, rate), not onSave, and avoid native event names like click/change — they collide with real DOM events on the host element.

Self-test

Can you say what [(value)] really is?

$event in an output binding is the emitted value (here a RateEvent), not a DOM event. That single fact is also how two-way [(banana-in-a-box)] binding works under the hood: an input x plus an output xChange — which is exactly what model() generates.

Traps

The five ways this trips people up.

  • Thinking $event is a DOM event. In an output binding it's the emitted value (your payload type), not a browser event.
  • Naming outputs onX. Name them for the event (rate, saved); the on prefix belongs on the parent's handler, not the output.
  • Shadowing native events. An output named click or change collides with the real DOM event of the same name on the host.
  • Treating output() like a Subject. It has no .subscribe() and can't be fed from outside — it's emit-only by design. Use an RxJS Subject + outputFromObservable if you need a stream source.
  • Manual unsubscribe. Output bindings are torn down with the component — no cleanup needed (unlike a hand-rolled EventEmitter.subscribe()).

Questions from the back row

Before you go

Four things to remember.

  • output<T>() creates a typed event emitter on a child.
  • Emit with .emit(value); the parent listens with (name)="handler($event)".
  • The child never reaches into the parent, and can't — it only ever announces, it never decides.
  • Decorator form still works: @Output() x = new EventEmitter<T>(). Prefer output() in new code — it's emit-only, which keeps the contract one-directional by construction.
