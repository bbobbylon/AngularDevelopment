Component Outputs

Outputs let a child notify its parent that something happened. The modern output() function creates a typed emitter; the parent listens with event-binding syntax (outputName)="handler($event)".

The mental model: an output is a doorbell, not a door. The child can ring it — "someone picked four stars" — but it cannot walk in and rearrange the furniture. What happens next is entirely the parent's decision, and the child neither knows nor cares. That is what makes the child reusable in a screen it was never designed for: it has no opinion about the consequences of its own events.

Data flows down through inputs. Events flow up through outputs. Nothing ever goes the other way.

Declaring & emitting

export class Rating {{ '{' }}
  rate = output<RateEvent>();      // typed output
  select(stars: number) {{ '{' }}
    this.rate.emit({{ '{' }} stars, at: new Date() {{ '}' }});  // push a value up
  {{ '}' }}
{{ '}' }}

Notice what the demo above does not do: the child never reaches into the parent. It emits, the parent changes its own state, and the new value comes back down as an input. The whole cycle only ever moves one way:

$event in an output binding is the emitted value (here a RateEvent), not a DOM event. Outputs are how [(two-way)] binding works under the hood: an input x plus an output xChange — which is exactly what model() generates.

Outputs from an Observable

import {{ '{' }} outputFromObservable {{ '}' }} from '@angular/core/rxjs-interop';
// expose a stream as an output:
saved = outputFromObservable(this.savedSubject$);
Subscriptions to outputs are cleaned up automatically when the component is destroyed — no manual unsubscribe. Name outputs for the event (saved, rate), not onSave, and avoid native event names like click/change to prevent confusion with DOM events.

The classic @Output / EventEmitter

The decorator equivalent you will meet in exams and older code:

@Output() rate = new EventEmitter<RateEvent>();
this.rate.emit(payload);

output() is preferred: it's not a full Subject (no .subscribe on the instance, no values pushed in from outside), which keeps the contract one-directional and clear.

Pitfalls that show up in exams & code review

  • Thinking $event is a DOM event. In an output binding it's the emitted value (your payload type), not a browser event.
  • Naming outputs onX. Name them for the event (rate, saved); the on prefix belongs on the parent's handler, not the output.
  • Shadowing native events. Avoid output names like click/ change — they collide with real DOM events on the host.
  • Treating output() like a Subject. It has no .subscribe() and can't be fed from outside — it's emit-only by design. Use an RxJS Subject + outputFromObservable if you need a stream source.
  • Manual unsubscribe. Output bindings are torn down with the component — no cleanup needed (unlike a hand-rolled EventEmitter.subscribe()).

Exam corner

What is $event in (rate)="onRate($event)"?
The value passed to rate.emit(...) — here a RateEvent. Output $event is the payload, not a DOM event.
How does two-way [(x)] binding relate to outputs?
It desugars to an input x plus an output xChange. model() generates exactly that pair.
output() vs @Output() EventEmitter?
Same wiring for parents. output() is preferred — it's emit-only (no external subscribe/next), keeping the child→parent contract one-directional.

Key takeaways

  • output<T>() creates a typed event emitter on a child.
  • Emit with .emit(value); the parent listens with (name).
  • The handler receives the emitted value as $event.
  • Decorator form: @Output() x = new EventEmitter<T>().
