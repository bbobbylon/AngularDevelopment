The Angular Router maps URLs to components, so a single-page app can have a dozen "pages" without a single server round trip. You define a route table, mark where components render with <router-outlet>, and link with routerLink. Almost every bug in this lesson comes from one rule: the router reads that table top to bottom and stops at the first entry that fits.

The problem

One index.html. A dozen different screens. How?

Here is the part that's easy to skip past: /about is not a file on a server anywhere. This is a single-page app — there is exactly one HTML document, downloaded once, and nothing about a URL changing tells the browser to swap in new content on its own. Something has to notice the address changed, decide what that address means, and put the right component on screen. That something is the Angular Router.

Once you accept that routing is a deliberate decision Angular makes rather than something the browser does for you, three questions fall out on their own, and this lesson answers them in order: how do you describe the mapping from URL to component, how does the router decide which mapping wins when more than one could apply, and what does clicking a link actually set in motion?

Two links, side by side, both saying "About" and both pointing at /about. One is <a routerLink="/about">; the other is a plain <a href="/about"> someone typed by mistake. Both take you to the same place when clicked. Are they doing the same thing to get there? There's a comparison and a quiz further down to check your answer against.

The mental model

The router is a line of desks, and it stops at the first one that fits you.

Picture a row of desks at passport control, each with a sign overhead. You don't compare every sign and pick the best match — you walk down the line and stop at the first desk whose sign fits you. The router works the exact same way: it reads the route table top to bottom and stops at the first entry that matches the URL, even if a better match was sitting two rows down.

Two consequences follow immediately, and between them they explain most routing bugs you'll ever hit. Put a desk labelled "anyone" (**) near the front and nobody ever reaches the specific desks behind it. A sign that matches more loosely than you intended quietly claims traffic meant for something further down the line.

First match wins. Specific routes go above general ones, and ** goes last. If a route "never fires", something above it in the table matched first.

The setup step every snippet above skipped

router-outlet and routerLink don't exist until you import them.

Every snippet above prints <router-outlet /> and <a routerLink="/about"> as if they just work. On a standalone component, they don't — RouterOutlet, RouterLink and RouterLinkActive are directives like any other, and the component using them has to list each one in its own imports array. Miss one and you get two completely different failures, depending on which:

NG8001: 'router-outlet' is not a known element — a build-time error. Angular has never seen the tag before, because no imported directive claims it.

No error at all. routerLink="/about" with no matching import is just an unrecognised HTML attribute as far as Angular is concerned — the anchor renders, looks completely normal, and clicking it does nothing but a useless self-navigation. Nothing in the console says why.

RouterModule is the older, all-in-one alternative — importing it pulls in RouterOutlet, RouterLink and RouterLinkActive together, which is why older NgModule-based apps never hit this trap by accident.

Under the hood

What "matching" actually compares.

The router splits both the URL and each route's path into segments on /, then compares them left to right. A literal segment must equal the URL's exactly; a :param segment matches any single segment and captures its value; ** matches everything left over. That's the whole algorithm — the dialogue above and the live table below are both running it.

By default, matching is prefix matching: path: 'users' matches /users, /users/7, and deeper — because the route only has to match the start of the URL. That's usually exactly what you want for a parent route with children, and it's the single biggest trap for a redirect.

The trap that only shows up after you deploy

Refresh on /about in production, and the server 404s.

Every route on this page works perfectly under ng serve — and that's part of the trap. By default the router uses PathLocationStrategy, which relies on the browser's History API: /about is a real URL that whatever answers your requests has to know how to serve. ng serve fakes this for you with a built-in fallback; a plain static host (an S3 bucket, a bare nginx config) does not — it looks for a file called about, finds nothing, and returns a genuine 404, even though the exact same link worked a moment ago by clicking through the app instead of refreshing.

Fix How Trade-off
Rewrite unknown paths to index.html on the server nginx: one try_files $uri /index.html; line (Netlify/Firebase have their own equivalent config file) None — the URL stays real, so this is usually the right default
provideRouter(routes, withHashLocation()) Every route grows a #: /about becomes /#/about, and the browser never sends anything after the # to the server, so there is nothing left for it to 404 on Worse SEO and analytics — hash URLs are a special case for a lot of tooling

Worth pinning to the board

Five traps, each one a one-line fix.

Without it, {{ '{' }} path: '', redirectTo: 'home' {{ '}' }} redirects every URL, because they all start with the empty prefix. A ** or a greedy prefix placed early wins before more specific routes below it ever get a chance. Use routerLink for in-app navigation. A plain href re-downloads and re-boots everything. routerLinkActive matches by prefix too — add [routerLinkActiveOptions]="{{ '{' }} exact: true {{ '}' }}" to the / link only. routerLink="/users" is absolute; routerLink="users" is relative to the current route. Mixing them up navigates somewhere surprising.

Questions from the back row

Before you go

Five things to remember.

  • A route table is scanned top to bottom, and the first match wins — even if a better one was further down. Specific routes go above general ones; ** goes last.
  • Matching defaults to prefix, not exact. An empty-path redirect without pathMatch: 'full' claims every URL in the app; a link's routerLinkActive without {{ '{' }} exact: true {{ '}' }} lights up on every page for the same reason.
  • routerLink navigates client-side and keeps your app's state intact. A plain href to an in-app route reloads everything — a full document navigation, not a shortcut.
  • A leading slash is absolute; no leading slash is relative to the current route. From code, that's the difference relativeTo controls.
  • Prefer loadComponent over component for anything beyond a landing page — it's the easiest way to keep the initial bundle small, and this whole app is built that way.
