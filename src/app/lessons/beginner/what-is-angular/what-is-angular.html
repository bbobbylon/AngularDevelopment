If you've never touched a frontend framework before, welcome — you're exactly who this page is for. The one idea to carry out of it: a framework is a machine that keeps the screen in sync with your data. You describe what the UI should look like for a given state, you change the state, and Angular works out the DOM edits and applies them — you almost never touch the DOM yourself. Everything below exists to make that sentence feel obvious rather than just true: why it needs to exist at all, what a component actually is, and the handful of ways beginners trip over it in the first week.

The problem

You changed a value. The browser did nothing.

Here's the thing nobody says out loud on day one: assigning a value in JavaScript does nothing to a web page. Write total = 42 and you've updated one slot in memory — full stop. The browser isn't watching that slot. Nothing calls you back. If you want the number on screen to change, you have to go and change it yourself, by name, every single place it appears:

The mental model

Angular calls you. You don't call Angular.

A library (jQuery, or React on its own) is code you call: you stay in charge of the app's structure, and you reach for the library's functions when you need them. A framework like Angular is code that calls you — it owns bootstrapping, rendering and dependency injection, and it runs your components at the moments it decides. This is sometimes called the Hollywood Principle: don't call us, we'll call you.

State → template → DOM, and Angular owns everything to the right of the first arrow. Change the state; never reach for the DOM yourself. If you catch yourself writing document.querySelector inside a component, you're fighting the framework rather than using it.

The practical payoff of handing over that control is that Angular is batteries-included: routing, forms, HTTP and testing tooling are all official, versioned together, and built to fit one another. You trade some up-front learning for far fewer glue decisions later.

Under the hood

How does any of this even start?

Every Angular app starts from one call that mounts the root component and installs app-wide features:

From there, a page renders in five predictable steps:

  1. main.ts bootstraps the root component with the app-wide providers.
  2. The router reads the URL and picks the matching component, lazy-loading its code if needed.
  3. Angular instantiates that component, running its constructor and injecting whatever it asks for.
  4. The template renders, reading signals and inputs to produce the initial DOM.
  5. When a signal the template read changes, that view is marked dirty and Angular re-renders only the affected DOM on the next pass — the mechanism behind the notify trap above.
Mental model: state → template → DOM, and Angular owns the last arrow. Your job is to keep the state correct; keeping the pixels correct is the framework's job.

Pulling it together

What actually makes Angular, Angular.

  • TypeScript-first — even templates are type-checked, so a typo in a binding is a compile error, not a blank screen.
  • Opinionated & complete — one official answer for routing, forms and HTTP means less bikeshedding.
  • Dependency injection — a hierarchical DI system wires your services together for you.
  • Signals — fine-grained reactivity that enables precise updates and zoneless apps.
  • Tooling — the CLI, Language Service, DevTools and schematics come as one package.
  • Rendering options — client-side, server-side (SSR) and hydration are all built in.

Angular ships a major version roughly every six months, each with about 18 months of support and automated ng update migrations, so upgrades are routine rather than rewrites. It's maintained by Google and used across many of its own products — and because routing, forms, HTTP and testing are all official, an Angular codebase from one team looks a lot like the next, which matters on large or long-lived projects.

Questions from the back row

Before you go

Six things to remember.

  • A framework calls you, not the other way round — the Hollywood Principle. Hand Angular a component; it decides when to construct it, render it, and check it again.
  • A component is three files pretending to be one thing: a class holds behaviour and state, a template says what to paint, a stylesheet says how it looks — and @Component staples them together.
  • State drives the DOM, never the other way round. Change a signal; Angular finds every place that reads it and repaints only those. You should never see document.querySelector inside a component.
  • Nothing renders until something notifies Angular. A plain field can change in memory and sit invisible on screen for as long as nothing tells Angular to look — that's not a bug, that's the mechanism, and Change Detection is where the full story lives.
  • Replace, don't mutate: items.update(list => [...list, x]) notifies; items().push(x) changes the data and tells nobody.
  • Standalone is the modern default. A snippet starting with @NgModule is the legacy style — the ideas map across, but write it the standalone way shown here.
