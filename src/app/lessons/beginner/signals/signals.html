A signal is a value that announces when it changes. Anything that reads it — a template, a computed, an effect — re-runs on its own when the value moves. Three functions is the whole API, and you can learn them in ten minutes. The other twenty minutes on this page are the part that stops signals surprising you: when the work actually happens, what counts as a change, and the five ways to make one look broken.

The problem

You changed the number. Nobody told the screen.

Assigning a value in JavaScript is a completely silent act. count = 5 writes one slot in memory and that is the end of it. No event fires. Nothing in the language will call you back. The old number is still painted on the screen, the total that was calculated from it is still wrong, and not one line of code has any idea. 

{{ plainVsSignalSample }}

That is the entire problem signals exist to solve. A plain variable is a silent box. A signal is a box that keeps a list of everyone who has ever read it and tells them the moment its contents change. Everything else on this page — computed, effect, zoneless change detection — is built on that one behaviour.

Before you scroll: who does the telling? Most people guess that Angular quietly watches the field and notices. It does not — there is no hook in JavaScript that fires when you read or write obj.count, so watching is not on the menu. Hold your guess. The real answer is stranger and better, and it explains every signals bug you are ever going to write.

The mental model

Angular handed you a spreadsheet.

You already know this system. Type 5 into cell A1. In B1 type = A1 * 2. Change A1 to 7 and B1 becomes 14 — and you never told it to. You did not write an update function, subscribe to A1, or remember to refresh anything. The sheet knows that B1 read A1, because reading it is how the formula was written.

that last sentence is the whole trick — reading is subscribing

Signals are that spreadsheet, in your component. And the analogy keeps paying out past the introduction, because a spreadsheet has a second habit worth stealing: it does not recalculate a cell nobody is looking at. Scroll a formula off screen, change its inputs a hundred times, and the sheet does the arithmetic exactly once — when you scroll back. Signals do the same thing, and Laziness & caching below is where that stops being trivia and starts being the answer to “why did my computed run four times?”

Holds a value you can write to. A1 = 5. It is the only one of the three you are allowed to set. Holds a value derived from other cells. B1 = A1 * 2. Read-only, cached, and it recalculates itself. Holds no value at all. It does something — logs, saves, redraws a chart — whenever a cell it watched changes.
Hold, derive, do. signal holds a value, computed derives one, and effect does something with them. If you catch yourself deriving inside an effect, you have reached for the wrong one of the three.

Laziness & caching

A formula nobody reads never runs.

Here is where most people's mental model is quietly wrong. They picture a write pushing new values outward through the graph: change count, and doubled recalculates, and then the template updates. Reasonable, and backwards. Signals pull. A write does almost nothing; the read does the work.

The demo below has one computed with a run counter wired into its body. Nothing on screen reads it until you press “read it once”. Commit to a number now: if you press “change the source” five times and then read it once — how many times will the body have run? And if you read it a second time straight after, without touching the source?

Read again without changing anything and the count does not move — that is the cache answering. Lazy means the body waits to be asked; memoised means it refuses to answer twice.

Side effects

Effects are for doing, not for deriving.

An effect runs whenever any signal it read changes — once immediately when it is created, then again on each change. It returns nothing, and that is the point: it exists for the work that has no return value. Writing to localStorage. Logging. Handing a value to a charting library that knows nothing about Angular. Anything where the doing is the result.

Two things on that snippet are worth carrying away on their own. Cleanup: whatever your effect opens, onCleanup is where you close it, and it fires before the next run as well as on destroy — so an effect that opens a socket per user never has two open at once. And ownership: an effect created outside an injection context has nothing to be destroyed with, so Angular refuses to create it rather than letting you leak one per click.

Live — an effect logging every change to the counter

    2. }

Press + and − at the top and entries appear here. Notice the first line arrived without anyone pressing anything — an effect always runs once on creation, which is a difference from computed worth committing to memory.

Under the hood

Pull, not push.

A signal is not magic and it is not big. It is an object holding a value, a version counter, and a set of consumers — the computeds, effects and template bindings that have read it. The step almost everyone skips when picturing this is the third one.

  • Reading tracks; writing bumps a version. Calling count() inside a reactive context — a computed body, an effect, or template evaluation — registers that context as a consumer. Calling set or update increments the signal's version and marks every registered consumer dirty. It does not run a single one of them.
  • "Dirty" means "maybe stale", not "wrong". When something finally reads a dirty computed, it compares the versions of everything it read last time. All unchanged? Hand back the cached value without running the body at all. This is why a signal set back to the value it already had costs nothing downstream.
  • Equality stops the ripple. After a computed re-runs, its new result is compared with its old one. Equal by Object.is — or by your own equal function — and its consumers are never notified. A change can travel one hop and die.
  • A template binding is a consumer like any other. Which is exactly how OnPush and zoneless change detection work: a signal write marks only the components that read it, so Angular can update a leaf without walking the tree — and an app whose state is all signals no longer needs Zone.js at all.

The guarantee

You never see a half-updated value.

Reactive systems have a famous failure mode called a glitch: for one instant, two values that are supposed to agree do not, because the update reached one of them first. It happens whenever a source reaches the same reader by two paths of different lengths — and that shape is far more common than it sounds.

You get this for free and will probably never think about it — which is the point. It is also the strongest argument for the rule back in Derivation: derive with a computed and the guarantee holds; derive by hand inside an effect and you have built the glitch back in yourself, because your copy updates one tick after the thing it copies.

The traps

Five ways to make a signal look broken.

Every one of these produces code that runs without error and screens that do not update. That combination is what makes them worth memorising — there is nothing in the console to search for.

Live — mutate against replace, on the same signal

    @for (item of items(); track $index) {
  • {{ item }}
    • }

Press mutate three times: nothing appears. Press replace once and all four new entries arrive together — the ghosts were in the array the whole time. Press mutate again and then the no-op button, which changes no state at all, and the missing item shows up anyway. The writes were never lost. They were never announced, and something unrelated happened to cause a render later.

A signal compares with Object.is. For an object or an array that means same reference, no news — so replace, never mutate. update(list => [...list, x]), not list().push(x).

You do not need any of these today. They are listed here so that when you meet the names you already know which hole each one fills — every one of them is a variation on something on this page.

API The hole it fills
linkedSignal(fn) A computed you are also allowed to write to — a formula cell you can type over, which goes back to being a formula the next time its source changes. The classic use is a selection that should reset when the list behind it reloads.

Questions from the back row

Before you go

Five things to remember.

  • Reading is subscribing. count() is a call, and the call is what registers you as a consumer. That is why the parentheses are not optional and why there is no dependency list to keep in sync.
  • Hold, derive, do. signal holds a value, computed derives one and stays pure, effect does the impure work. Deriving inside an effect builds a second source of truth that is always one tick behind.
  • Writes mark; reads run. A set() bumps a version and flags consumers — nothing else. A computed nobody reads may never run again, and a read that finds every version unchanged returns the cache without running anything.
  • Same reference, no news. Equality is Object.is unless you supply equal, so mutating an array or object inside a signal notifies nobody. Replace it.
  • Effects are scheduled and owned. They run once on creation, batch multiple writes into one run, clean up through onCleanup before every re-run, and must be created where Angular can tie them to a lifetime.
