@let declares a local variable inside a template. Use it to name a computed value once and reuse it — keeping templates DRY and readable without adding fields to the component class. It's reactive, read-only, and lexically scoped, with one performance nuance most people miss.

The problem

Repeat the expression, or name it once?

{{ '{{' }} price() * qty() {{ '}}' }} works fine once. Write the same expression in three places on the same template — a subtotal line, a tax line, a total line — and you've committed to updating all three together forever. Worse: pipe the same observable, user$ | async, into three bindings and you don't just repeat text — you create three separate subscriptions.

@let total = price() * qty(); sits in a template. You click a button that changes something completely unrelated elsewhere on the page — nothing to do with price or qty. Before you scroll: does that total line's multiplication actually re-run anyway?

The mental model

A sticky note, not a locked box.

Picture @let as a sticky note you stick on a value mid-recipe — "this is subtotal now" — so you can point at the note instead of redoing the arithmetic every time you mention it later in the same recipe. A computed() is a locked box in the pantry instead: it only gets refilled when specific ingredients change, and anyone in the kitchen can open it without asking.

The nuance the whole lesson turns on: a sticky note gets rewritten from scratch every single time the recipe card is read, whether or not the ingredients actually changed. Cheap to write, never smart about it.

A name, not a cache. @let saves you from repeating an expression. It does not save you from recomputing it every reachable change-detection pass — that's computed()'s job, not this one's.

The basic shape

Declare once, reuse everywhere.

Live

@let subtotal = price() * qty(); @let tax = subtotal * 0.2; @let total = subtotal + tax;
Subtotal {{ subtotal | currency }}
Tax (20%) {{ tax | currency }}
Total {{ total | currency }}

Edit price or qty above: all three @let lines re-run on the very next change-detection pass because they read the price()/qty() signals — that's the live template above, not a screenshot.

Each @let may reference earlier ones (chaining, as above), template reference variables, and pipes. Its value updates reactively whenever a dependency changes.

The classic misconception

@let is not memoized.

A @let is re-evaluated on every change-detection pass, like any template expression — it is not cached the way computed() is. For cheap arithmetic that's fine. For anything expensive (sorting, filtering a big list, formatting thousands of rows), compute it in the class with computed(), which only recomputes when its signal dependencies actually change:

The one nobody warns you about

Re-running an expression is fine. Re-allocating one isn't.

Cheap arithmetic re-running every pass is harmless — that's the whole memoization nuance above. But @let re-runs the entire expression, and an object or array literal is an expression too. Build one inside a @let and hand it to a child's input, and you're not just repeating work — you're handing that child a brand-new object, by reference, on every single change-detection pass, whether anything inside it actually changed or not.

@let is a name, not a cache — and never a place to allocate. Hoist any object or array a child needs to a readonly class field (stable forever) or a computed() (stable until its real dependencies change) instead. If all a @let needs to carry is a primitive — a string, a number, a boolean — there's nothing to allocate and nothing to fix; the trap is specifically about objects and arrays.

The rules

Scoped like a block. No hoisting.

  • Read-only. You can't assign to a @let from an event handler — it's derived, not state. Put mutable state in a signal.
  • No forward references. A @let is usable in its own scope and nested scopes, but not earlier in the template. Using it above its declaration is a compile error.
  • Scoped like a block. Declared inside @if/@for, it's visible only within that block (and deeper). 
@if (user(); as u) {{ '{' }}
  @let greeting = 'Hi ' + u.name;
{{ '}' }}
<p>{{ '{{' }} greeting {{ '}}' }}</p>
<!-- ERROR: greeting is out of scope here -->

<p>{{ '{{' }} label {{ '}}' }}</p>
<!-- ERROR: used before its declaration below -->
@let label = 'later';
@if (user(); as u) {{ '{' }}
  @let greeting = 'Hi ' + u.name;
  <p>{{ '{{' }} greeting {{ '}}' }}</p>
  <!-- valid: still inside the block -->
{{ '}' }}

@let label = 'later';
<p>{{ '{{' }} label {{ '}}' }}</p>
<!-- valid: declared above this read -->

Myths worth unlearning

Six claims about @let, and why each is false.

  • "@let is memoized like computed(), so it's fine in a hot loop." False. It re-evaluates on every change-detection pass that touches it — no caching, no dependency tracking. Expensive work belongs in a computed() class field, not a @let.
  • "You can update a @let from a click handler." False — it's derived and read-only, with no setter. (click)="total = total + 1" on a @let name is a compile error, not a silent no-op.
  • "Once declared, a @let is visible for the rest of the file, like a JS var." False — there's no hoisting. It's scoped to the block it's declared in (and nested blocks below it); reading it earlier or outside that block is a compile error, not undefined.
  • "@let needs curly braces, like @if {{ '{' }} {{ '}' }}." False — @let name = expr; is one statement ending in a semicolon. It has no block body of its own, unlike @if/@for/@switch.
  • "Binding the same expression in three places always means three evaluations." Only if you repeat the raw expression. A @let computes it once per reachable pass and every binding that reads the name just reuses that stored value — the whole reason it fixes the multi-subscription async pipe problem.
  • "@let supports reassignment further down, like JS let." False — there is no name = newValue; syntax in a template at all. Each @let is a single declaration plus initializer, which is exactly why it's suited to derived values rather than mutable state.

Questions from the back row

Before you go

Things to remember.

  • @let name = expr; creates a reusable, reactive, read-only template variable.
  • It re-runs every change detection — not memoized; use computed() for expensive work.
  • Lexically scoped: usable at and below its declaration, never before it — enforced at compile time, with no hoisting.
  • It lives in a slot on the current view, not on the component class — inside @for/@if every embedded view gets its own independent copy.
  • Ideal for unwrapping an async value once and for per-row values in @for.
