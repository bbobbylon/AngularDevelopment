The built-in @if block picks which version of your UI is real right now — and, this page's actual subject, throws the losing version away completely. It replaced the old *ngIf directive and needs no import: it's compiled straight into your component, not resolved by a directive at runtime. You'll leave knowing exactly what @if compiles to, when its condition reruns, why ; as is a compiler requirement rather than a style choice, and what happens to a viewChild() sitting inside a branch that just disappeared.

The problem

A template can only be one truth at a time.

Write a component with a logged-in view and a logged-out view and you've written two different UIs for the same patch of the page. A live DOM, though, can only ever hold one of them at once — so something has to decide which one exists right now, and something has to deal with whichever one just lost.

  • Which branch wins? (the condition)
  • What happens to the branch that loses? (creation and destruction)
  • What if the losing branch was holding onto something — a half-typed answer, a scroll position, a subscription?
Type a sentence into a text box. Make the box disappear. Bring it back. Is your sentence still sitting there, or is the box starting from nothing? Most people guess it survives — text boxes usually do, everywhere else in software. There's a live version of exactly this a few sections down; hold your guess until you get there.

The mental model

@if evicts. [hidden] just draws the blinds.

Picture two ways a landlord can deal with a room. One way: change the locks, clear it out, hand back the keys — the tenant is gone, and whoever moves in next starts from an empty room with no memory of who lived there before. The other way: just close the blinds. The tenant is still inside, their furniture is exactly where they left it, and opening the blinds again reveals the room precisely as it was.

@if is the first landlord. [hidden] — and display: none — is the second. Neither is wrong; they solve different problems, and picking between them out of habit rather than by which one you actually need is exactly where a live demo, a few sections from now, will catch you out.

Eviction, not a blackout. A false @if branch doesn't dim the lights — it tears the whole room out: DOM, component instances, their signals, scroll position, focus, all of it. Reach for [hidden] when the tenant needs to stay.

The syntax

Three blocks, one winner.

Here's the whole shape: an @if, as many @else ifs as you need, and one optional @else at the end. Angular checks them top to bottom and stops at the first match — there's no fall-through, and no bare @else standing on its own.

Live

@if (user(); as u) {

✅ Welcome back, {{ u.name }}.

@if (u.role === 'admin') {

You have admin privileges.

} @else {

Standard member access.

} } @else {

👋 Please log in to continue.

}

Nesting works exactly like this: the inner block checking u.role only exists at all once the outer block is already showing — Angular never even builds it while u is null.

The ; as alias

; as isn't a nicety. It's the only thing that compiles.

The pitch you'll usually hear for ; as is convenience — reuse the value, skip repeating user(). That's true, and it undersells it. Under strictTemplates — this app's own default, and most real ones — the version without it doesn't just look worse. It doesn't compile.

Under the hood

One @if compiles to two functions and a switch.

Your template isn't interpreted at runtime. It's compiled, ahead of time, into ordinary functions — one per branch, plus a single instruction in the parent that decides which branch, if any, is currently active.

The nodes and bindings for exactly one branch. Building or throwing away one of these, as a whole, is the entirety of what @if does — nothing in between. Registers a branch's template function under a slot number. Runs once per branch, ever — it does not create anything by itself, it just makes the branch available to be created later. Runs on every Update pass. Picks a slot number; a changed slot destroys the old view and creates the new one. This one call is the whole of @if / @else.
"@if is slow" is almost always about what's inside the branch, not the check itself. Picking a slot is one comparison. What costs real time is whatever the winning branch's own update pass does — and that runs every time a pass reaches it, same as any other binding.

Scheduling

The condition doesn't run once. It reruns every pass that reaches it.

The line above is the part most explanations skip. A condition isn't asked once when the branch first appears — it's asked again on every single change-detection pass that reaches this view, exactly like an interpolation or a property binding would be. What decides whether that pass happens at all is a completely separate question, and it's the one that catches people.

Press the first button and the left panel flips immediately — reading readySignal() inside the condition registered this view as a consumer, so .set() marks it and schedules the very pass that reruns the condition. Press "flip the plain field, silently" as many times as you like: the right panel does not move, because nothing about a plain assignment inside a setTimeout marks anything or schedules anything. Now press the no-op button — which changes no state at all — and the right panel catches up in one jump. The write was never lost. It was never announced, and something unrelated finally caused the pass that reads it.

One more cost

Don't let the condition do real work.

"Reruns on every reachable pass" has a sharper edge than it first looks: whatever expression sits inside @if (…) reruns too, in full, every single time — including any allocation it performs, whether or not the branch is about to flip.

The eviction, made concrete

Losing a branch means losing everything inside it.

@if compiles to an embedded view that is created when the condition turns truthy and destroyed when it turns falsy. Destroyed means gone: the DOM nodes, any component instances inside them, their signals, and any scroll/focus/typed-text state all reset the next time the block reappears — because there is no "next time" for any of that, only a fresh start. Type into both boxes, hide, then show again.

Live — @if vs [hidden]

{{ showBoxes() ? 'visible' : 'hidden' }}

@if — element removed

@if (showBoxes()) { }
text lost, and a brand-new child was built

[hidden] — element kept

text survives, and it's the same child throughout

Watch the "instance #" number in the left panel: it climbs every single time you show the boxes, because a fresh ToggleChild is constructed and fetches all over again. The right panel's number never moves after the first render — [hidden] never destroyed it, so there was never anything to rebuild or refetch.

The decision rule: cheap, frequent, and must keep state (a panel you flip constantly, a form mid-edit) → [hidden]. Expensive and rare (a modal, a whole route-level page) → @if. Expensive and frequent → keep the actual data outside the branch entirely — a service-level signal, a cached resource — so throwing the view away is cheap even though the view itself really is destroyed.

One more consequence

Even your reference to it disappears.

The eviction two sections back takes more than the DOM with it. Anything you asked Angular to remember about that DOM — a viewChild(), the older @ViewChild decorator — goes with it too, and that's what catches people who assume a query just... has the answer, permanently, once.

Live — a viewChild() pointed inside an @if

@if (showRefBox()) { }

{{ refCheck() }}

Type something, press "check the ref" — found. Close the box, press it again — undefined, because the branch destroyed it. Open the box back up and type something new: the log below reacts on its own the instant the query actually has an answer, without you pressing anything.

    @for (line of refAppearances(); track $index) {
  1. {{ line }}
    2. } @empty {
  2. — nothing yet —
    3. }
The signal viewChild() handles this on its own — it's simply undefined until there's an answer. The older decorator form, @ViewChild('refBox', { static: true }), isn't just unnecessary here — it's invalid. static: true promises Angular the target exists before the very first check, which nothing inside an @if, @for or @defer can ever promise. Coming from *ngIf

*ngIf still works. Here's what @if replaced.

*ngIf is the old structural directive; @if is template syntax that replaces it. The most-missed detail in a migration is the then/else template-ref pattern — @if folds those extra <ng-template>s into inline branches.

Questions from the back row

Before you go

Five things to remember.

  • @if evicts; it doesn't hide. A false branch's DOM, component instances and their state are destroyed, not paused — reopening it builds something new from scratch.
  • The condition reruns every pass that reaches it, exactly like any other binding. A signal read inside it registers this view as a consumer, so a .set() schedules the pass that catches it; a plain field only catches up whenever something else causes one.
  • ; as isn't a nicety. TypeScript can't narrow through a function call, so reading the same call a second time inside the block fails to compile under strict templates — capture the result once and narrow that instead.
  • A ref inside @if disappears with the branch. viewChild() is undefined while the branch is false, and for a beat right after it flips true — read it from an effect(), not ngOnInit.
  • It replaced *ngIf with an inline @else (no <ng-template>, no reference to keep in sync), no import, and narrowing the compiler can actually rely on.
