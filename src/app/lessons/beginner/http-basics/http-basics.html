HttpClient Basics

HttpClient is Angular's typed wrapper over the browser's fetch/XHR. It returns RxJS Observables, integrates with interceptors, and gives you typed responses.

The mental model: a recipe card, not a meal

Here is the thing that trips up everyone arriving from fetch. When you call http.get('/api/posts'), no request is sent. What you get back is a recipe card: a written-down description of a request that could be made. It sits there doing nothing until somebody actually cooks it — and in Angular, cooking is subscribe().

Two consequences fall straight out of the picture, and between them they cover most beginner HTTP bugs. Nothing happens if you never subscribe — no request, no error, no clue. And if you hand the same recipe card to three different people, you get three meals, because a recipe is not a leftover. Three subscriptions means three network requests.

get() hands you a recipe, not a result. Subscribing is cooking, and every subscriber cooks their own.

1. Provide it once

// app.config.ts
providers: [provideHttpClient(withFetch())]

2. Inject & request

private http = inject(HttpClient);

load() {
  this.http.get<Post[]>('https://jsonplaceholder.typicode.com/posts')
    .subscribe(posts => this.posts.set(posts));
}

http.get() is lazy: nothing happens until you subscribe() (or use the async pipe / toSignal). Each subscription fires a new request.

So it is worth knowing exactly which of the things you might write actually count as subscribing:

What you write Request sent? Cleans up after itself?
http.get(url) alone No n/a — nothing started
.pipe(map(…), catchError(…)) No — pipe only builds a longer recipe n/a
.subscribe(fn) Yes No — add takeUntilDestroyed()
data$ | async in a template Yes, once per async in the template Yes, on destroy
toSignal(http.get(url)) Yes Yes, on destroy
await firstValueFrom(…) Yes Yes, on the first value

Handling errors

this.http.get<Post[]>(url).pipe(
  catchError(err => { console.error(err); return of([]); })
).subscribe(...)

The error is an HttpErrorResponse with status, message and the parsed error body — branch on err.status to handle 401/404/500 differently.

Bridging to signals & cancellation

// turn the Observable into a signal (auto-subscribes & cleans up):
posts = toSignal(this.http.get<Post[]>(url), { initialValue: [] });

// switchMap cancels the previous request when a new one starts (typeahead):
results$ = this.query$.pipe(switchMap(q => this.http.get(`/search?q=${q}`)));

Because requests are Observables, unsubscribing cancels the in-flight HTTP call (with withFetch(), via AbortController) — no wasted responses. The async pipe and toSignal unsubscribe for you.

Under the hood

Cooking the recipe is six steps, and it is worth holding them in order — nearly every HTTP topic you meet later is a modification to exactly one of them:

  • The request isn't built until subscribe() runs. http.get() returns a cold Observable whose subscribe callback is what actually constructs the HttpRequest and dispatches it — subscribing twice creates two independent requests that flow through the pipeline separately.
  • Interceptors form a linked chain of handlers. Each provided interceptor wraps the next HttpHandler; calling next.handle(req) passes control down the chain to the final backend, then the response bubbles back up through the same interceptors in reverse — so one interceptor can transform both the outgoing request and the incoming response.
  • Requests are immutable — interceptors clone to change them. You can't mutate a request's headers/body in place, so an auth interceptor calls req.clone({{ '{' }} setHeaders: {{ '{' }} … {{ '}' }} {{ '}' }}) to attach a token, producing a new request object for the next handler.
  • The body is parsed based on responseType. The default is 'json' (the raw body is run through JSON.parse); asking for {{ '{' }} responseType: 'text' {{ '}' }} or 'blob' skips that parsing entirely — mismatching this against what the server actually sends is a common source of parse errors.
  • Unsubscribing tears down the network call itself. With withFetch() the teardown logic calls AbortController.abort(); with XHR it calls xhr.abort() — this is why switchMap genuinely cancels the previous request instead of just ignoring its response.

Pitfalls that show up in exams & code review

  • Forgetting to subscribe. http.get() is a cold Observable — no request fires until subscribe(), the async pipe, or toSignal.
  • Subscribing multiple times. Each subscription is a new HTTP call. Share with toSignal/async or shareReplay.
  • Manual subscriptions that leak. A hand-rolled .subscribe() should be cleaned up (takeUntilDestroyed()); async/toSignal do it for you.
  • Swallowing errors. catchError that returns a value hides failures — branch on err.status and surface real problems.
  • Not typing the response. get<Post[]>() gives you compile-time safety; get() returns Object.

Key takeaways

  • Provide once with provideHttpClient(); inject HttpClient.
  • Methods return cold Observables — subscribe (or async pipe) to trigger them.
  • Type the response with the generic: get<Post[]>().
  • Handle failures with the RxJS catchError operator.
