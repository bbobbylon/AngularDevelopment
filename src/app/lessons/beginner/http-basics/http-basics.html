HttpClient is Angular's typed wrapper over the browser's fetch/XHR. Every method on it returns an RxJS Observable, and almost every beginner HTTP bug traces back to one fact about that Observable: it does nothing at all until something asks it to.

The problem

You called http.get(). The Network tab stayed empty.

Here's the thing that trips up everyone arriving from fetch: this.http.get('/api/posts') returns something immediately, and yet nothing goes out over the network. No request, no error, no clue that anything happened at all — the line just quietly returns a value and moves on.

That value is not a promise of data on its way. It is a cold Observable: a description of a request that could be made, sitting inert until something specifically asks it to run. Three questions fall out of that one fact, and between them they cover almost every HTTP bug a beginner hits:

  • What actually has to happen before a request is sent at all?
  • What happens if two different places in the app ask for the same thing?
  • What happens to a request that outlives its usefulness — cancelled, or its component destroyed?
Component A calls this.http.get('/api/posts') and stores the result somewhere shared. Component B, elsewhere entirely, reads that same value and calls .subscribe() on it too, just to be safe. How many network requests fire? There's a concrete version of this question — with a real answer — a little further down.

The mental model

Think of http.get() as a recipe card, not a meal.

A recipe card is a written-down description of a meal that could be made. It sits there doing nothing until somebody actually cooks it — and in Angular, cooking is subscribe(). Two consequences fall straight out of that picture. Nothing happens if you never subscribe: no request, no error, no meal. And if you hand the same recipe card to three different cooks, you get three meals, because a recipe is not a leftover — three subscriptions means three network requests.

get() hands you a recipe, not a result. Subscribing is cooking, and every subscriber cooks their own — three subscriptions to the same call is three separate meals, not one shared plate.

The mechanism

Cooking the recipe is six steps, in a fixed order.

It's worth holding these steps in order, because nearly every HTTP topic you meet later — interceptors, auth headers, retries, cancellation — is a change to exactly one of them.

The request object isn't built until subscribe() runs. Subscribe twice and you get two independent requests, flowing through the pipeline separately. You can't mutate a request's headers or body in place. Worth knowing exactly

Not everything that looks like a request is one.

So it's worth knowing exactly which of the things you might write actually count as subscribing:

What you write, and whether it actually sends anything
What you write Request sent? Cleans up after itself?
http.get(url) alone No n/a — nothing started
.pipe(map(…), catchError(…)) No — pipe only builds a longer recipe n/a
.subscribe(fn) Yes No — add takeUntilDestroyed()
data$ | async in a template Yes, once per async in the template Yes, on destroy

The other four verbs

Five verbs, one shape.

Every one of these is exactly as lazy as get() — nothing fires until something subscribes. HttpClient CRUD takes request bodies, params and headers apart in full; this is just the shape.

Handling failure

A failed request is not a thrown exception.

A rejected HTTP call doesn't throw in the way a synchronous error would — it arrives as an HttpErrorResponse down the error channel of the Observable, and RxJS's catchError is how you intercept it before it reaches — or skips — your subscribe.

A question worth asking

Two things a Promise cannot give you.

A request only ever resolves to one thing, so it's fair to ask why HttpClient bothers with RxJS at all instead of just returning a Promise. Side by side:

Resolves once, with whatever the first response was. There's no way to call in afterwards and say "never mind" — the request keeps running to completion even once nothing cares about the result any more.

Want to retry on failure, or wait a moment before firing? There's no shared vocabulary for that — you write it yourself, by hand, every time you need it.

An HttpClient call returns a stream. Unsubscribing from it — including a component simply being destroyed — tears down the real network request via AbortController (or XMLHttpRequest.abort()).

retry, debounceTime, timeout and switchMap all apply to it completely unchanged, because they're operators on the exact same Observable type as everything else in RxJS.

The payoff

Unsubscribing doesn't just ignore the response — it cancels the call.

Because a request is an Observable, the same teardown logic that runs when any Observable is unsubscribed applies here too. The async pipe and toSignal unsubscribe for you; a hand-rolled .subscribe() needs takeUntilDestroyed() to do the same.

toSignal and the async pipe unsubscribe for you. A hand-written .subscribe() does not — clean it up yourself with takeUntilDestroyed(), or its callback keeps running after the component that started it is gone.

Pitfalls

Where this goes wrong in code review.

  • Forgetting to subscribe. http.get() is a cold Observable — no request fires until subscribe(), the async pipe, or toSignal.
  • Subscribing multiple times. Each subscription is a new HTTP call. Share with toSignal/async or shareReplay.
  • Manual subscriptions that leak. A hand-rolled .subscribe() should be cleaned up (takeUntilDestroyed()); async/toSignal do it for you.
  • Swallowing errors. catchError that returns a value hides failures — branch on err.status and surface real problems.
  • Not typing the response. get<Post[]>() gives you compile-time safety; get() returns Object.

Questions from the back row

Before you go

Four things to remember.

  • http.get() hands you a recipe, not a meal — nothing is sent until subscribe(), the async pipe, or toSignal cooks it, and every subscriber cooks their own.
  • A request travels inward through the interceptor chain to the backend, and the response travels back out through the same chain in reverse — cloning, never mutating, at every step.
  • Type the response with the generic (get<Post[]>()), and branch on err.status in catchError instead of quietly returning a fallback value that hides the failure.
  • Unsubscribing genuinely cancels the network call via AbortController — which is why switchMap is the fix for out-of-order responses, not just a way to ignore them.
