The @for block repeats a chunk of template once for every item in a collection — and unlike its predecessor, it requires you to say how it should tell one item from another across updates. That one word, track, decides almost everything interesting on this page: which DOM nodes get reused, what happens to state living inside a reordered row, and what breaks when you get it wrong. This page proves each answer live, not just states it.

“I don't even know a row moved. Position zero is still position zero.”

One list, one reorder, one half-typed word — and it ends up belonging to a stranger, with both tracking strategies swearing they did exactly what they promised.

The parties: track item.id, which follows the data wherever it moves. track $index, which only ever follows a position. And the node at hook zero, which never moved at all — it just started meaning something else.

track doesn't decide whether nodes move — it decides what Angular treats as "the same row." Track by a stable id and a moved row's node moves with it. Track by $index and Angular simply rebinds whatever node already occupies that position with fresh data — the node is a slot, not an identity, and anything it was holding now belongs to whoever the data says lives there today.

Picture a classroom where track item.id writes each student's actual name on their own desk — move the desks around and the name moves with them. track $index writes only "seat 1", "seat 2" on the floor, once, and never updates it when the desks rotate. Whoever sits in seat 1 today wears yesterday's name tag, because the floor never learned anyone moved.

The mental model

Angular is a coat check, not a row of hooks.

That's the argument. Here's the rule it settles: picture handing your coat to an attendant and getting back a numbered ticket. When you return, that ticket — not which hook the coat happens to be hanging on — is what reunites you with it. Staff can rehang every coat in the place while you're gone, and it still works, because the ticket travels with the coat, not with the hook.

track item.id is that ticket: a real, stable number stapled to the data itself. However the array reorders, Angular can always find the DOM node that belongs to a given item and simply move it, no matter where it now sits. track $index throws the ticket away and keeps the hook system instead — "your coat is whatever's on hook 3." That's fine, right up until someone reshuffles the rack — which is exactly what you're about to watch happen to a form input.

Track the thing, not the slot. A stable id follows the item wherever it moves; $index is just a hook number, and hook numbers don't move with anything. Picture three names in a list, each with its own text box beside it, and you've just typed half a sentence into the box next to the second name. A brand-new row arrives — not at the end, at the very top. Where does your half-typed sentence end up: still riding along with the same name, or now sitting next to whichever name happens to land in that same box on screen? Hold your guess — there's a live version of exactly this a few sections down that will settle it either way.

The mechanism

One update is a keyed diff, not a re-render.

@for isn't a directive you import — like @if, it's block syntax the Angular compiler understands directly, the same way *ngFor used to be a structural directive built on an <ng-template> and an NgForOf class underneath. That difference is exactly why track can be enforced at compile time instead of merely recommended: the compiler already owns the whole block, so it can simply refuse to build one that doesn't have one.

Read line 7 twice: @empty is not else. It's a sibling branch that fires only when the bound collection's length is exactly 0 — a null or undefined collection gives @for nothing to iterate over at all, and it throws instead of quietly rendering nothing.

The nodes and bindings for exactly one item. Building or discarding one of these, as a whole, is what a keyed diff spends its entire cost on. Whatever your track expression returns for a row — compared, not the row's contents. The same key next pass means "reuse this exact node." New keys are matched against last pass's keys. A key that already existed keeps its node and just gets rebound; a brand-new key gets a freshly built one. Built once, shown only while the collection's length is 0. A null/undefined collection never reaches this branch at all — it throws instead.
track is mandatory. Skip it and @for won't compile — not a lint warning, a build failure. For primitive arrays with no id, track item (the value itself) is fine as long as values are unique; for objects with no id you control, track $index is the honest fallback, accepting that a middle-insert or sort re-renders every row after it. In nested loops, alias each level's variables so they don't collide: @for (row of rows; track row.id; let r = $index) then an inner @for (cell of row.cells; track cell.id; let c = $index).

The contextual variables

Six variables ride along with the block, for free.

Inside @for, on top of the item itself, Angular hands you a small set of implicit values about the current iteration — not properties on your data, values the block computes fresh, on every single pass:

Zero-based position of this item in the current pass — recomputed for every row, every time the collection changes. Booleans, true for exactly one row each: position 0, and the final position. Neither ever fires on an empty collection — there's nothing to be first or last. Alternates by position. The usual use is zebra-striping a list, nothing more exotic than that. Total length of the bound collection — recomputed on every pass, and identical for every row in it.

Alias whichever ones you need with let, in any order, under whatever names make sense to you:

Live — $index, $first, $last, $even

@for (task of tasks(); track task.id; let i = $index, isFirst = $first, isLast = $last, isEven = $even) {
#{{ i }} {{ task.label }} @if (isFirst) { first } @if (isLast) { last }
}

Add or remove a task above and watch every badge here recompute — $index, $first and $last are never stored on your data; they're rebuilt from scratch, for every row, on every pass that reaches this block.

$index isn't the slow choice. It's the wrong one.

{{ letter.ch }}
}

@for (letter of letters(); track $index) {
{{ letter.ch }}
}

Type something into a couple of the "note" boxes, then click Shuffle. On the left (track letter.id) Angular matches each DOM node to its data item and moves the node, so your note travels with the same letter. On the right (track $index) Angular matches by position, so the input stays put and now holds whichever letter landed in that slot — the note appears to "jump" to a different letter.

There's a third way to get track wrong, and it's neither of the two above: not a duplicate, not a reorder — a key that is stable at first and then isn't, because it's the very field the user is editing.

Live — click into a name field and try to type more than one letter

track row.name — the field you're editing

@for (row of editRows(); track row.name) { }

track row.id — stable

@for (row of editRows(); track row.id) { }

Both columns edit the same underlying rows. On the left, the track key is the field you're typing into — every keystroke produces a "new" identity, so Angular destroys the input that just had focus and creates a fresh one in its place. Try to type a whole word and watch focus drop after the first letter. On the right, id never changes, so the same DOM node survives every keystroke and typing feels ordinary.

track has to be unique, stable and cheap — all three, not just the first one. Unique rules out duplicates (Angular throws). Stable rules out anything that changes while the row is on screen, including a field the row itself lets you edit — $index fails this the moment the list reorders, and an edited field fails it the moment the edit happens. Cheap rules out recomputing something expensive per item just to get a key.

Pitfalls that show up in exams & code review

Five ways to get bitten.

every one of these compiles cleanly except the first
The mistake What actually happens
Omitting track Unlike the old *ngFor, track is required — the template simply won't compile without it.
track $index on a reorderable list Angular keys rows by position, so a sort or middle-insert re-renders rows and can desync form or checkbox state. Track a stable id instead.
Tracking a non-unique value Duplicate track keys throw at runtime — at least it's loud. For primitive arrays with possible duplicates, fall back to $index.
Colliding aliases in nested loops Reusing let i = $index at both levels lets the inner one silently shadow the outer. Give each level its own alias name.
Expecting @empty to fire on null It renders only for a genuinely empty iterable (length 0); a null/undefined collection errors out instead — default to [] at the source.

Under the hood

Compiled syntax, not a runtime guess.

  • @for is native block syntax, not a directive. Unlike *ngFor (a structural directive that the * micro-syntax desugars to an <ng-template>), @for is compiled directly into repeat/track instructions by the Angular compiler — there is no NgForOf instance to inject or override.
  • Why track became mandatory. *ngFor's trackBy was an easy-to-forget optional input; without it Angular defaulted to identity-by-index, which silently broke on reorders. Making track a required part of the @for grammar turns that footgun into a compile-time error instead of a runtime perf-and-state bug.
  • @empty needs an actual iterable, not just a falsy one. A 0-length array reaches @empty just fine; a null or undefined collection isn't an empty iterable, it's the absence of one, so @for has nothing to diff against and throws rather than guessing which branch you meant.

Questions from the back row

Before you go

Five things to remember.

  • @for (x of xs; track x.id) repeats a template once per item — track is required, not a best practice.
  • Reordering a tracked list moves DOM nodes; it never rebuilds them. That's the entire performance-and-state-preservation story in one sentence.
  • track $index keys by position, not identity — safe for a list that only ever grows at the end, wrong for anything that reorders or inserts in the middle.
  • $index, $first, $last, $even, $odd, $count are computed fresh every pass — alias them with let, and give nested loops their own names so they don't shadow each other.
  • @empty is a sibling branch, not an else — it renders for a genuinely empty collection, and throws for null/undefined.
