Control Flow: @for

The @for block repeats a chunk of template for each item in a collection. A track expression is required so Angular can identify items efficiently across updates.

The mental model: the coat check

You hand your coat to the attendant and get a numbered ticket. When you come back, the ticket is what matches you to your coat — not where the coat happened to be hanging. Staff can shuffle the rack all afternoon and it still works, because the ticket travels with the coat.

track is that ticket. track item.id staples a real number to the item, so however the array reorders, Angular can find the DOM node that belongs to it and simply move it. track $index is the other system: "your coat is the one on hook 3." That is fine until someone reshuffles the rack, and then everybody goes home in the wrong coat — which is precisely what you are about to see happen to a form input.

Track the thing, not the slot. A stable id follows the item wherever it moves; $index is just a hook number, and hook numbers do not move with anything.

track is mandatory. Use a stable unique id (track item.id). Only use track $index for static lists that never reorder. Good tracking lets Angular reuse DOM nodes instead of recreating them — this is the single biggest list-perf lever.

For primitive arrays with no id, track item (the value itself) is fine if values are unique. For objects without an id you control, you may track $index — accepting that edits in the middle re-render rows. In nested loops, alias each level's variables so they don't collide: @for (row of rows; track row.id; let r = $index) then an inner @for (cell of row.cells; track cell.id; let c = $index).

Contextual variables

Inside @for you get handy implicit variables:

Live — $index, $first, $last, $even

@for (task of tasks(); track task.id; let i = $index, isFirst = $first, isLast = $last, isEven = $even) {
#{{ i }} {{ task.label }} @if (isFirst) { first } @if (isLast) { last }
} 
@for (item of items(); track item.id;
      let i = $index, e = $even, f = $first, l = $last, c = $count) {{ '{' }} … {{ '}' }}
  • $index — zero-based position
  • $first / $last — boolean edges
  • $even / $odd — parity helpers
  • $count — total length of the collection

track by id vs. track by $index

@for (letter of letters(); track $index) {

Type something into a couple of the "note" boxes, then click Shuffle. On the left (track letter.id) Angular matches each DOM node to its data item and moves the node, so your note travels with the same letter. On the right (track $index) Angular matches by position, so the input stays put and now holds whichever letter landed in that slot — the note appears to "jump" to a different letter.

Pitfalls that show up in exams & code review

  • Omitting track. Unlike the old *ngFor, track is required — the template won't compile without it.
  • track $index on a reorderable list. Angular then keys rows by position, so a sort or middle-insert re-renders and can desync form/checkbox state. Track a stable id instead.
  • Tracking a non-unique value. Duplicate track keys throw at runtime. For primitive arrays with possible dupes, fall back to $index.
  • Colliding aliases in nested loops. Give each level its own let i = $index alias; reusing the same name shadows the outer one.
  • Expecting @empty to fire on null. It renders for an empty iterable; a null/undefined collection errors — default to [].

Under the hood

Here is what actually happens when the bound collection changes. Note how little of it is "rendering" — the expensive part is the matching, and track is the only input you give it:

  • @for is native block syntax, not a directive. Unlike *ngFor (a structural directive that the * micro-syntax desugars to an <ng-template>), @for is compiled directly into repeat/track instructions by the Angular compiler — that's part of why track can be enforced at compile time instead of merely recommended.
  • track drives a keyed diff, not a naive re-render. On each update Angular computes the new collection's track keys, matches them against the previous run's keys, and only creates/moves/destroys the DOM nodes whose keys actually changed — the same reconciliation idea keyed lists use in other frameworks.
  • Why track became mandatory. *ngFor's trackBy was an easy-to-forget optional input; without it Angular defaulted to identity-by-index, which silently broke on reorders. Making track a required part of the @for grammar turns that footgun into a compile-time error instead of a runtime perf/state bug.
  • $index/$first/$last/$count/ $even/$odd are implicit template context variables, not properties on your data — the @for block computes them fresh for the current iteration, and they only exist inside that block's let aliasing, which is why nested loops need distinct alias names to avoid shadowing.
  • @empty is a sibling branch, not a fallback value. It renders only when the bound collection's length is 0; a null/ undefined collection skips both branches and throws, because @for needs an actual iterable to diff against.

Key takeaways

  • @for (x of xs; track x.id) repeats a template — track is required.
  • @empty renders when the collection is empty.
  • Implicit vars ($index, $first, …) are aliased with let.
  • Track a stable id for reorderable lists; $index only for static ones.
