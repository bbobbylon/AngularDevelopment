Template-driven forms keep the model in the template. Write ngModel on an input, give it a name, and Angular builds the form object for you — you never call new FormControl() or new FormGroup() yourself. This page takes that "for you" apart, piece by piece: who actually builds the model, what it silently tracks about you as you type, and the several very different ways a submit button can end up doing nothing at all.

Two completely different bugs make the exact same Submit button do exactly nothing — and neither one leaves a single line in the console.

Template-driven forms are quiet by design. That's wonderful right up until something's actually wrong and stays just as quiet. Here's every question that silence leaves behind.

Two doors, both shut, both silent. One has no bell wired to it at all — you knock, nobody ever hears it, and nothing tells you that. The other has a doorman standing in front of it who turns you away before you even reach the door — you never got as far as knocking. From where you're standing, outside, both look exactly the same: nothing happened.

The problem

You typed into a box. Where did that value just go?

Here's the part nobody points out: a plain <input> keeps its value entirely in the DOM. The browser knows what you typed. Your JavaScript does not — not unless you go and ask for it by hand, with something like document.querySelector('input').value. Nothing pushes that value anywhere on its own.

Angular forms exist to close exactly that gap: turning "the value is sitting in the DOM" into "the value is sitting in an object my code can read" — the form model — continuously, as the reader types. Template-driven forms answer with one very specific promise: you will never build that model yourself.

Below is a real form with three inputs, each wearing ngModel and a name. You are never going to write new FormControl(...) anywhere on this page. So when the reader clicks Submit, where does the object handed to your submit() method actually come from — and who built it? Hold that guess; the next section names the thing doing the building.

The mental model

Angular hands you a librarian, not a blank ledger.

Picture filling out a paper form at a library counter. You write in each box by hand — name, email, plan — and a librarian stands behind you, copying every field into a master ledger the moment you write it. You never touch the ledger yourself. You just fill in boxes, and by the time you're done, the ledger already matches.

That librarian is ngModel and ngForm, working together: ngModel copies one box, and ngForm holds the ledger every copy lands in. Reactive forms — the other way to build a form in Angular — hand you the blank ledger first: you build a FormGroup yourself, in the class, before the paper form even exists, then wire the paper form up to read from it. Neither one is "the right way" — this page is about the librarian's version.

The librarian does one more job worth knowing about before you meet the API. While copying, they keep notes on which boxes you've actually written in and which ones currently fail a rule — that's what powers the dirty/pristine, touched/untouched and valid/invalid states, and the ng-* CSS classes Angular paints onto every control because of them, with not one line of JavaScript from you.

You fill in boxes; the librarian keeps the ledger. Template-driven forms build the model for you as you write in the template — that's the whole trade against reactive forms, where you build the model yourself, up front, in the class.

The same idea, drawn

Three switches flip while you type, and Angular flips them for you.

The ledger isn't the only thing the librarian keeps. Every control also carries three independent yes/no flags, and Angular stamps each one straight onto the element as a CSS class, live, with no JavaScript from you to read it.

Starts pristine. The very first keystroke — not a blur, a keystroke — flips it to dirty, and it stays that way until the form itself is reset. Starts untouched. A blur — clicking or tabbing away — flips it to touched. Typing alone never touches it; only leaving does. The only one of the three that goes back and forth. It re-evaluates on every keystroke, so a field can be invalid one moment and valid the next, forever, with no reset involved.

That's the border colour you saw flip in the demo above: a common styling pattern is input.ng-invalid.ng-touched, which is exactly invalid AND touched — so a pristine required field never turns red the instant the page loads, only once the reader has actually had a chance to fix it.

Variations

ngModel reads four slightly different ways.

A modern twist

A signal can sit inside a two-way ngModel binding.

Template-driven forms predate signals, but the two integrate cleanly: write [(ngModel)]="mySignal" — the bare signal, no call parentheses — and Angular's template compiler recognises the two-way-binding target as a writable signal, reads the current value for you, and rewires the write-back to mySignal.set(newValue) instead of an illegal reassignment.

Live — username strength derived with computed()

length: {{ usernameLength() }} strength: {{ usernameStrength() }}

username is a plain WritableSignal<string>. Every keystroke calls username.set(...) through the two-way binding; usernameLength and usernameStrength re-derive automatically because they read username() — nothing here is wired up by hand.

The quiet failure

A missing FormsModule fails loudly. This doesn't.

Forgetting FormsModule gets you a build error you cannot miss. This next mistake produces no error at all — the build succeeds, the page loads, and clicking the button does something so unremarkable you might not even notice it happened.

That's the quiet failure mode worth remembering: a silent no-op is harder to debug than a compile error, precisely because nothing tells you to go looking.

A different quiet failure

required and minlength are doing double duty.

This time (ngSubmit) is wired up correctly. The attributes that Angular reads as validators — required, email, minlength — are, at the exact same time, ordinary HTML the browser enforces on its own, natively, before your click handler ever gets a turn.

The fix: add novalidate to the <form> tag — <form #f="ngForm" novalidate (ngSubmit)="submit(f.value)"> — so the browser stands down and Angular's own validation, driven by the same attributes, is the only one running. This is the other reason a form can "do nothing" on click with no console error and no breakpoint hit in your handler: sometimes the handler was never called at all.

Same visible result, both times — a click that does nothing — from two mechanisms that share no code at all. One trips over a missing binding; the other never leaves the DOM in the first place. Reading the console won't tell you which: neither one writes anything there.

Under the hood

Nothing about ngModel is special-cased magic.

It's ordinary Angular directive machinery, composed of three cooperating pieces that exam questions love to ask about individually — and knowing them is what turns "it just works" into "I know exactly why it works."

Custom form controls — a star-rating widget, a colour picker — implement the same ControlValueAccessor interface to plug into ngModel and reactive forms identically; nothing about it is private to the built-in <input>.

Choosing between the two

Neither approach is the wrong one — they trade in different situations.

Quick to write for a small, mostly-static form — a login box, a short signup. Validation reads as plain HTML attributes, and there is nothing to inject or build before the template can use it.

Harder to unit test without actually rendering the component, because the model does not exist until the template creates it — and harder to reshape once fields need to appear or disappear at runtime.

The model is a real object in the class — a FormGroup you can inspect, compose and unit test without a fixture. Cross-field validation, where a validator needs to look at several controls at once, attaches naturally to the group that contains them.

More to write up front: you build the group with FormBuilder before the template exists, and every field needs a matching formControlName.

The exam traps

Eight ways this bites people who otherwise understand it fine.

  • Missing name. ngModel without a name inside a <form> throws — see the rule box further up.
  • Forgetting FormsModule. A build-time NG8002 — loud, immediate, and the opposite of the missing-(ngSubmit) trap a few sections back.
  • Reading f.value too early. Empty inside ngOnInit, because control registration happens in a microtask — the self-test below asks this one directly.
  • Showing errors before interaction. Gating only on invalid (forgetting touched) shows every validation message the instant the page renders, before the reader has typed anything.
  • [(ngModel)]="signalName()" with a call. Adding the parentheses when two-way-binding to a signal does not compile — the write-back would need to reassign a call expression, which the compiler rejects outright.
  • Confusing name with id. id is only for the <label for> pairing — it has zero effect on form.value. Only name (and ngModelGroup nesting) shapes the value object.
  • Reaching for it on a complex, dynamic form. Adding or removing controls at runtime, cross-field validation, and testing without rendering the DOM are exactly where reactive forms win.
  • Assuming one-way is two-way. <input name="q" ngModel /> feeds f.value only. It does not update a component field unless it is written as [(ngModel)]="query".

Before you go

Five things to remember.

  • You never build the model. Import FormsModule, write ngModel and a name on each control, and ngForm assembles f.value for you as you type.
  • Three flags, stamped as classes. pristine/dirty and untouched/touched only ever move one way; valid/invalid flips back and forth on every keystroke.
  • Two silent failures, not one. A missing FormsModule fails loudly at build time; a missing (ngSubmit) fails by doing precisely nothing, with no error anywhere.
  • [(ngModel)]="signal" wants the bare signal. No call, no parentheses — Angular rewires the write-back to .set() for you.
  • Registration is a microtask. That is the entire reason f.value can still read empty inside ngOnInit — nothing has checked in yet.
