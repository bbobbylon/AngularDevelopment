Template-Driven Forms

Template-driven forms keep the logic in the template using ngModel. You never construct a FormControl or FormGroup yourself — Angular walks the DOM, finds every ngModel-decorated element, and assembles a matching control tree behind the scenes. Great for small, mostly-static forms. (Reactive forms, covered later, move that model explicitly into the component class for complex, dynamic, or heavily-tested cases.)

Setup

Import FormsModule into the component that owns the form:

{{ setupSample }}

Line-by-line

  • import {{ '{' }} FormsModule {{ '}' }} from '@angular/forms'; — pulls in the directive bundle that ships NgModel, NgForm, NgModelGroup, and the attribute-based validators (required, minlength, maxlength, pattern, email). It is a small standalone-friendly module, distinct from ReactiveFormsModule.
  • imports: [FormsModule] in the standalone @Component metadata — this is what actually makes ngModel a legal template attribute on this component. Standalone components don't inherit directives from anywhere else; every template needs its own import list.
  • Omit the import and the template still "compiles" syntactically, but Angular's compiler doesn't recognize ngModel as a known property, so you get an NG8002: Can't bind to 'ngModel' error at build time — a very common first-timer mistake covered again in Exam pitfalls below.

Anatomy of the name field

The name field above is the smallest complete example of every moving part in a template-driven control. Here it is in isolation: 

{{ anatomySample }}

Line-by-line

Line / attribute What it does here
#f="ngForm" on <form> Every <form> in an app with FormsModule imported gets the NgForm directive attached automatically (it matches the form element selector, no explicit attribute needed). #f="ngForm" just grabs a template reference to that directive instance so the template can read f.value, f.valid, and call f.resetForm().
(ngSubmit)="submit(f.value)" NgForm listens for the native submit event, calls preventDefault() for you (so the page never hard-navigates/reloads), and re-emits it as ngSubmit. Using (ngSubmit) instead of (submit) is what gets you that automatic preventDefault().
name="name" The key the control registers under on the parent form. f.value ends up as {{ '{' }} name: ..., email: ..., plan: ... {{ '}' }} — the object shape is built entirely from these name strings, not from the element's id (which is only there for the <label for> association and has no meaning to Angular).
ngModel (bare, no brackets) This is the directive selector itself. Bare ngModel (no [ngModel]/[(ngModel)]) still creates and registers a FormControl — it just means "manage this control, but don't push a value into it from the component." One-way-out only: the form model reads from the DOM, nothing writes back into the DOM from the class.
required, minlength="2" Plain HTML validation attributes. NgModel detects them via Angular's built-in validator directives (RequiredValidator, MinLengthValidator, etc., all shipped inside FormsModule) and folds their results into the control's errors object — no separate "validators array" to wire up like in reactive forms.
#name="ngModel" A template reference to this control's NgModel directive instance, exposing name.invalid, name.touched, name.dirty, and name.errors for the error-message logic just below it.
@if (name.invalid && name.touched) Gates the error block on both conditions. invalid alone would show "Name is required" on a completely untouched, empty field the instant the page loads — touched only becomes true after a blur event, so the message waits until the user has actually interacted with (and left) the field.
name.errors?.['required'] errors is null when the control is valid, so the optional-chain ?. is load-bearing — without it, reading ['required'] off null throws the moment the field becomes valid.

How it works

  • ngModel + a name registers a control on the parent ngForm.
  • #f="ngForm" exposes the form; #name="ngModel" exposes one control.
  • Validators are plain HTML attributes: required, minlength, email, pattern.
  • Angular tracks states & CSS classes: ng-valid/ng-invalid, ng-touched, ng-dirty.
  • (ngSubmit) fires on submit; bind [disabled]="f.invalid" to gate it.

ngModel variations

{{ variationsSample }}

Line-by-line

  • <input name="q" ngModel /> — bare ngModel, one-way into the form model only. The DOM value flows up to f.value.q; nothing flows back down from the component. Use this when the component only cares about the value at submit time.
  • <input name="q" [(ngModel)]="query" /> — the "banana in a box" syntax, sugar for [ngModel]="query" (ngModelChange)="query = $event". Now it's genuinely two-way: setting this.query in the class updates the input's displayed value, and typing updates this.query on every keystroke (via the input event under the hood).
  • <input ngModel #x="ngModel" /> — a standalone control with no surrounding <form>. It still gets a working FormControl and template reference (x.value, x.valid, …); it simply never rolls up into a parent NgForm's value object. Handy for a single search box that doesn't need the ceremony of a full form.
  • <div ngModelGroup="address"> — nests every ngModel control inside it under an address key, so form.value becomes {{ '{' }} address: {{ '{' }} city: ... {{ '}' }} {{ '}' }} instead of a flat object. It mirrors FormGroup nesting from the reactive-forms world, purely through template structure.
  • <input name="city" ngModel /> inside that group — same rules as any other control, it just registers on the NgModelGroup instead of directly on the root NgForm, which is why its value lands at form.value.address.city rather than form.value.city.

Angular also reflects control state as CSS classes you can style directly — no JavaScript needed for basic error styling: ng-valid/ng-invalid, ng-touched/ng-untouched, ng-dirty/ng-pristine. A common pattern is input.ng-invalid.ng-touched {{ '{' }} border-color: red; {{ '}' }} — invalid AND touched, so pristine required fields don't turn red on page load.

Live demo — a signal living inside a two-way ngModel binding

Template-driven forms predate signals, but the two integrate cleanly: write [(ngModel)]="mySignal" — the bare signal, no call parentheses — and Angular's template compiler recognizes the two-way-binding target as a writable signal, so it reads the current value for you and rewires the write-back to mySignal.set(newValue) instead of an illegal reassignment. Pair the signal with a computed() and you get form state that recalculates itself on every keystroke, with no manual subscriptions and no (ngModelChange) handler to write.

Live — username strength derived with computed()

length: {{ usernameLength() }} strength: {{ usernameStrength() }}

username is a plain WritableSignal<string>. Every keystroke calls username.set(...) through the two-way binding; usernameLength and usernameStrength are computed() signals that re-derive automatically because they read username() — nothing here is wired up imperatively. 

{{ signalFormSample }}

Line-by-line

  • protected readonly username = signal(''); — a plain writable signal, not a form control. Template-driven forms don't know or care that the backing store is a signal; from NgModel's point of view it's just a value that can be read and written.
  • [(ngModel)]="username" — the bare signal reference is the whole trick. Writing [(ngModel)]="username()" (with a call) targets the signal's current value — a plain string — and the write-back would need to reassign that call expression, which the compiler rejects outright as an unsupported two-way-binding target. Leaving off the parentheses lets the compiler see the target itself is a WritableSignal, so it reads it for the current value and rewires the write-back to username.set($event) instead of a plain assignment.
  • readonly usernameLength = computed(() => this.username().length); — computed() instead of a plain getter because it memoizes: it only recalculates when username actually changes, and — critically — reading it in the template registers the template as a dependent, so Angular knows precisely when to re-render this binding.
  • readonly usernameStrength = computed(() => ...) — derives from usernameLength(), not from username() directly. Computed signals can depend on other computed signals; Angular builds the dependency graph from whichever signals are actually read during the computation, so this stays lazy and correct without you declaring the dependency anywhere explicitly.
Reach for template-driven forms for small, mostly-static forms. Prefer reactive forms when you need dynamic controls, complex/cross-field validation, or unit-testable form logic without a rendered DOM. Template forms are asynchronous — the model is assembled over a tick, so f.value may be empty in the very first ngOnInit.

Under the hood

Nothing about ngModel is special-cased magic — it's ordinary Angular directive machinery, composed of three cooperating pieces that exam questions love to ask about individually: 

{{ underTheHoodSample }}
  • ControlValueAccessor is the bridge between the DOM and Angular's form model. For a plain <input>, Angular's built-in DefaultValueAccessor implements writeValue() (model → DOM, sets .value), registerOnChange() (DOM → model, wires the input event to notify Angular), and registerOnTouched() (wires blur). Custom form controls (a star-rating widget, a color picker) implement this same interface to plug into ngModel and reactive forms identically.
  • Control creation is asynchronous. NgModel registers itself with the parent NgForm in ngOnChanges, but that registration is deferred with a Promise.resolve().then(...) (a microtask) to avoid the "expression changed after it was checked" error that would fire if the form's value changed synchronously during its own creation pass. That microtask delay is exactly why f.value can read as {{ '{' }}{{ '}' }} (empty) if you inspect it inside ngOnInit — the controls haven't finished registering yet.
  • Validators compose into one function. Each attribute validator (RequiredValidator, EmailValidator, …) contributes a small pure function; Angular combines them with Validators.compose() into a single validator that runs on every value change and populates control.errors. That's why errors can hold multiple keys at once — e.g. {{ '{' }} required: true {{ '}' }} — even though only one validator directive is failing at a time in practice.
  • Status changes propagate as an observable. Every control exposes statusChanges and valueChanges observables under the hood; the CSS classes (ng-valid, ng-dirty, …) and the invalid/touched getters you read in the template are just synchronous snapshots of that same underlying state machine.

Exam pitfalls

  • Missing name attribute. ngModel without a name inside a <form> throws at runtime — the name is the key it registers under, so Angular has no way to place the value in form.value.
  • Forgetting FormsModule. No import → ngModel isn't a known property and the template fails to compile with NG8002.
  • Reading f.value too early. Control registration happens in a microtask, so it can be empty ({{ '{' }}{{ '}' }}) in the component's own ngOnInit — a classic "why is my form empty" trick question.
  • Showing errors before interaction. Gating only on invalid (forgetting touched/dirty) shows every validation message the instant the page renders, before the user has typed anything.
  • [(ngModel)]="signalName()" with a call. Adding the () when two-way-binding to a signal does not compile — the write-back would need to reassign a call expression, which the compiler rejects outright. Bind the bare signalName and Angular rewires the write-back to .set() for you.
  • Confusing name with id. id is only for the <label for> pairing and accessibility — it has zero effect on form.value. Only name (and ngModelGroup nesting) shapes the value object.
  • Using it for complex, dynamic forms. Adding/removing controls at runtime, cross-field validation, and unit testing without rendering the DOM are exactly where reactive forms win — template-driven forms suit small, mostly-static shapes.
  • Two-way binding vs one-way. A question that shows <input name="q" ngModel /> and asks "will typing update the component's query field?" — the answer is no unless it's [(ngModel)]="query"; bare ngModel only feeds f.value, not a component property.

Exam corner

Why does ngModel need a name inside a form?
The name is the key the control registers under on the parent ngForm — form.value is built from those names. Omitting it throws.
What do #f="ngForm" and #name="ngModel" give you?
Template reference vars exposing the form directive and a single control's state (valid, touched, errors, value).
Template-driven vs reactive — when each?
Template-driven for small, mostly-static forms. Reactive for dynamic controls, cross-field validation, or unit-testable logic (model lives in the class).
What does [(ngModel)]="username" actually compile to, and why no parentheses?
Two-way binding to a bare writable signal desugars to [ngModel]="username()" (ngModelChange)="username.set($event)" — Angular reads the current value for the input side and rewrites the write-back to .set(). Writing username() as the binding target instead targets the signal's plain string value, and the write-back would need to reassign that call expression — the compiler rejects it as an unsupported two-way-binding target.
Why can f.value be an empty object inside ngOnInit?
Controls register with their parent NgForm via a microtask (deferred with Promise.resolve().then()) to sidestep an "expression changed after checked" error. ngOnInit runs synchronously before that microtask flushes, so the form can still look empty at that point.

Key takeaways

  • Import FormsModule; drive everything from the template with ngModel — no manually-constructed FormControl/FormGroup.
  • Template reference vars (#f="ngForm", #ctrl="ngModel") expose form and control state directly in markup.
  • Validation uses HTML-attribute validators composed into the control's errors/state — gate error UI on touched or dirty, not just invalid.
  • [(ngModel)]="signal" — bind the bare signal (no call) to two-way bind it; Angular rewires the write-back to .set() automatically.
  • Under the hood: ControlValueAccessor bridges DOM ↔ model, registration is deferred to a microtask, and validators compose into one function feeding statusChanges.
