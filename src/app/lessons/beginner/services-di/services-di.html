A service is a class for logic and state that doesn't belong to any one component — shared data, business rules, anything two components both need. Angular's dependency injection (DI) creates those instances and hands them to you, so you never write new yourself. One decision controls almost everything about how DI behaves — where you register a service — and this page proves it live before it explains it: watch two components share one cart, then watch two more count in perfect isolation, from services that look identical on paper.

The problem

Two components need a cart. Who owns it?

Try the obvious approach: every component that needs a cart just writes new CartService() inside itself. It compiles. It even looks like it works — for about five seconds, until you put two components on the same page that are both supposed to show the cart, and they show two different numbers, because they each built their own object and neither has ever heard of the other. Worse, you can never swap in a fake cart for a test: new hard-wires you to this exact class, forever.

Dependency injection is a straightforward flip. A class stops building its own dependencies and instead asks for them — "I need a CartService" — and something else, the injector, decides what to hand back. Sometimes that's a brand-new object, built to order. Sometimes it's the exact same object every other asker already has. The whole of this lesson is that one decision, and how you control it.

Both pairs inject a service that looks about the same on paper — one signal, a couple of methods that change it. Before you scroll: do you think both pairs will behave the same way? The mental model

Angular runs the front desk. You never cut your own key.

Picture a hotel. You don't forge your own room key at a hardware store — you go to the front desk and ask for one. The person behind the desk decides what to hand you, and the answer depends entirely on what you asked for and which desk you're standing at.

Ask for "the master key to the laundry room" — a resource the whole hotel shares — and every desk in the building hands you the exact same key: cut once, the first time anyone ever asks, then reused for every guest after. That's a service registered providedIn: 'root' — one instance, built lazily, handed to everyone.

Ask for "a key to my room", though, and the desk on your floor cuts you one that belongs to no one but you — the guest one floor down gets a different key to a different lock, even though both keys were stamped from an identical blank. That's a service listed in a component's own providers array: same class, a fresh instance every time it's requested from that scope.

the injector is the desk — the class is only the blank the key gets cut from

And just like a real hotel, there isn't one front desk. There's a whole chain of them — one on every floor, all the way down to the lobby — and a request a floor desk can't answer gets walked down to the next one. That chain is the injector tree, and Under the hood below draws exactly what it looks like.

Marks a class as something an injector is allowed to build. On its own it registers the class nowhere. Tells Angular which injector owns this class and builds it lazily there. 'root' is the whole-app front desk. A list on a component (or a route) that gives that scope its own copy — shadowing anything with the same type further up. The request itself. Walks up from wherever it's called until it finds a desk with an answer.
Ask, don't build. You never call new on a service. You ask the injector for one, and where you asked from — which floor's desk — decides whether you get the one shared key or a fresh one cut just for you.

Under the hood

How does a lookup with no local provider find anything at all?

Every component gets its own element injector, nested inside its parent's, all the way up to the app's root injector. Calling inject(X) starts at the calling component's own injector and works outward, one ancestor at a time, until something answers or the walk runs out of ancestors.

Reference

Registration decides how many instances exist — and how long they last.

Registering a service isn't all-or-nothing. Where you register it controls how many instances exist, who shares which one, and — the row most people never think to ask about — when, if ever, that instance goes away.

Going further

A third scope: providers on the route itself.

Root and component providers cover most of what you'll write day to day, but there's a third scope worth knowing before you leave this lesson: a route can own its own providers too.

  • Every component under /checkout — the routed component and everything inside it — resolves the exact same CheckoutStore instance.
  • Navigate away and the router destroys that environment injector, so CheckoutStore (and any state it holds) is gone. Come back to /checkout and you get a brand-new instance, reset from scratch.
  • If CheckoutStore also has a providedIn: 'root' registration somewhere, the route's own copy shadows the root one — but only for components inside /checkout. Everywhere else in the app still sees the root instance.

The row the table half-answers

Service teardown: does ngOnDestroy actually run?

Every provider-location decision so far has been about how many instances exist. There's a second question the table above only hints at: when, if ever, does one of those instances go away?

Services can implement OnDestroy exactly like components can, and Angular calls it at the same moment: when the injector that owns the instance is destroyed. For a component-provided service, that's the component. For a root service — read that row again — it's the whole application. In a browser tab, that's effectively never.

The other failure mode

inject() needs an injection context.

inject() only works while Angular is actively constructing something — a component, a directive, a pipe, or a factory function it invokes directly, like a functional route guard. Call it later, and there is no injector left for it to walk from.

Field initializers, constructors, and factory functions (route guards/resolvers written as plain functions) are injection contexts. A click handler, a setTimeout callback, or any method invoked after the object already exists is not — capture what you need as a field first.

The trap two services build together

When the walk can't finish: NG0200.

There's one more way inject() can fail, and it has nothing to do with a missing provider — it's two services that each need the other.

Two fixes, in order of how often each one is actually the right answer:

  1. The design fix — pull what they share into a third service. Whatever both classes actually need — say, the current token — almost never needs to live inside either of them. Extract it into a TokenStore that neither AuthService nor ApiService needs the other to reach. Two dependents of one shared thing isn't a cycle.
  2. The mechanical escape hatch. Capture private injector = inject(Injector) in one of the two classes, then call this.injector.get(ApiService) lazily, inside a method, the first time it's actually needed — by then both classes have finished constructing, so there's nothing left to be circular about.

forwardRef, covered fully in Advanced DI, solves a related but different problem: a declaration-order issue inside one file, not two services that generally need each other.

Exam pitfalls

The trap almost everyone falls into first.

  • Calling inject() outside an injection context throws NG0203, it doesn't fail silently — see the section above.
  • @Injectable() alone does not register a provider. The decorator only makes a class eligible for DI metadata; without providedIn or an entry in some providers array, injecting it throws NullInjectorError: No provider for X! — a common "works in one component, crashes in another" bug.
  • providedIn: 'root' means one instance per root/environment injector, not "one instance, ever, no matter what." The route-providers section above is exactly this exception in practice — the phrasing matters on an exam.
  • Mutating shared service state in place (e.g. this.items.push(x) instead of this.items.update(i => [...i, x])) breaks the same-reference check signals rely on. A service is not an escape hatch from Angular's reactivity rules — it still needs immutable updates to notify consumers.

Questions from the back row

Before you go

Six things to remember.

  • A service is asked for, never built. inject() (or a constructor parameter) walks the injector tree from wherever it's called until something answers.
  • @Injectable({{ '{' }} providedIn: 'root' {{ '}' }}) = one lazily-built, tree-shakable instance for the whole app. A component's own providers: [Service] = a brand-new instance for that subtree, shadowing anything with the same type further up.
  • The walk stops at the first match — that's why a local provider shadows root instead of adding to it, and why two CounterWidgets never see each other's count.
  • Registration doesn't just decide how many instances exist — it decides when, if ever, ngOnDestroy runs. A root service's cleanup effectively never runs; a component- or route-provided one is destroyed with its owner.
  • inject() needs an injection context — a constructor, a field initializer, or a factory Angular invokes directly. Reach for it in a base class instead of repeating constructors; expect NG0203 anywhere else.
  • Two services injecting each other throws NG0200 before either finishes constructing — the fix is almost always to extract what they share into a third service, not to reach for forwardRef.
