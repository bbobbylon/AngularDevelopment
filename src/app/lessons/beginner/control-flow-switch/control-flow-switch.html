@switch renders exactly one branch out of several, chosen by testing a single value against a list of exact matches — the template's version of a switch statement, but with no break and no fall-through to manage. That one sentence hides real rules worth getting precise about: how the match is judged, what happens when nothing matches, how far a case's type narrowing reaches, and — new in this version of Angular — what the compiler can now prove for you before you ship. This page takes each one with a live demo, not just a claim.

The problem

One value. Four screens. Which one shows?

Say your component tracks one thing — a request's status — and it is always exactly one of four strings: idle, loading, success, error. You already know how to render that with a chain of @if / @else if: one comparison per state, in order, with an @else at the end to catch whatever is left. 

{{ chainedIfSample }}

It works. It also gets uglier every time a fifth state shows up, because now you are maintaining N almost-identical comparisons against the same variable, and nothing stops you from typing status() === 'sucess' and having the whole branch quietly never run. @switch is Angular's answer to that specific shape — one value, several exact possibilities. You write the value once and list the values it might equal.

Here is the question the rest of this page turns on. status is holding the string '1'. Somewhere in a switch there is a @case (1) — the number one. Does that case match? Hold your answer — there is a live version further down that will settle it either way, and the reason behind whichever answer you gave is worth understanding before you read on.

The mental model

@switch is a bouncer holding a guest list.

Picture a bouncer at the door of a club, holding a clipboard. One person arrives — that is your switch expression, checked exactly once at the door, not re-checked every few seconds while they wait in line. The bouncer reads the guest list top to bottom, comparing the name in front of them against each entry, and the moment a name matches exactly, that guest is let in — and the bouncer stops reading. Nobody further down the list even gets glanced at, because the search is already over.

"Exactly" is doing real work in that sentence. This bouncer does not do "close enough" — a photocopy of your ID is not your ID, even if every word on it is identical, and it turns out type matters too, which is exactly what the napkin question above is really asking. Hold that thought; the live demo a few scrolls down settles it for good.

Evaluated exactly once per check — the ID at the door, not re-scanned every time someone glances at it. Compared against the switch value with strict ===. Order matters — first match wins, and the search stops there. Optional. Runs when nothing else matched. Skip it, and an unmatched value renders nothing at all.
One value, checked once, matched top to bottom. @switch reads its expression a single time per check, then walks its @case list from the top and stops at the very first exact match — everything after that point, including an identical case further down, is never reached.

The mechanism

Exactly once, then compared top to bottom.

Live — one value, four exact possibilities

@switch (status()) { @case ('idle') {

💤 Nothing happening yet.

} @case ('loading') {

⏳ Loading your data…

} @case ('success') {

✅ Loaded successfully!

} @default {

❌ Something went wrong.

} }

Four buttons, one rendered paragraph at a time. Switching states does not toggle a hidden element — the previous branch is destroyed and the new one is built, which the Under the hood section below proves with a real lifecycle hook.

No fall-through, but you can still group

Every case is exact — but several can share one body.

"No fall-through" used to come with an asterisk: you could not stack values either, so five fruits that all render the same markup meant five copies of that markup. That changed. A @case left with no body now folds into whichever @case comes directly after it that does have one — so several values can share a single block, with no cascading and nothing to remember about ordering beyond "put the shared body last."

Live — six fruits, three bodies

@switch (fruit()) { @case ('apple') {} @case ('pear') {

🍎🍐 Pome family — a core full of seeds.

} @case ('cherry') {} @case ('peach') {

🍒🍑 Drupe family — one big stone in the middle.

} @case ('banana') {

🍌 Its own case — nothing else here looks like it.

} @default {

🤷 Not on the list — the general-admission line.

} }

Apple and pear render the identical paragraph; so do cherry and peach. Press kiwi and watch @default catch it — grouping cases did not change that rule at all.

What still does not work: {{ multiValueCaseSample }} — a @case block accepts exactly one parameter. Try to comma-stack values inside one case and the compiler stops you outright, in its own words: "@case block must have exactly one parameter." Stack separate cases instead, the way the demo above does.

The real superpower

Match the tag, and the rest of the shape unlocks.

Switch on the discriminant of a tagged union and Angular narrows the type inside each @case — so branch-specific fields are readable and type-checked, the same way a TypeScript switch (s.kind) narrows in a .ts file. There is one requirement that is easy to miss the first time, and it is worth seeing fail before it is explained. 

{{ shapeDirectCallSample }}

This fails to compile. shape() is a function call, and TypeScript never narrows through one — the second shape() on line 3 is a completely different expression from the one the switch checked, so it is still typed as the full Shape union, and radius does not exist on two of its three arms. 

{{ shapeLetSample }}

s is a stable reference — a plain identifier, not a call — so it narrows exactly like a discriminated-union switch does in TypeScript. This is the same rule @if (user(); as u) exists for; @switch just spells it @let instead.

Live — one union, three shapes, one compiler-checked switch

@let s = shape(); @switch (s.kind) { @case ('circle') {

⬤ Circle · radius {{ s.radius }} → area = π·r² = {{ area() }}

} @case ('square') {

◼ Square · side {{ s.side }} → area = s² = {{ area() }}

} @case ('triangle') {

▲ Triangle · {{ s.base }}×{{ s.height }} → area = ½·b·h = {{ area() }}

} }

Inside @case ('circle'), s.radius compiles; s.side would not — the compiler knows s is the circle variant there. All three Shape variants are covered above, so there is nothing left for a @default to catch — the next section turns that into a promise the compiler will actually check.

New in this version of Angular

Add a fourth shape, and the build breaks — on purpose.

@default never; replaces a normal @default block with a promise: "these cases are the whole story." The compiler checks that promise the same way TypeScript checks an assertNever(x: never) call — by proving that after every @case above has been subtracted, nothing is left. If nothing is left, the line compiles and does nothing further at runtime. If something is left, the build fails, pointing at that exact line.

Live — the same shapes, now a compiler-checked promise

@let kind = shape().kind; @switch (kind) { @case ('circle') {

⬤ 'circle' — one of three, accounted for.

} @case ('square') {

◼ 'square' — one of three, accounted for.

} @case ('triangle') {

▲ 'triangle' — one of three, accounted for.

} @default never; }

Every value shape().kind can hold is handled above, so @default never; compiles clean. Notice this panel captures its own kind with a fresh @let, rather than reusing s from the narrowing panel above — the code lab below explains why that is not just habit.

The exhaustiveness check is only as strong as the reference underneath it. Switch on a stable value — @let the discriminant itself, not just the object it lives on — give every arm its own @case, and @default never; turns a forgotten variant into a build failure instead of a blank panel.

A case most people trip on

An enum member has to be reachable from the template.

@case can reference any member on the component instance, not only literals — including an imported enum. The trap is that a template can only read the class, never a module-level import directly, so @case (RequestStatus.Loading) compiles only if RequestStatus is also exposed as a field on the class — the same protected readonly X = X; pattern the enums lesson teaches for exactly this reason.

Live — switching on a string enum

@switch (requestStatus()) { @case (RequestStatus.Loading) {

⏳ Working on it…

} @case (RequestStatus.Success) {

✅ Done.

} @case (RequestStatus.Failed) {

❌ It broke.

} }

This compiles because the class also declares protected readonly RequestStatus = RequestStatus;. Delete that one line and every @case below fails with "Property 'RequestStatus' does not exist on type 'ControlFlowSwitch'" — even though the enum is imported right at the top of the file.

Choosing between them

Same job, two different shapes of test.

When each one reads better
@switch chained @if / @else if
Shape of the test one value vs several exact constants unrelated boolean expressions
Evaluation expression once, then === per case a fresh condition evaluated at every rung
Type narrowing narrows the discriminant inside each case narrows only what each condition itself proves
Compiler exhaustiveness @default never; catches a forgotten case no equivalent — there is no fixed set of "cases" to check
Reads best for state machines, enums, union tags ranges, combined conditions, feature flags

Coming from *ngSwitch

One block replaces three cooperating directives.

{{ legacySwitchSample }}

Three cooperating directives — NgSwitch, NgSwitchCase, NgSwitchDefault — imported from CommonModule, each holding its own ViewContainerRef behind the scenes. The classic footgun lived in the asterisk: *ngSwitchCase="'loading'" desugars to a property binding, [ngSwitchCase]="'loading'", so the value is always an expression. Drop the star and write the attribute bare — ngSwitchCase="1" — and it is read as a plain HTML attribute, the string '1', not the number. Same characters on the screen, two different values, and nothing warns you which one you wrote. 

{{ blockSwitchSample }}

One built-in block, nothing to import, and no attribute-vs-binding ambiguity to trip over — every @case value is always an expression, always compared with ===. Structurally identical to the version on the left; the loose-equality trap is simply gone, because there is no longer a bare-attribute spelling to fall into.

Under the hood

Not a jump table — a sequence of checks.

  • Shares its engine with @if. Under the hood, @switch and a chained @if/@else if compile through the exact same conditional-branch instruction — the compiler works out which index should be active and swaps in that branch's view. @switch is @if/@else if with tidier syntax for one specific shape of test, not a different mechanism underneath.
  • Not a jump table — a sequence of === checks. The switch expression is evaluated once, then compared top to bottom against each @case literal by strict equality until one matches, or @default catches the rest. There is no compiled lookup table the way a low-level switch statement might use.
  • Switching away destroys, it does not hide. Because a non-matching branch is never instantiated, moving from 'loading' to 'success' runs the spinner component's ngOnDestroy and constructs the results component fresh — unlike [hidden], which never removes anything from the DOM.
  • No directive instance at runtime. Legacy *ngSwitch/*ngSwitchCase are real directives holding a ViewContainerRef and toggling embedded views imperatively. @switch is compiled directly into conditional instructions by the template compiler — there is no NgSwitch object to inject or override.
  • @default — and @default never; — are just other branches. Neither has special runtime behaviour beyond being selected (or, for never, proven unreachable) — compiled the same way as every other branch.

Pitfalls that show up in exams & code review

Seven ways to get bitten.

every one of these compiles cleanly and misbehaves silently
The mistake What actually happens
Strict ===, including for objects @case (someObj) matches only the same reference, never a structurally-equal one. Switch on a primitive discriminant, not an object.
No multi-value case @case ('a', 'b') fails to compile — a case accepts exactly one parameter. Stack bodyless cases instead (see Grouping cases above).
No fall-through — but a duplicate case still compiles Exactly one branch runs. A second @case for a value already matched above compiles cleanly and simply never fires — nothing warns you.
Silent empty render No matching case and no @default renders nothing, with no error. Add a @default — or @default never; if the switch is meant to be exhaustive — so a missing case is visible one way or another.
Number vs string cases @case (1) never matches the string '1'. Keep the switch value and every case literal the same type.
Enum or constant case needs the symbol on the class @case (Status.Loading) only compiles if Status is also a class member — a template can read the instance, never a module-level import directly.
Narrowing needs a stable reference @switch (shape().kind) renders correctly but narrows nothing inside each case, because a function call cannot be narrowed. @let s = shape(); @switch (s.kind) is the fix.

Questions from the back row

Before you go

Six things to remember.

  • @switch (value) is evaluated once per check, then compared top to bottom against each @case with strict === — no coercion, and the first exact match wins.
  • No break, no fall-through — but bodyless cases stack to share one body. A @case that matches a value already handled above is legal and silently dead.
  • Switching on a union's discriminant narrows the type inside each case — but only when the switch value is a stable reference. A bare function call, like a signal read, narrows nothing; name it once with @let first.
  • @default never; turns an exhaustive switch into a compiler-checked one: add a union member without a matching case, and the build fails instead of the screen going quietly blank.
  • An enum or constant used in a @case has to be re-exposed as a field on the class — a template never sees a bare module-level import.
  • Reach for @switch for one-value-many-states; use an @if chain for unrelated booleans. Under the hood they compile through the same mechanism, so the choice is about readability, not performance.
