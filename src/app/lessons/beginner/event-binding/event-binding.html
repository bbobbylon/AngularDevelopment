Event binding — (event)="statement" — is the other half of data binding: where [prop]="expr" only ever renders, (event)="stmt" runs a template statement when a DOM event (or a component's own output()) fires. The user does something; your class finds out.

The problem

Data only went one way. Where's the other half?

Property binding renders a value into the DOM — [value]="text", [disabled]="busy" — and it does that beautifully. But it is read-only by design: the expression on the right may never assign, never mutate, never have a side effect, because Angular is free to re-run it as often as it likes. So the moment a page needs to react to something the user does — a click, a keystroke, a value the user typed — property binding has nothing to offer. Something else has to carry information back out of the DOM and into your class.

Bind [value]="text" onto a native <input>, where text is a plain signal. Type into that box. Does text() change? Before you scroll: what would actually have to exist, wired to what, for a keystroke to update text?

The mental model

One conversation, not two syntaxes.

Picture [prop]="expr" and (event)="stmt" not as two unrelated features to memorise, but as the two directions of one conversation. Square brackets are you talking: you hand the DOM a value, it renders it, end of exchange — the DOM never gets to interrupt. Parentheses are the DOM talking back: something happened over there, and it genuinely interrupts your code to tell you, handing over a statement that is allowed to do something about it.

That asymmetry is the whole reason two syntaxes exist instead of one. A statement may assign, mutate, chain with ; — because it is reacting to a fact that already happened, not predicting a value that must stay reproducible.

Brackets IN, parens OUT. [prop] only ever reads and renders — a one-way, side-effect-free expression. (event) only ever fires in response to something that already happened — a statement, free to assign and chain. Confuse the two and you either try to assign inside an interpolation, or wonder why $event isn't always the same type.

The mechanism

A statement, then five steps to a repaint.

Interpolation ({{ '{{' }} … {{ '}}' }}) and property bindings must be pure expressions — Angular is free to re-evaluate them any number of times per check, so they can never assign or mutate. Event bindings are the one place a template runs statements: you can assign (box.value = '', below), and chain several with ;. Keep the statement itself short, though — real logic belongs in a method, because a long inline statement is hard to read in a diff and impossible to unit test directly.

Marking dirty and rendering are two different moments. The view is flagged synchronously inside the handler, but the actual repaint is scheduled — in this zoneless app it's coalesced into a microtask, so several events firing back to back still produce one pass, not one per event.

The other kind of $event

Same syntax, a completely different payload.

Angular has no built-in .prevent/.stop modifiers, and returning false from a handler does nothing — you call the DOM methods yourself. And for a component's own output(), $event is not a DOM event at all: it's the emitted value.

Under the hood

What a listener binding actually compiles to.

(click)="doThing()" is not simply element.addEventListener('click', () => this.doThing()). The template compiler generates a listener instruction that runs once per component instance to register a real DOM listener via Renderer2 — and it wraps your statement in its own function first.

The classic mistake

A bare identifier never calls anything.

Other pitfalls that show up in exams and code review:

  • Brackets vs. parentheses. [click]="…" is property-binding syntax and click isn't a DOM property, so it either does nothing useful or errors — event listeners always need (click).
  • Heavy work in (mousemove)/(scroll). They fire constantly, and each firing marks the view dirty and can trigger a render pass — throttle, or move the work off the hot path.
  • $event is the emitted value for outputs. For a component output() it's not a DOM event — don't call preventDefault() on it.
  • Key name casing. Pseudo-events match event.key as lowercase words: (keyup.enter), (keydown.arrowup), not Enter/ArrowUp.
  • meta vs control. (keydown.meta.k) only matches ⌘/Win-key combos — a Ctrl+K press needs a separate (keydown.control.k) binding.

Questions from the back row

Before you go

Things to remember.

  • (event)="stmt" reacts to DOM events and component outputs, and runs a statement — not a pure expression like interpolation or a property binding.
  • $event is the payload — a DOM event for a native event, the emitted value for an output.
  • Use pseudo-events like (keyup.enter) and combos like (keydown.control.s).
  • No .prevent modifier — call preventDefault() yourself, inside the handler.
  • Every template listener marks its view and every ancestor dirty and schedules a pass — one of the five official OnPush re-check triggers — before your statement's own effect on the DOM is even considered.
  • (click)="save" (no parens) never calls anything — it just references the method and discards it.
