A pipe takes a raw value — a number, a Date, a whole object — and hands back something ready to look at, right inside the template, using the | operator you've probably already used in a terminal. That much takes ten minutes to learn. The other twenty are the part most tutorials skip: which pipes are memoized and which aren't — the built-in docs get this one wrong more often than you'd think — where | is and isn't legal, and the one pipe, async, that almost never gets taught at all despite being the one you'll reach for the most.

The problem

You have a number. The user needs to see a price.

num() holds 1234.5. Nobody wants to see that on screen — they want $1,234.50. Where does that formatting logic go?

One answer: a method on the class, called from the template — {{ '{{' }} formatPrice() {{ '}}' }}. It works, and it quietly costs more than it looks like it does: a method call in a binding re-runs on every single change-detection pass that reaches that view, whether the price moved or not. Another answer: format it once, store the result in a second field, and remember to update that field every time the price changes. That is the exact effect-writing-a-second-signal mistake from the signals lesson, wearing a different hat — a second source of truth, one write away from disagreeing with the first.

Angular's actual answer is neither: a small, template-only operator built for exactly this job, and nothing else.

{{ '{{' }} price() | currency {{ '}}' }} — does that call currency's transform() again on every pass that reaches this binding, the way the method call above would? Or does something stop it? Hold your guess — Purity, further down this page, is where the real answer lives, and it is stranger than a plain "yes" or "no".

The mental model

You've used this symbol before.

ls | grep .ts | sort — a shell pipeline. Each command reads what arrived on its left, transforms it, and passes the result to its right. Nothing upstream is touched; nothing downstream needs to know how the transformation happened. Angular didn't invent a new idea for its template pipe — it borrowed this one, including the symbol, because it is already the right shape for "take a value, transform it, hand it on".

{{ '{{' }} now() | date:'fullDate' | uppercase {{ '}}' }} reads exactly the same way: now() goes in, date formats it, and whatever date produced goes straight into uppercase — which has no idea a Date object was ever involved.

A class with one job — a transform() method. name in its @Pipe decorator is the word you write after |. Everything following a : becomes a positional parameter to transform(), in the order written: currency:'EUR':'code' passes two. The output of one pipe becomes the input to the next. date | uppercase formats, then uppercases — swap the order and you get a different, usually wrong, result. Angular remembers the last input and can skip transform() entirely when nothing changed. What "changed" means is the whole of the next big section.
Left to right, like a shell pipe. Value in, transformed value out, and the pipe never touches what you handed it. Chain three together and you are simply piping the output of one into the input of the next.

The mechanism

A pipe is a class. That's the whole trick.

No runtime magic beyond one decorator. Here is a made-up pipe — not UpperCasePipe itself, so nothing about it can be mistaken for special-cased built-in behaviour.

Which means using a pipe has one more rule than it looks like it should: a standalone component only sees the pipes it lists. Forget to add DatePipe to imports and you don't get a blank date — you get a compile-time error naming exactly the problem: No pipe found with name 'date'.

Live — the same call, from the template and from TypeScript

template: {{ now() | date: 'shortTime' }} TypeScript: {{ formattedInClass() }}

formattedInClass calls this.datePipe.transform(this.now(), 'shortTime') by hand — DatePipe was inject()-ed like any other service, which only works because it is also listed in this component's own providers. Press refresh: both numbers move together, because they are the same call, made from two different places.

The everyday set

Text and numbers, formatted where they're read.

Live — text pipes

uppercase {{ text() | uppercase }}
lowercase {{ text() | lowercase }}
titlecase {{ text() | titlecase }}
slice:0:5 {{ text() | slice: 0 : 5 }}

Live — number pipes, with parameters

number:'1.2-2' {{ num() | number: '1.2-2' }}
percent {{ num() / 100 | percent }}
currency:'USD' {{ num() | currency: 'USD' }}
currency:'EUR':'code' {{ num() | currency: 'EUR' : 'code' }}

'1.2-2' decodes as minInteger.minFraction-maxFraction: at least 1 integer digit, at least 2 and at most 2 fraction digits. It is a format string, not a range — '1.2-2' does not mean "1 to 2".

Chaining is nothing special — it's the mental model from above, applied. 
{{ '{{' }} now() | date: 'fullDate' | uppercase {{ '}}' }}
→ {{ now() | date: 'fullDate' | uppercase }}
date runs first and hands its string to uppercase, which never sees the original Date at all — the same left-to-right handoff as a shell pipeline, and the same rule for why order matters: uppercase | date would try to format an already-uppercased string as a date, and fail.

The date pipe

The bug that ships to production.

Live — format strings

date {{ now() | date }}
date:'short' {{ now() | date: 'short' }}
date:'fullDate' {{ now() | date: 'fullDate' }}
date:'HH:mm:ss' {{ now() | date: 'HH:mm:ss' }}
date:'medium':'UTC' {{ now() | date: 'medium' : 'UTC' }}
date:'medium':'+0530' {{ now() | date: 'medium' : '+0530' }}

date's full signature is date:format:timezone:locale. Leave timezone out and Angular renders in your browser's own zone — which is exactly the setting that is different on every reader's machine, and the setting a bug report about "the wrong day" almost always turns out to hinge on.

That timezone parameter controls display — which clock the same instant is read against. It has nothing to do with a much sharper trap: parsing a bare date-only string, where Angular and plain JavaScript quietly disagree.

Live — the same string, both parses, both rendered in your own local time

'2024-03-15' | date:'medium' {{ '2024-03-15' | date: 'medium' }}
nativeParsedDate | date:'medium' {{ nativeParsedDate | date: 'medium' }}

nativeParsedDate is new Date('2024-03-15'), computed once in the class. If your browser's zone is west of UTC (most of the Americas), the second row shows the previous evening — the UTC midnight that string parsed to, translated back into a zone several hours behind it. East of UTC you'll usually see the same date with a different time instead. Either way, the two rows are provably not the same instant, despite starting from one identical string.

The fix: store instants in UTC (an ISO string with a Z, or epoch milliseconds), and choose the display zone with the timezone argument explicitly rather than trusting whatever a bare date-only string happens to parse to. For a value that is genuinely date-only — a birthday, not a moment — keep it as a string and format with timezone:'UTC' so no zone conversion happens at all. An unparseable value throws NG02311: Unable to convert "…" into a date rather than rendering silently wrong, which is at least a mercy.

A correction

Locale-aware pipes don't call Intl.

date, currency, number and percent all format according to LOCALE_ID — but they are not thin wrappers over the browser's Intl.DateTimeFormat / Intl.NumberFormat. Angular ships its own locale tables, generated from CLDR data, one file per locale under @angular/common/locales. LOCALE_ID just says which table to read from. 

import localeFr from '@angular/common/locales/fr';
registerLocaleData(localeFr);

// then, at bootstrap:
providers: [{{ '{' }} provide: LOCALE_ID, useValue: 'fr' {{ '}' }}]

Only the default, 'en-US', ships without asking. Request any other locale without registering it first and Angular throws its own error before formatting ever begins — NG0701: Missing locale data for the locale "…" — which is the tell that the failure lives inside Angular's table lookup, not inside the browser's Intl engine.

Pipes for containers

json and keyvalue play by a different rule.

Live — json (great for debugging)

{{ sample() | json }}

Live — keyvalue, sorted or in insertion order

    @for (entry of settings() | keyvalue: (sorted() ? undefined : noSort); track entry.key) {
  • {{ entry.key }}: {{ entry.value }}
    • } 
{{ '{{' }} obj | keyvalue {{ '}}' }}             <!-- sorted by key, default -->
{{ '{{' }} obj | keyvalue: noSort {{ '}}' }}      <!-- pass a compareFn to keep insertion order -->

keyvalue turns an object (or Map) into an array of { key, value } pairs so @for can iterate it — a plain object isn't itself iterable. On a big object bound in a hot template, re-sorting on every pass is a real cost; precompute a sorted array in a computed() instead if the source is large.

Both of these re-run their transform() on every single change-detection pass that reaches them, no comparison first — which is exactly the subject of the next section, and the point where the old version of this page was flatly wrong.

Purity

Pure by default. Four exceptions, each for its own reason.

Most built-in pipes are pure — not all of them. A pure pipe memoizes: Angular compares the new input against the one from last time, and if it is === the same, transform() never runs again. Four built-ins opt out of that entirely with pure: false, and each one has a genuinely different reason to.

pure by default — four deliberate exceptions
Pipe Pure? Why
uppercase / lowercase / titlecase Pure Strings are primitives — cheap to compare by value, nothing to mutate in place
number / percent / currency Pure Numbers, same reasoning
date Pure Compared by reference when given a Date object — mutating one in place with d.setHours(…) won't re-render either, the same trap as mutating a signal's array
json Impure Its whole job is to show what's inside an object right now, mutations included — memoizing it would make a debugging tool that lies
keyvalue Impure Turns a mutable object/Map into an array — mutating the source never changes its reference, so it has to re-diff every pass to notice anything
slice Impure Same reasoning as keyvalue — slicing a mutable array has to see mutations, not just replacements
async Impure Not about mutation at all — it owns a subscription and has to be given the chance to check on every pass

Live — the same mutation trap from the signals lesson, with an impure pipe watching

{{ sample() | json }}

Press mutate a few times: nothing happens yet — no signal write means no pass was scheduled. Press the no-op button, which changes no state at all, and every mutated tag appears at once. If json were pure like uppercase, it would compare sample()'s reference — unchanged by a mutation — and stay stale forever, no matter how many no-op clicks you sent its way.

Pure compares first; impure just runs. A pure pipe skips transform() entirely when the input is === what it saw last time. An impure one never checks — it re-runs on every pass that reaches it, which is precisely why async, json, keyvalue and slice are the only four built-ins marked that way, and why each one needed a specific reason to be.

The pipe nobody taught you

async subscribes so you don't have to.

Every other pipe on this page is a pure function of a value that already exists. async is different in kind: hand it an Observable or a Promise and it subscribes on your behalf, hands back whatever has arrived so far, and re-checks itself on every pass because it has to — it never knows when the next value is coming.

Every binding subscribes on its own

Bind the same observable with | async three times and you get three independent subscriptions — on a cold, HTTP-backed source, that is three network requests for what reads like one expression.

Live — three bindings vs. one, on the same cold source

Three separate | async bindings on the exact same observable:

a: {{ coldSource() | async }} b: {{ coldSource() | async }} c: {{ coldSource() | async }}

The as pattern — one binding, its result reused three times:

@if (coldSource() | async; as shared) {
a: {{ shared }} b: {{ shared }} c: {{ shared }}
}

Top row: three different numbers — each | async is its own subscription, so the producer ran three separate times. Bottom row: three identical numbers, because as shared subscribes once and every later {{ '{{' }} shared {{ '}}' }} is a plain interpolation, not a new pipe. This is exactly why @if (data$ | async; as data) is the idiom, not an optional nicety.

null until something arrives

transform() always returns immediately. Before the first emission, that means null — every template using async has to have an opinion about what to show meanwhile.

Live — a source that waits 1.5s before its first emission

@if (delayedSource() | async; as value) {

{{ value }}

} @else {

Loading…

}

For a second and a half, | async is returning null, and @else is what catches it. Skip the @else and a real app renders an empty gap where a loading state should be — not an error, just nothing, which is often harder to notice in review.

Unsubscribing happens for you

When the view hosting an async binding is destroyed, the pipe's own ngOnDestroy unsubscribes — the entire trick behind never writing .unsubscribe() yourself.

Live — remove the ticker, then bring it back

@if (showTicker()) {

tick: {{ ticker | async }}

}

Let it climb, then remove it and bring it back. It restarts at 1 every time — proof the old subscription was actually torn down, not just hidden. If it hadn't been, a second interval would now be racing the first, and the count would already be high, or climbing unevenly, the moment it reappeared.

Exam traps

Three places | quietly doesn't do what you expect.

A pipe only works inside a value expression — an interpolation or a property binding.

<button (click)="save() | uppercase">
  Save
</button>
<button (click)="save()">
  {{ '{{' }} status() | uppercase {{ '}}' }}
</button>

The third trap is subtler, and it lives inside an expression that compiles just fine — a pipe written inside a ternary.

Rule of thumb: if a pipe needs to apply to the result of a ternary rather than to one branch of it, wrap the ternary in parentheses first. Nothing about the compiler will warn you — both spellings are syntactically legal, and only one of them does what it looks like it does.

Questions from the back row

Before you go

Five things to remember.

  • value | name:arg1:arg2 calls transform(value, arg1, arg2) on an ordinary class. The pipe is the class; name is what you write after |, and everything after a : becomes a positional argument, in order.
  • Pure by default. Angular remembers the last input and skips transform() when it's === the same. async, json, keyvalue and slice opt out for four different, specific reasons — not because "some pipes are just slower".
  • Angular ships its own locale data — CLDR tables via registerLocaleData() — not the browser's Intl. A locale you never registered throws NG0701, not something inside Intl.
  • A bare 'YYYY-MM-DD' string is local midnight to Angular's date pipe but UTC midnight to plain new Date(…) — the same string, two different instants, depending on which parser touches it first.
  • Pipes only work in a value expression — never in an event binding's statement, never in track — and inside a ternary, | binds to the branch it's written in, not the whole conditional, unless you parenthesise.
