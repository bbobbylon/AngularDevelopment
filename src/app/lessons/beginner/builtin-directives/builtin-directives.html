Built-in Directives & Legacy Control Flow

Modern Angular gives you the @if / @for / @switch blocks you've already met. But every existing codebase — and the certification exam's question bank — is full of the structural directives they replaced: *ngIf, *ngFor, *ngSwitch, plus the attribute directives ngClass and ngStyle. You must be fluent in both. This lesson is the legacy half — and the demo below is running the real directives.

These directives live in @angular/common. A standalone component imports the ones it uses (NgIf, NgFor, …) — or the whole CommonModule in an NgModule app. Forget the import and current Angular stops you at compile time with NG8103; older versions treated the *ngIf as an unknown attribute and rendered the element unconditionally, with no error at all. Either way, @if has nothing to forget — that's one of its quieter advantages.

The mental model: a stencil, not a node

An <ng-template> is a stencil. It is a cut-out shape, and a cut-out is not ink on the page — you can hold a stencil all day and nothing appears. Something has to decide to press it down, and how many times.

That is the whole job of a structural directive. *ngIf holds one stencil and presses it once, or not at all. *ngFor holds one stencil and presses it once per item. And the * is simply the compiler being told "turn this element into a stencil for me."

The star turns the tag into a stencil. One star per element — you only get one stencil, which is why *ngIf and *ngFor cannot share a tag, and why <ng-container> exists to give the second one somewhere to live.

The asterisk is sugar

<!-- The star is sugar. One element, one attribute, nothing else visible. -->
<p *ngIf="loggedIn">Welcome</p>

<!-- is exactly -->

<!-- The compiler LIFTS the host element into an <ng-template> wrapper.
     That template is a blueprint: it is parsed, but nothing is rendered yet. -->
<ng-template [ngIf]="loggedIn">
  <!-- The original element becomes the CONTENT of the blueprint. The <p> only
       reaches the DOM when NgIf decides to stamp this template out. -->
  <p>Welcome</p>
<!-- The star is gone; what is left is an ordinary property binding, [ngIf],
     feeding the directive that now sits on the template. -->
</ng-template>

*ngIf — with else, then & as

<!-- `user as u` does two jobs at once: it tests `user` for truthiness AND
     binds the result to a local `u` for the body. That is why you write
     `u.name` and not `user!.name` — inside here, `u` cannot be null. -->
<p *ngIf="user as u; else loading">Hi {{ '{{' }} u.name {{ '}}' }}</p>

<!-- `#loading` is a template reference variable. It NAMES this blueprint so the
     `else` above can point at it. Nothing renders here until NgIf asks for it. -->
<ng-template #loading>Loading…</ng-template>

<!-- then/else both as templates -->

<!-- With an explicit `then`, the host element's own content is ignored entirely
     — hence the empty <div>. Both branches now live in named templates, so
     this line is pure routing: true → `content`, false → `spinner`. -->
<div *ngIf="ready; then content; else spinner"></div>

*ngFor — track, index and the booleans

<!-- Read the quoted part as five clauses separated by `;`. It is Angular's
     "microsyntax", not HTML — which is why no comment can go inside it:

     let item of items   →  `item` is the current element; one <li> per entry
     let i = index       →  0-based position. `index` is the built-in name,
                            `i` is the local you invent to hold it
     let first = first   →  true only on the very first iteration
     let last  = last    →  true only on the very last  (`even`/`odd` alternate)
     trackBy: trackById  →  names the function below; see the warning after -->
<li *ngFor="let item of items;
            let i = index;
            let first = first; let last = last;
            let even = even; let odd = odd;
            trackBy: trackById">
  <!-- Every `let` name above is in scope here, and ONLY here — they belong to
       this iteration, not to the component. -->
  {{ '{{' }} i {{ '}}' }}: {{ '{{' }} item.name {{ '}}' }}
</li>

<!-- Lives in the component class, not the template. Angular calls it for every
     item and uses the RETURNED VALUE as that row's identity. Returning
     `item.id` means "a row is the same row if its id is the same" — so Angular
     reuses the existing DOM node instead of destroying and rebuilding it. -->
trackById(index: number, item: Item) {{ '{' }} return item.id; {{ '}' }}
Always provide trackBy for lists that change. Without it Angular tracks by object identity and re-creates every DOM node when the array reference changes — slow, and it destroys input focus/animation state. (The new @for makes track mandatory for exactly this reason.)

[ngSwitch]

<!-- [ngSwitch] is a PLAIN property binding — no star. It holds the value to
     match against and does no rendering of its own; the container stays. -->
<div [ngSwitch]="status">
  <!-- These DO have stars: each case is its own template, stamped out only
       when its value matches. Note the quotes inside quotes — 'loading' is a
       string literal in the expression, not an attribute value. -->
  <p *ngSwitchCase="'loading'">Loading…</p>
  <p *ngSwitchCase="'success'">Done</p>
  <!-- The fallback. No expression to match, so it needs no value at all.
       Matching is strict (===), which is the usual reason a case "silently"
       never fires: a number 1 will not match the string '1'. -->
  <p *ngSwitchDefault>Unknown</p>
</div>

ngClass & ngStyle

<!-- object: keys are classes, truthy values apply them -->
<div [ngClass]="{{ '{' }} active: isActive, disabled: !enabled {{ '}' }}">
<!-- string or array forms too -->
<div [ngClass]="'a b c'">   <div [ngClass]="['a', 'b']">

<div [ngStyle]="{{ '{' }} color: c, 'font-size.px': size {{ '}' }}">

For a single class or style, the native bindings [class.active]="isActive" and [style.color]="c" are lighter — reach for ngClass/ngStyle when you're toggling several at once from an object.

ng-container & ng-template

<ng-container> is a grouping element that leaves no node in the DOM — perfect for applying a structural directive without an extra wrapper: 

<ng-container *ngIf="user as u">
  <h2>{{ '{{' }} u.name {{ '}}' }}</h2>
  <p>{{ '{{' }} u.email {{ '}}' }}</p>
</ng-container>

<!-- a named, reusable fragment rendered on demand -->
<ng-template #row let-name><td>{{ '{{' }} name {{ '}}' }}</td></ng-template>
<ng-container *ngTemplateOutlet="row; context: {{ '{' }} $implicit: 'Ada' {{ '}' }}"></ng-container>

Old → new at a glance

*ngIf="x" @if (x) {{ '{' }} … {{ '}' }}
*ngIf="x; else e" @if (x) {{ '{' }} … {{ '}' }} @else {{ '{' }} … {{ '}' }}
*ngFor="let i of xs; trackBy: fn" @for (i of xs; track i.id) {{ '{' }} … {{ '}' }}
[ngSwitch] + *ngSwitchCase @switch + @case
<ng-container *ngIf> (no wrapper needed — blocks aren't elements)

Under the hood

  • Structural directives desugar to <ng-template>. The * shorthand is sugar the compiler expands into a <ng-template> wrapping the host element, with the directive's input bound via microsyntax. The directive itself calls viewContainerRef.createEmbeddedView(templateRef) to insert or remove that view — that's the mechanism, not magic CSS hiding.
  • @if/@for/@switch aren't directives at all. They're built-in control-flow blocks the compiler emits straight into the component's template function — no directive class, no injector lookup, no CommonModule needed. That's exactly why forgetting to import NgIf breaks *ngIf, but there's nothing to "import" for @if.
  • NgFor keeps a live embedded view per item and reconciles by identity. Each change-detection run it diffs the new iterable against the previous one — by trackBy if you supplied one, otherwise by object reference — and only creates, moves or destroys the embedded views that actually changed.
  • [ngClass]/[ngStyle] diff-and-patch; they don't replace the attribute. Each cycle they compute which class/style entries changed since last time and call renderer.addClass/removeClass (or setStyle/removeStyle) only for those deltas — the static class/style attribute is left alone and merged with, never overwritten wholesale.
  • <ng-container> compiles to a comment node, not an element. It never creates a DOM element at all — the compiler emits an anchor comment, so a structural directive has somewhere to attach without introducing a wrapper into the rendered HTML.

Common mistakes

Two structural directives on one element *ngIf and *ngFor together is a compile error. Move one onto an <ng-container>.
*ngIf renders nothing and no error You forgot to import NgIf/CommonModule in the standalone component.
List re-renders / loses focus on every change Missing trackBy. Return a stable id.
[hidden] used like *ngIf [hidden] only toggles CSS display — the element (and its component, subscriptions, etc.) stays alive. *ngIf removes it entirely.
Combining [ngClass] and class and expecting one to win They merge. Static class plus [ngClass] object both apply; don't fight them.

Key takeaways

  • * = structural directive = adds/removes DOM; it desugars to <ng-template>.
  • *ngIf (else/then/as), *ngFor (trackBy/index/first/last/even/odd), [ngSwitch].
  • ngClass/ngStyle for multiple classes/styles; native [class.x]/[style.x] for one.
  • ng-container groups without adding a DOM node; ng-template is a fragment you render on demand.
  • You'll write @if/@for in new code, but you must read the directive forms fluently.
