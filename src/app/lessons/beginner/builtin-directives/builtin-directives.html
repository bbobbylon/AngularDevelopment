Modern Angular gives you the @if / @for / @switch blocks you've already met — and those are what you should write today. But open any codebase older than Angular 17, most tutorials, half of Stack Overflow, and a good chunk of the certification's question bank, and you'll meet a different syntax entirely: the structural directives *ngIf, *ngFor, *ngSwitch, plus the attribute directives ngClass and ngStyle. You need to read both fluently, even though you'll only ever write one of them — that asymmetry is the whole point of this page, and the demos below run the real directives so the mapping is never just asserted.

The problem

One star, and a rule nobody explains.

Here's a rule you'll hit in your first hour of reading legacy Angular: you can never put two structural directives on the same element. Not a style-guide preference — a compile error. Memorise the rule on its own and it's a trap waiting for a tired afternoon. Know why, and the mistake stops being conceivable, because you'll be able to see exactly what each star is trying to do to your markup.

These directives live in @angular/common. A standalone component imports the ones it uses (NgIf, NgFor, …) — or the whole CommonModule in an NgModule app. Forget the import and current Angular stops you at compile time with NG8103; older versions treated the *ngIf as an unknown attribute and rendered the element unconditionally, with no error at all. Either way, @if has nothing to forget — that's one of its quieter advantages.
You're allowed to put *ngIf on any element you like. You're allowed to put *ngFor on any element you like. Before you scroll: why can't you put both on the same element — what would actually have to happen for <li *ngIf="show" *ngFor="let x of xs"> to make sense, and why can the compiler not just pick an order for you?

The mental model

An <ng-template> is a stencil, not a page.

A stencil is a cut-out shape. It is not ink on the page — you can hold a stencil all day and nothing appears. Something has to decide to press it down, and how many times.

That is the whole job of a structural directive. *ngIf holds one stencil and presses it once, or not at all. *ngFor holds one stencil and presses it once per item. And the * is simply the compiler being told "turn this element into a stencil for me." Once you picture it that way, the rule from the last section answers itself: an element can only be lifted into one stencil, because it is only one element. Two structural directives both wanting to wrap it is two stencils fighting over one piece of paper.

The star turns the tag into a stencil. One star per element — you only get one stencil, which is why *ngIf and *ngFor cannot share a tag, and why <ng-container> exists to give the second one somewhere to live.

*ngFor in the wild

*ngFor — track, index and the booleans.

*ngFor holds its stencil once per item, and it hands you a small bundle of local variables you never have to compute yourself — index, first, last, even, odd — plus the one input that decides whether re-rendering that list is cheap or expensive.

Always provide trackBy for lists that change. Without it Angular tracks by object identity and re-creates every DOM node when the array reference changes — slow, and it destroys input focus/animation state. (The new @for makes track mandatory for exactly this reason.)

Under the hood

Five mechanisms, not five coincidences.

Every rule this page has thrown at you traces back to one of five actual behaviours. Pin these down and there's nothing left to memorise by rote:

The * shorthand is sugar the compiler expands into an <ng-template> wrapping the host element. The directive itself calls viewContainerRef.createEmbeddedView(templateRef) to insert or remove that view. They're built-in blocks the compiler emits straight into the template function — no directive class, no injector lookup, no CommonModule. Nothing to import means nothing to forget. Each check it diffs the new iterable against the previous one — by trackBy if supplied, else by reference — and only creates, moves or destroys the views that actually changed. Each cycle computes which class/style entries changed since last time and patches only the deltas. The static attribute is never overwritten wholesale. It never creates an element at all — the compiler emits an anchor comment, so a structural directive has somewhere to attach without adding a wrapper to the rendered HTML.

The famous trap

[hidden] looks like *ngIf. It is not *ngIf.

Both make an element disappear from the page. Only one of them makes it stop existing. Mixing them up is one of the most common mistakes in the certification's question bank, precisely because the visual result — nothing on screen — is identical either way.

There's a second, quieter way [hidden] fails, and it has nothing to do with lifecycles — CSS specificity. The attribute works by leaning on one very ordinary browser rule, [hidden] {{ '{' }} display: none {{ '}' }}, and any rule of yours that also sets display on that same element is competing with it on equal terms.

Questions from the back row

Before you go

Five things to remember.

  • * means structural directive — it desugars to <ng-template> and adds/removes real DOM, never just hides it. One star per element, because there's only one template to wrap.
  • *ngIf (else/then/as) and *ngFor (trackBy/index/first/last/even/odd) both hand you local template variables that live only inside the tag that declared them.
  • [ngSwitch] is a plain binding on a container that never disappears; *ngSwitchCase/*ngSwitchDefault are the starred templates that do the appearing, matched strictly (===).
  • ngClass/ngStyle diff-and-patch for multiple classes/styles from an object; reach for native [class.x]/[style.x] when it's just one.
  • <ng-container> groups without adding a DOM node — reach for it whenever a structural directive would otherwise force an unwanted wrapper into your layout.
