Three files govern everything that happens before your code runs: package.json says what to install, angular.json says how to build, and the tsconfig family says how to compile TypeScript. Almost every "mystery build error" is really just the wrong file getting edited for the problem you have — and knowing which knob lives where turns that mystery into a five-minute fix.

The problem

Which file do you open first?

Here's the trap: all three files are JSON (or close to it), all three sit at the project root, and none of them announces what it owns. So when something needs changing — a build setting, a version, a compiler flag — the first move is a guess. Guess the wrong file and nothing obviously fails; you just spend ten minutes editing something that was never going to do anything.

A teammate says: "the build just started failing — something about a budget." Before you read any further: which of the three files do you open first — package.json, angular.json, or tsconfig.json? Hold that answer in your head; the explorer further down will tell you if you were right.

The mental model

Picture a building site: three jobs, three different people.

Nobody on site confuses the person who orders materials with the person who draws the floor plan — and yet that is exactly the mix-up "mystery build errors" usually turn out to be. You would not phone the lumber yard to change where a wall goes. Most of what feels like an Angular bug is that call, made on the wrong file.

What gets delivered to the site, and which of it is scaffolding that goes home again (devDependencies) versus timber that stays in the walls (dependencies). Which crew does which job, in what order, and what the finished house is allowed to weigh — the builder, its options, and every named configuration. The rules your work is inspected against before anyone is allowed to move in — one base ruleset, extended by a leaf for the app and a leaf for the tests.
Install → Build → Compile. package.json installs, angular.json builds, tsconfig compiles. When you don't know which file to edit, ask which of those three verbs your problem belongs to.

The mechanism

The three don't run at once — each is read at a different moment.

That ordering is what explains most of their surprising behaviour. A file consulted once, at startup behaves completely differently from one re-read on every keystroke, and step 2 below is exactly that kind of file.

In depth · package.json

package.json — what to install, and how to run it.

dependencies ship with the app — framework code that ends up in your bundles. devDependencies are build-time tools: the CLI, the compiler, the test runner. A deploy pipeline running npm ci --omit=dev skips the tooling entirely.

Ranges express intent; the lockfile guarantees reality. package-lock.json freezes the entire resolved tree, so npm ci installs the exact same thing on your machine and in CI. Deleting it to "fix" an install is how works-on-my-machine bugs are born.

In depth · tsconfig

The tsconfig family — one base, two leaves.

Three files, one inheritance chain
File Role Key contents
tsconfig.json Base ("solution") config every leaf extends strict, target, module, angularCompilerOptions.strictTemplates
tsconfig.app.json The application compilation files: main.ts · excludes *.spec.ts
tsconfig.spec.json The test compilation includes spec files · "types" adds the runner globals (describe/it)

The split exists because the two compilations need different file sets AND different ambient types: describe exists only where the test runner's type package is listed. Sweep spec files into the app build and CI greets you with "Cannot find name describe".

strictTemplates is the single highest-value flag to verify in an existing repo: it extends type-checking into templates, so a wrong-typed [input], a misspelled interpolation member, or an untyped $event fails the build instead of a user's session.

Pulling it together

Three files, one build.

What each file governs, and when it gets read
File What it governs When it's read
package.json What gets installed, and the npm command palette Whenever you run npm install or npm run <script>
angular.json Builder, options, budgets, named configurations Once, at CLI startup — never mid-session
tsconfig*.json Compiler strictness, file sets, ambient types On every compile — each save under ng serve, or once under ng build
Same three verbs, every time: install, build, compile. A "mystery" config problem almost always resolves the moment you name which of those three your problem actually is.

Questions from the back row

Before you go

Five things to remember.

  • package.json installs, angular.json builds, tsconfig compiles. Three verbs, three files — name the verb and you know the file.
  • dependencies ship, devDependencies build; ranges express intent, and the lockfile pins reality.
  • angular.json's styles/scripts arrays are GLOBAL bundles, not commands — and config edits need a server restart to take effect.
  • Budgets make bundle size a build-time failure instead of a production surprise — cross maximumError and ng build stops on purpose.
  • One base tsconfig, two leaves: the app leaf excludes specs; the spec leaf adds the test-runner types that make describe exist at all.

Drill this with the Tooling & Config challenges, or see the real files in this very repo — it is a standard CLI workspace.
