Build a complete authentication flow: a login form, JWT token storage, an HTTP interceptor that attaches the token to every request, and a route guard that protects private pages. This is a practice project, not a single-concept lesson — it puts pieces from several other lessons together into the thing they are usually assembled into, and the live demo below is the real working thing, not a mockup.

The problem

Every protected page asks the same three questions.

Strip away the framework and any app with a login is answering three questions, over and over, for every single request: who is this (identity), are they still who they say they are (a live session, not a one-time check), and are they allowed to be here (authorization). Get the wiring wrong and you end up asking the user for their password on every page, or — worse — not asking at all after the first click.

By the end of this page you will have built:

  • A signal-based AuthService that holds the current user and token
  • A login form with error feedback
  • A profile page shown only when logged in
  • An HTTP interceptor that automatically attaches Authorization: Bearer ...
  • A functional route guard (authGuard) that redirects unauthenticated users

The mental model

A JWT is a wristband, not an ID card.

You show your ID once, at the gate. Nobody looks at it again all weekend. What you carry instead is a wristband, and every bar, stage and gate checks that — quickly, without phoning anyone.

The token is the wristband. Your password is the ID, and it is presented exactly once, at login(); after that every request carries the band instead. That explains most of what follows: the band is bearer credentials, so whoever holds it is treated as you, which is why it must not be left lying around. It expires at midnight rather than lasting forever, because a stolen band should stop working soon. And the re-entry pass you left in the safe at the hotel — the refresh token — is how you get a new band without going back to the gate with your ID.

A token is a wristband, not an ID card. Whoever holds it is you, so keep it short-lived and keep it out of anywhere a script can read it.

The pieces

Three small pieces, and none of them talk to each other directly.

Everything on this page is one of three collaborators, or something built on top of them. Meet all three before any code, because the shape of the system is easier to hold in your head than any one file:

Holds the signed-in user as a signal and the token as a private field. Every other piece asks this, never each other. Reads getToken() and attaches it to every request that leaves the app. Runs whether or not the route was guarded. Reads isLoggedIn() before letting a navigation through. Runs whether or not the request that follows is intercepted.

Piece 1 of 3 · state

Where does the token actually live?

Four places a browser will let you put a token, and they differ on exactly three things that matter:

Where Readable by JavaScript? Survives refresh? Sent automatically?
localStorage Yes — any script on the page Yes, and across tabs No
sessionStorage Yes — any script on the page Yes, this tab only No
In-memory field No — gone when the page unloads No No
HttpOnly cookie No — invisible to document.cookie Yes Yes — which is why CSRF applies

Read down the second column and the production answer falls out: only the last two rows are safe from a script, and only one of those survives a refresh. That is the pairing — access token in memory, refresh token in an HttpOnly cookie — and each covers precisely the weakness of the other.

With that decided, here is the whole AuthService: the signal store, the in-memory token, and the sessionStorage-backed profile restore that lets the UI render immediately on a refresh without exposing anything readable.

Piece 2 of 3 · outbound requests

Every request needs the same header. Write it once.

Without an interceptor, every service that calls the backend would need to remember to attach the token — and the first one that forgets is a silent 401 in production. A functional interceptor sits between your code and the network exactly once, so nothing downstream has to know auth exists at all.

Piece 3 of 3 · routes

The guard that lets everyone in.

Fixed — a UrlTree, never a call to router.navigate():

A guard is a UX convenience, not a security control. It only hides the route in the browser — anyone can open devtools and call the router directly. The server is the only real gate, and it must re-check the token on every request without exception.

The last piece

The component that ties it together.

The service, interceptor and guard exist independently of any one screen. Somewhere, though, a form has to call login(), show a loading state, and send the user back where the guard intercepted them.

Now make it production-shaped · RBAC

Not every signed-in user should see everything.

Signed in and allowed here are different questions, and the second one usually has more than one answer. Role-based access control chains a second guard after the first: authGuard asks "is anyone signed in?", adminGuard asks "is it an admin?" — and both must pass.

The same signal drives the template too — try logging in as the admin account above and look for auth.isAdmin() gating the "admin access" line on the profile card. The rule to hold onto: guards and template conditionals decide what renders, never what is allowed. Your backend must still authorize every API call independently, or a curious user with devtools open gets further than a hidden button was supposed to let them.

Guarding the way out, not just the way in

Leaving a page can be dangerous too.

Every guard so far runs canActivate, on the way in to a route. CanDeactivateFn runs on the way out — the shape a "you have unsaved changes" prompt actually takes, generic enough to protect any form-editing screen in the app.

Wired up the same way as any other guard, just on the other property: canDeactivate: [unsavedChangesGuard] in the route, and readonly hasUnsavedChanges = computed(() => this.form.dirty) on the editing component. Call form.markAsPristine() after a successful save, or the guard nags on the way out of a form that was just saved. One thing it cannot stop: a browser refresh or a closed tab never reaches the router at all — that needs a separate beforeunload listener.

Enterprise pattern · silent refresh

Short-lived tokens need a second interceptor.

Enterprise apps issue access tokens that expire in minutes, not hours. When one does, every API call starts returning 401 — and the fix has to be invisible to whatever component made the call, or every screen in the app needs its own retry logic.

Enterprise pattern · multi-tab sync

One tab logs out. The others don't know — yet.

Imagine this app open in two browser tabs, both signed in. You click "Log out" in tab A. What does tab B's profile card show, right now, with no refresh? Signals live in a single JavaScript context per tab — so before reading on, guess whether tab B has any way to find out.

The honest answer is: nothing, on its own. A signal write in tab A cannot reach across to tab B — they are separate JavaScript contexts entirely. BroadcastChannel is the browser API built for exactly this: same-origin tabs can open a channel with the same name and pass messages between them instantly.

Enterprise pattern · revocation

Clearing the client is not the same as logging out.

Clearing the in-memory token stops this device from making authenticated requests. It does nothing to the refresh-token cookie sitting in the browser — if that is still valid, another device (or an attacker who stole it) can silently obtain a fresh access token. Real logout has to tell the server to revoke it.

Concept map · federated login

Most enterprise apps don't roll their own login.

They delegate to an identity provider — Google, Microsoft Entra ID, Okta, Auth0 — using the OAuth2 Authorization Code flow with PKCE (Proof Key for Code Exchange). Your Angular app never sees the user's password at all; the IdP handles it and hands back tokens.

Questions from the back row

Before you go

What you practiced.

  • A signal store for auth state — private token, read-only user signal, computed isLoggedIn / isAdmin flags that can never disagree with each other.
  • The storage decision itself — access token in memory, never in localStorage or sessionStorage; only the profile persists, for UI convenience, never the credential.
  • A functional HTTP interceptor that attaches the header exactly once, so no other service in the app has to know auth exists.
  • A functional route guard that always returns a UrlTree, never calls router.navigate(), and saves returnUrl so login can send the user back.
  • Role-based access — a second guard chained after the first, and the same computed signal driving both the route and the template.
  • CanDeactivate for unsaved changes, silent token refresh on a 401, multi-tab logout with BroadcastChannel, and real server-side revocation — the difference between a toy and something you could actually ship.
  • None of the pieces talk to each other directly. The service is the one thing every other piece asks — that is what makes each of them independently testable and replaceable.

Further extensions

  • Share the refresh Observable with shareReplay(1) so concurrent 401s send only one refresh request
  • Replace confirm() in the canDeactivate guard with a custom Angular dialog component
  • Write a test for authGuard using TestBed with a mocked AuthService
  • Add silent re-auth on app load: call /api/auth/refresh on startup and set the token before the first protected route resolves
  • Implement "logout all devices" by adding a jti (JWT ID) claim and maintaining a server-side revocation list
