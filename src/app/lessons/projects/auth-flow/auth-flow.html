Project: Auth Flow

Build a complete authentication flow: login form, JWT token storage, an HTTP interceptor that attaches the token to every request, and a route guard that protects private pages.

What you will build

  • A signal-based AuthService that holds the current user and token
  • A login form with error feedback
  • A profile page shown only when logged in
  • An HTTP interceptor that automatically attaches Authorization: Bearer ...
  • A functional route guard (authGuard) that redirects unauthenticated users

The mental model: a festival wristband

You show your ID once, at the gate. Nobody looks at it again all weekend. What you carry instead is a wristband, and every bar, stage and gate checks that — quickly, without phoning anyone.

The token is the wristband. Your password is the ID, and it is presented exactly once, at login(); after that every request carries the band instead. That explains most of what follows: the band is bearer credentials, so whoever holds it is treated as you, which is why it must not be left lying around. It expires at midnight rather than lasting forever, because a stolen band should stop working soon. And the re-entry pass you left in the safe at the hotel — the refresh token — is how you get a new band without going back to the gate with your ID.

A token is a wristband, not an ID card. Whoever holds it is you, so keep it short-lived and keep it out of anywhere a script can read it.

Architecture overview

AuthService (root service)
  currentUser: Signal<AuthUser | null>    // read-only
  isLoggedIn:  Signal<boolean>            // computed
  isAdmin:     Signal<boolean>            // computed
  login(email, password): boolean         // sets user + token
  logout(): void                          // clears both

authInterceptor (functional interceptor)
  reads AuthService.getToken()
  clones the request with Authorization header
  passes to next()

authGuard (functional CanActivateFn)
  reads AuthService.isLoggedIn()
  returns true or UrlTree('/login')

Step 1 — The AuthService signal store

Four places a browser will let you put a token, and they differ on exactly three things that matter:

Where Readable by JavaScript? Survives refresh? Sent automatically?
localStorage Yes — any script on the page Yes, and across tabs No
sessionStorage Yes — any script on the page Yes, this tab only No
In-memory field No — gone when the page unloads No No
HttpOnly cookie No — invisible to document.cookie Yes Yes — which is why CSRF applies

Read down the second column and the production answer falls out: only the last two rows are safe from a script, and only one of those survives a refresh. That is the pairing — access token in memory, refresh token in an HttpOnly cookie — and each covers precisely the weakness of the other.

Key decision: where to store the JWT

We keep the token in memory (a private class field) — not localStorage. In-memory tokens are invisible to other tabs and XSS cannot read them with document.cookie or localStorage.getItem. The downside: the user is logged out on page refresh. For production, use an HttpOnly cookie (server-set) or a short-lived access token refreshed from a secure refresh token cookie. 
@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class AuthService {{ '{' }}
  private readonly _user  = signal<AuthUser | null>(null);
  private _token: string | null = null;  // in-memory only — no localStorage

  // Public read-only signals
  readonly currentUser = this._user.asReadonly();
  readonly isLoggedIn  = computed(() => this._user() !== null);
  readonly isAdmin     = computed(() => this._user()?.role === 'admin');

  // Called only by the interceptor — never exposed to templates
  getToken() {{ '{' }} return this._token; {{ '}' }}

  login(email: string, password: string): Observable<AuthUser> {{ '{' }}
    return this.http.post<{{ '{' }} user: AuthUser; token: string {{ '}' }}>('/api/auth/login',
      {{ '{' }} email, password {{ '}' }}
    ).pipe(
      tap(res => {{ '{' }}
        this._user.set(res.user);
        this._token = res.token;
      {{ '}' }})
    );
  {{ '}' }}

  logout() {{ '{' }}
    this._user.set(null);
    this._token = null;
  {{ '}' }}
{{ '}' }}

Step 2 — The HTTP interceptor

Concept: functional interceptors

Interceptors sit between your code and the network. Every HTTP request passes through them. The auth interceptor reads the token and attaches it as a header — your services never need to know about auth. 
// auth.interceptor.ts
// HttpInterceptorFn is a plain FUNCTION — no class, no @Injectable. It gets
// the outgoing request and `next`, the rest of the chain.
export const authInterceptor: HttpInterceptorFn = (req, next) => {{ '{' }}
  // inject() works here because Angular runs interceptors inside an
  // injection context. Calling it inside a nested callback would NOT work.
  const auth  = inject(AuthService);
  const token = auth.getToken();

  // Calling next(req) hands the request to the next interceptor (or the
  // backend). Returning it unchanged is how you opt out for anonymous calls —
  // and it is what stops you sending "Bearer null" to the server.
  if (!token) return next(req);   // not logged in — pass through unchanged

  // HttpRequest is IMMUTABLE. You cannot set a header on req directly; clone()
  // returns a modified copy. Forgetting this is the #1 interceptor bug —
  // mutating req appears to work and silently changes nothing.
  const authedReq = req.clone({{ '{' }}
    // headers.set() is also immutable, returning a new HttpHeaders. set()
    // replaces an existing value; append() would add a second one.
    headers: req.headers.set('Authorization', 'Bearer ' + token)
  {{ '}' }});
  // Pass the MODIFIED request down the chain, not the original.
  return next(authedReq);
{{ '}' }};

// app.config.ts — register it:
export const appConfig: ApplicationConfig = {{ '{' }}
  providers: [
    provideHttpClient(
      // The array is ordered: interceptors run left-to-right on the way out,
      // and right-to-left on the way back with the response.
      withInterceptors([authInterceptor])
    ),
  ],
{{ '}' }};
// The payoff: not one service in the app mentions a token. Every HTTP call
// they make is authenticated, and swapping to a different scheme is a
// one-file change.

Step 3 — The route guard

Critical: always return a UrlTree, never call router.navigate()

Calling router.navigate() inside a guard and returning undefined lets the original navigation proceed. Always return a UrlTree to block AND redirect atomically. 
// auth.guard.ts
// CanActivateFn is another plain function. `state.url` is the URL the user
// was TRYING to reach — the piece that makes the round trip work.
export const authGuard: CanActivateFn = (route, state) => {{ '{' }}
  const auth   = inject(AuthService);
  const router = inject(Router);

  // true = allow the navigation, unchanged.
  if (auth.isLoggedIn()) return true;

  // Return a UrlTree — blocks AND redirects in one operation:
  // A UrlTree is a parsed URL object, and returning one means "not there,
  // HERE". The router cancels this navigation and starts the new one as a
  // single atomic decision — no flash of protected content, no race.
  return router.createUrlTree(['/login'], {{ '{' }}
    // Stash the intended destination so login can send them back. This is
    // the difference between "please sign in" and "please sign in, then find
    // your way back to that invoice yourself".
    queryParams: {{ '{' }} returnUrl: state.url {{ '}' }}    // save where they were going
  {{ '}' }});
{{ '}' }};

// In routes:
{{ '{' }}
  path: 'dashboard',
  // loadComponent = lazy: this chunk is only downloaded if the guard passes.
  loadComponent: () => import('./dashboard').then(m => m.Dashboard),
  // The guard runs BEFORE loadComponent, so an unauthenticated visitor never
  // even downloads the protected bundle.
  canActivate: [authGuard],          // guard runs before the component loads
{{ '}' }},

// In LoginComponent — redirect back after login:
// .snapshot because the value is read once, at construction. (Use the
// queryParamMap observable instead if the same component stays mounted
// across parameter changes.)
readonly returnUrl = inject(ActivatedRoute).snapshot.queryParams['returnUrl'] ?? '/dashboard';
// After successful login — closing the loop the guard opened:
this.router.navigateByUrl(this.returnUrl);
// REMEMBER: a guard is a UX feature, not a security control. It only hides
// the route in the browser. The API must re-check the token on every
// request, because anyone can edit the JavaScript that runs this guard.

Step 4 — The login component

@Component({{ '{' }}
  standalone: true,
  imports: [ReactiveFormsModule],
  template: '
    <form [formGroup]="form" (ngSubmit)="submit()">
      <!-- type="email" gives mobile users the right keyboard; type="password"
           masks the field and keeps it out of password-manager confusion. -->
      <input formControlName="email"    type="email" placeholder="Email" />
      <input formControlName="password" type="password" placeholder="Password" />
      <!-- One error slot for the whole form. Note what it will NOT say:
           "no such user" or "wrong password". Distinguishing the two tells an
           attacker which emails are registered. -->
      @if (error()) {{ '{' }}
        <p class="error">{{ '{{' }} error() {{ '}}' }}</p>
      {{ '}' }}
      <!-- Disabled while in flight, so an impatient double-click cannot fire
           two login requests. -->
      <button type="submit" [disabled]="loading()">
        <!-- The label doubles as the progress indicator — no spinner needed. -->
        {{ '{{' }} loading() ? 'Signing in...' : 'Sign In' {{ '}}' }}
      </button>
    </form>
  '
{{ '}' }})
export class LoginComponent {{ '{' }}
  private auth   = inject(AuthService);
  private router = inject(Router);
  // Where to go AFTER a successful login. The guard put this in the query
  // string when it bounced the user here, so someone who deep-linked to
  // /orders/42 lands back on /orders/42 rather than the generic home page.
  // ?? '/' covers a direct visit to /login with no returnUrl.
  readonly returnUrl = inject(ActivatedRoute).snapshot.queryParams['returnUrl'] ?? '/';

  form = new FormGroup({{ '{' }}
    email:    new FormControl('', [Validators.required, Validators.email]),
    // minLength(6) is CLIENT-side convenience only. The server must enforce
    // its own rules — anyone can POST straight past this.
    password: new FormControl('', [Validators.required, Validators.minLength(6)]),
  {{ '}' }});

  // Two pieces of local UI state. They belong to the component, not the auth
  // service: a different login screen would want to present them differently.
  readonly error   = signal('');
  readonly loading = signal(false);

  submit() {{ '{' }}
    // Guard clause. ngSubmit still fires on an invalid form (pressing Enter
    // in a field submits), so this check is what stops a pointless request.
    if (this.form.invalid) return;
    this.loading.set(true);
    // Clear any previous failure, or the old message lingers under the
    // spinner during the retry and reads as if it just failed again.
    this.error.set('');

    // The `!` non-null assertions: FormControl values are typed
    // `string | null` because reset() can null them, but the invalid check
    // above guarantees both are filled in by the time we reach this line.
    this.auth.login(this.form.value.email!, this.form.value.password!).subscribe({{ '{' }}
      // navigateByUrl takes the full URL string, including any query params
      // that were captured in returnUrl. (navigate() takes a segment array.)
      next: () => this.router.navigateByUrl(this.returnUrl),
      error: () => {{ '{' }}
        // Deliberately vague, and deliberately identical for both failure
        // modes — see the note in the template above.
        this.error.set('Invalid email or password');
        // Reset loading HERE, in the error branch only. The success branch
        // navigates away, so the component is destroyed and its loading
        // state stops mattering.
        this.loading.set(false);
      {{ '}' }},
    {{ '}' }});
  {{ '}' }}
{{ '}' }}

Step 6 — Persist the user across tab refresh (sessionStorage)

Key decision: user object vs token

Store the user profile (name, role) in sessionStorage so the UI can restore immediately on refresh — no API round-trip needed. Never store the JWT in sessionStorage (it is vulnerable to XSS). The token stays in memory only and the user re-authenticates silently via a refresh-token cookie when they revisit. 
@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class AuthService {{ '{' }}
  // On construction, attempt to restore from sessionStorage. Doing it in the
  // field initialiser means the user is already known before the first
  // render — no flash of the signed-out header on refresh.
  private readonly _user = signal<AuthUser | null>(this.loadSession());
  // A PLAIN FIELD, not a signal, and never persisted. In memory only, so a
  // successful XSS payload cannot read it out of storage — it dies with the
  // tab. This asymmetry is the whole design: profile persists, token does not.
  private _token: string | null = null;  // token stays in-memory only

  login(email: string, password: string) {{ '{' }}
    return this.http.post<AuthResponse>('/api/auth/login', {{ '{' }} email, password {{ '}' }}).pipe(
      // tap performs a side effect WITHOUT changing what flows downstream —
      // the caller still receives the AuthResponse. map() would replace it.
      tap(res => {{ '{' }}
        this._user.set(res.user);
        this._token = res.accessToken;
        // Persist the user profile — NOT the token. The profile is display
        // data (name, role); leaking it is embarrassing, leaking the token
        // hands over the account.
        sessionStorage.setItem('auth_user', JSON.stringify(res.user));
      {{ '}' }})
      // Returned un-subscribed, on purpose: the CALLER subscribes, so the
      // login component controls its own loading and error UI.
    );
  {{ '}' }}

  logout() {{ '{' }}
    // Clear all three places state lives, in the same method. Miss one and
    // you get the classic bug where the UI logs out but the next request
    // still carries a valid token.
    this._user.set(null);
    this._token = null;
    sessionStorage.removeItem('auth_user');
  {{ '}' }}

  private loadSession(): AuthUser | null {{ '{' }}
    try {{ '{' }}
      const raw = sessionStorage.getItem('auth_user');
      // getItem returns null when absent; the ternary avoids JSON.parse(null),
      // which would return null anyway but reads as an accident.
      return raw ? JSON.parse(raw) : null;
      // Any corrupted value lands here. Returning null degrades to "signed
      // out" — the safe direction to fail in an auth service.
    {{ '}' }} catch {{ '{' }} return null; {{ '}' }}
  {{ '}' }}
{{ '}' }}
// Worth stating plainly: a restored session is a UI convenience, nothing
// more. It says "this browser recently held a session", not "this user is
// authenticated". Only the server, checking a real token, can say that.

Step 7 — CanDeactivate guard for unsaved changes

Concept: CanDeactivateFn prevents accidental navigation away

When a user has unsaved form edits, ask them to confirm before navigating away. The guard gets a reference to the component, so it can call a method on it or read a signal. 
// Shared interface — components that support deactivation checks implement it.
// Without it the guard would be tied to one component class; with it, any
// component that can answer this question is compatible.
export interface CanDeactivateComponent {{ '{' }}
  hasUnsavedChanges: Signal<boolean>;
{{ '}' }}

// The guard — generic, reusable across any component.
// The type parameter is what gives you a TYPED `component` argument below;
// CanDeactivateFn passes the actual component instance being left.
export const unsavedChangesGuard: CanDeactivateFn<CanDeactivateComponent> = (component) => {{ '{' }}
  // Nothing to lose → leave silently. Prompting on a pristine form is the
  // fastest way to train users to click through your dialogs.
  if (!component.hasUnsavedChanges()) return true;
  // confirm() returns boolean, which is exactly what a guard wants: true =
  // leave, false = stay. (A real app would use a styled dialog; window.confirm
  // blocks the whole thing and cannot be themed.)
  return window.confirm('You have unsaved changes. Leave anyway?');
{{ '}' }};

// In routes:
{{ '{' }}
  path: 'profile/edit',
  component: ProfileEditComponent,
  // canDeactivate runs on the way OUT, unlike canActivate on the way in.
  canDeactivate: [unsavedChangesGuard],
{{ '}' }},

// In ProfileEditComponent:
// `implements` is what makes the compiler check this component actually
// satisfies the guard's contract.
export class ProfileEditComponent implements CanDeactivateComponent {{ '{' }}
  form = new FormGroup({{ '{' }} ... {{ '}' }});
  // `dirty` flips true as soon as the user changes any control, and back to
  // false after form.reset() or markAsPristine() — so call one of those after
  // a successful save, or the guard will nag on the way out of a saved form.
  readonly hasUnsavedChanges = computed(() => this.form.dirty);
{{ '}' }}
// Note this guard cannot stop a browser refresh or a closed tab — the router
// never sees those. For that you also need a beforeunload listener.

Step 8 — JWT refresh token interceptor (enterprise pattern)

The problem: short-lived access tokens expire

Enterprise apps use access tokens that expire in 15 minutes. When they do, every API call returns 401. The solution is a refresh token interceptor that catches the 401, silently calls /api/auth/refresh (the server reads an HttpOnly refresh token cookie automatically), gets a new access token, then retries the original request — all invisible to the component that made the call. 
// token-refresh.interceptor.ts
import {{ '{' }} inject {{ '}' }} from '@angular/core';
import {{ '{' }} HttpInterceptorFn, HttpErrorResponse, HttpClient {{ '}' }} from '@angular/common/http';
import {{ '{' }} catchError, switchMap, throwError {{ '}' }} from 'rxjs';
import {{ '{' }} AuthService {{ '}' }} from './auth.service';

export const tokenRefreshInterceptor: HttpInterceptorFn = (req, next) => {{ '{' }}
  const auth = inject(AuthService);
  const http = inject(HttpClient);

  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {{ '{' }}
      // Only intercept 401s — and never retry the refresh call itself
      if (error.status !== 401 || req.url.includes('/api/auth/refresh')) {{ '{' }}
        return throwError(() => error);
      {{ '}' }}

      // Call the refresh endpoint — browser sends the HttpOnly cookie automatically
      return http.post<{{ '{' }} accessToken: string {{ '}' }}>(
        '/api/auth/refresh', {{ '{' }}{{ '}' }}, {{ '{' }} withCredentials: true {{ '}' }}
      ).pipe(
        switchMap(({{ '{' }} accessToken {{ '}' }}) => {{ '{' }}
          auth.setToken(accessToken);       // update the in-memory token
          // Replay the original request with the new token attached:
          return next(req.clone({{ '{' }}
            headers: req.headers.set('Authorization', 'Bearer ' + accessToken),
          {{ '}' }}));
        {{ '}' }}),
        catchError((refreshError) => {{ '{' }}
          // Refresh token is expired too — force the user to log in again
          auth.logout();
          return throwError(() => refreshError);
        {{ '}' }}),
      );
    {{ '}' }}),
  );
{{ '}' }};

// Register both interceptors in app.config.ts — order matters:
// authInterceptor runs first (attaches token), tokenRefreshInterceptor retries on 401.
export const appConfig: ApplicationConfig = {{ '{' }}
  providers: [
    provideHttpClient(
      withInterceptors([authInterceptor, tokenRefreshInterceptor])
    ),
  ],
{{ '}' }};
Why switchMap, not mergeMap? switchMap cancels any previous in-flight refresh. If two requests 401 simultaneously, only one refresh call goes out. For production, share a single refresh Observable with shareReplay(1) so concurrent 401s all wait on the same call rather than firing multiple refresh requests.

Step 9 — Multi-tab sync with BroadcastChannel

Problem: logging out in one tab doesn't affect other tabs

Signals live in a single JavaScript context. Tab B has no way to know Tab A logged out — until you use the BroadcastChannel API, which sends messages between all same-origin tabs instantly. 
@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class AuthService {{ '{' }}
  private readonly _user  = signal<AuthUser | null>(this.loadSession());
  private _token: string | null = null;

  // One channel shared across all tabs on the same origin:
  private readonly channel = new BroadcastChannel('auth_events');

  constructor() {{ '{' }}
    // Listen for messages sent by OTHER tabs (not ourselves):
    this.channel.onmessage = ({{ '{' }} data {{ '}' }}: MessageEvent<string>) => {{ '{' }}
      if (data === 'logout') {{ '{' }}
        this._user.set(null);
        this._token = null;
        sessionStorage.removeItem('auth_user');
        // Optionally navigate to /login here via inject(Router)
      {{ '}' }}
    {{ '}' }};
  {{ '}' }}

  logout() {{ '{' }}
    this._user.set(null);
    this._token = null;
    sessionStorage.removeItem('auth_user');
    this.channel.postMessage('logout'); // broadcast to all other tabs
  {{ '}' }}
{{ '}' }}

Step 10 — Server-side logout (token revocation)

Client-only logout is not real logout

Clearing the in-memory token means the current device can no longer make authenticated requests. But if the refresh token cookie is still valid, an attacker (or another device) can silently obtain a new access token. Real logout tells the server to invalidate the refresh token in its database. 
// In AuthService:
logout(): Observable<void> {{ '{' }}
  return this.http
    .post<void>('/api/auth/logout', {{ '{' }}{{ '}' }}, {{ '{' }} withCredentials: true {{ '}' }})
    .pipe(
      finalize(() => {{ '{' }}
        // Always clear locally — even if the server call fails
        this._user.set(null);
        this._token = null;
        sessionStorage.removeItem('auth_user');
        this.channel.postMessage('logout');
      {{ '}' }})
    );
{{ '}' }}

// Server must:
// 1. Read the refresh token from the HttpOnly cookie
// 2. Delete (or mark revoked) that token in the DB
// 3. Clear the cookie:  Set-Cookie: refresh_token=; Max-Age=0; HttpOnly; Secure

// In the component:
logoutClick() {{ '{' }}
  this.auth.logout().subscribe(); // subscribe to trigger the HTTP call
{{ '}' }}
finalize() vs tap() — use finalize() to guarantee local state is cleared whether the server call succeeds or fails. Using tap() would skip the cleanup if the network request errors.

PKCE / OAuth2 OIDC — federated login (concept map)

Most enterprise apps don't roll their own auth

They delegate to an Identity Provider (IdP) — Google, Microsoft Azure AD, Okta, Auth0 — using the OAuth2 Authorization Code flow with PKCE. Your Angular app never sees the user's password; the IdP handles it and returns tokens. 
// High-level PKCE flow (what happens in the browser):
//
// 1. User clicks "Sign in with Google"
// 2. App generates: code_verifier (random), code_challenge = SHA-256(code_verifier)
// 3. App redirects to IdP:
//    https://accounts.google.com/o/oauth2/auth
//      ?client_id=YOUR_CLIENT_ID
//      &redirect_uri=https://yourapp.com/callback
//      &response_type=code
//      &scope=openid email profile
//      &code_challenge=BASE64URL(SHA256(verifier))
//      &code_challenge_method=S256
//
// 4. IdP authenticates the user, redirects back to /callback?code=AUTH_CODE
// 5. App exchanges the code:
//    POST https://oauth2.googleapis.com/token
//      {{ '{' }} code, code_verifier, client_id, redirect_uri, grant_type: 'authorization_code' {{ '}' }}
//    Response: {{ '{' }} access_token, id_token (JWT), refresh_token {{ '}' }}
//
// 6. App decodes the id_token JWT (claims: sub, email, name, picture)
// 7. App sends id_token to YOUR backend for verification and session creation

// Angular library: use @angular/fire for Firebase/Google, or @auth0/auth0-angular,
// or the lightweight 'angular-oauth2-oidc' package.

// angular-oauth2-oidc — minimal setup:
export const appConfig: ApplicationConfig = {{ '{' }}
  providers: [
    provideHttpClient(withInterceptors([authInterceptor])),
    importProvidersFrom(
      OAuthModule.forRoot({{ '{' }}
        resourceServer: {{ '{' }}
          allowedUrls: ['https://api.yourapp.com'],
          sendAccessToken: true,       // auto-attach token to matching URLs
        {{ '}' }},
      {{ '}' }})
    ),
  ],
{{ '}' }};

// In AppComponent.ngOnInit():
this.oauthService.configure({{ '{' }}
  issuer: 'https://accounts.google.com',
  clientId: 'YOUR_CLIENT_ID',
  redirectUri: window.location.origin + '/callback',
  scope: 'openid email profile',
  responseType: 'code',
{{ '}' }});
await this.oauthService.loadDiscoveryDocumentAndTryLogin();
// PKCE is enabled by default in auth0-angular and angular-oauth2-oidc >=13

Recap — what you practiced

  • Signal store for auth state — private token, read-only user signal, computed flags
  • SessionStorage persistence — user profile survives tab refresh; token stays in-memory
  • Functional HTTP interceptor — auto-attaches Authorization header
  • Functional route guard — returns UrlTree to redirect, saves returnUrl
  • CanDeactivate guard — prevents accidental navigation from unsaved forms
  • Role-based access — computed isAdmin() signal, admin guard, template conditionals
  • JWT refresh token interceptor — catches 401, silently refreshes, retries original request
  • BroadcastChannel multi-tab sync — logout in one tab reflects everywhere instantly
  • Server-side logout — revokes refresh token on the server with finalize() safety net
  • PKCE / OAuth2 OIDC — federated login flow with an external identity provider

Further extensions

  • Share the refresh Observable with shareReplay(1) so concurrent 401s send only one refresh request
  • Replace confirm() in the canDeactivate guard with a custom Angular dialog component
  • Write a test for authGuard using TestBed with a mocked AuthService
  • Add silent re-auth on app load: call /api/auth/refresh on startup and set the token before the first protected route resolves
  • Implement "logout all devices" by adding a jti (JWT ID) claim and maintaining a server-side revocation list
