This is the first capstone project in the curriculum: not one new concept, but everything you've already met — signals, a signal store, components, two-way binding and localStorage — wired together into one working Kanban board. The walkthrough below builds it piece by piece, in the order you'd actually write it; the live board underneath is the real thing, extended past the walkthrough with a priority filter and deadlines, and you can click around in it right now.

What you're building

A three-column board that survives a refresh.

  • A three-column Kanban board: Todo → In Progress → Done
  • Add tasks with a title, a priority, and an optional deadline
  • Move tasks between columns, or remove them, with one click each
  • Tasks persist across page reloads via localStorage
  • Live stats: total, done, and high-priority remaining

The shape of the build

Data goes down through three views. Events come back up through two.

Before any code: this is the shape every piece below has to fit. A task travels down through the component tree until it lands on TaskCard, a leaf with no state of its own — and a click on that same card travels all the way back out, through the same rings, as an event.

That is the static picture — what contains what. The one worth memorising is the moving picture: what happens between a click and the screen actually changing.

The mental model

The store is a warehouse with one loading dock.

The tasks are the stock on the shelves, and nobody is allowed to wander in and rearrange them. Everything goes through one loading dock: a short list of named operations — add, move, remove, clearDone.

That is what private readonly _tasks plus readonly tasks = this._tasks.asReadonly() buys you. Components can look at the shelves as much as they like; to change anything they have to go to the dock. When something is wrong with the board, the list of things that could have caused it is the list of methods on the store — not every template in the app.

Private writes, public reads. One signal owns the state, asReadonly() exposes it, and named methods are the only way in. Break that rule anywhere and you lose the guarantee everywhere.

Piece 3 of 6 · the only way in

Four named methods, and nothing else that writes.

Every mutation follows the same two-line shape: replace the array, then save(). That repetition is not an accident — it is the whole discipline, written out four times so it can never be forgotten once.

Which is the real argument for the loading dock. It is not about tidiness — it is that the correct way is only correct if it is the only way: 

// in a component
store.tasks().push(task);
store.tasks()[0].status = 'done';
store.tasks().sort(byDate);

// mutates in place → same reference
// → no notification → stale board
// → and nothing saved to storage
// in a component
store.add(title, priority);
store.move(id, 'done');

// inside the store:
this._tasks.update(l => [...l, task]);
this.save();

// new reference → consumers notified
// → and save() cannot be forgotten

Piece 4 of 6 · persistence

Two private methods make a refresh harmless.

Persistence lives entirely inside the store — no component knows localStorage exists. save() runs synchronously inside every mutator above; load() runs once, in the field initialiser for _tasks, before the component has even rendered.

Going further

Swap localStorage for an HTTP call, and save() stops being free.

A local write cannot fail in any way this board cares about. An HTTP write can — the network drops, the server 500s, another user's edit conflicts with this one. Port add() to a backend by swapping one line and nothing else, and the board develops a new failure mode nobody wrote a test for: 

{{ httpMutationTrapSample }}

The fix is optimistic updating: show the change immediately, as before, but track which tasks are still unconfirmed so a failed request can undo exactly the one thing it caused — and nothing else on the board.

That pattern is deliberately per-mutation and synchronous-looking — it needs to know exactly which task to roll back. A different kind of write, a bulk background sync of the whole board, wants the opposite: batch a burst of edits into one request instead of firing one per keystroke. That's the one place effect() actually is the right tool for persistence: 

{{ debouncedSyncSample }}
Two different sinks, two different strategies — neither one is "the" right way to persist. A synchronous, per-mutation write suits a local sink that cannot fail. A debounced effect() suits a bulk network sink where batching matters more than immediacy. Optimistic update with rollback suits a per-action network write where the user needs to know whether that specific action succeeded.

Going further

Everything above assumes a browser exists. What if it doesn't yet?

_tasks is initialised from this.load(), and load() reads localStorage — both in a field initializer, which runs the moment TaskStore is constructed. If this same component were ever rendered on a server (server-side rendering, or hydration), what happens the instant that field initializer runs — and would you find out from a test, or from a production error?

There is no test in this project that would catch it, because there is no server render in this project. That's exactly the trap: the code above works today, in this browser-only app, and would keep silently working right up until the day someone adds SSR to the build: 

{{ ssrTrapSample }}
localStorage does not exist in Node. A field initializer that touches it runs wherever the class is constructed — including on the server — so the failure isn't a bug you'll hit while clicking around the browser. It's one that only appears the day this component's rendering strategy changes underneath it.

Going further

Open the live board in two tabs. Add a task in each. One of them vanishes.

Every mutator above reads this._tasks() — this tab's in-memory copy — and writes the whole array back to the same storage key. Nothing ever re-reads storage after the first load, so two tabs editing the same board are really two independent copies that each believe they're the only writer: 

{{ twoTabsRaceSample }}

The fix is to notice when another tab wrote, not just when this one did:

There's a second bug hiding in the same scenario: nextId is computed once per tab, from whatever that tab loaded at construction time. Two tabs open at once can hand out the same id to two different tasks — a counter reseeded from a snapshot is not a source of unique ids across more than one writer. crypto.randomUUID() for id removes the collision entirely, because it never needs to agree with anything another tab computed.

Piece 5 of 6 · the host component

Provide the store, inject it, and let the template do the rest.

The host component's own job is small on purpose: provide the store at this level (not root), inject it, and hand data down through bindings. It never touches _tasks — it doesn't even know the field exists.

Piece 6 of 6 · the TaskCard leaf

One input, two outputs, zero state.

TaskCard receives one task and reports what was clicked. It has no internal state, no injected store, and no idea what the parent will do with an event — which is exactly what makes it reusable anywhere a Task needs to be shown.

Questions from the back row

Before you go

Six things to remember.

One store, one loading dock: every mutation is a named method that replaces the array and calls save() before it returns. If a bug touches the board's state, the list of suspects is the list of methods on TaskStore — nothing else.
  • Derive, don't duplicate. One computed split three ways beats three signals that could quietly disagree.
  • track task.id, never track $index, whenever rows can move or disappear — an index is a position, not an identity.
  • Save inside the mutator, not in an effect(). A synchronous write means nothing is lost to a refresh that lands before a scheduled effect would have run.
  • [(ngModel)] is sugar for two one-way bindings, nothing more — the same property binding and event binding you would otherwise wire up by hand.
  • Scope decides lifetime. providers: [TaskStore] on the component, not providedIn: 'root', is what makes a fresh visit start from storage rather than a stale instance.

Where to take it from here

Further extensions.

  • Add drag-and-drop between columns (HTML5 drag events — no library needed)
  • Add an urgency sort within columns: tasks due soonest appear first
