Project: Task Manager

Build a Kanban-style task manager from scratch. This walkthrough connects signals, a signal store, components, two-way binding, control flow and localStorage persistence into one working application.

What you will build

  • A three-column Kanban board: Todo → In Progress → Done
  • Add tasks with title and priority (high/medium/low)
  • Move tasks between columns
  • Tasks persist across page reloads via localStorage
  • Live stats: total, done, high-priority remaining

The mental model: a warehouse with one loading dock

The store is a warehouse. The tasks are the stock on the shelves, and nobody is allowed to wander in and rearrange them. Everything goes through one loading dock: a short list of named operations — add, move, remove, clearDone.

That is what private readonly _tasks plus readonly tasks = this._tasks.asReadonly() buys you. Components can look at the shelves as much as they like; to change anything they have to go to the dock. When something is wrong with the board, the list of things that could have caused it is the list of methods on the store — not every template in the app.

Private writes, public reads. One signal owns the state, asReadonly() exposes it, and named methods are the only way in. Break that rule anywhere and you lose the guarantee everywhere.

Architecture overview

TaskManagerPage          ← host component (injects TaskStore)
  AddTaskForm            ← child component, emits new-task event
  KanbanBoard            ← renders 3 columns from byStatus computed
    TaskCard x N         ← leaf component, input task, emits move/remove
TaskStore (service)      ← signal store: private state, computed, methods

That is the static picture — what contains what. The one worth memorising is the moving picture: what happens between a click and the screen changing.

Step 1 — Define the data model

Concept: TypeScript interfaces for domain types

Always start with your data model. Strong typing catches bugs before they reach the browser. 
// UNION TYPES, not string. Typo 'hgih' anywhere in the app and the compiler
// stops you; `string` would happily let it through to production. These also
// give you autocomplete everywhere a Priority is expected.
type Priority = 'low' | 'medium' | 'high';
type Status   = 'todo' | 'in-progress' | 'done';

interface Task {{ '{' }}
  id: number;                // stable identity — what @for tracks by
  title: string;             // the only field the user types
  priority: Priority;        // reuses the union above, so it can't drift
  status: Status;            // which Kanban column this task sits in
  createdAt: number;         // Date.now() ms timestamp, not a Date object —
                             // numbers survive JSON.stringify/parse intact,
                             // and a Date would come back as a string
{{ '}' }}

Step 2 — Sketch the signal store interface

Before writing code, sketch what the store exposes:

// Public API of TaskStore:
readonly tasks:    Signal<Task[]>       // all tasks
readonly byStatus: Signal<Record<Status, Task[]>>   // grouped for columns
readonly stats:    Signal<{{ '{' }} total, done, high {{ '}' }}>

add(title: string, priority: Priority): void
move(id: number, status: Status): void
remove(id: number): void

Step 3 — Implement the signal store

Concepts: signal(), computed(), .asReadonly(), private writes

The store owns all task state. Components read signals but never write directly. localStorage is synced on every mutation. 
// No `providedIn: 'root'` — this store is provided by the page component,
// so its state dies when you navigate away. Deliberate for a feature store.
@Injectable()
class TaskStore {{ '{' }}
  // ---- THE ONE SOURCE OF TRUTH ----
  // `private` + the underscore convention: nothing outside this class can
  // call .set() or .update() on it. `readonly` stops the field itself being
  // reassigned. The initial value comes from localStorage, so a refresh
  // restores your board.
  private readonly _tasks = signal<Task[]>(this.load());

  // ---- READ-ONLY WINDOW ONTO IT ----
  // asReadonly() returns the SAME signal with the write methods stripped from
  // its type. Zero runtime cost — it's TypeScript telling components "look,
  // don't touch". They must go through add/move/remove below.
  readonly tasks    = this._tasks.asReadonly();

  // ---- DERIVED STATE ----
  // The board needs three columns. Rather than store three arrays and keep
  // them in sync (three chances to get it wrong), derive them from the one.
  // Note the wrapping parens below. Without them JavaScript reads the braces
  // as a function body rather than an object literal, and the computed
  // returns undefined.
  readonly byStatus = computed(() => ({{ '{' }}
    todo:        this._tasks().filter(t => t.status === 'todo'),
    // Quoted because the key contains a hyphen — not a plain identifier.
    'in-progress': this._tasks().filter(t => t.status === 'in-progress'),
    done:        this._tasks().filter(t => t.status === 'done'),
  {{ '}' }}));
  // A second computed off the same source. Both recompute only when _tasks
  // actually changes, and only if something is currently reading them.
  readonly stats = computed(() => ({{ '{' }}
    total: this._tasks().length,
    done:  this._tasks().filter(t => t.status === 'done').length,
    // "High priority, still outstanding" — the number that belongs on a badge.
    high:  this._tasks().filter(t => t.priority === 'high' && t.status !== 'done').length,
  {{ '}' }}));

  // ---- MUTATIONS: the only way in ----
  add(title: string, priority: Priority) {{ '{' }}
    // Build the full object here, in the store. The caller passes intent
    // (title + priority); the store owns id, default status and timestamp.
    const task: Task = {{ '{' }} id: this.nextId++, title, priority, status: 'todo', createdAt: Date.now() {{ '}' }};
    // update() takes the current value and returns the NEXT one. The spread
    // builds a new array — a new reference — which is what makes the signal
    // notify. `l.push(task)` would mutate in place and change nothing on screen.
    this._tasks.update(l => [...l, task]);
    this.save();   // persist after every mutation, so state survives reload
  {{ '}' }}
  move(id: number, status: Status) {{ '{' }}
    // map() rebuilds the array; the ternary replaces only the matching task
    // with a spread copy carrying the new status, and returns every other
    // task untouched (same reference — so their TaskCards don't re-render).
    this._tasks.update(l => l.map(t => t.id === id ? {{ '{' }} ...t, status {{ '}' }} : t));
    this.save();
  {{ '}' }}
  remove(id: number) {{ '{' }}
    // filter() naturally returns a new array, so this one is safe by default.
    this._tasks.update(l => l.filter(t => t.id !== id));
    this.save();
  {{ '}' }}

  // ---- PERSISTENCE ----
  // Reading this._tasks() inside save() is fine: it's a plain method call,
  // not a computed, so it creates no reactive dependency.
  private save() {{ '{' }} localStorage.setItem('ng-tasks', JSON.stringify(this._tasks())); {{ '}' }}
  private load(): Task[] {{ '{' }}
    // ?? '[]' covers the first-ever visit (getItem returns null).
    try {{ '{' }} return JSON.parse(localStorage.getItem('ng-tasks') ?? '[]'); {{ '}' }}
    // The try/catch is not paranoia: one corrupted entry — a half-written
    // value, a manual edit in DevTools — would otherwise throw during field
    // initialisation and take the whole component down with it. Falling back
    // to an empty board is far better than a blank screen.
    catch {{ '{' }} return []; {{ '}' }}
  {{ '}' }}
{{ '}' }}

Which is the real argument for the loading dock. It is not about tidiness — it is that the correct way is only correct if it is the only way: 

// in a component
store.tasks().push(task);
store.tasks()[0].status = 'done';
store.tasks().sort(byDate);

// mutates in place → same reference
// → no notification → stale board
// → and nothing saved to storage
// in a component
store.add(title, priority);
store.move(id, 'done');

// inside the store:
this._tasks.update(l => [...l, task]);
this.save();

// new reference → consumers notified
// → and save() cannot be forgotten

Step 4 — Host component

Concepts: inject(), providers[], template control flow

Provide the store at the component level (not root) so the board has its own isolated state. Inject it with inject() and pass data down via template bindings. 
@Component({{ '{' }}
  standalone: true,
  // Providing it HERE, not with providedIn:'root', gives this component tree
  // its own TaskStore instance. Two boards on one page would not share state,
  // and leaving the route destroys the store with the component.
  providers: [TaskStore],
  template: '
    <div class="stat-row">
      <!-- stats() is called three times. That is fine: a computed caches its
           result, so the filtering work happens once per change, not once per
           interpolation. -->
      <span>Total: {{ '{{' }} store.stats().total {{ '}}' }}</span>
      <span>Done: {{ '{{' }} store.stats().done {{ '}}' }}</span>
      <span>High priority: {{ '{{' }} store.stats().high {{ '}}' }}</span>
    </div>

    <div class="add-form">
      <!-- [(ngModel)] is two-way: typing updates newTitle, and clearing
           newTitle in add() below empties the box on screen. -->
      <input [(ngModel)]="newTitle" placeholder="New task..." />
      <select [(ngModel)]="newPriority">...</select>
      <!-- The template calls the component method, never store.add directly,
           because add() also has to reset the form. -->
      <button (click)="add()">Add Task</button>
    </div>

    <div class="board">
      <!-- OUTER loop: the three column definitions. A static array, so
           `track col.id` is just good hygiene here. -->
      @for (col of columns; track col.id) {{ '{' }}
        <div class="column">
          <div class="col-head">
            <h3>{{ '{{' }} col.label {{ '}}' }}</h3>
            <!-- Indexing the byStatus record by the column id is what makes
                 one loop body serve all three columns. -->
            <span class="col-count">{{ '{{' }} store.byStatus()[col.id].length {{ '}}' }}</span>
          </div>
          <!-- INNER loop: the tasks in this column. `track task.id` is the
               line that matters — track by identity and moving a task keeps
               its DOM node (and any animation or focus on it). Track by
               index and Angular would recycle nodes into the wrong rows. -->
          @for (task of store.byStatus()[col.id]; track task.id) {{ '{' }}
            <!-- Data DOWN via [task]; events UP via (onMove)/(onRemove).
                 $event is whatever the child passed to emit(), so here it is
                 the {{ '{' }} id, status {{ '}' }} object and the plain number respectively. -->
            <app-task-card [task]="task"
              (onMove)="store.move($event.id, $event.status)"
              (onRemove)="store.remove($event)" />
          {{ '}' }}
        </div>
      {{ '}' }}
    </div>
  '
{{ '}' }})
export class TaskManagerPage {{ '{' }}
  // `protected` = reachable from the template, invisible to other classes.
  // inject() is the field-initialiser form; no constructor needed.
  protected readonly store = inject(TaskStore);
  // Plain fields, not signals — ngModel writes to them directly and these
  // are transient form state, not application state the store should own.
  newTitle = '';
  newPriority: Priority = 'medium';

  add() {{ '{' }}
    // The component's whole job: hand the store the user's intent...
    this.store.add(this.newTitle, this.newPriority);
    // ...and reset the input. Note it does NOT reset newPriority — someone
    // adding three high-priority tasks should not re-pick it each time.
    this.newTitle = '';
  {{ '}' }}
{{ '}' }}

Step 5 — TaskCard child component

Concepts: input(), output(), child components

TaskCard receives one task via input and emits move/remove events to the parent. It has no internal state — it's a pure presentation component. 
@Component({{ '{' }}
  selector: 'app-task-card',
  standalone: true,
  template: '
    <div class="task-card">
      <!-- task is a SIGNAL, so every read is a call: task(), then .title. -->
      <p class="task-title">{{ '{{' }} task().title {{ '}}' }}</p>
      <div class="task-meta">
        <!-- Interpolation inside a class attribute builds a dynamic class
             name: priority-high / priority-medium / priority-low, so one CSS
             rule per priority colours the badge. -->
        <span class="priority priority-{{ '{{' }} task().priority {{ '}}' }}">{{ '{{' }} task().priority {{ '}}' }}</span>
        <!-- Hide the "complete" button on tasks already done. -->
        @if (task().status !== 'done') {{ '{' }}
          <!-- emit() sends the payload to whatever the parent bound to
               (onMove). The card decides WHAT happened; it has no idea how
               the parent will store it. That ignorance is the point — this
               component is reusable anywhere. -->
          <button (click)="onMove.emit({{ '{' }} id: task().id, status: 'done' {{ '}' }})">✓</button>
        {{ '}' }}
        <button (click)="onRemove.emit(task().id)">✕</button>
      </div>
    </div>
  '
{{ '}' }})
export class TaskCard {{ '{' }}
  // .required means there is no default — forget [task] on the parent and
  // the build fails, instead of rendering an undefined card at runtime.
  task = input.required<Task>();
  // The type parameter IS the event payload contract. Emit the wrong shape
  // and TypeScript catches it here, before the parent ever sees it.
  onMove   = output<{{ '{' }} id: number; status: Status {{ '}' }}>();
  onRemove = output<number>();
  // Notice what is NOT here: no state, no store, no injected service. The
  // card renders what it is given and reports what was clicked — nothing
  // else. That is what "presentational component" means in practice, and it
  // is why this class needs no test setup beyond setInput().
{{ '}' }}

Recap — what you practiced

  • Signal store pattern — private writes, public reads, computed selectors, named mutations
  • Priority filter — a _priorityFilter signal applied inside byStatus computed
  • Deadline field — optional timestamp stored in the model; urgency computed at render time
  • clearDone() — a named store mutation, immutable update with filter()
  • Two-way binding — [(ngModel)] for text, select, and date inputs
  • @for with track — efficient list rendering in three columns
  • localStorage persistence — save on every mutation, hydrate in the store constructor

Further extensions

  • Add drag-and-drop between columns (HTML5 drag events — no library needed)
  • Add an urgency sort within columns: tasks due soonest appear first
  • Write a unit test for TaskStore.add() and clearDone()
  • Add a "tag" system: comma-separated tags stored in the model, filter by tag
