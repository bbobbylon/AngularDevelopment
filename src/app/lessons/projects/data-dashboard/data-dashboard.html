This is the biggest build in the Projects track: a sales dashboard with category, region and month-range filters, a sortable table, pagination, one-click CSV export and a live KPI row — all of it computed off one signal store. The interesting part was never the UI. It's the derivation chain underneath it: one writable signal at the root, five computed selectors hanging off it, and a guarantee that nothing on the page can ever quietly disagree with anything else on it.

The brief

One dataset, five moving parts.

  • KPI cards: total revenue, record count, average deal, top region
  • Filter by category (hardware/software/services), region, and a two-thumbed month range
  • A sortable table — click a column header to sort by it, click again to reverse it
  • Pagination, and a one-click CSV export of exactly what's filtered
  • A category-revenue bar chart, entirely signal-driven — no charting library
  • All of it computed from one signal store: zero state stored twice

The problem

Five controls. If any one of them lies, the whole page lies.

Picture the shortcut version of this dashboard: totalRevenue, pageCount, topRegion and visibleRows are each their own signal, and every filter's click handler writes to all four by hand. It's the obvious first design, and it even works — right up until you add a fifth control, forget one of the four writes, or reorder two of them in a refactor. Then the total on the KPI card and the total on the table quietly stop agreeing, and nothing in the type system will ever tell you.

Four "shortcut" signals — totalRevenue, pageCount, topRegion, visibleRows — each written by hand from every filter's click handler. Name one situation where two of them end up disagreeing. Then keep reading: the design below makes that situation impossible to reach, not just less likely.

The mental model

A dashboard is a production line, not a pile of state.

A dashboard is not a pile of state — it is one set of records with a line of machines bolted to it. Raw rows go in at one end. The first station drops the ones that fail the filters. The next works out how many pages that leaves. The next sorts and cuts out the slice you're looking at. The KPIs are a station tapped off the middle of the line, not the end.

Only the raw records are stored. Everything else is a station, and a station only runs when something upstream of it moves. That's why changing the sort is cheap and changing a filter is not — and why the pager and the KPIs never disagree with the table, since all three are cut from the same line.

Store the decisions, derive the consequences. The filters, the sort and the page number are decisions. Row counts, totals and the visible slice are consequences — and a consequence you store by hand is a consequence that will go stale.

Performance

Never compute inside the template.

A method call in a template binding runs on every CD pass. computed() runs only when its signal dependencies change. For a dashboard, that's the difference between re-formatting 1,000 rows every frame versus only when the filtered set actually changes.

Questions from the back row

Before you go

What to remember.

  • Store the decisions, derive the consequences. Eight signals were the only mutable state; every KPI, count and visible row was a computed() reading some subset of them.
  • A selector only reruns when a signal it actually reads changes. Sorting never touches filtered or summary; filtering never bypasses sorted.
  • Reset the page on every filter and sort change. The one line that's easy to forget, and the first thing that visibly breaks when you do.
  • summary reads filtered, never paginatedRows. Otherwise turning a page would look like your revenue just changed.
  • A method call in a template binding reruns on every CD pass; computed() reruns only when it has to. Same output, wildly different cost at scale.
  • CSV export is a Blob and an object URL — no server, no library — and it exports the filtered set, not just the visible page, because that's what "export" means to the person clicking it.

Further extensions

  • Load data from a real API using rxResource() — the "Going further" section above is the exact swap
