Project: Data Dashboard

Build a sales dashboard with live filtering, sorting, KPI cards and a category breakdown chart. This project focuses on reactive data patterns — computed selectors, signal stores for filter state, and performance best practices.

What you will build

  • KPI cards: total revenue, record count, average deal
  • Filter by category (hardware/software/services) and region
  • Sortable data table with click-to-sort column headers
  • Category breakdown bar chart (signal-driven, no library)
  • All computed from a signal store — zero redundant state

The mental model: a production line

A dashboard is not a pile of state — it is one set of records with a line of machines bolted to it. Raw rows go in at one end. The first station drops the ones that fail the filters. The next works out how many pages that leaves. The next sorts and cuts out the slice you are looking at. The KPIs are a station tapped off the middle of the line, not the end.

Only the raw records are stored. Everything else is a station, and a station only runs when something upstream of it moves. That is why changing the sort is cheap and changing a filter is not — and why the pager and the KPIs never disagree with the table, since all three are cut from the same line.

Store the decisions, derive the consequences. The filters, the sort and the page number are decisions. Row counts, totals and the visible slice are consequences — and a consequence you store by hand is a consequence that will go stale.

Architecture overview

SalesStore (service)

  sorted:   computed()  // reorders filtered() — reads the sort key, nothing else

Step 2 — Signal store with filter + sort state

Key pattern: all UI state in signals, all derived data in computed()

The filter and sort values are signals. The filtered/sorted list and all KPIs are computed() — they re-derive automatically whenever any input signal changes. There is no "refresh" method and no intermediate state to synchronize. 
@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class SalesStore {{ '{' }}
  // ---- SOURCES: five signals, and that is the entire mutable state ----
  // Everything else on this class is derived. If you can name the sources,
  // you can predict every pixel on the dashboard.
  private readonly _data         = signal<SaleRecord[]>([]);      // the rows
  private readonly _catFilter    = signal<'all' | Category>('all');   // 'all' = no filter
  private readonly _regionFilter = signal<'all' | Region>('all');
  private readonly _sortKey      = signal<SortKey>('amount');     // which column
  private readonly _sortDir      = signal<'asc' | 'desc'>('desc'); // biggest first

  // Filtering and sorting are SEPARATE selectors on purpose —
  // see the quiz below for what that buys you.
  readonly filtered = computed(() => {{ '{' }}
    // Read both signals into locals FIRST. Reading them inside the filter
    // callback would work, but it re-reads once per row; this reads once and
    // makes the dependency list obvious at a glance.
    const cat = this._catFilter(), reg = this._regionFilter();
    return this._data()
      // Each clause short-circuits on 'all', so "no filter" costs one
      // comparison rather than a special case elsewhere in the code.
      .filter(r => (cat === 'all' || r.category === cat)
                && (reg === 'all' || r.region === reg));
  {{ '}' }});

  readonly sorted = computed(() => {{ '{' }}
    const key = this._sortKey(), dir = this._sortDir();
    // THE SPREAD IS NOT OPTIONAL. Array.sort() sorts in place, and
    // filtered() hands back its cached array — sorting it directly would
    // mutate another computed's memoised value behind its back.
    return [...this.filtered()].sort((a, b) => {{ '{' }}
      // One comparator for both column types: localeCompare for text
      // (handles accents and casing properly), subtraction for numbers.
      // The `as` casts are needed because a[key] is a union of both.
      const cmp = typeof a[key] === 'string'
        ? (a[key] as string).localeCompare(b[key] as string)
        : (a[key] as number) - (b[key] as number);
      // Direction is applied by negating the result — one comparator, both
      // directions, no duplicated logic.
      return dir === 'asc' ? cmp : -cmp;
    {{ '}' }});
  {{ '}' }});

  readonly summary = computed(() => {{ '{' }}
    // Note: reads filtered(), NOT sorted(). The KPIs are the same numbers
    // however you order the rows, so depending on sorted() would recompute
    // them every time a user clicked a column header for nothing.
    const rows  = this.filtered();
    const total = rows.reduce((s, r) => s + r.amount, 0);
    // `|| 1` guards the empty case: filter everything out and this would
    // otherwise be 0/0 = NaN, which renders as literal "NaN" on the card.
    return {{ '{' }} total, count: rows.length, avg: Math.round(total / (rows.length || 1)) {{ '}' }};
  {{ '}' }});

  // ---- The only writers. Components call these; they never touch signals. ----
  setCatFilter(v: string)    {{ '{' }} this._catFilter.set(v as any); {{ '}' }}
  setRegionFilter(v: string) {{ '{' }} this._regionFilter.set(v as any); {{ '}' }}
  setSort(key: SortKey) {{ '{' }}
    // Clicking the column you are ALREADY sorted by flips the direction...
    if (this._sortKey() === key)
      this._sortDir.update(d => d === 'asc' ? 'desc' : 'asc');
    // ...clicking a different one switches column and resets to descending,
    // because "show me the biggest" is what people mean on a first click.
    else {{ '{' }} this._sortKey.set(key); this._sortDir.set('desc'); {{ '}' }}
  {{ '}' }}
{{ '}' }}

Step 3 — Loading real data with resource()

// For a real HTTP backend, replace the mock signal with rxResource():
@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class SalesStore {{ '{' }}
  private http = inject(HttpClient);

  // rxResource fetches once on init, exposes isLoading/error/value signals:
  private salesResource = rxResource({{ '{' }}
    // The loader runs automatically — there is no ngOnInit and no subscribe.
    // rxResource subscribes for you and unsubscribes when the store is torn
    // down, which is the whole reason to prefer it over a manual subscription.
    loader: () => this.http.get<SaleRecord[]>('/api/sales'),
  {{ '}' }});

  // Re-export the resource's own signals under friendlier names. Components
  // then depend on SalesStore, not on the fact that it uses rxResource — swap
  // the implementation later and no template changes.
  readonly isLoading = this.salesResource.isLoading;
  readonly error     = this.salesResource.error;

  readonly filtered = computed(() => {{ '{' }}
    // value() is `SaleRecord[] | undefined` — undefined during the first
    // load. `?? []` means every downstream computed can assume an array and
    // the table renders empty instead of crashing on .filter of undefined.
    const data = this.salesResource.value() ?? [];
    // ... same filter/sort logic
  {{ '}' }});
{{ '}' }}

// In template — all three states, in one chain, with no boolean flags:
@if (store.isLoading()) {{ '{' }}
  <!-- A skeleton, not a spinner: it reserves the layout so the page does not
       jump when the rows land. -->
  <div class="loading-skeleton">Loading...</div>
{{ '}' }} @else if (store.error()) {{ '{' }}
  <!-- Always give the user a way out. An error message with no retry button
       forces a full page reload for what is often a transient blip. -->
  <div class="error">Failed to load data. <button (click)="store.reload()">Retry</button></div>
{{ '}' }} @else {{ '{' }}
  <!-- Only reached when loading finished AND nothing failed, so the table
       below can read the data without any further guards. -->
{{ '}' }}

Step 4 — Performance: computed() vs. template methods

Never compute in the template — always use computed()

A method call in the template runs on every CD pass. computed() runs only when its signal dependencies change. For a dashboard, this is the difference between re-sorting 1000 rows every frame vs. only when the sort column changes. 
// ❌ Recomputes on every CD pass (can be 60x/sec under interaction):
<td>{{ '{{' }} formatCurrency(record.amount) {{ '}}' }}</td>

// ✅ Computed selector — recomputes only when filtered() changes:
readonly formattedRows = computed(() =>
  this.store.filtered().map(r => ({{ '{' }}
    ...r,
    displayAmount: new Intl.NumberFormat('en-US', {{ '{' }} style: 'currency', currency: 'USD' {{
        '}'
      }}).format(r.amount)
  {{ '}' }}))
);

// ✅ Pure pipe alternative — also memoized by Angular:
@Pipe({{ '{' }} name: 'currency', pure: true {{ '}' }})
export class CurrencyPipe implements PipeTransform {{ '{' }}
  transform(value: number): string {{ '{' }}
    return new Intl.NumberFormat('en-US', {{ '{' }} style: 'currency', currency: 'USD' {{ '}' }}).format(value);
  {{ '}' }}
{{ '}' }}

Recap — what you practiced

  • Signal store with filter/sort/page state — all UI state as signals, derived data as computed()
  • Month range filter — two range inputs bound to monthFrom/monthTo signals
  • Pagination — currentPage + totalPages computed from filtered().length; paginatedRows slices it
  • CSV export — Blob + URL.createObjectURL(), no server needed; always exports the full filtered set
  • Performance best practices — no logic in templates, computed() over methods
  • Derived chart data — bar widths from percentage signals, no chart library needed

Further extensions

  • Load data from a real API using rxResource() — replace MOCK_SALES with the HTTP call
  • Add a sparkline SVG trend chart using path data computed from monthly totals
  • Add column visibility toggles — a Set<string> signal + NgClass to show/hide columns
