The View Transitions API animates between two DOM snapshots: freeze the old pixels, let your code do whatever it wants to the DOM, then animate old into new with plain CSS. Angular wires it into the router with one function, withViewTransitions() — and this very app runs on it for every navigation, including the one that got you here. This page takes apart what a transition actually is, where Angular has to step in by hand, exactly how a shared-element morph breaks in production, and the handful of options a bare withViewTransitions() call won't show you.

The problem

A route changes. The old page just vanishes.

Here's what a Single Page App normally hides from you: a route change is not a transition, it's a demolition. Angular tears down one component tree and builds another, and it does this between one paint and the next — there is no in-between frame where both exist together. The old page doesn't fade or slide anywhere. It's simply not there any more, replaced by something else, instantly.

Which makes the whole idea of an "animated route change" stranger than it sounds. To animate something, you normally need it to still exist while the animation plays. So here's the actual puzzle every polished app with smooth page transitions has quietly solved:

You can't keep the old DOM around — Angular genuinely has to destroy it to build the new page. So what could the browser possibly hold on to, if not the DOM itself, that would let it show you where you came from while the new page settles in? Hold that guess — the whole mechanism is built around the answer.

The mental model

It isn't animating a page. It's cross-fading two photographs.

Picture the browser holding a camera. The instant before your code runs, it takes a photo of the screen exactly as it is. Then it lets your code do whatever it wants to the DOM — however violent, however instant. Once you're done, it takes a second photo. Now it has two flat, static images, and animating between two photographs is easy: no live DOM to keep in sync, no timing races, no matter how catastrophic the actual DOM surgery was in between.

That's the whole trick, and it explains the two strangest things about the API. It explains why the browser doesn't care how you changed the DOM — router navigation, a signal write, direct manipulation, it sees none of that, only the before and the after. And it explains why nothing on screen is genuinely live while a transition plays: hover a button mid-transition and nothing happens, because you're hovering a photograph of a button.

Frozen means frozen — a background <video> or an animating <canvas> stops moving too, and every click during the transition lands on a picture, not a control. That's the practical reason to keep transitions short: 150–250ms reads as instant, but a multi-second "artistic" transition is a multi-second stretch of dead clicks.
Snapshot old. Run your code. Snapshot new. Animate the bitmaps. If you remember one shape, remember that the animation never touches your real DOM — only two photographs of it, taken a moment apart.

The mechanism

One call, four steps — and a tree of pseudo-elements to style.

Here's the primitive itself. Three phases, one function call: the browser captures the old state, runs your callback and waits for the promise you return, then captures the new state and animates between the two.

While a transition runs, the page is covered by a tree of pseudo-elements you can style like any other element — and because they're pseudo-elements, not real DOM, containment is the whole story: everything nests inside ::view-transition, grouped per name.

The five pseudo-elements — and the only ones you'll ever style
Pseudo-element What it is
::view-transition root overlay covering the viewport for the duration of the transition
::view-transition-group(name) per-name container; its default animation is the position/size morph itself
::view-transition-image-pair(name) holds the two snapshots for that name together
::view-transition-old(name) the outgoing snapshot (default: fades out)
::view-transition-new(name) the incoming snapshot (default: fades in)

Cross-route morphs

The same name on both pages is the entire trick.

In practice you'll only ever type a view-transition-name in three shapes:

Anything without its own name falls in here automatically. Style the whole-page effect via ::view-transition-old(root) / ::view-transition-new(root). The exact same string on the list page and the detail page. The browser pairs the two occurrences across the navigation and morphs position, size, everything. Derived from an id at render time, e.g. 'card-' + id. Must be unique across the whole page at the moment of the snapshot — not just within your own list.

Assign the same view-transition-name to a matching element in the old and new route, and the browser pairs them — the classic "thumbnail expands into hero image" effect, no FLIP math, no animation library:

Name only one side — an element leaving on the old page, say, with nothing claiming that name on the new one — and there's no partner to morph into. It still gets its own ::view-transition-group, it just runs alone: a plain fade instead of a position/size morph. 

.card {
  overflow: hidden;
  border-radius: 16px;
}
.card__thumb {
  view-transition-name: 'item-' + id;
}

The name is on .card__thumb, which lives inside a clipped, rounded parent. The moment the transition starts, that thumbnail is lifted into the top-level overlay — a sibling of your entire app, not a child of .card any more. .card's overflow: hidden has nothing left to clip, and the image visibly balloons past the card's rounded corners for the length of the animation. 

.card {
  view-transition-name: 'item-' + id;
  overflow: hidden;
  border-radius: 16px;
}

Now the element being paired across the transition is the clipped box, not something trapped inside it. Its own radius and overflow travel with it when it's lifted out, instead of being left behind on a parent that no longer applies.

A name only works on a single box. display: contents, an inline element that wraps across two lines, or content split by a multi-column layout don't generate one — the view-transition-name is silently ignored and the element just cross-fades as part of its parent's group instead of morphing on its own.
A morphed image can look squashed mid-flight — the group animates the box, but the image inside it needs its own fit rule: ::view-transition-old(hero), ::view-transition-new(hero) { height: 100%; object-fit: cover; }. Got a dozen independently-named elements that should share one timing? Tag them with view-transition-class instead of repeating CSS per name — style="view-transition-class: card" lets you write ::view-transition-group(.card) { animation-duration: .4s } once for all of them.
A named element must generate exactly one box, and for the length of the transition it is lifted out of every ancestor's clipping, radius and transform. Style the clip on the element you name, not on its parent.

Pulling it together

So when do you still reach for the old animations DSL?

View Transitions vs @angular/animations
View Transitions API @angular/animations route animations
Setup 1 line + CSS trigger + query/group/animate DSL on the outlet
Shared-element morph built in (names) manual FLIP-style measurement, hard
Runs on compositor snapshots — old view stays visible while the new one loads live DOM — both trees exist simultaneously in the outlet
Works outside Angular yes — it's a web platform API no
Support needs a modern browser (graceful no-op elsewhere) everywhere Angular runs
The animations package is also in maintenance mode. For route-level motion, view transitions are the modern default — reach for the DSL only when you need orchestration the snapshot model genuinely can't express (per-element choreography with no route change involved, for instance).

Questions from the back row

Before you go

Six things to remember.

  • A route change is a demolition, not a transition — the API works only because it never diffs live DOM, just two flat screenshots.
  • Four steps, always: snapshot old → your callback mutates the DOM → snapshot new → animate the two bitmaps. A shared view-transition-name upgrades the last step from a cross-fade to a geometry morph.
  • Angular's part is one flag, withViewTransitions() — but a scheduled render is not a render: call appRef.tick() (or let the router do it) inside the callback, or the "after" screenshot captures the same picture as the "before" one.
  • A named element must render as a single box, and for the length of the transition it's lifted out of every ancestor's clipping, radius and transform — style the clip on the element you name, not on its parent.
  • transition.ready rejects when a transition is skipped; transition.finished always resolves. Preload lazy routes so a slow chunk doesn't freeze the old screenshot on screen.
  • Always add the reduced-motion override — 0.01ms, never none — so the transition still finishes and cleans up after itself.
