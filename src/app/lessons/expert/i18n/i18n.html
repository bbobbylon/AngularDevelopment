"Just add a translation library" is the beginner's plan, and it is wrong for Angular's own built-in system, which does not look anything up at runtime at all. This page takes the whole discipline in order: when translation actually happens, how the words themselves get marked so a machine can find them, and what the framework still owes you once they are translated — grammar, dates, money, and which way the page reads.

The problem

You've used i18n before. Angular's is not that.

Every runtime translation library works the same way: a dictionary, keyed by language, loaded as data, looked up on every render. It is reasonable to assume @angular/localize — Angular's own, built-in system — does the same thing. It does not.

Angular's built-in i18n translates at build time. The English text in your source is not looked up when the app runs — it is replaced, permanently, before the app is ever bundled. By the time a French user's browser downloads anything, there is no English left in it to find.

Before you read on: does @angular/localize ship a JSON file per language that your app loads and looks up, the way every other i18n tool you've used probably does? Or does something else happen the moment you run ng build --localize? There's a demo further down that proves the answer either way.

The mental model

Two ways to print a menu.

A restaurant serving four languages has two honest options. Print a separate menu per language — expensive up front, one for each language on the shelf, but a diner reads it instantly and nothing can go wrong at the table. Or print one menu with a QR code on every dish — cheap to print, but every single order now costs a phone, a scan, and a network request, and if the wifi is down the diner is staring at a QR code instead of a name.

That is the whole disagreement between compile-time and runtime i18n. Built-in @angular/localize is the printed menu: pay the cost once, at build time, per language, and reading is free forever after. A runtime library (ngx-translate, Transloco) is the QR code: nothing to print in advance, but every string now costs a lookup, and the lookup can fail.

And translation is only the most visible of i18n's jobs — not the only one. Four things have to be right before an app is genuinely usable in another language, and mixing them up is the source of most of the pitfalls further down this page:

Marking source strings so a machine can find and replace them — i18n, $localize. Plural and gender rules, which are not the same shape in every language — ICU plural/select. Dates, numbers and currency, which render differently per locale even with zero words translated — Intl and the locale pipes. Right-to-left scripts, which is a CSS problem wearing a translation costume — dir and logical properties.

The choice

Compile-time vs. runtime — the trade in numbers.

The interview-ready framing: built-in i18n trades deploy complexity (n bundles, per-locale routing) for perfect runtime performance. Runtime libraries trade a lookup layer for flexibility. Neither is "better" — the requirement "switch language without a reload" decides it for you.

The exam trap

Why stable ids matter — watch a translation get orphaned.

A message with no custom id already has a translation on file. You fix a small typo in its English source text and rebuild. What happens to the existing translation? The box below lets you make the edit yourself and watch the id in real time.

custom id: @@homeGreeting — stable no matter how the text changes ✓

Without a custom id, the message id is a hash of the source text (and meaning). Fix a typo → new id → every existing translation of it is orphaned, and the text falls back to the source language. Real projects pin ids on high-traffic strings.

No custom id → the id is a hash of the text. Edit the text, get a new hash, and every existing translation for the old hash is instantly orphaned — whether or not you meant to touch its meaning.

Grammar isn't binary — ICU plurals & selects.

Language Categories What that means for the translator
Japanese, Chinese 1 — other only No plural marking at all; one branch covers every count.
English 2 — one, other The two-branch grammar it's easy to assume is universal.
Polish 4 — one, few, many, other The count's last digit and whole-vs-fractional value both matter.
Arabic 6 — zero, one, two, few, many, other A dedicated dual form for exactly two of something.

The words, in code

Text in TypeScript — $localize.

Template i18n attributes can't reach strings built in code — toasts, error messages, titles set from a service. Tag them with $localize instead: the same extraction pipeline picks them up, and placeholders get names a translator can actually see.

The pipeline

Extract, translate, build — in that order, always.

Each locale is a separate application build under dist/<locale>/. Serving is a deployment concern from there: subpaths (/fr/, /es/) with server routing, or Accept-Language negotiation at the edge. SSR composes cleanly — each locale's server bundle renders its own language, with nothing to look up at request time.

The numbers

Locale data — what makes the pipes right.

Translation is only one of i18n's four jobs. Dates, numbers and currency format differently per locale — the date/number/currency pipes read registered locale data and LOCALE_ID (set automatically per localized build). See how much actually changes with not one word translated:

Separators swap (1.234.567,89 in German), currency symbols move, calendars and scripts change, and Arabic flips the reading direction — set dir="rtl" on <html> and audit your CSS with logical properties (margin-inline-start over margin-left).

LOCALE_ID picks the grammar — separators, symbol position, plural rules. DEFAULT_CURRENCY_CODE picks the currency. They are two different facts about a user, and Angular refuses to guess one from the other.

Questions from the back row

Before you go

Six things to remember.

  • Built-in i18n is not a runtime lookup. Translation happens once, at build time, and the result is baked into one optimized bundle per locale — @angular/localize's own loadTranslations() is the one part of it that does look things up live.
  • Nothing works until ng add @angular/localize has run. Skip it and you get two different failures: a compile error from a template i18n, or a runtime ReferenceError from $localize.
  • Message anatomy is meaning|description@@id — pin custom ids on high-traffic strings, because an id with no pin is a hash of the text, and a typo fix silently orphans every translation of it.
  • i18n-<attr> only translates a literal attribute string. A bound or interpolated value has to be translated in TypeScript with $localize first.
  • ICU plural/select moves language grammar into the translation, where it belongs — English's two branches are not a universal shape; Polish needs four, Arabic six.
  • LOCALE_ID and DEFAULT_CURRENCY_CODE are different facts: one picks grammar, the other picks currency, and setting one does not set the other.
