Once observables underpin your data flow, two skills separate senior code from junior code: combining streams declaratively, and choosing the right flattening strategy for nested async work. This page has live laboratories for both, then covers subjects, hot/cold sharing, error recovery, custom operators, and where signals take over.

Wire a save button to mergeMap out of habit instead of thinking about it, and a user double-clicking on slow wifi doesn't cost you a UI glitch — it costs your API real, duplicate writes. Here's the bill. 

save$.pipe(
  mergeMap(() => http.post('/orders', order))
);
// 3 clicks → 3 concurrent POSTs, no cancellation
save$.pipe(
  exhaustMap(() => http.post('/orders', order))
);
// 3 clicks → 1 POST; clicks 2 and 3 are ignored entirely

The mechanism

Here's exactly why — mergeMap has no concept of "a save is already running." It just subscribes to every inner observable it's handed, the instant it's handed one.

Two clicks. Two real writes racing toward your database. mergeMap never asked whether the first one was already running — deciding that was never its job.

The problem

A save() call hits your API. The button is wired to (click) → an RxJS pipeline → http.post(...). Someone double-clicks it fast, the way people actually do on slow wifi.

The mental model

A stream is a camera feed. This lesson is the control room.

Every observable so far in this course has been one camera pointed at one thing. Advanced RxJS is what happens once there is more than one feed running at the same time, and you need a control room to make sense of them: several feeds coming in, monitors that hold onto old frames or don't, one shared recording so you aren't paying for four cameras pointed at the same shot, and a video wall that has to decide, moment by moment, what the audience actually sees.

The Subject variants below are just different kinds of monitor — the question is always "does it remember anything from before I tuned in, and how much?" Hot vs cold is whether turning a monitor on starts a private screening or joins a broadcast already running, and shareReplay is the building's shared antenna: one dish instead of one private screening per apartment. The combination operators are the video-wall director, choosing what the wall shows once several feeds are live together.

Subject variant = which kind of monitor. Hot vs cold = does subscribing START the show or JOIN it. shareReplay = one shared antenna instead of N private screenings of the same broadcast.

The video wall, nested

Higher-order observables — the flattening four.

A map that returns an observable gives you an observable of observables — the flattening operators subscribe to those inner streams for you, and differ only in their concurrency policy. If the four-receptionists picture from RxJS: Core Operators is fresh, this is the same four policies; this lab is where you watch them fight over real timers instead of imagining them.

Operator When a new outer value arrives while an inner is running… Canonical use
switchMap cancel the running inner, switch to the new one typeahead search, route param → detail fetch (only the latest matters)
mergeMap run them in parallel (optional concurrency cap) independent side-by-side requests, fire-and-forget logging
concatMap queue it — strict order, one at a time writes that must not interleave (audit trails, sequential saves)
exhaustMap ignore it until the running inner completes submit buttons, login — swallow double-clicks

Pick a strategy, then hammer "fire request" a few times fast. Every request is a real 1.5-second timer; the log shows what each policy does with the overlap:

switchMap: earlier requests report "cancelled" — only the last response lands. mergeMap: all responses land, ordered by completion. concatMap: all land, in click order, 1.5s apart — later ones wait in the queue. exhaustMap: clicks during a flight are ignored so those requests never even start.

Set the lab to switchMap, fire twice within a second, and watch for the ✗ cancelled mid-flight line. That line is finalize proving the first request's subscription really was torn down — not just a log message pretending it was.

Different kinds of monitor

Subject varieties — what a late arrival gets to see.

Back to the control room: every Subject variant answers one question differently — what does a monitor show the instant someone turns it on?

Type What a NEW subscriber receives Typical job
Subject only values emitted after subscribing event bus, imperative → reactive bridge
BehaviorSubject(seed) the current value immediately, then updates state holders (pre-signals); requires an initial value; has .value
ReplaySubject(n) the last n values, even from before subscribing late subscribers needing history (e.g. last route event)
AsyncSubject only the final value, only on complete rare — "result of a computation" semantics
The table above describes what a new subscriber sees — not what happens once a Subject has already errored or completed. Once either happens, next() silently does nothing, forever, and any new subscriber receives that same terminal notification immediately instead of ever joining the stream — a Subject cannot be restarted. Never route a request's error into a long-lived Subject (map it to a value first, or catchError it before .next() ever runs), and never complete() a shared Subject from a component's ngOnDestroy — it belongs to the service that created it, not to whichever component happened to unsubscribe last. Exam framing: "the event bus stopped delivering after one failed request — why, and what would you change?"

One antenna, not one dish per apartment

Hot vs cold — and sharing one execution with shareReplay.

A cold observable (like every HttpClient call) runs its producer per subscriber — a private screening each time, projector and all. Two async pipes on the same stream means two HTTP requests, in parallel, for identical data.

When a feed cuts out

Error handling & retries — and where you catch matters.

retry isn't unconditional. {{ retryIdempotencyRule }} The conditional delay above is how you encode that: a 4xx re-throws immediately instead of burning three backoff cycles on a request that will never succeed.

The typeahead example above hides a mistake nearly everyone makes once: putting catchError on the wrong stream. Same error, two placements, two completely different outcomes:

retry before catchError, always. Swap the order and there is nothing left for retry to retry — catchError will already have ended the stream with its fallback.
  • Errors travel the pipe like values — the first operator that handles one decides the stream's fate.
  • An error unsubscribes the source. Handle errors on the inner stream (inside the flattening operator) — catch on the outer stream instead, and one bad response ends everything downstream.
  • finalize runs on complete, error and unsubscribe — the right home for "loading = false".

Where signals take over.

Concern Reach for
synchronous state + derivations signals: signal/computed — no subscription management at all
events over time: debounce, cancellation, races, retries RxJS — signals have no time axis
observable → template toSignal(obs$, { initialValue }) (or the async pipe)
signal → observable world (e.g. debounce a signal) toObservable(sig), pipe, then toSignal back

Where this bites in code review

Common mistakes.

combineLatest seems silent It emits nothing until every source has emitted once. Seed slow inputs with startWith(initial).
forkJoin never fires It needs every source to complete. HTTP calls complete; interval/fromEvent don't — cap them with take(n) or use combineLatest.
One failed request kills forkJoin A single error rejects the whole join. catchError(() => of(null)) per inner stream to keep the others.
Re-running an HTTP call per subscriber Each subscribe re-fires a cold stream. Share with shareReplay({{ '{' }} bufferSize: 1, refCount: true {{ '}' }}).
catchError after retry but expecting more retries Once catchError swaps in a fallback the stream completes — order operators as retry → catchError.
Nesting subscribe inside subscribe Use a flattening operator (switchMap/mergeMap/…) instead — it manages the inner subscription for you.

Questions from the back row

Before you go

Recap — what to carry out of the control room.

  • A Subject variant is a kind of monitor — what does it show a subscriber who just tuned in? combineLatest/forkJoin/withLatestFrom differ in exactly what they wait for before they'll show anything at all.
  • The flattening four differ only in concurrency policy: cancel (switchMap), parallel (mergeMap), queue (concatMap), ignore (exhaustMap) — reads want switchMap, writes want exhaustMap.
  • Handle errors on the inner stream, not the outer one — an error there unsubscribes everything downstream; order retry before catchError; finalize for cleanup that must always run.
  • Share cold streams with shareReplay({{ '{' }} bufferSize: 1, refCount: true {{ '}' }}) — one antenna, not one dish per subscriber.
  • Signals own synchronous state; RxJS owns time. toSignal/toObservable are the bridge between them.
