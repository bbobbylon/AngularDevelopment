Change detection is the machinery that keeps the DOM agreeing with your component state. Almost everything confusing about it comes from three questions being answered by three different mechanisms, and people trying to answer all three with one idea. This page takes them one at a time — when a pass is scheduled, which views it refreshes, and what one refresh actually does — with live counters proving each answer.

The problem

Your data changed. Who tells the screen?

Here is the thing nobody says out loud: changing a value in JavaScript does nothing to a web page. Assigning this.total = 42 updates one slot in memory. The browser is not watching that slot. Nothing in the language will call you back about it. Somewhere between your assignment and a repainted pixel, something has to go and look.

That "going and looking" is change detection. And the moment you accept that it is a deliberate act rather than magic, the questions that actually matter show up on their own:

  • What makes Angular decide to go and look at all? (scheduling)
  • Once it starts looking, how much does it look at? (strategy)
  • What does "looking at one component" actually consist of? (the check)
Two counters on a page. One is a signal; you call set(). The other is a plain field; you increment it inside a setTimeout. Both values genuinely change in memory. What do you think each one shows on screen a second later — and can you say why before you scroll? There is a live version further down to check yourself against.

The mental model

Angular is a proofreader with a photocopy.

Picture a proofreader holding a photocopy of yesterday's page. Their job is not to re-typeset the page. It is to go line by line, compare each line against the copy, and re-print only the lines that differ. A page where nothing changed still costs a full read-through — but zero printing.

That is a change-detection pass, almost exactly. The photocopy is a plain array of the values every binding had last time. The read-through is the traversal. And the reason a mutated array "doesn't render" is that the proofreader is comparing the page reference, not the words: same sheet of paper, so nothing to re-print, no matter what you scribbled on it.

Mark, schedule, walk, compare. Every change-detection question is really a question about which of those four steps went missing. A mutation skips mark. A missing notify skips schedule. OnPush prunes the walk. And === is the whole of compare.

The mechanism

One check is one function call.

Your template is not interpreted at runtime. It is compiled, ahead of time, into an ordinary function that runs in two modes: build the nodes once, then compare the bindings every time. Here is that function for a template as small as <p>Count: {{ '{{' }} count() {{ '}}' }}</p>.

So "change detection is slow" is nearly always a misdiagnosis. The traversal is a flat array walk with a reference compare per slot. What is slow is what you put inside the bindings — because line 9 re-runs ctx.count() on every check, and if that expression sorts a list, it sorts the list every time.

One array per component instance, holding its DOM nodes, its state, and the previous value of every binding. Slots are found by index, never by query. One entry in that array. Checking a binding means comparing the fresh value against the slot with === and writing to the DOM only on a difference. The RenderFlags.Create branch. Builds the DOM nodes and allots the slots. Never runs again for that view. The RenderFlags.Update branch. This — and only this — is what people mean by "a component was checked".
Never call an expensive function from a template binding. {{ '{{' }} expensiveSort(list) {{ '}}' }} runs on every check of that view, including every no-op pass. Wrap it in a computed() (or a pure pipe) so the work re-runs only when its inputs change.

Question 1 of 3 · scheduling

When does Angular decide to look?

zone.js monkey-patched every async API in the browser. When anything finished — a click, a timeout, a fetch, a resolved promise — it fired a full application tick.

Reliable, and blunt: a third-party library polling on an interval could tick your entire component tree several times a second while nothing on screen was changing.

Nothing is patched. A pass is scheduled only when something explicitly says so — a signal write, a template event listener, a markForCheck(), an input write.

The notifications are coalesced, so five signal writes in one function still produce exactly one pass.

The catch is the one that bites people migrating: in a zoneless app, code that changes state without notifying simply never renders. Under zones the same code got away with it, because something unrelated ticked a moment later and swept the change up.

Question 2 of 3 · strategy

How much of the tree does it look at?

A pass starts at the root and travels inward through every ancestor to reach a leaf. That is the part worth picturing: a component is not visited directly, it is arrived at, and every view on the path in gets a decision made about it.

The four things — and only these four — that get an OnPush view checked
Condition What that looks like in practice
An input reference changed The parent binding passed a new object, not a mutated one
An event fired inside the component A button click anywhere in the OnPush subtree
cdr.markForCheck() was called An async pipe emission, or your own call after an external mutation
A signal the template reads changed count.set(1), from anywhere at all — even a shared service

Every click re-checks the Default child — its counter climbs even on no-ops. The OnPush child's counter moves only when its input actually changes: the pass reaches it, finds no dirty flag and no new reference, and prunes. Question 3 of 3 · reactivity

Who gets flagged as dirty?

This is the question signals answer, and they answer it better than anything before them. A template that reads a signal is silently recorded as one of its consumers. So a write does not have to guess where to start looking — it already knows exactly which views care.

The escape hatch

Or leave the tree completely.

OnPush says "skip me unless something changed". detach() says "do not visit me at all" — the view stops being part of any traversal, and even a changed input renders nothing. You have taken over rendering, and you own consistency from then on.

Live — cdr.detach() against the exact same input binding

Detach, then press the input button a few times, then reattach. The value that appears is the current one — the binding was always up to date in memory; only the rendering was switched off. detach() is the nuclear option for genuinely hot components (tickers, canvas overlays) that you re-render yourself on your own cadence.

markForCheck() goes up and runs later. detectChanges() goes down and runs now. Nearly every misuse of either one is a swap of those two axes.

The famous error

NG0100 is not a bug. It's a smoke alarm.

In development, Angular runs every pass twice and compares the results. If a binding produced a different value the second time, then something changed state during the pass — and the pass it was changed during had already finished with it.

Fixes, best first:

  1. Move the write to its owner. Data flows down, events flow up. If the child needs the parent's title changed, it should emit and let the parent change it.
  2. Make the state a signal. A signal write during a pass schedules the next one instead of corrupting the current one — the framework absorbs the ordering problem for you.
  3. Defer past the pass with afterNextRender(). This works, and it is last for a reason: it silences the alarm without moving the fire.

Pulling it together

Three questions, three layers.

Layer The question it answers How the answer evolved
Scheduling When does a pass run? zone.js (after any async) → zoneless (only on explicit notification)
Strategy Which subtrees get refreshed? Default (always) → OnPush (dirty or changed-input only)
Reactivity Who gets marked dirty? manual (markForCheck, events) → signals (automatic, per view)
Signals + OnPush + zoneless is the modern stack: explicit scheduling, pruned traversal, per-view marking. Each layer composes with the others, and each has its own lesson in this app.

Angular cannot know your handler changed nothing: every template listener marks its view and notifies the scheduler before your code runs. No-op passes are a fact of life, which is the whole argument for keeping bindings cheap.

Questions from the back row

Before you go

Five things to remember.

  • Nothing in JavaScript tells the screen a value changed. Change detection is a deliberate act, and every question about it is really "what triggered the act, and how far did it reach?"
  • A check is the compiled update function running: === per binding slot, and a DOM write only where the slots differ. The walk is cheap; your bindings are the cost.
  • Default checks always. OnPush needs one of four things — a changed input reference, an event inside it, a markForCheck(), or a signal it reads — and prunes the subtree otherwise.
  • A signal write does two jobs: it marks exactly the views that read it, and it schedules the pass. A plain mutation does neither, which is the whole of "mutation doesn't render".
  • markForCheck() is up-and-later; detectChanges() is down-and-now. NG0100 means state moved mid-pass — fix the data flow rather than suppressing the error.
