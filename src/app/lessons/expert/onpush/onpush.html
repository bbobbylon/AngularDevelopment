ChangeDetectionStrategy.OnPush is a contract you sign with the framework: "this component renders purely from its inputs, its own events, and the signals/observables it reads — so skip it otherwise." Angular holds you to it, literally. This page proves the skip with five live counters, walks the exact dirty-marking mechanics, and shows every classic way the contract gets broken in production.

The problem

Default checks everything, always. What if you don't want that?

Default change detection is thorough and indiscriminate: every pass walks every view, whether or not that view's own data had anything to do with why the pass started. Fine for a small tree. Expensive for a dashboard with hundreds of rows, most of which never change on any given click. OnPush is Angular's answer — but it isn't a faster version of the same check. It's a promise that lets Angular skip a view outright.

A parent holds two signals: value, fed into an OnPush child's [input], and pokes, read only by the parent's own template — never passed anywhere. You click a button that updates pokes alone. Before you scroll: does the OnPush child's self-check counter move?

The mental model

A smoke detector, not a night patrol.

Picture Default change detection as a night patrol: someone walks every hallway, every round, whether or not anything is actually wrong. OnPush is a smoke detector instead — it does nothing, ever, until one of a short, fixed list of alarms actually trips it. No alarm, no matter how real the change behind it, means the detector stays silent and nobody comes.

That list of alarms is exactly five items long, not "anything that changed" — and almost every OnPush bug in a real codebase is a change that genuinely happened but never tripped one of the five.

Five ways in, one way to sleep. A changed input reference, its own template event, an async-pipe emission, a signal it reads, or a manual mark — those are the five alarms. Anything else, and the view sleeps through it, no matter how real the change was.

The mechanism

What re-checks an OnPush view — the complete list.

Trigger Mechanism Scope
Input reference change the template binding writes a new value → the view is marked dirty this view (+ ancestors get "traverse me" flags)
Event bound in its template every (click)-style listener wraps the handler in markViewDirty() this view up to the root
async pipe emission AsyncPipe literally calls ChangeDetectorRef.markForCheck() on every value this view up to the root
Signal read in the template changed the view is a reactive consumer of the signal → marked dirty directly only the views that read it
Manual: markForCheck() / detectChanges() you tell Angular yourself next pass / synchronously now

Everything else — a setTimeout, a promise resolution, a WebSocket message, a third-party callback that mutates a field — changes your data but tells nobody. Under OnPush the view stays exactly as it was.

Treat every input as immutable. Not a style preference — the mechanism itself only looks at whether the reference changed, never what's inside it. Replace objects and arrays; never mutate them.

Under the hood

Marking walks up. Checking walks down.

markForCheck() goes up and runs later. detectChanges() goes down and runs now. Nearly every misuse of either one is a swap of those two axes.
markForCheck() detectChanges()
What it does flags the view (+ ancestor path) dirty; refresh happens on the next scheduled pass synchronously runs change detection on this view and its children, right now
Schedules a pass? yes (in a zoneless app this is what triggers the tick) no scheduling — it IS the check
Typical use async callback updated state outside Angular's knowledge forcing a synchronous re-render (tests, imperative DOM measurement flows)
Risk none notable — it's the polite one NG0100 (ExpressionChanged…) when called mid-pass; easy to overuse

Two more ways the contract quietly breaks

Impure reads, and subscriptions that forget to announce.

Two more pitfalls that show up in interviews:

  • Third-party libs (charts, maps) mutating shared state in their own callbacks — wrap the state write in a signal or call markForCheck().
  • OnPush on the container, Default on a child. Skipping the container prunes the child too — the child's own strategy never even gets consulted if the parent subtree is pruned first.

Testing

detectChanges() doesn't rescue a test either.

This is the first wall almost everyone hits after adopting OnPush, and it looks exactly like a framework bug: the test sets component.title = 'Updated', calls fixture.detectChanges(), and the DOM is unchanged — because nothing in that sequence tripped any of the five triggers from the table above. A direct field assignment on the instance isn't an input write, isn't a template event, and isn't a signal — the view was never marked dirty, so there is nothing for detectChanges() to refresh.

If a real user action would have gone through one of the other four triggers (an input, an event, a signal, the async pipe), the test shouldn't need this escape hatch at all — reach for it deliberately, not as a reflex to make a red test go green.

Questions from the back row

Before you go

Five things to remember.

  • OnPush re-checks on exactly five things: input reference change, own template events, async-pipe emissions, signal reads, and manual marking. Everything else = stale view.
  • Treat inputs as immutable — replace objects/arrays, never mutate.
  • Marking walks up (view + ancestor path), checking walks down (root → leaves, pruning clean OnPush subtrees).
  • markForCheck() flags for the next pass; detectChanges() checks synchronously — know which one a question is really asking about.
  • Signals subsume the whole pattern: writes mark precisely the reading views, which is the bridge to zoneless scheduling — this app itself runs zoneless.
