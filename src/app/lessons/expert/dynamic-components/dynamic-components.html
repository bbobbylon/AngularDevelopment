Dynamic components let you decide which component to render at runtime — not at write time. Angular gives you two APIs: the declarative NgComponentOutlet directive (template-driven) and the imperative ViewContainerRef.createComponent() (TypeScript-driven). They power dashboards, CMS block renderers, modal systems, and toast overlays.

Most of the time a template already knows what it's showing — a <user-card>, a <price-tag>, written by hand, once. But sometimes the component itself is a piece of data: a CMS returns a block type string, a notification carries a severity, a plugin registers a widget your app has never heard of at build time. You can't write an @if/@else if chain for components that don't exist yet.

Scroll down to Demo 1 and swap between Info, Warning and Success a few times before reading on. Notice: nothing in Angular's template says which component renders — that decision is made by a plain value, at runtime, and the template just points at it.

Think of NgComponentOutlet as a furnished rental: you tell the leasing office who's moving in, and they handle move-in, move-out, and cleanup automatically — you never get a key of your own. createComponent() is building your own house instead — put it in any container, even document.body — but nobody manages it for you. You wire the utilities (inputs) yourself, you answer the door yourself (subscribe to outputs), and you're the one who has to remember to lock up (destroy()) when you leave, or the bills — leaked subscriptions, a DOM node nobody's tracking — keep running.

Bind the class, own nothing. Call createComponent(), own everything — cleanup included.

Where does the create call actually go?

Every demo on this page calls createComponent() from a click handler — deliberately, because that's always safe. The question learners actually hit in real code is what happens from a lifecycle hook instead:

ngAfterViewInit is the one to watch. Angular is still mid-way through checking this view's children when that hook runs — creating a component there changes the very tree Angular is checking, which is exactly the shape of bug NG0100 exists to catch. ngOnInit and any event handler run outside a change-detection pass entirely, so they're both safe; afterNextRender() is the sanctioned fix on the rare occasion the creation genuinely has to happen after the view is built (it needs a real, painted DOM node to measure, say).

Under the hood — views, hosts and attachment

  • No factories anymore: since Ivy, the component class is the factory — createComponent() reads the compiled definition off the class (ɵcmp). The old ComponentFactoryResolver/entryComponents ceremony is dead; any standalone class reference works.
  • Environment vs element injector: environmentInjector supplies app/route-level services; the optional elementInjector layers per-instance tokens (dialog data) on top — the resolution walk from the DI lesson applies unchanged.

NgComponentOutlet vs createComponent()

NgComponentOutlet ViewContainerRef.createComponent()
Style declarative, in the template imperative, in TypeScript
Inputs [ngComponentOutletInputs] object ref.setInput() per input
Outputs not bindable — a real limitation ref.instance.someOutput.subscribe()
Lifecycle/cleanup automatic (binding change / host destroyed) yours: ref.destroy() / vcr.clear()
Position control where the ng-container sits any container, any index, even document.body
Best for CMS blocks, pluggable widgets, tab bodies modals, toasts, overlays, drag-drop insertion

ComponentRef API cheatsheet

API What it does
ref.setInput('name', value) Trigger-safe input update — validates the name, marks the view dirty, drives signal inputs & ngOnChanges
ref.instance The component class instance (call methods, subscribe outputs)
ref.location.nativeElement The host DOM element
ref.hostView The view — what gets attached to / detached from CD
ref.changeDetectorRef Per-component CD control (markForCheck etc.)
ref.onDestroy(fn) / ref.destroy() Cleanup hook / teardown + detach from the view tree
vcr.clear(), vcr.remove(i), vcr.move(view, i) Container-level management of created views
appRef.attachView(ref.hostView) Attach a root-level view (e.g. toast overlay on body)
Prefer NgComponentOutlet when you can. It handles inputs, the injector, and lifecycle cleanly in the template. Reach for createComponent() only when you need the ComponentRef handle — modal services, programmatic toasts, output subscriptions, or attaching to document.body.
Always destroy what you create. Leaked ComponentRefs hold their whole subtree in memory and keep subscriptions alive. Call ref.destroy() or vcr.clear() in ngOnDestroy or after the user closes the overlay — and remember output subscriptions die with the ref, so destroy order matters if you need the final event.

Key takeaways

  • NgComponentOutlet mounts a class declaratively — swap the class to change components (destroy+create), change the inputs object to update in place.
  • createComponent() returns a ComponentRef: setInput for inputs, instance.output.subscribe for outputs, destroy() when done.
  • Views must live in a CD tree — ViewContainerRef attaches automatically; manual creation needs attachView.
  • Dynamic import() + a class signal gives you code-split dynamic components; custom element injectors deliver dialog data.
  • Cleanup is yours in the imperative world — leaked refs are the classic production bug.
