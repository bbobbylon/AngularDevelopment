Angular's injector isn't one container — it's two cooperating trees, and every advanced DI feature is a way of steering inject() through them. This page proves the resolution rules with live components wired to real instances, then covers everything built on top: multi providers, view-scoped providers, where inject() is legal, tree-shakable tokens, authoring your own provideX() functions — and the one cycle forwardRef flatly cannot fix.

The problem

You call inject(Beacon). Which one do you get?

Ask a beginner lesson and the answer is easy: there's one Beacon, provided once, and inject(Beacon) finds it. But a real app provides the same service at a dozen different levels — a component here, a lazy route there, root as the fallback everywhere else. The moment that's true, "which instance do I get?" stops having one answer and starts depending on exactly where you're standing when you ask, and exactly which words you put after the comma.

That's the whole of advanced DI. Not new concepts so much as new ways to answer one question more precisely: where, exactly, should this search start and stop?

Below, a lesson component provides one Beacon. Two children both call inject(Beacon) — one of them also provides its own. Do the two children get the same instance? Does your answer change for the one with its own provider? There's a live proof a few paragraphs down to check yourself against.

The mental model

An injector is a building inside a city.

Picture the component tree as a building: one apartment per component, stacked the way your templates nest. Need a service? You don't build one — you go looking for a copy someone already has. First you check your own apartment. Not there? You knock on the door above you, then the one above that, all the way up the stairwell — that's the element injector chain, and it mirrors the DOM exactly.

Reach the roof with nothing to show for it, and you don't give up — you step outside, into the environment injector chain: the local borough office (your lazy route's own providers, if you're inside one), then city hall (root — where almost everything ends up), then, in the rarest case, the national government (platform, shared by every Angular app sharing the page). NullInjectorError means you knocked on every door in the building and asked every office in the city, and nobody had it.

Your own room, then the stairwell, then the street. self only checks your own room. The default walk checks your room, then knocks up the stairwell — every DOM ancestor's element injector — and only steps into the street (the environment chain) once the whole building has been asked. skipSelf starts one door up. host refuses to leave the stairwell at all.

The proof

Four words that steer the exact same walk.

optional, self, skipSelf and host don't add new behaviour to the injector — they all just answer "where does the walk from the last section start, and what happens if it comes up empty?" differently. Four short cards, then three real components proving each answer against real instance ids.

Extension points

One token, many contributors.

Every provider you've seen so far replaces whatever was registered for its token before it. multi: true is the one exception: it turns a token into a collection instead of a single value, and every provider that registers with it adds to the array rather than overwriting it.

This is the extension-point pattern the framework itself is built on: NG_VALIDATORS (every validator on a control), NG_VALUE_ACCESSOR, app initializers, and router interceptors all collect contributions exactly this way. Forgetting multi: true on one registration doesn't error — it silently replaces the whole collection with just that one entry, which is what makes it a genuinely nasty production bug: nothing throws, something you registered just quietly stops existing.

Encapsulation

Not every provider should be public.

providers and viewProviders look almost identical and answer completely different questions. Both sit on the same component. The only difference is who is allowed to see them — and that difference only shows up for content someone else projects into your component.

Reach for viewProviders when a service is an internal implementation detail — state your component manages for itself — that a consumer's projected content must not be able to accidentally inject and start depending on. It's encapsulation, spelled in DI instead of in TypeScript's private.

The rule everyone hits eventually

inject() only works for a moment, not forever.

inject() isn't gated by which FILE or FUNCTION you're in — it's gated by timing. There's a brief window, while Angular is actively constructing something, called an injection context, and inject() only works inside it.

Field initializers, constructors, provider factories, and router guards/resolvers/interceptors all run inside a context by design — that's the whole list. Anywhere else — a click handler, a subscribe callback, a setTimeout — needs the bridge: capture Injector while a context is still open, then use runInInjectionContext later.

Scope & lifetime

Where a token lives decides how many copies exist.

Three scopes for providedIn — and how many instances each one actually makes
providedIn Instances Lives at
'root' exactly one the app's root environment injector — the default choice, and tree-shaken away if nothing injects it
'platform' one per page shared across every Angular app running on that page — genuinely rare
'any' one per environment injector that asks root gets its own; each lazy route's environment injector gets a separate one of its own
A service can silently duplicate itself. Give Metrics providedIn: 'root' and also list it in a lazy route's own providers array, and components under that route get a second, disconnected instance — not the root one. Nothing errors. The tell is state that resets every time you navigate into the feature. The usual fix is simply deleting the redundant providers entry; providedIn: 'root' already registered it everywhere.

The modern payoff

This is why forRoot() went away.

Every function you've called on this page — provideRouter, provideHttpClient, provideAnimations — is the same shape underneath: a plain function that builds a provider array and hands back something that can only be dropped into an environment injector's configuration. That's makeEnvironmentProviders, and it's exactly how you'd author the equivalent for your own library.

The mix-up worth being precise about

forwardRef fixes one cycle. Not every cycle.

forwardRef is famous for "fixing" circular references. Before the next bit: does it fix a real circular dependency — two services each needing the other to be constructed? Or does it only fix one very specific, much narrower kind of cycle?

Both of the cases below throw the exact same error — NG0200: Circular dependency in DI detected — and that shared error message is precisely what causes the mix-up. They are not the same problem. 

{{ cycleFixableSample }}

One class, referencing itself before its own definition has finished running. Nothing structural is wrong — the class just isn't done yet at the moment the decorator reads it. Delaying the read past that moment is the entire fix, and it always works. 

{{ cycleUnfixableSample }}

Two different classes, each one's constructor requiring the other to already exist. There is no order to build them in — delaying WHEN the reference is read changes nothing, because the problem was never about timing.

Three real fixes for the right-hand case, in the order to reach for them:

  1. Extract the shared piece into a third service. If both sides need to talk, they usually both need the same underlying thing — pull it out, and neither one needs the other anymore.
  2. Invert one direction with an event or a token. Have the "callee" expose an Observable, an EventEmitter, or a narrow interface token instead of the concrete class — the other side depends on the abstraction, not on each other.
  3. Defer the lookup with a captured Injector. One side injects Injector instead of the service directly, and calls injector.get(TheOtherService) lazily, inside the method that actually needs it — by the time that method runs, both instances already exist. Last resort, because it trades a compile-time dependency for a runtime one.

Questions from the back row

Before you go

Six things to remember.

Forgetting multi: true on a repeat registration doesn't error. It replaces the entire collection with your one new entry — silently, and only at the moment something actually reads the token.
  • Two trees, walked in order. Element injectors (this component, then every DOM ancestor) first; only once that whole chain is empty does the environment chain (route → root → platform) take over.
  • optional/self/skipSelf/host steer WHERE the walk starts and what a miss does — the live table above is the proof, and none of the four add new behaviour beyond that.
  • multi: true turns a token into a collection that every matching provider adds to. viewProviders hides a provider from projected content that providers would expose.
  • inject() needs an open injection context — a brief window during construction, not a property of where the code lives. runInInjectionContext is the bridge back in once it has closed.
  • makeEnvironmentProviders is how a provideX() function guarantees it can only configure an environment injector — never get dropped into one component by mistake.
  • forwardRef only fixes a declaration-order cycle. A real construction cycle between two services needs redesigning, not wrapping.
