Publishing a library is not "my code, but with an npm command in front of it." Everything hard about it comes down to three questions most tutorials skip: what actually gets built and shipped when you run one CLI command, what's the contract you're handing a stranger who will never read your source, and how do they install and later upgrade it without you standing over their shoulder. This page takes all three seriously — with a real config-API pattern, a real file-editing schematic, and the install task most examples quietly leave out.

The problem

Do you even need a published library?

Every Angular codebase eventually grows a Button, a DataTable, an auth service that more than one team wants. The reflex is ng generate library — but that command is the easy 5% of the job. The other 95% is everything this page is actually about: what ships, what's public forever, and how consumers get it onto their machines and keep it there.

Two apps in the same monorepo already share a Button today, through a plain workspace path. A third team, in a different repo with its own release schedule, wants it too. Which of those two relationships needs the full machinery this page is about — npm publish, peerDependencies, migration schematics — and which needs nothing more than what already works? Decide before you scroll; the table below gives it away.
Do you even need a published library?
Situation Right tool
Several apps in ONE repo share UI or logic A workspace library — path-mapped, built together, no publishing ceremony

The mental model

A library is a flat-pack, not a finished shelf.

Picture two ways to send someone a bookshelf. You could build it in your own workshop, glue it solid, and ship the finished object — heavy, and it only ever fits the exact room you built it for. Or you could ship the parts: pre-cut boards, an instructions card, and a note saying which screws you're including and which ones you're assuming the buyer already owns from their own toolbox. The second one is a flat-pack, and it is also, almost exactly, what npm publish does to an Angular library.

Partial compilation is the flat-pack boards. ng-packagr doesn't glue your templates into one Angular version's exact internal instruction format, because that format isn't a stable, public contract — it's allowed to change between versions. Instead it compiles to a stable, declarative intermediate form — calls like ɵɵngDeclareComponent(...), embedded right in the bundle — and the consumer's own build finishes assembly, using their installed Angular version's linker to expand those declare-calls into real instructions. That handshake, not luck, is why one published library version works across a range of Angular majors.

Ship the parts, not the finished shelf. Partial compilation, peerDependencies and public-api.ts are the same idea three times over: assume nothing about the workshop it gets assembled in, bring only the parts the workshop won't already have, and hand over one sealed instructions card — reprint it later and every shelf already assembled out there is now wrong.

That "which tools do you already own" question is exactly what peerDependencies answers, and it's worth hearing as the negotiation it actually is — npm deciding what to install against what your library's own package.json asks for:

The same code, NOT flattened — one file per source module. Mainly for tools that analyze or re-bundle your library themselves; most app builds never read this folder directly. Generated from your TypeScript, restricted to what public-api.ts exported. Consumers get autocomplete for Button, nothing for button.ts's private helpers. An exports field pointing each entry point at its own bundle, plus "sideEffects": false — permission for a bundler to delete an unused export entirely, not just leave it unreferenced.
public-api.ts is your contract, forever. Everything exported there is public API forever — renaming an exported symbol is a breaking change requiring a major version. Export deliberately, not export * from every file.

A failure mode

Editing dist/ is not editing your library.

That dist/ folder isn't just where a published library ends up — a workspace library generates a tsconfig.json path mapping that points the whole app at it too, even before anyone publishes anything: 

{{ tsconfigSample }}

Which means the app imports compiled output, never your source. Two setups actually work: keep ng build ui-kit --watch running in a second terminal so dist/ui-kit stays current as you edit, or repoint paths at projects/ui-kit/src/public-api.ts for source-level development — which costs you testing the real APF output, and needs its own path entry per secondary entry point. Either way, deleting dist/ to "start clean" breaks the app's typecheck with a module-not-found on your own library, because that mapping has nowhere else to point.

The red-carpet install

ng add is the difference between one command and a five-step README.

Before a schematic's factory ever runs, its options are validated against a schema.json — the file the widget sample referenced earlier but never showed:

An ng-add rule adds a brand-new entry to the consumer's package.json — a second package your library now depends on — but the rule never calls context.addTask(new NodePackageInstallTask()). The Tree commits fine; the new line really is in package.json now. Does npm install for that new dependency run on its own?

ng add my-lib installs the package, then runs its ng-add schematic — which is where you wire providers into app.config.ts, add styles to angular.json, or queue the extra install the napkin above just asked about. The difference between "works after one command" and a five-step README is this schematic.

Need a follow-up schematic to run only once those newly installed packages actually exist on disk — say, detecting which UI framework the consumer just pulled in and generating starter files for it? Pass the install task's own id as a dependency: context.addTask(new RunSchematicTask('post-install', options), [installTaskId]). The devkit won't start that second task until the first one it depends on has finished, so you get a real two-step pipeline instead of guessing that npm install is already done.

Upgrading consumers

ng update is a codemod your library ships with itself.

This is exactly how ng update @angular/core rewrites your code across majors — the framework ships its own migrations, keyed the same way. Offering the same for your library is what keeps consumers upgrading instead of pinning an old version forever out of fear.

The rest of tooling

Builders run every build; schematics run once.

A builder is a function from options and a context to a BuilderOutput — registered the same way a schematic is, in a JSON collection, then swapped into angular.json's architect section by name:

A library's own component styles are inlined into the compiled JS at build time — there is no loose .css file to ship for those. A theming partial meant for the consumer's own Sass compilation is different: it has to ship as real source, listed under assets, because inlined component CSS is already compiled and isolated, and nothing outside the component can @use it.

Pitfalls

Where teams actually get burned.

  • An untested peer range. Your peerDependencies claims >=19 <22? CI should build and test a consumer app on each major in that range — semver compliance is a promise, not a guarantee your code keeps it.
  • Leaking internals. A "temporary" export from public-api.ts becomes load-bearing in someone's app within a week. Deprecate before removing, and ship a migration schematic when you can.
  • Testing schematics by publishing. SchematicTestRunner and npm pack plus a local install cover this without ever touching the registry — publishing to test is how broken versions escape into the wild.
  • Forgetting sideEffects: false. Without it, a bundler can't safely delete an unused export from your library, even though ng-packagr already split everything into clean ES modules for it.

Pulling it together

Three questions, three contracts.

Layer The question it answers Where the answer lives
Packaging What ships, and in what shape? Angular Package Format + partial compilation, via ng-packagr
Contract What can consumers depend on? public-api.ts (forever) + peerDependencies (borrowed, not owned)
Automation How do they install and upgrade? ng-add schematic (install) + ng-update migrations (upgrade)
Every layer here composes with the others. A well-designed provideMyLib() is what an ng-add schematic wires up; a well-scoped public-api.ts is what an ng-update migration can rewrite cleanly, because there's a small, named surface to target instead of "anything a consumer might have imported."

Questions from the back row

Before you go

Five things to remember.

  • Partial compilation is why one published artifact serves a whole range of Angular majors — the consumer's own compiler finishes the job, not yours.
  • public-api.ts is forever; peerDependencies borrow, they don't own — put anything framework-shaped there or you risk shipping two copies of it.
  • provideX() + makeEnvironmentProviders() + a discriminated withXyz() union is how you design a library's own config surface — the modern replacement for forRoot().
  • A schematic Rule transforms an atomic, in-memory Tree. Editing an existing file needs its own recorder discipline — one beginUpdate/commitUpdate pair per file, or the second write silently clobbers the first.
  • ng-add is the install experience, NodePackageInstallTask included; ng-update runs every migration between the installed and target version, in version order.
