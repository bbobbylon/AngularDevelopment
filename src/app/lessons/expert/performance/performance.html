Performance work fails most often not from ignorance of the fixes, but from applying the right fix to the wrong symptom. This page treats load time, runtime, and Google's Web Vitals scorecard as three separate diagnoses — and instead of an "Impact: High" table cell, proves the two most quotable claims on this page with a counter you can watch move.

The problem

"Slow" is not a diagnosis. It's a symptom.

Every performance bug report says the same word, and the word is nearly useless. "Slow" describes how it feels, not what's wrong — and a fix aimed at the feeling instead of the cause reliably does nothing, because the two problems hiding under that one word don't share a toolkit.

Three genuinely different diagnoses share the word "slow" in this lesson:

  • Load time — how long until the browser even has your JavaScript and can paint something.
  • Runtime — how long the app takes to respond once it's already running, interaction by interaction.
  • Web Vitals — the specific scorecard Google measures both of the above through, because a raw millisecond count isn't what search rankings read.

Images turn out to be a lever that pulls on two of those at once, so they get their own section rather than a fourth bullet. And profiling — finding out which of the three you actually have — sits last on this page and first in the order you should actually do things, which the next section explains.

The mental model

Treat it like triage, not surgery.

Picture an emergency room instead of an operating theatre. A patient who says "I feel awful" does not go straight to surgery — a doctor asks questions, runs a scan, and only then decides what to treat. Performance work wants the same discipline, and for the same reason: operating on the wrong organ doesn't just waste the afternoon, it leaves the actual problem untouched while you feel productive.

Load time is the waiting room — how long before anyone even sees you. Runtime is the treatment room — how fast you're actually helped once you're in one. Web Vitals is the satisfaction survey the hospital gets graded on afterward. And the profiler is the diagnostic scan: the one step every guide, including this one's opening line in its previous version, tells you to do first and then skips.

Symptom, then diagnosis, then treatment. "It's slow" is the symptom. Load time, runtime and Web Vitals are three different diagnoses hiding under it. The profiler is the diagnosis step — never skip straight to treatment because a checklist told you a fix was "High impact" on average.

Load time

Ship less JavaScript before the first paint.

JavaScript is the most expensive resource type a browser handles — every byte is downloaded, then parsed, then compiled, then executed, and none of that overlaps for free. The single highest-leverage load-time fix is simply not sending JavaScript the current screen doesn't need yet.

Lazy routes — split between pages

Every feature behind loadComponent or loadChildren becomes its own downloadable chunk.

Preloading — download quietly, after the app is already usable

Lazy alone means a user pays the download cost at the moment they navigate. Preloading starts that download earlier, in the background, once the initial screen is already interactive — so by the time they click, the chunk is often already there.

@defer — split within a page

A route can be lazy and still contain one component too heavy to ship eagerly — a chart library, a rich editor. @defer code-splits that one component out of its own route's chunk.

Runtime

Do less work per interaction, not more of it faster.

Once the app is running, the cost model is the one the change detection lesson lays out in full: a pass is cheap — a flat array walk with a === compare per binding slot. What's expensive is what you put inside a binding, because that work re-runs on every single pass that reaches the view, whether or not anything it depends on actually changed.

OnPush + signals — prune the walk itself

Before touching what's inside a binding, make sure a pass reaches this view only when it has to. That's what OnPush is for — this page assumes the mechanism and moves straight to the shape.

computed() remembers. A template call never does.

Even inside a view that does get checked, a plain method call in a binding re-runs on every pass — the framework has no way to know it would return the same answer without calling it. Wrapping the same expression in computed() gives Angular something to check first: has anything this depends on actually changed?

@for needs a way to tell "this is the same row, just moved" from "this row was deleted and a new one appeared." track $index answers with position; track item.id answers with the row's actual identity — and only one of those survives a reorder.

In the left list, Angular matches each row by id — your note follows "Apple" wherever it lands. In the right list, Angular matches by position — the note stays in the DOM node that started as row 1, which after a shuffle is sitting next to a different name entirely. Nothing errored. The data is correct. The note is just attached to the wrong thing now.

When the list itself is the bottleneck

track item.id stops a reorder from destroying rows, but it does not shrink the DOM. Once a list is genuinely long — hundreds of rows on screen, not tens — the bottleneck quietly moves from change detection to raw DOM node count: layout, paint and memory all scale with how many real elements exist, whether or not Angular ever re-checks them.

@angular/cdk/scrolling answers that with windowing: render only the rows currently in (or near) the viewport, and recycle a small pool of real DOM elements as the user scrolls, instead of creating one element per row.

This is not *cdkVirtualFor — this app has no @angular/cdk dependency — it's the same idea hand-rolled from a scroll event and two computed()s: track scrollTop, work out which slice of 500 is visible, render only that slice. A production app would reach for the CDK directive above instead of this by-hand version, for the recycling and the accessibility work it already did.

The subscription nobody remembered to end

A leaked subscription is a runtime cost that grows with time rather than with data: every navigation that leaves one behind keeps a destroyed component's callback alive, still doing work, for the life of the app.

Web Vitals

The scorecard Google actually grades you on.

Core Web Vitals distill "is this page fast" into a handful of numbers measured from real users' browsers, not a lab benchmark — and they feed directly into SEO ranking, which is why they get their own section rather than folding into load time or runtime.

Time until the largest visible element — usually a hero image or heading — has rendered. The clearest proxy for "does this feel loaded" a user has. Time from a user interaction to the next frame actually painting. Replaced FID in 2024, and measures your handler's own execution time, not just Angular's. The sum of every unexpected layout shift during load. Fixed with explicit dimensions and skeleton placeholders, not with anything change-detection related. Server response time — before Angular has run a single line. SSR lowers it by sending real HTML instead of waiting for the client bundle to bootstrap.
Angular-specific fixes, per vital
Vital Angular-specific fix
LCP [priority] on the LCP image with NgOptimizedImage, SSR for above-the-fold content, and never @defer the LCP element itself.
INP Short, non-blocking event handlers — see the ladder below. OnPush helps only the change-detection half of the story.
CLS Explicit width/height (automatic with NgOptimizedImage), correctly-sized @defer placeholders, never inserting content above what's already on screen.

INP: the ladder of fixes, not just OnPush

This is the trap the checklist row above names directly: OnPush reduces how much a change-detection pass checks. It does nothing about time your own handler spends running before a pass even begins — and that is exactly where a slow synchronous handler burns its 400ms.

Note what's absent from the fix above: no OnPush, no computed(), no signal anywhere. A long task inside your own handler is a JavaScript-execution-time problem — the change-detection knobs from the Runtime section don't touch it at all.

Images

The single biggest LCP lever most teams skip.

Images are, more often than any other element, the LCP candidate — and NgOptimizedImage (built into @angular/common, no install) handles the four things that usually go wrong by hand: priority hints, lazy loading, responsive sizing, and reserved layout space.

What NgOptimizedImage does for you
Feature Plain <img> NgOptimizedImage
Lazy loading below the fold Must add loading="lazy" yourself Automatic
LCP priority preload Must add fetchpriority and a preload <link> Add [priority] — one attribute
Responsive srcset Written by hand Automatic, with a configured loader
Missing size hints Silent layout shift Build-time error if width/height are missing
Blur-up placeholder Written by hand [placeholder] — one attribute
src and ngSrc are mutually exclusive — using both on the same image is a build error. Migrate by renaming every src= to ngSrc= and adding the width/height the directive now requires.
Mark one image priority — your actual LCP element. The directive warns in the console the moment it sees more than one, and for good reason: fetchpriority="high" on every image competes with itself for the same limited bandwidth, which is the opposite of what priority is for.

Measuring

This should have been step one.

Back to the ER analogy: everything above this section is a treatment. None of it should be applied before the diagnostic scan tells you which room the patient actually needs.

The flame chart the profiler produces answers three questions directly:

  • Which components ran change detection on the interaction you just recorded, and how many milliseconds each one's check took.
  • Which components run a pass constantly but rarely change anything visible — usually the first sign an OnPush is missing.
  • Which single component dominates the widest bar — the one worth fixing first, before recording again.

Questions from the back row

Before you go

Six things to remember.

computed() and track item.id are the same rule wearing two syntaxes: tell Angular what changed instead of making it re-derive the answer from scratch.
  • "Slow" is at least three unrelated bugs wearing one word — load time, runtime, and Web Vitals. Fixing the wrong one isn't a failed sprint, it's a wasted one: nothing breaks, it just doesn't help.
  • Bundle size is solved before Angular even boots: lazy routes and @defer split the JavaScript, and budgets fail the build instead of failing the user.
  • A change-detection pass is cheap. What you put inside a binding is not — computed() and track item.id both exist to stop Angular redoing work nothing asked it to redo, and the Cost Lab demo proved the difference in real call counts, not an estimate.
  • Once a list is genuinely long, the bottleneck moves from change detection to raw DOM node count. That's what virtual scrolling answers, and it's a different fix from anything OnPush or track can give you.
  • LCP wants one priority image. INP wants a short handler — OnPush does nothing for a slow synchronous loop inside your own click callback. CLS wants explicit dimensions. Three different diagnoses, three unrelated fixes.
  • The profiler is step one, not step five, no matter where it sits on this page.
