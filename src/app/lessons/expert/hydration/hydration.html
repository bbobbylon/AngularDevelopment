Server-side rendering paints real HTML before a line of your JavaScript runs. What happens next is what this page is about: does the client adopt that HTML, or quietly throw it away and build a second page on top of the first? Hydration is Angular choosing the first option — and the price of that choice is a strict contract about what the client is allowed to find when it goes looking. This page covers the adoption mechanism itself, how to tell it actually worked, the ways the contract gets broken, and two escape hatches that sound like the same idea and are close to opposites.

The server already did the work — a finished <article>, a filled-in form, a <video> already mid-frame. Skip one function call in app.config.ts and Angular throws every bit of that away the instant it boots, then pays to build all of it again.

Angular boots knowing nothing about what's already on screen. It builds its own component tree from scratch and swaps every node in over the top — the mid-frame video included — whether or not anything needed to change at all.

Angular boots holding the map the server shipped alongside the HTML. It walks the existing DOM confirming each node matches that map, adopts what's there, and never touches a node that was already right.

The mechanism

Hydration has to be turned on — it isn't the default just because a route is server-rendered.

You paid the server to render it once. Skip one function call, and you pay the client to render it again.

Every step in the destructive column costs something real — a repaint, a lost cursor position, a video that jumps back to frame zero. Hydration's whole pitch is that the right-hand column costs none of it.

Here's a way to hold both boot paths in your head with no Angular vocabulary at all. Imagine two ways to move into an apartment that already has furniture in it.

The destructive way: you carry every piece of the existing furniture out to the curb — sofa, bookshelf, the lamp that was already plugged in and lit — and build your own from flat-pack, room by room, while the previous tenant's furniture sits on the lawn. The apartment ends up looking identical. It just spent an afternoon looking like a demolition site to get there, and the lamp that was on when you arrived is off now, because it got unplugged along the way.

The hydration way: you walk in holding the floor plan the previous tenant left you — which piece is in which room, in what order — and go room to room confirming the furniture matches the plan. Where it does, you leave it exactly where it is and start doing tenant things: plugging your own lamp cord into the socket that's already there, instead of installing a socket. Nothing goes outside. The lamp that was already lit stays lit.

Map, walk, claim, verify. The server emits the map — ngh plus the ng-state blob. The client walks the existing DOM in the order the map describes, claims each node instead of creating it, and verifies it got what the map promised. A "no" at verify is NG0500.

This is why the contract is strict. The walk only succeeds if the DOM the client finds is exactly the DOM the map describes, in structure and order. Verifying it

How do you know it actually worked?

A page that looks fine tells you nothing — a destructive re-render looks fine too, a beat later. Three real ways to check, none of which require reading a stack trace:

  • The dev console prints a one-line summary after every hydrated navigation: how many components and nodes were adopted, and how many were skipped.
  • Angular DevTools has a dedicated hydration overlay in the Components tab — it colours the tree by hydrated / skipped / mismatched, so you can see where the walk gave up instead of parsing an error.
  • The proof is in view-source too: the ngh attributes and the <script id="ng-state"> blob from the section above are just sitting in the response your server sent. Missing entirely, and nothing upstream of Angular is even trying.

Dev and prod disagree on what to do about it. In development, a mismatch throws loudly, on purpose, so you can't ship it unnoticed. In production, Angular recovers quietly — silently destroying and re-rendering just the affected subtree. Never assume "no error in the console" means "hydration worked."

The exam trap

Skip and never are not the same escape hatch.

Both ngSkipHydration and @defer (hydrate never) leave a region "not hydrated," and that's the only thing they have in common — otherwise they're close to opposites:

The same region, three different treatments
Question Hydrate normally ngSkipHydration @defer (hydrate never)
Server DOM reused? Yes No — destroyed & rebuilt Yes, forever
JS downloaded for it? Yes Yes No — never shipped
JS executed for it? Yes Yes No
Ever becomes interactive? Yes Yes, after the rebuild No — stays inert
ngSkipHydration is valid only on a component's host element. It's inherited by everything beneath it, and it's all-or-nothing — there's no opting a deeper child back in once an ancestor has skipped.
Skip re-renders it. Never freezes it. ngSkipHydration pays full JS cost and throws away the DOM; @defer (hydrate never) keeps the DOM and pays zero JS cost. If you remember which one costs JavaScript, you remember both.

Event replay

The click that almost got lost.

Between first paint and hydration there's a window where the page looks interactive but isn't yet — listeners simply haven't attached. Event replay is what stops the eager visitor's first click from vanishing into that gap. 

HTML painted — page looks interactive
        │
   visitor clicks "Add to cart"
        │
hits a listener-less button: LOST
        │
   hydration finishes attaching
listeners — too late, click is gone
HTML painted — page looks interactive
        │
   visitor clicks "Add to cart"
        │
click recorded at the document root
        │
hydration attaches the real listener
        │
recorded click replays into it — kept

What replay does not save you from:

  • preventDefault() and stopPropagation() inside the replayed handler. The real event already finished — its default action already ran, its propagation already happened — by the time your handler executes, so calling either one now does nothing.
  • Listeners you attached yourself with raw addEventListener outside a template binding. The jsaction attribute only gets stamped on Angular's own (event) bindings.
  • Work that genuinely needed to start before hydration — an API call gating what the button even does. Replay can deliver the click to the listener; it can't make data exist that hasn't been fetched yet.

Incremental hydration

Ship the pixels now, the JavaScript later.

Full hydration still eventually downloads and executes the JavaScript for the whole page. Incremental hydration goes further: the server renders everything, but marked sections stay dormant — real, visible DOM, zero attached JS — until their trigger fires.

Every hydrate on trigger
Trigger Hydrates when… Use for
hydrate on idle the browser goes idle default "eventually" sections
hydrate on viewport scrolled into view below-the-fold content (comments, footers)
hydrate on interaction the visitor clicks or focuses it widgets that are static until touched
hydrate on hover pointer approaches menus, cards with actions
hydrate when expr a boolean turns true app-driven activation
hydrate never never — stays static HTML forever purely presentational server output

The rules that come with the feature, none of which are optional:

  • Event replay is automatic inside a hydrate block too. A click on dormant content is buffered exactly like a click anywhere else on the page.
  • The scope is the initial SSR document only. A client-side route navigation into the same component has no server DOM to adopt, so the block just defers normally and shows @placeholder like a plain @defer would.
  • ngSkipHydration and hydrate triggers don't mix. Pick one dormant strategy per region, not both at once on the same component.
  • Nested hydrate blocks resolve top-down. A child's trigger can't fire before its parent has hydrated — a hydrate on interaction child inside a hydrate on viewport parent waits for the viewport trigger regardless of what the child's own trigger is doing.

Pulling it together

What hydration buys you — and what it never promised.

Buys

  • No flash of re-rendered content, no CLS spike at bootstrap
  • Less client work — adopting beats rebuilding
  • Preserved media and iframe state
  • With incremental hydration, dramatically less JavaScript executed up front

Doesn't buy

  • A faster first paint — that's SSR itself, not hydration
  • Relaxed SSR-safety rules — server and client still must render identical output
  • Immunity from a mismatch, or a way to skip verifying it worked
Hydration doesn't make the page faster to first paint — SSR already did that. What hydration buys is a client takeover the visitor never notices, instead of a second render stacked on top of the first.

Questions from the back row

Before you go

Six things to remember.

  • Hydration's whole job is one promise: don't build a second page over the first one. It walks the server's DOM instead of recreating it, matching each node against the ngh map the server shipped alongside it.
  • That promise only holds if the DOM the client finds is byte-for-byte what the server produced. Anything that perturbs it in between — a proxy's minifier, a browser "fixing" invalid HTML, an injected script — breaks the walk.
  • A dev-time NG0500 isn't the whole story: production recovers on its own, silently rebuilding just the mismatched subtree. The only way to know it happened is to go looking.
  • ngSkipHydration and @defer (hydrate never) are near-opposites, not siblings. Skip re-renders it; never freezes it.
  • withEventReplay() buys back clicks lost in the pre-hydration gap — but not a working preventDefault(), a handler wired up outside a template, or work that genuinely needed to start earlier.
  • Incremental hydration only changes what happens on the document the server actually rendered. Reach the same @defer (hydrate ...) block by client-side navigation instead, and it behaves like a plain @defer — placeholder and all.
