NgModules & Standalone Migration

For a decade, every component lived inside an NgModule; standalone components made that ceremony optional, then made its absence the default. Senior work still demands both: you'll read NgModule code in every mature codebase, migrate it incrementally, and explain why the old model confused people — which is exactly what its compilation-scope rules did.

NgModule anatomy — four arrays, two different worlds

{{ anatomySample }}
Array Governs Visibility rule
declarations template scope private to this module unless exported; each declarable in exactly ONE module
imports template scope pulls in other modules' exports
exports template scope this module's public template API (can re-export imported modules)
providers injector ignores exports entirely — eager modules merge providers app-wide

The asymmetry in that last row — template scope obeys exports, the injector doesn't — generated years of confusion and is a core motivation for standalone's cleaner split: components own template deps, app.config.ts/routes own providers.

forRoot / forChild — why that pattern existed

{{ forRootSample }}

A module imported by five lazy features would register its providers five times — five instances of a "singleton". forRoot() returned module-plus-providers for the root import; forChild() returned the module without them. It was a convention (not a language feature) papering over the provider-scope asymmetry — standalone's provide*() functions make the whole dance unnecessary.

The standalone world

{{ standaloneSample }}
  • Template deps live on the component — its imports array names exactly what its template uses (components, directives, pipes, or whole NgModules).
  • standalone is the default — modern components don't write standalone: true; NgModule-declared components are the ones that need explicit marking (standalone: false).
  • Providers centralize — app.config.ts for the app, route providers for feature scope, component providers for per-instance.

The migration — three schematic passes

{{ migrationSample }}

HttpClientModule provideHttpClient(withInterceptors(...))
RouterModule.forRoot(routes) provideRouter(routes, withComponentInputBinding(), …)
RouterModule.forChild(routes) a plain Routes file + loadChildren: () => import('./x.routes')

BrowserAnimationsModule gone with the deprecated animations package (see Animations)
CommonModule (for *ngIf/*ngFor) usually nothing — @if/@for are built into templates; import only the pipes you use (DatePipe, AsyncPipe…)

Mixing worlds during migration

{{ interopSample }}
Both directions work, so migrate leaf-first without a big bang: convert leaf components to standalone (NgModules can import them), walk up the tree, delete each module when its last declaration leaves, and finish by swapping platformBrowserDynamic().bootstrapModule(AppModule) for bootstrapApplication(App, appConfig).

Error messages, decoded

Error Meaning Fix
"'app-x' is not a known element" X isn't in the compilation scope standalone: add to the component's imports; NgModule: export from its module and import that module
NG6007 "part of the declarations of 2 modules" declarable double-declared declare once in a shared module — or make it standalone
NG6008 "standalone and cannot be declared" standalone component in a declarations array move it to the module's imports
NG0302 "the pipe 'date' could not be found" pipe not in scope import DatePipe (standalone) / CommonModule (NgModule)

Exam corner

Module A imports module B. Can A's components use B's declared-but-unexported directive?
No — imports grant access to B's exports only. Declarations are private by default. This asymmetry (vs providers, which leak app-wide from eager modules) is the single most-tested NgModule fact.
Why did RouterModule need forRoot/forChild?
To register the router's singleton services exactly once: forRoot returned module + providers for the app root; forChild returned only the directives for lazy features — otherwise each lazy import would create duplicate router state. provideRouter() + plain route arrays replaced the whole pattern.
During migration, how does an NgModule use an already-converted standalone component?
Add the component class to the NgModule's imports array (not declarations — that's NG6008). Standalone things import like modules.
A library only ships SomeLibModule with providers. Standalone app — now what?
importProvidersFrom(SomeLibModule) inside app.config.ts providers extracts the module's provider graph into the environment injector. It's the designated bridge until the library ships a provideSomeLib() function.
Do you still need CommonModule in standalone components?
Rarely. @if/@for/@switch replaced the structural directives, so you import only what you actually use — typically individual pipes like AsyncPipe or DatePipe. Blanket CommonModule imports are a migration smell.

Key takeaways

  • NgModule mental model: declarations are private, exports are the public template API, imports pull in exports — and providers ignore all of it.
  • forRoot/forChild existed to fake provider scoping; provide*() functions made it obsolete.
  • Standalone puts template deps on the component and providers in app.config/routes — the two concerns NgModules tangled.
  • Migrate leaf-first with ng generate @angular/core:standalone (convert → prune modules → bootstrap), bridging gaps with importProvidersFrom.
  • Know the error map: unknown element = scope; NG6007 = double declaration; NG6008 = standalone in declarations.
