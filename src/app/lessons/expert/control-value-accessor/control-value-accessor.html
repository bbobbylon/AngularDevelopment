ControlValueAccessor is the bridge that lets your own component behave like a native <input> inside Angular forms — usable with formControlName, [(ngModel)], validation, statuses and disabled state. It's the same mechanism Angular uses for native inputs: DefaultValueAccessor, CheckboxControlValueAccessor and friends are just built-in CVAs, and by the end of this page yours will be built the same way.

"4," writeValue renders. "4," onChange reports. "4," writeValue renders again — nobody has typed anything since the first 4.

A writeValue(4) is only supposed to paint four stars. This one also calls onChange(4) — and now the form believes a user just entered 4, when the write was entirely programmatic.

The parties: writeValue, whose whole job is rendering what the form hands it. onChange, whose whole job is reporting a value back to the form. And FormControl, which reacts to whatever onChange tells it, with no way to see where that call actually came from.

writeValue and onChange each behaved exactly as documented — the bug is not in either method, it is in the one call connecting them. A ControlValueAccessor is a contract about a direction that never runs backward: model-to-view methods render, they never report; view-to-model methods report, they never render. Cross that line once, and every party downstream reacts correctly to a value nobody actually entered.

Play a microphone's own pickup back out of a nearby speaker, and the sound loops through the system again and again — not because the microphone or the speaker malfunctioned, but because an output stage got connected back into its own input. writeValue and onChange are the same arrangement: each one is fine in isolation, and the feedback squeal only starts once one calls the other directly.

The mental model

A translator who must never talk to themselves.

Picture two diplomats at a summit who share no language. One — FormControl — only speaks setValue and reads valueChanges. The other — your component — only understands its own clicks and its own state. ControlValueAccessor is the interpreter standing between them. Diplomat A speaks; the interpreter renders it for diplomat B. Diplomat B reacts; the interpreter reports it back to diplomat A.

There is exactly one rule every interpreter follows, and it's the rule this whole lesson exists to enforce: never repeat a diplomat's own sentence back to them. Break it, and you get two people frantically re-translating each other's words forever — which is precisely the echo loop that follows from calling onChange from inside writeValue.

IN never calls OUT. writeValue and setDisabledState are IN (model → view) — they only render. onChange and onTouched are OUT (view → model) — they only report. An interpreter who repeats a diplomat's own words back to them isn't translating any more; that's the echo loop.

The mechanism

Four methods. Only two directions.

A native <input> does two jobs for the forms system: it renders a value it's given, and it reports a value the user typed. Before you scroll — how many separate methods do you think Angular needs from a component to cover both jobs, plus the "leave me alone, I'm disabled" case? Try to name them, not just the count.

Strip away the ceremony and a ControlValueAccessor is four methods sorted into two directions. Here is one full round trip — a programmatic write, then a user edit — as a single sequence, because the two directions aren't separate features, they're two halves of the same bridge.

The four methods — and which direction each one belongs to
Method Direction When it fires
writeValue(v) model → view setValue(), patchValue(), reset(), the initial value — render v, and expect null on reset
registerOnChange(fn) view → model the form hands you its callback once at setup; you call fn(value) on every user edit
registerOnTouched(fn) view → model call fn() when the user "leaves" the control (blur) — drives touched and error-display logic
setDisabledState(b) model → view control.disable() / enable() — reflect it or the API silently doesn't work
Touched belongs to blur, not to every keystroke. Call onChange on every edit; save onTouched for the moment the user leaves. Call it on every keystroke instead and validation errors flash while they're still typing.

Becoming a control

The entire act is one provider.

Implementing the four methods makes a class capable of the job. What actually gets you into formControlName's address book is a single entry in providers — everything else in this lesson is what happens once that entry exists.

An exam question

A custom control's validation config is an @Input. Why doesn't changing it re-validate?

min and max above are input()s, not constants — a consumer can change [max] at runtime. validate() already reads this.max(), so it looks correct. Try it:

Flip max down to 3 while the value sits at 4 — with the fix below in place, status flips to INVALID immediately, with no click on the stepper itself.

Without the fix, that toggle does nothing. The form only ever calls validate() again in response to a value change — setValue, onChange, a sibling validator re-running. Angular has no built-in way to know your validator's own configuration just moved, because from the form's point of view, nothing did.

Under the hood

How formControlName actually finds you.

The classic mistake

writeValue only renders. It never reports.

Back to the interpreter. The single most common CVA bug is a writeValue that also calls onChange — reporting the write straight back to the form that just made it, as if the user had typed it themselves. 

writeValue(v: number) {{ '{' }}
  this.value.set(v);
  this.onChange(v);   // ✗ echoes the write straight back to the form
{{ '}' }}
writeValue(v: number) {{ '{' }}
  this.value.set(v);
  // writeValue only renders. The form already knows this value —
  // it just told you. Reporting it back teaches the form nothing
  // and risks a feedback loop.
{{ '}' }}
Already checked yourself against this exact bug at the top of the page — the wrong-vs-right code above is the literal source of the microphone-and-speaker feedback loop the block opened on.

Choosing between them

CVA vs plain input/output.

value input + output ControlValueAccessor
Works with formControlName / ngModel no yes — both, unchanged
touched / dirty / statuses reimplement by hand free
Validation integration manual wiring per consumer NG_VALIDATORS, composed automatically
form.disable() ignored setDisabledState
Best for non-form widgets (toolbars, toggles outside forms) anything a user "fills in"

Questions from the back row

Before you go

Five things to remember.

  • CVA is the same contract native inputs use — implement it and every form API (reactive and template-driven) works with your component, unchanged.
  • Four methods, two directions: writeValue / setDisabledState are IN (model → view); onChange / onTouched are OUT (view → model). Never let one call the other.
  • The provider is what actually registers you: NG_VALUE_ACCESSOR + multi: true + forwardRef + useExisting, on the component itself (@Self() lookup).
  • Handle null in writeValue — that's what reset() sends — and honour setDisabledState or disabling the form silently does nothing to your control.
  • Add NG_VALIDATORS to ship a self-validating control, and store view state in signals so OnPush just works.
