PWA & Service Worker

A Progressive Web App installs to the home screen, works offline, and loads instantly on repeat visits. Angular ships a generated, declarative service worker — you write JSON config, not worker code — with atomic versioned updates and a small runtime API (SwUpdate/SwPush). This page covers the engine, the caching strategies, the update lifecycle, and the production gotchas.

What makes a PWA — and what ng add scaffolds

  • HTTPS — service workers refuse to register on insecure origins (localhost excepted).
  • A web app manifest — manifest.webmanifest: name, icons, theme_color, display: "standalone". This is what makes the browser offer "install".
  • A service worker — the offline/caching engine.
{{ setupSample }}
The worker is disabled in ng serve and only activates in a production build served over HTTPS/localhost. Test with ng build + any static server. Caching bugs that "survive" your fixes are usually a stale worker — unregister it in DevTools → Application → Service Workers, or bump the version.

How the engine works (this is the exam-worthy part)

ng build generates ngsw.json — a manifest listing every cacheable file with its content hash. The generic ngsw-worker.js engine reads it and treats each manifest as an immutable app version:

  • Atomic updates — the worker serves the current version in full while downloading the next one in the background. Users never get v1's HTML with v2's JS (the classic broken-deploy bug ngsw exists to solve).
  • Hash-verified — if a cached file's hash doesn't match the manifest (a CDN served a stale file), the worker treats the version as broken and falls back to the network.
  • One tab, one version — a running tab keeps its version until reload; the new version activates on the next load or when you call activateUpdate().

Production gotchas & debugging

  • ngsw/state — visit /ngsw/state in the app: the worker reports its current versions, clients, and update status. First stop for "why is it serving old code".
  • ngsw-bypass — add the ngsw-bypass header (or query param) to any request and the worker steps aside — essential when debugging API calls you suspect are cached.
  • The safety worker — shipping a broken worker can pin users to a bad version. Angular provides safety-worker.js: deploy it at the same URL to unregister the worker and clear its caches for everyone.
  • Never cache what you can't hash — external CDN scripts in assetGroups (via urls) are cached but not hash-verified; prefer bundling or dataGroups with a short maxAge.
  • index.html must not be aggressively CDN-cached — the worker bootstraps from it; an edge cache serving week-old HTML defeats the whole update mechanism.

Exam corner

freshness vs performance — which for a stock ticker, which for a country list?
Ticker: freshness (network-first with timeout — stale prices are harmful). Country list: performance (cache-first — instant, and staleness for 7 days is irrelevant).
Why don't users see a half-updated app during deploys?
Updates are atomic: the worker serves the complete current version while the new manifest's files download; only when every hash-verified file is cached does the new version become activatable — on next load or explicit activateUpdate().
A user reports week-old code. Diagnosis path?
Check /ngsw/state for the served version; verify index.html isn't edge-cached with a long TTL; confirm the tab isn't simply long-lived without a checkForUpdate() poll; worst case, the deployed worker is broken — ship the safety worker to unregister it.
Why is the service worker off during ng serve?
Dev rebuilds constantly change file hashes — the worker would thrash caching stale bundles and mask live-reload. It's enabled only for production builds (enabled: !isDevMode()), served over HTTPS or localhost.

Key takeaways

  • PWA = HTTPS + manifest + service worker; ng add @angular/pwa scaffolds all three.
  • The generated engine versions the app via hashed manifests — updates are atomic and verified.
  • assetGroups cache the app (prefetch/lazy); dataGroups cache APIs (freshness/performance + maxAge/timeout).
  • Drive updates with SwUpdate.versionUpdates (VERSION_READY → prompt → activateUpdate() → reload); poll long-lived tabs.
  • Debug with /ngsw/state and ngsw-bypass; keep safety-worker.js in your back pocket.
