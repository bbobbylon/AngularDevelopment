A Progressive Web App installs to the home screen, works offline, and loads instantly on repeat visits. Angular runs the whole thing like hotel management renovating the building while every room stays occupied — nobody gets moved mid-stay, and the new wing only opens once every last fixture has been checked. This page covers the engine behind that guarantee, the caching strategies, the update lifecycle, and the production gotchas.

The mental model

A hotel that renovates without ever closing a room.

Picture hotel management upgrading the building one version at a time, guests still checked in throughout. They don't touch a single occupied room. Instead they build an entire new wing off to the side — every fixture, every file — and don't open it to anyone until every last item has been checked against the blueprint. Guests already checked in keep their current room for the rest of their stay; only new check-ins, or guests who choose to move, ever set foot in the new wing.

That's the whole engine. The "blueprint" is ngsw.json, a manifest listing every cacheable file with its exact content hash. "Building the new wing" is the worker downloading v2 in the background. "Checking it against the blueprint" is hash verification — if one cached file doesn't match, the worker treats that whole version as unsafe and falls back to the network rather than serving a half-broken room. And "guests keep their room until checkout" is the one-tab-one-version rule: nothing moves your already-open tab until it reloads.

New wing, same guests. The worker never touches a room while someone's in it — it finishes and inspects the entire new version off to the side first, and existing tabs don't move until they check out (reload).

In practice

What makes a PWA — and what ng add scaffolds.

  • HTTPS — service workers refuse to register on insecure origins (localhost excepted).
  • A web app manifest — manifest.webmanifest: name, icons, theme_color, display: "standalone". This is what makes the browser offer "install".
  • A service worker — the offline/caching engine.
The worker is disabled in ng serve and only activates in a production build served over HTTPS/localhost. Test with ng build + any static server. Caching bugs that "survive" your fixes are usually a stale worker — unregister it in DevTools → Application → Service Workers, or bump the version.

The mechanism

How the engine works — this is the exam-worthy part.

ng build generates ngsw.json — the blueprint from the analogy above, an immutable manifest listing every cacheable file with its content hash. The generic ngsw-worker.js engine reads it and treats each manifest as one app version:

  • Atomic updates — the worker serves the current version in full while downloading the next one in the background. Users never get v1's HTML with v2's JS (the classic broken-deploy bug ngsw exists to solve).
  • Hash-verified — if a cached file's hash doesn't match the manifest (a CDN served a stale file), the worker treats the version as broken and falls back to the network.
  • One tab, one version — a running tab keeps its version until reload; the new version activates on the next load or when you call activateUpdate().

In practice

Push notifications — SwPush in one glance.

requestSubscription needs your VAPID public key and user permission; the resulting subscription goes to your backend, which sends pushes through the browser's push service. Messages arrive on swPush.messages; clicks on notificationClicks. The heavy lifting is the backend integration — treat it as a real feature, not a checkbox.

Debugging

Production gotchas.

  • ngsw/state — visit /ngsw/state in the app: the worker reports its current versions, clients, and update status. First stop for "why is it serving old code".
  • ngsw-bypass — add the ngsw-bypass header (or query param) to any request and the worker steps aside — essential when debugging API calls you suspect are cached.
  • The safety worker — shipping a broken worker can pin users to a bad version. Angular provides safety-worker.js: deploy it at the same URL to unregister the worker and clear its caches for everyone.
  • Never cache what you can't hash — external CDN scripts in assetGroups (via urls) are cached but not hash-verified; prefer bundling or dataGroups with a short maxAge.
  • index.html must not be aggressively CDN-cached — the worker bootstraps from it; an edge cache serving week-old HTML defeats the whole update mechanism.

Questions from the back row

Before you go

Recap — five things to remember.

  • PWA = HTTPS + manifest + service worker; ng add @angular/pwa scaffolds all three. The engine runs your app like a hotel renovating without ever closing a room.
  • The generated engine versions the app via hashed manifests — updates are atomic and verified, and a running tab never moves to the new wing until it checks out (reloads).
  • assetGroups cache the app (prefetch/lazy); dataGroups cache APIs (freshness/performance + maxAge/timeout).
  • Drive updates with SwUpdate.versionUpdates — VERSION_READY means built and inspected, not occupied — prompt, then activateUpdate(), then reload; poll long-lived tabs.
  • Debug with /ngsw/state and ngsw-bypass; keep safety-worker.js in your back pocket.
