A Progressive Web App survives a lost connection and installs like a native one — and Angular's version of that is unusual: you write no fetch handler and no cache code at all, just a JSON config file that a generated engine called ngsw-worker.js interprets for you. Almost every real question about it comes down to three things: which file answers a request nobody wrote a route for, what actually gets cached and what quietly doesn't, and how a running tab ever finds out a new version exists. This page takes all three apart with a manifest you can read line by line, two live simulators, and the exam traps that show up because the engine's rules are stricter — and more specific — than "cache everything."

The problem

Turn off the wifi. What happens?

Ordinarily: nothing good. A hard reload with no connection hands you the browser's own dinosaur, and every byte of your app — the JS, the CSS, the HTML shell itself — simply isn't there to serve. Nothing about a normal website changes that, because the browser only ever has one way to get your files: ask the network.

A service worker is the thing that gets to say no, ask me first. It sits between your app and the network for every single request, and it gets to answer from a cache instead of ever touching the wire. Hand-write one and that is a real, tedious job — a fetch event listener, a versioning scheme you invent yourself, cache invalidation you get to debug at 2am. Angular's answer is to generate the worker from a JSON file you write declaratively, and interpret it with one script, ngsw-worker.js, that ships the same for every Angular app that has ever used it.

Picture the same reload, offline, on two identical apps. Neither has a single line of custom caching code. One never called provideServiceWorker; the other did, and you'd visited it once before while online. Hold a guess for each screen before you read on — and notice that the second one doesn't need you to have written a single fetch handler to pull that off.

The mental model

It runs a museum, not a warehouse.

A warehouse restocks shelf by shelf, whenever a new box arrives — a visitor mid-aisle might see three old items and two new ones on the very same shelf. A museum does not work that way. Overnight, while the building is empty, the whole exhibition changes at once; a visitor at 9am the next morning sees either all of yesterday's pieces or all of today's, never a mix, because the swap only ever happens between visits.

That is exactly the promise ngsw-worker.js makes about your app. It never serves v1's HTML next to v2's JavaScript — the classic broken-deploy bug this entire engine exists to prevent. Every file in a build is hashed into one manifest, ngsw.json, and the worker treats that whole set as one version: complete, immutable, and swapped in only when a tab is willing to reload.

Generate, hash, freeze, swap. ng build generates the manifest, every file gets hashed, that whole hashed set is frozen as one version, and a running tab only ever swaps onto a new one when it explicitly asks to. Skip any one of those four and the guarantee breaks.

The mechanism

One CLI command, one provider.

ng add @angular/pwa writes the manifest, the icons and ngsw-config.json, and wires the one provider that actually registers the worker. Nothing about caching strategy lives in this file — that is what ngsw-config.json is for, in the next section.

The worker is disabled in ng serve and only activates in a production build served over HTTPS (or localhost). Test it with ng build plus any static file server. A caching bug that "survives" your fix is almost always a stale worker — unregister it from DevTools → Application → Service Workers, or bump the version.

Question 1 of 3 · what answers the request

Which file answers a request nobody wrote a route for?

Every navigation your router handles — a deep link, a bookmark, a browser back button — is, from the worker's point of view, just another request. It is not looking at your Routes array; it has never heard of it. It is running a much simpler check against four fields at the top of ngsw-config.json.

The one file the worker is allowed to hand back for a navigation request it decides to answer itself. Almost always your SPA shell. Versioned build files, hashed and grouped by how eagerly to cache them — prefetch or lazy. Runtime API responses, cached by their own strategy and maxAge — independent of the app's version. The include/exclude patterns deciding which navigations even reach the index fallback above.
The classic trap: a same-origin OAuth redirect (/auth/callback) or a stray client-side navigation into /api/... is, to the worker, indistinguishable from a deep link. Forget to exclude it from navigationUrls and it gets swallowed by the index fallback — the browser lands on the Angular app shell instead of the real response, and nothing throws or logs anything.

Question 2 of 3 · what gets cached

assetGroups ship with you. dataGroups don't.

This is the split the whole rest of the config hangs off. An assetGroup file exists the moment ng build finishes — it has a name, a hash, a known size, before a single request has been made. A dataGroup URL is a promise about something that only exists at runtime: your server might return something different on every call, and the worker has never seen the bytes until the first real request goes out.

What a dataGroup will not do

GET (and HEAD) only

A POST-based search endpoint is never cached, no matter what the config says — dataGroups don't intercept mutating requests at all.

Opaque cross-origin responses

A response from another origin with no CORS headers is opaque — its body is invisible to the worker, so by default it isn't cached. cacheOpaqueResponses: true overrides that, and you accept you're caching bytes you can't inspect.

The query string is part of the key

?page=1 and ?page=2 are two entries, not one, by default. Only set cacheQueryOptions: {{ '{ ignoreSearch: true }' }} when every variant really is the same resource.

Contrast this with the Server-Side Rendering lesson's transfer cache, which exists for a completely different purpose and — unlike this one — can include POST bodies in its key. Two similarly-named "cache the response" knobs in this app behave differently; do not assume one taught you the other.

Question 3 of 3 · how a tab finds out

Deploying doesn't touch a single open tab.

A running tab keeps its version until it reloads. That is the atomic-update guarantee from the analogy above, seen from the other side: nothing pushes a change into a page that is already open. Everything that happens next is a tab asking, or an app author wiring up code that asks on the tab's behalf.

An ops engineer leaves a status dashboard open on a wall-mounted monitor and never touches it again. Over the next two weeks your team ships four deploys. Before you scroll: how many of those four versions does that tab ever run?

Beyond the three questions

Or skip the browser tab entirely.

Caching and updates are what make a PWA work offline. Installability is what makes it feel like an app — its own icon, its own window, no address bar. The criteria are separate from everything above and all of them have to be true at once:

  • Served over HTTPS (or localhost).
  • A linked manifest.webmanifest with a name, a start_url, and at least a 192×192 and a 512×512 icon.
  • display set to standalone, fullscreen or minimal-ui — browser disqualifies it.
  • A registered, working service worker. Angular's generated one qualifies automatically.

When your app is also server-rendered

Both lessons in this slice can be true at once.

Nothing about ngsw-config.json knows or cares whether index.html was rendered on a server per request or shipped as one static file — it only knows the URL it's asked to fetch. That makes it easy to get badly wrong the moment both are in play.

  • The asset manifest still hashes your client bundle. Enabling server rendering doesn't change what assetGroups track.
  • Never assetGroup-cache server-rendered HTML for a personalised route. An assetGroup serves the exact same cached bytes to everyone — cache one user's dashboard that way and the next visitor gets it too.
  • Set navigationRequestStrategy: "freshness" (from the manifest above) to restore genuine per-request SSR: the worker asks the network first for every navigation, and only serves the cached index as an offline fallback — the best of both, at the cost of losing the instant response "performance" gives a pure SPA.
  • The service worker has no opinion about hydration — it only decides which bytes reach the browser. But serving a stale cached shell to a client expecting to hydrate against fresh server state is exactly the kind of mismatch that produces a hydration error, so the two lessons are worth reading together.

Production gotchas

Where to look when it's serving the wrong thing.

  • /ngsw/state — visit it in the running app: the worker reports its current versions, clients and update status. First stop for "why is it serving old code" — and it's the same Cache Storage stack from the diagram above, in plain text.
  • ngsw-bypass — add the header (or query param) to any request and the worker steps aside entirely. Essential when you suspect an API call is being served from cache.
  • The safety worker — a broken deployed worker can pin users to a bad version forever. Angular ships safety-worker.js: deploy it at the same URL to unregister the worker and clear its caches, for everyone, unconditionally.
  • Never cache what you can't hash. External CDN scripts added to an assetGroup via urls are cached but never hash-verified — prefer bundling them, or a dataGroup with a short maxAge instead.
  • index.html must not be aggressively CDN-cached. The worker bootstraps from it; an edge cache serving week-old HTML defeats the entire update mechanism regardless of how correct your ngsw-config.json is.

Questions from the back row

Before you go

Six things to remember.

  • There's no hand-written worker here. You write JSON; one generated ngsw-worker.js interprets it against one hashed manifest, ngsw.json.
  • Updates are atomic and hash-verified: a tab keeps its version until it reloads, and a version that fails a single hash check never activates at all.
  • assetGroups cache the files that ship with your build; dataGroups cache runtime API responses — GET only, and the query string is part of the cache key.
  • navigationUrls decides which navigations get the index fallback. Exclude anything that isn't your app shell — /api/**, an OAuth callback — or it gets silently swallowed.
  • Check SwUpdate.isEnabled before you do anything else; poll checkForUpdate() for long-lived tabs; activateUpdate() plus a reload are both required to actually run the new code.
  • Getting installed is beforeinstallprompt + preventDefault() + your own button + prompt()/userChoice — and iOS has none of it; Add to Home Screen is the only path there.
