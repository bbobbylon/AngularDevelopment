hostDirectives lets a component — or another directive — put someone else's behavior directly onto its own host element: no base class, no wrapper element, no consumer who has to remember an attribute. It happens entirely at compile time, and almost every rule about what is and isn't allowed is enforced by the compiler, not by convention. This lesson builds one card from a hover behavior and a colour behavior, live, then takes apart every rule the compiler is quietly checking on your behalf — including the one people still get wrong three directives deep.

The problem

Two behaviors, one component. Now what?

Say you want a card that lifts a little on hover. Fine — write a directive, Elevate, that holds the host bindings for that. Now say you also want a card with a coloured accent stripe. Also fine — write Accent. Now you want one card with both, and TypeScript answers the question before Angular ever gets a say: a class can only extend one base class.

If Hoverable and Accentable were both base classes, how would FancyCard extend both at once? There's no good answer — and that gap is the entire reason this API exists.

The mental model

A host directive is a costume, not your DNA.

Inheritance writes behavior into a class's DNA — every instance is born with it, and there's exactly one bloodline to be born into. A host directive is closer to a costume: you can put more than one on at once, you can put it on something that was never designed to wear it, and taking it off doesn't require rewriting who the wearer fundamentally is. hostDirectives doesn't change what class FancyCard is — it changes what's attached to FancyCard's own host element, the very tag the component already renders.

Costume, not DNA. Inheritance bakes behavior in, once, at birth, from one bloodline. hostDirectives puts it on, as many times as you like, from the outside.

The mechanism

Composing behavior in, one line at a time.

Five separate facts are hiding in those twenty lines. Pin them down explicitly:

The compiler inlines hostDirectives into the component's own definition. The array has to be statically analyzable — no ternaries, no pushing to it later. Every host directive is constructed before the host component, in array order. Their ngOnInit/ngOnDestroy all run, interleaved by that same order. A host directive is a normal provider on the element injector. The host can inject() it; it can inject() the host back with forwardRef. The composed behavior lands on the existing host element. CSS layout, the a11y tree and any querySelector see nothing different. A directive can declare its own hostDirectives. Behavior nests arbitrarily deep — exactly how the CDK builds its menu and button primitives. There's a whole section on this below.
The array must be statically analyzable. No ternary, no [...conditional], no pushing to it at runtime — the compiler reads it once, at build time. Need to choose directives at runtime instead? That's a different API, and it's a few sections away.

Private by default

Composed behavior doesn't leak out on its own.

Elevate's lifted signal and its liftedChange output exist whether or not FancyCard does anything about them. But bind (liftedChange) directly on <app-fancy-card> in a consumer template, without changing FancyCard itself, and it won't compile. Composed behavior is private by default — the host has to deliberately hand each piece of it back out, optionally under a new name.

Exam corner

Five compile-time guardrails, not five conventions.

Everything so far has been about what hostDirectives lets you do. The compiler also enforces a short list of things it will not let you do — silently, at build time, long before a user could ever see a broken card.

The five diagnostics guarding `hostDirectives`
Code Fires when… The fix
NG2014 the listed directive isn't standalone every host directive must compile standalone — there's no NgModule context left to resolve one through
NG2015 you listed a @Component, not a @Directive only directives compose this way — a component needs its own template and host element
NG2017 you re-exported an input/output name the directive doesn't declare check the spelling against the directive's own input()/output() names
NG2018 your alias collides with a name the host already has two bindings can't answer to one name — rename the alias or the host's own field
NG2019 the directive has an input.required() you never exposed expose it — there is otherwise no way for any consumer to ever set it

Three levels deep

Composing a composition? Exposure doesn't skip a level.

A directive can list its own hostDirectives, and a component can compose a directive that does that. Nothing stops the chain going three, four, five levels — but exposure is decided fresh at every single hop, and nothing carries through automatically.

The one exception

It's compile-time — mostly.

The intro table called hostDirectives static, and within its own metadata it still is: no conditionals, no runtime pushes. But if you're already creating a component dynamically — the Dynamic Components lesson covers ViewContainerRef.createComponent() in full — you can choose its directives at that same moment, complete with a live signal binding.

Where you've already used it

The CDK is built out of exactly this.

CdkMenuItem composes focus and typeahead behavior into every menu item; Material buttons compose ripple and interactivity directives the same way. The pattern to copy: keep each behavior a small, independently testable directive, then assemble components — and other directives — from them.

Questions from the back row

Before you go

Six things to remember.

  • Nothing gives a class more than one base class. hostDirectives is composition, not inheritance — behavior goes ON the host; it isn't inherited into it.
  • Inputs and outputs are private until re-exported, optionally under a new alias. That isn't an oversight — it's the API boundary composition is built on.
  • Same host property, two directives? Later in the array wins. The component's own host binding beats every host directive, always.
  • Five compiler diagnostics guard this at compile time — NG2014 (not standalone), NG2015 (not a directive), NG2017 (unexported name), NG2018 (alias collision), NG2019 (unexposed required input). None of them are runtime surprises.
  • Exposure doesn't skip a level. A three-hop composition needs the input relayed — and possibly renamed — at every single hop, independently.
  • hostDirectives is compile-time and static. Need to choose directives at runtime instead? That's createComponent()'s directives array, not this.
