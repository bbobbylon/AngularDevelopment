With SSR, Angular renders your components to real HTML on a server, so the browser paints something real the instant the response arrives — before a single line of your JavaScript has executed. This page is about earning that first paint: turning the capability on, choosing it per route, writing code that survives actually running in Node, and the trap of assuming SSR did more than it did. What the client does with that HTML once its own JavaScript finally shows up is a different lesson's job — hydration's, covered next.

The whole bug, in one picture

Node has no browser in it at all — no window, no document, no localStorage. The single most common real SSR bug is code that quietly assumes otherwise, and it doesn't warn — it takes the entire response down.

It throws — a ReferenceError: window is not defined — and that takes down the entire response for every visitor who hits the route, not a warning tucked into a console only you would see. window, document, localStorage and navigator simply do not exist in the Node process doing the rendering, and nothing polyfills them by default. The fix is not scattering existence checks everywhere — it is moving the line into a browser-only slot, afterNextRender() or a platform guard.

A restaurant's kitchen has ovens and knives — no tablecloths, no dining-room lighting, nothing that only makes sense once a guest is seated. Ask the kitchen to do something that belongs to the dining room and there is simply nothing there to do it with. Node is the same kind of place: a process, a filesystem, a network stack — no window, no document, no browser at all. Code that only makes sense in a browser has to wait for the dining room, the same way plating a dish for a table that doesn't exist yet never works.

The problem

Your JavaScript hasn't even downloaded yet. What's on screen?

Ship an Angular app the plain way and the server's answer is almost nothing. It sends one HTML file with an empty <app-root></app-root> in it, and everything a visitor actually sees has to wait for a chain of events: download the bundles, parse them, boot Angular, run change detection, then — usually — fire off an HTTP request and wait for that before there's real content on the screen. A slow connection or a search-engine crawler that doesn't execute JavaScript sees a blank page and nothing else.

Server-side rendering answers a narrower question than people think it does: not "how do I make my app faster," but "how do I make the very first thing the browser paints not be blank."

Two visitors load the same product page: one over CSR, one over SSR. Both are on a slow connection, and both are running the exact same client JavaScript bundle. Whose bundle finishes downloading first? Flip through the three strategies below and watch where each one's FCP marker lands relative to the JS download step — the answer is not what most people guess.

The mental model

SSR is a restaurant that plates your appetizer in the kitchen.

Picture two restaurants. In the first, you sit down and your appetizer lands on the table almost immediately — it was cooked out of sight, in the kitchen, before you even arrived. In the second, the chef wheels a portable stove to your table and cooks from scratch in front of you: no food at all until several minutes of chopping and searing finish first. Both restaurants serve exactly the same dish. The only thing that differs is when you get to look at it.

The second restaurant is plain client-side rendering: your browser is the chef, cooking at your own table, and it cannot start until every raw ingredient — the JS bundles — has actually arrived in the room. The first is SSR: the kitchen (a Node server) does the same cooking somewhere you can't see, using the same recipe, and what reaches your table is already-finished HTML. Nothing about the size of the kitchen or the recipe changed — only where and when the cooking happened.

And here's the part that trips people up: hiring a kitchen doesn't mean you fire the chef at the table. The exact same client bundle still ships, still has to arrive, and still has to do its own cooking once it gets there — taking over from the plated appetizer so the rest of the meal (interactivity) can happen. That takeover is what the next lesson, hydration, is entirely about.

Same dish, earlier table. SSR moves where the first course gets cooked — never what's on the menu. The same client bundle still has to arrive and take over; that hand-off is hydration's job, not SSR's.

The mechanism

Turning the kitchen on is one provider and one class.

SSR isn't the default — a plain Angular app has no kitchen at all until you add one. Here's the whole thing: the config that turns it on, and — underneath that config — the class actually doing the cooking.

The build now ships two bundles. A browser bundle (same as always) and a server bundle, plus a small Node entry point you deploy or adapt. ng serve renders through the server engine in development too, specifically so SSR bugs surface immediately instead of after a deploy.

The real architecture decision

Not every page needs the same kitchen.

Modern Angular doesn't force one strategy on the whole app. A ServerRoute[] table assigns each route its own RenderMode — so a single deployment mixes static marketing pages, per-request SSR, and client-only authenticated areas without contradiction.

Rendered once, at build time, into a real .html file. Zero per-request compute — the fastest possible delivery for content that's identical for every visitor. The same engine.render() call from above, run again for every request. Right for content that's fresh, personalized-but-crawlable, or too large a param space to prerender. No server render at all — the plain CSR shell from the top of this page. For content that gains nothing from being pre-painted, like a dashboard sitting behind a login wall.

The exam trap

    
There's no window, document or localStorage in that kitchen.


    

      Node has no browser globals at all — no layout engine, no window, no document, no
      localStorage, no navigator. The single most common real SSR bug is code that touches one
      of these unconditionally, because it works perfectly in the browser and nobody thinks to ask what happens on the
      other side of the fence.

A second, quieter trap

    
A leaked timer doesn't die when the "page" does.


    

      A crash is the easy failure to catch — it shows up in every log, on the very first request. This one doesn't. A
      server render isn't a browser tab: closing a tab tears down its entire JavaScript context, timers included.
      Finishing an SSR response does not do that. The Node process serving that request
      keeps running, and keeps running, and serves the next ten thousand requests in the exact same process.
    


    

      Stability trap, restated: the server also waits for the app to become stable (pending
      HttpClient requests resolved, no queued macrotasks) before it will serialize anything at all. An
      innocent setInterval started in a constructor doesn't just leak later — it can hang
      that very render until a timeout fires. Start recurring timers in afterNextRender so they
      only ever exist in the browser.
    


    
  


  
  

    
Killing the double fetch

    
The server already has the data. Don't ask twice.


    

      The server fetched your data to render the page — and then the client app boots and, left to its own devices,
      fetches the same data again. The HTTP transfer cache is what stops that: server-side
      HttpClient responses are embedded in the HTML and replayed as instant cache hits during hydration,
      then discarded once they've served their purpose.
    


    

    

      Every win above is also a data-leak vector for a personalized response.
      The cache isn't a server-side memory trick — it's embedded straight into the page as a
      <script id="ng-state"> tag, which means anything cached is visible to
      anyone who receives that HTML: view-source, a shared proxy, a saved copy, a CDN edge node. Two escape
      hatches: withNoHttpTransferCache() turns the whole mechanism off for routes where it isn't worth the
      risk, and the rule to actually live by is
      personalized route ⇒ Cache-Control: private (or skip server rendering for it
      entirely with RenderMode.Client) — the transfer cache should never be the thing standing between a
      shared cache and someone else's data.
    


    
  


  
  

    
Seen in real deployments

    
The mistakes that actually ship.


    
    
      
  • 
        Auth-gated APIs return 401 during SSR — the server's HttpClient does not
        automatically forward the user's cookies. Read them from the REQUEST token and attach them
        explicitly, or make those routes RenderMode.Client.
      
    • 
      
  • 
        Absolute vs relative URLs — on the server, a relative /api/… URL has no origin to
        resolve against unless the server entry configures one. An interceptor that prefixes the API origin is the
        standard fix.
      
    • 
      
  • 
        Memory leaks are amplified — the exact trap from the quiz above. A leak that costs one browser
        tab now costs a long-running Node process serving every visitor. Clean up in DestroyRef/ngOnDestroy
        religiously.
      
    • 
      
  • 
        Different output per render — randomness or timestamps in a template make the server's HTML
        differ from the client's first render; that's a hydration mismatch, covered fully in the
        hydration lesson.
      
    • 
      
  • 
        Prerender plus late data — an SSG page is frozen at build time. If its data changes hourly,
        either rebuild on a schedule, switch that route to RenderMode.Server, or fetch the volatile part
        client-side.
      
    • 
    

  


  
  

    
Pulling it together

    
What SSR buys you — and what it never promised.


    

      

        
Buys

        
    
          
  • Real HTML in the very first response — visible before any JS downloads
    • 
          
  • Content search-engine crawlers and link-preview bots can actually read
    • 
          
  • A faster first paint, specifically
    • 
          
  • Per-route control: static, per-request, or skip it entirely
    • 
        

      

      

        
Doesn't buy

        
    
          
  • A smaller client JavaScript bundle — it's exactly the same bundle either way
    • 
          
  • Skipping hydration or its rules — the same client app still has to boot and adopt the DOM
    • 
          
  • Freedom from SSR-unsafe code — window, timers and cookies are still the server's problem
    • 
          
  • A faster app overall — only a faster first paint
    • 
        

      

    


    
      SSR buys a faster first paint and crawlable HTML. It never buys a smaller client bundle, skips a
      single SSR-safety rule, or does hydration's job for it.

Before you go

    
Six things to remember.


    
    
      
  • 
        SSR moves where the first render happens, not how much JavaScript ships — the
        same client bundle still has to arrive and hydrate.
      
    • 
      
  • 
        Turning it on is one provider, provideServerRendering(), plus a route table. The real work happens
        inside CommonEngine's render(), once per request that isn't prerendered.
      
    • 
      
  • 
        Prerender bakes one HTML file per param set at build time; Server re-renders
        every request; Client opts a route out entirely — pick per route, not per app.
      
    • 
      
  • 
        No window, document, localStorage or navigator on the
        server. Guard with isPlatformBrowser() when logic must branch; reach for
        afterNextRender() for anything that just needs the DOM.
      
    • 
      
  • 
        A leaked timer doesn't die with the "page" the way it would in a closed browser tab —
        it keeps running in the same long-lived Node process, compounding with every request.
      
    • 
      
  • 
        The HTTP transfer cache stops the client re-fetching data the server already fetched;
        TransferState is the manual version for anything that skipped HttpClient.
