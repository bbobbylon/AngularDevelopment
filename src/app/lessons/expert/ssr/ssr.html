Server-Side Rendering (SSR)

With SSR, Angular renders your components to HTML on the server, so the browser paints real content before a single byte of JavaScript executes — then the same app boots on the client and hydrates the existing DOM. This page covers the three delivery strategies, per-route render modes, SSR-safe coding patterns, and the transfer cache that prevents double-fetching.

Writing SSR-safe code

On the server there is no window, document, localStorage, navigator, or layout engine. The number-one SSR bug is touching them during construction or rendering — the render crashes (or silently produces wrong HTML) for every request:

Need SSR-safe tool
Measure/manipulate the DOM after paint afterNextRender() — browser-only by design, never runs on the server
Branch logic per platform isPlatformBrowser(inject(PLATFORM_ID))
Read the incoming request (cookies, headers) inject REQUEST (Angular's server DI tokens)
Third-party browser-only library dynamic import() inside afterNextRender, or @defer the component using it
Storage cookies (exist on both sides) or guard localStorage behind a platform check
Stability trap: the server waits for the app to become stable (pending HttpClient requests resolved, no queued macrotasks) before serializing. An innocent setInterval started in a constructor keeps the app unstable — the server render hangs until a timeout. Start recurring timers in afterNextRender so they only ever exist in the browser.

The double-fetch problem & the transfer cache

The server fetched your data to render the page — then the client app boots and fetches the same data again. Angular solves this with the HTTP transfer cache (on by default with provideClientHydration()): server-side HttpClient responses are embedded in the HTML and replayed as instant cache hits during hydration, then the cache is discarded:

For non-HttpClient data (a database read in a server route, a heavy computation), use TransferState directly with makeStateKey — same mechanism, manual keys.

Pitfalls seen in real deployments

  • Auth-gated APIs return 401 during SSR — the server's HttpClient does not automatically forward the user's cookies. Read them from the REQUEST token and attach explicitly (or make those routes RenderMode.Client).
  • Absolute vs relative URLs — on the server, a relative /api/... URL has no origin to resolve against unless the server entry configures one. Interceptor that prefixes the API origin is the standard fix.
  • Memory leaks are amplified — a leak that costs one browser tab now costs a long-running Node process serving every user. Clean up in DestroyRef/ngOnDestroy religiously.
  • Different output per render — randomness or timestamps in templates make the server HTML differ from the client's first render; that's a hydration mismatch (covered in the Hydration lesson).
  • Prerender + late data — an SSG page is frozen at build time; if its data changes hourly, either rebuild on a schedule, switch that route to RenderMode.Server, or fetch the volatile part client-side.

Exam corner

When would you choose Prerender over Server rendering?
When the page is the same for every visitor at request time — marketing pages, docs, blog posts, enumerable product pages. It's rendered once at build (per param set via getPrerenderParams) and served statically: no per-request compute, best TTFB. Server mode is for per-request/personalized-but-crawlable content.
Why did the SSR response take 30 seconds, then render fine?
Something kept the app from becoming stable — usually a recurring timer or a never-completing observable tied to a macrotask started during bootstrap. The server waits for stability before serializing. Move timers into afterNextRender.
How does Angular avoid fetching data twice (server + client)?
The HTTP transfer cache: server-side HttpClient responses are serialized into the HTML and replayed on the client during hydration. Enabled by default with provideClientHydration(); tune with withHttpTransferCacheOptions() (e.g. include POST or requests with auth headers). Manual data goes through TransferState.
Where does localStorage access belong in an SSR app?
Behind a browser boundary: inside afterNextRender(), or guarded by isPlatformBrowser. On the server it doesn't exist — unguarded access throws for every request.

Key takeaways

  • SSR renders per request; prerender renders at build; client mode opts a route out — mix all three via ServerRoute configs.
  • FCP happens before JavaScript with SSR/SSG; crawlers and previews see real HTML.
  • Guard browser globals (afterNextRender / isPlatformBrowser); keep timers out of bootstrap or the server render hangs.
  • The HTTP transfer cache kills the double fetch; TransferState is the manual escape hatch.
  • Server-side HttpClient forwards no cookies by itself — handle auth explicitly.
