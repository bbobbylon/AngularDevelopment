Every Angular app collects values that change over time and has to decide, for each one, where it lives and who is allowed to change it. Get those two questions right with a plain @Injectable and you may never need a state-management library at all. Get them wrong, and no library saves you. This page builds the pattern from a single private field up to the point where a library actually starts paying for itself.

The problem

Two components need the same answer. Where does it actually live?

Picture two components that have never met. CartIcon, in the header, shows a badge with the number of items in the cart. CartPage shows the full list, with an "Add to cart" button. Click that button, and the badge has to change too — even though neither one has a parent that passes anything down between them.

That's state in its plainest form: a value that changes over time, which more than one part of the UI needs to agree on. The moment two components need the same answer, an @Input stops being enough — there's no parent in the middle to hand it through.

Three questions decide the whole architecture from here: where does this value live, who's allowed to write it, and when do you need more ceremony than a class with some signals? This page takes them in that order.

If CartIcon and CartPage each declared their own signal<CartItem[]>([]), what would the badge show after you click "Add to cart" on the page? What do you think has to change about that setup before the two views can agree on anything?

The mental model

A signal store is a bank, not a filing cabinet.

A filing cabinet has no rules: anyone who can reach it can pull out a folder and scribble in it. A bank has three things a filing cabinet doesn't. A vault nobody but staff can enter. A lobby display anyone can glance at. And exactly one counter where change actually happens — you fill out a slip, hand it to a teller, and the teller updates the ledger.

That's not decoration, it's the whole reason a signal store beats "a service with some public fields." Nothing stops a component from writing garbage into a public field. Plenty stops it from writing garbage into a private one it cannot even see.

Vault, board, counter — or in code: a private signal, an asReadonly() projection, and one named method per action. Nearly every state-management bug is one of those three going missing.

The mechanism

The whole pattern is four lines with a rule attached.

Strip away the demo and the library options, and a signal store is always the same four moves: a private writable signal, a asReadonly() projection of it, a computed() for anything derived, and a named method for every way it's allowed to change.

Never export the writable signal, even by accident. readonly items = signal([]) — no .asReadonly() — means nothing stops store.items.set(garbage) from any component that injects this store. The whole contract lives in that one method call.
update((list) => [...list, x]), never list.push(x). A signal only notices a new reference — the contents changing under the same reference is invisible to it. The change detection lesson is the mechanism behind why.

Question 1 · scope

How far should one piece of state be allowed to travel?

Local state lives in one component — a tooltip's open flag, a form's dirty bit — and is a plain signal field. Feature state is shared by a handful of components in one area (a cart, a wizard) and wants a store scoped to that subtree. Global state — auth, theme, notifications — wants a store that outlives any one screen.

One more job for the store

Who talks to localStorage?

Persistence is a side effect, and a store is exactly where it belongs — one place syncing to storage, instead of every consumer remembering to. Hydrate once, when the store is built; sync back with an effect().

When you outgrow this

Same contract, more ceremony — is it worth it?

One class you already know how to read: fields, a constructor, methods.

Encapsulation is one keyword — private — not a folder of action creators and selectors.

Nothing to wire up beyond @Injectable; no devtools extension required to see what happened.

Every change is an action — a typed record of intent, logged and replayable.

A reducer is the only thing allowed to touch state, and it must be pure — this is what makes time-travel debugging possible at all.

Effects isolate the impure work (HTTP, timers) so the reducer never has to be async.

@ngrx/signals sits between the two: the same private-write/public-read shape, generated by composing with* features instead of hand-writing the class.

Classic NgRx is the full ceremony — and the two mistakes that actually cost people time:

Matching the tool to the situation
Situation Recommended approach
One component needs transient UI state Plain signal field
A feature's components share state (cart, wizard) Signal store, listed in that feature's providers

The other kind of state

Server data needs the same rules, not new ones.

A fetched value is state too, and hand-rolling a loading/error/data triple in every store is boilerplate the signal era has an answer for.

Read-only, synchronous, cached. Use it whenever the value can be worked out from other signals with no I/O. Derived AND user-writable. The one primitive for "start from this default, but let the user override it." Same idea as computed, but the derivation is asynchronous — loading/error/data come built in.

Rule of thumb: computed for pure derivations, linkedSignal when the derived value must also be user-writable, resource when the derivation itself is asynchronous. All three slot straight into the store pattern above — nothing about them replaces private-write/public-read, they're just more shapes state can take.

Questions from the back row

Before you go

Five things to remember.

  • Classify state before reaching for a tool: local → a component field, feature → a store scoped to that subtree's providers, global → a store at the root.
  • The contract behind every signal store: private writes, public reads, named mutations, derived values via computed(). Break any one of those four and the encapsulation is gone.
  • A signal only notices a new reference. update((l) => [...l, x]) renders; l.push(x) changes the data and renders nothing.
  • Persist with an effect() created in the constructor, syncing from the store; hydrate by reading storage in the signal's field initializer, not in ngOnInit().
  • Reach for @ngrx/signals or classic NgRx only once you feel the pain a plain store doesn't solve — an action log, time-travel debugging, or a team too large to coordinate by convention alone.
