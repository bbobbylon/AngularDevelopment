State Management

Every Angular app manages state — values that change over time and drive the UI. Choosing where that state lives and who can change it is one of the most consequential architecture decisions you make.

The three tiers of state

Think of state in three buckets before reaching for any library:

Local / UI state

Lives inside one component. Tooltip open, tab index, form dirty flag. Use a plain signal or class field.

Feature / shared state

Several components in a feature share it (cart, current user). Use a signal store service.

Global / cross-feature state

Auth session, theme, notifications. Signal store with providedIn: 'root' or NgRx.

The signal store pattern (no library needed)

A signal store is just an @Injectable that owns private writable signals, exposes read-only signals and computed selectors, and mutates state only through explicit methods. Components inject it and read; they never write directly. 

@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class CartStore {{ '{' }}
  // --- private writable state ---
  private readonly _items = signal<CartItem[]>([]);
  private readonly _coupon = signal<string | null>(null);

  // --- public read-only projections ---
  readonly items   = this._items.asReadonly();
  readonly coupon  = this._coupon.asReadonly();

  // --- derived / computed selectors ---
  readonly subtotal = computed(() =>
    this._items().reduce((s, i) => s + i.price * i.qty, 0)
  );
  readonly discount = computed(() =>
    this._coupon() === 'SAVE10' ? this.subtotal() * 0.1 : 0
  );
  readonly total = computed(() => this.subtotal() - this.discount());

  // --- mutations: one clear entry-point per action ---
  addItem(item: CartItem) {{ '{' }}
    this._items.update(list => {{ '{' }}
      const exists = list.find(i => i.id === item.id);
      return exists
        ? list.map(i => i.id === item.id ? {{ '{' }} ...i, qty: i.qty + 1 {{ '}' }} : i)
        : [...list, {{ '{' }} ...item, qty: 1 {{ '}' }}];
    {{ '}' }});
  {{ '}' }}
  removeItem(id: number) {{ '{' }} this._items.update(l => l.filter(i => i.id !== id)); {{ '}' }}
  applyCoupon(code: string) {{ '{' }} this._coupon.set(code.toUpperCase()); {{ '}' }}
  clearCart() {{ '{' }} this._items.set([]); this._coupon.set(null); {{ '}' }}
{{ '}' }}
The contract that makes this pattern work: writable state is always private, mutations go through named methods, and derived values use computed(). Any component can inject the store but none can break its invariants.

Persisting state to localStorage

Hydrate from storage in the constructor; sync back in an effect:

@Injectable({{ '{' }} providedIn: 'root' {{ '}' }})
export class ThemeStore {{ '{' }}
  // HYDRATE — the signal's initial value comes straight from storage, so the
  // correct theme is in place before the first render. Read it in ngOnInit
  // instead and the user sees a flash of the wrong theme.
  private readonly _theme = signal<'light' | 'dark'>(
    // getItem returns `string | null`. The cast narrows it to the union, and
    // ?? 'light' covers the first visit. (A cast is a promise to the
    // compiler, not a check — a junk value in storage would slip through.)
    (localStorage.getItem('theme') as 'light' | 'dark') ?? 'light'
  );
  readonly theme = this._theme.asReadonly();

  constructor() {{ '{' }}
    // SYNC BACK — an effect must be created in an injection context, which
    // the constructor provides. It runs once immediately, then again after
    // every change to a signal it read.
    effect(() => {{ '{' }}
      // Reading _theme() here is what SUBSCRIBES this effect to it. Tracking
      // is automatic and dynamic: no dependency array to keep in sync.
      // Persistence is exactly the right job for an effect — a side effect
      // on the world outside Angular. Deriving a value is not; use computed.
      localStorage.setItem('theme', this._theme());
    {{ '}' }});
  {{ '}' }}
  // The only writer. update() receives the current value and returns the next.
  toggle() {{ '{' }} this._theme.update(t => (t === 'light' ? 'dark' : 'light')); {{ '}' }}
{{ '}' }}

NgRx Signal Store — when you want structure

@ngrx/signals wraps the same pattern with conventions: typed state slices, built-in entity management, and RxJS-powered side effects. The shape is identical in concept — private writes, public reads — but the toolkit gives you entity CRUD helpers, devtools integration and a consistent team API. 

// with @ngrx/signals (separate package — install first)
import {{ '{' }} signalStore, withState, withComputed, withMethods {{ '}' }}
  from '@ngrx/signals';

// signalStore() returns a class you can inject — the `with*` calls are
// composable features applied in order, each one adding to the store's type.
export const TodoStore = signalStore(
  // Same option you'd pass to @Injectable.
  {{ '{' }} providedIn: 'root' {{ '}' }},
  // withState defines the state slice. Every top-level key here becomes a
  // signal on the store automatically — you get store.todos() and
  // store.filter() for free, no boilerplate declarations.
  withState({{ '{' }} todos: [] as Todo[], filter: 'all' as Filter {{ '}' }}),
  // withComputed receives the store built so far, so `s.todos` already exists
  // and is fully typed. This is the equivalent of an NgRx selector.
  withComputed((s) => ({{ '{' }}
    remaining: computed(() => s.todos().filter(t => !t.done).length),
  {{ '}' }})),
  // withMethods is where the writers live — the store's public API.
  withMethods((store) => ({{ '{' }}
    add(title: string) {{ '{' }}
      // patchState is imported from '@ngrx/signals' — shallow-merges a partial
      // of the state, so you name only the keys you're changing and `filter`
      // is left alone. Note the spread: same immutability rule as raw signals.
      patchState(store, {{ '{' }} todos: [...store.todos(), mk(title)] {{ '}' }});
    {{ '}' }},
  {{ '}' }}))
);

NgRx Store — Redux for large teams

Classic NgRx (actions → reducers → selectors → effects) shines when you need a strict, auditable flow, time-travel debugging, or a large team that must reason about all state changes via an action log. 

// ---- ACTIONS: every state change is one of these, and nothing else ----
// The '[Source] Event' string convention is what makes the devtools log
// readable: you can see at a glance WHERE an action came from.
export const loadTodos    = createAction('[Todos] Load');   // no payload — just "go"
// props<T>() declares the payload shape. Dispatch the wrong shape and it
// fails to compile, which is most of NgRx's safety in one line.
export const todosLoaded  = createAction('[Todos] Loaded', props<{{ '{' }} todos: Todo[] {{ '}' }}>());
export const todosFailed  = createAction('[Todos] Failed', props<{{ '{' }} error: string {{ '}' }}>());
// THREE actions for one request — that trio (start / success / failure) is
// the pattern for every async operation in Redux-style state.

// ---- REDUCER: (state, action) => new state. Pure. Synchronous. ----
export const todosReducer = createReducer(
  // Argument 1 is the initial state.
  {{ '{' }} todos: [] as Todo[], loading: false, error: '' {{ '}' }},
  // Each on() maps an action to a handler. `s` is the current state, `a` the
  // action. Every handler SPREADS the old state and returns a NEW object —
  // never mutates — which is what powers time-travel debugging.
  on(loadTodos,  (s)    => ({{ '{' }} ...s, loading: true  {{ '}' }})),
  on(todosLoaded,(s, a) => ({{ '{' }} ...s, loading: false, todos: a.todos {{ '}' }})),
  // Note both terminal handlers clear `loading`. Miss one and the spinner
  // spins forever — the single most common NgRx bug.
  on(todosFailed,(s, a) => ({{ '{' }} ...s, loading: false, error: a.error  {{ '}' }})),
);

// ---- SELECTORS: how components READ. Plain functions of the whole state ----
// Components never reach into state.todos.todos themselves; they subscribe to
// a selector, so the state shape can be refactored without touching them.
export const selectTodos   = (state: AppState) => state.todos.todos;
export const selectLoading = (state: AppState) => state.todos.loading;

// ---- EFFECTS: where the impure work goes. Actions in, actions out. ----
export class TodoEffects {{ '{' }}
  loadTodos$ = createEffect(() =>
    // actions$ is a stream of EVERY action dispatched anywhere in the app.
    this.actions$.pipe(
      // Filter it down to the one we care about.
      ofType(loadTodos),
      // switchMap CANCELS an in-flight request when a new loadTodos arrives —
      // the right choice here, since only the latest result matters. (Use
      // concatMap for saves, where every one must complete.)
      switchMap(() => this.api.getAll().pipe(
        // Success: turn the data into a new action for the reducer.
        map(todos => todosLoaded({{ '{' }} todos {{ '}' }})),
        // Failure: turn the error into an action too. catchError is INSIDE
        // the inner pipe on purpose — put it on the outer stream and one
        // failed request kills actions$ permanently, silently breaking every
        // future load. This is the classic NgRx trap.
        catchError(e  => of(todosFailed({{ '{' }} error: e.message {{ '}' }})))
      ))
    )
  );
{{ '}' }}

Choosing the right tool

Situation Recommended approach
One component needs transient UI state Plain signal field
A feature's components share state (cart, wizard) Signal store service, providers:[Store]
App-wide auth / theme / notifications Signal store, providedIn:'root'
Large team, strict conventions, time-travel devtools NgRx Store
NgRx Store but you'd like signal ergonomics @ngrx/signals signalStore
Every component has its own copy of shared state Anti-pattern — use a shared store
Subjects scattered across multiple services Anti-pattern — consolidate into a store

Common mistakes

Mistake Fix
Expose writable signal: readonly items = signal([]) Use .asReadonly() on the public property
Mutate arrays in place: this._items().push(x) Always use update(l => [...l, x]) — immutable updates trigger CD
Reach for NgRx on a solo/small project Signal store is enough for < 5 devs; add NgRx when the team and complexity justify it
Calling effect() inside a store method effect() is for side-effects triggered reactively; use it in constructor

Async state — resource() and linkedSignal()

Server data is state too, and hand-rolling loading/error/data triples in every store is boilerplate. Two signal-era primitives cover the common shapes: 

// resource(): request params in, async loader out — with status signals built in
readonly userId = signal(1);
readonly user = resource({{ '{' }}
  params: () => ({{ '{' }} id: this.userId() {{ '}' }}),          // reactive — re-fetches on change
  loader: ({{ '{' }} params {{ '}' }}) => fetch('/api/users/' + params.id).then(r => r.json()),
{{ '}' }});
// user.value() · user.isLoading() · user.error() — no manual triple

// linkedSignal(): writable state that RESETS when a source changes
readonly options = input.required<string[]>();
readonly selected = linkedSignal(() => this.options()[0]);
// user picks an option → selected.set(...)  (writable!)
// options input changes → selected resets to the new first option

Rule of thumb: computed for pure derivations, linkedSignal when the derived value must also be user-writable, resource/httpResource when the derivation is asynchronous. All three slot straight into the store pattern above.

Exam corner

Why must the store expose asReadonly() signals instead of the writable ones?
Encapsulation of invariants: with a writable signal any component could set() arbitrary state, bypassing validation, derived-state assumptions and the "one entry-point per action" audit trail. Read-only projections make the named methods the only mutation path — the same reason Redux only allows dispatching actions.
A computed selector doesn't update after this._items().push(x). Why?
Signals compare by reference: push mutates the same array, so the signal's value never "changed" and no consumer is notified. Immutable updates (update(l => [...l, x])) produce a new reference — that's what triggers computed recomputation and view marking.
Feature store vs root store — how do you scope a store to one feature, and what's the lifetime difference?
providedIn: 'root' = one app-wide instance, lives forever. Listing the store in a component's providers (or a lazy route's providers) scopes one instance to that subtree/feature — created with it, destroyed with it. Wizard/cart-per-page state belongs at feature scope; auth/theme at root.
When is classic NgRx genuinely worth its boilerplate over a signal store?
When you need the action log itself: time-travel debugging, audit requirements, many developers coordinating on shared state slices, or complex cross-cutting side-effects modeled as effects listening to the same actions. For most apps below that bar, the signal store gives the same guarantees with a fraction of the ceremony.
Where do side effects (persistence, analytics) belong in a signal store?
In an effect() created in the store's constructor (an injection context), reading the public signals — like the localStorage sync above. Not inside mutation methods (they'd run imperatively and get skipped by other mutation paths), and never in components (every consumer would duplicate the side effect).

Key takeaways

  • Classify state first: local → component field; shared → signal store; global → root store.
  • The contract: private writes, public reads, named mutations, derived via computed().
  • Persist with effect() syncing to localStorage; hydrate in the constructor.
  • Reach for NgRx/ngrx-signals when you need time-travel, strict conventions, or entity helpers.
  • Always update state immutably — spread or filter, never push/splice in place.
