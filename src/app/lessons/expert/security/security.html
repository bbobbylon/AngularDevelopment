Angular sanitizes automatically, and that fact makes people stop thinking about security entirely — which is exactly the gap this page exists to close. You'll watch the sanitizer work on a real attack payload, watch it get bypassed two different ways — one on purpose, one by accident — and then work outward through CSRF, token storage, secrets and the headers only your server can set. Angular's protection stops precisely at the edge of the template, and knowing where that edge is is the whole subject.

The problem

Every text box is a stranger typing directly into your DOM.

A comment field, a display name, a search box, a URL query param — every one of them is a channel an attacker can type into, and every one of them eventually reaches your page as a string. The browser does not know or care where that string came from. If it looks like HTML by the time it lands in the DOM, the browser will happily parse it as HTML — <script> tags, onerror handlers and all.

That is the entire premise of Cross-Site Scripting, and it is also the entire reason Angular exists to stand in the way: every value your template binds is treated as untrusted, sanitized by context, before it ever touches the DOM. The catch — the one this whole lesson is really about — is that "every value your template binds" is a narrower promise than it sounds like.

Two identical attacker strings — <script>alert(1)</script> — go into two different bindings on the same page: one is {{ '{{' }} payload {{ '}}' }}, the other is [innerHTML]="payload". Does either one execute? Do they even look different once rendered? There's a live version further down to check yourself against.

The mental model

Angular is a customs officer, not a wall.

A firewall blocks or allows — one rule, everywhere. Angular's sanitizer behaves more like a customs officer standing at four different doors, applying a different rulebook depending on which door you walked through. The same suitcase gets searched differently at the "text" door than at the "loadable code" door — not because the officer is inconsistent, but because each door leads somewhere with different rules about what's dangerous there.

Those four doors have names — Angular calls them security contexts — and which one applies is decided entirely by where a value is bound, never by what the value contains.

One officer, four rulebooks. Interpolation never even asks — there's no HTML parser in that path at all. [innerHTML] asks "is this a script?" and keeps the rest. [href]/[src] ask "is this scheme executable?" and neuter the ones that are. RESOURCE_URL doesn't ask — it refuses by default until you personally vouch for the value.

The mechanism

Every binding has a context, and every context has its own rules.

Here are the four doors, with the exact syntax that walks a value through each one. Angular decides the context from the binding itself at compile time — SecurityContext.HTML, SecurityContext.URL, SecurityContext.RESOURCE_URL and so on are the enum values DomSanitizer uses internally to remember which rulebook applies where.

The safest binding is the one that never asks a question. Interpolation doesn't pass through an HTML parser at all — it writes to textContent. If you only ever need to display text, not render markup, interpolation isn't just simpler than [innerHTML], it's a strictly smaller attack surface.

The gap nobody warns you about

Leave the template layer, and the sanitizer doesn't follow you.

Everything above proves Angular's bindings are safe. It teaches the wrong lesson by omission, because the XSS bugs that actually ship in production Angular apps almost never come from a binding — they come from code that reaches the DOM some other way: ElementRef.nativeElement.innerHTML, Renderer2.setProperty(el, 'innerHTML', …), document.write, or a jQuery/third-party widget doing its own thing to the page. None of those go through Angular's compiler, so none of them are sanitized — not because Angular forgot, but because it never gets the chance.

The deliberate escape hatch

Sometimes you have to bypass the sanitizer — and then you own the risk.

A legitimate video embed, a PDF preview, a trusted CMS's rich HTML — sometimes you genuinely need to render something the automatic sanitizer would strip. DomSanitizer exposes five methods for exactly this, one per security context. Calling any of them means one thing and only one thing: "I, the developer, personally vouch that nothing in this value is attacker-controlled."

@for (m of bypassMethods; track m.heading) { {{ m.body }} }
Never call bypassSecurityTrust* on user-supplied data, a query param, or an API response — anything that could carry a value you don't fully control. Every call should be code-reviewed on sight, because from that line on, nothing downstream will catch a mistake.

Defense in depth

CSP and Trusted Types back up the sanitizer. They don't replace it.

Code review catches most bad bypassSecurityTrust* calls. It doesn't catch all of them — a tired reviewer, a large diff, a dependency that adds one deep in a library. Two browser-enforced backstops exist for exactly that gap, and each one closes off a different way the sanitizer could be skipped.

A strict CSP has no unsafe-inline.

Most Angular CSP examples you'll find online — including, until this pass, this one — ship style-src 'self' 'unsafe-inline' with a shrug: "Angular inlines some styles." That's exactly the hole a real CSP exists to close. Angular has had a first-class answer since v16: a nonce.

Trusted Types makes bypasses auditable by the browser, not just by eye.

Look at the last two lines of the "after" policy above: require-trusted-types-for 'script' tells the browser that no string may be assigned to a script-executing sink — innerHTML, eval, a <script>'s src — unless it came from an approved policy. angular is the policy name Angular's own sanitizer registers automatically; anything that went through a normal binding already satisfies it. angular#unsafe-bypass is a second name, and it exists for one reason: it is the only thing that makes a bypassSecurityTrust* call legal under this header. List it, and a bypass call works as before. Leave it off, and every single bypassSecurityTrust* call in your codebase becomes a runtime TypeError in the browser — even the ones your own code review approved. That's the enforcement the old warning box on this page used to gesture at without ever explaining: your CSP header becomes the actual allow-list of who may bypass, not just a comment in a pull request.

Roll it out safely: ship Content-Security-Policy-Report-Only first and watch the browser console for violations from code you didn't know was touching an unsafe sink, then switch to the enforcing header once the reports go quiet.

Cross-site request forgery

A tab you never opened can still spend your session.

You're logged into your bank in one tab. In another, you're reading a meme site with a hidden, auto-submitting form pointed at your bank's "transfer funds" endpoint. Your browser doesn't know or care which tab initiated the request — it attaches your bank's session cookie to any request headed for your bank's domain, from any tab, automatically. That's CSRF, and it works entirely without stealing anything: the forged request rides on a cookie you already had.

Your server owns half of this contract: it must set the XSRF-TOKEN cookie (readable by JavaScript, not HttpOnly) and verify the X-XSRF-TOKEN header matches on every mutating request. Angular only ever handles its half — reading the cookie and mirroring it into the header. Spring Security and Express both ship CSRF middleware that speaks this exact convention.
What actually stops a forged request
Scenario CSRF risk?
Traditional cookie-based session, mutating POST Yes — needs a CSRF token
JWT in an Authorization header (not a cookie) No — browsers never auto-attach headers
GET requests (read-only) No — should never mutate state in the first place
Cookie with SameSite=Strict / Lax Mitigated for most real-world cases
withCredentials: true + JWT stored in a cookie Yes — still needs a CSRF token

There's a quieter gap even in a correctly configured app: the interceptor doesn't attach the header to every request, on purpose.

Wherever the access token lives, a route guard is the front door — and it is worth being precise about what kind of door it is.

returnUrl is attacker-controllable. A link crafted as /login?returnUrl=https://evil.example would send this exact guard straight there after a successful login. Validate before you navigate: accept only relative, same-origin paths, and reject anything starting with // or carrying its own scheme — or the "convenience" query param becomes an open-redirect phishing vector.

The token still has to reach every request somehow, and eventually expire and refresh without ever bothering the user. That's two interceptors' worth of work.

Secrets

If it shipped to the browser, it was never a secret.

Rule: if it's in your Angular bundle, it is public — full stop. No API keys, database credentials, private tokens or encryption secrets in frontend code: not in environment files, not in TypeScript constants, not anywhere. A plain strings ./main.js or DevTools → Sources reveals every one of them in seconds.
What belongs where
Value Where it lives
Public API base URL (your own backend) environment.ts — fine
Analytics measurement ID (public by design) environment.ts — fine
A third-party API key with rate limits or billing attached Backend proxy only
Stripe secret key, database password, JWT signing secret Server env vars only — never in the bundle
An LLM provider's API key Backend proxy — never in the browser

The last line

Some defenses only your server can set.

Response headers tell the browser what it is and isn't allowed to do with your page. None of them live in Angular code — they belong on your web server or CDN, configured once for the whole app.

Headers worth setting on every response
Header What it does
X-Content-Type-Options: nosniff Stops the browser guessing a response's type, closing off polyglot-file attacks.
Strict-Transport-Security Forces HTTPS for the given duration. Add it once you know HTTPS works everywhere.
X-Frame-Options: DENY Stops your app being embedded in someone else's iframe (clickjacking).
Referrer-Policy: strict-origin-when-cross-origin Limits how much of your URL is leaked as a Referer header to other origins.
Permissions-Policy Turns off browser features you never use — camera, microphone, geolocation.

Questions from the back row

Before you go

Seven things worth carrying into the exam.

  • Sanitization is a property of the binding, not the DOM — leave the template layer (nativeElement, raw Renderer2 HTML, document.write) and nothing protects you any more.
  • Four contexts, four rulebooks: interpolation never parses HTML at all; [innerHTML] strips scripts and handlers; [href]/[src] block executable URL schemes; RESOURCE_URL refuses by default and needs an explicit bypass.
  • bypassSecurityTrust* means you vouch for the string. Never call it on anything that contains user input, a query param, or an API response you don't fully control.
  • CSP and Trusted Types don't replace the sanitizer — they're the next two rings out. angular#unsafe-bypass in a Trusted Types policy is what makes every bypassSecurityTrust* call in your codebase auditable by the browser, not just by a reviewer's eyes.
  • The XSRF interceptor is quieter than it looks: it skips GET/HEAD and skips absolute URLs on purpose. A third-party API call needs its own plan.
  • Store a token in memory or an HttpOnly cookie, not localStorage — and remember a route guard is a UX nicety, not a security boundary. The backend authorizes every request regardless.
  • Everything in your Angular bundle is public. If it's a real secret, it lives on your server.
