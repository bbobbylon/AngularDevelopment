Zoneless Angular drops Zone.js completely — no monkey-patched setTimeout, no wrapped Promise, no automatic full-tree tick after every async completion. Instead, a pass runs only when something explicitly says so: a signal write, a template event, an input the framework itself wrote. This very app runs zoneless — there is no zone.js in its dependencies — so every proof on this page is the real thing, not a simulation.

The problem

How did Angular ever know to check — before you told it to?

Every other lesson in this track can quietly assume a change-detection pass happens and ask what it does once it starts. This one has to answer the question they all skip: what actually causes one? For Angular's first eight years the answer was blunt — assume any async completion, anywhere, might matter, and check everything to find out.

That blunt answer had a name: Zone.js. It is gone from this app, and the rest of this lesson is about what replaced it, what that replacement quietly does not cover, and the one gap the framework's own marketing copy tends to skip over.

Two values, both written from a setTimeout firing 300ms from now. One is a plain field (this.value = …); the other is a signal you call .set() on. Both really change in memory, at the same moment. Which one do you think shows up on screen — and can you say why, before you scroll down to the live version and check yourself?

The mental model

Zone.js was a concierge who patrols every hallway. Zoneless hands out room-service buttons.

Picture a hotel with one overworked concierge. They cannot tell which room actually needs something, so they compensate by walking a full circuit of every hallway and knocking on every door — the instant any guest event happens anywhere in the building: a phone call ends, a delivery arrives, a shower shuts off. Most knocks get "we're fine, thanks." The concierge has no way to know that in advance, so the walk happens anyway, every time.

Zoneless is the same hotel with a call button in every room. Nothing happens until a guest actually presses one — and the concierge visits only the rooms whose buttons lit up. Fewer walks, and every walk means something. The trade a room makes for a button, though, is that a guest who never presses it never gets visited — which is exactly the shape of the bug this lesson spends most of its time on.

Zone-era Angular is guess, then check everything. Zoneless Angular is tell me, then I'll check exactly that. Every scheduling question on this page is really asking which of those two sentences describes the code you're looking at.

The mechanism

One monkey-patch, twenty places to be wrong.

"Zone.js watches for changes" undersells what it did. It does not read your component state at all — it monkey-patches the browser's own async surface, once, at startup, so that anything completing later runs inside code Angular can observe.

A execution context zone.js ran your whole app inside. Every async callback executed inside it, so the zone could see it both start and finish. Swapping a global function — setTimeout, Promise, addEventListener — for a version that does the original job and tells the zone about it. The browser's queue of pending .then() callbacks. "Drained" means everything currently queued has run — zone.js's signal that a burst of async work has settled. ApplicationRef.tick() from the very top of the component tree. Not the component that changed — every component, every time.

That bluntness is the entire cost story: a ~25 kB gzipped polyfill shipped on every page load forever, twenty-plus patched globals slowing down boot and polluting stack traces, and a full tree walk triggered by things with nothing to do with your app — a third-party analytics ping, a chat widget's heartbeat, a WebSocket keepalive. The only lever teams had was NgZone.runOutsideAngular(), wrapping hot code so its async completions stayed invisible to the zone on purpose.

The stepping stone most teams pass through first: provideZoneChangeDetection({{ '{' }} eventCoalescing: true, runCoalescing: true {{ '}' }}) — on by default in modern Angular even with the zone still installed. eventCoalescing collapses one physical DOM event into a single tick even when it bubbles through several (click) listeners on its way up the tree — without it, one click three parents all listen for ticked the app three times. runCoalescing does the same across separate NgZone.run() calls made in the same synchronous stretch of code. Neither one changes what triggers a tick, only how many ticks one physical event produces — it's real progress, and still fundamentally the concierge's full walk, just a shorter one. The comparison table near the end of this lesson lines all three eras up side by side.

The replacement

Six things, and only six things, schedule a pass now.

No zone, no patched globals, no guessing. A zoneless app keeps one small, closed list of triggers, and every one of them calls the exact same notify() — there is no separate "urgent" path.

The complete list — nothing outside it schedules anything
Trigger What that looks like
Signal write, read somewhere reactive count.set(1) — marks its consuming views dirty and notifies
Template or host event listener any (click), (input), (mousemove) — Angular wraps every one
markForCheck(), directly or via the async pipe an observable emission flowing through | async
Input written by the framework a parent binding wrote a new value, or setInput() on a component ref
Structural operations attaching or detaching a view, createComponent()
Explicit tick ApplicationRef.tick() — the manual crank, rarely the right tool

Everything outside this list — a raw setTimeout, a promise chain, a fetch callback, a WebSocket message, a listener attached by hand with addEventListener — updates your data and tells absolutely no one.

That guarantee is broader than it sounds, and this is the gap a lot of "zoneless removes wasted passes" explanations skip: it applies to every template event, at whatever frequency it fires.

The gap the marketing copy skips

Sixty small events a second is sixty full passes a second.

A (click) firing a handful of times a session is free. A (mousemove) binding on a draggable panel, or a (scroll) binding on a long list, fires up to sixty times a second while the pointer moves — and every single firing is a template event, which means every single firing marks the view and schedules a pass, whether or not the handler changes anything at all. That is precisely the problem runOutsideAngular() used to solve, and it has not gone away just because the zone that made it necessary has.

A template event listener schedules a pass every time it fires, no matter what its body does. For anything above a few events a second — mousemove, scroll, a drag, a resize — handle the raw event outside a template binding and write only a summarized value into a signal. It is the modern, explicit replacement for runOutsideAngular() + manual markForCheck().

Under the hood

One flag is the entire coalescing mechanism.

Every trigger from the table above — a signal write, a template event, markForCheck(), a framework input write — funnels into one scheduler, and that scheduler's whole job is deciding whether a new notification needs a new pass or can ride along on one already coming.

Zoneless changed when a pass gets scheduled. It did not touch what a pass does once it starts — root to leaves, OnPush pruning entire subtrees, === per binding slot. Scheduling and strategy are still two separate questions; this lesson only answers the first one.

The half nobody explains

What actually decides the app is "stable"?

Zone.js did not just trigger renders — it also gave Angular a free way to know when the app had gone quiet: "the microtask queue drained" doubled as "nothing is happening right now." Take the zone away and that free signal disappears too, yet ApplicationRef.isStable and fixture.whenStable() still exist and still work. What drives them now is a separate, easy-to-miss service: PendingTasks.

HttpClient registers a pending task for every request it makes, automatically — which is the entire reason whenStable() and SSR already correctly wait for your HTTP calls without a single line of code from you. The moment data arrives from anywhere else — a raw WebSocket, a third-party SDK's callback, a bare setTimeout — that automatic coverage stops, silently, with no error to point at the gap.

Two concrete failure modes, same root cause. On the server: a zoneless SSR page waiting on a third-party analytics SDK for its data serializes an empty list, because nothing told PendingTasks to wait — the HTML goes out before the data ever arrives. In a test: your own recommended pattern, await fixture.whenStable(), resolves correctly when the component's data comes from HttpClient and resolves too early — a green test asserting against stale state — the moment it comes from anything that never registered.
Walk one screen of a real project in your head. Which of its data sources are HttpClient calls, and which are something else — a socket, a third-party widget, a polling library? The ones in the second group are the ones that need an explicit PendingTasks call if SSR or a test ever has to wait for them.

Getting there

Six steps, each one unlocked by the last.

Migrating a real zone app is not a single flag flip — it's mostly a hunt for code that was quietly relying on the concierge's full walk. Doing the steps out of order tends to surface every failure at once, with no way to tell which change caused which break.

Testing

fakeAsync retires. whenStable() takes over.

fakeAsync and tick() are zone features — they fast-forward a clock that only exists because the zone patched time itself. Zoneless tests use real async instead, driven by the exact same notification rules production runs on. That is a feature, not a downgrade: a test that fails under whenStable() is showing you a component that would render stale in production, not a quirk of the test harness.

Pitfalls

The ways this bites in a real codebase.

  • "It worked before." Code assigning fields inside subscribe() rendered fine under the zone — the fix once it stops is signals or the async pipe, never sprinkling manual tick() calls to paper over the gap.
  • Removing the provider is not the whole job. provideZonelessChangeDetection() alone does not remove the polyfill — forgetting to delete "zone.js" from angular.json's polyfills keeps shipping the 25 kB you migrated to save.
  • A rare library still expects the zone. Anything awaiting onStable for overlay positioning — very old CDK versions, mainly — needs an upgrade; modern Angular Material and CDK are zoneless-ready.
  • requestAnimationFrame loops for canvas or WebGL never needed change detection in the first place — keep them completely plain, and write only summarized state into a signal on the rare frame the UI actually needs to reflect it.

Questions from the back row

Before you go

Six things to remember.

  • Zone-era Angular guessed — any patched async completing anywhere ticked the whole tree. Zoneless Angular is told: only the six triggers in the table above schedule anything.
  • A plain mutation still happens in memory; it just notifies no one. The fix is always a signal write, markForCheck(), or another trigger from that same list — never a manual tick().
  • Every template event listener schedules a pass on every firing, whether or not its body changes anything. High-frequency events need summarizing, not direct binding — the replacement for runOutsideAngular().
  • The scheduler's whole coalescing trick is one flag: a pass already pending absorbs every further notification until it actually runs.
  • Stability now runs on PendingTasks, not the zone. HttpClient registers it for you; anything else async — sockets, third-party SDKs, raw timers — is invisible to whenStable() until you register it yourself.
  • Migrate in order: OnPush first, then async-assigned fields, then a PendingTasks audit, then the provider flip — reversing the order turns one clear failure into several confusing ones.
