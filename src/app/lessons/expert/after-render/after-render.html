Some work can only happen after Angular has actually painted something: measuring an element, wiring up a chart library, focusing a node. Getting that right is not one fact, it's three — how many times a hook fires, what it's allowed to do while it runs, and how long it lives — and this page proves each one with something you can click, not just something you can read.

The problem

The DOM exists in your template. Does it exist in the browser yet?

By the time ngOnInit runs, your template has already been compiled into the exact function you'll meet in a minute — every element it describes has a slot reserved for it. It is extremely easy to read that as "the DOM is ready", and it is not close to true: 

{{ earlyReadSample }}

Zero. Not wrong, not late — the browser genuinely has not laid this element out yet, because change detection has not finished writing it into the page. ngAfterViewInit gets you further — the children now exist — but it still runs mid-check, before the browser has necessarily settled the layout. And on the server it runs against a document that either has no real layout engine behind it at all, or doesn't recognise a browser-only API your third-party code assumes exists. Every request crashes the same way, forever, until someone notices.

Which is really three separate promises a lifecycle hook would need to make, and this one keeps none of them:

  • How many times does it get to run — once, ever, is a different promise from every time.
  • What is it allowed to do while it runs — reading a layout and writing one in the same breath is how you get the browser doing extra work.
  • How long does it stick around — forever, by default, whether you meant that or not.
Two counters live further down this page. One is meant to fire exactly once; the other, on every single render. Before you scroll — if a render hook writes to a signal that its own template reads, what happens to the page? There's a live version to check yourself against.

The mental model

Render hooks are building inspectors, not architects.

Picture two different jobs on a construction site. The architects revise the blueprint constantly — every change to the plan gets redrawn, whether or not a single brick has been laid — and they do this work in the blueprint office, which doesn't need a real building to exist at all. That's change detection: it runs on every platform, including the one with no browser and no real DOM, just a description of one being assembled into a string of HTML.

The inspectors are a different role entirely. An inspector only ever walks a physical, finished building — never the blueprint office — and that isn't a habit, it's the whole of the job. Render hooks are the inspectors: browser-only, by contract, not by convention.

Two shifts work the site. The final-walkthrough inspector — afterNextRender — shows up exactly once, right after construction finishes, checks the wiring, hooks up the utilities, and never comes back. The daily inspector — afterEveryRender — is back after every change to the building, however small, and has to move fast, because there's always a next visit.

And there's a rule the whole site depends on: inspectors are never allowed to phone the architects and ask for a blueprint revision. If they did, the architects would redraw it, the crew would rebuild, and the inspector would be called back in to check the rebuild — forever.

Once. Every. Only when it's dirty. That's the whole cadence of the three render hooks, in the order you'll meet them: afterNextRender fires once, afterEveryRender fires on every render forever, and afterRenderEffect fires only on a render where something it actually reads changed.

The mechanism

Three functions, one shared contract.

All three hooks below share the same non-negotiables: register them from an injection context — a constructor is the easy way; anywhere else, capture an Injector and pass it — and they simply do not exist as far as the server is concerned. The callback is never invoked, not skipped, not caught, never called. What tells them apart is timing.

Fires on the first render this component reaches, then never again. The right place for new ThirdPartyWidget(...) — anything that must happen exactly once. Fires after every render the whole app produces, unconditionally, for as long as it's registered. No memory of what changed — only that something did. A reactive computation wearing a render hook's timing. Runs at least once, then only on a render where a signal it reads actually changed.

Question 1 of 3 · frequency

How many times does a hook actually run?

Choose this when the work is genuinely one-shot: constructing a third-party widget, focusing an element on entry, reading a value you'll never need again. Getting called a second time would be a bug, not a feature.

Choose this when the DOM needs to track something continuously and nothing else can watch it for you — syncing a <canvas>'s pixel size to its CSS size, say. It has to justify running on every render of the entire app, so keep the body trivial.

afterRenderEffect, next, is the answer to "I want the second one, but only when something specific changed" — the middle ground neither of these covers.

Question 2 of 3 · discipline

What is a hook allowed to do while it runs?

Interleaving DOM reads and writes forces the browser into repeated synchronous layout passes — write, then a read forces layout, then a write invalidates it, then a read forces it again. The phases you saw in the flow diagram above exist to stop that: every hook's work is sorted into one of four buckets, and every bucket runs app-wide before the next one starts.

The four phases, in the order they run after every single render
Phase Order For
earlyRead 1 reading layout needed to compute a write — measure before you reposition
write 2 DOM writes — styles, attributes, canvas sizing
mixedReadWrite 3 — the default genuinely interleaved read/write, and where every unphased bare callback lands, from any of the three hook functions
read 4 final measurements, after every write has landed

Question 3 of 3 · lifetime

How long does a hook stick around?

Every one of these functions returns an AfterRenderRef, and almost nobody keeps it — because by default, each hook ties its own teardown to the nearest DestroyRef for you. That default has one sharp edge: "nearest" means whichever injector you handed it, not necessarily the component you meant.

Two different kinds of "stop" live on these hooks, and they aren't interchangeable. ref.destroy() shuts the whole hook down — no phase of it runs again. onCleanup, available inside every phase callback (including afterRenderEffect's), is smaller: it runs right before that phase's next invocation, or on destroy if there never is one — the tool for undoing one run's side effect before the next one starts.

Pass { manualCleanup: true } only when you intend to call .destroy() yourself — otherwise Angular already wires it up for you, which is correct almost all of the time.

So which one is "right"? Creation still belongs to afterNextRender — you want it to run exactly once, tied to nothing, and afterRenderEffect's "at least once, then only when dirty" contract is a worse fit for a line that must never repeat. Reach for afterRenderEffect the moment your render-hook code exists to keep the DOM in sync with a signal — which, in practice, is most of what used to live inside that nested effect(), injector and all.

Pulling it together

The right tool for the job.

Need Tool
One-time DOM setup or measurement afterNextRender
Keep the DOM in sync after every single render, unconditionally afterEveryRender — tiny callbacks, right phase
Keep the DOM in sync with a specific signal afterRenderEffect — dependency-gated, guaranteed to run after render
React to an element resizing, not a render ResizeObserver — renders don't imply resizes, resizes don't imply renders
Per-frame animation work requestAnimationFrame loop — render hooks fire per render, not per frame
React to signal changes with no DOM involved effect() — reaching for a render hook without DOM work is a smell

Pitfalls, collected:

  • NG0203 outside an injection context — calling a hook from a click handler or a timer. Register in the constructor, or pass { injector } captured earlier.
  • A signal write inside the wrong hook — schedules another render, which runs the hook again, forever. True without qualification for afterEveryRender/afterNextRender, whose bodies run unconditionally: write to any signal your own templates read there and each render creates the next one. afterRenderEffect narrows the danger to signals it itself reads — see the "rule" box above.
  • Measuring too early anyway — fonts and images load after the first render and change layout. For anything size-sensitive, pair the initial read with a ResizeObserver.
  • Heavy afterEveryRender callbacks — they run on every render of the whole app; treat the body like code inside a hot loop.
  • Old name: afterRender was renamed afterEveryRender — you'll see both in code from different years, meaning the same thing.

Questions from the back row

Before you go

Six things to remember.

  • Change detection runs everywhere, including the server. Render hooks are the narrower promise — browser-only, always after the DOM is real, never mid-check.
  • afterNextRender is once; afterEveryRender is every render, forever; afterRenderEffect is only when something it reads changed. Once, every, only-when-dirty — the whole cadence in three words.
  • A bare callback always lands in mixedReadWrite. Batching only happens when you explicitly sort your work into earlyRead and write.
  • Never write, inside a hook, to a signal that same hook — or its own template — reads. That's the one way to make an inspector call the architects back.
  • Hooks clean themselves up via DestroyRef by default — but only relative to whichever injector you gave them. Hand them the wrong one and they outlive the component.
  • The chart-host recipe hasn't changed its shape — create once, sync continuously, tear down on destroy — only which tool does the middle step.
