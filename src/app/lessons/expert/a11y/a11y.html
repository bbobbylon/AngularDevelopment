An accessible app works for keyboard users, screen-reader users and low-vision users — and, not coincidentally, works better for everyone else too. Most of it is semantic HTML done right; Angular adds dynamic ARIA binding and the CDK a11y toolkit on top. This page is hands-on: every rule below has a live demonstration, a prediction to make before you see it, or the exact keys and math behind it.

The problem

Every other bug in this app throws. This one doesn't.

NG0100 throws. NG0303 throws. A stale RxJS subscription leaks memory you can watch climb in DevTools. Nearly every mistake taught elsewhere in this curriculum announces itself, sooner or later, to the person who made it. Accessibility bugs are the exception, and it's worth sitting with why: a div styled like a button looks perfect to the sighted developer testing it with a mouse. The code compiles. The build succeeds. Nothing in the console complains. The only person who discovers the bug is someone who was never in the room while it was written — and by then it has shipped.

That's the whole shape of this subject: every rule below exists to close a gap between what a sighted, mouse-using developer can verify by looking, and what actually reaches a keyboard or a screen reader. Nothing on this page is decoration. It's a checklist for the half of the experience your own eyes can't audit.

Put your hand on the Tab key instead of the mouse for the rest of this page. Every live demo below is built to be judged that way — including the one right after this box.

The mental model

A screen reader takes a phone call, not a photograph.

A sighted user takes in a page the way you take in a photograph: all at once, whatever draws the eye first, free to glance ahead and back. A screen-reader user receives the same page the way you receive a phone call — linearly, one utterance at a time, with no way to see what's coming and no peripheral vision to lean on. Nothing on the call happens unless somebody says it out loud.

That reframes almost every rule in this lesson as a question about speech. Semantics are what let the page say "heading" or "button" instead of staying silent about what something is. ARIA state is you mentioning, out loud, that something just changed — expanded, invalid, selected. And a live region is you speaking up before you're asked, the way you'd interrupt a call to say "hang on, that just failed" rather than waiting for the other person to ask.

Name it, state it, announce it. Semantics name what a control is. ARIA attributes state what condition it's in. Live regions announce what changed without being asked. Nearly every fix on this page is restoring one of those three that went missing.

The <div> above is deliberately left broken so you can feel the gap the prediction just described — it carries no role, no tabindex and no keyboard handler, on purpose, so it stays genuinely unreachable rather than only nominally so. To fix it properly you'd need tabindex="0", role="button", a keydown handler for both Enter and Space, and your own disabled styling — four things a real <button> gives you for free.

The first rule of ARIA: don't use ARIA — use the native element with the behaviour built in (button, a, label, dialog, details, headings, landmarks). ARIA only fills genuine gaps, and bad ARIA is worse than none: it makes confident, wrong announcements.

The visual

"On screen" and "in the tree" are two different questions.

Nearly every confusing case in this subject — aria-hidden, display: none, the "visually hidden" CSS trick — is really the same 2×2 grid in disguise. An element is either painted on screen or it isn't, and independently, it's either present in the accessibility tree or it isn't. Four techniques, four quadrants, and mixing them up is where most real bugs live:

On screen ↓ / In the tree → In the accessibility tree Pruned from the tree
Painted on screen Ordinary content. Also: text with a visible alt or label. aria-hidden="true" on a visible element — the div-styled-as-a-button trick's evil twin. Fully visible, fully invisible to a screen reader.
Removed from layout The "visually hidden" CSS technique (clipped to 1px, off-screen, never display: none) — invisible to sighted users, fully readable by a screen reader. Used for skip links and icon-only button labels. display: none, visibility: hidden, Angular's [hidden], or an @if that's false. Gone from both worlds at once — the cleanest, least error-prone quadrant to be in when content should genuinely disappear.

Why the form demo's role="alert" above got away with it. role="alert" is an implicit assertive live region, and assistive tech vendors special-cased it years ago specifically so that error text can appear already populated — because that's exactly how form validation ships. That special case doesn't generalize: a toast, a save-status pill or any other aria-live="polite"/role="status" region still needs to exist before its text changes, and reliability even for role="alert" varies across screen-reader/browser combinations — it's a convention most implementations honour, not a spec guarantee. For anything that has to work everywhere, skip markup entirely and call the CDK's LiveAnnouncer (further down this page) — it owns one persistent region for the whole app, so there's no "was it there yet?" question to get wrong.

Focus management

The SPA-specific discipline the browser won't do for you.

A full browser navigation resets focus to the top of the page automatically. An SPA route change swaps the content while focus stays exactly where it was — sometimes on a link that no longer exists. Every case below is the same underlying discipline: when the DOM changes out from under a user's focus, something has to decide where it goes next, on purpose, or the reader goes silent.

Move focus to the new view's heading (tabindex="-1" plus .focus()), keep a skip-to-content link, and update the document title so a screen reader announces where you landed. Focus moves in on open, is trapped while open (cdkTrapFocus), and returns to the trigger on close. Native <dialog> with showModal() gives you most of this for free. If the focused item disappears — a deleted row, a closed tab — the browser drops focus to <body> unless you move it deliberately, and the reader goes silent with no announcement at all. A positive value hijacks the natural reading order and reorders the entire page's Tab sequence around it. Use DOM order for the sequence, and only 0 or -1 as values.

Ratio = (L1 + 0.05) / (L2 + 0.05) over relative luminance. 4.5:1 for body text, 3:1 for large text (≥ 24px or 18.66px bold) and for UI components/focus indicators. This is the single most-failed criterion in real audits — the pass/fail labels above are never colour alone, on purpose.

Testing workflow

No single tool catches all of this.

  • Keyboard-only pass — unplug the mouse: reach everything, see focus everywhere, no traps.
  • Automated — axe DevTools / Lighthouse catch roughly a third of issues (labels, contrast, ARIA misuse). This very lesson is scanned by axe-core on every test run — a useful floor, never the ceiling.
  • Screen reader — NVDA (Windows, free) or VoiceOver (macOS, built in) on your critical flows.
  • Motion and zoom — honour prefers-reduced-motion; check that 200% zoom doesn't break layouts.

Questions from the back row

Before you go

Five things to remember.

  • This is the one bug category that never throws. Nothing here fails a build or shows up on the author's own screen — treat every rule as a checklist item, not a thing you'll notice by looking.
  • Semantics name it, ARIA states it, live regions announce it. A screen reader gets the page one utterance at a time, like a phone call — nothing reaches the listener that nobody said out loud.
  • "On screen" and "in the tree" are independent questions. aria-hidden hides from the tree only; display: none/[hidden] hides from both; the visually-hidden CSS trick hides from the screen only.
  • ARIA state binds through [attr.aria-*], never [aria-*] — there is no matching DOM property for property binding to target, which is exactly why it throws NG0303.
  • The CDK a11y toolkit exists so you never hand-roll a focus trap — trap focus, monitor its origin, announce updates, and manage focus yourself on every route change, dialog and deletion.
