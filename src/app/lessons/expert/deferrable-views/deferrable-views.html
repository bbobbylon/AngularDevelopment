Every component you import ships in the JS bundle by default — whether anyone ever opens the panel that shows it or not. @defer is Angular's answer: mark a region of a template as deferrable, and every component, directive and pipe used only inside it is cut into its own file, fetched exactly once, exactly when a trigger you choose says it's time. No dynamic import() to hand-write, no lazy route to carve out — just a block, written directly where the content already lives.

The problem

Everything you import ships. Even the parts nobody opens.

Angular's bundler doesn't know or care whether a component is used the instant the page loads or only after someone clicks through three menus to find it. If it is imported and referenced anywhere in an eagerly-loaded part of your app, its code goes into the JavaScript everyone downloads — on day one, before a single person has asked for it.

@defer is the fix, and it is unusually granular: not a whole route, not a whole feature — a single region of a single template. Wrap a chunk of markup in @defer, and everything used only inside it gets its own file, downloaded exactly when a trigger you name says it's time.

Picture a settings page with an "Advanced analytics" panel almost nobody opens — say it pulls in a 200 KB charting library. In a completely ordinary Angular template, with no @defer anywhere, does that 200 KB ship in the bundle every visitor downloads on day one — even the ones who never click that button? There's a real build a few sections down that answers this for real numbers. Guess first.

The mental model

Angular is a restaurant, not a buffet.

Ordinary bundling is a buffet: every dish is cooked and laid out before the first guest arrives, whether they eat it or not, and the kitchen's whole output just sits there. @defer turns your template into a restaurant instead — nothing is cooked until someone orders it. Nobody pays the cost of a dish nobody asked for.

Push the analogy one step further and the four companion blocks stop being four names to memorise and become one thing you already understand: a trip to a restaurant has exactly four moments, and each block is one of them.

Menu, buzzer, meal, 86'd. @placeholder is the menu you're handed while you wait — it's what's actually in front of you right now. @loading is the buzzer going off once your order is being made. The deferred content itself is the meal arriving. And @error is the kitchen telling you, sorry — that one's out tonight.

The mechanism

One block that loads. Three that never do.

Only the content directly inside @defer is ever split into a lazy chunk. The three companion blocks — @placeholder, @loading, @error — ship in the ordinary main bundle, exactly like the rest of your template, and render instantly. That's why they should stay light: a 600px chart living inside @loading defeats the entire point.

What renders before the trigger fires. Ships in the main bundle — the same JS everyone downloads on day one, so keep it cheap. Shown only while the chunk downloads. Also main-bundle. after skips it on fast connections; minimum stops it blinking on and off for slow ones. The one thing genuinely split out. Nothing here ships until the trigger fires — that's the entire feature. Shown if the dynamic import fails — offline, or a deploy that pruned the old chunk's hash. Also main-bundle, so it's always there to show.

This app uses exactly this pattern on its own lesson grids: @defer (on viewport; prefetch on idle) around each level's card grid, with a same-sized shimmer skeleton as the @placeholder, so scrolling to a new level never shifts the page.

The trigger vocabulary

Seven ways to say "when."

Trigger When it fires Mechanism
on idle (default) browser is idle requestIdleCallback
on viewport the watched element enters the viewport one shared IntersectionObserver
on interaction first click / keydown on the watched element listeners on that element's root node
on hover first mouseenter / focusin same, hover + focus events
on timer(2s) after the delay setTimeout
on immediate as soon as rendering finishes no waiting — but still async
when expr() the expression becomes truthy — one-way, it never unloads normal change detection

Combine triggers with a semicolon (OR semantics): on hover; on timer(5s) loads whichever fires first. Every viewport/interaction/hover trigger needs a real DOM node to watch — normally the placeholder's own root element, though it doesn't have to be, which is where this section ends up.

On interaction

Live — click the placeholder to fetch the chunk

@defer (on interaction) { } @placeholder { } @loading (minimum 400ms) {

⏳ Fetching widget chunk…

} @error {

⚠ Failed to load.

}

On timer

Live — loads automatically after 2 seconds, no interaction needed

@defer (on timer(2s)) { } @placeholder {

⏳ Widget arrives in 2 s…

}

On hover, with a prefetch running underneath it

Live — hover (or Tab to it) to load; the chunk is prefetched while the browser is idle

@defer (on hover; prefetch on idle) { } @placeholder {
Hover me, or Tab and hold focus — the chunk is already prefetched in the background
}

on hover listens for focusin too, which is why giving the placeholder tabindex="0" makes it keyboard-reachable — a mouse isn't the only way to "hover" something.

…or point it at something that isn't the placeholder at all

Every trigger above can take an explicit element in parentheses — on viewport(someRef), on interaction(someRef) — pointing at a #templateRef variable declared anywhere else in the same template. It cannot reference something inside another block that is itself deferred, since that element might not exist yet when the compiler needs to wire up the observer.

Live — this button is not part of the block it loads

Nothing connects that button to the block below except the reference in parentheses — no (click) handler, no signal.

@defer (on interaction(loadTrigger)) { } @placeholder {

Waiting for the button above…

}

The full prefetch vocabulary mirrors the trigger vocabulary exactly:

  • prefetch on idle — download during idle time, keep showing the placeholder until the real trigger fires
  • prefetch on viewport / on interaction / on hover / on timer(x) / on immediate — same idea, different early signal to start the download on
  • prefetch when expr() — a custom condition for starting the download

The pairing that shows up constantly in real apps: on interaction; prefetch on hover — the chunk starts downloading the moment a pointer hovers over the trigger, so by the time the actual click lands, the swap is instant.

The one-way door

Loading is not showing.

@defer (when expr()) answers exactly one question: when should Angular start loading this block? It never answers "should this be visible right now" — once loading has happened, there is no value of expr() that reverses it.

Live — load on demand via a signal

@defer (when showWidget()) { } @placeholder {

Waiting for showWidget() to become true…

}

For genuine show/hide behaviour, nest a plain @if inside the loaded block, and drive that with its own condition — completely independent from whatever triggered the load in the first place.

The mechanism, again — differently

The split happens once, at compile time.

The compiler collects every component, directive and pipe used only inside a @defer block and rewrites the reference as a real dynamic import() — the same call you would write by hand for manual code splitting. The bundler's own static analysis is what turns that call into a separate file on disk; Angular never touches bytes on the network itself.

Chart is imported in the class, and used once, eagerly, somewhere else entirely in this very same template — completely unrelated to the @defer block above. Does that block still fire its trigger and swap its states correctly? Does it still save any bytes?
The silent un-split is the #1 way @defer savings evaporate. The block still works exactly as documented — trigger fires, states swap — it just no longer saves a single byte, because the same component is required in the main bundle anyway. Only standalone dependencies can be split this way at all; anything still declared through an NgModule cannot.

@defer vs the other lazy techniques.

@defer lazy route (loadComponent) @if
Granularity any template region whole route/page —
Saves bundle bytes yes (new chunk) yes (new chunk) no — code ships regardless
Can un-render no (one-way) on navigation yes — that's its whole job
Trigger vocabulary viewport/hover/idle/timer/when… navigation (+ preloading strategies) any expression
Best for below-the-fold & heavy widgets on a busy page feature areas pure visibility logic

The exam trap

hydrate isn't "the SSR version" of a trigger. It's a second, separate trigger.

Under SSR, a plain trigger means the server renders only the placeholder — the real content was never loaded on the server either, so there is nothing else to send. A hydrate trigger changes that: the server renders the full content, immediately visible to users and crawlers, and only the JavaScript behind it — the part that makes it interactive — waits for the trigger, client-side.

What a hydrate trigger depends on
Entry path What happens to the hydrate keyword What ships
Fresh page load (SSR) Governs it for real — the server renders the full content JS deferred until the trigger fires client-side
Client-side navigation (a SPA route change) Has no meaning — nothing is hydrating. Falls back to a plain trigger, if one was also written If hydrate on X was the only trigger written, there is no fallback — renders eagerly, no lazy chunk at all
provideClientHydration() without withIncrementalHydration() Every hydrate keyword anywhere in the app is silently ignored Behaves exactly as if hydrate had never been written
hydrate only governs the server-rendered page load. Reached the same route by clicking inside a running app? Nothing hydrated, so nothing about hydrate applies — pair every hydrate on X with a plain on X too, or the block just renders eagerly with nothing deferred: @defer (on viewport; hydrate on viewport).

Testing it

Don't let the states auto-play through your assertions.

The default test behaviour plays the real states — placeholder → loading → complete — which makes an assertion racy: it runs against whichever state happened to be current the moment it executed. DeferBlockBehavior.Manual lets a test drive each state deterministically instead.

Pitfalls

Six ways this goes wrong in production.

  • Layout shift. A 40px placeholder replaced by a 600px chart yanks the page — that's CLS. Size placeholders like the real content: skeletons, fixed-height shells.
  • Deferring above-the-fold content. LCP now waits on a second network round-trip. Defer what's below the fold or genuinely optional — never the hero.
  • on immediate / on idle still flash. The chunk fetch is async, so there is always at least one placeholder frame. Use @loading (after 100ms) so a fast load never blinks a spinner into existence.
  • The silent un-split. An eager reference anywhere else wins — see the compiler mechanics above. Verify with a real build, never by assuming.
  • @defer inside @for. Legal, but N blocks means N triggers and N registrations — cheap individually, real in aggregate. Prefer virtualization, or one defer around the whole list, once a list gets long.
  • viewport/hover/interaction with no watchable element. A compile error if there's neither a @placeholder with a single root element nor an explicit reference in parentheses — the trigger genuinely needs a DOM node to attach to.

Questions from the back row

Before you go

Six things to remember.

  • @defer code-splits a template region and every dependency used only inside it — a real dynamic import() under the hood, standalone dependencies only.
  • Menu, buzzer, meal, 86'd — @placeholder, @loading, the content, @error. Only the content is ever split; the other three ship eagerly, so keep them light.
  • Seven trigger words, combinable with OR semantics, and every one of them can point at an element that isn't the block's own placeholder — on interaction(someRef).
  • when is a one-way door for loading, not a visibility switch — nest an @if inside the block for genuine show/hide.
  • An eager reference anywhere in the app silently un-splits the chunk. Trust a real build, not the block "working."
  • hydrate triggers only govern the server-rendered load — pair every one with a plain trigger too, or a client-side navigation renders the block eagerly with nothing deferred at all.
