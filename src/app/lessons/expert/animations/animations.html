For a decade, animating an Angular app meant learning a whole second language — trigger, state, transition, query, stagger — bolted on top of the one the browser already speaks natively. That package is now deprecated. The modern approach is almost insultingly simple: plain CSS does the animating, and Angular steps in for exactly one thing CSS genuinely cannot do alone — holding a door open long enough for an element to walk out before the node disappears. Everything on this page is built around that one fact.

The problem

CSS can animate anything on screen. It can't animate what's already gone.

Entering is the easy half. An element gets added to the DOM, a CSS animation class is on it, the browser plays the animation — nothing about that needs Angular's help. Leaving is the hard half, and here's why: the moment @if or @for decides an element should go, Angular removes it from the DOM immediately. Not after a tick, not after a frame — instantly, in the same pass that evaluated the condition.

A CSS animation needs the element to still exist while it plays. So if Angular's default behaviour is "gone means gone right now", a plain @keyframes fade-out never gets the chance to run — there's nothing left on the next frame to animate. That one collision is the entire reason this lesson exists.

Picture a toast notification with a CSS fade-out class on it, and nothing else — no special Angular binding. You click dismiss and @if flips to false. Does it fade away, or does it just vanish on the spot? Think about when the browser gets told to animate something, versus when Angular tears the node out. There's a live version below to check yourself against.

The mental model

Angular is a doorman, not a choreographer.

A choreographer designs the moves. A doorman doesn't — he doesn't care how you dance out the door, he just controls when the door closes. That's the whole shift this lesson is about: the legacy @angular/animations package tried to be the choreographer, with its own DSL for describing motion. The modern approach hands the choreography entirely back to CSS (or a JS library of your choice) and keeps Angular doing exactly one job — timing.

Hold, run, tell. That's the whole of animate.leave: Angular holds the node in the DOM, runs your animation — a class or a callback, your choice — and waits to be told, by the animation ending or by animationComplete(), before it actually removes anything.

The toolkit

Four tools, one job each.

Angular adds this class right after the node is inserted, then strips it once the animation ends. You never remove it yourself. Angular keeps the node alive, adds this class, and removes the node only when that animation finishes. Same contract, your code: call event.animationComplete() yourself, from the Web Animations API, GSAP, anything. Gives a transition a "before" state to animate from on an element's first paint. No Angular involved at all.

Tool 3 · the callback form

When a class isn't enough, hand Angular a promise instead.

animate.enter and animate.leave also accept an event binding — (animate.leave)="handler($event)" — instead of a class name. This is the entire integration point for a JavaScript animation library: the Web Animations API, GSAP, Motion One, a physics engine, or anything else that can eventually resolve. You take over the motion; Angular only asks to be told when you're finished.

With the toggle off, the card fades and shrinks out and is gone from the DOM the instant the animation finishes — animationComplete() ran on cue. Arm the bug, remove it again, and open your devtools Elements panel: the card sits there fully invisible but still genuinely in the DOM for a few extra seconds before Angular gives up waiting.

A forgotten animationComplete() doesn't leak — it stalls. Angular force-finishes it after MAX_ANIMATION_TIMEOUT, 4 seconds by default and configurable if you genuinely need longer.

Tool 4 · pure CSS, no Angular at all

@starting-style answers half the question before Angular gets involved.

Normally a transition can't run on an element's initial styles — there's no "before" to animate from on the very first paint. @starting-style is a native CSS block that supplies one. Paired with transition-behavior: allow-discrete, it's enough to animate a <dialog> or a popover open and closed with zero JavaScript and zero framework — genuinely just CSS.

Where does that leave animate.enter? Overlapping, not obsolete: for a simple fade or slide on insertion, @starting-style needs nothing from Angular at all. animate.leave stays necessary regardless, because closing is Angular's decision — the framework, not the browser, owns the moment a node actually leaves the tree, and only Angular can hold that moment open.

The replacement's own bug

animationend bubbles. (@trigger.done) never did.

The migration table above says (animationend) replaces (@trigger.done), and mostly it does — except for one behaviour nobody warns you about: a native DOM event bubbles. If any descendant inside your animated element also animates, its animationend reaches your listener too, firing your "the whole thing is done" logic early and often. 

<div class="card" (animationend)="onCardGone()">
  <span class="badge" animate.enter="pop">NEW</span>
  …
</div>

// fires once for the card's own fade-out —
// AND once more for the badge's little "pop"
onCardGone(event: AnimationEvent): void {
  if (event.target !== event.currentTarget) {
    return; // a descendant's animation, not this one
  }
  // …now it's safe to act
}

The compositor

Animate on the compositor, or animate on the main thread.

Every property in an animation costs a different amount, and the difference isn't subtle. Some properties are handled entirely by the compositor — a thread that only touches the final bitmap. Others force the browser to re-run layout, the same expensive pass that runs when the page first loads, on every single frame of the animation.

transform and opacity — the two safe defaults. No layout, no paint, off the main thread entirely, smooth even while your app's JavaScript is busy.

filter and clip-path are usually fine too — paint-only on modern engines, no layout cost.

height, width, top/left, margin — each one reflows the element and everything it displaces, every frame. This is the single most common source of animation jank. If you genuinely must animate one of these, contain: layout at least stops the reflow escaping this element's own box instead of recalculating the whole page.

Animated box-shadow is a repaint every frame across its whole bounding box — animate a separate pseudo-element's opacity instead.

Accessibility, not polish

Reduced motion is a requirement.

Vestibular disorders make large sliding or zooming motion physically unpleasant, not just distracting. prefers-reduced-motion reads an OS-level setting the user already chose — you're not guessing at their preference, they told the browser directly.

Open your OS accessibility settings and turn on "Reduce motion" (macOS), "Show animations" off (Windows), or the Android equivalent — then come back and press every button on this page again. Every demo here should go still, not broken. That's the actual test of whether reduced-motion support works: nothing missing, just nothing moving.

Questions from the back row

Before you go

Six things to remember.

  • Entering was never the hard part. An element already exists while it animates in — CSS handles it alone. Leaving is hard because Angular removes the node immediately, before a CSS animation gets a frame to run.
  • animate.enter/animate.leave are two shapes of the same idea: a class Angular applies and removes for you, or a callback — (animate.leave)="fn($event)" — where you call event.animationComplete() yourself, the entry point for any JS animation library.
  • Forgetting animationComplete() doesn't leak. MAX_ANIMATION_TIMEOUT (4 seconds by default) force-finishes the removal for you — a stall, not a leak, but still a bug at scale.
  • @starting-style + allow-discrete animates an element open with zero JavaScript. animate.leave stays necessary regardless, because closing is Angular's decision, not the browser's.
  • Read the legacy API, don't write it: :enter/:leave are aliases for void => */* => void, and a parent's destruction skips a child's own leave animation unless animateChild() says to wait for it — animate.leave follows the exact same rule.
  • Animate transform/opacity, never layout properties on a hot path, and honour prefers-reduced-motion — it protects CSS motion automatically and JS-driven motion not at all unless you check it yourself.
