The animations story changed recently, and knowing that is the expert signal: the classic @angular/animations package (trigger/state/transition) is deprecated. Modern Angular hands almost the entire job to native CSS, plus two small framework hooks for the one thing CSS can't do alone. This page is built around a single picture — hold onto it, because every section below is really just that picture again from a different angle.

The problem

Flip a boolean to false. Predict what your fade-out does.

CSS handles an element entering easily — give it a class, the browser animates it in. Removing one is where the trap lives.

The mental model

You're the keyframe artist. The browser is the in-betweener.

Traditional hand-drawn animation studios split the work in two: a lead artist drew the key poses — the start of a jump, the top, the landing — and junior "in-betweeners" drew every frame that connects them. CSS @keyframes is named after exactly this. You draw from and to — sometimes only one of them, letting the browser read the element's current style as the other — and the browser's compositor does the tedious part: filling in every frame in between, at 60 frames a second, without you specifying a single one of them.

The deprecated @angular/animations package didn't work this way. It made Angular the director and the in-betweener at once — a JavaScript state machine (state(), transition(), stagger()) computed intermediate frames on the main thread, the same thread running your app's change detection and everything else. Modern Angular fires the director. Each element is handed two poses and left to sort out its own motion, off the main thread entirely, which is both simpler to write and faster to run.

You draw the poses — the from and to of a @keyframes rule (or just one, and let the browser read the rest from the element itself). The browser is the in-betweener — it fills in every frame between them. That division of labor is exactly what "keyframe" has always meant, decades before CSS borrowed the word.

The mechanism

animate.leave — a stagehand, not an animator.

Angular's own job here is deliberately tiny. It doesn't compute a single frame of motion — CSS still does all of that. Angular just holds the curtain: when saved() flips to false, it applies your fade-slide-out class, waits for that animation to actually finish, and only then removes the node for real.

Reading old code

The legacy vocabulary — you'll still meet it.

Years of codebases (and exam questions) use @angular/animations. Read it fluently, map it mentally, and don't start new work with it:

Legacy (@angular/animations) Modern equivalent
transition(':enter', …) animate.enter="css-class"
transition(':leave', …) animate.leave="css-class" (framework delays removal)
state() + transition('a <=> b') class binding + CSS transition
query() + stagger() [style.animation-delay] per index
keyframes() CSS @keyframes
(@trigger.done) callback (animationend) / (transitionend) events
route transitions via @routeAnimations the router's View Transitions (withViewTransitions())
provideAnimationsAsync() not needed at all — CSS ships free

Under the hood, the legacy engine computed each frame's styles in JavaScript, on the main thread — the same thread running your app's change detection — and wrote them out via the Web Animations API. CSS animations of transform/opacity are handed to the compositor thread instead, which keeps animating smoothly even while the main thread is busy. That's the real reason for the deprecation: not that the old API was badly designed, but that a main-thread-driven in-betweener was always fighting a battle CSS never has to fight.

Migration honesty: the legacy engine still works and won't break tomorrow — the deprecation means no new investment. Migrate opportunistically (when touching a component), replace @routeAnimations choreography with view transitions, and delete provideAnimationsAsync() once nothing legacy remains — the engine is bundle weight the modern approach doesn't pay.

Performance

Only hand the in-betweener a pose it can move for free.

The compositor can reposition or fade an already-painted layer without asking the rest of the page to recompute anything. Ask it to change layout instead, and it has to redo the expensive steps first:

Only hand the in-betweener a transform or opacity change. Anything that touches layout — height, width, top, margin — makes it redraw the whole scene from scratch, every single frame.
Property Why
transform, opacity cheap composited on the GPU — no layout, no paint, off the main thread
filter, clip-path usually fine paint-only on modern engines
height, width, top/left, margin expensive trigger layout for the element AND everything it pushes — jank on weak devices
box-shadow (animated) expensive large repaints every frame — animate the opacity of a pseudo-element's shadow instead

The professional trick for "move from A to B" layout changes is FLIP: measure First and Last positions, apply the Inverted delta as a transform, then Play the transform back to zero — layout math once, motion entirely on the compositor. (The browser's View Transitions API automates exactly this.)

Accessibility

Reduced motion is a requirement, not polish.

Vestibular disorders make large sliding/zooming motion physically unpleasant. Honor the OS-level setting: keep opacity fades if you like, kill movement. This very page's demos include the media query below — enable "reduce motion" in your OS and they go static.

Questions from the back row

Before you go

Recap — five things to remember.

  • Modern Angular animation = CSS transitions/keyframes + class bindings; you draw the poses, the browser is the in-betweener. Angular only steps in for enter/leave.
  • animate.leave delays DOM removal until the exit animation finishes — the one genuinely hard problem, solved in one attribute.
  • @angular/animations is deprecated because it made Angular direct and in-between on the main thread: read it, map it, migrate opportunistically.
  • Animate transform/opacity; never layout properties on hot paths — they cost a full Layout + Paint pass every frame; use FLIP for layout moves.
  • prefers-reduced-motion support is an accessibility requirement.
