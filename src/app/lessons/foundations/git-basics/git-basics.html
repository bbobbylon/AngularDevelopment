Git is a program that runs on your own computer and remembers every version of your project you've ever committed to it — a time machine you can step back through, and a safety net that makes "I broke something and can't get back to what worked" a solved problem. Nearly every team on Earth uses it. The trick to Git actually making sense, instead of feeling like a pile of memorised incantations, is one picture: every change you make travels through three areas before it's genuinely safe. Get that picture solid and almost every command on this page turns out to be obvious.

The problem

How did people share code before Git existed? Badly.

Version control answers one question every developer eventually asks the hard way: "what did I have before I broke this?" Before tools like Git existed, the honest answer for most people was "whatever I happened to save under a different filename" — and that falls apart exactly when you need it most.

project-final.zip, project-final-REAL.zip, project-final-v2-fixed-FINAL.zip — no record of what actually changed between any two of them, no way back to yesterday if today's edit breaks something, and combining two people's edits means opening both zips and comparing files by eye.

One project, one history. Every commit says exactly what changed, when, by whom, and why — because you wrote the message. Going back to any point in time is one command, and combining two people's work is a named Git operation (merge), not a manual side-by-side comparison.

You and a teammate both edit the exact same line of the exact same file, on your own separate copies, without talking to each other first. Later, you try to combine your work into one file. What do you think actually happens — does Git pick one version automatically, silently keep both, or something else entirely? Hold your guess; the "famous scary thing" section further down has the real, mechanical answer.

The mental model

Every change walks through three rooms before it's safe.

Picture your project as a kitchen mid dinner-party. The working directory is the counter — knives out, vegetables half-chopped, a sauce you've re-seasoned four times. It's messy, it's yours, and Git barely watches it beyond noticing that something moved. The staging area is a tray: you deliberately load it with exactly the dishes going out for this course, chosen on purpose from everything sitting on the counter. And history is the course that already left the kitchen — once a plate goes out, you don't sneak back and re-season it. You serve a new course instead.

Edit, stage, commit — three verbs, three areas. A change is never safe until it's commit-ted, and it's never in the next commit until it's add-ed first. Most "my change disappeared" panics are really "I skipped the middle verb."

The everyday loop

Six commands cover almost your entire day.

You now know why three areas exist. Here is what actually moving between them looks like, typed out — the exact loop you'll run dozens of times a day, every day, for as long as you write code.

The six commands worth knowing cold
Command What it does Reach for it when…
git status lists what's changed, staged and not constantly — before anything else, always
git add <path> moves a change into the staging area you're happy with an edit and want it in the next commit
git commit -m "…" permanently snapshots what's staged the staged changes form one complete, describable idea
git log --oneline lists past commits, newest first you need a commit's id, or just want the story so far
git push uploads your commits to the remote you're ready for teammates (or CI) to see your work
git pull downloads and merges teammates' commits at the start of a session, before you start editing
Write it in the imperative, as if finishing the sentence "If applied, this commit will…" — Add login form, never Added stuff or Adds login form to the site finally. Six months from now, git log is the only documentation this decision will have.

Parallel universes

A branch just moves a label; checking one out rewrites your files.

So far, every commit has landed on the same single line of history. A branch breaks that: it's an independent line of commits, so you can build something risky or half-finished on your own line while main stays exactly as it was. When the work is ready, a merge combines the two lines back into one.

Branches are cheap on purpose — a branch is nothing more than a movable label pointing at one commit, which is why teams make one per feature or bug fix, however small.

That's the moment that makes branches click, and the one beginners find genuinely unsettling the first time: switching branches rewrites your working directory. A branch isn't a filter layered on top of one set of files — it's a genuinely different snapshot, and checking one out swaps your files to match it, right in front of you.

The famous scary thing

A merge conflict is a question, not an error.

Remember the napkin from the top of this page? Here's the honest, mechanical answer: Git does not guess. If both branches changed the exact same lines, it stops the merge and edits the file itself to show you both versions, side by side, right inside the file.

Resolve it by hand: decide what the line should actually say (keep one side, keep the other, or write something new entirely), delete all three marker lines, then git add the file and git commit to finish the merge. That's the entire ritual — a conflict has a scary reputation and a genuinely mechanical fix.

Those marker lines are real text Git wrote into your file. Forget to delete one and commit anyway, and <<<<<<< HEAD becomes permanent, syntactically-broken content in your codebase. Always re-read the file — or let your editor's diff view highlight the markers — before you add a resolved conflict.

Remotes & collaboration

Nothing you commit reaches anyone else until you say so.

Everything on this page so far has happened entirely on your own machine — Git works completely offline, and every commit exists only in your local project until you decide otherwise. A remote is a copy of the repository hosted somewhere else; GitHub (or GitLab, or Bitbucket) is where that somewhere else usually is.

Teams almost never merge straight into main. The usual workflow is: push your branch, then open a pull request — literally "please pull my branch into main" — where teammates read the diff, leave comments on specific lines, and automated checks run before anyone merges it. This is where code review actually happens, and a long, thoughtful pull-request history is something interviewers genuinely read.

git pull merges their commit into yours first (creating a merge commit), or git pull --rebase replays yours on top of theirs for a straight-line history — either way, the ordinary git push from the everyday loop then succeeds normally.

A rejected push is Git protecting you. --force deletes that protection, silently, the instant you type it — which is exactly why the next paragraph exists.

git push --force is the same idea as an ordinary push, with one safety check switched off — the one that normally stops you from overwriting commits you haven't seen yet.

Add a .gitignore file the moment you start a project, listing what Git should never track: node_modules/ (huge, and — as the npm lesson covers — sometimes tied to one specific machine's binaries), build output like dist/, and anything secret (.env, API keys). Set it up before your first commit: a file already committed keeps being tracked even after you add it to .gitignore later, and a leaked secret stays readable in your history forever unless you rewrite history specifically to remove it — treat a committed secret as compromised and rotate it.

The pattern behind all four: committed work is nearly impossible to lose — it's sitting in history, addressable by its id, forever. Uncommitted work is fragile — a stray restore, a deleted folder, a computer that dies, and it's gone. The practical takeaway isn't "memorise four commands," it's commit early and often, because a commit is the only one of these states with a genuine safety net under it.

Questions from the back row

Before you go

Six things to remember.

  • Three areas, three verbs: working directory (edit) → staging (add) → history (commit). Nothing is safe until it's committed, and nothing is in the next commit until it's staged.
  • git status first, always. It's free, instant, and tells you exactly what state everything is in before you commit to anything.
  • Small, focused commits with imperative messages ("Add X", not "stuff") — six months from now, git log is the only documentation this decision will have.
  • Branches are cheap, independent lines of history; checking one out genuinely rewrites your files to match it — nothing is deleted, you're just looking at a different snapshot.
  • A merge conflict is Git asking a question it genuinely cannot answer on its own: resolve it, delete the three marker lines, add, commit.
  • Commit is local; push and pull are the only two commands that cross the wire, and both are things you choose to run. --force on a shared branch can silently erase a teammate's work — reach for --force-with-lease instead.
