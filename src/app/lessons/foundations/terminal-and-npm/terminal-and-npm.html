To build apps you'll type instructions into a terminal (also called a command line or shell) — a text window where you tell the computer what to do by typing instead of clicking. It looks intimidating from the outside; it isn't once you have the right mental model. This page gives you exactly that model, the eight commands worth knowing cold, and the npm ecosystem every single Angular project quietly depends on.

The problem

Typing feels slower than clicking. It isn't, and here's why.

  • Precision & repeatability — ng serve means exactly one thing, on every machine, every time. No hunting through menus that moved in the last update.
  • Automation — commands can be chained, scripted and run by robots. Your future CI pipeline is just the commands you're learning now, run by a server on every push, with nobody there to click anything.
  • It's where the tools live — the Angular CLI, npm, Git: all terminal programs. Every tutorial, error message and forum answer you will ever read assumes you can run them.
You're about to type your very first command. When it runs perfectly — no typo, nothing wrong — what do you expect it to print back at you? Hold that guess in your head. The next section has the actual answer, and it surprises almost everyone the first time.

The mental model

You are always standing in one room of a house.

Picture your project as a house. Every folder is a room, and rooms contain other rooms — src/ is a room off the front hallway, app/ is a room off that one, and so on. Here is the one fact that makes the whole terminal make sense: you are always standing in exactly one room, and every command you type acts on the room you're currently standing in. ls lists what's in this room. npm install installs into this project. Half of all beginner terminal errors are really just "I'm standing in the wrong room" — pwd is how you check.

pwd asks "where am I?", ls asks "what's here?", and cd says "take me there." When a command misbehaves, ask those three questions in that order before anything else — most beginner terminal errors really are just standing in the wrong room.

Which finally answers the question from the napkin above: silence usually means success. A command prints something when it has something to report — a listing, a warning, an error. The npm ecosystem

Three files, one job each, and only one of them is yours.

Node.js lets JavaScript run outside the browser — it's the engine Angular's build tools, dev server and CLI all run on. Installing Node also installs npm (Node Package Manager), whose entire job is managing packages: folders of code someone else wrote that your project depends on. Three files and folders make up the system, and mixing up who owns which one is the single most common npm mistake a beginner makes.

The project manifest: name, npm scripts, and your dependencies with version ranges. Small, human-edited, and committed to Git. The exact resolved version of every package, including dependencies of dependencies. It's what guarantees you and a teammate get byte-identical installs. The downloaded packages themselves — often hundreds of megabytes. Never edit it by hand, never commit it; anyone can rebuild it from the two files above with one command.
You write package.json. npm writes package-lock.json. Nobody edits node_modules/ by hand. It is pure generated output, safe to delete, and rebuilt byte-for-byte by running npm install again.

The failure story

"Delete node_modules and reinstall" isn't the fix for everything.

Every example so far has been the happy path — npm install, then a short line saying how many packages arrived. The first real wall most beginners hit looks nothing like that: a screaming block of red text. Two of them show up constantly, and neither one means what people assume.

The other classic wall shows up on a global install — npm install -g @angular/cli — and it's a completely different kind of problem: not a version conflict, but the operating system itself refusing to let npm write files where global packages live.

Commands worth knowing by heart

Five commands, and what each one actually does.

Three of these start with the same word and do genuinely different jobs — that's the part worth slowing down for.

Version ranges

That caret in package.json is a promise, not decoration.

Version numbers in package.json follow semver (semantic versioning) — major.minor.patch, where a major bump is the number's own way of warning you it might break something. The symbol in front of the number controls exactly how much npm is allowed to move on your behalf.

npm scripts

package.json is also where a team agrees on shortcuts.

Why not just type ng serve directly? Two reasons. Scripts document the project's standard workflows in one place that every teammate can read, and npm quietly puts this project's own node_modules/.bin first on the PATH while a script runs — so the project's pinned CLI version runs, not whatever version happens to be installed globally on your machine. Teams rely on that for reproducibility.

install vs. ci

npm install and npm ci both "install the dependencies." They disagree about how strict to be.

npm install

Reads package.json. If it and package-lock.json have drifted apart, npm quietly reconciles them — rewriting the lock file to match — and installs anyway. Nothing stops; nothing is deleted first. 

npm ci

Deletes node_modules/ completely, then installs exactly what package-lock.json already says. If that disagrees with package.json, it stops immediately with an error instead of guessing.

The Angular CLI

One command per verb: new, serve, generate, build, test.

ng serve is where you'll live: it compiles the app, serves it locally, and recompiles plus refreshes the browser every time you save a file. It keeps running — that's why the prompt never comes back — until Ctrl+C stops it. localhost:4200 means "this machine, door 4200."

Three more things stop ng commands before they even start, and all three look scarier than they are:

Node itself is too old

{{ nodeVersionMismatchSample }}

node --version matters after all: every Angular major declares a minimum Node version in its own "engines" field, and the CLI checks it before doing anything else. The fix isn't "download the newest Node" either — odd-numbered majors (19, 21, …) are never Long-Term-Support releases and Angular doesn't support them. Install a version manager (nvm, nvm-windows, fnm, Volta) so each project can pin the Node version it actually needs — the same "version range" idea as ^18.0.0 above, just applied to the runtime instead of a package.

Port already in use

{{ portInUseSample }}

Almost always a previous ng serve that never got a Ctrl+C — often in a terminal tab you forgot about. Answer "yes" to try the next port, or add --port 4300 yourself.

'ng' is not recognized

{{ ngNotFoundSample }}

Means npm install -g @angular/cli either never ran or failed partway — the same global-install machinery as the EACCES example above. Re-run the global install; a fresh terminal window sometimes needs to open before the PATH change is picked up.

Questions from the back row

Recap

Five things worth remembering.

  • You are always standing somewhere. pwd tells you where, ls lists what's there, and cd moves you — most beginner errors are just the wrong room.
  • Silence usually means success. A command that finishes cleanly, with nothing new to report, typically prints nothing at all and hands you a fresh prompt. Errors, by contrast, always say so.
  • Three files, three owners. You write package.json; npm writes package-lock.json; nobody touches node_modules/ by hand — and never, ever commit it, partly for size and partly because its compiled binaries can be tied to one specific machine.
  • npm install is forgiving, npm ci is strict. Use install on your own machine; reach for ci anywhere reproducibility matters more than convenience.
  • A caret never crosses a major version on its own. ^18.0.0 can climb to any newer 18.x.y, but never to 19.0.0 — that's a deliberate upgrade, not something npm install decides for you.
