Every programmer, beginner to expert, writes code that breaks — the only difference is what happens in the next ten seconds. A beginner reads the first five words and starts guessing. An expert reads the whole report: what kind of mistake it was, exactly what happened, and the trail of calls that led there — then tests a hypothesis instead of poking randomly. This page teaches that report end to end, in an Angular project specifically: the browser errors you already expect, the compiler errors Angular adds on top of them, and what to do the moment there is no error at all.

The problem

Something just broke. Now what?

Here's the reflex almost everyone starts with: the screen turns red, the eyes skip straight to the first few words, and the hands go back to poking at the code. That is not reading an error — that's reacting to one, and it throws away nearly everything the error was trying to tell you.

An error message in JavaScript is not a vague complaint. It is a precise, three-part report, generated the instant something the engine cannot proceed past happens, and it always contains — in order — what kind of mistake this was, exactly what went wrong, and the exact trail of function calls that led to it. Nothing about that report is trying to be difficult. It is trying to save you time, and most of the frustration people feel while debugging is really frustration at not having read the whole thing.

Here's a real one, unedited: TypeError: Cannot read properties of undefined (reading 'email'), with a trace ending at showProfile (app.ts:51:24). Before you read a single word of the next section — can you already say, in one sentence, roughly what went wrong and where you'd look first? Hold that guess. You'll check it against the actual method in a moment.

The mental model

The computer isn't attacking you. It's dictating a report.

Picture a very literal-minded witness at the scene of a small accident — not hostile, not embarrassed, just relentlessly precise. Ask what happened and they will not soften it, summarize it, or spare your feelings: they will name the category of thing that went wrong, describe the exact moment in careful detail, and then recite, from memory, every single step that led them to be standing there. That is a JavaScript error, almost exactly. The "attitude" beginners read into red console text is entirely imagined — it is the most literal, least judgmental record of a mistake you will ever get.

Type, message, stack. WHAT kind of mistake, WHAT exactly happened, and HOW you got there. Every JavaScript error is built from exactly these three pieces, in exactly this order, every single time.

Before you even open the console

Errors show up in two different places.

Every example so far, and everything the field guide further down throws, happens after your code is already running, in the browser. In an Angular project that is only half the story — and for a beginner, it usually isn't even the half you meet first.

TypeScript and Angular's own template compiler check your code before any of it executes — a misspelled property, the wrong argument type, a template binding to a field that doesn't exist. Fail one of these checks and the browser doesn't receive new code at all: ng serve just keeps serving whatever last compiled cleanly, so the page sits there looking completely unchanged.

You'll meet these two ways: as a red squiggle under the exact characters, right there in your editor, and — the one beginners miss — as a block of text printed in the terminal window running ng serve, which most people have minimized or covered up.

Everything from the anatomy section below, and every case in the field guide further down, happens here: your code compiled just fine and is now actually executing, one instruction at a time, and something it does — reading a property, calling a function — fails partway through.

This is the console you already know to check. It's also the only half of the two that a beginner is usually taught to look at at all.

The single most disorienting bug of week one: you save a file, the browser doesn't change, and the console is completely empty. That's not a broken app — it's a compile error, and the console was never going to show it. Check the terminal running ng serve before you check anything else.

Angular's own template compiler produces the same kind of report for your HTML — NG9: Property 'titel' does not exist on type 'AppComponent' means exactly what it looks like: a typo in a binding, caught before the page ever loads.

The trail

Two directions through the same list.

Angular's own errors

Angular speaks in codes.

Two different families share that NG-prefixed style. One is the template diagnostic you just met — NG9, checked at compile time, same idea as TS2339 but for your HTML. The other is a separate family of runtime errors — thrown while the app is actually running, same moment as a TypeError, just Angular's own instead of the language's.

Every one of these carries a code like NG0201 right there in the message. That code — not the sentence around it — is the part to put in a search bar: paste NG0201 into angular.dev/errors/NG0201 and you land on the official page explaining exactly what triggers it and how to fix it. The sentence around the code has your own class and variable names baked into it, which nobody else's search results will ever match.

A short list of NG codes worth recognizing on sight
Code What it means Typical cause
NG0100 ExpressionChangedAfterItHasBeenCheckedError State changed after Angular finished checking it this pass — e.g. writing to a bound value from ngOnInit. The change-detection lesson takes this apart in full.
NG0201 No provider found for X You're injecting a service nobody registered — check providedIn, or the providers array.
NG0200 Circular dependency detected Two injectables depend on each other, directly or through a chain of other services.
NG0303 Can't bind to X since it isn't a known property Usually an ARIA attribute bound the wrong way — [aria-expanded] needs to be [attr.aria-expanded].
NG0912 Duplicate hydration id Two elements ended up with the same server-rendering marker — a topic for the Rendering track.

One more tool worth knowing exists, even though this lesson doesn't have room to tour it: the Angular DevTools browser extension. Where the browser's own DevTools stop at the DOM and plain JavaScript, Angular DevTools shows you the component tree with live @Input and signal values, the injector tree — the fastest way to chase down an NG0201 — and a profiler that attributes render time to individual components. Worth ten minutes any time an NG error mentions a provider or a component you don't recognize.

Tool #1

The console is more than console.log.

Half of all debugging is one sentence: "I assumed this value was X; logging proved it was Y." The log's job is to test an assumption. Which means: before you log, say out loud what you expect to see — if you can't, you're not debugging yet, you're staring.

Tool #2

DevTools is the cockpit. (F12)

Every log you write, and every error nobody caught. The file:line on the right of an entry is a real link — click it and jump straight to that exact line of source. The live DOM — the current tree, not your HTML file. Click any element and see exactly which CSS rules apply, and which are crossed out because something more specific won. Every request the app makes: URL, status code, and the actual JSON that came back. "The data is wrong" always starts here — was it the server's answer, or what your code did with it? Where you set a breakpoint. Click a line number and execution genuinely pauses there next time it runs — hover any variable to see its value, then step through line by line.

Pausing the world, properly

A breakpoint earns its ten minutes because a paused program hands you more than any log ever could. Four controls do almost everything: resume runs until the next breakpoint, step over runs the current line without diving into functions it calls, step into follows the call down into that function, and step out runs the rest of the current function and pauses again right after it returns. While paused, the Scope pane lists literally every variable visible at that exact instant, and the Call Stack pane is the live, clickable version of the stack trace you've already learned to read — click any frame and the Scope pane updates to show the world exactly as it looked at that caller's moment.

  • Conditional breakpoint — right-click a line number, add an expression like id === 42. Pauses only when it's true; essential inside a loop.
  • Logpoint — right-click → "Add logpoint". Prints a value on every hit, with zero code changes and zero recompiles.
  • Add script to ignore list — right-click a framework frame in the Call Stack pane. Keeps internals out of your step-through, so Step Into only ever lands in your own code.

Shines when you want to watch a value across many events — every click, every request, a loop running hundreds of times. You decide in advance what to print, which means you already need a rough idea what's wrong.

Shines when you want the entire world at one paused moment — every variable in scope, not just the ones you thought to log. You don't have to guess what matters beforehand; it's all just there.

Why a production error looks unreadable. The browser is genuinely running one giant minified file in production — your TypeScript doesn't exist there anymore. A .map file is what lets DevTools show you readable source anyway, which is exactly what you're seeing every time the Sources panel shows your actual .ts during development. Angular can produce the same map for a production build (sourceMap: true), which is also why error-tracking services ask you to upload one — without it, a production stack trace is a wall of single-letter names and no line numbers worth trusting.

The method

Debugging is a science, not a vibe.

Every tool above is only as good as the method wrapped around it. Here is the one that actually works, every time, regardless of which tool you reached for.

Two force-multipliers: search the exact error text (in quotes, minus your own variable names) — someone has hit this exact message before. And explain the bug out loud, to a colleague, a rubber duck, or an empty chair — verbalizing forces you through the evidence in order, and the answer routinely arrives mid-sentence. This is a real, named technique: rubber-duck debugging.

Questions from the back row

Before you go

Six things to remember.

  • An error is a report, not a punishment: type (what kind), message (what exactly), stack (how you got there) — and the stack prints newest-frame-first, the opposite order to how the calls happened.
  • Reading Cannot read properties of undefined (reading 'x'): the undefined thing is always one hop to the left of 'x'.
  • Angular errors show up in two different places — compile time (terminal + editor, before anything runs) and runtime (the browser console, while it's running). When the browser doesn't update after a save, check the terminal first.
  • Angular's own runtime errors carry NG codes (NG0100, NG0201…) — searchable by the code alone, documented at angular.dev/errors, and distinct from plain TypeErrors and ReferenceErrors.
  • Async stack traces are short because the caller already left the stack — chase what scheduled the callback, not what "called" it.
  • Debug like a scientist: read the whole error, reproduce it, hypothesize, test with evidence, fix the cause and re-run.
