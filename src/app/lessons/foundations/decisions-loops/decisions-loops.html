Every program you've written so far runs in one straight line, top to bottom, exactly once. Real programs aren't like that — they need to make decisions ("if the user is logged in, show the dashboard") and repeat work ("for every product, show a card"). This lesson gives your code both: branching, so it can choose a path, and looping, so it can do something more than once without you writing it out by hand. Everything here reappears later wearing Angular's own syntax — @if, @for and @switch are these exact ideas inside a template.

The problem

Straight-line code can't say maybe.

A script that only ever runs top to bottom can't choose between two outcomes, and it can't do something a variable number of times. Both of those are things nearly every real feature needs — and both come from handing control of "what runs next" to a test instead of to the next line down.

Four values are about to meet an if: the empty string '', the string 'Bob', undefined, and the string '0'. Before you scroll any further — which of the four make if (value) { … } actually run its block? One of them is not what most people guess.

The mental model

if/else is a railway switch.

One train arrives. It hits a switch — the condition — and the switch sends it down exactly one of two tracks. It can never run down both, and it can never sit at the junction doing nothing. Everything in the first half of this lesson — else if chains, truthiness, the ternary, &&/||, even switch itself — is just another way of asking that same fork a question.

One train, one switch, exactly one track. An if / else if / else chain is one train hitting one switch — it leaves on exactly one track, never two, never none once a catch-all else exists.

Chains of else if test conditions top to bottom, first match wins — and stop the instant one matches. Order isn't cosmetic; get it backwards and a test upstream can swallow a case that should have gone somewhere more precise.

The gotcha

Six values fake being false.

JavaScript lets any value stand where a boolean is expected, silently converting it. Exactly six values convert to false — the "falsy six" — and every other value, no matter how empty-looking, is truthy. 

// the falsy six:
false   0   ''   null   undefined   NaN

if (userName) {{ '{' }} … {{ '}' }}     // runs unless userName is '' / null / undefined
if (items.length) {{ '{' }} … {{ '}' }} // runs when the array has at least one item

// ⚠️ trap: 0 is falsy but often a VALID value —
const discount = 0;
if (discount) {{ '{' }} … {{ '}' }}     // skipped! 0 fails the test even though 0 is real data
if (discount !== undefined) {{ '{' }} … {{ '}' }}  // ✅ say what you actually mean
The string '0' is not the number 0. Any non-empty string is truthy — including the three characters '0'. Read data straight from an input field or a URL and it arrives as a string; if (paramValue) happily runs even when paramValue is the text '0'. That's the answer to the napkin above.

Truthiness makes conditions short, but the professional habit is: when 0 or '' are legitimate values, compare explicitly. You'll meet the polished version of that fix — the nullish operator ?? — in the TypeScript tier.

Expressions, not statements

Sometimes you just want a value, not a branch.

if/else is a statement — an instruction that runs code. It can never sit on the right-hand side of =, and it can never appear inside a string. Often what you actually want isn't a branch at all, it's one value or another — and for that, JavaScript has an expression form of the same fork.

Read condition ? a : b out loud as "condition — if so, `a`; otherwise, `b`." The ? is the fork, the : is the word "otherwise." Say it that way a few times and the punctuation stops looking like noise.

&& and || are value-producing too

These two look like they only glue booleans together, but neither one actually returns true/false — each hands back one of its own operands, unchanged.

The other branch

switch: one value, many exact matches.

When a chain of else if is really just testing one variable against a list of exact values, switch says the same thing more clearly. It tests with strict === — so a case 1 never matches the string '1' — and it has one behaviour if/ else doesn't: once a case is entered, execution keeps running downward until it hits a break, whether or not the next case's label still matches.

Switch to pending and turn the toggle off: the log prints both "Verification pending." and "Account banned." — a pending account is never banned, but with no break, execution doesn't know to stop and just keeps running downward. 

switch (status) {{ '{' }}
  case 'pending':
    log.push('Verification pending.');
    // ← missing break!
  case 'banned':
    log.push('Account banned.');
    break;
  default:
    log.push('Unknown status.');
{{ '}' }}

// status = 'pending' logs BOTH lines —
// 'banned' fires even though the
// account isn't banned at all.

One forgotten break and a pending account gets told it's banned too. Nothing crashes — it just quietly runs code that was never meant to run for this value. 

switch (day) {{ '{' }}
  case 'Sat':
  case 'Sun':
    return 'Weekend';   // both share this line
  default:
    return 'Weekday';
{{ '}' }}

// 'Sat' has no code of its own — it
// falls straight through into 'Sun',
// which is exactly the point.

Same mechanism, aimed on purpose: stack cases with no body between them and they all run the line that finally has one. No break needed until the group is done.

The mechanism, again

A for loop packs four instructions into one line.

The classic counting loop is one line doing four jobs: ① init (once, before anything), ② test (before every lap), ③ body, ④ step (after every lap, then back to the test). Own that cycle and every loop bug you'll ever hit is really just "which of the four went missing."

Sets up whatever the loop needs to track — almost always a counter — before the first test. A boolean, checked before every lap including the first. false ends the loop immediately — the body doesn't run one more time. The code between the braces. Runs once per lap, in full, before the step. Almost always what moves the loop toward failing its test. Skip it and you've written while (true) by accident.

Init once, test before, step after. Forget the step in a while loop and the test never turns false — the tab freezes, not crashes. Every loop needs something moving it toward the exit; when a page hangs, that's the first thing to check.

Loops you'll actually write

for...of, while, and the exits only loops have.

  • for...of replaces most counting loops: no off-by-one bugs, reads like English. Use the counting for only when you genuinely need the index.
  • while is for "until something happens" — retries, polling, games. Its danger is the infinite loop: if the condition never turns false, the browser tab freezes.

Two traps hiding in plain sight

"Just use array methods" has an asterisk.

Later in this lesson you'll meet map/filter/reduce as the modern replacement for raw loops — and that's good advice, right up until you need something a plain function can't give you: an early exit, or a change made to the very list you're walking.

forEach has no break — none at all

Not a smaller version of break. Not skippable with return. forEach has no early-exit mechanism whatsoever.

Mutating the array you're mid-loop over

splice doesn't just remove an item — it shifts every later item one slot left. Do that from inside a counting loop that's still climbing upward, and whatever just slid into the deleted slot gets stepped straight over.

Run the buggy version: a 4 survives, because it was the two adjacent evens — 2 then 4 — that triggered the skip. Reset and run the safe version and every even number is gone. filter never has this problem, because it builds a brand-new array instead of performing surgery on the one it's walking.

The modern way

map, filter, reduce: looping without a loop.

Most production code doesn't write raw loops at all. Arrays carry helper methods that do the looping for you — you supply a small function describing what to do with one item, and it's applied to each. 

const nums = [1, 2, 3, 4, 5, 6];

nums.map(n => n * 10)          // [10, 20, 30, 40, 50, 60]  transform each (same count)
nums.filter(n => n % 2 === 0)  // [2, 4, 6]                 keep passers (fewer or same)
nums.reduce((sum, n) => sum + n, 0)   // 21                 boil down to ONE value

// and they CHAIN — each returns a new array for the next to consume:
nums.filter(n => n % 2 === 0)  // [2, 4, 6]
    .map(n => n * 10)          // [20, 40, 60]
    .reduce((s, n) => s + n, 0) // 120
  • map — same length out, every item transformed. "Turn each product into a price."
  • filter — the function is a yes/no test; survivors pass through unchanged. "Keep the in-stock products."
  • reduce — carries an accumulator across items; the seed is its starting value. "Total the cart."
  • None of them touch the original array — they build new ones. That "don't mutate, produce anew" habit becomes load-bearing when you reach OnPush change detection in the expert tier.

Why this matters in Angular

@if, @for and @switch are these exact ideas.

Everything above is plain JavaScript, running in your head or in a console. Angular templates use the identical concepts, wearing template syntax instead of statement syntax:

Same ideas, Angular's syntax
Plain JavaScript Angular template
if / else if / else @if / @else if / @else
for...of @for (item of items; track item.id)
switch / case / default @switch / @case / @default
list.filter(...).map(...), then render @for over an already-filtered/mapped signal
Every trap on this page ports directly: an Angular @switch case still can't fall through because it has no break at all (Angular removed the footgun); an @if still runs exactly one branch; and a list you render with @for is still best built with filter/map rather than mutated in place — the exact habit §9 and §10 were building.

Questions from the back row

Before you go

Six things to remember.

  • if / else if / else chains test top to bottom, first match wins — order conditions most-specific first, and remember that exactly one branch runs (or none, without an else).
  • Truthiness lets almost anything stand in for a boolean, but the falsy six include real, valid data — 0 and '' especially. Compare explicitly (!== undefined, or the ?? you'll meet soon) when either could legitimately happen.
  • A ternary (cond ? a : b) is an expression, not a statement — it can sit inside interpolation; if can't. && and || short-circuit and return one of their operands, not necessarily a boolean.
  • switch tests one value against many exact matches with ===, and falls through without a `break` — a bug by accident, a feature when deliberate for grouped cases. default catches whatever didn't match.
  • A for loop is ①init → ②test → ③body → ④step, looping while the test holds. forEach has no break/continue at all, and mutating an array (splice) while you're mid-loop over it skips items — build a new array instead.
  • map transforms, filter selects, reduce collapses to any shape you build (including an object) — none of the three mutate, and that habit is exactly what Angular's change detection will reward later.
