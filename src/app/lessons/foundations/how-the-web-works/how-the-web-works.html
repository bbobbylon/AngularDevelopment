The problem

Two computers are about to have a very structured conversation.

When you open a website, two machines talk to each other, and they play two completely different roles:

  • The client — your browser (Chrome, Safari, Firefox), on your phone or laptop. It asks for a page and shows it to you.
  • The server — a computer somewhere on the internet that stores (or generates) the website and answers requests for it. "Server" isn't special hardware — it's any computer whose job is to sit there and answer. Your own laptop becomes one the moment you run ng serve.

Two rules of that relationship matter for everything you'll build later, and they're both easy to say and easy to forget:

  • The client always starts. Servers never call you out of the blue — they only answer. (WebSockets keep a line open for two-way chat, but even those begin with a client request.)
  • Each request stands alone. HTTP is stateless: the server doesn't inherently remember your previous request. "Staying logged in" only works because the browser re-sends a small proof — a cookie or token — with every single request. Hold on to that sentence; it explains half of web security and all of authentication.
A plain page with one stylesheet and one script file loads. Before you read any further: how many separate round trips between browser and server do you think that single page load actually costs? Hold a number in your head — the diagram a little further down will let you count for real.

The mental model

Think of it as a restaurant, not a phone call.

You (the client) order from a menu; the kitchen (the server) prepares the food and sends it back. The order travelling there is the request, and the meal travelling back is the response. And crucially — the waiter who takes your second order has genuinely forgotten you were ever here before. That's not rudeness, that's statelessness: unless you show them something that proves who you are (your receipt, your loyalty card — your cookie), every visit starts from nothing.

HTTP remembers nothing between requests. "Staying logged in" is not the server recognizing you — it's your browser re-sending a cookie or token with every single request, and the server re-checking it fresh, every single time.

Not the same protocol

HTTP and HTTPS aren't the same thing wearing a padlock.

Port 80 by default. The browser opens a TCP connection and sends the request straight away — no handshake beyond that.

Every byte — including headers and cookies — travels as plain text. Anyone on the network path (a café Wi-Fi router, an ISP) can read or alter it.

Port 443 by default. Before a single HTTP byte is sent, browser and server run a TLS handshake: the server proves its identity with a certificate, and both sides agree on encryption keys.

Every byte from here on is encrypted, and the server's identity has been verified — the padlock in your address bar is that handshake succeeding, not just a decoration.

It isn't HTTP with a padlock bolted on afterwards. The port is different, and an entire extra handshake happens first — only after that handshake do the request and response from the sample above ever actually get sent.

Three languages

A page is built from three completely different kinds of code.

The body of that 200 response was HTML — but every page is really three technologies working together:

Headings, paragraphs, buttons, images. Like the walls and rooms of a house. Colors, fonts, spacing, layout. The paint and the furniture. What happens when you click, type or scroll. The electricity and plumbing that make things do something.

When HTML arrives, the browser parses it into the DOM — a live tree of objects, one per element — and paints it. JavaScript's superpower is that it can reach into that tree and change it after the page is on screen: add elements, remove them, rewrite text, react to clicks. Hold on to that sentence — it is literally Angular's job description. Angular is a large, organized system for deciding what the DOM should look like right now and updating it when your data changes, written in TypeScript (a safer JavaScript we cover soon).

Where Angular fits

A classic website reloads everything. A single-page app reloads almost nothing.

A simple web page mostly shows information (a blog post, a news article). A web app is interactive software that runs in the browser — Gmail, Google Maps, your online bank. The difference is where the work happens:

Every click asks the server for a whole new HTML page. The browser blanks and redraws. The server does the thinking; the browser mostly displays.

The first response ships one HTML shell plus a JavaScript bundle. From then on, clicks are handled by that JavaScript, in your browser: it swaps content in place and fetches only raw data (JSON) from the server when needed. No blank flashes.

Angular builds SPAs. You're inside one right now: click between lessons and watch the address bar change without a page reload. The Angular router intercepts the click, rewrites the URL, and swaps the lesson component into the page — the seven stops from the diagram above happened only once, when you first loaded the app.

The router intercepts the click entirely inside the browser — no network request happens at all. The "page" you land on was already sitting inside the JavaScript bundle from the very first load.

The browser does what it always does on a fresh load: sends a real GET /lessons/42 straight to the server. A plain static-file host has no file at that exact path on disk, and answers 404 — for the identical URL that worked perfectly one click earlier.

This also explains a trade-off you'll hear about later: an SPA's very first load carries the whole JavaScript bundle (a slower start), after which everything feels instant. Techniques you'll meet at the expert tier — lazy loading, server-side rendering, hydration — are all attacks on that first-load cost. The vocabulary of this page is the foundation for all of them.

Questions from the back row

Before you go

Six things worth remembering.

  • The client (browser) always starts the conversation; the server only ever answers. Each request stands alone — HTTP remembers nothing, and "staying logged in" is really the browser re-proving who you are on every single trip.
  • A URL decomposes into scheme, host, port, path, query and fragment — and only the fragment never actually leaves the browser.
  • A page load is a strict relay, not six things at once: DNS → TCP/TLS → request → response → parse → paint, and a render-blocking stylesheet or script can stall that last step long after the HTML already arrived.
  • An HTTP message is a verb/status line, headers, a blank line, then a body. Status families: 2xx success, 3xx redirect, 4xx your fault, 5xx the server's fault — and none of that applies at all when the failure is a dead connection, because then no server ever answered.
  • HTTP and HTTPS are different pipelines, not one protocol with a setting flipped — a different default port, and an entire handshake that has to finish first.
  • Pages are built from HTML (structure), CSS (style) and JavaScript (behavior) that rewrites the live DOM. A SPA — what Angular builds, and what this app is — loads that trio once, then updates the DOM in place and fetches only JSON from then on.
