Some things are instant (2 + 2). Others take time — fetching data from a server, waiting for a timer. Here's the constraint that shapes everything on this page: JavaScript runs on a single thread — one lane, one instruction at a time — and it's the exact same lane the page uses to respond to clicks and repaint the screen. This page is about what JavaScript does instead of waiting.

The problem

What happens while your code is busy?

Picture one line of code that genuinely takes two seconds to run — no network, no timer, just a slow calculation. While it runs, nothing else on the lane can move: not a click, not a scroll, not the theme toggle at the top of this page. If JavaScript really did stand still and wait for slow things, the whole page would freeze for exactly as long as the wait.

Would you bet on "the page freezes" or "everything still works fine" while that slow line runs? Keep your answer in mind — the rest of this page is the reason you're right either way, because the language that actually ships never lets that two-second freeze happen at all.

So JavaScript never waits. It starts slow work, keeps going, and deals with the result later. Every tool on this page — callbacks, Promises, async/await — is a different way of saying the same sentence: "I'll let you know when it's done."

The mental model

Every async tool below is the same buzzer.

You order a coffee, and instead of making you stand at the counter, the barista hands you a buzzer. You sit down, read, chat — the program keeps running. When the coffee is ready, the buzzer goes off and you collect it. Nobody stood frozen, and nobody had to guess when it would be ready; the buzzer announces it.

Hold onto that picture. A callback is the barista shouting your name across the shop. A Promise is the buzzer itself — an actual object you can hold, hand to someone else, or set on the table and ignore for a while. async/await is the same buzzer, just with a nicer way of saying "wait right here for the beep." Three outfits, one idea.

The mechanism

Async code runs when it's ready — never where it's written.

Round 2

Promises: the buzzer as an actual object.

A Promise makes "a value that will arrive" into a thing you can hold, store, and attach handlers to. It is always in exactly one of three states:

A Promise's three states — and only ever one at a time
pending still working — the buzzer hasn't gone off
fulfilled done, with a value — .then handlers run
rejected failed, with a reason — .catch handlers run

A Promise settles exactly once — the buzzer can't ring twice. (Angular's Observables, coming later, are the "can ring many times" upgrade to this same idea.)

Round 3

async/await: the same buzzer in plain clothes.

An async function always returns a Promise itself — its return value is what that Promise fulfills with. Async is contagious: whoever calls you must await you, or .then you.

await pauses only the function it's written in — never the page. If something on screen looks frozen, the bug is somewhere else.
The forgotten-await bug — the most common async mistake in real code. Forgetting await doesn't fail, or even print a warning — it just quietly hands you the buzzer instead of the coffee.

A subtler bug

The last response to land wins — not the last one you sent.

One request failing is at least visible. This bug is quieter: two requests both succeed, and the wrong one still ends up on screen — because nothing ties a response back to which request asked for it.

}

"cat" is typed first but answers slowest; "caterpillar" is typed second but answers fastest. For a moment the screen is briefly, correctly showing the "caterpillar" results — and then "cat"'s slow response lands and overwrites it, leaving stale results on screen for a search the user already replaced. This is a race condition: the order responses arrive in is not guaranteed to match the order requests were sent in.

The fix: tag every outgoing request (an id, or just "the newest wins") and ignore any response that isn't the latest — or cancel the previous request outright. Angular's switchMap and the resource API you'll meet later do exactly this, automatically, which is the actual reason they exist.

Pulling it together

Three rounds, one buzzer.

Hand a function to run later. Simple for one step; nests into a pyramid once steps depend on each other. The buzzer as an object — pending, fulfilled or rejected. .then chains flatten the pyramid; one .catch covers the whole chain. Same Promises, top-to-bottom syntax. try/catch for errors — but a missing await is still the classic trap.

Questions from the back row

Before you go

Five things to remember.

  • JavaScript is single-threaded and shares its lane with the UI — so it never waits; slow work is started, and its result is handled later. Async callbacks run only after the current code finishes and the microtask queue is empty (A, C, then B — even at 0ms).
  • Evolution: callbacks (nest into pyramids) → Promises (pending → fulfilled/rejected; .then chains flat, one .catch for the whole chain) → async/await (same Promises, top-to-bottom syntax, try/catch errors).
  • await pauses only the function, never the page; a missing await hands you the buzzer ([object Promise]) instead of the coffee.
  • Independent work runs in parallel with Promise.all — sequential awaits are a silent performance bug.
  • Observables (Angular's tool for values-over-time) are this same mindset, many-values edition.
