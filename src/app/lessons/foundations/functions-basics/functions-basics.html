A function is a set of instructions you write once and can run as many times as you like, by name. That alone would make it worth learning — but it hides a second, bigger idea: a function is itself a value. You can store one in a variable, hand it to another function, and let someone else decide when to press the button. That second idea is the one that eventually explains map, every Angular event binding, and most of what RxJS does. This page builds both, in that order, with a live call traced moment by moment so "the function runs" stops being a black box.

The problem

You're about to write the same three lines a third time.

const bill1 = 50;
const tip1 = bill1 * (20 / 100);
const total1 = bill1 + tip1;

const bill2 = 80;
const tip2 = bill2 * (20 / 100);
const total2 = bill2 + tip2;

const bill3 = 120;
const tip3 = bill3 * (20 / 100);
const total3 = bill3 + tip3;
// ...and the fourth bill? The fortieth?

Every line of that block is correct. The problem is that it is the same three lines, retyped with different numbers, and it will keep needing to be retyped for every bill that ever arrives. What you actually want is one set of instructions you can hand different numbers to, over and over — write the recipe once, use it forever. That is a function, and nearly everything else on this page is detail on that one sentence.

Forget syntax for a second. If you were designing "a machine that can compute any bill's tip", what would it need? Something has to go in (which numbers?), something has to happen (the actual maths), and something has to come back out. Picture that shape — in, work, out — before the next section names the three parts for you. You will be right, and being right on paper before you're told the words is exactly how the words stick.

The mental model

A function is a vending machine.

Picture a vending machine. You put coins in a slot — that's an input. Something happens inside that you don't have to think about — gears turn, a mechanism runs. A snack drops into the tray — that's the output. Crucially, none of that happens just because the machine exists. It happens because you pressed a button and pushed coins in. The machine can sit there, fully built and ready, for a year without ever dispensing a single snack.

A function is the same shape, with different words for the same three parts. The parameters are the coin slot — placeholders for whatever comes in. The body is the gears — the work, hidden from whoever's using the machine. The return value is the tray — what comes back out. And exactly like the vending machine, writing a function does not run it. function tip(bill, percent) { ... } on its own does nothing at all — no maths happens, nothing is computed — until something presses the button by writing tip(50, 20).

Defining builds the machine. Calling presses the button. And once pressed, the call itself disappears — it's replaced by whatever the machine handed back. That's the rule every example on this page is secretly demonstrating.

The vocabulary

Four words explain the whole machine.

Time to put names on the machine's parts, using the smallest possible function.

The placeholder name written inside the parentheses of a function's definition — n in function double(n). It has no value of its own; it's a name waiting to be filled in. The real value you hand over when you call a function — 5 in double(5). Arguments are matched to parameters by position: the first argument fills the first parameter, no matter what either one is named. The only thing that makes a function's body actually run. double alone is just a name pointing at a machine; double(5) — with parentheses — is what presses the button. What a call collapses into once the body finishes. double(5) isn't just "a thing that ran" — the whole expression becomes 10, as if you'd typed 10 there yourself.

Get comfortable moving between those four words — "parameters are matched to arguments by position" is a sentence you will see verbatim on an exam, and it means exactly what double(n) and double(5) just showed you: 

function add(a, b) {{ '{' }} return a + b; {{ '}' }}

add(2, 3);   // a = 2, b = 3 — matched by POSITION
add(3, 2);   // a = 3, b = 2 — same function, different pairing, different answer

…and when there are too many arguments, or you don't know how many are coming?

Extra arguments aren't an error either — a function only ever looks at as many as it has parameters for, and the rest are silently thrown away. Sometimes, though, you genuinely want any number of arguments as a single list. That's what the three dots below are for.

Scope

A function can see out, never in.

Variables declared inside a function — including its parameters — are local: created fresh at each call, invisible outside it, and destroyed when the call ends. The function can see outward to variables declared around it; visibility is one-way, inside-out. This is a feature, not a limitation: it's what lets hundreds of functions coexist in one app without their internal names leaking out and colliding.

Going deeper

A function can remember where it was born.

The Scope section above ended on a promise: locals die the moment their call ends. That is true — except when it isn't. If a function hands back another function, and that returned function still reads a variable from the call that created it, something has to keep that variable alive. It has to, or the returned function would be reading garbage. That "something" is a closure, and it is one of the most-tested ideas in this entire curriculum.

A function remembers where it was born, not where it's called. Every fresh call to makeCounter() gives birth to a brand-new scope, and every function returned from that call is bound to that one scope for life — never to any other. The superpower

Handing over a function is not the same as running it.

const add2 = … a few sections back already gave it away: a function can be stored in a variable. Which means it can also be passed to another function — and that flips the relationship entirely. Instead of you running it, you hand it over and someone else runs it later. A function passed around like this is called a callback.

shout vs shout(). The name is the machine; the parentheses press its button. When handing a callback over, you always pass the machine, unpressed — parentheses at the wrong moment call it right now instead of later.

Angular runs on exactly this: (click)="onSave()" hands the framework a function to call on each click; RxJS, effects and route guards are callbacks end to end. Get comfortable passing functions and half the framework's API surface stops looking mysterious.

There's a quieter payoff too, easy to miss once you're chasing callbacks: a function lets you name an idea. calculateTotal(), isLoggedIn(), sendEmail() read like sentences and hide their messy insides from whoever calls them. Most good programs turn out to be a lot of small, well-named functions calling each other — Angular itself is thousands of them.

One more distinction

Some functions promise to touch nothing outside themselves.

Every function you've written on this page so far computes something from its arguments and hands it back — never touching anything outside itself. That's not an accident of the examples; it's a property worth naming, because plenty of real code breaks it on purpose, and knowing which kind you're looking at is one of the fastest ways to reason about a bug.

Questions from the back row

Before you go

Six things to remember.

  • A function = parameters in → body runs → return out. Defining it does nothing; calling it (parentheses) runs it, and the call is replaced by whatever it returns.
  • A missing argument becomes undefined (often NaN downstream); extra ones are silently dropped. Default parameters (percent = 15) and rest parameters (...args) are how you take control of both.
  • Locals and parameters live only for one call and are invisible outside it — except when a returned function keeps reading them. That's a closure: it remembers where it was born, never where it's called.
  • A function declaration is hoisted whole and callable before its own line; a const holding a function is not — order matters for one and not the other.
  • Functions are values — pass one without parentheses and you've handed over a callback for someone else to run later. map, event handlers, timers and most of Angular run on exactly this.
  • A pure function (same input, same output, touches nothing outside) is the easiest kind to reason about; a guard clause uses "return ends the function" to keep the main path flat.
