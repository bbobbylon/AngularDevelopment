Programming means writing instructions for a computer to follow, one at a time, top to bottom. Almost every instruction works with two ideas: a value (a piece of information) and a variable (a place to keep one so you can use it again later by name). This page builds both properly, shows you exactly how a computer walks through a program, and — because this is where every beginner gets bitten at least once — defuses the traps before you meet them for the first time in an exam.

The problem

A computer never guesses what you mean.

Ask a friend to "grab the big one" and they will glance around, use context, and probably get it right. A computer cannot do any of that. It runs the exact instructions you gave it, in the exact order you gave them, and nothing else — no guessing, no filling in gaps, no "I think you meant". That sounds limiting, and it is also the entire reason programming is learnable: the machine's behaviour is completely predictable once you know what instruction you actually wrote.

So the very first problem every program has to solve is a small one: where do I keep the information I'm working with, so a later instruction can use it? That question is what values and variables answer, and it is worth taking seriously — the rest of this entire course is built on top of the answer.

You write let score = 0;. A little later, some other line runs score = 10;. Is that the exact same box with new insides, or does JavaScript throw the old box away and make a brand new one? Commit to an answer now — you'll get to check yourself against a real diagram in a few paragraphs.

Values

Every value has a kind, and the kind decides what happens next.

A value is one single piece of data. The everyday kinds — called types — you will use constantly:

The four types you'll meet in almost every program
Type What it looks like
Number 42, 3.14, -7 — for counting and maths. Never in quotes.
String 'Ada', 'hello world', even '42' — text, always inside quotes. The quotes are the only thing telling you (and the computer) that this is text and not a number.
Boolean true or false — a plain yes/no answer, named after logician George Boole. Every decision a program ever makes boils down to one of these two words.
undefined / null Two different flavours of "nothing here": undefined means a variable was never given a value; null means something was deliberately left empty on purpose.

The mental model

A variable is a labelled box — not the thing inside it.

A variable is a box with a name written on the outside, sitting somewhere in the computer's memory, holding one value so a later instruction can find it again. Here is the part worth sitting with: the label on the box does not care what's currently inside it. You can open the box, throw out the old contents, and put something new in — the box is still the same box, still has the same label, and any other instruction that reaches for it by name still finds it in the same place.

You create ("declare") a box with let or const, and the two keywords disagree about one thing only — whether the box can ever be refilled:

Default to const. Professional code uses const for almost everything and reaches for let only when a value genuinely must change later — a counter, a running total. A sealed box is one less thing that can go wrong: if something tries to overwrite it by mistake, the program announces the mistake immediately instead of silently corrupting data.

The mechanism

Programs run one instruction at a time, and a box never "keeps up".

Here is the single most useful skill on this entire page: being able to trace code — play computer, one line at a time, tracking exactly what every box currently holds. Reading an assignment line the way the computer does means running it in a fixed order, every single time:

Right side first, then into the box. Every assignment reads the current contents of whatever is on the right, computes an answer, and only then stores that answer in the box on the left. Once stored, the answer has no memory of the formula that produced it.

Which leads straight to the trap: if total was calculated from price and qty, and then qty changes, does total update itself?

The toolkit

Operators do the work — but not always the job you'd guess.

You have already met +, -, = and ===. A handful more come up constantly enough to learn on purpose rather than by accident:

Open your browser's developer console (usually F12) and type 7 % 3, then 5 === '5', then true && false. Reading about an operator and watching it answer your question are two different kinds of learning — this page can only do the first one for you.

Comparisons don't do anything on their own — each one produces a boolean that you can store, print, or hand to a decision (the very next lesson). &&, || and ! let you combine several yes/no questions into one: "is the user logged in AND is the cart non-empty?"

The famous trap

One equals sign is not like the other two.

Three different symbols, spelled almost identically, doing three unrelated jobs. This single family of confusion produces more beginner bugs — and more exam questions — than anything else on this page, so it earns its own section rather than a footnote.

  • = — one equals sign. Assigns. "Store the right side into the left side."
  • == — two. Compares, after silently converting types. Legacy, and banned by modern style.
  • === — three. Compares, with no conversion at all. The one you should reach for by default.

The most dangerous of the three is the single one, because using it where you meant a comparison is completely legal JavaScript that runs without any error:

Two equals signs are almost as risky, in a quieter way — they compare, but only after converting one side to match the other's type:

One = assigns. Three === compares. Never write two. If you ever catch yourself reaching for ==, you almost certainly wanted === — and if a condition looks suspiciously easy to satisfy, check it for a stray single equals sign first.

Professional habits

Name things for the next reader — probably you, next week.

Code is read far more often than it is written, so a variable's name is a tiny piece of documentation that never goes stale. The convention in JavaScript and TypeScript is camelCase: the first word lowercase, every following word capitalised, no spaces or underscores. 

const x = 86400;
let n = 3;
const arr = [];

Runs perfectly. Six months from now — or six minutes — nobody, including you, can tell what any of it is for. 

const secondsPerDay = 86400;
let itemsInCart = 3;
const pendingOrders = [];

Identical behaviour, and the code now explains itself without a single comment.

Comments are the other half of writing for a reader: text the computer skips entirely, left behind for the next human.

Best practice you'll see throughout this codebase: comment the why, not the what. // add 1 to i restates what the next line already says in plain sight; // cart prices arrive as strings from the API saves the next reader an entire investigation.

Pulling it together

Four traps you will meet again — probably this week.

'5' + 5 gives '55', not 10 — one string on either side of + switches the whole operation from addition to gluing text together. A box holds the answer of a calculation, never the calculation itself. Change an input afterwards and nothing recalculates on its own. if (score = 100) assigns and always passes. It never compares anything — that would need a third equals sign. A missing value doesn't crash on its own — it hands back undefined and waits. The crash always arrives one step later, when something tries to use it.

Questions from the back row

Before you go

Five things to remember.

  • A value has a type, and the type decides what an operator means — 5 + 5 is addition, '5' + '5' is gluing, and '5' + 5 silently glues too.
  • A variable is a labelled box, not the value inside it. Reassigning a let box keeps the same box with new contents; a const box refuses a new owner outright, and the attempt throws rather than quietly failing.
  • Programs run one instruction at a time, and every assignment reads its right side first, computes an answer, then stores it. A box never "keeps up" with a value that changes after it was written — you must recalculate on purpose.
  • = assigns, === compares with no conversion, and == compares after secretly converting types. if (x = value) is a legal, silent bug — always double-check you wrote enough equals signs.
  • Name variables for meaning in camelCase, and comment the why, not the what.
