A variable holds one thing. Real programs deal in many things (a list of users, a cart of products) and in one thing with many parts (a user's name, age and email). Those are arrays and objects, and between them they are the shape of essentially all app data. Hiding inside them is one idea — references — that will later explain why a screen refuses to update even though your data is perfectly correct. We take that idea very seriously on this page.

The problem

You cannot name three hundred variables.

So far every value you have stored got its own name. That works beautifully for two things and falls apart at four: 

{{ tooManyNames }}

The moment you write fruit3, you have already lost. You cannot loop over those names. You cannot ask how many there are. You cannot add a fourth without editing your code. What you actually wanted was one name holding many values — and, separately, one name holding many labelled facts about a single thing. Those two wishes are exactly what arrays and objects are.

Before any of that, a question to keep in your pocket. You make two shopping lists. Both say ['milk'] — same word, same single item, written on two different pieces of paper. In JavaScript that is const a = ['milk'] and const b = ['milk']. Is a === b true? Commit to an answer now. Nearly everyone gets this wrong the first time, and the reason it is wrong is the most useful thing on this page.

The mental model

An array is a row of numbered lockers.

Picture a corridor of lockers bolted together in a row. Each locker holds one thing. Nobody named them — they are just numbered, left to right, and the number is how you get at what is inside. Add a locker to the end of the row and the row gets longer; take one away and it gets shorter. The row itself has one name; the lockers have positions.

That is an array. The position is called an index, and here is the part that catches everyone: the first locker is number 0, not number 1. The count and the last index are therefore never the same number, which is a fact worth staring at for a moment.

OBOE — the off-by-one error. It is so common it has an acronym. When a loop misses the last item, or you read undefined from a list you can see has data in it, check the boundary before you check anything else: [0] is first, [length - 1] is last, and [length] is always one step into the void.

The toolkit

Two families of method. Tell them apart.

Arrays come with a few dozen built-in methods, and they split cleanly into two families that behave in opposite ways. Confusing the families is the source of a genuinely nasty class of bug, so learn the split before you learn any individual method. 

{{ mutatorsSample }}

push, pop, shift, unshift, splice, sort, reverse. They edit the array in place and mostly return something else entirely — push hands back the new length, pop hands back the item it removed. 

{{ producersSample }}

map, filter, slice, concat, join. They read the original, leave it exactly as it was, and hand you back a new value. Nothing you were holding changes underneath you.

The four you will use every day

"Turn every item into something else." One in, one out — the result is always the same length as the original. "Keep only the items that pass this test." Same items, fewer of them. When nothing passes you get [] — an empty array, never undefined. "Give me the first one that passes." Not a list — the item itself, or undefined when there is no match. This is the one people trip over. "Boil the whole list down to one value." A total, a longest name, a lookup object — whatever you build in the function you hand it.

The other shape

An object labels its slots instead of numbering them.

Same corridor, different building. This time each locker has a name written on the door instead of a number — think of a paper form, where every box has a printed label beside it: Name, Age, Member?. You do not fetch the value in box two; you fetch the value labelled age.

A label is called a key (or a property — the words are used interchangeably), and what sits behind it is the value. An object is a bag of key–value pairs describing one thing. Order is irrelevant, because nothing is found by position.

The last line is the whole argument for bracket access. key is a variable whose contents you are changing from a dropdown, and person[key] follows it. Swap in a dot and it breaks: person.key hunts for a property literally spelled k-e-y, finds none, and quietly hands back undefined.

The error message never points at the broken line. A missing key gives you undefined and no complaint — same as reading past the end of an array. So person.adress.city (note the typo) does not blow up where the typo is: person.adress quietly evaluates to undefined, and it is asking that for .city that explodes. Read Cannot read properties of undefined (reading 'city') as: whatever was immediately left of .city was nothing. When you only want a value if the parent exists, person.adress?.city — the optional chaining operator — hands back undefined instead of crashing.

The shape of real data

Almost everything is an array of objects.

Neither shape is exclusive: an object's value can be an array, and an array's slot can hold an object. Stack them and you get the shape that virtually all application data arrives in — a list of records, each record a labelled group. A cart of products. A feed of posts. The lesson list in this app's sidebar is literally one of these.

Notice that nothing new was introduced to make that work. There is no "nested object" feature — a value can be anything, objects and arrays are values, and that single rule is what produces every shape you will ever meet. Reading them is always the same discipline: go left to right, one hop at a time, naming the type you are holding at every step.

The combination, queried

And here is why the two halves of this lesson were worth learning together. You reach into the list with the array vocabulary — map, filter, find, a number in brackets — and then into whatever it hands you with the object vocabulary, a key after a dot. Every table, cart and feed you will ever render is this one snippet with different words in it.

The trap

A variable never holds an object.

Back in Programming Basics, assignment copied a value: let b = a put a second, independent 5 into a second box. Objects and arrays do not behave that way at all, and the difference is the root cause of an entire genus of bug.

Here is the sentence to memorise before anything else: a variable holding an object does not contain the object. Somewhere in memory there is an object, and the variable contains an arrow pointing at it — an address, a note saying "it's over there". Assignment copies the arrow, not the thing at the end of it.

Press x.count++ a few times: y climbs too, and x === y reads true, because there is only ever one object. Now press the copy button — === flips to false and the two numbers go their separate ways forever. Nothing about the contents changed at the moment you copied. What changed is that there are now two objects.

Which finally answers the napkin from the top of the page: const a = ['milk'] and const b = ['milk'] are a === b → false. Two separate [ ] literals ran, so two arrays exist, and === was never looking at the milk. It was comparing the arrows.

Boxes hold values. Arrows hold objects. Copy a box and you get a second value. Copy an arrow and you get a second way to reach the same object — and === only ever asks whether two arrows land in the same place.

Four consequences you will meet this week

  • === compares arrows, not contents. Two objects with identical properties are !== unless they are literally the same object. There is no built-in operator that compares contents.
  • const seals the arrow, not the object. const person = { age: 36 }; person.age = 37; is perfectly legal. Only pointing person at something else is blocked.
  • A function receives your arrow, not a copy of your data. Anything it mutates, it mutates for you too. Spooky action at a distance, unless the function copies first.
  • Frameworks lean on this to detect change cheaply. "New arrow = something happened" is fast to check. Mutate in place and the arrow never moves — which is the screen didn't update, coming to a lesson near you.

The way out

Three dots make a real copy.

If sharing an object by accident is the problem, deliberately making a new one is the fix. The tool is the spread operator — three dots — and it reads as "pour everything from that into this new one".

Spread copies the top drawer only. Everything one level down is still shared. Copy at every level you intend to change — { ...user, settings: { ...user.settings, theme: 'dark' } } — or use structuredClone() when you genuinely need the whole thing duplicated.

Destructuring — the same idea, running backwards

Spread pours values into a new container. Destructuring pulls them out into ordinary variables. It uses the same braces and brackets, on the other side of the =, which is exactly why it looks so wrong the first time you see it.

Read it right to left. The thing after the = is what you have; the braces before it are a shopping list of what you want out of it. const { name } = person is not building an object called name — it is saying "from person, hand me the name". Say the sentence out loud a few times and the syntax stops fighting you.

Why this matters later

This is the Angular bug you have not hit yet.

Everything above is plain JavaScript, and you would be forgiven for filing it under trivia. It is not. Angular — and React, and Vue — decide what to redraw by comparing the value a template used last time against the value it has now, with ===. You already know what === does to objects: it compares arrows.

Which is why this very lesson's demos are written the way they are. Look at add() in this page's source: it does [...list, v] rather than list.push(v), and setName() does { ...p, name } rather than p.name = name. Not style — those are the versions that render. The habit of copying instead of mutating starts here, months before you meet the framework that demands it.

The bargain, stated once: you promise to hand Angular a new array or a new object whenever something changes, and in exchange Angular promises to notice with one cheap comparison instead of scanning your data. The signals and OnPush lessons are both, underneath, about keeping your end of it.

Questions from the back row

Before you go

Five things to remember.

  • Arrays are numbered, objects are named. First is [0], last is [length - 1], and reading past either end — or asking for a key that is not there — gives you undefined rather than an error. The crash always arrives one hop later.
  • Know what shape comes back. map and filter hand you arrays; find hands you one item or undefined; reduce hands you whatever you built. And push, splice and sort change the original while map, filter and slice never do.
  • A variable never holds an object — it holds an arrow to one. Assignment copies the arrow, so two names can share one object; === compares arrows, so two identical objects are not equal; const freezes the arrow, not the contents; and a function you pass an object to is editing yours.
  • Copy with spread, and remember it is shallow. { ...old, key: newValue } is the single most-typed pattern in modern app code — but anything one level down is still shared, so spread at every level you mean to change.
  • "New reference = something changed" is the deal you will strike with Angular. Mutating in place keeps the arrow identical, the framework's === says nothing happened, and your correct data sits behind a stale screen. Start copying now and that bug never gets to exist.
