We've covered values, functions and collections. Now: how does code actually change what's on the screen, and respond when you click something? The answer is the DOM and events — and once you've seen both properly, every framework feature you meet later stops being magic and becomes "oh, it's doing that for me."

The problem

Your HTML file is not what's on the screen.

Right-click any page and choose "View Page Source", and you'll see the raw text the server sent — the file, exactly as written. Now open DevTools and look at the Elements panel. On a modern Angular app those two views can look nothing alike: source shows a handful of near-empty tags, and Elements shows a fully built page with thousands of nodes neither you nor the server ever typed.

Both are real. They are just two different things. The file is static text — call it the recipe. What the browser builds from that text, the moment it starts reading, is a live, in-memory object tree called the DOM (Document Object Model) — the cake. Once the DOM exists, the file is irrelevant. JavaScript never touches your HTML file again; every "the page changed" you will ever see is something rewriting the DOM.

If the file and the DOM are different things, which one does document.querySelector('button') search? And which one does a screen reader, or the browser's own Find-in-page, actually read? Hold an answer in your head — the FAQ at the bottom names it directly.

The mental model

Indentation in the file becomes nesting in the tree.

Every tag becomes one node. Nodes get family-tree vocabulary, used completely literally: a tag written inside another becomes its child, the outer one becomes its parent, and two tags at the same depth with the same parent are siblings. That's the entire rule — how deep a tag sits in the source is how deep its node sits in the tree.

On-screen means attached-to-the-tree. Nothing else counts. Not written in the file, not sitting in a variable, not "rendered but hidden" — a node shows up the instant it is attached somewhere inside document, and disappears the instant it is removed. Everything else in this lesson is a consequence of that one sentence.

The subtlety

An attribute is frozen text. A property is live.

Every element starts life with its properties matching its HTML attributes — <input value="seed"> gives you both an attribute and a property reading 'seed'. The trap is assuming they stay matched. They don't: the attribute is whatever was written in — or last set with setAttribute — and never changes on its own. The property is the element's live, current state, and the browser updates it constantly as the user interacts with the page.

The property tracks every keystroke. The attribute never moves — it is stuck at whatever the markup said, exactly like the code sample above predicted.

Reacting to the user

An event is something that happened. A listener is you finding out.

A click, a key press, the mouse moving, a form submitting — the browser notices all of it and is happy to tell you, if you ask. addEventListener is how you ask: you hand the browser a function, and it calls that function later, whenever the named event actually fires.

event.preventDefault() Cancels the browser's own reaction — you'll call this one for the rest of your career

The full journey

An event doesn't fire on one element. It fires on all of them.

Here's the part that surprises people, and the old version of this lesson only told half of it. A click on a deeply nested element doesn't just fire there — it travels through the entire ancestor chain, twice. First inward, from document down to the target: the capture phase. Then it fires at the target. Then outward again, target back up to document: the bubble phase — the leg almost everything you write actually listens on.

Starts at document, travels down through every ancestor toward the target. Almost nothing listens here by default — you have to opt in with { capture: true }. The event reaches the element that was actually interacted with. Any capture- and bubble-phase listeners registered on the target itself both fire here. Retraces the same path back out, ancestor by ancestor, to document. This is the default — every (click) you've written on this page has been a bubble-phase listener.

Angular's (click) syntax has no way to express { capture: true }, so this toggle is wired with real addEventListener calls underneath — the one place on this page that reaches past the framework.

Three methods on `event` that sound alike and do different jobs
Method What it actually stops
event.stopPropagation() Halts the journey — no ancestor (or descendant, during capture) gets a turn after this one
event.stopImmediatePropagation() Does that, and cancels every other listener still waiting on this exact element — even ones registered after this one
event.preventDefault() Doesn't touch propagation at all — cancels the browser's own reaction: a form reloading, a link navigating
Capture goes in, bubble comes out — and `(click)` only ever listens on the way out unless you explicitly ask for capture. When someone says "an event bubbles up", they're naming one leg of a round trip, not the whole journey.

Who actually got clicked?

Bubbling isn't a quirk to work around — it's the mechanism behind event delegation: put one listener on a list instead of one per row, and it hears clicks from every current and future row, because the click bubbles up to it regardless of which row fired it. Reading which row takes two different properties, and mixing them up is the single most common delegation bug.

Why this matters

The hard way — and why it doesn't scale.

Wire the click counter from earlier by hand, and you must keep the data and the screen in sync yourself:

A real app has hundreds of data-to-screen connections — a reset button, a second counter in the header, a running total elsewhere on the page. Miss one line 7 and you've shipped the classic bug: the data is correct and the screen is a lie. And the selector strings in lines 2–3 are a second, quieter problem — rename an id in the HTML and the JavaScript breaks with no warning until it runs.

This is the problem Angular exists to solve. You declare what the screen should look like for the current data — {{ '{{' }} count() {{ '}}' }} — and Angular runs the sync line for you, for every connection, whenever the data changes. The click counter demo earlier on this page is Angular: (click)="onClick()" is addEventListener wearing template syntax, the handler only ever touches the data, and the DOM syncs itself. No selector strings, no stale-screen bugs, and the connections are checked when the app is built, not when a user happens to hit the broken path.

Questions from the back row

Before you go

Five things to remember.

  • The DOM is the browser's live tree of node objects, built from — and then completely independent of — your HTML file. On-screen literally means attached to the tree; textContent, innerHTML, remove() and append() are how you edit it by hand.
  • .textContent is always literal text. .innerHTML parses markup — which is exactly what makes an untrusted string dangerous the moment it reaches it. Angular's [innerHTML] binding sanitizes automatically; raw nativeElement.innerHTML does not.
  • An attribute is frozen text from the HTML; a property is the live current state. They start in sync and drift apart the moment anything changes — disabled="false" is still disabled, because presence, not the string, is what counts.
  • Every event travels capture → target → bubble. Nearly everything you write only ever listens on the bubble leg; stopPropagation() halts the journey, stopImmediatePropagation() also cancels sibling listeners on that element, and preventDefault() doesn't touch propagation at all.
  • Plain JavaScript forces you to sync data and screen by hand, one connection at a time, forever. Angular's whole job is running that connection for you — (click) and {{ '{{' }} {{ '}}' }} are addEventListener and .textContent, automated.
