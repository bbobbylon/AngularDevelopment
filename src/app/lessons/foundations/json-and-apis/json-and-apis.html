Nearly everything an app does comes down to data — a user's profile, a list of products, a chat message — living on a server somewhere else. Two ideas make that whole exchange possible: JSON, the plain-text format the data actually travels in, and APIs, the doorways you ask for it through. Every HttpClient lesson later in this course is built directly on top of both, so this page goes deep rather than skimming.

The problem

Your object cannot leave the building.

Somewhere in your running app sits a real, live JavaScript object — it might have methods, a Date, references to three other objects. The moment you try to send it anywhere — across the internet to a server, into a file, into localStorage — you hit a wall: none of that can travel. A network connection carries bytes, not live objects. Not methods. Not a Date instance. Just characters, one after another.

And it gets worse before it gets better: the program on the other end of that connection might not even be JavaScript. It could be Java, Python, Rust — a completely different language with its own idea of what an "object" even is. So whatever format you send has to be something every language can read back, not just yours.

That is the whole problem this page solves. JSON is the agreed-upon shape data takes when it travels; an API is the agreed-upon set of addresses you send and receive it at. Almost everything below is just a consequence of those two sentences.

You build const event = { title: 'Launch day', when: new Date() }. You send it to a server, and a moment later you get back what looks like the exact same shape. Before you read on — does event.when.getFullYear() still work on what comes back? Commit to yes or no. You'll get the full proof partway down this page, and the reason it goes the way it does is worth more than the answer itself.

The mental model

JSON is a flat-pack box.

You cannot post a chair. What you can post is a flat box of planks with a printed instruction sheet, and someone at the other end rebuilds the chair from it. That is the entire idea of JSON. JSON.stringify flat-packs a live object into text; JSON.parse assembles the text back into a live object. Different room, different building, different country, different language even — the box travels fine, because everything inside it is flat.

Which immediately tells you what cannot go in the box. Not the carpenter — a function is a skill, not a plank, and it does not survive the trip. Not "the leg that isn't there" — an empty slot is just an absent plank, which is what happens to undefined. And a Date goes in as a printed label reading 2026-08-29T09:00:00Z, so what comes back out is a label, not a date. Keep the box in your head and most of the rest of this page is just consequences of it.

Only flat things fit in the box. Six value types cross the wire — string, number, boolean, null, array, object. A Date arrives as a string, and functions and undefined do not arrive at all.

The vocabulary

Six types. That's the whole alphabet.

JSON (JavaScript Object Notation) is text shaped like the objects and arrays you already know from JavaScript. That "text" part is the whole point — over a network, in a file, in localStorage, data always travels as characters, and JSON is simply the agreed way to write structured data down so that any program, in any language, can read it back.

It looks like a JavaScript object, but it is stricter — and the rules that trip up almost everyone at least once are exactly the ones a JavaScript object literal doesn't enforce.

The doorway

An API is a menu of URLs you're allowed to ask.

An API (Application Programming Interface) is a server's menu of addresses you may request data from. The dominant style, REST, organizes those addresses around things — called resources — and reuses the HTTP verbs from How the Web Works as actions on them.

One specific address the server listens on — /users/42/orders. Each endpoint is a promise: ask this way, get this shape back. The thing the URL names — a user, an order, a comment. REST paths are built from nouns, never verbs. GET, POST, PUT, PATCH, DELETE — the action performed on the resource. The verb lives in the method, never in the path. The server's one-word verdict on how it went — 200 said yes, 404 said no such thing, 500 said something broke on its end.

Two more rules fall out of this. First, the response always pairs a status code with JSON: 200 plus data, 201 ("created") after a successful POST, 404 when the id doesn't exist, 400 when your JSON was malformed, 401/403 when you aren't allowed. Your app must branch on these — a good UI shows "user not found," not a blank screen. Second, most APIs require identification, typically a token sent in a header (Authorization: Bearer eyJhbG…) with every single request — HTTP is stateless, so you prove who you are again each time.

One more sharp edge, easy to miss because it looks so harmless: query strings built by plain string concatenation don't escape anything, and a special character silently corrupts the URL.

Exam vocabulary

Safe and idempotent are not the same word.

Safe means the call changes nothing on the server. Idempotent means making the call ten times leaves the world in the same state as making it once. Those are not the same thing — DELETE changes plenty, but deleting user 42 five times still leaves exactly one user 42 gone. Almost every REST rule you have been told to follow falls out of this one table.

Questions from the back row

Before you go

Things to remember.

  • A live object cannot leave the process it lives in. JSON is the flat, text-only shape data takes to cross the wire: double-quoted keys and strings, six value types, no functions, no undefined, no trailing commas. It looks like JS but a parser rejects what JS tolerates.
  • JSON.parse (throws on bad input — wrap it in try/catch) and JSON.stringify (drops what it can't express; dates become strings) convert between wire text and live objects. Round trips are not always lossless.
  • A REST API is nouns in paths (/users/42), verbs as HTTP methods, filters in query strings, identity in headers, and a status code plus JSON in every single answer.
  • fetch needs two awaits (the response, then .json()) and does not reject on 404/500 — you check res.ok yourself.
  • GET must never mutate. Ever. Browsers and caches assume it.
