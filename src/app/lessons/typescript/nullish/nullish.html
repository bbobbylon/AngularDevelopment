Two operators, and three quiet decisions hiding inside every use of them: does this check care about nullish or falsy? Does a guard protect one link in a chain or the whole tail? And does "absent" mean null, undefined, or both? Every trap on this page — and there are more than you'd guess for two characters and a question mark — is one of those three questions answered differently than you assumed.

The problem

Reaching three properties deep is a bet that all three exist.

user.address.city reads beautifully and fails the instant reality disagrees with your optimism. If address hasn't been filled in yet — a brand-new signup, an API response mid-flight, a form nobody's finished — JavaScript doesn't quietly return undefined for the missing piece. It throws, and takes everything after it down with it: TypeError: Cannot read properties of undefined (reading 'city'), on a line that looks completely innocent.

You've probably written the old fix: user && user.address && user.address.city. It works. It is also three separate truthiness checks for what is really one question, asked three times: is this link nullish?

Here's the shape of the whole lesson in one guess. user?.address?.city, where address genuinely doesn't exist — what value does the whole expression produce? Not a crash, not null — say the actual value out loud, and say why it's that one and not the other, before you read on.

The mental model

?. is a chain of checkpoints, not a single lock.

Picture a relay, not one locked door. user?.address?.city sets up a checkpoint at every ?. — a guard whose only job is to check one thing: is the value that just arrived nullish? Pass, and the baton — the rest of the expression — moves on to the next checkpoint. Fail, and that guard doesn't throw you out. They call the whole relay off, right there, and hand back one specific answer: undefined. Every checkpoint after the failed one — every . and () still to come — never runs at all.

That last part is the one people miss. A failed checkpoint doesn't skip ahead and try the next check anyway — it ends the entire relay from that point on. a?.b.c.d() with a nullish a never reads .b, never reads .c, never calls .d(). One failure, one exit, for the whole rest of the chain.

Ask, don't assume. Every ?. asks "are you there?" before doing anything else. A nullish answer stops the whole rest of the chain immediately and hands back exactly one value — undefined — never null, whatever was actually missing.

The mechanism

Under the hood, it's just ifs you didn't have to write.

?. works before a property read, a call, and an index — the same one guard, three shapes:

user?.address?.city          // property access
user?.greet?.()              // call — only if greet is itself non-nullish
list?.[0]                    // index access — ?. works before [ ] and ( ) too

None of that is special syntax hiding special behaviour. Here's user?.address?.city ?? 'Unknown' unrolled by hand into the plain ifs it means — not literal compiler output, just what has to be true for the short version to make sense.

Three rules

Memorize these, and every ?. question on an exam is arithmetic.

''?.length is 0, not undefined — an empty string is a perfectly good string. The check is always === null || === undefined, never a truthiness test. Short-circuiting always produces undefined — even when the thing that was actually nullish was null. null?.x === undefined, never null. In a?.b.c.d(), a nullish a stops everything after it — .b, .c and .d() never run. Guard every link that can genuinely be missing, not just the first. 
a?.b.c

Safe against a alone. If b can also be nullish, this throws — the second link never got a guard. 

a?.b?.c

Every nullable link has its own ?.. Neither a nor b can throw here.

The other operator

?? asks one question. || asks a much blunter one.

a ?? b yields b only when a is null or undefined. a || b yields b whenever a is falsy — which wrongly swallows 0, '' and false, all legitimate values. Classic real bugs: a volume setting of 0 resetting to the default, an empty-string search box reverting to a placeholder query, showBanner: false being silently ignored.

Watch null specifically: it is the one value where all three strategies disagree with each other in a way that matters. || and ?? both replace it — but only ?? does that on purpose. The default-parameter row keeps it completely untouched, which is exactly the trap the next section is about.

You can't mix ?? with || or && without parentheses — a ?? b || c is a syntax error by spec (the committee refused to define a precedence people would misremember). Be explicit: (a ?? b) || c.

The one nobody mentions

Default values agree with ?? on almost everything. Almost.

?? and a default value — function f(x = 'fallback'), or const { x = 'fallback' } = obj — both exist to fill in "absent". They just define absent differently. ?? means null-or-undefined. A default means only undefined.

const body = { tags: null }; then const { tags = [] } = body; — what is tags now? An array, or null? Commit to an answer before you scroll to the table.

One row disagrees, and it's the row that matters most in practice: null. A default parameter treats it as a real, present value — because to the language, it is one — and hands it straight through untouched.

The fix is the operator this whole page is about: const tags = body.tags ?? [];. ?? catches both null and undefined; the destructuring default only ever caught one of them.

Putting them together

The idiom is two operators doing two different jobs.

const city = user?.address?.city ?? 'Unknown';
const theme = settings?.prefs?.theme ?? 'dark';

After a line like this runs, city is plain string — not string | undefined. The compiler agrees, no assertions needed, nothing left to prove downstream.

The assignment trio

??=, ||=, &&= — and the call that never happens.

All three short-circuit the assignment itself — and, as the second half of this sample proves, that means the right-hand side isn't merely unused when the guard fails, it is never evaluated at all.

Narrowing by force

! — two assertions, zero runtime checks.

Both flavors silence the compiler and add no runtime check — if you're wrong, the crash still happens, just further from the lie. Prefer a real guard, ?./??, or in Angular: input.required<T>() and signal-based queries, which remove the classic "populated later by the framework" cases where ! used to be routine.

Exam corner · syntax

Four places ?. refuses to go, and one bracket that changes everything.

Where the guard does and doesn't reach
Expression What happens Why
obj?.a.b — obj exists, obj.a is undefined Throws — TypeError reading b of undefined ?. after obj only guards obj itself. Past it, .a.b is ordinary, unguarded access — guard every link: obj?.a?.b.
(user?.address).city Throws, even though user?.address.city (no parens) is fine Parentheses end the optional chain. What's inside evaluates first; .city then reads from that result unguarded.
user?.name = 'new value' SyntaxError, at compile time An optional chain is not a valid assignment target — there's no such thing as "assign, unless nullish".
new user?.Ctor() SyntaxError, at compile time new needs a definite constructor; the spec forbids an optional chain directly inside a new expression.
delete user?.address Perfectly legal — evaluates to true if user is nullish delete is allowed to short-circuit: nothing to delete, and nothing failed.
user?.method?.() Two independent guards, not one The second ?. guards method itself being missing — a nullish callback — not user a second time.

A stricter compiler flag

noUncheckedIndexedAccess makes arr[0] stop lying to you.

By default, TypeScript trusts you completely about array bounds. const first = list[0] types first as string, never string | undefined, even though list might be empty. Map.get() has always been honest about this — map.get(key) is T | undefined unconditionally, because a Map makes no promise the key exists. noUncheckedIndexedAccess applies that same honesty to [] access — and it is not part of strict: true, so most codebases have never turned it on. 

const list: string[] = [];
const first = list[0];   // string — the compiler is sure
first.toUpperCase();     // compiles. Throws: list is empty.
const list: string[] = [];
const first = list[0];   // string | undefined — honestly
first.toUpperCase();     // ✗ 'first' is possibly 'undefined'

Three idiomatic fixes, all of which tell the truth up front:

  • Destructure and guard — const [first] = list; if (!first) return;
  • Reach for .at(-1) (or .at(0)), which has always returned T | undefined regardless of the flag.
  • Lean on ?? at the read site — map.get(id) ?? fallbackUser.

The temptation is list[0]! — and sometimes that's fine: right after you .push() the only item, you already know it's there. On req.query.ids[0] from an incoming request, it isn't a promise you can make; that data came from outside your program.

In Angular templates

Same operators, same rules — plus one idiom worth adopting.

<p>{{ '{{' }} user()?.address?.city ?? 'n/a' {{ '}}' }}</p>

@if (user()?.address; as addr) {{ '{' }}
  <p>{{ '{{' }} addr.city {{ '}}' }}</p>   <!-- narrowed once, used clean -->
{{ '}' }}

Template expressions support both operators with identical semantics — even reading through a signal call like user() changes nothing about how ?. or ?? behave. When a template reads several members off the same maybe-nullish object, prefer @if (…; as x) — one check, then plain reads — over repeating ?. on every binding.

Questions from the back row

Before you go

Six things to remember.

  • ?. checks nullish, never falsy, and always yields undefined on short-circuit — never null — because it normalizes every missing link to the same one value.
  • Each ?. only guards the thing to its left. a?.b.c is not a?.b?.c, and a stray (user?.address).city throws because the parentheses ended the chain before .city was ever protected.
  • ?? asks "null or undefined?"; || asks "falsy?" — they agree everywhere except 0, '' and false, which is where real bugs live. Mixing ?? with ||/&& without parentheses is a syntax error by design.
  • A default parameter or destructuring default asks a narrower question than ?? — only "undefined?", never "null?". They are not interchangeable, and the gap is exactly null.
  • ??=/||=/&&= short-circuit the assignment, including skipping evaluation of the right-hand side entirely — which is what makes ??= the tool for lazy, pay-once initialization.
  • ! (both flavors) is a compile-time-only promise with zero runtime check. Prefer a real guard, ?./??, or — in Angular — input.required<T>() and signal queries, which remove most of the cases ! used to cover.
