TypeScript adds a compile-time layer on top of JavaScript, and Angular's own tooling — including your templates — is fully type-checked against it. Two facts explain almost everything confusing about the type system on this page: types are erased before a single line runs, and TypeScript checks shape, not names — a rule with consequences we'll get to. Read on for how you make a claim about a value, how the compiler makes one for you when you don't, and what's left of either claim the moment your code actually runs.

The problem

JavaScript already runs. So what is a type actually for?

Delete every : Type from a TypeScript file and it still runs — perfectly, in a plain JavaScript engine that has never heard of TypeScript. Sit with that for a second, because it means an annotation isn't doing anything the language needs. So what is it doing? 

function greet(user) {{ '{' }}
  return 'Hi ' + user.name + '!';
{{ '}' }}

greet('Ada');   // 'Hi undefined!' — runs fine. No crash, no warning, wrong forever.

Nothing here throws. 'Ada'.name is simply undefined, and the greeting silently degrades into nonsense that ships to production and stays there until a human notices. Add one annotation and the exact same mistake stops compiling, weeks before anyone runs it against real data: 

function greet(user: {{ '{' }} name: string {{ '}' }}): string {{ '{' }}
  return 'Hi ' + user.name + '!';
{{ '}' }}

greet('Ada');
// ❌ Argument of type 'string' is not assignable to parameter of type '{{ '{' }} name: string; {{ '}' }}'.

So a type is a claim — about a parameter, a return value, an object's shape — that the compiler is willing to check before your code ever runs. Three questions fall out of that framing, and this whole page is really just answering them one at a time:

  • Who writes the claim — you, or the compiler? (annotation vs inference)
  • What happens to the claim once your code compiles? (this one has a genuinely surprising answer)
  • What do you say when you don't know the shape yet — or want to say "this fits anything"? (any, unknown, never, void)
Here's the erasure question up front, because almost everyone gets it wrong the first time. Once greet(user: {{ '{' }} name: string {{ '}' }}) above passes the compiler and gets built into plain JavaScript, does anything in the running app still check that a caller passed an object with a name property? Say yes or no before you keep reading — the mechanism section proves it either way.

The mental model

TypeScript is a building inspector who leaves before anyone moves in.

Picture an inspector who visits exactly once, before a tenant ever gets a key. They walk the blueprints against the actual construction: does this room match what the permit claims? Every mismatch gets flagged right there, before anyone signs a lease. Once the inspection passes, though, the inspector leaves — for good. Nobody official is present when the tenants move in, and nobody comes back next year to check that a room still matches its permit.

That is exactly what happens between compiling and running. tsc is the inspection: it walks every annotation — the ones you wrote and the ones it filled in for you — against how each value is actually built and used, and it does that once. The moment the check passes, the type information is stripped out entirely, and what's left is ordinary JavaScript running with nobody watching.

Claim, check, vanish. An annotation — yours or inferred — is a claim. tsc checks it exactly once, at compile time. Then every trace of it vanishes from what actually runs.

The vocabulary

Every value has a shape. Here's how you write one down.

  • readonly number[] / readonly [string, number] forbid mutation — push simply doesn't exist on the readonly type. Prefer readonly for anything you hand out of a service, where a caller mutating your internal array would be a bug you'd rather catch at build time.
  • Labels on a tuple ([x: number, y: number]) are pure documentation — they don't change what the type accepts — but they make a function signature readable without opening its body.

One more gap worth knowing before you trust an index read: xs[i] always types as the element type, never T | undefined, no matter what i is. 

{{ indexAccessSample }}

strict mode — this app's setting — turns on eight separate checks, and this isn't one of them. noUncheckedIndexedAccess is the opt-in flag that fixes it: flip it on and every indexed read in the program — array elements, Record lookups, index signatures — becomes T | undefined, forcing a check, .at(), or ?? before you can use it. It's off by default because it's noisy — a loop like for (let i = 0; i < xs.length; i++) total += xs[i] suddenly needs a guard on every line — so most teams leave it off and lean on discipline instead.

Open this project's tsconfig.json, add "noUncheckedIndexedAccess": true under compilerOptions, and run a typecheck. However many new red squiggles show up is exactly how many index reads in this app were already unsound — revert the flag once you've had a look.

Inference & widening

You almost never write this one. The compiler infers it — badly, unless you know why.

You rarely annotate an initialized variable; TypeScript infers the type from the initializer. The escape hatches

Four types for when you don't know the shape — or want to say "anything".

Turns off checking completely. Assignable to and from everything — and contagious: every value your code derives from an any becomes any too. One untyped API call can quietly de-type an entire call chain. Holds anything, same as any, but you cannot call a method or read a property until you've narrowed it. Same flexibility at the boundary, none of the spread. No value can ever have it. Returned by a function that always throws; the type control-flow analysis lands on once every branch of a union has been eliminated — which is what makes exhaustiveness checking possible. Means "don't rely on a return value" — not "returns nothing". A () => void callback is still allowed to return something; the type only promises nobody reads it. That's why arr.forEach(x => list.push(x)) compiles even though push returns a number.

Discriminated unions

Tag every arm, and the compiler tells them apart for you.

Give every union member a shared literal field — the discriminant, here kind — and TypeScript can identify the whole arm from that one comparison:

area() is exactly the switch above. Inside each branch the editor's autocomplete offers only that arm's own properties — narrowing is an editor feature as much as a checker feature.

Model impossible states this way — status: 'loading' can't carry an error message, because that arm has no message field to carry one on — and a whole class of bugs becomes something the compiler catches instead of something a user reports. The type narrowing lesson goes deep on the never-exhaustiveness trick this pattern sets up — how one extra union arm turns into a build failure at the exact switch that forgot it.

Structural typing

TypeScript checks the shape. Never the name.

TypeScript is structural — "duck typing" — which means names are irrelevant and members are everything. Two interfaces that never mention each other are still compatible if they happen to describe the same shape:

The excess-property check only fires on a fresh literal. Route the exact same object through a variable, a function return, or a spread, and the check is skipped — which is exactly how a typo'd optional property escapes into a codebase undetected. If you want the check on data that didn't arrive as a literal, that's what satisfies is for, a couple of sections from now.

Questions from the back row

Before you go

Six things to remember.

  • Types are erased before a single line runs. Annotate for the compiler and your editor — never for anything that happens in the browser.
  • let widens what it holds to a settleable type; const keeps the literal; as const freezes a whole value, deeply. A class field's = [] gets none of the leniency a local variable's does — it commits straight to never[].
  • any is contagious and checks nothing; unknown holds anything just as flexibly but makes you narrow before you touch it. Reach for unknown at every untyped boundary.
  • A discriminated union — one shared literal field, a different shape per arm — turns "did I handle every case" into something the compiler proves.
  • Typing is structural: shape beats name, except on a fresh object literal, where the excess-property check catches the typo a shape check alone would wave through.
  • satisfies validates without widening; as and ! are promises the runtime never checks. Narrow first, satisfies second, assert last.
