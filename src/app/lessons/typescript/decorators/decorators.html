You've typed @Component, @Input and @Injectable thousands of times without asking what the @ actually does. This page answers three questions in order — what a decorator IS underneath the syntax, when it runs (and how rarely), and what Angular's own compiler does with the ones you write for it — with real decorators, compiled by this project's own config and executed live on this page, not simulated.

The problem

It's just a function. So why does it feel like magic?

Strip away the @ syntax and a decorator is an ordinary function, called for you, at a moment and with a signature that TypeScript picks based on what you stuck it on. That's the entire mechanism. Everything that feels mysterious about decorators — why @Component takes an object but @HostListener takes a string, why a memoized method's cache is shared by every instance, why @Component can vanish completely in production — is a consequence of when that call happens and what it's called with, not of any special power decorators have that functions don't.

The three questions worth actually answering, in the order this page answers them:

  • What gets called, with what, and how many times? (mechanism)
  • In what order, when more than one decorator stacks on the same thing?
  • What does Angular's own compiler do with the ones it ships? (and what happens to yours, nearby)
You'll meet a real @Memoize decorator further down, applied to a class you can construct as many times as you like. Guess: does its caching Map get built once for the whole class, or once per instance? And separately — you already know @Component decorates a class. Guess whether it actually executes when your built app runs in someone's browser. Hold both guesses; this page proves both, live, before it's done.

The mental model

A decorator is an inspector who visits your blueprint exactly once.

Picture a class not as an object, but as a factory blueprint. A decorator is an inspector who walks onto the factory floor, reads or restamps a specific part of that blueprint, and leaves — before a single unit is ever built. Every unit that later comes off the line already carries whatever the inspector did. The inspector never comes back for unit #47; by then there's nothing left for them to do.

That single picture explains most of what confuses people. A memoized method's cache is shared by every instance because there's only ever one stamp on the blueprint, not one per unit. A decorator can't see a field's initial value because the blueprint doesn't have "values" yet — only shapes. And Angular's AOT compiler doesn't need to run @Component at all, because it can read what's stamped on the blueprint without ever switching the factory on.

Stamped once, on the blueprint, before a single unit is built. Every decorator question is really asking what got stamped — and what a unit built from that blueprint inherits from the stamp.

The mechanism

Five targets, one calling convention each.

A decorator's signature is decided entirely by what kind of thing it decorates — that's the whole reason you can't put @Component on a method or @Input on a class: the function would be called with arguments it isn't shaped to receive.

@Component, @Directive, @Injectable, @Pipe. Receives the class itself, and may return a replacement for it — that's Flavour B, two sections down. @HostListener. The only kind with a real PropertyDescriptor to rewrite — which is why every wrapping decorator on this page (@Logged, @Memoize, @Debounce) is a method decorator. @Input, @Output, @ViewChild, @HostBinding. No descriptor means it can only install something new — never wrap an existing value. See the exam trap this causes, further down. @Input on a setter. Same shape as a method decorator, aimed at a get/ set pair instead of a function. @Inject, @Optional, @Self, @SkipSelf, @Host. No TC39 stage-3 equivalent at all — one whole reason inject() exists.

Two flavours

A class decorator can patch your class, or replace it outright.

Every method decorator on this page returns nothing — it mutates descriptor.value in place. A class decorator has a second option a method decorator doesn't: it can return a brand-new class, and whatever binds to your class name afterwards is that new class instead.

The inheritance trap

Metadata doesn't inherit. Your fields do.

Subclass a decorated Angular class and it's easy to assume the decorator comes along for the ride. It doesn't — and the failure mode is a real, everyday one: an abstract base class holding an @Input() or an inject() call, with no decorator of its own, fails to build.

What does carry across extends, with no help needed: ordinary class members. A subclass of a decorated @Component still has every @Input(), every @HostListener, every inject()-ed dependency its parent declared — those are just fields and methods, and fields and methods are exactly what extends copies forward. What a subclass does not get is the parent's own @Component metadata: no template, no selector, nothing. A component subclassing another component needs its own @Component({ ... }), in full.

@Component doesn't inherit. Your fields, your @Input()s and your inject() calls do — because those live on the class itself, and the class itself is exactly what extends copies forward.

What Angular actually does

In production, @Component never runs at all.

Here's the part that separates "knows the syntax" from "knows the system": in a production (AOT) build, @Component never executes. The compiler (ngtsc) statically reads the decorator's metadata at build time, compiles your template into instructions, and replaces the decorator with generated static fields on the class. It's a compile-time marker, not a runtime mechanism:

Two consequences fall straight out of this: decorator metadata has to be statically analyzable — template: someRuntimeString() breaks AOT because the compiler can't evaluate a function call at build time — and you can't apply @Component conditionally, because by the time your code runs, the decorator is already gone. JIT mode (rare today — some tests, dynamic compilation) is the one place Angular decorators genuinely execute, which is why experimentalDecorators stays switched on in CLI projects at all.

The exam trap

Give the field an initializer, and the decorator goes silent.

Here's a genuine trap, and it's a favourite in interviews precisely because it looks like it shouldn't matter. A property decorator can only install an accessor on the prototype — no descriptor, remember, nothing to wrap. Whether that accessor ever actually fires depends on something that has nothing to do with the decorator at all: whether the field that carries it has an initializer.

The other dialect

TypeScript speaks two decorator dialects. Angular only understands one.

TypeScript 5 ships the standardized (TC39 stage-3) decorator proposal alongside the legacy dialect every sample on this page has used so far. They're genuinely different languages with different signatures — Angular still targets the legacy one, which is exactly why this repo's tsconfig.json sets experimentalDecorators: true. Remove that flag and the compiler switches to stage-3 semantics, and every Angular decorator on the page breaks.

Pulling it together

Where each decorator lands in the signal era.

Modern Angular replaces most member decorators with plain functions that create signals — no reflection, better types, and none of the field-initializer trap above, because there's no prototype accessor left for an initializer to shadow. The class decorators stay — they're still the compiler's entry points.

Decorator era → signal era
Decorator era Signal era Gained
@Input() x = 0 x = input(0) read-only signal, required inputs, transforms — no accessor to shadow
@Output() e = new EventEmitter() e = output() no RxJS coupling, cleaner types
@Input + @Output pair x = model(0) two-way binding in one line
@ViewChild('ref') viewChild('ref') signal, timing-safe, required variant
@ContentChildren(Tab) contentChildren(Tab) signal of a readonly array
constructor(@Inject(TOKEN) t) t = inject(TOKEN) works in field initializers & functions, inheritance-friendly, needs no reflection
@HostListener / @HostBinding host: {...} metadata statically analyzable, the style guide's preference
@Component, @Directive, @Injectable, @Pipe stay — they're how the compiler finds Angular classes at all

Questions from the back row

Before you go

Six things to remember.

  • A decorator is a plain function, called once at class-definition time with a signature that depends on what it's attached to — never once per instance, never once per call.
  • Stack several: factories evaluate top-down; the decorators they return apply bottom-up, so the one closest to the member wraps first and ends up innermost.
  • A class decorator can mutate the class you wrote (add statics, freeze it) or replace it outright by returning a new one — and a replaced class can lose its own .name.
  • Metadata doesn't inherit through extends; fields, @Input()s and inject() calls do. An undecorated abstract base using Angular features fails to compile (NG2007) until it gets a bare @Directive().
  • In an AOT build, @Component and friends never execute — ngtsc reads their metadata statically and replaces them with ɵcmp/ɵfac. That's also why the metadata has to be statically analyzable.
  • A property decorator can only install an accessor; a class field with an initializer creates its own instance property first and silently shadows it. Signal functions like input() exist partly to sidestep this exact trap.
