A union type says "one of these". Narrowing is how you get from that to "this one" — and it is not a cast, a hint, or a favour the compiler does you. It is bookkeeping: at every point in your function TypeScript holds a set of types the value could still be, and every check you write shrinks that set. Learn to see the set and every guard, every trap and every exam question on this topic turns into the same question — what is still on the list here?

The problem

A union is a value you are not allowed to touch.

You write function fmt(x: string | number), and then you cannot do anything with x. Not x.trim(). Not x.toFixed(2). Not x.length. The compiler rejects all three, and the error feels like an insult when you can plainly see the value in the debugger.

It is not being difficult. A union gives you the intersection of the members, not the union of them — you may only touch what exists on every arm. And all string and number have in common is toString() and valueOf(), neither of which is what you came for. The compiler is holding two possibilities at once and refusing to guess between them, which is exactly what you asked it to do when you wrote the |.

So the real question is not "how do I make the error go away". It is:

  • What counts as evidence that a value is one arm and not the other?
  • How long does that evidence stay valid?
  • And what silently throws it away without telling you?
Here is one to commit to before you scroll. Given x: string | Date | null, you write if (typeof x === 'object'). Inside that branch, what does the compiler think x is? Say it out loud — there is a live bench three sections down where you can watch the answer happen, and a quiz that will hold you to it.

The mental model

The compiler is working a shortlist of suspects.

Picture a detective with five names on a whiteboard. They do not add a suspect because of new evidence — the board was written the moment the case opened. Every fact that arrives does one thing only: it crosses names off. When one name is left, that is your answer. When no names are left, you have proved the scenario impossible.

That is control-flow analysis, almost exactly. The whiteboard is the type you declared. Each if, return, throw and switch case is a fact that eliminates arms. And the part that trips people up is the part detectives get for free: an alibi cuts both ways. If typeof x === 'string' is true, only string survives; if it is false, everything except string survives. You never write the second check, and the else branch narrows anyway.

Narrowing is subtraction, not casting. A guard can only remove arms from the union you already wrote — it can never invent a type that was not on the board. So when a narrowing result surprises you, the question is never "what did it cast to?" It is which arm did I fail to eliminate?

Two end states are worth naming now, because the rest of the lesson keeps returning to them. When the shortlist reaches one, you have narrowed, and that type's own members are yours. When it reaches zero, the compiler prints never — the empty type, held by no value at all — and that is not a failure, it is a proof that execution cannot reach here. Every exhaustiveness check you will ever write is built on that second case, and it comes back with a vengeance four sections down.

Guard 1 · the primitive one

typeof knows about eight things. One of them is a lie.

typeof is a JavaScript operator that returns a string, and it can return exactly eight of them. That is its strength and its ceiling: it separates the primitives cleanly and then dumps everything else into one bucket labelled "object".

Every tag typeof can return, and what actually lands in each
Tag What lands there Worth knowing
"string" string and every string literal type Clean. No surprises.
"number" number, including NaN and Infinity typeof NaN === "number" — "not a number" is a number.
"bigint", "boolean", "symbol" Their own primitives Also clean.
"undefined" undefined only The one nullish value typeof reports honestly.
"function" Anything callable, classes included A class is a function at runtime, so typeof MyClass === "function".
"object" Objects, arrays, Date, Map, RegExp — and null The bucket everything falls into. Never enough on its own.
Comparing against a tag that does not exist is a compile error, not a false branch. Typo typeof v === 'strng' and TypeScript raises TS2367 — this comparison appears to be unintentional, then helpfully lists all eight legal tags. It is one of the few places the compiler catches a string typo for you.

Guard 2 · the blunt one

if (x) is the guard that eats your zeros.

Writing if (x) to mean "if x exists" is the most common narrowing habit in JavaScript, and it is wrong roughly as often as your data contains a 0 or an empty string. JavaScript has eight falsy values — false, 0, -0, 0n, "", null, undefined and NaN — and only two of them mean absent. A truthiness check cannot tell "absent" from "legitimately zero".

Use if (x) only when you genuinely want truthy, and if (x != null) when you want present. Say the two words out loud when you write the check; nearly every falsy bug is someone who meant "present" and typed "truthy".

The whole family

Every guard asks a different question, and every one is blind to something.

Five guards do almost all the work in real code. They are not interchangeable: each one asks a different runtime question, and each has one blind spot that shows up in exams precisely because it shows up in production.

Eight tags, and only one of them covers all objects. Its blind spot is null, which reports "object". Walks the prototype chain. Blind to interfaces (erased before runtime, error TS2693) and to objects from another iframe or worker, which have a different Date entirely. Narrows a union by which arm declares a key. Blind spot: an optional property counts as declared, so 'x' in obj can be true while obj.x is undefined. The reliable array check, and the one that works across realms where instanceof Array does not. It is a type predicate in the standard library — that is why it narrows. Comparison against a literal type. A switch is a stack of these. Blind spot: it only narrows when the field is typed as a literal, not as string.

The one the exam is about

Give every arm a literal tag and the compiler does the rest.

If you take one pattern away from this page rather than one fact, take this one. A discriminated union is a union of object types that all declare the same field, each with a different literal type. Comparing that one field identifies the whole arm — and once the compiler knows the arm, it knows every property on it.

The template's @switch is not a decorative mirror of the TypeScript one — Angular's template type-checker runs the same control-flow analysis, so a discriminated union narrows inside @case exactly as it does in code. Try reading message from the @case ('loaded') block and the build fails, not the browser.

You can pull the discriminant out and still narrow the object. TypeScript 4.4 taught the compiler to follow both halves of that, and both halves need a const. An aliased condition narrows — const isLoaded = s.status === 'loaded'; then if (isLoaded) gives you s.data. So does an aliased discriminant — const status = s.status; then if (status === 'loaded') narrows s itself, not merely status. TypeScript 4.6 added the destructured version, so const { status, data } = s; followed by a check on status narrows data alongside it. Change any of those consts to a let and it all stops working instantly, because a binding that could be reassigned is no longer evidence about anything.

Your own guards

Your own guard is a promise nobody checks.

Sometimes the check you need is too involved for an if. So you extract it into a function — and discover the extraction destroys the narrowing, because a function returning boolean tells the compiler an answer without telling it what the answer means. A type predicate is how you say what it means.

Live — a custom guard picking the branch

speak() → {{ sound() }}

The expression behind those buttons is isCat(pet) ? pet.meow() : pet.bark(). In the true arm pet is Cat, so meow exists. In the false arm the compiler has subtracted Cat from the union, leaving Dog, so bark exists. One predicate, two narrowings, no casts anywhere.

A predicate is an axiom, not a proof. The compiler checks only that Cat is possible for p, then believes the body without ever reading it. So keep guards tiny, keep them beside the type they guard, and write tests for them — a type predicate is the one place where a five-line function can silently break a whole codebase's type safety, and the only place a unit test is checking the compiler's assumptions rather than yours.

Narrowing by force

Two more moves: assert it, or prove it cannot happen.

A predicate returns an answer you have to branch on. An assertion function does the opposite — it throws instead of returning false, so if execution reaches the next line the claim held, and every line after the call is narrowed with no if and no nesting.

The last function in that snippet is the other half of this section, and it uses the strangest type in TypeScript. never is the empty type: no value has it, so a parameter typed never can only be satisfied by something the compiler has already eliminated. Put one at the bottom of a switch and you have converted "I handled every case" from a hope into a build guarantee.

Wire assertNever into every switch over a discriminated union. It costs one line and it converts the most common class of "we forgot to handle the new state" bug from a production incident into a red squiggle at the moment the union grows.

The part nobody teaches

Narrowing is about a place in the flow, not about a variable.

Everything so far has been about earning a narrower type. This section is about keeping it, and it is where most real bugs live — because some of the things that destroy narrowing produce a loud compiler error, and some of them produce nothing at all and crash in production instead.
