TypeScript's type system is a second, smaller programming language, hiding inside the one you already know — and it runs at compile time, on types instead of values. It has loops over keys (mapped types), if/else (conditional types), pattern-matching variables (infer), and string interpolation (template literal types). Every utility type you leaned on in the last lesson — Partial, Pick, ReturnType — is a short program written in exactly that language, and by the end of this page you can read every one of them, write your own, and see coming the handful of places this language stops behaving like the one you learned first.

The problem

Every utility type you've used is a program someone else wrote.

You've reached for Partial<User>, Pick<User, 'id'>, maybe ReturnType<typeof fetchUser> — and if you're honest, each one felt a little like magic. Type an angle bracket, get a transformed type out, no idea how. Here's the whole secret: Partial<T> is not a compiler built-in. That loop reads: "for every key K of T, produce an optional property K whose type is whatever T had at K." Fine for an object. So what does Partial<string[]> become — an object with 0?, length?, push? and the rest of the array's methods, all optional? Or something else entirely? Hold that guess. The answer, and why it fools almost everyone, is a few sections down.

The mental model

Four features. That's the whole language.

Everything below is built from four moves, each one a compile-time stand-in for something you already do at runtime. Pin them down now and every later section is just one of these four, applied to a new problem.

Loops over every key of T, producing a new object type — one pass, one new property per key. An if/else the compiler evaluates. Fed a bare type parameter and a union, it can run once per member. Pattern-matching for types: name a piece of a matched shape, then reuse it in the branch that matched. String interpolation for types — and, matched the other way round, a way to parse a string apart.
Loop, test, capture, build. Every mapped type is a loop, every conditional type is a test, every infer is a capture, and every template literal type builds a new string. Whatever you're staring at below, it's one of these four.

The exam trap

Some mapped types copy the shape you gave them. Most don't.

Every mapped type you've seen so far was written [K in keyof T], with T sitting there completely bare. That specific shape has a name — homomorphic — and it isn't just trivia: TypeScript special-cases it. A homomorphic mapped type copies the input's own structure instead of building a fresh object from scratch. An array stays an array. A tuple stays a tuple, arity and all. A plain object is the only input that still comes out as a plain object.

The moment the loop stops being exactly [K in keyof T] — a renamed key, a filtered key, a loop over some other type parameter entirely — that special case switches off, and you get an ordinary object back, no matter what went in. 

type Optional<T> = {{ '{' }} [K in keyof T]?: T[K] {{ '}' }};

T appears bare inside keyof T. Whatever shape you feed it comes back out.

type Flagged<K extends PropertyKey> = {{ '{' }} [P in K]: boolean {{ '}' }};

K is its own type parameter — T is nowhere to be found. Always a plain object.

The semantics nobody explains

Feed a conditional a union, and it runs once per member.

When the checked type is a bare type parameter and you instantiate it with a union, the conditional doesn't run once over the whole union — it runs once per member, and the results are reassembled into a new union. That's the rule that makes a one-line filter over a union work at all:

Distribution runs however the union was spelled — even when you didn't spell it as a union yourself. boolean is secretly true | false, so Exclude<boolean, true> distributes over both members and comes out as false, not never. A tidy proof that distribution operates on the union's actual members, not on how confident you feel that T "isn't really a union."

When you don't want that — when T should be treated as one whole union, not iterated — wrap both sides in a one-element tuple. A tuple is no longer a bare type parameter, so the special case never fires:

Distribution's sharp edge: never is the empty union — zero members to iterate over — so a distributive conditional fed never returns never itself, no matter what either branch says. IsNever<T> = T extends never ? true : false famously evaluates to never, not true. The fix is the same tuple wrap: [T] extends [never].
A bare type parameter distributes over a union — the conditional runs once per member. Wrap both sides in a one-element tuple, [T] extends [U], and it runs once, on the union as a whole.

The half nobody shows you

A template literal type can take a string apart, too.

Building a string is the easy half. The half that earns the feature — and the half interviews actually ask about — is matching: given a route like '/users/:id/posts/:postId', pull every :param segment out as a union of string literals, entirely at the type level.

The same trick, walked over an object's own keys instead of a URL's segments, is how a type-safe deep getter — get(obj, 'address.city') — infers what its own return type should be.

Power budget: in application code you should mostly consume the built-in utilities; write custom mapped/conditional types when you're building reusable libraries or framework-level helpers (typed form builders, API clients, event maps). Before you go

Five things to remember.

  • The type system is a language: mapped types are loops over keyof, conditionals are if/else, infer is pattern-match capture, template literals are string interpolation — and can parse a string apart just as well as they build one.
  • Homomorphic mapped types copy structure. Only the exact shape [K in keyof T], with T bare, preserves arrays and tuples — every other mapped type produces a plain object, always.
  • Bare-parameter conditionals distribute over unions (how Exclude works); wrap in [T] tuples to opt out. never distributes to nothing; any in the checked position takes every branch at once.
  • A recursive conditional type has a depth limit — and hits it far sooner when the recursive call isn't the direct result of a branch. Keep the call in tail position.
  • Every built-in utility is a one-liner you can now derive — Omit = Pick<T, Exclude<keyof T, K>> — and they compose. Reach for hand-written type programs in libraries and helpers, not everyday app code.
