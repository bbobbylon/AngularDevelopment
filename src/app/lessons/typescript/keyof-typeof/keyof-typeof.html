These three operators let you derive a type from a value, or from another type, instead of typing it out by hand and hoping it stays right. That flips the usual direction of maintenance: the object becomes the single source of truth, and every union, check and autocomplete the compiler offers you is recomputed from it, on every build. Add a key to the object, and everything downstream updates itself — nothing can drift, because there is only ever one place to edit.

The problem

You hand-wrote a type. The data just moved on without it.

Here's a shape you've probably typed before: a small config object, and right underneath it, a union of its keys — written out by hand because that felt like the obvious thing to do. 

{{ configSample }}

Six months later, someone adds a fourth field — retryDelay — to config. Nothing about ConfigKey changes. It still compiles. Autocomplete on a variable typed ConfigKey quietly refuses to offer the new field, forever, until someone remembers to come back and edit a completely different line of code than the one they just touched.

So before any operator gets a name, sit with the actual question:

  • What would make ConfigKey recompute itself the moment config gains a field?
  • Is there a way to make the type read the object, instead of being typed out next to it?
Below is this exact scenario, made real: a THEME object and a colour picker built entirely from keyof typeof THEME. Add a fourth colour to THEME in your head — say warning. Does the picker gain a fourth button? Does anything anywhere need to be told about it by hand? There's a live version further down the page to check yourself against.

The mental model

Typing a type by hand is typing a number into a spreadsheet cell.

Think about a spreadsheet. You can type 47 directly into a cell, or you can type =SUM(A1:A10). Both show 47 today. Only one of them is still right after somebody edits row 6. Writing ConfigKey by hand is typing in the number. typeof, keyof and indexed access — T[K] — are the formula bar.

The analogy keeps paying off in two more places. as const is telling the spreadsheet to keep the exact value instead of rounding it — leave it off and the literals widen, and your formula quietly returns string, the "any number at all" of types. And erasure is the printout: the formulas live in the workbook, but the page that comes out of the printer has only values on it. Your compiled bundle is the printout — which is exactly why none of this costs a byte, and exactly why none of it can check data arriving at runtime.

typeof lifts, keyof lists, [K] looks up. Lift a value into a type, list that type's keys, look up what's stored at one. Chain all three and you can read most of the generic TypeScript you'll ever meet.

The mechanism

typeof — lift a value into a type.

Start with the only hand-written thing on this whole page: an ordinary const.

Worth flagging early: this typeof shares a keyword with the runtime typeof x === 'string' from the narrowing lesson — but it's a completely different operator. The type-level one only exists in a type position and never runs; the compiler tells the two apart purely by where they appear.

One bracket further

T[K] — look up what's stored at a key.

One operator left: given a type and a key, what's actually stored there?

That last idiom — indexing by number — is common enough to deserve its own live demo. These buttons are generated straight from an as const array, and the type of the selected role comes from indexing it.

Live — T[number], indexing an array by position

@for (r of roles; track $index) { }

roles[{{ roleIndex() }}] = '{{ role() }}' 

const roles = ['admin', 'editor', 'viewer'] as const;
type Role = (typeof roles)[number];   // 'admin' | 'editor' | 'viewer'

Add a fourth role to the array and the Role union — and these buttons — pick it up with zero other edits. Same single-source-of-truth idea as the THEME demo further down, applied to a tuple-like array instead of an object.

Putting the brackets together

The chain, link by link.

Three separate operators, learned three separate ways — and then a real codebase hands you (typeof ROUTES)[keyof typeof ROUTES] on one line and it looks impenetrable. It isn't; it's every step below, written inside-out, like a formula.

Putting the three together

Build the classic type-safe getter, piece by piece.

In plain English, not TypeScript syntax yet: how would you describe a function prop(obj, key) whose return type automatically matches whatever key turns out to be? What has to be true about key for that to even be checkable at compile time?

Read the three type parameters as a sentence: "given any object T and a key K that provably belongs to T, I return exactly the type stored at K." No overloads, no casts — and it self-updates when User gains a field. This one signature shape (K extends keyof T … T[K]) is the backbone of typed form helpers, ORMs, state selectors, and half the generic APIs you'll ever read.

One more wrinkle

    
as const never calls Object.freeze.


    

      Everything above is a compiler-only promise. Nothing about as const touches the
      array at runtime — no freezing, no locking, nothing a debugger could ever see. The type system enforces the rule;
      the array itself is exactly as mutable as it always was.
    


    

    

      Compile-time and runtime immutability are independent — having one tells you nothing
      about the other. as const alone protects nothing once a cast or a plain .js caller gets
      involved; reach for Object.freeze(ROLES) too when the array must actually resist mutation, not just
      fail a type check.

Under the hood

    
None of this exists once your code runs.


    
That's worth sitting with, because it explains both the power and the limits of these operators.


    
    
      
  • 
        Full erasure, zero runtime cost. The compiler resolves
        typeof/keyof/T[K] entirely during type-checking, then strips every type
        annotation before emitting JS. The buttons in the THEME demo above are generated by the real runtime call
        Object.keys(THEME) — ThemeKey itself never appears in the compiled output, not even as
        a string array.
      
    • 
      
  • 
        Resolution is structural, not name-based. keyof T
        doesn't look up a declaration by name; the compiler walks T's actual member list (however it was built — an
        interface, an inferred object literal, a mapped type) and unions the property keys it finds. That's why
        keyof typeof THEME works on a plain const with no interface in sight.
      
    • 
      
  • 
        Index signatures widen the union. keyof on a type with a
        [key: string]: V index signature includes string (and number, since
        numeric property access is stringified) in the key union — the compiler can't enumerate an open-ended
        signature's members, so it falls back to "any string/number key is valid."
      
    • 
      
  • 
        This is why "add a key, everything updates" actually holds. Because the union is recomputed
        from T's structure on every compile rather than cached from a prior declaration, there is no second place that
        can go stale — the const object is the type, one build behind.

Recap

    
Five things worth remembering.


    
    
      
  • 
        typeof value (type position) lifts a value/function into a type — pair with
        as const for precise literals and ReturnType<> for function results.
      
    • 
      
  • 
        keyof T = union of key names; the everyday combo is keyof typeof someConstObject.
      
    • 
      
  • 
        T[K] looks up member types; T[keyof T] = all value types; T[number] =
        array/tuple element type.
      
    • 
      
  • 
        <T, K extends keyof T>(obj: T, key: K) => T[K] is the canonical type-safe accessor — learn
        to read it as a sentence.
      
    • 
      
  • 
        The strategic win: one const object as source of truth, all unions derived — add a key once,
        everything updates, typos can't compile.
