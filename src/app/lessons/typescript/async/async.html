A Promise is a one-shot state machine for a value that doesn't exist yet: it starts pending, and settles exactly once — to fulfilled with a value or rejected with a reason — and never changes again. async/await is syntax laid over that machine, not a separate feature; every ordering surprise on this page, every dropped rejection, every accidental sequential loop is really the same machine misunderstood in a different spot. Get the machine right and the syntax stops being magic.

The problem

You can't have the value yet. What do you hold instead?

Call a function that hits the network, and the answer isn't there. Not slow — not there. Nothing in JavaScript can make your code wait for bytes that haven't arrived without freezing every tab in the browser, so the function has to return something, right now, before any real answer exists. Something has to stand in for the value before the value does.

That stand-in is the Promise. Not the answer — a receipt for an answer that's coming. Everything confusing on this page traces back to one of three questions about that receipt:

  • When does code waiting on the receipt actually get to run? (timing)
  • What happens if the receipt comes back saying no? (failure)
  • How do you hold several receipts at once? (combining)
Here's one to commit to before you scroll. You call an async function. It has exactly one await in it, partway through. What does the call itself return, immediately — before that await has settled? Say it out loud. There's a live demo a couple of sections down, and a predict-the-order puzzle right after it, that will hold you to the answer.

The mental model

A Promise is a claim ticket, not the coffee.

You hand over your order; the barista hands you a ticket. The ticket isn't the coffee — it's a promise (sorry) that one of two things will happen: the coffee shows up, or someone tells you they're out of beans. Either way, once that happens, it has settled — the ticket doesn't change again, no matter how many more times you wave it at the counter.

And here's the detail that trips people up later: the kitchen starts on your order the second you hand over your money — not when you first glance at the ticket. A Promise is eager in exactly that sense: its executor runs at construction, before anything has attached a .then() to it.

Pending → settles once → fulfilled or rejected, never both, never again. Every question about a Promise is really a question about which side of that arrow you're standing on.

Fulfilled

The executor called resolve(value). Every .then() attached to this promise — even one attached after it already settled — runs with that value.

Rejected

The executor called reject(reason), or threw. Every .catch() — or the nearest catch block around an await — runs with that reason instead.

The mechanism

Await doesn't wait. It suspends and schedules a comeback.

Start with the shape everyone already half-knows: an eager executor, a .then() chain, and the async/await spelling of the exact same thing.

Now the part that matters: what does the compiler turn await into? Nothing magical — a continuation scheduled on a microtask queue.

Put those two facts together and you get the single most useful sentence on this page: an async function runs synchronously up to its first await, then returns to its caller immediately — with a pending promise, not a value. Nothing blocks. The event loop keeps servicing everything else while that promise is out there.

Question 1 of 3 · timing

When does the paused code actually resume?

Every continuation — every resumed await, every .then() callback — is a microtask. Every timer, click and repaint is a macrotask. The rule that decides everything on this page: 

console.log('1: sync');
setTimeout(() => console.log('4: macrotask (timer)'));
Promise.resolve().then(() => console.log('3: microtask'));
console.log('2: sync');

After the current synchronous code finishes, the engine drains the entire microtask queue — every promise reaction, every suspended await continuation — before it takes even one macrotask. A microtask that queues another microtask keeps the drain going, which is exactly how an accidental infinite microtask loop starves rendering entirely — no error, no warning, just a page that stops painting.

Question 3 of 3 · combining

How do you run several of these at once?

Two ways to structure the same three tasks, and only one of them overlaps them:

// sequential (slow): the second await doesn't start until the first settles
const a = await taskA();  const b = await taskB();

// parallel (fast): start both promises first, THEN await
const [a2, b2] = await Promise.all([taskA(), taskB()]);

Sequential ≈ 3 × 400ms because each await parks the function until the previous task settles. Parallel ≈ 400ms because all three timers run concurrently — awaiting only joins the results.

await inside a for loop is the stealth version of the sequential case — same cost, much easier to write by accident. To parallelize, map to promises first: await Promise.all(items.map(fetchOne)), and note the promises start during the map, not during the all.

Four ways to combine them once they've started, and they disagree about failure on purpose:

Resolves with every value, in order. Rejects the instant any one input rejects — the other results still happen, but they're discarded. Resolves with one {status, value|reason} per input, always. Inspect each result yourself. Resolves or rejects with whichever input settles first — fulfillment or rejection, either one wins. Resolves with the first fulfillment. Rejects only if every input rejects, with an AggregateError.

The escape hatch

Or cancel one before it finishes at all.

None of the four combinators above actually stop anything — race only stops listening. AbortController is the real thing: a signal an async operation can check, and react to, while it's still in flight.

Two shortcuts worth knowing once you understand the manual version: AbortSignal.timeout(5000) hands you a signal that aborts itself after 5 seconds — no setTimeout of your own required — and AbortSignal.any([sig1, sig2]) combines several signals into one that aborts the moment any of them does, which is exactly how you'd wire "cancel on navigation OR on a 5-second timeout" together.

Pulling it together

One value, or many — and who's actually in control?

Three shapes for "a value that arrives later" now, not two. Angular's own HttpClient hands you an Observable; this page has been building a Promise by hand; and modern fetch responses can stream as an async iterable. Side by side:

Three ways to hold a value that isn't here yet
Promise Observable (RxJS) Async iterable (for await)
Values exactly one settlement zero, one, or many over time zero, one, or many, pulled one at a time
Eager / lazy eager (executor runs at construction) lazy (producer runs per subscribe) lazy (generator body runs only once iterated)
Cancellable no yes (unsubscribe tears down the producer) yes (break calls .return(), running cleanup)
Retryable no — settled is settled yes — resubscribe (retry) no — a consumed generator is done

Questions from the back row

Before you go

Five things to remember.

  • A promise is eager — the executor runs at construction — and settles exactly once. async functions always return a promise and run synchronously up to their first await, then suspend.
  • Await continuations are microtasks: the whole queue drains before any timer, click or paint gets a turn — and the order things were queued, not the order they appear in your file, decides who goes first.
  • Use return await inside a try/catch. A floating async call — forEach(async …), an un-awaited promise — is a bug magnet, not a shortcut. catch gives you unknown, always check before you touch it.
  • Start every promise before you await any of them. Promise.all is fail-fast, allSettled never rejects, race and any pick a winner — none of the four cancels a loser. AbortController is what actually can.
  • Observables are lazy, multi-valued, cancellable and retryable where Promises are none of those; async iterables add pull-based, one-at-a-time consumption. Bridge with firstValueFrom/from, and remember resource() and fetch-backed HttpClient both cancel through the exact AbortSignal you just used by hand.
