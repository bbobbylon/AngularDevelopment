Angular is class-based — components, services, directives and pipes are all classes underneath. Strip away TypeScript and what's left is JavaScript's prototype system in a suit: a constructor function, one shared set of methods, and per-instance fields. TypeScript layers private, abstract, parameter properties and this-typed returns on top of that — and every one of them is a promise checked at build time, except a single two-character prefix the engine itself enforces. Telling those two categories apart is this whole page.

The problem

You wrote private. The compiler forgot it existed.

Open the compiled JavaScript for any TypeScript class and go looking for private, protected, readonly, abstract, even an implements clause. You won't find them. Every access modifier, every abstract keyword, every interface name — gone, as if you never typed it. TypeScript's type system is a build-time-only layer bolted onto ordinary JavaScript, and a class is where that fact matters most, because a class is the one place TypeScript spends the most ink pretending otherwise.

So before anything else, the real question this page is about: which parts of a class are TypeScript being helpful, and which parts are the JavaScript engine actually enforcing something? Get that distinction wrong and you'll trust a private field to keep a secret, or panic about a readonly array TypeScript happily still lets you .push() into.

  • What does private actually stop, and what does it not?
  • Which keyword survives all the way to the running app?
  • And when does a class field quietly stop being a field at all?
You write class Vault {{ '{' }} private secret = 'shh'; {{ '}' }}, compile it, and open your browser's console on a running instance. Can you read v.secret? Say your answer out loud — a few sections down there's a compiled, running example of exactly this that will tell you if you were right.

The mental model

Every instance gets its own furniture. The building has one gym.

Picture an apartment building built from one blueprint. new Counter('clicks') doesn't hand you a copy of the blueprint — it hands you a fully furnished unit built from it. Your furniture (the fields — label, value) is yours alone; move it, and nobody else's apartment changes. But the building has exactly one gym in the basement (the methods, living on Counter.prototype), and every tenant walks down to use the same one. Nobody gets a private copy poured into their unit.

That single split explains almost everything confusing about classes: why two instances' methods are === to each other but their fields never are, why a method can be "stolen" by copying its reference — you're not copying a gym, you're copying a key to the one gym, and the key doesn't care whose door it's near — and why an arrow-function field is the deliberate exception: a private home gym installed inside your own unit, at your own expense, because you didn't trust the shared one to still recognize you once you'd left the building.

One prototype, many apartments. If a piece of state is different for every instance, it's a field. If it's the exact same code shared by every instance, it's on the prototype. An arrow field is the one thing that lives per-instance and is still a method — that combination is exactly what makes it survive detachment, at the cost of one extra function object per apartment.

Exam bait

Field initializers run before your constructor even starts.

That ordering rule turns genuinely dangerous the moment inheritance gets involved, because a base class's constructor runs to completion — including any method it calls — before the subclass has initialized a single one of its own fields.

The fixes, best first: don't call an overridable method from a constructor at all; pass what the base needs through super(...) instead; or give the class a genuinely lazy init method the subclass calls once construction is fully finished. Angular hands you exactly that as ngOnInit — "everything is wired now, including every subclass field."

Soft law vs hard law

Three privacies are the compiler's opinion. One is the engine's law.

Every access modifier, and what actually enforces it
Modifier What it means Enforced by
public The default. Accessible everywhere. Nothing — there's nothing to stop.
private Only inside the declaring class. The compiler, at build time only. Plainly visible in DevTools and via obj['value'].
protected The class and its subclasses. The compiler, same as private.
readonly Set once, then immutable — shallow. The compiler. A readonly array still lets you .push().
#name Hard, JS-native privacy. The engine itself. Truly inaccessible from outside the class, full stop.

There's a type-system consequence people miss: a private or # member makes its class nominal. Two classes with identical shapes are normally interchangeable — TypeScript is structurally typed — but a private member is only compatible with the exact same declaration, so class A {{ '{' }} private x = 1 {{ '}' }} and an identical class B are not assignable to each other. Teams exploit this deliberately for "branded" types that must never be mixed up.

Angular templates can only read public and protected members — hence this codebase's convention: template-facing state is protected, true internals are private. The template type-checker enforces it at build time, same as everything else on this row of the table.

Constructor sugar

A constructor parameter can declare a field just by being public.

Parameter properties are why classic Angular constructors read like dependency lists — every service the class needed showed up as private http: HttpClient, right there in the signature.

The field-initializer form with inject() wins on three fronts: it works inside field initializers themselves, so a field can depend on a service before the constructor even runs; it survives class inheritance without re-declaring constructor parameters; and it doesn't rely on parameter decorator metadata. One rule transfers to both forms though — each only works inside an injection context, meaning construction time. Call inject() later, from a click handler, and it throws.

Sharing behavior

super() must run before you touch this. That's physics, not opinion.

  • A subclass constructor must call super() before touching this — the base class builds the object first; that's engine law, not a TypeScript rule.
  • This project enables noImplicitOverride: overriding without the override keyword is an error, and — the direction people don't expect — writing override on a method that isn't overriding anything is equally an error. Rename or delete the base method and every stale override becomes a compile error instead of a silently forked implementation.
  • Prefer composition to deep hierarchies where you can: Angular itself moved from base-class patterns to composition — host directives, inject()-based helpers — for exactly the fragile-base-class reasons this section just walked through.

Methods get this from the call site — obj.m() binds obj; a bare m() binds nothing, in strict mode, which every file in this project compiles as. Arrow fields close over the instance once, at construction, and keep it forever. This is exactly why event-handler callbacks passed by reference historically needed .bind(this) — arrow fields are the modern fix, at the cost of one function per instance instead of one shared on the prototype.

Two more places this shows up as a type, both worth recognizing on sight. A this-typed parameter — function bindCheck(this: HTMLElement, e: Event) — types what this is supposed to be inside a plain function, so calling it detached, or with .call(wrongThing), is a compile error instead of a runtime surprise; it costs nothing at runtime, TypeScript strips it from the emitted signature entirely. And asserts this is Loaded puts an assertion function on the class itself, narrowing what this is for every line after the call — the class-level cousin of the asserts x is T functions the narrowing lesson covers for plain values.

A different this entirely

this in a return type isn't a value — it's a promise about the caller's own type.

This is a completely different this from the one above — not the runtime receiver, but a polymorphic return type meaning "whatever concrete type the caller actually was." It's what makes chainable APIs survive being subclassed.

Two ways to share a shape

abstract builds something. implements only checks the shape.

  • extends inherits implementation — one base maximum. implements only checks shape — many allowed, zero runtime trace. Lifecycle hooks are the everyday example: implements OnInit makes the compiler verify ngOnInit() exists, but Angular calls the hook by name either way, with or without the implements clause.
  • Abstract classes survive to runtime as real constructors, which is why Angular DI can use one as a token: {{ '{' }} provide: Logger, useClass: ConsoleLogger {{ '}' }} with abstract class Logger. An interface could never be the token — it's erased.
implements gives a member no contextual typing. The compiler checks that your class HAS a matching method; it never flows the interface's parameter types INTO that method's body for you.

The duality

The word User means two different things depending on where you write it.

User the type means "an instance"; typeof User means "the constructor." The new () => T shape is how factories and DI providers get typed — Angular's own useClass accepts exactly a constructor type, nothing narrower and nothing looser.

Questions from the back row

Before you go

Six things to remember.

  • A class is two runtime things, not one: fields land per-instance, methods land once on the prototype — every quirk about this, sharing, and detachment follows from that split.
  • Access modifiers are a compiler opinion, not an engine rule — private/protected/readonly vanish at compile time; only #private is enforced by the JavaScript engine itself.
  • Field initializers run base-first, top to bottom, before any constructor body — including the base's own. Calling an overridable method from a constructor reads the subclass's fields one beat too early.
  • strictPropertyInitialization and useDefineForClassFields are two separate traps around the same keyword — declare fixes both: it tells the compiler "something else owns this slot," and emits nothing.
  • override guards both directions once noImplicitOverride is on: forget it on a real override, or add it to a method that isn't one, and the build catches it either way.
  • this shows up as three different things — the runtime value a method receives (lost on detachment, kept by arrow fields), a return type meaning "whatever the caller's own type was" (: this, for chainable APIs), and an assertion target (asserts this is T). Keep them straight, and remember a class is a type and a value at once — User describes an instance, typeof User is the constructor.
Everything with a keyword in front of it disappears at compile time — private, protected, readonly, abstract, implements, interface, even this as a return type — except one two-character prefix: #. That's the entire difference between a promise and a lock.
