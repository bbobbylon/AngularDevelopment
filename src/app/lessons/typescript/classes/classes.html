Angular is class-based — components, services, directives and pipes are all classes. Under the hood a class is still JavaScript's prototype system in formal dress: the class is a constructor function, methods live once on the prototype, and fields are per-instance. TypeScript layers access modifiers, parameter properties and abstract members on top of that — nearly all of it erased at runtime. Knowing which parts are real and which are compiler fiction is the whole page.

The problem

You wrote private. Open DevTools anyway.

Mark a field private and TypeScript keeps its word — reach for it from outside the class anywhere in your own code and the compiler stops you cold, red squiggle and all. It certainly feels like a lock. So here's the uncomfortable question: open your browser's dev console on a running Angular app, find any instance of that class, and type its name. The value is right there. No error, no resistance — as if the word private was never written at all. Was that a TypeScript bug, or is it working exactly as designed?

The mental model

A sign says don't. A lock says can't.

Think of private as a "staff only" sign on an unlocked door. It works great as long as everyone reading it cooperates — which is exactly what the TypeScript compiler does: it checks every door in your own source code and refuses to build if a sign is ignored. But it is still just a sign. Once you're past the compiler — plain compiled JavaScript, DevTools, a stray as any — nothing physically stops you walking through, because by then the sign has already been taken down.

#hard is a locked door with a keycard reader. The lock isn't a social convention a well-behaved caller respects — it's a mechanism the building itself, the JavaScript engine, enforces. There is no cast, no trick, no console command that opens it from outside the class body. That's the difference between type-checked and actually private, and the rest of this page is really one long elaboration of it.

A sign says "don't." A lock says "can't." private is the sign — TypeScript-only, gone by the time your code runs. #hard is the lock — real JavaScript, enforced by the engine that runs it.

The mechanism

Every field initializer runs before your constructor even starts.

That order — fields, then constructor body — is fixed and is exam bait. In a subclass, it gets one layer deeper: the base's fields and constructor finish completely before the subclass's own fields are touched at all.

Never call an overridable method from a constructor. The call can dispatch into a subclass override whose own fields haven't initialized yet — see the predict below for exactly how that goes wrong.

The vocabulary

Five keywords, one real lock.

public Default. Accessible everywhere.
private Only inside the declaring class — compile-time only; the property is plainly visible in the emitted JS, in DevTools, and via obj['value'].
protected The class and its subclasses.
readonly Set once (declaration or constructor), then immutable — compile-time, shallow.
#name JS-native hard private — enforced by the engine. Truly inaccessible outside the class; survives compilation because it IS JavaScript.

A subtle type-system consequence: private/# members make a class nominal. Two classes with identical shapes are normally interchangeable — that's structural typing — but a private member is only compatible with the same declaration, so two otherwise identical classes each with their own private x = 1 are not assignable to each other. Teams exploit this deliberately for "branded" types that must not be mixed up.

Angular templates can only read public and protected members — hence the convention in this codebase: template-facing state is protected, true internals are private. The template type-checker enforces it at build time.

In practice

Parameter properties — and the inject() shift.

Parameter properties are why classic Angular constructors looked like dependency lists. The field-initializer form with inject() wins on three fronts: it works inside field initializers themselves (so a field can depend on a service), it survives class inheritance without re-declaring constructor params, and it doesn't rely on parameter decorator metadata. One rule transfers either way: both forms only work in an injection context — construction time. Calling inject() later, say inside a click handler, throws.

Inheritance

super, override, and noImplicitOverride.

  • A subclass constructor must call super() before touching this — the base class builds the object first; that's engine law, not a TS rule.
  • This project enables noImplicitOverride: overriding without the override keyword is an error. The payoff is the reverse direction — if the base method is renamed or removed, every stale override becomes a compile error instead of silently forking behavior.
  • Prefer composition to deep hierarchies: Angular itself moved from base-class patterns to composition (host directives, inject()-based helpers) for exactly the fragile-base-class reasons.

Methods get this from the call site (obj.m() binds obj; bare m() binds undefined in strict mode). Arrow fields close over the instance instead. This is why event-handler callbacks passed by reference historically needed .bind(this) — arrow fields are the modern fix, at the cost of one function per instance.

Contracts

extends brings code. implements only checks shape.

  • extends inherits implementation (one base max); implements only checks shape (many allowed, zero runtime effect). Lifecycle hooks are the everyday example: implements OnInit makes the compiler verify ngOnInit() exists — but Angular calls the hook by name either way, interface or not.
  • Abstract classes survive to runtime — they're real constructor functions — which is why Angular DI can use one as a token: { provide: Logger, useClass: ConsoleLogger } against abstract class Logger. An interface could never be the token; it's erased.

One more wrinkle

A class name means two different things.

class User {{ '{' }} name = ''; {{ '}' }}

const u: User = new User();      // type position: the INSTANCE shape
const ctor: typeof User = User;  // value position: the constructor itself
function make(C: new () => User) {{ '{' }} return new C(); {{ '}' }}  // constructor type

User the type means "an instance"; typeof User means "the constructor." The new () => T form is how factories and DI providers are typed — Angular's useClass accepts exactly a constructor type.

Questions from the back row

Before you go

Recap — five things to remember.

  • Classes are constructor functions + prototypes; field initializers run before the constructor body, base before derived — never call overridables from constructors.
  • private/protected/readonly are compile-time (soft, the sign); #name is engine-enforced (hard, the lock). Any private member makes the class nominally typed.
  • Parameter properties power classic constructor DI; inject() in field initializers is the modern form — both need an injection context.
  • override + noImplicitOverride guards both directions of rename drift; methods lose this when detached, arrow fields don't.
  • abstract = contract + shared code + runtime constructor (hence usable as a DI token); implements = erased shape check. A class name is an instance type; typeof C is the constructor.
