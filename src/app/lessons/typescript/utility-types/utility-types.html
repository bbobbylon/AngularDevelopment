TypeScript ships built-in generic types that transform one shape into another — pure compile-time, zero emitted JavaScript. The promise is one source of truth: change User once and every type derived from it follows. This page spends most of its time on where that promise quietly breaks — keyof over a union, an overloaded function, a dictionary that lies about which keys exist — because that is exactly the material an exam, and a code reviewer, actually tests.

The problem

One interface, four copies — and only one of them is still telling the truth.

Here's a shape everyone writes eventually: interface User {{ '{' }} id: number; name: string; email: string {{ '}' }}. And here's what happens next, in almost every codebase: a form needs a version where every field is optional, an API patch needs the same thing with id pinned, a summary view needs just two of the three fields, and a lookup table needs one entry per role. Four new shapes, and the fast way to get them is to retype User by hand, four times, with small changes.

That's the trap. User gains a fifth field eight months from now, and nothing forces the four hand-written copies to notice. Three of them still compile — they were valid object types the moment you wrote them — and they quietly drift out of sync with the interface they were supposed to describe. No error, no warning. Just a form that's missing a field nobody remembered to add back.

So the actual problem was never "how do I write four extra types". It's:

  • How do you derive a variant from User instead of retyping it?
  • What happens to that variant the moment User changes?
  • And which of TypeScript's built-ins does that job for you, for free, at compile time only?
You hand-write type Patch = {{ '{' }} id?: number; name?: string; email?: string {{ '}' }} next to interface User {{ '{' }} id: number; name: string; email: string {{ '}' }}. Next sprint someone adds role: string to User. Does Patch gain a role? field too — and if you think "no", where exactly does that leave the code that reads Patch?

The mental model

TypeScript's utility types are stamps, not photocopies.

Picture User as a signed master document kept in exactly one folder. Every time you need a variant, you don't retype the document from memory — you press a rubber stamp onto a fresh copy of it. Partial stamps every field "OPTIONAL". Required stamps every field "MANDATORY". Readonly stamps the whole page "DO NOT EDIT". Pick stamps out everything except the clauses you named. Every stamp reads the master document at the moment you press it — so if the master changes, the next copy you stamp changes with it.

Retype the document by hand instead — which is exactly what four hand-written interfaces are — and you've made a photocopy on someone else's photocopier: correct the moment you made it, and invisible to every future change to the original.

Every utility type reads one interface; none of them duplicate it. The moment you retype a shape by hand instead of deriving it, you've reintroduced the exact bug these exist to prevent.

Two consequences of these definitions are worth internalising. Homomorphic mapping preserves modifiers — because Partial/Pick/Readonly map directly over keyof T, an existing readonly or ? on T carries straight through, so Pick<T, K> keeps a readonly member readonly. Record maps over an arbitrary key union instead of over keyof T, so it preserves nothing — there's no T to preserve anything from.

And Pick validates its keys; Omit doesn't. Look at the constraints again: Pick's K extends keyof T rejects Pick<User, 'emial'> at the call; Omit's K extends keyof any accepts any key at all, real or not. Omit<User, 'emial'> compiles happily and removes nothing — a typo in an Omit is a silent no-op, not a build failure.

All six of these are shallow — one level deep. Readonly<State> lets you mutate state.user.name freely. Deep variants are recursive mapped types you write yourself (or take from a library) — the mapped-conditional lesson builds one. And one more wrinkle worth knowing: with exactOptionalPropertyTypes off, {{ '{' }} a?: string {{ '}' }} treats "missing" and "explicitly set to undefined" as the same thing; turn it on and a Partial<User> patch that assigns {{ '{' }} name: undefined {{ '}' }} to deliberately clear a field becomes a typed action instead of a silent no-op.

The trap

But keyof doesn't know what a union is.

Everything so far has been about one object type. Real Angular state is rarely that — it's a discriminated union, the shape the narrowing lesson spends a whole page on: one shared literal-tagged field, several arms, each carrying different extra data. Reach for Pick or Omit on a shape like that and something breaks that nothing in the last section warned you about.

 Pick/Omit read keyof T as one flat, intersected set of keys. Apply either straight to a union and you get one flattened object, not per-arm results — distribute first (T extends unknown ? Omit<T,K> : never) whenever T might be a union.

The other family

A conditional type takes the union apart on its own.

Exclude, Extract and NonNullable also filter a union — and they don't have the problem you just saw at all. Same word, "union", completely different mechanism underneath.

Each member of the union is run through the conditional independently and the results are unioned back — never members simply vanish. That per-member "distribution" is the engine behind every union filter, and it's the reason these helpers do nothing useful on a non-union type: there's only one member to distribute over.

Extractor 1 of 3 · the basics

Function types get their own extractors.

A second job entirely: not filtering a union, but reading a piece back out of a function or a promise you already declared. These are conditional types using infer — the compiler pattern-matches the shape you gave it and captures one piece.

What a function hands back. Blind to overloads except the last one declared — next section. Every argument, as a labelled tuple. Shares the same last-overload rule as ReturnType — same infer mechanism underneath. Parameters' sibling for new X(...) instead of X(...). Takes typeof on a class, not an instance. What new X() actually produces. Reads a constructor's return position the way ReturnType reads a function's. Unwraps one Promise, or several stacked ones, down to the value underneath. The one extractor here that recurses — next section but one.

Extractor 2 of 3 · the exam trap

ReturnType only ever sees ONE of your overloads.

Real functions in a library you didn't write are often overloaded — Router.createUrlTree, FormBuilder.group, plenty of the DOM's own APIs. Ask an extractor about one of them and it doesn't average the overloads, and it doesn't pick the one you'd expect.

Order your overloads with this in mind. If a type-level query like ReturnType ever needs to see a specific overload, put it last — or, better, don't rely on the order at all and name the return type explicitly instead of deriving it from an overloaded declaration.

Extractor 3 of 3 · recursion

Awaited doesn't stop at the first wrapper.

Every other extractor on this page reads one layer and stops. Awaited is the exception — it models what await actually does to a chain of nested thenables, which is also the type Promise.all uses for its own results.

The lying dictionary

Record<string, V> makes a promise it can't keep.

Record<Role, string> from earlier works because Role is a closed, finite union — every member has to show up, or the assignment itself fails to compile. Swap the finite union for plain string and you get the shape most people reach for by default, and it makes a promise TypeScript can't actually keep: that every string is a valid key.

Questions from the back row

Before you go

Six things to remember.

  • Every utility type reads one interface and produces a new one — nothing is duplicated, so nothing can silently drift, because there is only ever one copy of the wording.
  • -? on Required strips both the ? and any | undefined on the property. Turn on exactOptionalPropertyTypes if you need "missing" and "present but undefined" to mean different things.
  • Pick/Omit read keyof T as one flat, intersected set. Apply either directly to a union and you get one flattened object, not per-arm results — distribute first.
  • Exclude/Extract/NonNullable distribute automatically, because they're bare conditionals over a naked type parameter. Pick/Omit wrap T inside a mapped type, so they never do — same-looking T, opposite behaviour.
  • ReturnType/Parameters on an overloaded function see only the last declared signature, whether or not that's the one most callers use.
  • Record<string, V> type-checks every read and lies about it — turn on noUncheckedIndexedAccess (or reach for a Map) so a missing key is V | undefined instead of a runtime crash.
