Both interface and type describe the shape of data, and both vanish before your code ships — pure compiler-facing paperwork. What actually decides whether a value "is" a User is not a keyword you wrote anywhere on the object; it is whether the object's fields match. That one fact — structural typing — explains almost everything on this page: why you never write implements on a plain object, why an object can satisfy an interface it has never heard of, and why exactly one situation gets checked more strictly than everything else.

The mental model

TypeScript reads a resume like a hiring checklist, not a bouncer checking an ID.

You've probably heard "if it walks like a duck and quacks like a duck…" — and most explanations stop right there, which is a shame, because it skips the actual mechanism. Here's the fuller picture. Picture a hiring manager holding a checklist for a role: must know TypeScript, must have two years of experience, must be able to start Monday. The manager reads every resume that arrives and asks exactly one question of each: does this resume tick every box on the checklist? They do not care whose letterhead the resume is printed on. They do not care whether the applicant ever filled in a form declaring "I hereby apply as a checklist-satisfier." If the boxes are ticked, the application passes — even if the applicant has no idea the checklist exists.

That's structural typing, and here is the mechanism it actually runs, precisely: TypeScript does not check the name of a type at all — it checks the shape. Give it an interface and an object, and it walks the interface's members one at a time, asking "does the object have a property with this name, and is that property's type compatible?" Every required member has to tick; optional members are allowed to be missing; and — this is the part most explanations skip — the object is allowed to have more properties than the interface asks for. A resume with extra qualifications the job never listed isn't disqualified for over-delivering. There is exactly one exception to that generosity, and it has its own name and its own reason to exist — it gets a full section below, because it's one of the most-tested gotchas on this whole topic.

Shape, not name. TypeScript never asks what a value calls itself — no implements, no shared ancestor, not even the same file. It asks only: does this value have every property the interface lists, with a compatible type in each? Tick every box and you're in, no matter whose resume it's printed on.

Two philosophies

Java asks who you are. TypeScript asks what you have.

Most mainstream languages with interfaces are nominal: satisfying Point requires a class to say so, in writing, with implements — and the compiler checks that declaration, not the class's members. The narrower rule

One case gets checked harder: a fresh literal.

There is one place TypeScript does look for extra fields, and it earns its own paragraph because it trips up almost everyone once. The moment an object literal is written directly where a typed location expects a shape, TypeScript runs a second, stricter pass called the excess property check. This is not structural typing being violated — it is an extra safety net bolted on top of it, for one narrow, sensible reason: a key that appears out of nowhere on a freshly-written literal is almost always a typo (retrys instead of retries), and plain structural typing would wave it straight through, because it never demanded an exact match in the first place. The check applies only to a literal written in that exact spot — a variable, a function's return value, anything one step removed loses the extra scrutiny, because by then TypeScript is comparing two already-known types instead of proofreading a fill-in-the-blank form.

Only a freshly-written object literal gets the excess-property check. The instant that value has a binding of its own — even one line earlier, even trivially — TypeScript stops looking for stowaways and falls back to ordinary structural comparison.

Building bigger shapes

    
extends and & agree — until a member conflicts.


    

    

      Both express "this, plus more," and they agree right up until a property conflicts — then they diverge sharply.
      extends checks compatibility at the declaration: redeclare a member as an
      incompatible type and the interface itself refuses to compile, right there, naming the exact property. An
      intersection with the same conflict doesn't complain about the type at all — it quietly computes an impossible
      member (string & number collapses to never), and the failure only surfaces
      later, at whatever line actually tries to build one, pointing at a spot far from the
      real cause. extends fails early and clearly; intersection fails late and cryptically.

      The same mechanism lets libraries accept plugin-added fields (Express's Request, i18n key tables,

      type can't do it: aliases are bindings, and re-binding a name is an error; interfaces are
      declarations, and declarations accumulate.

Before you go

    
Six things to remember.


    
    
      
  • 
        Satisfying an interface is about shape, never about declaring implements or
        sharing a name — TypeScript checks structurally, every time, with no declaration required.
      
    • 
      
  • 
        More properties than required is fine through a variable; a fresh object literal gets the
        stricter excess-property check, because an unrecognised key there is almost always a typo.
      
    • 
      
  • 
        extends fails early, at the interface itself, on a conflicting member. The
        intersection equivalent (&) fails late, producing a never
        member that only breaks wherever you try to build one.
      
    • 
      
  • 
        Only interface gets declaration merging — re-declaring the same name adds to it
        rather than erroring, the sanctioned way to augment types you don't own. Do the same with type and
        you get TS2300: Duplicate identifier.
      
    • 
      
  • 
        An interface can be more than an object shape — callable, indexed, generic, or a hybrid of several — but it can
        never carry a method body. The moment you need shared executable code, reach for a class.
      
    • 
      
  • 
        Interfaces are erased before the JavaScript ships, which is the one fact behind three separate surprises: no
        instanceof on them, Angular DI needs classes or InjectionTokens for them, and a
        runtime check needs a discriminant or a type guard instead.
