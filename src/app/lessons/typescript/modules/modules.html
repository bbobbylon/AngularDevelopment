Every .ts file with at least one import or export is an ES module — and that single fact rewrites the rules of the file: everything inside starts private, reachable elsewhere only if you deliberately hand it out. Imports and exports aren't just a language mechanic, either — they're the raw graph Angular's build reads to decide what to tree-shake and what to lazy-load. This page takes the whole system in the order that actually explains it: why scope needed fixing, the mental model that makes "private by default" click, and then everything built on top of it — export forms, resolution, barrels, import type, dynamic import(), and the one property every module has whether you asked for it or not. (Heads up: ES modules are not Angular's legacy NgModule — the same word describing two unrelated things; more on that in the FAQ.)

The problem

Two files, one shared scope — and a collision.

Here's something most tutorials skip straight past: before modules existed, every <script> tag loaded onto a page ran in the exact same, single global scope. Declare a variable in one file and a second file with the same name doesn't get its own copy — it gets the same slot, and depending on how the two collide, you get a hard crash or a silent overwrite with no warning either way.

That collision is the entire reason modules exist, and the fix turns out to be almost embarrassingly simple: give every file its own private scope by default, and require one explicit keyword — export — for anything a file wants to hand outside itself.

Two plain <script> tags on the same page each declare let helper = 5;. Two separate module .ts files each do the exact same thing. One of those setups throws a duplicate-declaration error the instant the page loads. The other runs forever, side by side, with nobody noticing a thing. Which is which — and why?

The mental model

A module file is a shop with one window.

The two <script> tags crash — a duplicate let in one shared global scope is a hard syntax collision, caught the moment the second file parses. The two module files run fine, forever: each .ts file gets its own private scope, so helper in one has nothing whatsoever to do with helper in the other. That one sentence — every module file is private by default — is the entire reason the collision above stops being possible.

Picture a module file as a shop. There's a back room full of stock — every const, every helper function, every bit of working state — and none of it is visible from the street. The only things the public can reach are the items you deliberately put in the window, and export is the act of putting something there.

That's more than a metaphor for privacy — it's a promise about refactoring. Anything not in the window is yours to rename, restructure or delete, because nobody outside could ever have depended on it. Keep that promise in mind; it's what makes the barrel problem later on this page feel inevitable rather than surprising.

export is the only door out. Everything else in a module file is back-room stock — private by default, and safe to change.

How a module actually turns into values.

The sharp edge

Re-exports and barrels — convenient, until they're not.

A barrel is one file — usually index.ts — that re-exports a whole folder's public surface, so consumers get one tidy import instead of three:

Somewhere below, one of these files imports its own barrel — the very file that is supposed to be collecting exports from it. Before you scroll: does that even run? And if it does, what actually breaks?
How barrels go wrong — the actual mechanism. Modules load once, in dependency order. If a.ts imports the barrel, and the barrel lists b.ts, and b.ts imports something from the barrel again, you have a cycle: one of the files executes while the other is only partially initialized, and you get the infamous "Cannot access 'X' before initialization" at runtime — often only in production builds where module order differs. Rules of thumb: a folder's own files never import their own barrel; hot paths import specific files; keep barrels for genuinely public package surfaces.

Erased by design

Type-only imports — gone before the browser ever sees them.

Why a keyword for this at all? Because this project — like most modern ones — compiles with isolatedModules, where each file is transpiled alone. The compiler can't peek into ./user to check whether User is a type it should erase or a value it must keep, so you tell it, locally, with type.

The bonus is real, not academic: an erased import creates no runtime dependency edge at all, which can dissolve a circular-import crash exactly like the one above, when the cycle was only ever about types.

The engine of lazy loading

Everything so far has been a declaration: written at the top of a file, resolved before anything runs. Dynamic import() breaks that rule on purpose — it's an ordinary expression, and that single change is the entire mechanism behind Angular's lazy loading.

One property every module shares

Module state is a singleton, whether you asked for it or not.

Step 3 of the loading sequence above said it plainly: top-level code runs once. That single fact makes module scope a natural singleton — a genuine tool when used deliberately, and invisible coupling when it isn't.

The other module system

Every real app eventually installs a package that isn't ESM at all.

Everything so far has been ESM — the module system TypeScript and Angular write. The npm ecosystem is still full of CommonJS — Node's original system, built on require() and module.exports instead of import/export. A CommonJS module exports exactly one value; it has no concept of "default" at all.

Import a CommonJS package the ESM way and you hit a shape mismatch: import moment from 'moment' asks for a default export that module.exports = momentFn never actually created. esModuleInterop — on by default in every Angular project — is the compiler flag that papers over this by synthesizing the wrapper for you.

The Angular-specific remedy. A CommonJS dependency also defeats tree-shaking — the bundler can't statically prove which of its exports go unused, because module.exports is just an ordinary object built at runtime, not a set of named bindings the compiler can see. The CLI knows this and warns you the moment one lands in your dependency graph:

allowedCommonJsDependencies in angular.json doesn't fix the tree-shaking gap — it just tells the CLI you know about this specific package and don't need the warning repeated. Every real Angular app eventually hits one of two failures from this: X is not a function / default is not a callable at runtime when the interop guess is wrong, or this build-time warning when it isn't.

Pulling it together

Six import forms, one rule for choosing.

every import form this page covered, and when it actually earns its place
Form Written as Reach for it when…
Named import {{ '{' }} x {{ '}' }} from './m' Almost always. Refactor-safe, auto-importable, tree-shakeable.
Default import x from './m' An Angular lazy route accepting a component's default export directly.
Namespace import * as ns from './m' A genuine grab-bag of helpers where a shared prefix reads well.
Side-effect import './m' A polyfill or registration that must run once, with nothing to bind.
Type-only import type {{ '{' }} X {{ '}' }} from './m' isolatedModules demands it, or a cycle is only about types.
Dynamic await import('./m') Code you want split into its own chunk, fetched only when needed.

Questions from the back row

Before you go

Six things to remember.

  • A module is a file-private scope; the export list is the public API. Everything unexported is refactor-safe implementation detail.
  • Six import forms, one house style: named almost always, default for the lazy-route niche, namespace for a genuine grab-bag, side-effect when nothing needs binding, and type-only the moment isolatedModules asks for it.
  • Paths resolve three ways: relative (./), bare (node_modules), aliased (tsconfig paths).
  • Barrels tidy imports but enable cycles — "cannot access X before initialization" means a circular import; never import your own barrel from inside the folder it describes.
  • import() is an expression, not a declaration — it returns a promise and triggers code-splitting, which is literally how Angular lazy loading works.
  • Module top-level code runs exactly once. Every later import is a cache hit, which makes module state a shared singleton — genuinely useful on purpose, dangerous by accident.
