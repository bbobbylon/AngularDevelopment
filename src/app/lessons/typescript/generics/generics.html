A generic is a promise, not a mystery: hand a function or a class a value of some type, and it hands you back something built from that exact type — never a looser one it made up along the way. T is a variable, but it lives in type space, and — the part almost everyone misses — you almost never fill it in yourself. TypeScript reads it straight off your arguments. Every <T> threaded through Angular — signal<T>, Observable<T>, FormControl<T>, HttpClient.get<T> — is running on exactly the rules this lesson covers, plus the one trap that looks identical to safety and isn't.

The problem

any works. It also stops checking anything.

Say you want a function that hands back exactly what was passed in — a pass-through, an identity. The obvious first attempt reaches for any, and it compiles, and it runs, and it quietly throws away every reason you were using TypeScript in the first place.

Three ways to write "give me back whatever I handed you": one function per type, one function typed (value: any): any, and one function typed <T>(value: T): T. Only one of the three lets identity(42).toFixed(2) compile AND catches identity(42).toUpperCase() as an error. Decide which before you scroll — the panel right below settles it.

T is solved from the argument, and the return type is T too — so whatever went in comes back out with its exact type intact, not any, not a widened guess.

That is the entire subject of this lesson: how a T gets solved, what buys you the right to touch what is inside it, and the one place a label gets printed on a box the compiler never actually checked.

The mental model

A generic is a label on a box, not a peek inside.

Think of a generic as a labelled shipping box. A courier moving boxes around never needs to open one — they only need to read the label and make sure a box's contents never get swapped for something else's. Box<T> works exactly like that courier: it can hold any T you hand it, move it, wrap it in a bigger box, hand it straight back — all without ever caring what is actually inside. The moment it needs to open the box and use a specific capability — call .bark(), read .id — it needs a constraint: proof, in writing, of what the label guarantees.

A generic doesn't look inside the box. It reads the label once — infers T from what you handed it — and every promise it makes afterwards is built from that exact T, never a looser one it invented.

That is the whole subject laid out in order: how the label gets read (inference, next), what buys you the right to open the box (constraints), and the one place a label is printed on a box nobody actually checked (the cast trap).

How it actually gets solved

T is solved from your arguments — almost never from what you type.

Reach for <T> explicitly and most of the time TypeScript already found the same answer without you. Inference is the compiler reading your call site and working backward to a type parameter, and it follows a small, learnable set of rules.

One more rule worth knowing by name: context flows backward too. In const f: (x: number) => void = x => …, the lambda's parameter is inferred from the target type it is being assigned to — which is why a callback inside .map() or .subscribe() never needs its own annotation.

One more inference trap: a second argument can silently widen the first.

Sometimes T has more than one candidate site, and every site gets to vote — including one you only meant as a fallback. TypeScript 5.4 added NoInfer<T> specifically to opt a parameter out of that vote.

Generic classes

A class fixes T once. Its methods can each open a new one.

Two parameters cooperate in a generic class, and mixing them up is the single most common confusion in this section: the class's own T is fixed the moment an instance is created, while a method can introduce a second, independent parameter that is solved fresh on every call.

This is precisely the shape RxJS runs on: an Observable<T> whose pipe(map(fn)) produces an Observable<U>, with every operator in the chain a link that transforms the type parameter the same way .map does here.

Constraints with extends

Without extends, T has no members at all.

An unconstrained T could be anything, so you cannot touch a single one of its properties — the constraint is what buys you that capability, and it is worth internalising as a trade: you promise the compiler T has at least this much, and in exchange you get to use it.

Tying one parameter to another: K extends keyof T.

K extends keyof T is the most important constraint idiom in the language — the typed foundation under form builders, table column configs, pluck-style helpers, and state selectors.

The trap

A type parameter used once is a cast wearing a costume.

Every generic so far has had T pulling weight in two places — a parameter and the return, or two parameters. Here is what happens when it only shows up in one.

A type parameter earns its keep by appearing in two positions — two parameters, or a parameter and the return. Show up once, especially return-only, and it isn't inference doing the work. It's you, asserting.

Angular's http.get<User>(url) is this exact same honest lie: a convenient assertion about the wire format, not a validation. That is fine as long as you know it — and it is why schema validators (zod, valibot) exist for boundaries you do not fully trust.

Erasure meets DI

T doesn't survive to runtime, and neither does your injector's patience for it.

Every generic in this lesson compiles to plain JavaScript with no trace of <T> left in it. That is invisible right up until you try to use T to pick a dependency — because Angular's injector matches providers by the identity of a runtime value, and there is no runtime value called T.

The sharper trap isn't a compile error — it's a silent collision. Register two providers for the bare Repo token hoping for a different T each and the second registration wins; the first is simply gone, with no warning from either the compiler or Angular at runtime.

Variance

Box<Dog> and Box<Animal> aren't interchangeable in both directions.

Everything generic in this lesson has been safe to substitute so far — but substitution has a direction, and getting it backwards is a standard interview trap.

Box<Dog> — assignable to Box<Animal>? Now flip it: is Box<Animal> assignable to Box<Dog>? They cannot both be yes. Decide before you scroll — the panel below settles it in both directions, and whichever one you got wrong is the one worth remembering. 
{{ covariantSample }}

value: T only ever hands T out. A box that produces a Dog can safely stand in for a box that produces an Animal — every Dog already is one. 

{{ contravariantSample }}

accept(v: T) only ever takes T in. Something that can accept any Animal can certainly accept a Dog — the direction flips because the position flipped.

Both of those hold at runtime, not just at compile time. Arrays are the one place TypeScript knowingly lets an unsound version of the covariant rule through.

Reach for readonly Animal[] whenever a function only reads its array parameter. The compiler then refuses even a .push on the alias, not just on the line where you happened to notice — turning this exact unsoundness back into a compile error at the one place you can actually fix it.

Saying the variance out loud: in and out (TypeScript 4.7+).

Nobody writes in/out on a lesson-sized interface — structural inference already gets Box and Sink right without them. They earn their keep in large generic libraries, where a deeply nested relationship is either too slow for the compiler to work out from scratch or genuinely ambiguous — and unlike a comment, the annotation below is checked, not just documentation.

Interfaces, aliases, defaults

A generic type can default itself, the same way a parameter can.

The default is unknown, not any, on purpose. Defaulting to any would silently switch off checking for everyone who forgot the type argument; defaulting to unknown makes forgetting safe — every reader still has to narrow before touching the value.

Where generics actually show up

You mostly consume these generics. That's the point.

Most of the payoff in application code is not writing your own generics — it is reading the ones Angular already wrote correctly, precisely.

Usually inferred — signal(0) is already WritableSignal<number>. Annotate only when the initial value doesn't pin down what you want, e.g. signal<User | null>(null). The payload type for a custom event: saved = output<User>() makes every (saved)="onSave($event)" listener's $event a real User, not any. new FormControl<string>('') makes .value a real string everywhere it is read — no more any leaking out of a form. A generic that survives the erasure problem two sections up, because you write the <T> once, at the token's declaration, instead of hoping it infers through an erased class. The return-only generic from the cast-trap section, doing exactly what it does there: compile-time typed, runtime unverified. The query's result type — until the view exists it is undefined, so the signal it returns is really Signal<ElementRef | undefined>.

One more thing

Not everything needs a <T>.

Don't over-genericize. If a type parameter appears only once, replace it with a plain type — or recognise you have written a cast and say so. If a function never actually relies on what T is, unknown often serves better. Generic gymnastics in application code is usually a smell — the standard library and the framework already did the hard generics; your job is mostly good constraints on small helpers.

Questions from the back row

Before you go

Six things to remember.

  • T is solved from your arguments, with a best-common-supertype fold across multiple candidates; a literal widens unless pinned by as const, a const type param, or a literal-leaning constraint — and NoInfer<T> can remove a parameter from the vote entirely.
  • Constraints buy member access, and K extends keyof T plus T[K] is the idiom under typed property access, selectors and form helpers everywhere.
  • A generic preserves the caller's own type through your code. A parameter used only once — especially return-only, like http.get<T> — is a compile-time assertion, not safety, and the same erasure is why you cannot inject a generic service type directly.
  • Substitution has a direction. Box<Dog> → Box<Animal> is safe because T only comes out; a function accepting Animal standing in for one accepting Dog is safe because T only goes in. Arrays let the write-side version through unsoundly — readonly T[] closes that hole.
  • Default type params to unknown, never any; a class fixes T once per instance while its methods can each introduce a fresh one — the RxJS shape.
  • Angular's signals, outputs, typed forms, tokens and HTTP are all generic — consume them precisely before reaching to invent your own.
