TypeScript erases almost everything you write for it — interfaces, generics, type aliases, all gone by the time your code ships. A regular enum is the one exception, and that single fact is the spine of this whole lesson: what a numeric enum actually costs you at runtime, why a string enum refuses a value that is its own runtime type, why const enum needs a warning label, and why most modern code reaches for a literal union instead. Every claim below comes with the compiled output to prove it — not just assert it.

The problem

You need a fixed set of named values. JavaScript has no keyword for that.

No enum, no closed set of options, nothing built in. So people reach for what's available — a handful of magic strings ('LOADING', typo-prone and untyped), or a plain object nobody stops you from mutating. TypeScript gives you real answers: enums, in two flavours, plus a literal union that mostly makes the enum question moot. They are not interchangeable, and the surprise that explains every difference between them is this one fact:

Nearly every piece of syntax TypeScript adds to JavaScript — types, interfaces, generics, the as keyword — is erased completely before your code ever reaches a browser. It exists only to be checked, then thrown away. A regular enum is the one construct that breaks that promise.

The mental model

TypeScript erases itself — except this once.

Think of everything you annotate — : string, interface User, <T> — as a sticky note on a manuscript. Useful while you're editing, checked carefully, and then peeled off before the page goes to print. The reader of the printed page never sees a single one. That's the whole deal TypeScript makes with you: annotate freely, pay nothing at runtime.

A regular enum is the one sticky note that gets laminated into the page. It doesn't just get checked and discarded — it leaves behind an actual object, built by actual JavaScript, that ships in your bundle whether you asked for it or not.

enum is the exception, not the rule. Interfaces, generics, type aliases — gone by the time your code ships. A regular enum leaves a real object behind, and that one fact explains its reverse map, its bundle cost, and why const enum needs its own warning label later in this lesson.

A numeric enum leaves behind a two-way lookup table.

And it costs real bytes: the object is not tree-shakable, because the assignment expressions inside the IIFE are side effects a bundler can't prove are safe to remove.

Fully known at compile time — a literal, or built only from other constant members. This is what keeps an enum a closed, checkable set. Legal, but every member declared after a computed one needs its own = — TypeScript can no longer auto-increment from a value it can't know ahead of time. Continues counting from the last constant value: start one member at 5 with nothing else set, and the next one lands on 6, not 1. Pairing a numeric member with a string one compiles fine. Legal doesn't mean wise — nothing forces the two halves to relate, and keyof typeof is the one honest way to iterate either kind of member's names.

Erasure, kept

const enum erases completely. Everything else about it is a trade-off.

A const enum is declared exactly like a regular one — same keyword, one word added. Does it produce more runtime code than a regular enum, less, or exactly the same? The restrictions below are the price of getting that guess right.

Three real restrictions come with that zero cost:

  • No runtime value exists — you can't iterate its members, index into it dynamically, or pass "the enum" itself anywhere.
  • isolatedModules conflicts: tools that transpile one file at a time (esbuild, swc, Babel — most modern build chains, Angular's included) can't see another file's enum values to inline, so a cross-file const enum is rejected or silently demoted to a regular one.
  • Type-stripping runtimes reject it outright — and now reject a plain enum too, under the same erasableSyntaxOnly flag that also bans constructor parameter properties (see the classes lesson for that half of it). See "no dumb questions" below for the exact list of what it bans.
  • Never export one from a library: consumers inline your current values into their own bundles; if v2 renumbers a member, already-compiled consumers keep the stale number. The TypeScript team itself now discourages const enum in published code for exactly this reason.

The exam's favourite trap

Enums don't exist inside your own templates. Not without help.

Every enum on this page so far has lived entirely inside a .ts file. Try to reach one from a template and something surprising happens: the exact same expression compiles on one side of a single class field, and fails to compile on the other.

The modern default

Or skip the enum entirely. A literal union costs nothing and needs no import.

Most of the time you don't need a runtime construct at all. A literal union is fully type-safe, costs nothing at runtime, serialises naturally, and — as the last section just proved — needs no re-export to reach a template. And when you do want a runtime list or lookup alongside the type, one as const object derives both from a single declaration.

That derivation — (typeof X)[keyof typeof X] — comes up constantly once you start looking for it; the full mechanics live in the keyof / typeof lesson. Unlike a string enum, the raw literal 'debug' is assignable to the derived LogLevel type — usually exactly what you want at an API boundary.

Live — a literal union

@for (d of directions; track d) { }

heading: {{ dir() }} ({{ degrees() }}°)

The lookup above is typed Record<Direction, number> — the compiler proves every direction has an entry, so no fallback branch is needed, and adding a fifth direction to the union is a compile error right here until you give it degrees too.

Which one do you actually want?
Want… Use
A simple set of options (component state, a mode) String-literal union
Union + a runtime list or lookup as const object + derived type
Members must be used via the named constant only String enum (quasi-nominal)
Numeric / bit flags combined with | / & Numeric enum
Zero runtime footprint, safe under type-stripping runtimes as const object — both enum and const enum are banned there
Default to a string-literal union. It costs nothing at runtime, needs no re-export to reach a template, and narrows perfectly. Reach for an enum only when you specifically want bit flags, or quasi-nominal typing that forces every call site through one named constant.

One more place unions win

Exhaustiveness checking: the compiler notices what you forgot.

A literal union has one more advantage worth knowing for exams: the compiler can prove a switch covers every case, and name the exact line that needs updating when a new case is added later.

assertNever — see the narrowing lesson for the full trick — works for enums too, but literal unions give crisper errors here, and the compiler can even flag impossible comparisons like d === 'norht': a typo in an enum member name would simply fail to exist, while a typo in a raw string compared against a union is caught right at the comparison.

Questions from the back row

Before you go

Six things to remember.

  • TypeScript erases nearly everything it adds — except a regular enum, which compiles to a real, non-tree-shakable object. Numeric enums get a two-way reverse map; string enums don't.
  • String enums are quasi-nominal: only the member itself satisfies the type, even though its runtime value is the exact string you'd otherwise write by hand. Numeric enums leak plain numbers freely both ways.
  • const enum inlines to literals — zero runtime cost, but hostile to isolatedModules builds, rejected outright by type-stripping runtimes, and dangerous to export from a library.
  • Bit flags (1 << n, combine with |, test with &) are the strongest remaining reason to reach for a numeric enum on purpose.
  • An enum needs a class-side re-export to be readable from a template — protected readonly Status = Status; — because the template type-checker only resolves names against the component instance. A literal union never needs this.
  • Literal unions and as const objects cover most needs with zero runtime footprint, and (typeof OBJ)[keyof typeof OBJ] derives the union straight from the value.
