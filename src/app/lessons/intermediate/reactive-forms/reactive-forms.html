Reactive (model-driven) forms put the form's whole structure in the component class instead of the template: a tree of FormControl/FormGroup/FormArray objects that is the actual source of truth — typed, readable synchronously, and testable without ever touching the DOM. This page also bridges that model into Angular signals with toSignal(), so the same reactive-forms API you'll be tested on plays cleanly with the rest of modern Angular.

The whole bug, in one picture

Two controls, each subscribed to the other's valueChanges so they can stay in sync. One line writes to just one of them. Nothing here looks dangerous — until you notice that a write is exactly the thing a subscriber is listening for.

One write becomes an unbounded chain. loopA's valueChanges fires, and its subscriber patches loopB — itself a write, so loopB's own valueChanges fires, whose subscriber patches loopA right back. Each patch re-triggers the sibling's own subscription, synchronously, with nothing on either side ever telling the other "I already know — don't tell me again."

Tell one person a rumour and they whisper it to a second person out of habit — fine, once. But if that second person also whispers it straight back the instant they hear anything, and the first person does the same in return, the rumour never actually stops moving — it just bounces between the two of them, each relay counting as fresh news worth repeating. {{ '{ emitEvent: false }' }} is the agreed rule "don't relay what I just told you back to me" — without it, every patch is heard as something new.

The problem

Where does a form's truth actually live?

With [(ngModel)], the template is the model — Angular assembles a form object behind the scenes as it renders your markup. That's quick for a login box. It gets painful fast the moment you need two fields to agree with each other, need to add or remove fields while the app is running, or want a test that exercises validation without a browser and a DOM fixture — because there is no single object anywhere holding the form's real state; the template is the only place it exists.

Reactive forms fix that by building the model in TypeScript, on purpose, before any template exists at all.

Say a signup form needs password and confirm to match. There's an obvious-looking place to put that check: a validator on the confirm control, right next to the field that would show the error. Would that actually work? Hold your guess — "Two fields need to agree", a few sections down, settles it for good.

The mental model

A FormGroup is a filing cabinet, not a spreadsheet.

Here's the mental model: a FormGroup is a filing cabinet, and every FormControl it holds is a labelled folder inside it — name, email, age, whatever the shape calls for. Each folder is completely independent: it owns its own value, its own status, and its own validators, and it has no idea any other folder even exists.

The cabinet itself isn't just a box holding folders — it has one master status plate on the front, and that plate always reports the worst thing happening inside. Put something invalid in the email folder and the plate flips to INVALID immediately: one bad folder poisons the whole cabinet, even though the name and age folders never changed. And whenever anything in the cabinet changes, a clerk immediately walks every folder and copies what's currently written on each one onto a brand-new sheet of paper — that sheet is .value. Ask for it any time and you get the clerk's latest sheet. Scribble on that sheet all you like; the folders themselves never see it.

Cabinet, folder, snapshot. A FormGroup is the cabinet. Each FormControl is a folder inside it, with its own value and status. .value is the snapshot — a copy taken off the folders, never a live window back into them.

Putting it in code

So what does building one of these cabinets look like?

Every folder and every cabinet extends the same abstract base, AbstractControl, which is why they all share value, status, errors, valueChanges and statusChanges:

  • FormControl — a single leaf value (an input, a checkbox…): one folder.
  • FormGroup — a fixed set of named child controls: the cabinet, with a named drawer for each.
  • FormArray — a growable list of indexed child controls: a numbered drawer of same-shaped folders, covered in full further down.

FormBuilder (usually injected as fb) is a typed factory for these three — it saves writing new FormGroup({{ '{' }} name: new FormControl(...) {{ '}' }}) by hand.

Reading and writing

value or getRawValue — which one is telling you the whole truth?

With the typed-forms API, form.value and controls are strongly typed from the group() definition — no any. Use patchValue for partial updates, setValue for all fields.
Two subtleties: form.value types every field as optional and omits disabled controls — use getRawValue() for a complete, non-partial object. And controls are nullable by default (reset() sets null); build with fb.nonNullable.group({{ '{' }}…{{ '}' }}) when you want resets to restore the initial value instead — the password form below does exactly that.

Only a control can change a control. Mutating the object form.value hands you back — or any object nested inside it — never reaches the real FormControl. Change state through patchValue(), setValue(), or the control itself.

A subtler trap

Subscribe to valueChanges and patch another control? That can ping-pong forever.

emitEvent is an option almost nobody meets until it bites them: every write method — setValue, patchValue, reset, updateValueAndValidity, disable, enable — accepts {{ '{' }} emitEvent, onlySelf {{ '}' }}, and by default every write announces itself on valueChanges/statusChanges. That's harmless for one control. It stops being harmless the moment a subscriber to one control's valueChanges writes to a different control that has a subscriber writing back.

The buggy button writes once and the counter rockets to 40 — capped only so this page doesn't lock up proving the point; left uncapped, the same wiring keeps going until the browser's call stack gives up. The fixed button performs the identical write and the counter reads exactly 1.

Two traps worth naming on their own. (1) disable() emits on valueChanges too — by default — with the disabled control's key already dropped from the value, so disabling a field from inside a valueChanges subscriber is the classic accidental version of this same loop. (2) {{ '{' }} onlySelf: true {{ '}' }} stops a write from bubbling to the parent at all — useful to avoid re-validating a whole cabinet for one folder's edit, but it also means form.valid can go stale until something else touches the parent.

Cross-field validation

Two fields need to agree — whose job is it to check?

A validator is just a function: (control: AbstractControl) => ValidationErrors | null. Put one on a single folder (like Validators.required) when it only needs that folder's own value. The moment a check needs to compare multiple sibling folders — the textbook example being "password" and "confirm password" — it has to live on the FormGroup that contains them, because that cabinet is the only thing that can see both at once. Remember the guess from the top of this lesson? This is where it gets settled.

Live — group-level cross-field validator

group status(): {{ passwordStatus() }} @if (passwordsMismatch()) { passwordsMismatch error }

Neither control carries this error individually — passwordForm.get('confirm')!.errors stays null even while the two values differ. The error lives on the cabinet, because that's the control the validator was attached to.

Talking to a server

What does the form look like while it's still waiting on an answer?

An async validator has the same job as a sync one, but returns an Observable or Promise of ValidationErrors | null instead of the value directly — for checks that need a round trip, like "is this username taken?". Angular runs sync validators first; only if every one of them passes does it start the async ones, and the folder's own status is PENDING for however long that takes.

Try "admin", "root" or "ada" — the field goes PENDING for ~600ms before resolving to VALID/INVALID. Clear it or type 1–2 characters and notice the async check never even runs — the sync required/minLength validators fail first.

Dynamic lists

What if you don't know how many folders there'll be?

FormArray is for a variable-length list of same-shaped controls: tags, phone numbers, order line items. Unlike a FormGroup's fixed named keys, a FormArray is indexed — you grow or shrink it with push()/removeAt(), and the template loop's index is the binding. The FormArray lesson takes this shape apart in full; this is the version you need to read the demo below.

The mechanism

What does one write actually cascade through?

Every control is a node in a tree, and every write cascades through the same update pipeline — this is the pseudocode version of the folder-and-cabinet dialogue above, and it's what makes cross-field validators, PENDING, and "why does the view update without me subscribing to anything" all click into place: 

{{ underTheHoodSample }}
  • Every write calls updateValueAndValidity(): that one method runs this control's own sync validators, then (if those passed) its async validators, then emits on valueChanges and statusChanges.
  • It bubbles up by default: after updating itself, a control calls parent.updateValueAndValidity() too — exactly how editing either password field re-runs the group's passwordsMatch validator every time.
  • The directives are the bridge to the view: FormControlName/FormGroupDirective subscribe to valueChanges/statusChanges themselves, and that subscription's callback calls ChangeDetectorRef.markForCheck() on the host view. That's the actual mechanism — not magic — behind why form.valid in a template stays correct with zero manual wiring, even in this app's zoneless setup.
  • toSignal() taps the same stream: it's just another subscriber to valueChanges/statusChanges, storing the latest emission in a signal. Nothing about the underlying form model changes when signals sit on top — it's a different way to read the same pipeline.

Exam pitfalls

What trips people up on this, every single time?

  • value omits disabled controls. Use getRawValue() for a complete object including disabled fields.
  • setValue needs every field. It throws on a partial object — use patchValue for partial updates.
  • Disabling via the template. [disabled] on a formControlName input warns — set disabled in the model (disable() / the control config).
  • Controls are nullable and reset to null. Use fb.nonNullable when a reset should restore the initial value.
  • Wrong module. Reactive forms need ReactiveFormsModule, not FormsModule — mismatched imports give "no known property formControlName".
  • Cross-field validators go on the group, not a child control. A single control literally cannot see its siblings' values — attaching a "passwords match" check to the confirm control is a trap answer.
  • Async validators run only after sync ones pass, and status goes PENDING while they're in flight. Reading form.valid synchronously right after a change can catch a still-pending result.
  • An async validator's Observable must complete. A stream that never completes (e.g. a bare Subject with no take(1)) leaves the control stuck in PENDING forever.
  • Manual .subscribe() leaks like any Observable subscription. Prefer toSignal() (auto-cleanup) or takeUntilDestroyed() over a bare valueChanges.subscribe(...) in a component.
  • Tracking a FormArray loop by $index is correct here — unlike most @for loops, where a stable id is preferred, [formControlName]="i" IS the position, so the index is the identity that matters.

Questions from the back row

Before you go

What should actually stick?

  • FormGroup/FormControl/FormArray are all AbstractControls — cabinet, folder, and a numbered drawer of folders, sharing one API (value, status, errors, valueChanges, statusChanges).
  • Reading form.value hands you a snapshot object, rebuilt fresh whenever the cabinet changes — mutate it all you like, the real folders never hear about it. patchValue/setValue are the only doors in.
  • A cross-field check can only live on the group that can see both siblings — never on either child alone.
  • Async validators run only once every sync validator has passed, and PENDING is the status for "still checking," not a flavour of invalid.
  • Every write cascades through updateValueAndValidity(), bubbles to every ancestor, and the forms directives are what turn that into markForCheck() on the view — no manual wiring, even in a zoneless app.
