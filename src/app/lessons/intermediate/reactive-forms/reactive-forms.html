Reactive Forms

Reactive (model-driven) forms define the form structure in the component class. The model — a tree of FormControl/FormGroup/ FormArray instances — is the source of truth: fully typed, synchronous to read, and easy to unit test without touching the DOM. This page also bridges that model into Angular signals with toSignal(), so the same reactive-forms API you'll be tested on also plays cleanly with the rest of modern Angular.

Anatomy of a reactive form

Every node in a reactive form extends the same abstract base, AbstractControl, which is why they all share value, status, errors, valueChanges and statusChanges:

  • FormControl — a single leaf value (an input, a checkbox…).
  • FormGroup — a fixed set of named child controls (an object shape).
  • FormArray — a growable list of indexed child controls (same shape, repeated).

FormBuilder (usually injected as fb) is just a typed factory for these three — it saves you writing new FormGroup({{ '{' }} name: new FormControl(...) {{ '}' }}) by hand.

this.form.value Typed snapshot of the group's value. Every field is typed optional, and disabled controls are omitted entirely — this is the API you'll usually send to a server.

this.form.patchValue({{ '{' }} name: 'Grace' {{ '}' }}) Partial update — only the keys you pass are touched, everything else keeps its current value. No error if some fields are omitted.
this.form.setValue({{ '{' }} name, email, age {{ '}' }}) Full update — every key the group defines must be present, or it throws. Angular is deliberately strict here so you can't accidentally forget a field and silently lose it.
this.form.valueChanges.subscribe((v) => ...) An Observable that emits the new value on every edit. A manual subscribe() like this needs manual teardown — see the pitfalls list for the safer alternatives.
this.form.statusChanges.subscribe((s) => ...) An Observable of 'VALID' | 'INVALID' | 'PENDING' | 'DISABLED' — fires on every status transition, including the transient PENDING state while an async validator is running.
With the typed-forms API, form.value and controls are strongly typed from the group() definition — no any. Use patchValue for partial updates, setValue for all fields.
Two subtleties: form.value types every field as optional and omits disabled controls — use getRawValue() for a complete, non-partial object. And controls are nullable by default (reset() sets null); build with fb.nonNullable.group({{ '{' }}…{{ '}' }}) (or nonNullable: true) when you want resets to restore the initial value instead — the passwordForm below does exactly that.

Custom & cross-field validators

A validator is just a function: (control: AbstractControl) => ValidationErrors | null. Put one on a single control (like Validators.required) when it only needs that control's own value. When a check needs to compare multiple sibling controls — the textbook example being "password" and "confirm password" — it has to live on the FormGroup that contains them, passed as the second argument to group(), because that's the only node that can see both:

passwordForm = this.fb.nonNullable.group( fb.nonNullable produces controls whose value type drops | null and whose reset() restores the initial value instead of null — appropriate for a password field where "reset to null" makes little sense.

Async validators & the PENDING status

An async validator has the same job as a sync one, but returns an Observable or Promise of ValidationErrors | null instead of the value directly — for checks that need a server round-trip, like "is this username taken?". Angular runs sync validators first; only if they all pass does it start the async ones, and the control's status is PENDING for however long that takes:

validators: [Validators.required, Validators.minLength(3)], Sync validators run first, synchronously, on every keystroke. If either fails, Angular never even calls the async validator — no point checking availability for an empty or too-short name.
asyncValidators: [usernameTaken(['ada', 'admin', 'root'])], Only reached once sync validators pass. While it's in flight, control.status === 'PENDING' — a state most learners forget exists until an exam question tests it.

FormArray — dynamic, repeatable controls

FormArray is for a variable-length list of same-shaped controls: tags, phone numbers, order line items. Unlike a FormGroup's fixed named keys, a FormArray is indexed — you grow/shrink it with push()/removeAt(), and the template loop's index is the binding:

Line What & why
skills = this.fb.array([this.fb.control('Angular', Validators.required)]); fb.array() takes an initial list of controls (here, one pre-filled control) and returns a typed FormArray whose element type is inferred from that first control.
skillsForm = this.fb.group({{ '{' }} skills: this.skills {{ '}' }}); A FormArray is still just an AbstractControl, so it can be nested inside a FormGroup like any other control — that's what lets you bind it to a <form>.

@for (ctrl of skills.controls; track $index; let i = $index) Deliberately tracking by $index — see the pitfalls list below for why that's the correct choice here, not the anti-pattern it usually is.
<input [formControlName]="i" /> formControlName also accepts a number when its container is a FormArray — i is the control's position, not a name. This is the binding that makes the index the actual identity that matters.

Reactive vs template-driven

Reactive Template-driven
Model lives in the class (FormBuilder.group()) the template ([(ngModel)] builds it implicitly)
Import ReactiveFormsModule FormsModule
Typing fully typed from the control config — no any weakly typed; the shape only exists once the template renders
Cross-field / dynamic validation straightforward — group-level validators, FormArray awkward — needs custom directives or extra plumbing
Testability high — assert on the model directly, no DOM needed lower — usually needs TestBed + DOM queries
Best for non-trivial forms: dynamic controls, complex validation, heavy testing simple, mostly-static forms (a login box, a search field)

Under the hood — the AbstractControl tree

Every control is a node in a tree, and every write cascades through the same update pipeline — understanding this is what makes cross-field validators, PENDING, and "why does the view update without me subscribing to anything" all click into place: 

{{ underTheHoodSample }}
  • Every write calls updateValueAndValidity(): that one method runs this control's own sync validators, then (if those passed) its async validators, then emits on valueChanges and statusChanges.
  • It bubbles up by default: after updating itself, a control calls parent.updateValueAndValidity() too — which is exactly how editing either password field re-runs the group's passwordsMatch validator every time.
  • The directives are the bridge to the view: FormControlName/FormGroupDirective subscribe to valueChanges/statusChanges themselves, and that subscription's callback calls ChangeDetectorRef.markForCheck() on the host view. That's the actual mechanism — not magic — behind why form.valid in a template stays correct with zero manual wiring, even in this app's zoneless setup.
  • toSignal() taps the same stream: it's just another subscriber to valueChanges/statusChanges, storing the latest emission in a signal. Nothing about the underlying form model changes when you add signals on top — you're choosing a different way to read the same update pipeline.

Exam pitfalls

  • value omits disabled controls. Use getRawValue() for a complete object including disabled fields.
  • setValue needs every field. It throws on a partial object — use patchValue for partial updates.
  • Disabling via the template. [disabled] on a formControlName input warns — set disabled in the model (disable() / the control config).
  • Controls are nullable and reset to null. Use fb.nonNullable when a reset should restore the initial value.
  • Wrong module. Reactive forms need ReactiveFormsModule, not FormsModule — mismatched imports give "no known property formControlName".
  • Cross-field validators go on the group, not a child control. A single control literally cannot see its siblings' values — attaching a "passwords match" check to the confirm control is a trap answer; it belongs in the group's validators option.
  • Async validators run only after sync ones pass, and status goes PENDING while they're in flight. Reading form.valid synchronously right after a change can catch a still-pending (neither true nor false) result.
  • An async validator's Observable must complete. A stream that never completes (e.g. a bare Subject with no take(1)) leaves the control stuck in PENDING forever.
  • Manual .subscribe() leaks like any Observable subscription. Prefer toSignal() (auto-cleanup) or takeUntilDestroyed() over a bare valueChanges.subscribe(...) in a component.
  • Tracking a FormArray loop by $index is correct here — unlike most @for loops, where a stable ID is preferred, [formControlName]="i" IS the position, so the index is the identity that matters.

Exam corner

patchValue vs setValue?
patchValue updates a subset; setValue requires the full shape and throws if a field is missing.
Why is a disabled field missing from form.value?
By design — disabled controls are excluded. Use getRawValue() to include them.
When choose reactive over template-driven forms?
Dynamic controls, cross-field validation, heavy testing, or a typed model in the class. Template-driven suits simple, mostly-static forms.
Why must a "passwords match" validator sit on the group instead of the confirm control?
A validator only receives the AbstractControl it's attached to. A control-level validator on confirm has no reference to password's value — only the parent FormGroup can see both children via group.get('password').
What does status PENDING mean, and what two conditions cause it?
The control has one or more async validators currently in flight. It only happens (1) after all synchronous validators on that control have already passed, and (2) before the async validator's Observable/Promise has resolved — PENDING is neither valid nor invalid, it's "still checking".
This app runs zoneless. How does typing into a formControlName input still update the template?
Not zone.js, and not signals either (for the plain form.valid reads) — it's the reactive-forms directives themselves. FormControlName/ FormGroupDirective subscribe to the control's valueChanges/statusChanges and call ChangeDetectorRef.markForCheck() on every emission, same as the async pipe does for any other Observable.

Key takeaways

  • FormBuilder.group() defines a typed form model in the class, built from FormControl/FormGroup/FormArray, all sharing the AbstractControl API.
  • Bind with [formGroup] + formControlName (or formArrayName + a numeric formControlName for arrays).
  • Read state via value / getRawValue(), valid, errors, valueChanges, statusChanges — or wrap those Observables in toSignal()/computed() for signal-based reads.
  • Update with patchValue (partial) or setValue (full, throws if incomplete).
  • Cross-field validators live on the group; async validators run after sync ones pass and surface a transient PENDING status.
  • Every write cascades through updateValueAndValidity(), bubbles to the parent, and is what the forms directives use to keep the view in sync — no manual change-detection wiring required, even under OnPush/zoneless.
