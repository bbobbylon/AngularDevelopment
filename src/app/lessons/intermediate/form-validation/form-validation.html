Angular ships built-in validators, lets you write your own, and lets several fields gang up on one check together — but almost every real bug in this area comes from two questions hiding underneath all of that: when does a validator actually run, and when is the user allowed to find out it failed? Get the first wrong and an async validator hits your server on every keystroke. Get the second wrong and a brand-new empty form greets the user with a wall of red before they've typed a single key. This page answers both, live.

The problem

A required field is invalid the instant it's created. So why isn't it already red?

Create new FormControl('', Validators.required) and, before anything else happens, that control already has errors: { required: true }. Nobody clicked into it. Nobody typed anything. The validator ran the moment the control existed, because that is simply what a validator is — a function that gets asked "any complaints?" and the empty string already fails required.

And yet the demo further down this page doesn't show a single red message on load. You have to click into the username field and click back out again before anything appears. Same control, same validator, same result — so something else entirely is deciding whether the user ever gets told.

Two things are true at once here: the control really is INVALID from the first render, and the page shows nothing wrong until you visit and leave the field. What flag do you think is standing between "invalid" and "displayed as invalid"? "Which flag decides whether the user actually sees it?" further down names it exactly.

The mental model

Every control carries a small pad of sticky notes.

Picture every control with a pad stuck to it. Each validator that fails writes one note with its own name on it — required, minlength, hasDigit. Angular collects the notes into one object, and that object is control.errors.

A clean control has no notes at all, which is why errors is null rather than {} — and why a validator returns null to mean "valid". It isn't reporting success; it's reporting nothing to complain about. Hold on to the pad: it is doing more work in this lesson than it looks like at first.

A validator returns null when it is happy, and an object when it is not. It hands back the complaints it found — so no complaints means nothing to hand back.

The shape

What does a custom validator actually look like?

Not special syntax — a plain function matching one signature: take a control, hand back an error object or null. Validators.required and every other built-in validator match this exact shape, which is the whole reason a hand-written one composes with them so easily.

One level up

Where does a cross-field check actually go?

A validator that needs to compare two fields has a problem: it is only ever handed the one control it is attached to. The fix isn't a cleverer function — it's attaching the exact same kind of function to a different node in the tree, one that can actually see both fields.

Zooming out

Four places, and only four, a validator can attach.

['', [Validators.required]] — the shorthand used everywhere in this lesson. Sync validators only; it has no slot for an async one at all. { validators: [...], asyncValidators: [...] } — the longer form, and the only one that accepts asyncValidators or updateOn. The second argument to .group(). Sees every named child — this is where passwordsMatch lives, above. The second argument to .array(). Validates the array's own value — "at least one item" — never any one element. See the FormArray lesson.

Resolving the napkin

Which flag decides whether the user actually sees it?

touched and dirty are not interchangeable, and picking the wrong one is why a form either nags too early or stays silent too long. Every control carries five independent flags:

The five flags every control carries
Flag Means Flips when
touched / untouched The user visited the field On blur — focus left, whether or not anything was typed
dirty / pristine The user changed the value On the first value change from the UI (not from setValue)
valid / invalid Validators are satisfied Whenever updateValueAndValidity() runs
pending An async validator is still deciding Sync pass came back clean and the async queue started
disabled Excluded from the form entirely disable() — note it drops out of form.value and always reports valid

Tab straight through a form without typing and every control ends up touched but pristine. That is the case that answers the napkin: touched means "they have had their chance at this field", which is almost always the right moment to speak up — and it is exactly the flag the demo above gates its messages on.

Under the hood

Six steps run every time a control revalidates.

The gate at step four is the one worth memorising — it's the reason an async validator is conditional, not just slower:

  • A validator is just a function (control) => ValidationErrors | null. Validators.required and friends are all plain functions matching ValidatorFn; the custom hasDigit() above isn't special syntax — it's the exact same signature, which is why validators compose so easily.
  • valueChanges and statusChanges are Observables, not bespoke Angular machinery — every AbstractControl exposes them as RxJS streams. The reactive-forms directives (formControlName, formGroup, …) are themselves just subscribers wired up for you at bind time.
  • Sync validators run first, every time; async validators only run once every sync validator returns null. Each control keeps two separate validator queues internally. updateValueAndValidity() runs the synchronous queue immediately, and only if the control comes out VALID from that pass does it kick off the async queue, flipping status to PENDING until every async validator resolves.
  • updateOn decides which DOM event triggers that updateValueAndValidity() call — 'change' (default) hooks the input event, 'blur' hooks blur, 'submit' waits for the form's submit event. It changes when validators run, never what they check.
  • setErrors() bypasses the validator pipeline entirely. It writes directly to control.errors, which is why it clobbers the whole object instead of merging — the next updateValueAndValidity() call (from a value change, a blur, …) throws that away and rebuilds errors from the validator functions again.

Field notes

What actually goes wrong in code review.

  • Cross-field validator on a control. It belongs on the FormGroup — a single control can't see its siblings. Read the error from form.errors, not the control's.
  • Showing errors immediately. Gate on touched/dirty so users aren't warned before typing.
  • Reading a missing error key. errors is null when valid — use errors?.['required'], never errors['required'].
  • setErrors clobbers other errors. setErrors replaces the whole object; merge if you must keep existing keys, and call updateValueAndValidity() after imperative changes.
  • A validator with side effects. Validators must be pure and synchronous (async ones are a separate slot) — no HTTP, no state mutation.
  • Wrong-case error key. minlength / maxlength are lowercase; there's a callout on exactly this above the built-in validators table.

Questions from the back row

Before you go

Five things to remember.

  • A validator returns null when it's happy and an object when it isn't — it's reporting complaints, not verdicts, which is why "nothing wrong" is null rather than {}.
  • Cross-field validators go on the FormGroup, via its second argument — never on a single control, which can only ever see itself.
  • touched means visited, dirty means edited. Gate error messages on touched so a form doesn't nag before anyone has had a chance to type.
  • Sync validators run first, every time; the async queue only starts once every sync validator returns null — a deliberate gate, not a coincidence.
  • setErrors() bypasses the whole pipeline and replaces the entire errors object — the next updateValueAndValidity(), from any keystroke or blur, throws it away and rebuilds from the real validators again.
