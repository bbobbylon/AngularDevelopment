A pipe formats a value for display — currency, a relative date, a filtered list — without moving that logic into the component class or repeating it in five templates. The mechanics are five minutes of work: decorate a class with @Pipe, implement transform(), add it to a component's imports, and write | in the template. What is worth the other forty minutes is what pure actually promises you, exactly what breaks it, and the one honest reason to give it up.

The problem

Where does formatting for the screen actually live?

Say you need to show "3m ago" instead of a raw ISO timestamp. Nothing stops you from formatting it in the component — a getter, a method called from the template, or a field you write to when the data arrives. All three work. All three also share a problem you will not notice until the component is checked a lot: none of them remember the answer they gave last time.

  • A getter re-runs its whole body on every single read — and a template reads it once per binding, per check.
  • A method call in a binding, {{ '{{' }} formatPrice(price) {{ '}}' }}, is exactly the same cost with worse syntax.
  • Formatting at the source — storing "$4.00" instead of 4 — throws the real number away, so the next thing that needs to do math with it can't.

A pipe is the fourth option, and it is the only one of the four that can be genuinely cheap — because, unlike a getter, a pure pipe is allowed to remember its last answer and skip the work entirely when nothing has changed. That single fact is most of this lesson.

Picture a component checked forty times a second — nothing exotic, that's just forty clicks somewhere in a Default-strategy app. Its template has {{ '{{' }} getFormattedPrice() {{ '}}' }}, a getter that formats a number as currency. How many times does the formatting logic inside that getter actually run in that one second? Now guess again for {{ '{{' }} price | currency {{ '}}' }} on the same component, the same forty checks, formatting the exact same unchanged price. Both lines show identical text on screen. They do not cost the same — keep reading to find out why.

The mental model

A pure pipe is a bouncer with exactly one Polaroid.

Picture a bouncer at a door who is only allowed to hold one photo at a time. Someone walks up; the bouncer compares their face against the photo. Different person? Take a new photo, replace the old one, let them through after doing the actual work of checking ID. Same person as the photo — recognisably, unmistakably the same, not just similar — and the bouncer waves them through on sight, no ID check, no new photo. That is the entire deal a pure pipe offers Angular: one slot of memory, one comparison, and real work only on a miss.

The comparison the bouncer makes is ===, not "looks similar" — reference equality, the strictest kind. Two arrays with identical contents are two different people to this bouncer if they are not the literal same object in memory. That detail is not a footnote; it is the entire cause of the single most common pipe bug there is, and there is a live demo of it a few sections down.

One bouncer, one Polaroid. A pure pipe remembers exactly one input and one output — the last ones — and only redoes the work when what walks up next doesn't match the photo ===.

The mechanism

A pipe is a class with one method — transform().

Here is the whole shape, with the pipe that trims long text down to size. Read it once with the notes; every other pipe in this lesson is the same skeleton with a different transform().

Live — truncate (pure), with its default arguments exposed as a slider

original {{ longText }}

| truncate:{{ limit() }} {{ longText | truncate: limit() }}

Drag the slider back and forth — every position is a genuinely new limit argument, so the pipe's Polaroid never matches and transform() really does run on every single frame. That is fine: it is meant to. The interesting case is what happens when nothing changes at all, which is what the next demo below is built to show.

One more rule worth knowing up front: the string in name is what you type after |, and it must be unique across everything a component's imports array pulls in. Two different pipes both named format is a silent last-one-wins, not a compile error.

Chaining, and a syntax trap

Pipes chain left to right — but | doesn't bind the way you'd guess.

Chaining is just function composition with different punctuation: each pipe's output becomes the next pipe's first argument, in the order they're written.

Live — sentenceCase (pure), chained after truncate

| truncate:20 | sentenceCase {{ rawText() | truncate: 20 | sentenceCase }}

One more thing about that |: inside a template expression it is always the pipe operator, never bitwise OR. Write a | b expecting a bitwise trick from another language and Angular goes looking for a pipe named b — and fails to compile if there isn't one.

Generic pipes, and the cache

A pipe over an array is still just comparing references.

Nothing about the Polaroid changes when the value flowing through it is an array instead of a string — === on an array compares its address, not its contents. That single fact both makes a filter pipe fast and sets the trap for the single most common pipe bug in real apps.

Pushing into an array Angular already has a reference to changes its contents but not its address. A pure pipe compares addresses. An object or array literal written inline in a template is a brand-new reference on every single check, so the pipe never gets to reuse its cache at all — even when nothing meaningful changed. A pipe marked pure (the default) that quietly reads Date.now() or a mutable module-level variable can produce a genuinely different answer while Angular still sees the same input reference — and skips calling it. The output goes stale until something unrelated finally changes.
Scroll to the fruit list below. Before typing anything in the search box, press Push a Kiwi (mutate) two or three times, and watch the two counts: the total in the array, and the pills actually rendered. Then press Add a Kiwi (replace) once. Both buttons genuinely add a fruit. Only one of them ever shows up.

Live — filterBy (pure, generic), with a mutate-vs-replace switch built in

in the array: {{ fruits.length }} query: "{{ fruitQuery() || '(none)' }}"

@for (f of fruits | filterBy: 'name' : fruitQuery(); track f['name']) { {{ f['name'] }} } @empty { No fruits match. }

"In the array" jumps immediately on every press — that count reads fruits.length directly, no pipe involved. The pill row is the honest one: after mutate it does not budge, because filterBy's cached items argument is still the exact same array reference it was last time. After replace a Kiwi finally appears, because that button built a whole new array — a different reference, a cache miss, a real re-run.

Dependency injection

transform() runs inside an injection context, same as a component.

A pipe is an ordinary injectable class. inject() works inside one exactly as it does inside a component or a service — here, to reuse Angular's own built-in DatePipe as a fallback formatter rather than reimplementing date formatting from scratch.

Live — relativeTime (pure, injects DatePipe)

@for (post of posts; track post.id) {
{{ post.title }} {{ post.date | relativeTime }}
}

Impure pipes

pure: false means "ask me on every single check."

Sometimes a pipe genuinely needs to react to something a reference comparison cannot see — here, characters typed into a search box highlighting matches inside text that hasn't itself changed. pure: false switches off the Polaroid entirely: no cache, no skipped calls, transform() runs on every change-detection pass that reaches this view, whether or not its arguments moved.

Live — highlight (impure, pure: false)

@for (item of highlightItems; track item) {

}

This works here because this whole component uses the Default strategy, which checks every view on every pass regardless of what changed. That is not a guarantee — read on.

pure: false buys you certainty about whether transform() runs on a check. It buys you nothing about whether a check ever happens — and that second question belongs to change detection, not to the pipe.

The one legitimate exception

Some pipes own something that has to be torn down.

There is exactly one honest reason to reach for pure: false that has nothing to do with "the arguments didn't change but I need to re-check anyway": a pipe whose value changes on its own schedule — a timer, a socket, an Observable — because there is no argument change to key a cache off in the first place. Angular's own built-in async pipe is exactly this. Here it is, rebuilt from scratch.

@if (showClocks()) {
Clock A: {{ ticks$ | miniAsync }}s Clock B: {{ ticks$ | miniAsync }}s
}

Mount the clocks and the subscription count jumps to 2 — two separate bindings, two separate MiniAsyncPipe instances, two independent subscriptions to the same ticks$. Unmount, and it drops straight back to 0: Angular destroyed both bindings, which called ngOnDestroy on both pipe instances, which unsubscribed both. Nothing about that cleanup was written by you.

Pulling it together

Pure vs impure, side by side.

The whole decision, in one table
Property Pure (default) Impure (pure: false)
Re-runs when Any argument's reference changes Every change-detection pass that reaches this view
What's cached One input/output pair, per binding site Nothing
Reruns inside a non-dirty OnPush host? N/A — never re-checked either way No. Impure buys "every check", not "a check happens"
May own cleanup (a subscription, a timer)? No — nothing ever calls it when nobody's checking Yes, and it should implement ngOnDestroy if it does
Best for Formatting, filtering, mapping — presentational work Reacting to mutation, or owning a subscription's lifecycle
Reach for computed() before pure: false. The one legitimate reason to write an impure pipe is that it owns something that needs tearing down — a subscription, a timer — not that its output merely changes on its own.

Questions from the back row

Before you go

Six things to remember.

  • A pipe is @Pipe({ name, standalone: true }) plus transform(value, ...args). The first parameter is always what sat left of |; every :arg after it is a further parameter, defaults and all.
  • Pure by default means single-slot memoisation, per binding site — not a shared, keyed cache. Two identical bindings never share a result, and the slot is overwritten the instant an argument's reference changes.
  • That cache is exactly why mutating an array (or object) you pipe does not render — the reference is unchanged, so a pure pipe hands back its old answer. Replace it instead.
  • Impure (pure: false) reruns on every check that reaches its view — costly, and still silent inside an OnPush component nothing else marks dirty. Its one honest use is owning something with a teardown: a subscription, a timer, ngOnDestroy required.
  • The pipe operator binds tighter than a ternary's branches — cond ? a : b | pipe only ever pipes b. Parenthesise the whole conditional when you mean the whole thing piped.
  • For anything actually reactive — filtering, deriving, combining signals — reach for computed() first. A pipe is for genuinely presentational formatting.
