A synchronous ValidatorFn has one rule: answer right now, or don't answer at all. That falls apart the moment a rule needs a server — "is this username already taken?" can't be checked without a network round trip, and nothing about a plain function can pause and come back later. An AsyncValidatorFn solves it by changing what a validator is allowed to return: not the verdict itself, but a promise of one — an Observable<ValidationErrors | null>. While Angular waits for that Observable, the control sits in a third status, PENDING, that is neither valid nor invalid. This page builds one, races a debounced version against a naive one live, and then reads Angular's own source to see exactly what happens between one keystroke and the next.

Type admin into a username field with no debounce. Five keystrokes after the first — five separate 700ms "server" checks, and four of them for a username nobody was ever going to submit.

The mechanism

Cancelling a stale check stops it from ever answering. It does nothing about whether the check already went out — those are two different moments, and only one of them is what a debounce actually prevents.

Debounce doesn't make a check cheaper. It makes there be one.

The problem

Can a validator ever answer "not yet"?

A synchronous validator is a plain function. It runs, it returns, and by the time it returns Angular already needs the answer — there is no way to pause a function call and come back to it later. That's fine for Validators.required or Validators.email; the whole check happens in memory, in microseconds. It falls apart the instant the rule is "ask someone else" — is this username free, does this coupon code exist, has this email already registered. None of those answers live on your machine.

So async validation gets a different shape entirely. Instead of returning the verdict, an AsyncValidatorFn returns a promise of a verdict — and while that promise is unresolved, the control needs somewhere to sit that is neither VALID nor INVALID. That third place is PENDING, and almost every mistake in this lesson comes from forgetting it exists.

A control's status is 'PENDING' right now, mid-check. What do you think control.invalid equals at that exact moment — true or false? Hold that answer; "the submit-button trap" further down settles it with a live compare panel.

The mental model

A sync validator checks ID at the door. An async one calls head office.

Think of a synchronous validator as a bouncer checking ID at the door. They glance at the card, compare a birthdate against today's date, and wave you through or turn you away — all in the time it takes to look. Nothing about that check can be sped up or slowed down; it's arithmetic, not a phone call.

An async validator is the same bouncer handling a reservation instead. "Is there a table booked under this name?" isn't something they can answer by looking at you — they have to put you on hold and phone the front desk. Two things follow from that one change. First, you're neither confirmed nor turned away while the call is happening — you're on hold, which is exactly what PENDING is. Second, if you give a different name before the first call has been answered, a good bouncer doesn't let that stale answer come back and seat you under the wrong reservation — they hang up on it the moment you ask a new question, so only the answer to what you're asking right now can ever reach you.

A sync validator checks ID at the door. An async one calls head office — and hangs up on the last call the instant you ask a new question. Everything in this lesson is one of those two sentences with the technical names filled in.

The visual

What actually happens between two keystrokes?

You type ad — a check goes out. A moment later you type ada — a second check goes out. Suppose ad's response happens to arrive after ada's, because of an unlucky retry or just network jitter.

If both Observables were left running, whichever one calls next() last wins — even though it's answering a question you're no longer asking. The field would silently show the verdict for ad, a username that isn't even in the box any more.

Step 3 of the timeline above runs before the new check is even created: cancelExistingSubscription() unsubscribes ad's Observable completely.

ad's response can still be somewhere on the network — Angular doesn't wait for it and doesn't care. The subscription is severed, so its eventual next() call has nowhere to land. Only ada's check can ever reach setErrors().

The left counter climbs once per keystroke; the right counter only climbs after you stop typing for 400ms, because every keystroke cancels the debounced field's pending timer(400) before it can fire. That cancellation is real and automatic — it's AbstractControl doing it on your behalf, not something your component code arranges (see the visual above).

Myth to unlearn: "switchMap cancels the stale request" is the textbook line, and it's a fine habit — but for a single async validator on a single control, the cancellation you're relying on actually comes from AbstractControl itself (step 3 of the timeline above), not from switchMap. The operator becomes load-bearing once a validator's Observable can emit more than once per subscription — not in the common "debounce, then one HTTP call" shape shown here.

The one every "how would you check a username" interview misses

On an edit form, the validator has to let you keep your own name.

Every uniqueness check above assumes a create form — the field starts empty, so any taken value really does belong to someone else. An edit form starts with the record's own current value already sitting in the box, and uniqueUsername from the top of this page has no way to know that value is the user's own — it just sees 'ada' in the taken list and rejects it. The user cannot save their own profile without changing their username first.

Two more short-circuits worth knowing. Skip the check entirely when control.pristine — loading a saved record into a form should never itself fire a request; only the user's own edits should. And when a validator needs to resolve with "nothing wrong here", return of(null), never EMPTY: EMPTY completes without ever emitting a value, so — per "Under the hood" above — setErrors() is never called, and the control is left stuck on PENDING forever, exactly like the filtered-out bug just below.

Common shorthand, and where it stops being exactly true: "the async validator must complete" is the version most people learn, and it survives because of(), an HTTP call and a resolved Promise all naturally emit and complete together. The state machine

Four statuses, one field.

status is a single field with exactly one value at a time — never a combination. .valid, .invalid, .pending and .disabled are just getters that compare it to one value each:

No sync errors, and any async validator resolved to null. .valid is true; the other two are false. A sync validator returned errors, OR an async one resolved with a non-null value. .invalid is true; .pending is false. Sync validators passed and an async one is still running. .invalid is false here — that's the trap in the next section. The control (or an ancestor) is disabled. No validators run at all — not even the ones that would otherwise fire.

The one that bites in code review

Why does a submit button ignore PENDING?

Because PENDING is its own status, invalid is not true while a control is pending — the cards above show .invalid is false on that row. A submit button gated only on form.invalid stays clickable for the entire async check: 

{{ pendingWrongSample }}

While status === 'PENDING', invalid evaluates to false, so the button is clickable for the entire 700ms the "server" is being asked. 

{{ pendingRightSample }}

valid is only true when status === 'VALID', so this is true (disabled) for both INVALID and PENDING. Equivalent: form.invalid || form.pending.

invalid is only true for INVALID — never for PENDING. Gate a submit button on !form.valid (or form.invalid || form.pending), never on form.invalid alone.

Field notes

What actually goes wrong in code review?

  • Never emitting a value — not just "never completing". A filtered-out case, an empty combineLatest, a Subject nobody calls .next() on — strands a control on PENDING forever, silently. See "spot the silent failure" above.
  • Letting the Observable error instead of resolving. Angular's internal subscribe() has no error handler, so an errored source never calls setErrors() either — same stuck PENDING, plus an unhandled-error report in the console. Always catchError inside your own validator.
  • Gating submit on form.invalid alone. invalid is false while PENDING — use !form.valid, or check .pending explicitly.
  • A request per keystroke. Debounce (timer + switchMap) or set updateOn: 'blur'.
  • Putting it in the sync validators slot. The return types are incompatible — Angular composes each slot differently, and this throws at runtime.
  • Assuming multiple async validators run sequentially. They run in parallel via forkJoin; the slowest sets the pace, colliding error keys silently overwrite, and one that never completes freezes the whole control.
  • Forgetting sync gates run first. An empty required field never reaches the async validator — status must already be VALID from sync validators before Angular calls it.
  • Returning a boolean instead of null. Any non-null value — including false — means "has errors". There's a self-test on exactly this above.

Questions from the back row

Before you go

Five things to remember.

  • An async validator is a sync one with the return type changed: Observable<ValidationErrors | null> (or a Promise) instead of the value itself — the same null-means-valid contract either way.
  • PENDING is its own status, not a shade of invalid. .invalid is false while pending — gate a submit button on !form.valid, never on form.invalid alone.
  • A control resolves the moment its Observable emits — completion by itself is never checked. What actually strands a control forever is a source that never emits at all, not one that merely never completes.
  • Two or more async validators are combined with forkJoin, which genuinely does need every source to complete — so with multiple validators, one that emits but never completes freezes the whole control, even though the same validator alone would have been fine.
  • Debounce the request (timer + switchMap, or updateOn: 'blur') or you've built a keystroke-per-request API client — and the cancellation that saves you from a race is AbstractControl's job, not switchMap's.
