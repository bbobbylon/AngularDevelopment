@Injectable({ providedIn: 'root' }) answers exactly one question — build one of this. Everything below is the much bigger set of questions that leaves open: what do you hand over when there is no class to build, how do you swap an implementation for one subtree without touching the rest of the app, and where does Angular even look when nobody local has an answer. Four small recipes, one scope decision, and a hierarchy an inject() call quietly walks every single time it runs.

The whole bug, in one picture

Find the second providers: array — and watch a "singleton" quietly fork into two.

Two. The component's own providers: [Notifier] doesn't override the root registration — it builds a brand-new element injector for that one subtree, with its own separate instance. Every descendant of Dashboard gets instance B, forever; literally everything else in the app still gets instance A, forever. Nothing looks wrong: no error, no warning, no console message — both instances quietly exist side by side, out of sync from the moment the second one is born.

Picture inject(Token) as a request slip handed to a clerk: "give me a Notifier." The clerk doesn't build anything from imagination — there's a filing cabinet of instruction cards, one per token, consulted before anything else happens: "when this slip comes in, do X." A provider is that card. And the picture above is what happens when two different cabinets — root's, and `Dashboard`'s own — each file a card for the same token: two clerks, two cards, two completely different somethings handed back, and neither clerk knows the other cabinet exists.

The problem

@Injectable() only gets you so far.

providedIn: 'root' works because it answers a very narrow question — Angular reads the decorator, finds the class's own constructor, resolves whatever that needs, and calls new. That covers most services. It does not cover a dependency with no concrete class at all — a plain object, a string, an interface. It does not cover wanting to depend on an abstraction, so today's concrete implementation isn't hard-wired into every file that uses it. And it says nothing about swapping an implementation for one subtree, or one test, without touching the "real" registration.

None of those are "give me one of these" questions. They're when someone asks for THIS, do THAT instead questions — and that instruction is what a provider actually is. Not the dependency. The recipe for producing it.

abstract class Notifier { abstract send(msg: string): string; } Could you write @Injectable({ providedIn: 'root' }) abstract class Notifier {} and just inject(Notifier), the way you would for an ordinary service? Say yes or no — and say why — before you scroll.

No. providedIn's default recipe is call the class's own constructor, and an abstract class has no constructor you're allowed to call — new Notifier() is a compile error before DI ever gets involved. Something else has to tell the injector what to build when Notifier is asked for. That "something else" is the whole subject of this lesson.

Same idea, one more way

The instruction card, acted out.

You just read the filing-cabinet version. Here's the exact same slip-and-card exchange, spoken instead of pictured — with the four recipes named as four different instructions that card could carry.

useClass says build one from this blueprint. useValue says hand over this exact thing — it's already made. useFactory says run this function and give back whatever it returns. useExisting says don't build anything at all — walk over to THAT other card and bring back what it already has.

Value, Class, Factory, Existing. useValue hands over something already built. useClass builds it from a blueprint. useFactory runs a function and takes whatever comes back. useExisting builds nothing — it points at a recipe that already ran.

The recipes

Four ways to answer one slip.

All four recipes below produce a value for the same kind of request — { provide: Token, ... } — and differ only in how that value comes to exist.

The factory that got a shortcut.

Packaging

    
Every modern Angular API you've called is one of these.


    

      provideRouter(), provideHttpClient(), provideAnimationsAsync() — every one
      of them is a function that returns a bundle of providers, meant to be dropped into an app's own
      providers array. Writing your own is how you let consumers of a shared feature configure it, instead
      of asking them to copy a raw providers array out of your README.
    


    

    

      EnvironmentProviders only makes sense at the app or route level. Try passing
      provideAnalytics(...) inside a @Component's own providers: [...] and
      the compiler rejects it — Provider[] is what that array expects, and
      EnvironmentProviders is deliberately not one of those. The type itself is the guardrail, not a
      comment telling you not to.
    


    

      Sub-features layer on top of the same shape rather than inventing a new one:
      provideHttpClient(withInterceptors([...])) is provideAnalytics's pattern with a second
      function — withInterceptors() — narrowing what the outer one installs.
    

  


  
  

    
The search

    
Where inject() actually looks.


    

      Every injector this page has used so far — component providers, a token's own factory,
      providedIn: 'root' — is one stop on a chain. inject(Token) starts at your component's
      own element injector and, if nothing there has a recipe, steps outward:
      to any route/environment injector wrapping it, then to root, then to platform. The first provider found, walking
      outward, wins.

Under the hood

    
What the four words are hiding.


    
    
      
  • 
        Tree-shakable vs explicit registration. providedIn: 'root' attaches the provider
        definition to the service class itself — a hidden static field the compiler generates — so if nothing ever
        inject()s it, the bundler drops the class entirely. Providers listed in a
        providers array are referenced directly by component metadata, so they're always included whether
        used or not.
      
    • 
      
  • 
        One instance per injector, cached — not one instance per app. A lazy-loaded route or a
        component that lists a provider gets its own cached instance the first time something in that subtree
        injects the token; it never sees the root instance. This is the exact mechanism behind
        providedIn: 'any''s per-route forking above.
      
    • 
      
  • 
        Resolution happens once, synchronously, at construction. DI isn't reactive —
        inject() runs during the injector's construction of that class, and the result is cached forever
        after. Registering a different provider later has no effect on instances Angular already built; only destroying
        and recreating the injector picks up the change.
      
    • 
      
  • 
        providers vs viewProviders. A plain providers entry is
        visible to a component's own template and to content projected via <ng-content>; a
        viewProviders entry is visible only to the component's own view.
        Advanced DI has the worked example.
      
    • 
      
  • 
        Circular references need forwardRef. A class referencing a token that isn't
        defined yet at that point in the module — two services injecting each other, or a token naming the class that
        will provide it — needs forwardRef(() => Token) so the reference resolves lazily.
        Advanced DI has the full NG_VALUE_ACCESSOR case where this is
        unavoidable.

Questions from the back row, in multiple choice

    
The trap that looks like "just to be safe."


    

      You already met this exact trap on the whiteboard at the top of the page — two providers: entries,
      two silent instances, zero errors. It's worth having cold before an exam anyway, along with two more:
    


    
    
      
  • 
        A second providers: [...] entry never merges with root's. It builds a second,
        independent instance for that one subtree — the single most common source of "why isn't my state shared?" bugs
        in real Angular code, and nothing about it throws, warns, or looks wrong at a glance.
      
    • 
      
  • 
        Injecting outside an injection context. inject() works in constructors, field
        initializers, factories and guards — not in an arbitrary callback like a setTimeout or a raw event
        listener. Capture the dependency in the constructor instead, or bridge in with
        runInInjectionContext() — Advanced DI shows the bridge.
      
    • 
      
  • 
        Read the first line of a NullInjectorError. It genuinely reads
        NullInjectorError: No provider for <YourToken>! — the exact scenario the injector described
        back in the mental-model section. That name is where to add a provider, not a clue to go hunting for.

Before you go

    
Seven things to remember.


    
    
      
  • 
        A provider is the instruction, not the dependency — useClass builds,
        useValue hands over, useFactory runs a function, useExisting aliases.
      
    • 
      
  • 
        useExisting shares one instance under two tokens; useClass under a
        second token builds a second, independent one — a live counter is the only way most people end
        up believing that the first time.
      
    • 
      
  • 
        useFactory needs no deps array at all once you call inject() inside it —
        and removing the array removes the untyped, positional matching that made deps risky.
      
    • 
      
  • 
        providedIn: 'root' is one instance app-wide; 'platform' is one per page;
        'any' is one per environment injector, so a lazy route can silently fork its own
        copy of something that looks like a singleton.
      
    • 
      
  • 
        makeEnvironmentProviders() packages a feature's providers behind a provideX() function
        — and its return type is deliberately incompatible with a component's own providers
        array, so the scope mistake is a compile error, not a runtime one.
      
    • 
      
  • 
        multi: true collects several providers under one token into an array — the same mechanism behind
        HTTP_INTERCEPTORS, NG_VALIDATORS, and provideAppInitializer()'s queue of
        startup work.
      
    • 
      
  • 
        Resolution walks outward from the injector nearest you and stops at the
        first match; the whole search happens once, at construction — registering a
        different provider later never touches an instance Angular already built.
