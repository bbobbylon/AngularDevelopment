ng-template & NgTemplateOutlet

<ng-template> declares a view blueprint that is never rendered on its own — you stamp it out on demand via NgTemplateOutlet. This is the primitive Angular itself uses for @if, @for, skeleton loaders, and every "bring-your-own-row" table/list component.

1 — Define once, render multiple times

<ng-template #greetTpl>
  <p>Hello from the blueprint!</p>
</ng-template>

<!-- Render the same template in two places -->
<ng-container [ngTemplateOutlet]="greetTpl" />
<ng-container [ngTemplateOutlet]="greetTpl" />

2 — Template context ($implicit + named keys)

Pass a context object to inject variables into the template. $implicit maps to the unnamed let-x; other keys need let-x="key". 

<ng-template #personRow let-p let-badge="badge">
  <strong>{{ '{{' }} p.name {{ '}}' }}</strong> — {{ '{{' }} p.role {{ '}}' }}
  @if (badge) { <span>{{ '{{' }} badge {{ '}}' }}</span> }
</ng-template>

@for (person of people(); track person.name) {
  <ng-container
    [ngTemplateOutlet]="personRow"
    [ngTemplateOutletContext]="{ $implicit: person, badge: person.role === 'Admin' ? '★' : '' }"
  />
}

3 — Signal-driven layout swap

Store which template to use in a signal. Switching the signal changes the outlet immediately — no @if duplication needed. 

protected readonly view = signal<'compact' | 'detailed'>('compact');

// Template
<ng-container [ngTemplateOutlet]="view() === 'compact' ? compactTpl : detailedTpl"
              [ngTemplateOutletContext]="{ $implicit: item }" />

4 — TemplateRef as a component input()

Pass a TemplateRef into a child component — the child controls where/when to render; the parent controls what. This is the pattern behind Angular Material tables, CDK overlays, and any "bring-your-own-template" API. 

@Component({
  selector: 'app-slot-host',
  imports: [NgTemplateOutlet],
  template: `
    <ng-container
      [ngTemplateOutlet]="template()"
      [ngTemplateOutletContext]="ctx()"
    />
  `,
})
export class SlotHost {
  template = input.required<TemplateRef<unknown>>();
  ctx      = input<Record<string, unknown>>({});
}

// Parent
<ng-template #myRow let-who="who">
  <p>Hello {{ '{{' }} who {{ '}}' }}!</p>
</ng-template>
<app-slot-host [template]="myRow" [ctx]="{ who: 'World' }" />

When to reach for each API

Pattern Use when
[ngTemplateOutlet] Reusing a snippet 2+ times in the same component
TemplateRef as input() Building library-style "shell" components (table rows, card bodies)
Signal-driven outlet swap Skeleton ↔ content, list ↔ grid, view ↔ edit toggles
ng-content (projection) Consumer supplies entire slot with no context variables needed
Prefer ng-content for simple slot injection; reach for TemplateRef when you need to render the template in a different context or at a different time than where it was defined.

Under the hood

  • TemplateRef is a compiled, uninstantiated view factory. <ng-template> compiles to a function that knows how to produce a view (nodes plus bindings) but produces nothing by itself — nothing exists in the DOM until a ViewContainerRef calls createEmbeddedView() on it.
  • NgTemplateOutlet is a thin wrapper around that call. Internally it holds a ViewContainerRef on its host and calls viewContainerRef.createEmbeddedView(templateRef, context); pointing [ngTemplateOutlet] at a different TemplateRef destroys the old embedded view and creates a new one from the new template.
  • The context object is passed by reference, not copied per key. [ngTemplateOutletContext] hands the whole object to the embedded view; let-x="key" reads context.key, and the bare let-x shorthand reads context.$implicit. Because it's the same object reference, mutating a property (instead of replacing the object) updates the render without recreating the view.
  • Swapping context is cheap; swapping the template isn't. When only the context object's identity changes and the TemplateRef stays the same, Angular doesn't recreate the embedded view — it re-runs change detection on the already-created view with the new context. Change the TemplateRef itself and the old view is destroyed and a new one built.
  • This is the exact primitive @if/@for compile down to. Built-in control-flow blocks are compiled into the same createEmbeddedView/ViewContainerRef machinery — NgTemplateOutlet just exposes that machinery at the template-author level instead of hiding it inside a compiled block.

Pitfalls that show up in exams & code review

  • Forgetting [ngTemplateOutletContext]. Without it, every let-x in the template resolves to undefined — the outlet still renders, just with empty variables.
  • Named context keys must match exactly. let-badge="badge" reads context.badge; typo the key on either side and you silently get undefined, not a compile error.
  • Only one unnamed let-x per template. The bare shorthand always binds to $implicit — you can't have two different unnamed variables pulling from two different context keys on the same template.
  • A falsy [ngTemplateOutlet] renders nothing. null/undefined is a valid "no template" value — handy for optional slots, but easy to mistake for a bug when it's really a typo'd template reference.
  • Passing a TemplateRef into a child doesn't render it. An input() of type TemplateRef just hands over the blueprint — the child still needs its own NgTemplateOutlet to stamp it out.

Key takeaways

  • <ng-template> is a DOM blueprint — invisible until stamped by an outlet.
  • [ngTemplateOutlet] renders it; [ngTemplateOutletContext] injects variables.
  • $implicit → bare let-x; named key → let-x="key".
  • Signal-driven template swapping replaces repeated @if blocks cleanly.
  • Pass TemplateRef as an input() to build customizable shell components.
  • viewChild<TemplateRef<unknown>>('ref') captures a template in TypeScript.
