<ng-template> declares a view blueprint that is never rendered where it's written — you stamp it out on demand via NgTemplateOutlet. This is the exact primitive Angular itself uses for @if, @for, skeleton loaders, and every "bring-your-own-row" table or list component you will ever build.

That is not a bug. <ng-template> is deliberately inert. Whatever is written inside one compiles into instructions for building a view — and instructions are not the thing itself. Somebody still has to carry them out.

If <ng-template> alone renders nothing, what does it actually take to make its contents show up — and how many times could you make that happen from the very same block? Hold a guess before you read on; there's a live check further down.

The mental model

An <ng-template> is a rubber stamp.

Picture a rubber stamp. It carries the whole design, and it leaves no mark on the page at all until someone presses it down. Writing an <ng-template> is carving the stamp: all the work of designing it is done, and none of the work of printing it has happened yet.

NgTemplateOutlet is the hand that presses. The context object is the ink you load before each press — same stamp, different result every time. And handing a TemplateRef to a child component is handing over your stamp so they decide where to press it, how many times, and with what ink — which is the entire basis of every "bring your own row" table component you have ever used.

A template is a stamp, not a mark. Context is the ink. If nothing appears, nobody pressed it; if the wrong thing appears, check the ink.

Loading the ink

Context is how the same stamp prints something different each time.

Pass a context object alongside the template, and its keys become variables inside it. $implicit maps to the unnamed let-x; anything else needs let-x="key" naming the key explicitly.

Live — same template, different context each render

{{ p.name }} {{ p.role }} @if (badge) { {{ badge }} }
@for (p of people(); track p.name) { }

Worth predicting

Swapping the ink is cheap. Swapping the stamp is not.

Store which template to use in a signal, and switching the signal changes the outlet immediately — no @if/@else duplication of the row markup needed.

{{ p.name }} · {{ p.role }}

One step further

Pass the TemplateRef itself into a child component.

A TemplateRef is a value like any other — nothing stops you handing it into a child component as an input(). The child then controls where and when to render; the parent still controls what. This is the pattern behind Angular Material tables, CDK overlays, and any "bring-your-own-template" API.

@if (vcTemplate()) { }

#vcTpl is captured with viewChild() rather than read directly by name — the third way to get hold of a TemplateRef, alongside a plain #ref and an input().

Pulling it together

Four ideas, one mechanism.

Written markup to nodes on the page, as a small glossary of the parts that make it happen:

A function that knows how to build a view — nodes plus bindings. It produces nothing by itself; nothing exists in the DOM until a ViewContainerRef calls createEmbeddedView() on it. Holds a ViewContainerRef on its host and calls viewContainerRef.createEmbeddedView(templateRef, context). Point it at a different TemplateRef and the old embedded view is destroyed; a new one is built from the new template. Handed to the embedded view whole, not copied per key. let-x="key" reads context.key; the bare let-x reads context.$implicit. Mutate a property — rather than replace the object — and the render updates with no view recreated at all. Only the context's identity changes and the TemplateRef stays put? Angular re-checks the already-created view with the new context — cheap. Change the TemplateRef itself and the old view is destroyed, a new one built — expensive.

Putting it to work

Which tool for which job?

The consumer hands you a finished chunk of markup, and you provide somewhere to put it. Rendered exactly once, exactly where declared, with no data of your own to feed it.

You get a blueprint, not a finished chunk — render it zero times, one time, or a hundred times, with data you supply through the context object, whenever you decide to.

Pattern Use when
[ngTemplateOutlet] Reusing a snippet 2+ times in the same component
TemplateRef as input() Building library-style "shell" components (table rows, card bodies)
Signal-driven outlet swap Skeleton ↔ content, list ↔ grid, view ↔ edit toggles
ng-content (projection) Consumer supplies entire slot with no context variables needed
Prefer ng-content for simple slot injection; reach for TemplateRef when you need to render the template in a different context or at a different time than where it was defined.

Traps that show up in exams and code review:

  • Forgetting [ngTemplateOutletContext]. Without it, every let-x in the template resolves to undefined — the outlet still renders, just with empty variables.
  • Named context keys must match exactly. let-badge="badge" reads context.badge; typo the key on either side and you silently get undefined, not a compile error.
  • Only one unnamed let-x per template. The bare shorthand always binds to $implicit — you can't have two different unnamed variables pulling from two different context keys on the same template.
  • A falsy [ngTemplateOutlet] renders nothing. null/undefined is a valid "no template" value — handy for optional slots, but easy to mistake for a bug when it's really a typo'd template reference.
  • Passing a TemplateRef into a child doesn't render it. An input() of type TemplateRef just hands over the blueprint — the child still needs its own NgTemplateOutlet to stamp it out.

Questions from the back row

Before you go

Things to remember.

  • <ng-template> is a blueprint — invisible until an outlet stamps it, and stamp-able as many times as you like or not at all.
  • [ngTemplateOutlet] presses the stamp; [ngTemplateOutletContext] loads the ink.
  • $implicit → bare let-x; named key → let-x="key", matched exactly.
  • Swapping context is cheap; swapping the template isn't. Same TemplateRef, new context shape → in-place update. Different TemplateRef → destroy and rebuild.
  • Three ways to get a TemplateRef: a #ref in the same template, an input() for shell components, or viewChild<TemplateRef<unknown>>('ref') in TypeScript.
