Custom Attribute Directives

Attribute directives attach behavior to an existing element — no template of their own, just host bindings and event listeners. They are the primitive behind NgClass, NgStyle, and every third-party UI library's interactive helpers. In Angular 17+ the patterns got cleaner: inject() replaces constructor injection, input() replaces @Input(), and host: {} in the decorator replaces @HostBinding.

The mental model: bolt-on accessories

A component is a vehicle — it has a body, a shape, an interior you designed. An attribute directive is a roof rack. It has no engine and no chassis of its own; it bolts onto a car somebody else built and gives that car an ability it did not have. On its own it is just a box of brackets.

Which explains the parts of the API that otherwise look arbitrary. Several racks fit the same car at once — unlike structural directives, you can stack as many attribute directives on one element as you like. The rack borrows the car's bodywork, which is what a host binding is: styling and listening on an element you do not own. And when the car is scrapped, the rack goes with it — but the trailer you left parked in the street does not. That trailer is the tooltip div you appended to document.body, and it is the one thing Angular cannot clean up for you.

A directive has no body of its own — it borrows the host's. Angular removes everything you attached to the host automatically. Anything you created somewhere else is yours to destroy in ngOnDestroy.

Modern directive anatomy

@Directive({
  // The SQUARE BRACKETS make this an attribute selector: it matches any
  // element carrying appHighlight. Drop them and you'd be matching a TAG
  // called appHighlight, which is a component's job, not a directive's.
  selector: '[appHighlight]',
  standalone: true,
  // host: {} replaces every @HostBinding — compiled away at build time
  host: {
    // Keys read exactly like template syntax: [property] binds, (event) listens.
    // The VALUE is an expression string evaluated against this directive
    // instance — which is why the double quotes are nested inside the single
    // ones here. Without them Angular would look for a field named
    // background-color.
    '[style.transition]': '"background-color .15s ease"',
    '[style.backgroundColor]': 'bg()',   // reads a signal
  },
})
export class HighlightDirective {
  // signal input — replaces @Input(). The name of the field IS the attribute
  // name, so <div appHighlight="red"> feeds this. The argument is the
  // fallback used when the attribute is present but empty.
  appHighlight = input<string>('var(--amber)');
  // Internal state. protected, because only this class and its host bindings
  // need it — nothing outside should be able to set the colour directly.
  protected readonly bg = signal('');

  // @HostListener wires a DOM event on the HOST element to a method. Angular
  // removes the listener automatically when the directive is destroyed —
  // that automatic cleanup is exactly what a manual addEventListener lacks.
  // Setting bg() here is all it takes: the host binding above is watching it,
  // so the style updates with no direct DOM manipulation anywhere.
  @HostListener('mouseenter') onEnter() { this.bg.set(this.appHighlight()); }
  // Reset to '' rather than a colour, so the element falls back to whatever
  // the stylesheet says instead of being locked to a hardcoded default.
  @HostListener('mouseleave') onLeave() { this.bg.set(''); }
}

Three modern patterns in one directive:

  • host: {} — property/event bindings in the decorator metadata. No @HostBinding needed. Angular compiles these directly into the directive's change-detection code — faster than decorators at runtime.
  • input() — signal-based, typed, readonly. Reading it inside host bindings or effect() creates reactive dependencies automatically.
  • inject() in the constructor body or as a field initialiser — replaces constructor parameter injection. Same DI resolution, cleaner code.

The life of a directive instance

Injecting ElementRef and Renderer2

When you need to read or modify the host element directly, inject ElementRef and Renderer2. Use Renderer2 rather than touching .nativeElement directly — it stays compatible with SSR and Web Workers. 

private readonly el = inject<ElementRef<HTMLElement>>(ElementRef);
private readonly renderer = inject(Renderer2);

// Add a CSS class safely across all platforms:
this.renderer.addClass(this.el.nativeElement, 'is-active');

// Set an inline style:
this.renderer.setStyle(this.el.nativeElement, 'color', 'red');

// Create and append a child element:
const tip = this.renderer.createElement('span');
this.renderer.setProperty(tip, 'textContent', 'Hello');
this.renderer.appendChild(this.el.nativeElement, tip);

exportAs — access directive from the template

Set exportAs in the decorator to give the template a reference to the directive instance. Useful for calling directive methods from the parent. 

@Directive({
  selector: '[appBadge]',
  exportAs: 'appBadge',   // ← the alias
})
export class BadgeDirective {
  label = input<string>('New');
  active = signal(true);
  toggle() { this.active.update(v => !v); }
}

// Template — grab the directive instance via #b="appBadge"
<span appBadge label="Beta" #b="appBadge"></span>
<button (click)="b.toggle()">Toggle badge</button>

Real-world: tooltip directive

The app-wide tooltip in this platform (shared/tooltip.directive.ts) is an attribute directive. It dynamically appends a floating div to document.body, positions it via getBoundingClientRect(), and cleans up in ngOnDestroy. 

@Directive({ selector: '[appTooltip]', standalone: true })
export class TooltipDirective implements OnDestroy {
  // alias lets the FIELD be called `text` (readable inside the class) while
  // the ATTRIBUTE stays `appTooltip` (readable in the template). Without it
  // you'd have to name the field appTooltip too.
  text = input<string>('', { alias: 'appTooltip' });

  // ElementRef wraps the host DOM node. The generic tells TypeScript it's an
  // HTMLElement, so .nativeElement.getBoundingClientRect() type-checks.
  private readonly el     = inject<ElementRef<HTMLElement>>(ElementRef);
  // Renderer2 instead of document.createElement: it's an abstraction over the
  // DOM, so the same directive works during server-side rendering and inside
  // a web worker, where `document` doesn't exist.
  private readonly renderer = inject(Renderer2);
  // The handle on what we created. Null when no tooltip is showing — this
  // field is the entire cleanup story, so it must stay accurate.
  private tip: HTMLElement | null = null;

  @HostListener('mouseenter') show(): void {
    this.tip = this.renderer.createElement('div');
    this.renderer.addClass(this.tip, 'app-tooltip');
    // setProperty with 'textContent', not innerHTML — text can never be
    // parsed as markup, so a tooltip string can't inject a script.
    this.renderer.setProperty(this.tip, 'textContent', this.text());
    // Appended to document.body, NOT to the host. Deliberate: a tooltip
    // nested inside the host would be clipped by any ancestor with
    // overflow:hidden, and would inherit its stacking context.
    this.renderer.appendChild(document.body, this.tip);
    // position relative to host bounding box…
  }

  @HostListener('mouseleave') hide(): void {
    // The guard makes hide() idempotent, which is what lets ngOnDestroy call
    // it blindly below.
    if (this.tip) {
      this.renderer.removeChild(document.body, this.tip);
      // Reset the handle, or a second hide() would try to remove a node that
      // is no longer in the document.
      this.tip = null;
    }
  }

  // THE LINE THAT MATTERS. Angular cleans up host listeners and host bindings
  // for you — but this tooltip lives on document.body, outside the directive's
  // view. Navigate away mid-hover without this and the tooltip is orphaned on
  // screen forever. Rule: whatever YOU created, YOU destroy.
  ngOnDestroy(): void { this.hide(); }
}

Old patterns vs. modern equivalents

Old pattern Modern Angular 17+ equivalent
@Input() color = '' color = input<string>('')
@HostBinding('class.active') isActive host: { '[class.active]': 'isActive()' }
constructor(private el: ElementRef) {} private el = inject(ElementRef)
@Input('appTooltip') text (alias) text = input('', { alias: 'appTooltip' })
Manually implement OnChanges to watch inputs effect(() => { /* reads input() signals reactively */ })
When to use host: {} vs @HostBinding: host: {} is resolved at compile time and optimised — prefer it for all new directives. @HostBinding / @HostListener still work and may be clearer for simple cases.
Never write to el.nativeElement in a loop without Renderer2 — raw DOM access breaks SSR and makes tests harder. Renderer2 methods are always safe.

Key takeaways

  • @Directive with an attribute selector adds behaviour to any existing element — no template.
  • host: {} in the decorator replaces @HostBinding and is more efficient.
  • input() replaces @Input() — signal-based, reactive, readonly in the directive.
  • inject() replaces constructor param injection — works in the constructor body or as a field initializer.
  • exportAs lets the parent template call methods on the directive instance.
  • Always clean up created DOM and subscriptions in ngOnDestroy.
