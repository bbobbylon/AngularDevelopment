An attribute directive is a component with no view of its own — no template, just a set of instructions for decorating whatever element it lands on. It's the mechanism behind NgClass, NgStyle, and every hover/focus/drag helper any UI library has ever shipped. This page builds three real ones — a hover highlight, a badge you can reach from the template, and a tooltip that creates its own DOM — because the third one is where the interesting bug lives.

A directive has no view of its own to clean up — which is exactly why the one thing it creates somewhere else never gets cleaned up for it.

Angular is meticulous about tearing down anything it wired for you. It has no idea what you built by hand. Here's every question that gap leaves behind, answered before you hit it live.

A real roof rack only ever touches the car it's bolted to — tow the car away and the rack goes with it, no cleanup required. A directive isn't limited that way: it can reach past its own host and drop something somewhere else in the document entirely, the way a trailer gets left parked on a street corner. Angular will happily tow away the car — the host element — and every rack bolted to it. It has no idea the trailer back on that corner was ever connected to this directive at all.

The problem

A directive and a component are declared almost identically. What's actually different?

@Component and @Directive are both decorators on a class. Both can take inputs, both can be injected into, both go through the exact same dependency-injection machinery. Strip away the template and — that's it. That's the whole difference. A component paints something with a shape of its own. A directive attaches to a shape somebody else already painted.

That thin difference has consequences that look arbitrary until you've thought them through.

Three quick guesses about an attribute directive, before the mechanism explains them. Does it render any markup of its own? Can more than one of them sit on the exact same element at once? And if one of them creates a DOM node with renderer.createElement() while it's active, does destroying the host element clean that node up along with it? Two of your answers are probably the ones you'd expect. One of them is the trap this whole lesson is built around — there's a live version of exactly that trap further down the page.

The mental model

A directive is a roof rack, not a car.

A component is a vehicle — it has a body, a shape, an interior you designed. An attribute directive is a roof rack. It has no engine and no chassis of its own; it bolts onto a car somebody else built and gives that car an ability it didn't have. On its own it's just a box of brackets.

Which answers the first two guesses you just made. Several racks fit the same car at once — you can stack as many attribute directives on one element as you like, which is the sharpest difference from a structural directive, where the star allows exactly one. And the rack borrows the car's bodywork, which is what a host binding actually is: styling and listening on an element you don't own.

The third guess doesn't fall out of the analogy for free — because a real roof rack can't leave a trailer parked in the street. A directive can. That trailer is the tooltip div you append to document.body, and it's the one thing Angular cannot clean up for you. Hold onto that; it comes back.

A directive has no body of its own — it borrows the host's. Angular removes everything you attached to the host automatically. Anything you created somewhere else is yours to destroy in ngOnDestroy.

The mechanism

Anatomy of a modern attribute directive.

Three things changed about how you'd write this in Angular 17+: inject() replaces constructor injection, input() replaces @Input(), and the host object in the decorator replaces @HostBinding. Here's HighlightDirective in full — every line is doing something, so read the numbered notes rather than skimming.

Property and event bindings, written once, compiled straight into the directive's update function. No @HostBinding or @HostListener decorator required. Typed, readonly, and reactive by default — read it inside a host binding or an effect() and the dependency is tracked for you. Same DI resolution as a constructor parameter, usable as a field initialiser — which is what lets @HostListener stay a plain method instead of forcing everything through the constructor.

Reaching into the DOM

Injecting ElementRef and Renderer2.

Host bindings cover most of what a directive needs to do to its own element. When you need to go further — add a class conditionally in code, create a node — inject ElementRef for a handle to the host and use Renderer2 instead of touching .nativeElement directly. Renderer2 is an abstraction over whatever is actually drawing the page right now, which is what keeps a directive working under server-side rendering, where there is no document at all.

Talking back to the template

exportAs — grabbing the directive instance from the template.

Every example so far has been one-directional: the directive reacts to the host, and the template never touches the directive back. exportAs breaks that — it names the directive instance so a template reference variable can grab it directly, the same way #form="ngForm" grabs Angular's own form directive.

Pulling it together

The rest of the old-to-new mapping.

The three biggest swaps got their own comparison above. The rest are smaller, one-line trades:

Old pattern → modern equivalent
Old pattern Modern equivalent
@Input('appTooltip') text (alias) text = input('', { alias: 'appTooltip' })
constructor(private el: ElementRef) {} private el = inject(ElementRef)
Manually implement OnChanges to watch inputs effect(() => { /* reads input() signals reactively */ })
When to reach for host: {} vs the old decorators: always, for new code — it's resolved at compile time and is the modern default. The old decorators still work, and you'll still meet them reading existing codebases.
Never write to el.nativeElement in a loop without Renderer2 — raw DOM access breaks SSR and makes a directive harder to test. Renderer2's methods are always safe.

Questions from the back row

Before you go

Things to remember.

  • A directive is a component with no view of its own — it borrows the host's.
  • host: {} in the decorator replaces @HostBinding/@HostListener, compiled straight into the element's own update function.
  • input() replaces @Input() — signal-based, reactive, readonly inside the directive.
  • Attribute directives stack — as many as you like on one element. Structural directives don't: one * per element, full stop.
  • exportAs lets a template reference variable grab the directive instance directly.
  • Whatever you create outside the host, you must destroy yourself. Host bindings and listeners clean up automatically; anything appended to document.body does not.
