Guards are the yes/no checkpoints a navigation has to clear before Angular lets it happen — and a modern guard is nothing more than a plain function. Each one inject()s whatever it needs and returns boolean, a UrlTree/RedirectCommand (redirect instead), or an Observable/Promise of either. This page walks the whole checkpoint line in the order a real navigation actually clears it.

The problem

Can your app actually say no to a navigation?

Click a link in Angular and, left alone, nothing stops it: the router matches a URL, builds a component, and puts it on screen. If a page has to stay behind a login, or a form shouldn't be abandoned with unsaved changes, something has to be able to interrupt that process before it finishes. A guard is exactly that — a function the router asks a yes/no question at a specific moment, with the power to cancel the whole thing or send it somewhere else instead.

A route guard for /admin returns false. Does the browser's address bar change? Now imagine it returns a UrlTree pointing at /login instead — does the address bar change then? The two answers are not the same, and the reason why is most of the first half of this page.

The mental model

Angular's guards are an airport security line.

Picture a single line strung between where you are and where you're trying to go, with four checkpoints on it — and, crucially, each one is asked at a different moment, not all at once.

CanMatch is the departures board. Before you've walked anywhere, it decides whether a gate for your flight is even listed — if your ticket doesn't clear it, the destination was never announced, not denied. CanActivate is the ID check at the gate: you've already walked all the way there (the chunk is downloaded), and now someone checks whether you, specifically, may go through. CanActivateChild is that same ID check, posted once at the entrance to a whole terminal and re-applied at every gate inside it. CanDeactivate is customs on your way out — before the airport even looks at where you're headed next, it checks whether you're trying to leave your current spot with something undeclared, like a form full of unsaved changes.

In code, every one of those checkpoints is the exact same shape: a function typed CanActivateFn, CanMatchFn, CanActivateChildFn or CanDeactivateFn, returning boolean (yes/no), a UrlTree (go here instead), or an Observable/Promise of either when the checkpoint needs to ask someone first.

Leave, then match, then enter. Every guard question is really "which of these three checkpoints failed?" CanDeactivate always runs first, on the OLD route — before the router has even decided whether the new one exists.

The mechanism

One guard is one function that answers one question.

No classes, no decorators, no lifecycle to implement — a guard is a plain function the router calls at the right moment and reads a return value from. Here's the classic one: does the current user get into /admin?

Four guard types exist, and every one of them shares that exact shape. What changes between them is only when the router asks the question — mapped here onto the checkpoints from the analogy above:

Checked while the router is still matching a URL to a route — before any lazy chunk downloads. A false doesn't cancel anything; the router just tries the next route registered at the same path. The route already matched — its chunk is downloaded either way. This asks whether THIS user, specifically, may enter it. A false cancels the navigation outright. Declared once on a parent route, but Angular re-asks it for every matched child beneath that parent — one guard protecting a whole section. Checked on the route you're LEAVING, before the router has looked at the destination at all. The only guard type that receives your live component instance.
Learn that one return-value contract once and you've learned all four guard types. The only real differences are when each one is asked, and — for CanDeactivate — the extra argument it receives.

Does a route even exist for this URL, for this user?

The route matches regardless of the flag. Its lazy chunk downloads before the guard is even consulted. If the flag is off, the download already happened for a user who was never getting in — bytes spent on nothing.

canMatch runs during matching. If the flag is off, this Route object is never selected — the import() behind loadComponent never executes, and the router simply tries the next Route registered at the same path.

Every guard type accepts the exact same union of return values. The type you pick changes what happens next:

The whole return-value menu — shared by every guard type
Return Meaning Example
true Allow navigation to proceed exactly as requested. return true;
false Block navigation outright — no redirect, no message, just cancelled. return false;
UrlTree Cancel this navigation and atomically start a new one at the given URL. return router.createUrlTree(['/login']);
RedirectCommand Same redirect behaviour as UrlTree, but also lets you pass navigation options (e.g. skipLocationChange). return new RedirectCommand(router.parseUrl('/login'));
Observable<...> Any of the above, resolved asynchronously. The router takes the FIRST emitted value and unsubscribes — the source must complete or navigation hangs. return this.auth.isLoggedIn$.pipe(first());
Promise<...> Same async contract as an Observable, resolved once. return firstValueFrom(this.http.get('/api/check'));
Return the redirect, don't drive it. A guard hands the router a UrlTree and lets the router act on it as one atomic decision. Calling router.navigate() yourself starts a second, independent navigation that races the one already in flight.

Checkpoint 3 of 3 · leaving

Before any of that — were you even allowed to leave where you were?

This checkpoint is numbered third here because it's the one people forget, but remember the mnemonic above: CanDeactivate actually runs first, chronologically, on every real navigation — the router has to know you can leave before it spends any effort on where you're going.

The gap in checkpoint 3

Reload the tab, and CanDeactivate never gets asked at all.

CanDeactivate only fires when the router is the thing driving the navigation away. A hard reload, closing the tab, or typing a fresh URL into the address bar all leave the page a completely different way — the router is never consulted, so the guard never runs, unsaved changes and all.

Pair the two: CanDeactivate for in-app navigation, beforeunload for everything that bypasses the router. Note the browser's dialog is generic and non-negotiable — you get to trigger it, not word it.

A second, unrelated gap in the same checkpoint: pressing the Back button can trigger a popstate navigation that CanDeactivate then cancels — and by default, the router can't always restore the address bar to the exact entry it was on before that Back-press, leaving the URL and the screen briefly disagreeing about where you actually are.

Pulling it together

Three checkpoints, one shared answer shape.

What a false or a redirect actually does, checkpoint by checkpoint
Checkpoint A false result A UrlTree / RedirectCommand result
CanDeactivate — leaving Navigation is cancelled — you stay exactly where you were. Cancelled, then a new navigation starts at the returned URL instead.
CanMatch — matching This Route is skipped; the router tries the next Route at the same path. The same atomic redirect as any other guard — though most canMatch guards only ever return a plain boolean.
CanActivate / CanActivateChild — entering Navigation is cancelled outright. Cancelled, then a new navigation starts at the returned URL instead.
A guard on a parent route does not automatically protect its children. canActivate: [authGuard] on /admin only ever runs for /admin itself — a child like /admin/settings activates completely unguarded unless the parent also declares canActivateChild (or every child repeats its own canActivate). There is no error or warning when this is forgotten.

A security bug, not a convenience issue

Does a parent's canActivate re-run when you move between its children?

canActivate: [adminGuard] on /admin runs once, the moment the subtree is first entered — clicking from one already-active child to a sibling, like /admin/users → /admin/settings, reuses the same parent route node, and a plain canActivate on that parent is never asked again. canActivateChild, declared on the exact same parent, fires for every child activation instead. That's the entire difference: "may you enter this subtree" versus "may you enter each screen inside it" — and a session that expires mid-visit, or a permission that's per-child, is only ever re-checked by the second one.

Exam corner

Five ways this bites people in real code and in exams.

  • navigate() inside a guard. Return a UrlTree/RedirectCommand instead — imperative navigation races the in-flight one, exactly as the predict box above demonstrated.
  • Guarding a lazy route's download. canActivate fetches the chunk first, then denies. Use canMatch to skip the download entirely.
  • Assuming a parent's canActivate covers its children. It never does — that's what canActivateChild is for, and forgetting it fails silently.
  • An async guard that never completes. Like resolvers, an Observable guard must emit and complete, or navigation hangs forever — pipe first().
  • Calling inject() asynchronously inside a guard. It only works synchronously at the top of the function, before any await/.then()/setTimeout — the injection context is gone by then.

Questions from the back row

Before you go

Five things to remember.

  • Guards are functions returning boolean | UrlTree | RedirectCommand — or an Observable/Promise of any of those. All four guard types share this exact contract.
  • Order in one navigation: CanDeactivate (old route) → CanMatch → CanActivate → CanActivateChild → resolvers → activate. The route you're leaving is checked before the router has looked at where you're going.
  • Return the redirect, don't drive it. A UrlTree/RedirectCommand is one atomic decision the router acts on; calling router.navigate() inside a guard starts a second, racing navigation.
  • canMatch decides before the lazy chunk downloads; canActivate decides after. A false canMatch quietly tries the next route at the same path — a false canActivate cancels the navigation outright.
  • canActivate on a parent does not protect its children on its own — canActivateChild is what closes that gap. And inject() inside any guard only works synchronously, before the first await.
