An operator is a function that takes a stream and returns a brand-new one — never the same stream, never mutated. Chain them inside .pipe(...) and you've built an assembly line: each operator does one job to the values flowing through, then hands its output to the next. This page is about picking the right operators for a real interface — a search box — and about the one choice that actually causes production bugs: what to do when a new value arrives while the last one is still being handled.

The problem

Type "angular" into a search box. How many network requests should that cause?

A raw DOM (input) event fires once per keystroke — no waiting, no judgment, no memory of what you searched a moment ago. Wire it straight to this.api.search(value) and typing a seven-letter word fires seven separate HTTP requests, most of them for a query you'd already moved past by the time the response came back. And if the third response happens to arrive after the seventh, the box briefly shows results for "ang" long after you've typed "angular".

None of that is a bug in the browser or in HTTP. It's what happens when nothing stands between the event and the request. Operators are that something — and the four you're about to meet exist entirely to answer one question: what happens when a new value shows up before the last one finished being handled?

Of those seven keystroke-triggered requests, how many results should the user actually see land in the box, if you did nothing else at all? There's a live version of this exact scenario further down this page — count the real number against your guess.

The mental model

Every operator is a small machine bolted onto a conveyor belt.

.pipe(...) is the belt. Each operator you place on it is a machine with exactly one job — transform a value, drop one, wait, count — and each machine's output becomes the next machine's input. A value shows up at one end and comes out the other, machine by machine, in the order you wrote them: 

{{ assemblyLineSample }}

Two things about this belt are easy to say and easy to forget. First, the source is never touched — every operator, from map to the four you're about to meet, returns a brand-new Observable and leaves the one it was given alone. Second, the belt doesn't run itself: wiring up ten machines builds the machinery but moves nothing. Nothing happens until something calls .subscribe() at the far end and starts pulling values through.

An operator's whole contract is one input stream in, one new stream out. The moment you find yourself mutating the source, or reaching outside the pipe to fire a side effect that has to happen exactly once, you've stepped outside what an operator is for.

The mental model, continued

Four of those machines are receptionists, and the belt just handed them a second phone call.

The hardest — and most useful — operators handle a stream whose values each start another stream: a keystroke that triggers an HTTP call, a click that triggers a save. Call that inner stream "the phone call." The moment a receptionist is already on one call and a second one rings, there are exactly four sensible policies — and RxJS ships one operator per policy:

Cancels the in-flight inner stream and starts the new one. Rude — and exactly right when the old conversation is now pointless. Nobody wants search results for a query you've already finished typing. Starts the new inner stream without touching the old one — every call runs concurrently. Fast, and fine exactly when the calls have nothing to do with each other. Queues the new inner stream behind whichever one is still running. Slowest of the four — and the only one that guarantees the order they arrived in. Ignores the new value entirely while the current inner stream is still running. The one you want on a submit button — a second, impatient click is simply not answered.
Reads want switchMap. Writes never do. Cancelling a stale search is a feature; cancelling a half-finished save is data loss. When the values represent something the server should keep, reach for concatMap or mergeMap.

Same four policies, as a quick reference
Operator What it does
switchMap Cancel the previous inner stream when a new value arrives. Type-ahead search — you only want results for the latest query.
mergeMap Run all inner streams concurrently. Independent writes (e.g. save several items at once).
concatMap Queue inner streams in order, one completing before the next starts. Order-sensitive work.
exhaustMap Ignore new values while one is in flight. Submit buttons — block double-submits.

In practice you never weigh all four. You ask these in order and stop at the first yes:

Questions from the back row

Before you go

Five things to remember.

  • Operators chain in .pipe(); each returns a new Observable, never mutating the source. Nothing runs until something .subscribe()s.
  • Daily drivers: map, filter, tap, debounceTime, distinctUntilChanged, take, scan, startWith.
  • Flatten nested streams with the four receptionists — switchMap/mergeMap/concatMap/exhaustMap — the choice is about what happens to the call still in progress.
  • Reads want switchMap. Writes never do. Type-ahead → switchMap; parallel writes → mergeMap; ordered → concatMap; submit → exhaustMap.
  • catchError belongs on the inner observable, inside the flattening callback — on the outer stream it terminates the whole pipeline instead of just one failed request.
