"I built you a brand-new HttpParams," says .set(). "I'm still holding the old one," says the signal.

You call demoParams().set('sort', 'desc') right before rendering the URL. HttpParams builds a new object, correctly, with sort=desc inside it. And demoParams, the signal on screen, is still holding the exact object it had a moment ago — no sort anywhere.

Immutable isn't broken — it's a method that returns a new value instead of changing the old one, and a return value nobody captures simply evaporates. The bug was never inside .set(). It was in discarding what .set() handed back.

A photocopier makes a corrected copy of a page and hands it to you — it never edits the original sitting in the tray. Walk away without taking the copy, and the original in the tray is exactly what it always was. That's every HttpParams method: a photocopier, never an eraser.
The four write verbs below all share one shape: (url, body, options?). GET and DELETE don't — they drop the body and take options as the second argument instead. Swap one for the other and TypeScript (or a runtime 400) will tell you, but only after you've made the mistake once.

The verbs with bodies, params & headers

Every verb is one method call — the differences that matter are all in the signature, not the mechanics:

HttpParams and HttpHeaders behave the same way that a plain string does, not like an array or object: every method that looks mutating — .set(), .append() — actually leaves the original alone and hands you back a brand-new instance instead. Think of 'abc'.toUpperCase(): it doesn't rewrite 'abc', it returns 'ABC' for you to keep. Forget to keep the return value and the change simply never happened — no error, no warning, just silence. You just watched this exact argument play out at the top of the page — HttpParams and its own signal, both correct, and a return value that nobody kept.

HttpParams methods return, they don't mutate. If a .set() call isn't on the right-hand side of an assignment (or inside a signal.update()), it did nothing.

Anatomy of an HttpErrorResponse — status 0 isn't a real status

err.status and err.error mean two completely different things depending on where the request failed. A 404 from jsonplaceholder and a request to a host that doesn't resolve both land in the same catchError — but their fields tell very different stories:

Live — trigger each kind and inspect the raw fields

@if (errorAnatomy(); as e) {

status: {{ e.status }}

statusText: {{ e.statusText }}

error: {{ e.error | json }}

message: {{ e.message }}

}
  • status is the ACTUAL HTTP status the server sent back — 404, 500, whatever it chose to respond with.
  • error is the response body, parsed as JSON automatically when the Content-Type says so — a plain object (or array, or string) you can read fields off of.
  • status is always 0 — DNS failure, CORS block, offline, timeout: anything that never produced a response to have a status.
  • error is not a server body here — it's a client-side ProgressEvent (XHR transport) or the underlying TypeError (fetch transport, which this app uses). Reading error.message expecting server-authored text is the bug.
Branching only on err.status === 404 (or any specific code) without also handling 0 is the trap. Code that only checks for known server status codes silently mishandles "no network at all" as if some server had answered. Treat status === 0 as its own case — "the request never completed" — before trusting anything inside error.

Typed responses & options

Build query strings with HttpParams (immutable — each set returns a new instance, proved above). Set headers with HttpHeaders or a plain object. Cross-cutting headers (auth) belong in an interceptor, not every call.
Other useful options: withCredentials: true sends cookies cross-origin; reportProgress: true with observe: 'events' streams upload/download progress; and RxJS operators like retry({{ '{' }} count: 2 {{ '}' }}) and timeout(5000) add resilience around flaky networks. Because the result is an Observable, nothing is sent until you subscribe — and unsubscribing (or a switchMap switching away) aborts the request.

Under the hood — the request pipeline

http.get(...) doesn't send anything by itself. It returns a cold Observable: the request only fires when you subscribe() (the async pipe and toSignal subscribe for you). Each subscription is an independent request — subscribe twice and you make two calls; that's why shareReplay() is used to cache a single response for many consumers.

  • Nothing works without provideHttpClient(). It must be registered once in your app config (this app also passes withFetch(), switching the transport from XMLHttpRequest to the native fetch API) before inject(HttpClient) resolves anywhere — forgetting it throws a "no provider" DI error at the injection site, not at the call site.
  • Cancellable. Unsubscribing (or a switchMap switching away) aborts the in-flight HTTP request. This is a real advantage over Promises, which can't be cancelled.
  • Errors are notifications, not exceptions. A non-2xx response pushes an HttpErrorResponse through the Observable's error channel — handle it with catchError or the subscribe error callback, never a try/catch (HttpClient never throws synchronously).

Pitfalls that show up in exams & code review

  • Body vs options argument order. Write verbs take (url, body, options); GET/DELETE take (url, options) — easy to pass options where the body goes.
  • No error handling on writes. A failed POST/PUT should surface; a catchError that quietly returns a fake success value hides real data loss from the user.
  • Per-call auth headers. Cross-cutting headers belong in an interceptor, not repeated at every call site.
  • Forgetting provideHttpClient(). Without it, inject(HttpClient) throws a NullInjectorError — a startup crash, not a network failure, so don't go debugging CORS first.
  • Unguarded double-submits. A second click before the first POST resolves fires a second, independent request — no built-in de-duplication. Disable the button, or route the click stream through exhaustMap to ignore clicks while one is already in flight.

Key takeaways

  • Each verb is one method; write verbs take (url, body, options?), GET/DELETE take (url, options?) — no body slot.
  • Type responses with the generic; use observe: 'response' for headers/status, responseType for non-JSON bodies.
  • Use HttpParams/HttpHeaders for query strings & headers — both immutable, both require capturing the return value.
  • Always handle errors (catchError, which runs on the error channel, not a try/catch) on write operations.
  • provideHttpClient() is a hard prerequisite — its absence fails at injection, not at the network call.
