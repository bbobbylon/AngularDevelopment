HttpClient CRUD

Beyond GET, HttpClient handles POST/PUT/PATCH/DELETE, request bodies, headers, query params and typed responses. Every button below fires a real network request against a public fake-REST API (jsonplaceholder echoes writes back without actually persisting them, so it's safe to hammer). Read the code, then watch it happen.

The verbs with bodies, params & headers

The four write verbs all share one shape — (url, body, options?) — while GET and DELETE drop the body and take options as the second argument instead. That asymmetry trips people up constantly, so it's the first thing to internalize: 

{{ verbsSample }}

Line-by-line

Line What it does & why
http.post<Post>(url, body) POST creates a new resource. body is a plain positional argument (Angular serializes an object body to JSON automatically), and the generic <Post> types what the server hands back — not what you sent.
http.put<Post>(`${url}/${id}`, body) PUT replaces the whole resource at that URL. The id lives in the URL path (REST convention), never in the body. Send a partial body here and any field you omitted can be wiped server-side.
http.patch<Post>(`${url}/${id}`, partial) PATCH sends only the fields that changed; the server merges them into the existing record instead of overwriting it. This is the safe choice for "update one field" — see the exam pitfall below on PUT vs PATCH.
http.delete<void>(`${url}/${id}`) DELETE takes no body at all — the URL alone identifies what to remove. The <void> generic types the (usually empty) response.
http.get<Post[]>(url, { …options… }) GET and DELETE have no body argument, so the options object slides into the second parameter slot instead of the third — swap this with a write verb's signature and TypeScript (or a runtime 400) will tell you fast.
params: new HttpParams().set('userId', 1) Builds a query string (?userId=1) without hand-concatenating and URL-encoding strings yourself. Covered in depth — including its sharpest edge — two sections down.
headers: { Authorization: 'Bearer …' } Attaches a header to this call only. Fine for a one-off, but if every request needs the same auth header, that belongs in an interceptor — see the pitfall on per-call auth headers below.

What the demo buttons actually call

Every button funnels through one private run() helper so the loading/error bookkeeping only has to be written once: 

{{ demoSourceSample }}

Line-by-line

Line What it does & why
action.set(label) / status.set('loading') Two plain signals driving the UI's "last:" and "status:" pills. Setting them before subscribing means the "loading" state shows up immediately, not after the network round-trip.
isError.set(false) Resets the error flag from any previous call so a fresh request doesn't still show the last request's failure pill while it's in flight.
obs$.pipe(catchError((err: HttpErrorResponse) => { … })) catchError intercepts the Observable's error channel — the only place a non-2xx HTTP response shows up, since HttpClient never throws synchronously. err is typed HttpErrorResponse, giving you .status/.message instead of unknown.
isError.set(true); return of({ error: true, … }) Flags the failure for the UI, then returns a replacement Observable (of(...)) so the pipeline completes normally with a fallback value instead of propagating the error further and killing the subscription.
.subscribe((res) => { response.set(res); status.set('done'); }) Nothing is sent over the network until .subscribe() is called — HttpClient Observables are cold. This one callback handles both the real success path and the catchError fallback, since both now flow through the same "next" channel.
this.run('GET /posts/1', this.http.get<Post>(`${API}/1`)) A caller method's whole job is: build the request (URL, body, options) and hand the resulting Observable to run() with a human-readable label — no duplicated loading/error logic per verb.

HttpParams is immutable — see the bug happen live

HttpParams (and HttpHeaders) behave like strings or numbers, not like arrays or plain objects: every mutating-looking method returns a new instance and leaves the original untouched. Forgetting to capture that return value is one of the most common silent bugs in Angular HTTP code — silent because nothing throws, the request just quietly goes out without the param you thought you added.

Click "wrong way" a few times: the query string above never grows a sort param, because .set() built a brand-new HttpParams that the button then threw away. Click "right way" and it appears instantly, because that handler reassigns the signal to the new instance. 

{{ paramsImmutableSample }}

Line-by-line

Line What it does & why
this.demoParams().set('sort', 'desc'); Calling the signal (demoParams()) reads its current value, then .set() on that value builds and returns a new HttpParams — but the expression's result isn't assigned anywhere, so it's discarded and the signal's stored value never changes.
this.demoParams.update((p) => p.set('sort', 'desc')); signal.update() is exactly the missing step: it reads the current value, runs your callback, and writes the callback's return value back into the signal — completing the "build a new instance, then store it" cycle that HttpParams requires.
this.demoParams.set(this.demoParams().set('sort', 'desc')); The same fix spelled out manually, without .update()'s sugar: read the current params, call .set() to get the new instance, then hand that instance to signal.set() explicitly.

Typed responses & options

{{ typedOptionsSample }}

Line-by-line

Line What it does & why
http.get<Post>(url, { observe: 'response' }) By default the Observable emits just the decoded body. observe: 'response' changes what it emits to a full HttpResponse<Post> wrapper — same request, richer emission.
.subscribe((res) => { res.status; res.headers; res.body; }) Now res carries .status (the numeric HTTP status code), .headers (an HttpHeaders instance you can .get('X-Foo') on), and .body (your actual Post) — instead of just the bare body.
http.get(url, { responseType: 'text' }) Tells HttpClient not to JSON.parse the response. Skip this for a non-JSON payload (plain text, CSV, an XML feed) and body parsing throws, turning a perfectly good 200 into an error your code has to catch.
http.get(url, { observe: 'response', responseType: 'text' }) The two options are completely independent and compose freely — full envelope and raw text body in the same call.
Build query strings with HttpParams (immutable — each set returns a new instance, proved above). Set headers with HttpHeaders or a plain object. Cross-cutting headers (auth) belong in an interceptor, not every call.
Other useful options: withCredentials: true sends cookies cross-origin; reportProgress: true with observe: 'events' streams upload/download progress; and RxJS operators like retry({{ '{' }} count: 2 {{ '}' }}) and timeout(5000) add resilience around flaky networks. Because the result is an Observable, nothing is sent until you subscribe — and unsubscribing (or a switchMap switching away) aborts the request.

Under the hood — the request pipeline

http.get(...) doesn't send anything by itself. It returns a cold Observable: the request only fires when you subscribe() (the async pipe and toSignal subscribe for you). Each subscription is an independent request — subscribe twice and you make two calls; that's why shareReplay() is used to cache a single response for many consumers.

  • Nothing works without provideHttpClient(). It must be registered once in your app config (this app also passes withFetch(), switching the transport from XMLHttpRequest to the native fetch API) before inject(HttpClient) resolves anywhere — forgetting it throws a "no provider" DI error at the injection site, not at the call site.
  • Interceptor chain. Every request passes through your registered interceptors in order — one place to add auth headers, log, retry, or show a loading bar — then hits the backend (HttpXhrBackend, or the fetch backend with withFetch()).
  • Cancellable. Unsubscribing (or a switchMap switching away) aborts the in-flight HTTP request. This is a real advantage over Promises, which can't be cancelled.
  • One value, then complete. An HTTP Observable emits the response once and completes, so it tears itself down — no manual unsubscribe needed for a simple GET (but switchMap in a stream still gives you cancellation for free).
  • Errors are notifications, not exceptions. A non-2xx response pushes an HttpErrorResponse through the Observable's error channel — handle it with catchError or the subscribe error callback, never a try/catch (HttpClient never throws synchronously).

Pitfalls that show up in exams & code review

  • HttpParams is immutable. set()/append() return a new instance — params.set('a', 1) alone does nothing; reassign it (proved live above).
  • PUT vs PATCH. PUT replaces the whole resource; PATCH sends only the changed fields. Sending a partial body with PUT can wipe omitted fields.
  • Body vs options argument order. Write verbs take (url, body, options); GET/DELETE take (url, options) — easy to pass options where the body goes.
  • No error handling on writes. A failed POST/PUT should surface; a catchError that quietly returns a fake success value hides real data loss from the user.
  • Per-call auth headers. Cross-cutting headers belong in an interceptor, not repeated at every call site.
  • Forgetting provideHttpClient(). Without it, inject(HttpClient) throws a NullInjectorError — a startup crash, not a network failure, so don't go debugging CORS first.
  • Unguarded double-submits. A second click before the first POST resolves fires a second, independent request — no built-in de-duplication. Disable the button, or route the click stream through exhaustMap to ignore clicks while one is already in flight.

Exam corner

Why did params.set('page', 2) not change the URL?
HttpParams is immutable — set returns a new instance you must assign/pass. The original is unchanged. (This is the exact bug the live demo above walks through.)
PUT or PATCH to change one field?
PATCH — it sends only that field. PUT replaces the entire resource, so omitted fields may be cleared.
How do you read response headers or status, not just the body?
Pass { observe: 'response' } — you get the full HttpResponse with status, headers and body.
A component throws "NullInjectorError: No provider for HttpClient" at startup. What's missing, and why doesn't it show up as a network error instead?
provideHttpClient() was never added to the app's providers. Dependency injection resolves at construction time — before any request is ever made — so the failure is a wiring error, not a runtime network failure.
Why does a failed HTTP call need catchError instead of a try/catch around subscribe()?
HttpClient methods never throw synchronously — a non-2xx response is delivered as an error notification on the Observable, not a thrown exception. A try/catch around .subscribe(...) would never see it; you need catchError in the pipe, or the error callback passed to subscribe.

Key takeaways

  • Each verb is one method; write verbs take (url, body, options?), GET/DELETE take (url, options?) — no body slot.
  • Type responses with the generic; use observe: 'response' for headers/status, responseType for non-JSON bodies.
  • Use HttpParams/HttpHeaders for query strings & headers — both immutable, both require capturing the return value.
  • Always handle errors (catchError, which runs on the error channel, not a try/catch) on write operations.
  • provideHttpClient() is a hard prerequisite — its absence fails at injection, not at the network call.
