An Observable is a lazy, cancellable stream of values that arrive over time — zero, one, or thousands of them. RxJS is the library that builds and transforms streams like it, and Angular hands you one almost everywhere: HttpClient, the router, a form's valueChanges. Nearly everything confusing about it traces back to one property most people assume it doesn't have — nothing runs until you subscribe — so that's where this page starts.

The problem

You just asked for data. Did anything happen yet?

Here's a line of code: const users$ = this.http.get<User[]>('/api/users');. If you've written any JavaScript with fetch, your instinct says the request is already on the wire — fetch is eager, it starts the moment you call it, whether or not anything is listening for the result.

That instinct is wrong here, and it's wrong in a way that matters. Nothing has gone out. No socket opened, no bytes sent. users$ is sitting in a variable, inert, and it will stay that way forever unless something calls .subscribe() on it. An Observable is lazy — it is a description of work, not the work itself.

Two variables: const p = fetch('/api/users') and const o = new Observable(subscriber => {{ '{' }} console.log('running!'); subscriber.next(1); {{ '}' }}). Neither line is followed by anything else — no .then(), no .subscribe(). Which one prints something to the console, and which one prints nothing at all, ever? The mental model

An Observable is a recipe. Subscribing is cooking it.

A recipe card sitting in a drawer does nothing. Somebody has to follow it before a single ingredient gets touched — and here's the part that matters later in this lesson: follow the same card twice, and you cook it twice. Two separate pans, two separate meals, from the one card. Nobody would call that surprising for a recipe. It is exactly how most Observables behave, and it is the single most common thing learners get wrong about them.

A Promise is closer to a meal already on its way to your table the moment you order it — cooking whether you're watching or not, arriving exactly once, impossible to wave off once it's plated.

No subscribe, no run. And every subscribe runs it again — that second half is the one people forget, and it's the whole reason two subscribers to one cold source can mean two HTTP requests.

There's a shorthand for the common case: source$.subscribe(v => …) means exactly source$.subscribe({{ '{' }} next: v => … {{ '}' }}) — a bare function is still just the next callback, and RxJS supports it today. What's deprecated is the other shorthand, three separate positional arguments — subscribe(next, error, complete) — so reach for the object form the moment you need more than next.

The mechanism

Building one is just wrapping a function.

You'll rarely build an Observable by hand — the next section covers the helpers that do it for you — but seeing the raw shape once is what makes everything above stop being folklore and start being mechanism.

The lazy description itself. Building one — even wiring up new Observable(fn) — runs nothing. The {{ '{' }} next, error, complete {{ '}' }} object you hand to subscribe() — how you say what to do with each notification. What subscribe() returns. Call .unsubscribe() on it to stop early and run the producer's teardown. The guarded object your producer function actually receives. It wraps your Observer and enforces the contract — a rogue next() after complete() is silently dropped, never delivered.

RxJS people also draw this as a marble diagram — time left to right, one marble per value, | for completed, X for errored. You'll see plenty of these in the next lesson: 

--1--2--3--|        emits 1, 2, 3, then completes
--a----b---c--|      spacing is never meaningful — marbles aren't a clock
----------X          errors, and stops — nothing after the X
--1--2--3--4--…      never completes (a click stream, interval())

Chaining operators never touches the original.

source$.pipe(map(fn1), filter(fn2)) looks like it edits source$ in place. It doesn't. Each operator returns a brand-new Observable whose own producer subscribes to the one before it internally — so subscribing to the result is really subscribing through a stack of wrappers, inward, until it reaches the real source.

The crucial distinction

Subscribe twice, and you get two separate runs.

The producer runs inside subscribe(). Two subscribe() calls run it twice, from scratch, each getting its own private execution.

Cold by default: http.get(), interval(), anything built with new Observable(...). Two subscribers to the same http.get() really do mean two separate HTTP requests.

One producer runs once, and every subscriber is handed the same values as they go by — multicast, not re-run from the top.

Subject (next-but-one lesson) is hot by construction. shareReplay() turns a cold source hot on purpose, by putting a Subject in the middle for you.

The catch

Sharing one run can also mean it never stops.

shareReplay() is how you turn a cold source hot on purpose — but it has two signatures, and the short one has a sharp edge nobody warns you about until it's already in production.

Subscribe to both, watch the ticks climb, then unsubscribe from both. The left counter keeps climbing — the underlying interval is still running with nobody listening — while the right one freezes the instant you unsubscribe, because refCount actually tore its source down.

shareReplay(1) remembers forever. shareReplay({{ '{' }} bufferSize: 1, refCount: true {{ '}' }}) forgets the moment nobody's listening. Pick the second one unless you can name the reason you want the first.

The modern default

The async pipe subscribes for you. Once per place you write it.

| async is the recommended way to read an Observable straight from a template: it subscribes when the binding is created, unwraps each value, calls markForCheck() on your view every time a new one arrives — which is exactly why it renders correctly under OnPush, and under this whole app's zoneless setup, with no extra work from you — and unsubscribes automatically when the binding is destroyed.

That sounds like it solves everything, and it very nearly does — except for the one thing its name doesn't warn you about: it subscribes per binding site, not per Observable.

The escape hatch

Sometimes you just want one value, once.

Not every call site wants to think in streams. If you genuinely want exactly one value and then you're done, RxJS has a bridge straight back to plain async/await — but it has three ways to surprise you if the source doesn't behave the way you assumed.

Notice the fix for the apparent contradiction with the HTTP CRUD lesson, which teaches subscribe({{ '{' }} error {{ '}' }}): awaiting throws the underlying error, so here — unlike with subscribe() — a plain try/catch is exactly the right tool.

Where they come from

You'll rarely build one by hand.

RxJS ships creation helpers for the common cases, so new Observable(...) stays a rare sight:

Helper What it gives you
of(1, 2, 3) Fixed values, synchronously, then completes
from(promiseOrArray) Wraps an array, an iterable, or a Promise
interval(1000) 0, 1, 2, … every second, forever — never completes
timer(500, 1000) Waits 500ms, then emits every 1s after that
fromEvent(el, 'click') DOM events as a stream — never completes on its own
EMPTY / NEVER / throwError(() => e) The three edge cases, as values you can substitute in

And Angular hands you Observables built the same way, in most of the framework surface you'll touch:

this.http.get<User[]>('/api/users')      // HTTP responses
this.route.paramMap                       // route parameters, as they change
this.form.valueChanges                    // every edit to a reactive form
this.form.statusChanges                   // VALID / INVALID / PENDING, over time
fromEvent(window, 'resize')               // any DOM event stream

Because they're all Observables, the same operators and the same cleanup rules apply to every one of them — learn the pattern once, use it everywhere.

Always clean up an infinite subscription. Best options, in order: the async pipe (auto-unsubscribes with the binding), toSignal() from RxJS ↔ Signals interop, or takeUntilDestroyed(). Manual unsubscribe() in ngOnDestroy works too, and is exactly what this lesson's own demos do. A source that complete()s or errors tears itself down — but an infinite one (interval, fromEvent) leaks until you stop it yourself.

Where this bites people

Six ways this shows up on an exam.

  • Assuming two subscribe() calls share one run — by default (cold), each subscribe re-executes the producer — two identical HTTP requests, not one shared response.
  • Assuming unsubscribe() always cancels the underlying work — for HttpClient it does abort the request, but a source built from a Promise can't be cancelled; unsubscribing just stops you hearing about a result that still arrives.
  • Forgetting error and complete are mutually exclusive and terminal — code written to expect more next calls after either one will simply never see them.
  • shareReplay() with no refCount config keeps the source subscribed forever, even at zero active subscribers — a leak hiding inside the fix for cold duplication.
  • Two | async bindings on the same cold source in one template are two independent subscriptions, not one shared value — bind once with @if (...; as x) instead.
  • firstValueFrom() on a source that never emits and never completes — a Subject nobody pushed to, say — hangs forever, silently: no error, no timeout.

Questions from the back row

Before you go

Six things to remember.

  • An Observable is a lazy recipe, not a running process. Nothing happens until subscribe(), and a Promise you're used to comparing it against already started before you finished reading the line.
  • Most Observables are cold: the producer re-runs, from scratch, for every single subscriber. Two subscribers to one http.get() is two HTTP requests, unless something makes it hot.
  • next can fire any number of times; error and complete are mutually exclusive and terminal — at most one of them, ever, and nothing after it.
  • .pipe() never mutates the source — every operator hands back a brand-new Observable that wraps the one before it.
  • | async subscribes per binding site, not per Observable. Two uses of the same cold source is two runs — alias it with as to pay for one.
  • A source that complete()s cleans itself up. An infinite one doesn't — you stop it, with the async pipe, toSignal(), takeUntilDestroyed(), or a manual unsubscribe().
