A view query is how a component reaches back into its own template from code — grabbing an element to focus, a child component to call a method on, a list of rendered rows to count. The modern form, viewChild()/viewChildren(), returns ordinary signals: they read undefined (or []) until the view resolves, then update live as the view changes. Three questions answer almost everything about them — what a query can find, when it's safe to read, and how far it reaches — and this page keeps coming back to the same three, with a live demo proving each answer and the two runtime errors, NG0951 and NG0100, shown for what they actually are.

The problem

Your template is data. Sometimes you need it to be a handle instead.

Binding only goes one direction. [value]="x" and interpolation push data from your class into the DOM — Angular owns writing to the element, and most of the time that's the whole story. But every so often you need the other direction: call .focus() on an input the user just revealed, call a method a child component exposes, count how many rows an @for actually rendered. None of that is a binding. It's a handle — a typed reference to something that already exists in your own template — and viewChild()/viewChildren() are how you ask for one.

Three questions turn out to answer almost everything about them:

  • What can a query find? — a locator: a template reference, a component type, a directive type.
  • When is it safe to read one? — after the view exists. Never before.
  • How far does it reach? — this template only, and not one tag further.
Here's a field: box = viewChild('box'), and the template really does have <input #box> in it — no @if hiding it, nothing conditional at all. You read this.box() from inside the constructor. What comes back, and why? Hold that answer; the mechanism section proves it live.

The mental model

A view query is a claim ticket, not a delivery.

Picture a coat check. You hand over your coat and get a ticket back immediately — the ticket is real the second it's in your hand. But redeem it before your coat has actually been hung up and you get a shrug, not a coat: it isn't there yet, not because anything went wrong, but because you asked too soon. That's viewChild('box'). Declaring the field creates the ticket the instant the class is constructed; the <input #box> it points at doesn't exist until Angular actually builds the view — which happens strictly after the constructor runs.

.required() is the same ticket at a stricter counter. Redeem it early and instead of a shrug you get thrown out — NG0951 — because this clerk doesn't do "not yet," only "yes" or "error."

Declare early, redeem late. The field exists the moment your class does. The thing it points at doesn't exist until the view does. Read a query anywhere in between and you're early, no matter how the field was declared.

The mechanism

One declaration becomes a live handle.

One match, by template reference, component type, or directive type. undefined until the view resolves it — and again the moment it leaves. The same match, minus the undefined in the type. Read it too early — or it never matches — and it throws instead of waiting politely. Every match, live, as an array. Starts at [], never undefined — "no matches yet" and "nothing rendered yet" look identical to a list.

Exam trap

Required doesn't mean early. It means strict.

The optional form is forgiving about timing: read box() before the view exists and you get undefined, no matter how you asked. .required() changes what "too early" looks like — it still resolves at exactly the same moment, but reading it before that moment, or discovering it never matched anything, both throw instead of returning a value. That's the trap: "required" reads as a promise about the element, so it's easy to assume it only throws when something is genuinely missing. It doesn't.

.required() is a promise about the template, not about timing. Read it too early and it throws NG0951 — exactly like a genuinely-missing target would. The error text can't tell you which one happened; only the moment you read it can.

How far it reaches

Your template stops at your children's front door.

A view query walks this component's own template, plus anything Angular builds on your behalf inside it — the rows an @for repeats, the branch an @if renders, an ng-template you instantiate. Visually all of that reads as "stuff on my page." A <app-child> tag also reads as "stuff on my page" — but it isn't, not to a view query. Cross that tag and you've left your own template and entered a completely separate one, compiled from a completely separate file, that your query was never told to look inside.

Once you accept the wall, exactly two ways are left to reach past it — never a locator string, never read::

  1. Call a method the child exposes. viewChild(StatCard) gets you the instance — every public method and property on it is fair game, the same as calling a method on any other object.
  2. Have the child expose its own query. The child declares its own viewChild internally and re-publishes the result as a computed() or a plain getter, which the parent then reads like any other signal.

Locators and read:

Same match. Different question about it.

A locator decides what gets matched — a template reference, a component type, a directive type. read: is a completely separate decision, asked about that same match: which token comes back for it. They compose, and mixing them up is the second-most common "my query gave me the wrong thing" story, right behind the boundary above.

The old form, in depth

Decorator queries still exist. Here's the one real gotcha.

Decorator query vs. signal query
signal query (modern) @ViewChild (legacy)
Declaration box = viewChild('box') @ViewChild('box') box!: ElementRef
Read where anytime — it's a signal (undefined until ready) ngAfterViewInit (or first pass, with static: true)
Updates on view change yes — re-resolves reactively no — set once, unless you re-check manually
List type Signal<readonly T[]> QueryList<T> — subscribe to .changes
Works in effect() yes no

static: true is the one decorator option with no signal-query equivalent, and it comes with a real constraint: it tells Angular the target can never be removed by a structural directive, so it resolves once during the first change-detection pass and is already readable in ngOnInit. Ask for it on anything conditionally rendered and you get a stale or undefined reference the moment the condition is false — signal queries sidestep the whole question by always re-resolving, so there's no flag to get wrong.

The other famous error

A safe read can still set up an unsafe write.

Every rule so far has been about reading a query at the right moment. Reading at the right moment is necessary — but it isn't sufficient, if what you do with the result is write to something the child's own template depends on.

Fixes, best first:

  1. Make the child's state a signal, and write it from an effect(). A signal write during a pass schedules the next one instead of corrupting the current one.
  2. Reach for afterNextRender() when this is really about measuring. getBoundingClientRect() and friends belong here — read after the pass finishes, act on the result outside it. This is the canonical reason to write to a queried child at all.
  3. Flow it down as a binding instead. Give the child an input() for its own title and let the parent's template set it, so the value moves the direction Angular already expects.

Pulling it together

Three questions, three traps.

The same three questions, answered as failure modes
Question The trap The fix
What can it find? A locator string with no matching #ref in this template — often because it's declared inside a child's template instead Check it's declared here, not past a child's boundary
When is it safe to read? Constructor, a field initializer, or ngOnInit — .required() throws NG0951 there even if the target is unconditional An effect, a handler, afterNextRender(), or ngAfterViewInit
How far does it reach? read: ElementRef on a child, expecting something from inside it You get the host tag; expose a method or a child query instead

Questions from the back row

Before you go

Things to remember.

  • A view query is the deliberate act of reaching into your own template from code — for the things binding can't do. Declare early, redeem late: the field exists the moment the class does, the thing it points at doesn't exist until the view does.
  • .required() doesn't change when a query resolves — only what happens if you read it too early or nothing ever matches: NG0951 instead of undefined.
  • A view query never crosses into a child component's own template. Reach a child's internals through a method it exposes, or a query it exposes itself — never through read:, which only ever returns the host.
  • viewChildren() starts at [], never undefined — and its legacy .changes fires only on later re-matches, not the initial set.
  • Writing to a queried child after its view has been checked this pass is a second way to get NG0100. Measure with afterNextRender(), or make the state a signal, instead of assigning directly.
