Signals and Observables are not rivals. A signal is the right tool for synchronous state you read in a template — it always has a value, and reading it never subscribes to anything. An Observable is the right tool for events that arrive over time and need operators — debounce, retry, cancellation. @angular/core/rxjs-interop gives you exactly two bridges, one each direction, so you can convert at the boundary and use whichever fits the job in front of you.

“I always have a value. You just never told me what it was.”

One first render, one TypeError, three parties in the room — and not one of them made a mistake.

The parties: an HTTP Observable, this.http.get<User[]>('/api/users'), which answers when the server does, about 200 milliseconds in. toSignal, which turned that stream into a signal in a field initializer. And your template, which read users().length the moment it rendered. Here is the transcript.

An Observable may not have a value yet. A signal must always have one. Carry a value from the first world into the second and you owe the signal something to hold while you wait: initialValue pays that debt up front; requireSync is a signed statement that there is no wait at all, which Angular checks at creation and throws on if you've lied. Convert at the boundary — and pay at the boundary.

A signal is a whiteboard: there is always exactly one thing written on it, and anyone can walk up and read it. An Observable is a ticker tape: values print past, and until the first one prints there is nothing to see. toSignal is someone standing at the tape, copying each value onto the board the moment it prints. initialValue is what you write on the board before the tape starts.

The mechanism

toSignal is a subscription wearing a signal's clothes.

There is no special runtime trick here — toSignal subscribes to the Observable once, and every time it emits, it writes the value into an ordinary signal. That is exactly what it told the template in round one. Here is the idea with the real error-handling and scheduling stripped out, which is the same technique the Subjects lesson used for its own MiniSubject.

The value the signal holds until the very first emission arrives. Skip it and the type is T | undefined — the gap round one was arguing about. For sources that emit the instant you subscribe — a BehaviorSubject, a startWith(...) pipeline. Trades initialValue for a plain, non-optional T — and throws at creation if the source turns out not to be synchronous after all. An errored source does not crash the moment it fails. The error waits, and surfaces the next time something reads the signal — usually your template, mid-render. The Predict below catches you on it; put catchError in the pipe first. toSignal calls inject() underneath, and inject() only works there. Call it from ngOnInit and it throws — see the trap further down this page.
Whiteboard, tape. A signal always has a value; an Observable might not have one yet. initialValue, requireSync and that | undefined in your types are the same fact wearing three different outfits.

The other direction

toObservable is an effect wearing an Observable's clothes.

The bridge has a second lane, and the traffic on it starts from a different complaint. You have a query signal that changes on every keystroke, and you want the debounced version — the same text, but only once typing has paused for half a second. Look for a debounce() on the signals API and you will not find one: signals have no operators at all. The way out is not to grow one. It is to cross over, use RxJS's, and come back.

The crossing runs on the mechanism from the advanced signals lesson: an effect() reruns whenever a signal it reads changes. toObservable puts one of those inside a hand-built Observable, so every time the signal changes, the effect pushes the new value out.

A trap that only shows up under a burst of writes

toObservable reports where a signal lands, not every stop it made getting there.

An effect() doesn't get a turn every time a signal it reads changes — it gets a turn once, after the current synchronous block finishes. Write to a signal three times in a row, synchronously, and the effect behind toObservable only ever sees the value the signal settled on. This is a real difference from a Subject, whose .next() notifies subscribers immediately and synchronously, once per call.

Live — three synchronous writes, one subscriber

Writes made: @for (v of writesLog(); track $index) { {{ v }} } @empty { (none yet) }

Emissions the subscriber received: @for (v of emissionsLog(); track $index) { {{ v }} } @empty { (none yet) }

Click the button and the "writes made" row fills in with 1 2 3, but "emissions received" gains exactly one new entry — 3. The values 1 and 2 were real writes, but nothing was ever subscribed to see them: they were overwritten before the effect ran even once. If a caller genuinely needs every intermediate value — a running log, an audit trail — a signal is the wrong carrier for it; reach for a plain Subject instead.

Try it — the round trip

Out to RxJS, and straight back.

Put both bridges together and you get the shape you will reach for constantly: a debounced search box, with the network call left out. Traced end to end, the thing to notice is that both ends are signals — RxJS is somewhere the value visits, not somewhere it lives.

Live — query, out to debounceTime(500), and back to a signal

typed, instantly: {{ query() || '—' }} debounced, 500ms later: {{ debounced() || '—' }}

Type fast and the debounced value visibly lags, settling 500ms after you stop. It made the entire round trip — query → toObservable → debounceTime → toSignal → debounced — and both ends are just signals your template reads directly. This is exactly the shape of a debounced search box.

Automatic teardown

takeUntilDestroyed ends when the component does.

Not every stream is going through toSignal — sometimes you want to subscribe and react, not hold a value. takeUntilDestroyed() completes the stream (and so unsubscribes it) the moment the component is destroyed, which is what makes a hand-written .subscribe() in a constructor safe.

Live — toSignal turning interval(1000) into state

tick: {{ tick() }} tick × 10, round-tripped through toObservable: {{ tickTimesTen() }}

The interval is an RxJS stream, and tickTimesTen is fed by a second pipeline built from toObservable(tick) in the constructor — yet the template reads both exactly like any other signal, and both tear themselves down automatically the moment you navigate away.

The trap

Call it from the wrong place, and it throws.

Every toSignal on this page has been called from a field initializer or a constructor — never from a lifecycle hook. That is not a style choice; it is the one placement rule the bridge actually enforces.

Questions from the back row

Before you go

Five things to remember.

  • toSignal(obs$) consumes an Observable as a signal: it subscribes once, seeds itself with initialValue — what it holds during the gap before the first emission — and unsubscribes automatically when the component is destroyed.
  • toObservable(sig) exposes a signal as a stream by wrapping an effect() — so RxJS's operators can reach a value that would otherwise never leave the signal graph.
  • Round-trip freely: a signal can go out to RxJS and come back a signal. Both ends of the bridge are always signals — RxJS is a place a value visits, never a place it has to live.
  • takeUntilDestroyed() auto-unsubscribes when the injection context is destroyed — toSignal does the equivalent for you without you writing it.
  • Signals for state, RxJS for orchestration over time — convert only at the boundary, and never grow one shape to do the other's job.
