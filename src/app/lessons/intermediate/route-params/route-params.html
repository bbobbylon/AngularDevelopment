Routes carry data in the URL four different ways, and they are read through four different APIs — path params, query params, matrix params and the fragment. Confusing them is the single most common routing bug this app's exam bank sees. Read them reactively — the URL is state, and the same component often stays mounted while that state changes underneath it.

The whole bug, in one picture

One URL string. Four completely different mechanisms, with no visual seam between them.

The fragment (#bio). Everything left of the # — path, matrix and query — travels in the actual HTTP request line the browser sends. Everything after it is stripped off by the browser itself before the request ever leaves: it's a purely within-page instruction, invisible to anything that only ever sees that request — an interceptor, a server log, a backend API. It is not invisible to Angular code itself, though — a guard, a resolver, a component all run in the same browser the fragment never leaves, and can read it straight off route.fragment.

Path params are the street address — required, and changing one sends the courier somewhere else. Query params are delivery instructions on the label — optional, and they never change which house it's going to. The fragment is "once you're inside, go to the kitchen" — the courier never even passes that one to the depot. The fuller version, with all four laid out side by side, is one section down.

The mental model, in full

A URL is a parcel with four different labels on it.

Here's the URL from the top of this page again: /users/42;view=grid?tag=ng&tag=rxjs&sort=name#bio. It reads as one string, and that is exactly the trap — it is not one piece of information. It is four completely different mechanisms, concatenated with no visual seam between them, and the router reads each one through a different API. Treat them as interchangeable, which is the natural first assumption, and you'll write code that reads a value from the wrong place — or worse, code that reads a value which quietly went stale the moment you stopped looking at it.

Picture a parcel being delivered. Path params are the street address — they say which house, they are required, and changing one sends the courier somewhere else entirely. Query params are the delivery instructions written on the label: "leave at the back door, ring twice." Optional, reorderable, and they never change which house the parcel is going to. The fragment is "and once you're inside, go to the kitchen" — purely a within-the-house instruction that the courier (the browser) never even passes on to the depot (the server). And matrix params are a note stapled to one specific line of the address rather than to the parcel as a whole.

Path says which. Query says how. Fragment says where on the page. If removing a param still leaves a URL that makes sense, it belongs in the query string.
The street address. Required — remove it and there's no house to deliver to. Changing it sends you somewhere else entirely, and the router treats it as a different resource. The delivery instructions on the label. Optional, reorderable, shareable — and they never change which resource you're looking at, only how you're looking at it. "Once you're inside, go to the kitchen." A purely within-page instruction — the browser never even sends it to the server, so a resolver or a guard can never see it. A note stapled to one specific line of the address, not the parcel as a whole. Rare in practice, and it rides along in paramMap, not queryParamMap — the first surprise this lesson proves.

Reading them for real

Declare a param, then read it — two ways, one very different outcome.

Prefer the observable paramMap over the snapshot. Navigating /users/1 → /users/2 reuses the component — the router doesn't destroy and recreate it for a param change — so snapshot.paramMap is frozen at the first activation and never updates, while the observable emits the new id. This is the single most common routing bug in reviews.

A detail that only bites on real data

A param containing a slash, question mark or hash needs encoding — string-built links don't get it.

Every path param in this lesson so far has been a clean id like 42. Real values are messier — an order reference with a slash in it, a search term with a # — and only some of the ways to build a link actually encode that safely.

The array form — [routerLink]="['/users', id]" or router.navigate(['/users', id]) — encodes each segment for you. String interpolation into a template literal, or plain string concatenation into navigateByUrl, does not — whatever the value contains lands in the URL verbatim, which can silently turn one path segment into two. paramMap.get() always hands the value back already decoded, so you never encode or decode a param by hand.

Under the hood

Why would the same id ever go stale?

The staleness bug above is not really about snapshot being a bad API. It is about a decision the router makes in the middle, before either the snapshot or the observable ever gets a say. Staged as a conversation first:

Reduced to steps, that's the same decision path:

  • There's no typed route syntax. A path like users/:id matches any segment verbatim — the router never validates or coerces it, so /users/abc matches just as well as /users/1. That's the actual reason params are always strings: nothing upstream ever had a number to give you.
  • Query params live on the URL tree, not the route match. Changing ?sort= alone doesn't change which route or component activates — only the path segments decide that — which is also why a query-param-only navigation can reuse the component even under a stricter reuse strategy.

A second, unrelated bug hiding in the same call

Every query-param update also pushes a new Back-button stop — unless you tell it not to.

Fixing the merge bug above does not fix a second problem sitting right next to it: by default, router.navigate([], { queryParams }) pushes a brand-new history entry every time it runs. Wire that up to a debounced search box and twenty keystrokes leave twenty entries — the Back button now has to be mashed twenty times before it takes the user anywhere they'd recognise as "back".

The fix is replaceUrl: true, and it is a judgment call, not a default to flip everywhere: reach for it on state that is transient — a search term, a filter toggle, a sort order — so the current history entry is rewritten instead of piling up. Leave the default push in place for state the user should genuinely be able to Back out of, like a page number or opening a detail panel. skipLocationChange is a different knob again: the navigation still happens, but the address bar does not change at all — no push, no replace, nothing to look at in the URL.

Skipping ActivatedRoute entirely

Or don't inject anything — bind params straight to inputs.

Path params, query params and resolved data all bind to inputs by matching name — so avoid name collisions (a path :id and a ?id= and a resolver keyed id all target one input, and only one wins). Also: params are always strings or null. get('id') gives '42', not 42 — convert with Number(id) and validate, guarding the null case before parsing.

The fastest heuristic in code review: path params are required by the route definition; query params never are. If you can delete it and the URL still parses to a sensible route, it was never a path param.

Pitfalls that show up in exams & code review

The five ways this bites in practice.

  • Stale snapshot on reuse. Read route.paramMap (observable/signal), not snapshot.paramMap, when the same route can re-navigate with different params.
  • Everything is a string. +id / Number(id); a missing param is null, so parse defensively.
  • Default handling drops query params. Omitting queryParamsHandling replaces the whole query string — use 'merge' to keep the rest.
  • get vs getAll. Repeated keys need getAll; get silently returns just the first.
  • Query params don't re-run resolvers by default. That's a runGuardsAndResolvers setting — see Resolvers.

Questions from the back row

Recap — before you go

Six things to remember.

  • Path params identify a resource (:id); query params describe how you're viewing it; the fragment never leaves the browser; matrix params scope to one segment.
  • Read via the reactive paramMap/queryParamMap (or a signal from toSignal), not the snapshot, on any route that can reuse its component.
  • The router reuses a component whenever the matched route config is unchanged — param values are never part of that decision, which is the entire reason a snapshot can go stale.
  • queryParamsHandling: 'merge' preserves existing query params; the default replaces the whole query string.
  • A repeated query key needs getAll; get silently returns only the first.
  • Params are strings — convert explicitly. Number(null) is 0, not NaN, so check for null before you convert; withComponentInputBinding() maps them to inputs (mind name collisions).
