Route & Query Parameters

Routes carry data in the URL two ways: path params (/users/42) identify a resource, and query params (?sort=name&page=2) carry optional, shareable state. Read them reactively — the URL is state, and the same component often stays mounted while that state changes.

The mental model: a postal address

A URL carries several kinds of information at once, and they are as different from each other as the parts of an address on a parcel. Path params are the street address — they say which house, they are required, and changing one sends you somewhere else entirely. Query params are the delivery instructions written on the label: "leave at the back door, ring twice." Optional, reorderable, and they never change which house you are going to. The fragment is "and once you are inside, go to the kitchen" — so purely a within-the-page instruction that the browser does not even send it to the server. And matrix params are a note stapled to one specific line of the address rather than to the parcel as a whole.

Path says which. Query says how. Fragment says where on the page. If removing it still leaves a URL that makes sense, it belongs in the query string.

Prefer the observable paramMap over the snapshot. Setting query params: queryParamsHandling

What happens to the query params already in the URL depends entirely on this option:

Value Effect on existing query params
'' (default) replaced entirely by the new [queryParams] (drops the rest).
'merge' merged — new keys added/overwritten, others kept. Set a key to null to remove it.
'preserve' keeps the current query params, ignores the new ones.

Arrays, fragments & matrix params

{{ arraysSample }}
A key repeated in the URL (?tag=a&tag=b) is read with queryParamMap.getAll('tag') → ['a','b']; get('tag') returns only the first. Matrix params (/users;view=grid;page=2) attach to a single segment and live in paramMap — handy for scoping state to one route segment rather than the whole URL.

Component input binding

{{ inputSample }}
With withComponentInputBinding(), path params, query params and resolved data all bind to inputs by matching name — so avoid name collisions (a path :id and a ?id= and a resolver keyed id all target one input, and only one wins). Also: params are always strings or null. get('id') gives '42', not 42 — convert with Number(id) and validate, guarding the null case before parsing.

Under the hood

The staleness bug is not really about snapshot being a bad API. It is about what the router decides here, in the middle:

  • Reuse is a policy, not an accident. The default RouteReuseStrategy.shouldReuseRoute returns true whenever the matched route config (the path template) is unchanged, regardless of param values — that's precisely why /users/1 → /users/2 keeps the same UserPage instance while navigating to a different route destroys and recreates it.
  • paramMap is multicast on the surviving ActivatedRoute. Because the router keeps the same ActivatedRoute object across a reused navigation, a subscription started once in ngOnInit keeps receiving every later param change — no need to re-subscribe per navigation.
  • Only the reused node's params are swapped. The router resolves a whole new ActivatedRouteSnapshot tree per navigation, diffs it against the current tree, and reuses matching branches wholesale — the retained node just gets new params/queryParams/data pushed onto it, with no ngOnDestroy/ngOnInit cycle in between.
  • There's no typed route syntax. A path like users/:id matches any segment verbatim — the router never validates or coerces it, so /users/abc matches just as well as /users/1. That's the actual reason params are always strings: nothing upstream ever had a number to give you.
  • Query params live on the URL tree, not the route match. Changing ?sort= alone doesn't change which route/component activates — only the path segments decide that — which is also why a query-param-only navigation can reuse the component even under a stricter reuse strategy.

Pitfalls that show up in exams & code review

  • Stale snapshot on reuse. Read route.paramMap (observable/signal), not snapshot.paramMap, when the same route can re-navigate with different params.
  • Everything is a string. +id / Number(id); a missing param is null, so parse defensively.
  • Default handling drops query params. Omitting queryParamsHandling replaces the whole query string — use 'merge' to keep the rest.
  • get vs getAll. Repeated keys need getAll; get silently returns just the first.
  • Query params don't re-run resolvers by default. That's a runGuardsAndResolvers setting — see Resolvers.

Key takeaways

  • Path params identify resources (:id); query params carry optional, shareable state.
  • Read via the reactive paramMap/queryParamMap, not the snapshot, on reusable routes.
  • queryParamsHandling: 'merge' preserves existing query params; the default replaces them.
  • Params are strings — convert explicitly; withComponentInputBinding() maps them to inputs (mind name collisions).
