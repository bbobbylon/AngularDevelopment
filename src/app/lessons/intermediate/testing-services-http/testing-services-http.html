Testing Services & HTTP

Services are the easiest things to test because they're just classes. HTTP services need a bit more setup, but Angular's HttpTestingController gives you full, synchronous control over every request — no network, no async timing issues.

The mental model: you become the kitchen

Picture your service as a waiter. It writes an order — GET /api/users/1 — clips the ticket to the rail at the pass, and waits. In production a kitchen on the other side cooks something and hands back a plate. In a test, provideHttpClientTesting() fires the kitchen and gives you the apron.

Everything else follows from that. expectOne is you reading a ticket off the rail — and complaining if there are two tickets, or none. flush is you handing back a plate, with whatever is on it. And because you are the kitchen, nothing at all happens until you act: there is no network, no timer, no waiting. Which is why these tests are synchronous, and why http.verify() at the end — a glance at the rail to check no ticket is still hanging there — is not optional politeness. It is the only thing that notices an order you never cooked.

Expect the ticket, flush the plate, verify the rail. Every HTTP test is those three moves in that order. Skip the third and a test that asserted nothing at all still passes.

Pure services — no TestBed needed

A service with no DI dependencies can be tested with a plain constructor call. This is the fastest, most isolated test possible. 

// @Injectable service with only signals — no http, no router, no deps:
@Injectable()
export class CartService {{ '{' }}
  // The single source of truth. `private` + the underscore convention means
  // nothing outside this class can call .set() or .update() on it.
  private readonly _items = signal<CartItem[]>([]);

  // The public face of the same signal. asReadonly() strips the write methods,
  // so callers can read items() but cannot mutate your state behind your back.
  readonly items = this._items.asReadonly();

  // Derived, not stored. computed() re-runs ONLY when _items actually changes,
  // caches the result, and can never drift out of sync the way a manually
  // maintained `total` field would. reduce() walks the array summing prices;
  // `s` is the running total, `i` the current item.
  readonly total = computed(() => this._items().reduce((s, i) => s + i.price, 0));

  // update() receives the current value and returns the NEXT one. The spread
  // builds a brand-new array — signals compare by reference, so mutating the
  // existing array with .push() would change nothing that anyone can observe.
  add(item: CartItem) {{ '{' }} this._items.update(l => [...l, item]); {{ '}' }}

  // Same rule: filter() returns a new array rather than editing in place.
  remove(id: number) {{ '{' }} this._items.update(l => l.filter(i => i.id !== id)); {{ '}' }}
{{ '}' }}

// Test — no TestBed at all:
// describe() groups related tests and gives the failure output a heading.
describe('CartService', () => {{ '{' }}
  // Declared here, assigned in beforeEach — so every test sees it, but each
  // test gets a FRESH one. Sharing one instance across tests is how you get
  // failures that depend on the order the tests happened to run in.
  let service: CartService;

  // Runs before each `it` below, not once for the whole file.
  beforeEach(() => {{ '{' }}
    service = new CartService();       // plain constructor
  {{ '}' }});

  // it() = one behaviour, described in words that read as a sentence with the
  // describe() above it: "CartService adds items and computes total".
  it('adds items and computes total', () => {{ '{' }}
    // Arrange + Act: drive the service through its public API only.
    service.add({{ '{' }} id: 1, name: 'Widget', price: 10 {{ '}' }});
    service.add({{ '{' }} id: 2, name: 'Gadget', price: 25 {{ '}' }});

    // Assert. Note the parentheses: `items` is a signal, so `items()` READS it.
    // Forgetting them compares the function object itself and always fails.
    expect(service.items().length).toBe(2);

    // 10 + 25. Nothing recomputed this by hand — reading total() pulled the
    // computed, which is exactly the behaviour under test.
    expect(service.total()).toBe(35);
  {{ '}' }});

  it('removes an item', () => {{ '{' }}
    service.add({{ '{' }} id: 1, name: 'Widget', price: 10 {{ '}' }});
    service.remove(1);
    expect(service.items().length).toBe(0);
    expect(service.total()).toBe(0);
  {{ '}' }});
{{ '}' }});

HttpTestingController — full control over the network

import {{ '{' }} provideHttpClient {{ '}' }} from '@angular/common/http';
import {{ '{' }} provideHttpClientTesting, HttpTestingController {{ '}' }}
  from '@angular/common/http/testing';

// The remote control for the fake backend: it lets you assert what was
// requested and decide what comes back.
let http: HttpTestingController;
// The service under test — the thing that will call HttpClient.
let api: UserApi;

beforeEach(() => {{ '{' }}
  TestBed.configureTestingModule({{ '{' }}
    providers: [UserApi, provideHttpClient(), provideHttpClientTesting()],
  {{ '}' }});

  // Both come from the SAME injector, which is what connects them: requests
  // made by `api` land in this `http` controller's queue.
  http = TestBed.inject(HttpTestingController);
  api  = TestBed.inject(UserApi);
{{ '}' }});

// The safety net, and the reason silent tests get caught. verify() throws if
// the service made a request that no expectOne() ever claimed — i.e. an
// unexpected call — so a typo'd URL fails loudly instead of passing quietly.
afterEach(() => http.verify());   // fails if any request was made but not handled

Flushing responses — happy path

it('fetches a user', () => {{ '{' }}
  // A capture variable. It stays undefined until the observable emits, which
  // is what lets the final assertion prove the value actually arrived.
  let result: User | undefined;
  // Subscribing is what SENDS the request — HttpClient observables are cold,
  // so without this line nothing is ever dispatched and expectOne() fails.
  api.getUser(1).subscribe((u) => (result = u));

  // Claims the pending request and hands you a TestRequest. expectOne throws
  // a descriptive error if zero requests match, or if two or more do.
  const req = http.expectOne('/api/users/1');
  // req.request is the real HttpRequest object, so you can assert on anything
  // the service set — the verb...
  expect(req.request.method).toBe('GET');
  // ...and the headers. Worth checking: a missing Accept header is exactly the
  // kind of bug that only shows up against a picky real backend.
  expect(req.request.headers.get('Accept')).toBe('application/json');

  // flush() plays the role of the server responding. It runs SYNCHRONOUSLY,
  // so the subscribe callback above has already fired by the next line — no
  // tick(), no await, no done().
  req.flush({{ '{' }} id: 1, name: 'Ada Lovelace', email: 'ada@example.com' {{ '}' }});
  // Now the captured value is populated.
  expect(result?.name).toBe('Ada Lovelace');
{{ '}' }});

Simulating errors

it('handles 404 gracefully', () => {{ '{' }}
  let error: string | undefined;
  // The OBSERVER-OBJECT form of subscribe, so you can supply an error handler.
  api.getUser(999).subscribe({{ '{' }}
    // A guard clause: if next ever runs, the test fails immediately instead of
    // quietly passing because `error` stayed undefined and nothing checked.
    next: () => fail('should not succeed'),
    error: (e) => (error = e.message),
  {{ '}' }});

  const req = http.expectOne('/api/users/999');
  // flush() takes an optional second argument describing the response. Any
  // status >= 400 makes HttpClient wrap it in an HttpErrorResponse and push it
  // down the error channel instead of next.
  req.flush('User not found', {{ '{' }} status: 404, statusText: 'Not Found' {{ '}' }});
  // toContain, not toBe: Angular composes a longer message that embeds the
  // status code, so matching the exact string would be brittle.
  expect(error).toContain('404');
{{ '}' }});

it('handles network error', () => {{ '{' }}
  let error: any;
  // Shorthand observer — only the error channel is of interest here.
  api.getUser(1).subscribe({{ '{' }} error: e => (error = e) {{ '}' }});

  const req = http.expectOne('/api/users/1');
  // A DIFFERENT failure mode from the 404 above, and the distinction matters:
  // .error() means the request never reached the server at all — offline, DNS
  // failure, CORS rejection. There is no status code, so error.status is 0.
  req.error(new ProgressEvent('error'));
  expect(error).toBeTruthy();
{{ '}' }});

Flexible matching & POST body inspection

it('creates a user with correct body', () => {{ '{' }}
  let createdId: number | undefined;
  api.createUser({{ '{' }} name: 'Bob', email: 'bob@test.com' {{ '}' }}).subscribe(r => (createdId = r.id));

  // Match by predicate instead of exact URL:
  const req = http.expectOne(r => r.url.includes('/api/users') && r.method === 'POST');

  // Inspect what was sent:
  expect(req.request.body.name).toBe('Bob');
  expect(req.request.body.email).toBe('bob@test.com');

  req.flush({{ '{' }} id: 42, ...req.request.body {{ '}' }});
  expect(createdId).toBe(42);
{{ '}' }});

// match() returns ALL matching requests (useful for debounced search):
const reqs = http.match(r => r.url.startsWith('/api/search'));
reqs.forEach(r => r.flush([]));

// expectNone — assert no request was made:
http.expectNone('/api/admin');         // ensure unauthenticated users never hit admin routes

Testing HTTP interceptors

Test interceptors by registering them and then making a real HTTP call through the controller — the interceptor runs in the middle. 

describe('authInterceptor', () => {{ '{' }}
  let http: HttpTestingController;
  // Note: no service under test here. You inject HttpClient DIRECTLY, because
  // the interceptor sits between HttpClient and the network — nothing else is
  // needed to exercise it.
  let client: HttpClient;
  // A stand-in for whatever the interceptor reads the token from. Declared as
  // a const so the tests below can re-script it per case.
  const fakeAuth = {{ '{' }} accessToken: vi.fn().mockReturnValue('my-token') {{ '}' }};

  beforeEach(() => {{ '{' }}
    TestBed.configureTestingModule({{ '{' }}
      providers: [
        // The interceptor will resolve AuthService from the injector, so this
        // override is what actually controls the token it sees.
        {{ '{' }} provide: AuthService, useValue: fakeAuth {{ '}' }},
        // Registers the real interceptor. withInterceptors() takes the array
        // in run order — the first entry sees the request first.
        provideHttpClient(withInterceptors([authInterceptor])),
        // MUST come after provideHttpClient(). It swaps the HTTP backend for
        // the fake one; listed first, the real backend wins and your test
        // attempts an actual network call.
        provideHttpClientTesting(),
      ],
    {{ '}' }});
    http   = TestBed.inject(HttpTestingController);
    client = TestBed.inject(HttpClient);
  {{ '}' }});

  it('attaches Authorization header', () => {{ '{' }}
    // No callback needed — subscribing is only here to dispatch the request.
    // The interceptor runs during this call, before the fake backend sees it.
    client.get('/api/profile').subscribe();
    const req = http.expectOne('/api/profile');
    // The assertion IS the test: inspect the outgoing request and confirm the
    // interceptor rewrote it. 'Bearer ' + the token from fakeAuth above.
    expect(req.request.headers.get('Authorization')).toBe('Bearer my-token');
    // Respond so http.verify() in afterEach doesn't complain about an
    // outstanding request.
    req.flush({{ '{' }} name: 'Ada' {{ '}' }});
  {{ '}' }});

  it('does not attach header when not logged in', () => {{ '{' }}
    // ...Once — overrides the return value for the NEXT call only, so the
    // describe-level 'my-token' default is untouched for other tests.
    fakeAuth.accessToken.mockReturnValueOnce(null);
    client.get('/api/profile').subscribe();
    const req = http.expectOne('/api/profile');
    // .has() rather than .get(): asserting the header is ABSENT. This is the
    // test people skip, and it's the one that catches an interceptor sending
    // "Bearer null" to the server.
    expect(req.request.headers.has('Authorization')).toBe(false);
    req.flush({{ '{' }} name: 'Ada' {{ '}' }});
  {{ '}' }});
{{ '}' }});

Testing Observables — marble testing concept

Marble testing lets you describe Observable sequences as ASCII strings and compare them precisely. Most of the time you don't need it — fakeAsync + tick is simpler. Use marbles for complex operator chains. 

import {{ '{' }} TestScheduler {{ '}' }} from 'rxjs/testing';

describe('debounceSearch$', () => {{ '{' }}
  let scheduler: TestScheduler;
  beforeEach(() => {{ '{' }}
    // TestScheduler takes an ASSERTION FUNCTION, not a config object. RxJS
    // calls it at the end of run() with the actual vs expected notification
    // lists, and you delegate to whatever matcher your runner provides.
    scheduler = new TestScheduler((actual, expected) =>
      expect(actual).toEqual(expected)
    );
  {{ '}' }});

  it('debounces search input by 300ms', () => {{ '{' }}
    // Inside run(), RxJS patches time itself: every operator's delay runs on
    // the virtual clock, so a 300ms debounce costs zero real milliseconds.
    scheduler.run({{ '{' }} hot, cold, expectObservable {{ '}' }} => {{ '{' }}
      // Marble syntax: '-' = 10ms of silence, a letter = an emission at that
      // frame, '|' = complete, '#' = error. The second argument maps each
      // letter to the value it stands for.
      // hot() = already running, emits regardless of subscribers (a Subject,
      // a DOM event stream). cold() = starts fresh per subscriber (an HTTP
      // call). Picking the wrong one is the #1 marble-test mistake.
      // Count the characters to get the frames: 'a' at 10ms, 'b' at 30ms,
      // 'c' at 130ms — a user typing "h", "he", then "hello".
      const input$  = hot('-a-b---------c', {{ '{' }} a:'h', b:'he', c:'hello' {{ '}' }});
      // The operator chain under test.
      const result$ = input$.pipe(debounceTime(300));
      // Now trace it. 'h' starts a 300ms timer; 'b' arrives 20ms later and
      // RESTARTS it, so 'h' never emits. 'c' arrives at 130ms and restarts it
      // again, killing 'he'. Nothing follows, so 'hello' finally emits 300ms
      // after it arrived: 130 + 300 = frame 430.
      // '430ms c' is time-progression syntax — clearer than counting 43
      // dashes, and it's why the emission is NOT at frame 130. Getting this
      // arithmetic wrong is the usual reason a marble test refuses to pass.
      expectObservable(result$).toBe('430ms c', {{ '{' }} c:'hello' {{ '}' }});
    {{ '}' }});
  {{ '}' }});
{{ '}' }});

Simple Observable testing without marbles

// The `done` callback tells the runner "this test is async — wait for me".
it('maps and filters items', (done) => {{ '{' }}
  // One emission containing the whole array (not five separate emissions).
  const source$ = of([1, 2, 3, 4, 5]);
  const result$ = source$.pipe(
    // switchMap returns a NEW observable per emission; of() wraps the filtered
    // array back into one so the chain keeps its Observable type.
    switchMap(arr => of(arr.filter(n => n % 2 === 0)))
  );
  result$.subscribe(arr => {{ '{' }}
    expect(arr).toEqual([2, 4]);
    // Call done() INSIDE the subscription. Omit it and the test times out;
    // put the expect() after the subscribe block instead and the test passes
    // without ever running the assertion — a silent false green.
    done();
  {{ '}' }});
{{ '}' }});

// A cleaner alternative when the observable emits once and completes.
it('resolves the first value', fakeAsync(() => {{ '{' }}
  let val: number | undefined;
  // firstValueFrom converts an Observable to a Promise that resolves with the
  // first emission — no subscribe, no done(), no manual teardown.
  firstValueFrom(of(42)).then(v => (val = v));
  // The .then() above is queued as a microtask; tick() drains it so the
  // assertion sees the resolved value.
  tick();
  expect(val).toBe(42);
{{ '}' }}));

Testing BehaviorSubject / signals interop

it('toSignal reflects latest BehaviorSubject value', () => {{ '{' }}
  // A BehaviorSubject always holds a current value — 10 to start.
  const subject$ = new BehaviorSubject(10);
  // toSignal() needs an injection context (it registers a DestroyRef so the
  // subscription is cleaned up). Calling it bare in a test throws NG0203;
  // runInInjectionContext supplies the context TestBed already owns.
  const sig = TestBed.runInInjectionContext(() =>
    // requireSync tells Angular "this source emits immediately, so the signal
    // has no undefined phase" — which is why sig() is typed number, not
    // number | undefined. Pass it on a source that ISN'T synchronous and
    // Angular throws at runtime rather than handing you a silent undefined.
    toSignal(subject$, {{ '{' }} requireSync: true {{ '}' }})
  );
  // No subscribe, no async: the signal already has the subject's value.
  expect(sig()).toBe(10);

  // Push a new value through the stream...
  subject$.next(20);
  // ...and the signal reflects it synchronously. No detectChanges() needed —
  // reading a signal never depends on change detection.
  expect(sig()).toBe(20);
{{ '}' }});

Service test patterns reference

Scenario Pattern
Pure service (signals only) Plain new Service() — fastest
Service with inject() dependencies TestBed.configureTestingModule with providers
Service makes HTTP calls provideHttpClientTesting + HttpTestingController
Service has a timer/polling loop fakeAsync + tick/flush to control time
Service depends on another service Inject a mock/spy: useValue + vi.fn()
Test an interceptor Register with withInterceptors([...]) + HttpTestingController
Service uses localStorage Set/assert directly in beforeEach/afterEach

What NOT to test

Thing Why
Private methods directly Test through public API — internal impl can change
Angular internals (that HttpClient calls the right URL) Angular tests that — you test your logic around it
Every getter/setter independently Test behaviors, not structure: "cart total updates when item is added"

Test organization

// OUTER describe: names the unit under test. One per file.
describe('UserService', () => {{ '{' }}
  // Setup once per describe block in beforeEach — TestBed config, injections,
  // and the afterEach(() => http.verify()) that guards the whole suite.

  // NESTED describe per METHOD. This is the part worth copying: a failure
  // reports as "UserService > getUser() > throws 404 for unknown id", which
  // tells you where to look before you have read a single line of code.
  describe('getUser()', () => {{ '{' }}
    // Name each it() after the BEHAVIOUR, not the implementation. "fetches
    // user by id" survives a rewrite; "calls http.get with /api/users" does not.
    it('fetches user by id', ...);
    it('caches the result', ...);
    // Always include the failure cases. A suite with only happy paths tells
    // you the code works when nothing goes wrong, which is the easy half.
    it('throws 404 for unknown id', ...);
  {{ '}' }});

  describe('createUser()', () => {{ '{' }}
    it('posts the correct body', ...);
    it('returns the created user with id', ...);
    it('rejects with validation errors', ...);
  {{ '}' }});
{{ '}' }});

Before the takeaways: does this test pass?

Commit to an answer first. This shape shows up in real codebases constantly, and the reason it is dangerous is that the test looks like it is checking something.

Key takeaways

  • Pure services: new Service() — no TestBed, fastest possible test.
  • HTTP: provideHttpClientTesting() + HttpTestingController gives synchronous control.
  • expectOne + flush/error assert the request and deliver a response.
  • http.verify() in afterEach ensures no unhandled requests.
  • Test interceptors by registering them with withInterceptors([]) and using the controller.
  • Mock collaborators with useValue + vi.fn(); use vi.spyOn for partial mocks.
