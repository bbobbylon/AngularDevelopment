Every API call in every app you've ever built needs the same four things: somewhere to put the data, a flag for "it hasn't arrived yet", a flag for "it broke", and a way to cancel a request that's been overtaken by a newer one. resource() is Angular admitting that pattern is common enough to build once. This page proves it with live network requests, not prose — including a distinction almost every explanation of resource() gets backwards: changing what you're asking for and asking for the same thing again are two different states, and they render completely differently.

The problem

Every async load turns into the same four fields.

Say you need to show a user's profile. The data doesn't just appear — you write a signal to hold it, a signal for whether it's loading, a signal for whether it broke, and code to flip all three at the right moments. The mental model

Changing your mind and asking again are not the same request.

Picture a restaurant table with a runner working it. Ask for a new dish — a burger instead of a salad — and the runner clears your table right away and goes to fire the burger; you're looking at an empty table until it lands. Ask for the same dish again — "actually, redo this one, I think it came out cold" — and the runner leaves your current plate exactly where it is while a fresh one cooks, only swapping it in once it's ready.

That's the exact difference between a resource's two "a request is happening" moments, and it's the trap most write-ups of resource() get backwards: changing params is a new dish — status() goes back to loading and value() goes blank. Calling reload() with the same params is asking for the same dish again — status() becomes reloading and value() keeps showing what you already had.

New order, empty table. Same order, old plate stays. Every time you're unsure whether a resource will blank the screen or keep showing stale data, ask which one just happened — params changed, or the same params were asked for again.

The full picture

There are six states, not two.

Most explanations stop at "loading, then done, or error." The real type is six strings, and the two easiest to confuse are the pair from the mental-model section above:

ResourceStatus — the complete set
Status When you're in it What value() holds
idle The params callback returned undefined — deliberately no request to make undefined, or your defaultValue
loading The first-ever request, or any request that follows a params change undefined, or your defaultValue — nothing carries over
reloading You called reload() while params are unchanged — same request, again The previous resolved value, untouched, while the new one is in flight
resolved The loader finished and returned normally The fresh value it returned
local You wrote it yourself via value.set()/.update() Whatever you wrote
error The loader threw, or its promise rejected Throws if read directly — guard with hasValue() or status()

The trap

value() can be empty — or throw.

defaultValue is the fix for the empty half of that — but it only covers idle and loading. It does not cover error. 

count = resource({{ '{' }} loader: … {{ '}' }});
// value(): Signal<number | undefined>
// every template read needs hasValue() first
count = resource({{ '{' }} loader: …, defaultValue: 0 {{ '}' }});
// value(): Signal<number>
// reads directly — no guard for "nothing yet"
value() ?? 'fallback' does not catch this. Nullish coalescing only catches null/undefined — a thrown error skips straight past it. hasValue() works because it checks status() first and never calls the throwing getter while status() is 'error'.

The shortcut

httpResource() is resource(), wired to HttpClient.

Everything in "Declaring a resource" above — the abort wiring, the res.ok check, the fetch call itself — is boilerplate httpResource() removes, because it's built on HttpClient instead of a hand-written loader. 

resource({{ '{' }}
  params: () => this.userId(),
  loader: async ({{ '{' }} params, abortSignal {{ '}' }}) => {{ '{' }}
    const res = await fetch(url, {{ '{' }} signal: abortSignal {{ '}' }});
    if (!res.ok) throw new Error(…);
    return res.json();
  {{ '}' }},
{{ '}' }})

Typed variants exist for anything that isn't JSON: httpResource.text(), httpResource.blob(), httpResource.arrayBuffer() — same shape, different parsing. HttpResourceRef also adds three signals plain resource() doesn't have: headers(), statusCode() and progress() (when the request opts in with reportProgress: true).

The reactive-URL rule still applies. A signal has to be read inside the request callback. Build the URL from a plain variable captured outside it and the resource fetches once, on creation, and never again — no error, just silent staleness.

The RxJS sibling

rxResource() swaps a Promise for an Observable.

Same params/value/status shape as resource() — the only thing that changes is where the async work comes from, and the option name that carries it.

The cancellation model is the real difference. resource() cancels by firing an AbortSignal — built for a single Promise that either resolves or doesn't. rxResource() cancels by unsubscribing from the previous Observable and subscribing to a fresh one, which is exactly what lets operators like debounceTime, retry and switchMap-shaped chains compose naturally — a raw Promise loader has nowhere to attach them.

Pulling it together

resource() and its five alternatives.

Tool Gives you Reach for it when
resource() value + status + error + isLoading signals, auto re-fetch, cancellation your source is a Promise from something other than HttpClient — a custom SDK, IndexedDB, a non-HTTP API
httpResource() the same shape, built on HttpClient fetching from a normal HTTP endpoint for display — interceptors and a testing backend need to apply
rxResource() the same shape, Observable-driven your source is naturally a stream — RxJS operators, a WebSocket, a service that already returns Observables
toSignal(http$) a signal of the latest value only a one-shot fetch you just want as a signal; no built-in status/error
manual subscribe() full RxJS control complex streams (debounce, combine, retry) — but you manage state + teardown yourself
route resolver data before the route activates small, critical data that must be present on first paint (blocks navigation)

Under the hood

What the options object doesn't show you.

  • Why an injection context is required. resource() reads DestroyRef from the current injector so it knows when to tear itself down. Call it somewhere with no injector in scope — inside a plain method, say — and there's nothing to register that cleanup with, so Angular throws immediately rather than leaking silently. Pass {{ '{' }} injector {{ '}' }} explicitly to opt out of that check when you genuinely are creating one later.
  • Stale results are discarded by resource() itself, not just by your fetch. Every load tracks which request it belongs to; a result that resolves after a newer request has already started is thrown away the moment it lands — whether or not your loader ever looked at abortSignal. Wiring the signal into fetch stops the wasted network call; it isn't what stops the wrong data from appearing.
  • Writing value doesn't touch the loader. userResource.value.set(...) replaces the resource's internal state directly with a 'local' entry — a pure local mutation that can't retrigger params/loader tracking.
  • httpResource() automates what resource() makes you wire by hand. The abort signal, the res.ok check, the fetch call itself — all internal to HttpClient, which is also why interceptors run and provideHttpClientTesting can intercept the request in a test.
  • Still @experimental, all three of them. In this Angular version, resource(), rxResource() and httpResource() carry that label in their type declarations — one step earlier than @developerPreview. The core contract has held steady across several releases, but the framework team hasn't ruled out changing its shape without a deprecation cycle.

Questions from the back row

Before you go

Six things to remember.

  • Every async load needs the same four things — data, loading, error, cancellation. resource() is Angular building that pattern once instead of everyone hand-rolling it forever.
  • A params change and a reload() of the same params are different requests with different status() values — loading blanks the screen, reloading keeps the old value visible while a new one is fetched.
  • value() throws when status() is 'error' — defaultValue does not protect you there. hasValue() is the guard that works in every state, because it checks status() before ever touching value().
  • httpResource() is resource() wired to HttpClient — same reactive-URL rule, but interceptors run and a failure arrives as a real HttpErrorResponse.
  • rxResource() swaps the loader for a stream returning an Observable, cancelling by unsubscription instead of AbortSignal — which is what lets debounceTime/retry compose naturally.
  • resource(), rxResource() and httpResource() are all still @experimental in this Angular version — use them, but watch the changelog.
