The resource() API

resource() bridges async data and signals. You give it a reactive params and a loader; it tracks loading/error state, re-fetches when the params change, and cancels stale requests via an AbortSignal — all exposed as signals.

Think of it as a standing order at a counter

You hand the kitchen a ticket that says "whatever is on this card" rather than calling out an order. Change what's written on the card and the kitchen notices and starts over — you never place a second order, and you never ask "is it ready yet?" because the counter display tells you.

Three properties of that arrangement are the three things resource() gives you:

  • You describe what you want, not when to fetch. That's params: a function that reads signals. Change a signal it read, and the loader re-runs by itself. There is no refresh() call anywhere in a well-written resource.
  • The counter display is always accurate. That's status()/isLoading()/error() — loading and error state are part of the resource, not three booleans you maintain by hand and forget to reset.
  • Change your mind and they bin the half-made one. That's abortSignal, and it is the part people skip. Without it you get a race, which is worth seeing drawn.

The race this exists to kill

A user clicks Next twice, quickly. Two requests go out. Here is what happens when the first one happens to be slower than the second — which is common, not rare, because response times vary:

params must read the signal, and the loader must pass the abortSignal. params: () => this.userId() — the call has to happen inside the callback, because that callback is the reactive context; a signal read anywhere else is invisible to it and nothing will ever re-fetch. And fetch(url, { signal: abortSignal }) is what turns "ignore the stale response" into "there is no stale response". Miss the first and it never updates; miss the second and it updates to the wrong thing.

Declaring a resource

// The input that drives the fetch. Change it and everything below reacts.
userId = signal(1);

userResource = resource({{ '{' }}
  // params is a FUNCTION, so reading userId() inside it registers a
  // dependency. Set userId to 2 and the loader re-runs automatically —
  // there is no refresh() call anywhere in this component.
  params: () => this.userId(),                 // reactive — re-runs the loader
  // The loader receives the resolved params plus an abortSignal.
  loader: async ({{ '{' }} params, abortSignal {{ '}' }}) => {{ '{' }}
    // Passing abortSignal is the line people skip, and it is the best part:
    // if userId changes again mid-flight, Angular ABORTS this request before
    // starting the next. No wasted bandwidth, and no race where a slow
    // response for user 1 lands after user 2 and overwrites the screen.
    const res = await fetch(`/users/${{ '{' }}params{{ '}' }}`, {{ '{' }} signal: abortSignal {{ '}' }});
    // Note fetch does NOT reject on a 404 or 500 — res.ok is what you would
    // check in production before parsing.
    return (await res.json()) as User;
  {{ '}' }},
{{ '}' }});
// What you get back: userResource.value(), .isLoading(), .error(), .status()
// and .reload() — all signals, so the template needs no async pipe and no
// subscription to clean up.

What it exposes

userResource.value()      // Signal<User | undefined>
userResource.status()     // 'idle' | 'loading' | 'resolved' | 'error' | …
userResource.isLoading()  // boolean signal
userResource.error()      // unknown signal
userResource.hasValue()   // type-guard signal
userResource.reload()     // re-run the loader manually
Prefer rxResource (from @angular/core/rxjs-interop) when your loader is an Observable — pass a stream instead of a loader. Both re-run automatically when params change and abort the in-flight request.
The loader's abortSignal is wired to fetch so a stale request is genuinely cancelled when params change. You can write the value locally — userResource.value.set(edited) — for optimistic updates (the status becomes 'local') until the next reload. Returning undefined from a param means "no request" (idle), which is how you defer loading until inputs are ready.

resource() vs the alternatives

Tool Gives you Reach for it when
resource() value + status + error + isLoading signals, auto re-fetch, cancellation reactive reads keyed off a signal (an id, a filter) with real loading/error UI
toSignal(http$) a signal of the latest value a one-shot fetch you just want as a signal; no built-in status/error
manual subscribe() full RxJS control complex streams (debounce, combine, retry) — but you manage state + teardown
route resolver data before the route activates small, critical data that must be present on first paint (blocks navigation)

Under the hood

  • The params callback runs in a reactive context. Angular tracks every signal it reads while producing the request value — much like effect() — and reruns the loader whenever any of them change, not on a timer or a manual trigger.
  • Stale loads are aborted, not just ignored. Each loader call gets its own abortSignal tied to that request's generation; when a newer request supersedes it, that signal fires so a well-behaved fetch actually cancels the network call instead of the response just being discarded client-side.
  • Why it's still @experimental. The shape is stable enough to use, but the loader/stream split and how resources interact with SSR and hydration are still being finalized — the API surface can still shift in a minor release.
  • rxResource cancels by unsubscribing, not aborting. Instead of awaiting one Promise per request, it resubscribes to a fresh Observable from stream on every params change and unsubscribes the previous one — push-based cancellation that naturally supports operators like retry or debounceTime that a raw loader can't.
  • Writing value doesn't touch the loader. userResource.value.set(...) patches the cached signal in place; it's a pure local mutation, so it can't re-trigger params/loader tracking.

Check yourself

Pitfalls that show up in exams & code review

  • Reading params non-reactively. The params callback must read signals so the loader re-runs — a plain variable won't trigger re-fetch.
  • Ignoring abortSignal. Wire it into fetch (or rxResource) so stale requests are actually cancelled.
  • Expecting value() to always be set. It's undefined while loading/idle — guard with hasValue() or isLoading().
  • Observable loader in resource(). Use rxResource with a stream for Observable sources.
  • Forgetting the "no request" signal. Return undefined from a param to stay idle until inputs are ready.

Exam corner

How does a resource know to re-fetch?
Its params callback reads signals; when any change, the loader re-runs and the previous request is aborted.
resource() vs a route resolver?
resource() shows the route immediately and streams data in with loading/error signals. A resolver blocks navigation until small, critical data is ready.
My loader is an Observable — which API?
rxResource from @angular/core/rxjs-interop; pass a stream instead of a loader.

Key takeaways

  • resource() turns async loads into reactive signal state.
  • A change to params re-runs the loader and cancels the old one.
  • Read value, status, isLoading, error as signals.
  • Use rxResource for Observable-based loaders.
