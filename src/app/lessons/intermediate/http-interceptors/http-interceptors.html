An interceptor is a function that stands between your code and the network — every request passes through it going out, every response passes back through it coming in. That's the pitch in every doc, and it undersells three things that actually trip people up in code review and on exams: what you're handed and what you must hand back, what decides the order a chain of them runs in — forward, then in reverse — and what it means for one to end the chain right there, without the request ever reaching the network. This lesson proves all three with a chain you can actually run, then goes further: a real refresh-and-replay flow, and a correction — read straight out of Angular's own source — of a claim about retry() that keeps circulating.

Read the picture first; the words after it only point.

Nothing decides it, because nothing has to. Each box was handed exactly one thing: a next that is a call into the box below it. Calls nest, and nested calls return inside-out — the innermost next returns first, so error sees the response first and auth last. That's a call stack unwinding, and there's no setting that unwinds a stack the other way round.

Picture your request as the smallest doll in a matryoshka set. To send it, you hand it to the outermost doll — auth — which does its bit and passes it to the doll nested inside, and so on down to the backend. To get the response back out, you close the dolls in the only order you can: innermost first. That's the whole reversal — not a setting, a shape. And a doll can hand back something of its own without ever opening the one inside it: that's the escape hatch, three sections down.

Two rules, non-negotiable. req is immutable — .clone() to change anything about it, never assign into it. And whatever you do, the function must return an Observable — either next(...)'s, or one of your own making, on every code path.

The escape hatch

Some interceptors never call next() at all.

An interceptor doesn't have to continue the chain — it has to return an Observable of the right shape, and next(req) is only the most common way to make one. A caching interceptor can serve a stored response directly: the request never reaches the network, and — this is the part people miss — no interceptor further along the array runs either, because there's nothing left to hand them.

On a hit, there's no → REQUEST/← RESPONSE round trip at all — the interceptor answers on its own, instantly, and every interceptor after it in the array is skipped entirely.

Order has teeth

retry() resends the request. It does not refresh your token.

The obvious way to handle a 401 is to redirect to login and retry transient failures along the way:

A tempting "fix" that doesn't work: wrap the 401 branch in retry() and hope a differently-ordered auth interceptor supplies a fresh token on the next attempt. It won't, and reordering auth and error in the array changes nothing about it. retry() only resubscribes to the Observable that the single call to next(req) already produced — and for a request that reaches the backend, that Observable is HttpXhrBackend's own cold XHR dispatch. Resubscribing it fires a new XHR with the exact same req object, headers baked in. This is straight from Angular's own source (chainedInterceptorFn in @angular/common): every interceptor's function body runs exactly once, synchronously, to build the chain for one subscription. retry never re-runs any of that code — going in either direction — no matter where you put auth.

What does get you a fresh token is calling next a second time, yourself, after you've fetched a new one — a genuine, intentional second invocation, not a resubscription. That's a refresh-and-replay interceptor. Under the hood

What withInterceptors([...]) actually builds.

The array isn't iterated per request. At bootstrap, Angular folds it — once — into one function nesting each interceptor inside the next, closing over whichever interceptor should run after it: 

{{ compositionSample }}

That nested arrow you see on the right is a closure: the function Angular hands to a as its next parameter remembers b and everything nested inside it, even after withInterceptors has long since returned. Each interceptor only ever holds a reference to the one closure it was handed — never the whole array — which is exactly why array order fixes wrap order and nothing else does.

  • Requests are cold, end to end. Nothing in the chain runs until your code subscribes to the HttpClient call — directly, via async, or firstValueFrom. Subscribe to the same call twice and every interceptor re-enters from scratch; there's no built-in deduplication of an in-flight request (which is exactly the gap the refresh gate above fills by hand, for one specific case).
  • The innermost next is HttpBackend, not another interceptor. After the last interceptor in the array calls next(req), that call lands on Angular's backend — XHR by default, or fetch with withFetch() configured. Interceptors never see the raw XHR/fetch call, only the HttpRequest/HttpEvent abstraction.
  • Short-circuiting isn't a special API. An interceptor's signature is just (req) => Observable<HttpEvent>, and that's also what next itself returns — next(req) and of(cachedResponse) are both ordinary, correctly-typed return values. That's why TypeScript happily compiles an interceptor that never touches next at all: nothing in HttpInterceptorFn's type requires the body to reference it. What TypeScript does catch — see the mechanism section — is a function that falls off the end without returning anything, which is a much narrower guarantee than "the chain continues."
  • Legacy and functional interceptors can coexist. provideHttpClient(withInterceptorsFromDi(), withInterceptors([...])) folds HTTP_INTERCEPTORS-based classes and functional interceptors into one composed chain — the same out-in-order, back-in-reverse rule applies across the mixed set, with the legacy classes running together as whichever single link withInterceptorsFromDi()'s position makes them.

Pitfalls that show up in exams & code review

The five ways this goes wrong in practice.

  • Returning the wrong Observable, not "forgetting next()". The compiler catches a bare fall-through. What it can't catch is a function that type-checks perfectly but is wired to something that never emits — see the mechanism section's true hang.
  • Mutating the request. It's immutable; use req.clone(...) for every change.
  • Expecting retry() to refresh anything. It resends the same already-built request; it does not re-run any interceptor's code, in either direction.
  • A refresh interceptor with no concurrency guard. Without a shared, replayed gate, N simultaneous 401s produce N refresh calls that invalidate each other.
  • Caching whatever tap sees, unnarrowed. next() emits a stream, not one value — check instanceof HttpResponse before you store anything.

Questions from the back row

Before you go

Six things to remember.

  • An interceptor is one function, two jobs: look at the request, decide whether to keep going. Return next(...)'s Observable, or your own — always.
  • Out in array order, back in reverse. It's not a convention, it falls straight out of nested closures — whichever interceptor is closest to the backend sees the response first.
  • Not calling next() at all is the real short-circuit — a valid, differently-typed Observable, returned instead. Nothing downstream in the array ever runs.
  • retry() resends; it does not refresh. A fresh token needs an explicit second call to next(), guarded so N concurrent 401s produce exactly one refresh call.
  • HttpContext is a typed, per-request channel for your own interceptors — auth opt-outs, loading-spinner opt-outs, anything a call site needs to say without touching a header.
  • finalize is the one operator that runs on all three ways a stream ends — complete, error, or unsubscribe — which is exactly what a loading indicator needs and tap cannot promise.
