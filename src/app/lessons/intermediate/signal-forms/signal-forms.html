Every form API so far in this track has needed its own bespoke object — a FormGroup, a tree of FormControls — kept in sync with whatever state your component actually cares about. Signal Forms deletes the sync problem: you keep the plain signal you already had, and form() wraps it. No parallel object, no two sources of truth. This page builds one signup form from nothing, adding a capability at a time, so the API earns its keep in front of you instead of in the abstract.

The problem

Reactive Forms makes you keep two copies of everything.

A FormGroup is not your data — it is a second object that happens to shadow your data. Want the value somewhere else in your app? You call .value and copy it out. Want to set it from outside? You call .patchValue() and hope the shape matches. The control tree and your actual model are always two things, kept in sync by convention, not by the type system.

Signal Forms starts from a different premise: your model was already reactive. It's a signal. The form doesn't need its own copy of the data — it needs a way to read and write the signal you already have, plus somewhere to hang validation rules and interaction state. That "somewhere" is what form() returns.

If form() takes your signal and hands back something new, what do you think that new thing actually is? A class instance, like FormGroup? A plain object of getters? Keep that guess in mind — the next section answers it, and the answer is stranger than either option.

The mechanism

userForm.email is not a value. It's a function.

This is the one thing every reactive-forms veteran gets backwards on their first try, so it's worth slowing down for. form(mySignal) returns a FieldTree — and a FieldTree is callable. Calling it gives you that field's state. Reading a property off it, like .email, doesn't read a value — it gives you another callable, scoped one level deeper. Nothing resolves to a plain value until you call something.

Think of it like a stack of labelled, sealed envelopes rather than an open filing tray. userForm is the outer envelope for the whole form. userForm.email hands you the next sealed envelope, addressed "email" — still unopened. Only opening it, by calling it, shows you what's inside: the value, plus whether anyone's touched it, plus any errors. You can hold an unopened envelope, pass it around, check its label — but you can't read what's in it without that final call.

Live — the same three lines, typed at

typeof userForm: {{ whatIsIt.theForm() }} typeof userForm.nickname: {{ whatIsIt.theField() }} typeof userForm.nickname(): {{ whatIsIt.theState() }}

value(): "{{ nicknameForm.nickname().value() }}" touched(): {{ nicknameForm.nickname().touched() }}

All three typeof readouts say "function" — the form, the field, and even calling the field once more all land you back on more callables, until .value() finally hands you the string.

.value() is itself a WritableSignal. .touched() flips on blur; .dirty() flips the instant the value differs from its initial one. .errors() is a list, not one message — a field can fail several rules at once. .pending() is true while an async or HTTP validator is still running. Not opposites. valid() needs zero errors and zero pending validators; invalid() only needs one error. A pending field is neither.
Call it once for the tree, call it again for the state. A FieldTree property access walks the shape of your model; calling what you land on is what actually produces a FieldState with signals on it.

Under the hood

What actually happens between a keystroke and a red border.

Notice what's absent: no subscription, no .valueChanges.subscribe(), no manual markForCheck(). [formField] writes to the value signal directly, the schema is re-run automatically because it reads that signal, and the template updates because it reads the resulting FieldState signals. It's signals the whole way down — the form layer doesn't introduce a second change-detection story.

Validation

Rules live next to the shape they validate, not scattered through the template.

schema() takes a function that receives a path matching your model's shape, and you attach validators to pieces of that path — required(p.username, …), minLength(p.password, 8, …). Angular runs the whole schema function once and caches the rules; it does not re-run your setup code on every keystroke, only the individual rule checks that actually depend on what changed.

Live — the signup form, validated

@if (signupForm.username().touched() && signupForm.username().invalid()) { @for (e of signupForm.username().errors(); track e.kind) { {{ e.message }} } }
@if (signupForm.email().touched() && signupForm.email().invalid()) { @for (e of signupForm.email().errors(); track e.kind) { {{ e.message }} } }
@if (signupForm.password().touched() && signupForm.password().invalid()) { @for (e of signupForm.password().errors(); track e.kind) { {{ e.message }} } }
@if (signupForm.confirmPassword().touched() && signupForm.confirmPassword().invalid()) { @for (e of signupForm.confirmPassword().errors(); track e.kind) { {{ e.message }} } }

form valid: {{ signupForm().valid() }} form invalid: {{ signupForm().invalid() }}

The password-match error is attached to Confirm password even though the rule that produced it reads both fields — that's validateTree, next.

Where did Validators.required go? It didn't move — it isn't the same function. required, email, minLength and friends here are a separate export, shaped for a SchemaPath instead of a FormControl. They share a package and a name with the reactive-forms Validators namespace by coincidence, not by design.

Cross-field rules

Some checks can't live on one field, because they need two.

A password-confirmation check can't be a rule on confirmPassword alone — that field's own validator never sees password. It has to run on the tree, with access to the whole model, and then explicitly say which field the resulting error belongs to.

validateTree(p, (ctx) => …) runs with the whole model in scope, but the ValidationError it returns still names a target: fieldTree: p.confirmPassword. That's the same mechanism submit() uses to route a server rejection back to one exact field — cross-field validation and server-error mapping are the same primitive.

Conditional logic

A field can be required only sometimes — reactively, not with an *ngIf guess.

Live — check the box

@if (!signupForm.companyName().hidden()) {
@if (signupForm.companyName().touched() && signupForm.companyName().invalid()) { @for (e of signupForm.companyName().errors(); track e.kind) { {{ e.message }} } }
}

required(p.companyName, …) is registered unconditionally in the schema — it's hidden(p.companyName, …) that decides, live, whether it's currently in force.

Submission

A rejected username isn't a special case — it's one more validation error.

submit() runs your action, awaits it, and — if it returns errors — attaches each one to the exact fieldTree it names. Your template never learns the difference between a client-side rule and a server rejection; both surface through the same .errors() signal.

Live — try the username "admin" (everything else already fills in above)

outcome: {{ submitOutcome() }}

@if (signupForm.username().errors().length > 0) { @for (e of signupForm.username().errors(); track e.kind) { {{ e.message }} } }

The button is disabled while the form is client-side invalid — submit() itself doesn't gate on that for you, so it's worth doing yourself, the same way you would with any other form API.

Concurrent submissions are prohibited — a submit() already in flight for a field (or any ancestor of it) makes every other call on it a same-tick no-op that resolves false without ever running action.

Arrays

No FormArray. A list is just a field whose value is a list.

The FormArray lesson in this track pushes and removes FormControls imperatively — .push(), .removeAt() — and keeps that array of controls in sync with an array of values by hand. Signal Forms skips the imperative half entirely: the model's skills field is a plain string[], and applyEach attaches its rule to every current item and every item added later.

Live

@for (skill of skillsModel().skills; track $index) {
}

skills().valid(): {{ skillsForm().valid() }}

Adding an item means constructing a new FormControl, calling .push(), and trusting nothing else in the component still holds a stale reference to the old array of controls.
Adding an item means writing a new plain array to the signal you already own. applyEach already covers whatever lands in it — there's no second structure to keep in step.

Questions from the back row

Before you go

Five things to remember.

  • form() wraps a signal you already own — there is no second object to keep in sync. The form's data and your app's data are the same signal.
  • A FieldTree and a Field are both callable, not readable. Property access walks the model's shape; calling what you land on produces the FieldState with signals on it.
  • valid() and invalid() are not opposites — a field with a validator still pending is neither.
  • Cross-field checks and server errors use the same mechanism: validateTree and submit()'s action both return a ValidationError tagged with the exact fieldTree it belongs to.
  • hidden() only sets a signal — it does not remove anything from the DOM for you. That part of the job is still the template's.
