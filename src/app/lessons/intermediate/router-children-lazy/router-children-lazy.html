Split your app wrong and every visitor downloads all of it, whether they'll ever see most of it or not. Split it right and a route feels instant the first time someone visits it and instant every time after. This page takes apart how routes nest — one shell, many rooms, one outlet — and how code splits — a component, a whole feature, or a block within a page — with a live simulation proving each answer, not just stating it.

The problem

Everything, downloaded before anyone clicks anything.

Here's the default, if you do nothing special: every component your app can ever show, for every route, bundled into one file, downloaded before the visitor has clicked a single thing. A hundred lessons' worth of JavaScript, for someone who came to read one of them.

Two separate questions fix two separate parts of that — and people routinely answer the first while thinking about the second, which is where most of this topic's bugs come from:

  • Which outlet does a route's component render into? (nesting)
  • Has that component's code even arrived yet? (splitting)
  • Does code the visitor isn't allowed to see get downloaded anyway? (guarding)

The mental model

Your app is a building, not a room.

Picture the whole app as a building under construction. Each top-level route is a floor. <router-outlet> is the doorway into whichever room on that floor is currently open — and a route's children are the rooms sharing that one doorway, swapped in and out as you move around, without the floor itself ever being torn down and rebuilt.

Lazy loading is the same building, on a stricter budget: the floors aren't all pre-built. The first time anyone asks to go to floor nine, construction happens — that's the download — and then it stays built for the rest of the visit. Ask again, and there's nothing left to build.

canMatch is a receptionist who won't even call the construction crew for a floor you're not cleared for. canActivate is a guard standing at an already-built floor's door, checking your badge after the elevator has already arrived.

One doorway, many rooms. A component route builds one shell and one outlet; its children only ever swap what's showing inside that same doorway. The shell goes up once and comes down only when you leave its whole subtree — never when you move between the rooms inside it.

The mechanism

One shell. Many rooms. One doorway.

Angular compiles nested routing down to exactly what the building metaphor describes: one component owns an outlet, and its children's routes are matched relative to it and rendered inside it.

A componentless route is a pure grouping device. It never adds a ring to the diagram below — its children render straight into whichever outlet was already there, one level up:

What a componentless route buys you — everything a route can carry, except a place to render:

Runs once for the whole group. A user who fails it never reaches any child underneath — no wrapper component required to attach it to. Static config every child can read off its own ActivatedRoute — a flag, a title, a permission level — without a component to hold it. A child injector for the whole subtree. One service instance, shared by every child route, torn down only when the group is left entirely. Every child's path is written relative to this one, exactly as it would be under a component route — grouping costs nothing here.
Componentless parents are also where params/data inheritance to children is on by default (paramsInheritanceStrategy: 'emptyOnly') — a child under a componentless parent can read the parent's resolved data and params as if they were its own, because no component-with-its-own-scope sits between them.

The failure mode nobody warns you about

Switch rooms, and the floor stays standing.

This is the direct, load-bearing consequence of "one shell, many rooms": when you navigate between sibling children — /settings/profile → /settings/security — the router destroys only ProfileTab and creates SecurityTab. SettingsShell keeps the exact same instance. No ngOnDestroy, no ngOnInit, nothing re-runs on it at all.

Three consequences fall straight out of that, and all three are things people get bitten by in production:

  • Data the shell loaded once — a user profile, a list of settings sections — stays loaded. It does not refetch every time a tab changes, which is usually exactly what you want.
  • A guard on the shell's own canActivate runs once, on first entry, and never again for a sibling switch. A session that expires mid-visit, or a permission that differs per tab, needs canActivateChild instead — the one guard type that re-runs on every child activation.
  • A service in the shell's route providers lives for the whole subtree and is destroyed only when you leave /settings entirely — not when you move between its tabs.
You load /settings/profile, click over to /settings/security, then back a couple of times. Does SettingsShell's constructor — the code that runs once per instance — fire again on any of those clicks? The live counters below will tell you for certain.

Splitting the bundle

The floor isn't built until someone asks for it.

loadComponent and loadChildren are how you tell Angular "don't build this floor yet." Both take a function returning a dynamic import() — code the bundler cuts into its own chunk and the browser fetches only when that function actually runs.

This entire tutorial app uses loadComponent — every lesson is its own lazy chunk, which is why the initial bundle stays small while the app has 100+ lessons.

Three ways to split — pick by how much you're splitting

loadComponent one standalone component into a chunk a single lazy page
loadChildren a Routes array (a whole feature) into a chunk a feature area with several routes
@defer a block within a page below-the-fold / heavy widgets, no URL of their own

Verify, don't assume

Your bundle is still 900 kB. Why?

loadComponent being present in the route config is necessary but not sufficient — the bundler still has to agree that nothing outside the dynamic import() reaches into that folder. One stray import from the app's eager graph is enough to undo it, and the route config keeps reading as if nothing were wrong.

Rule to remember: only types may be imported eagerly from a lazy feature (import type), never a value. And set a bundle budget in angular.json so a build that quietly grows past it fails loudly instead of shipping.

Guard the download

canMatch stops the fetch. canActivate stops the render.

A subtle but genuinely important distinction. canActivate runs after the lazy chunk is fetched — so an unauthorized user still pays for the download. canMatch runs before matching, so a failing guard skips the route entirely and the chunk is never requested (and the router can fall through to another route with the same path):

canMatch decides whether to fetch. canActivate decides whether to render what's already been fetched. Failing the second one never refunds the download.

Scoping services to a feature

A reception desk for one floor.

A route can declare providers. They create a child injector for that route's subtree, so a service can be scoped to one feature instead of the whole app — created the moment you enter the feature, and shared by one instance across every route inside it:

Feature service leaking to root. If ShopApi is also registered providedIn: 'root', the route's providers entry doesn't scope it — the root registration already satisfied the injection, so the route-level one never gets a chance to run. Drop the root registration to actually keep it feature-local.

A second doorway

One floor, two doors.

Every outlet so far has been the same one — the default, unnamed primary outlet. A named outlet is a second one, opened and closed with its own piece of the URL, independent of whatever the primary outlet is showing:

A named-outlet route needs its outlet property set, or it silently targets primary instead — and each named outlet gets its own independent ActivatedRoute tree, so a guard or resolver on it never sees the primary route's params.

Paying the cost early, on purpose

Fetch it before anyone asks.

Lazy chunks load on demand by default. A preloading strategy fetches them in the background after the app boots, so later navigation feels instant without bloating the initial bundle:

How much of the building gets pre-built in the background
Strategy Behaviour
(none, default) each chunk downloads on first navigation to it.
PreloadAllModules after boot, background-fetch every lazy chunk.
custom strategy preload only routes you flag, e.g. data: { preload: true }.
ngx-quicklink community: preload chunks for the links currently in the viewport.

Pitfalls that show up in exams & code review

The traps, collected.

Seven traps, and the one-line fix for each
Pitfall Why it bites Fix
pathMatch: 'full' missing on an empty redirect The default 'prefix' matches every URL, so the redirect matches itself and loops. Add pathMatch: 'full'.
Guarding a lazy route with canActivate only The chunk still downloads before the guard denies entry. Use canMatch to skip the download entirely.
loadChildren resolves to the wrong shape It must resolve to a Routes array — a named export or the file's default export. A component class, an NgModule, or a plain object breaks at navigation time, not at build time. Export a Routes array (named or default) from the target file.
A stray value import un-lazies a route Bundler analysis sees the eager graph reaching into the "lazy" folder and inlines it. Only import type from a lazy feature, eagerly; verify with the ng build chunk list.
Feature service leaking to root If it's providedIn: 'root', route providers can't scope it. Drop the root registration to keep it feature-local.
Preloading everything on a huge app PreloadAllModules can flood the network right after boot. Prefer a flag-based custom strategy at scale.
ChunkLoadError after a redeploy A stale tab resolves a content-hashed chunk filename that no longer exists on the server. Catch it globally and reload — see below.

Questions from the back row

Before you go

Six things to remember.

  • A component route builds one shell with its own outlet; a componentless route (children with no component) adds nothing to render — its children render into whichever outlet was already there, one level up.
  • The shell isn't rebuilt when you move between its child routes. Data it loaded stays loaded, its canActivate doesn't run again, and its providers stay alive — all correct, and all reasons a per-tab guard needs canActivateChild instead.
  • loadComponent splits one component into a chunk; loadChildren splits a whole feature; @defer splits a block within a page that never gets its own URL.
  • A chunk being lazy in the route config doesn't make it lazy in the bundle. A stray value import from the eager graph silently un-lazies it — verify with the ng build chunk list, not by reading the syntax.
  • canMatch gates the download; canActivate gates the render. Only canMatch returning false can stop the fetch from happening at all.
  • Route providers scope a service to one subtree with a child injector; withPreloading fetches lazy chunks in the background so the first visit isn't the one that pays.
