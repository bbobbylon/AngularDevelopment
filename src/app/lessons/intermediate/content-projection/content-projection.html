Content projection lets a parent hand a child component real, live markup — not a string, not a config object, actual DOM — and let the child decide only where it goes. <ng-content> is the placeholder that makes it possible, select lets one component offer several different slots for different kinds of content, and contentChild() / contentChildren() let the child find what was handed to it. Nearly everything confusing about it disappears once you accept one fact: the child never builds what it hosts.

The problem

How do you let someone else's markup live inside your component?

Say you're building <app-callout> — a bordered box for a warning message. Simple enough, until you ask what actually goes inside it. Sometimes it's a sentence. Sometimes it's a sentence with a link. Sometimes it's a whole little form. You cannot write a message: string input for all of that, and you certainly cannot anticipate every combination in advance.

What you actually want is stranger than an input: you want the caller to hand you real markup — components, event bindings, structural directives, all of it — and for your job to be nothing more than deciding where that markup lands. That's not a value passed in. It's a hole left open on purpose.

Suppose Callout's own stylesheet has a rule targeting strong. The caller writes <app-callout><strong>Heads up!</strong></app-callout>. Does the caller's <strong> pick up Callout's style? Commit to an answer before you read the next section — it explains exactly why.

The mental model

A component with <ng-content> is a picture frame.

It decides the shape of the opening and everything around it — the border, the mount, the hook on the back. What it never does is make the photograph. The photo was printed somewhere else, by someone else, on their own paper.

Hold onto that and three otherwise-baffling behaviours become obvious. The child's styles do not reach the projected content, because the frame did not print the photo — which answers the napkin question above: no, Callout's strong rule never touches it. The child cannot use viewChild to find it, because a view query searches only what the child itself drew. And the photo gets printed whether or not the frame ever hangs on a wall — which is the trap a few sections down.

View is yours; content is theirs. viewChild searches your own template; contentChild searches what was handed in from outside. One question settles it every time: did this component's template contain that node?

The trap, said a second way

Why does my second <ng-content> render nothing?

Projection is a distribution, not a broadcast. Every projected node goes to exactly one slot — and only one bare <ng-content> in a template can be the catch-all.

Choosing a query

Which query am I even supposed to use?

Projection vs. ViewChild — the one question that decides it
Situation Use
Query something inside the component's own template viewChild() / viewChildren()
Query content projected from the parent contentChild() / contentChildren()
Access a projected element's DOM node contentChild(SomeDirective) then .el.nativeElement
Query projected components (not directives) contentChildren(MyComponent)
Projected content keeps its original injection context. The projected nodes are created by the parent, not the child. This means services, tokens, and lifecycle hooks belong to the parent component tree, not the child that hosts the ng-content.
Projected content is always instantiated eagerly, even if its ng-content slot is hidden by @if in the child. To truly defer projection, use @defer in the parent or pass a template reference (TemplateRef) and render it lazily via NgTemplateOutlet.

Questions from the back row

Before you go

Six things worth carrying into the exam.

  • <ng-content> is a relocation point, never a factory — it never builds what it shows, it only decides where already-built markup appears.
  • Projected content is compiled into, and belongs to, the parent's view — its styles, its injector, its lifecycle. That's why the child's CSS can't reach it and viewChild can't find it.
  • select routes matching nodes to named slots; the one bare <ng-content> left over is the catch-all, and a second bare one is always empty.
  • Fallback markup inside <ng-content> shows only when that exact slot receives nothing — not "less content", genuinely nothing.
  • contentChildren(Token) is a live signal over projected directives/components, resolved by ngAfterContentInit — read it any earlier and it's empty.
  • Projected content is instantiated eagerly, with the parent, whether or not the child ever displays it. If that's expensive, @defer in the parent or a TemplateRef is the fix — not an @if in the child.
