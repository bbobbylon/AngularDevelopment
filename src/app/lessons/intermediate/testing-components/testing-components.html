TestBed builds a real — but headless — copy of your component so you can render it, click it, type into it, and assert on the result. Almost every confusing test failure comes from one gap: something changed in memory, but nobody told the screen. This page is about closing that gap on purpose, every time.

The problem

It works when you click it. How do you prove that to a robot?

Here's a real, running component. No test has touched it yet — it's just an ordinary Angular component, rendered on this page right now.

Live — click it a few times

This is exactly the shape of component every sample on this page tests: one signal, one button, one thing that should happen when you click it.

You just proved it works, with your own eyes and a mouse. But your eyes don't run in CI, and neither does your mouse. Six months from now someone edits this component while chasing an unrelated bug, and nothing on this page will warn them if the button quietly stops incrementing. Something else has to click it, read the screen, and speak up — automatically, on every commit, forever.

Keep an answer in your head: what would it take to write code that clicks that button and checks the count went up, without a real browser window? You don't need the exact API — just the shape of the problem. The rest of this lesson is Angular's answer, one piece at a time.

The mental model

TestBed is a film set. Your component gets a stunt double.

TestBed.configureTestingModule() builds the set: it declares which imports and providers exist for this scene, exactly the way a real component's own imports array would. Nothing is standing on it yet.

TestBed.createComponent(Counter) is where the stunt double walks out — a real instance of your component class, constructed for real. But the stage is empty: this double isn't attached to the actual page you'd see in a browser, there's no router watching it, and nobody has called action yet. It is a component that exists but has never been asked to perform.

The ComponentFixture that call hands back is your remote control for that double. fixture.nativeElement lets you read what's currently on the little screen. fixture.debugElement lets you press its buttons without a real finger — .triggerEventHandler('click') instead of a physical click. But the screen stays blank and the buttons do nothing believable until you press the one control that actually starts the performance: fixture.detectChanges(). That's "action" — it runs ngOnInit, evaluates every binding for the first time, and only then is there anything real for your remote to read.

Build the set, cast the double, hand yourself the remote. configureTestingModule() builds the set, createComponent() casts the double onto an empty stage, and the ComponentFixture it returns is your remote — nothing airs until you press detectChanges().

The everyday case

Clicking and typing look easy. One line makes or breaks them.

Setting .value in code is not the same as typing. Angular's form directives listen for a real 'input' event — set the DOM property directly and the model never hears about it.

The shortcut

Can Angular just check for you? Sometimes — and it's a trade.

The trade-off: auto-detection hides when rendering happens, which makes timing bugs harder to spot. Prefer explicit detectChanges() while you're learning, or in any test where render order is the thing actually under test.

Change detection in a test is manual by default. A signal write, a mutated field, a resolved promise — none of them paint the DOM by themselves. Only detectChanges() (or autoDetectChanges(true)) does, so call it after every state change your assertion depends on.

Time, but controllable

Timers and promises don't wait for your assertions. Make them.

fakeAsync gives you a clock you can move by hand — use it for anything driven by setTimeout, setInterval or a debounced stream.

The error you will hit: "1 timer(s) still in the queue." fakeAsync throws if the test ends with work left over — a deliberate safety net that catches an interval you forgot to clear in ngOnDestroy. Fix it by flushing, or by discardPeriodicTasks() when a repeating timer is intentional.

Promises and HTTP calls are a different animal: they settle on a real clock, so you wait for them instead of fast-forwarding.

Dependency Recommendation
HTTP (an ApiService) Mock — via HttpTestingController or a vi.fn() stub
Router Use real — provideRouter([]) is cheap and catches genuine navigation bugs
Signal stores (pure signals, no HTTP) Use real — cheap, fast, and a fake teaches you nothing extra
localStorage / other browser APIs Mock — side-effectful and environment-dependent
Child components Depends — real for an integration test, stubbed for a narrowly focused unit test

Questions from the back row

Before you go

Six things to remember.

  • Nothing renders until you tell it to. createComponent() builds; only detectChanges() (or autoDetectChanges(true)) paints — every "why is my query returning null?" bug traces back to that gap.
  • Two query styles, two jobs: nativeElement for plain DOM reads, debugElement + By when you need Angular awareness — By.directive() by type, triggerEventHandler() for outputs with no real DOM event.
  • Match the async tool to what's actually pending. fakeAsync + tick() for timers on a clock you control; whenStable() (or a plain await) for promises and HTTP that settle on their own. A repeating interval hangs whenStable() forever.
  • Signal inputs go through fixture.componentRef.setInput(), never component.someInput = … — it's the path a real parent uses, and what actually marks the component dirty. Flush pending effects with TestBed.tick(); flushEffects() is the same thing under its old, deprecated name.
  • Mock only what's expensive, slow or unpredictable — HTTP, localStorage, timers. Test real signal stores and real reactive forms; a fake version of something cheap teaches you nothing extra.
  • A green test only proves what it actually looked at. Assert what a user would see, not an internal flag — and check the "before" state (a spinner, a disabled button) as carefully as the "after".
