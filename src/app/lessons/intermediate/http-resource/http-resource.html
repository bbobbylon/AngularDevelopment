The resource() lesson built the mental model by hand: a reactive request, a loader, a handful of signals describing what happened. This page assumes that model and asks one question — what changes when the loader is HttpClient instead of your own fetch() call? The answer is smaller than it looks, and one specific piece of it is the whole reason this page is allowed to run a real, live request in your browser right now.

The problem

You already built the loader. What's still missing?

Go back to resource-api's own loader for a second: a fetch() call, an if (!res.ok) throw …, a manual parse. It works. But it works outside everything else your app already knows about HTTP:

  • An interceptor that stamps an auth header on every request never sees this one — fetch() doesn't go through it.
  • A failure arrives as whatever you threw, not a structured HttpErrorResponse with a real status code.
  • Angular's own testing backend, HttpTestingController, has nothing to intercept — there's no HttpClient call to catch.

httpResource() is resource() with the loader already written for you — using HttpClient underneath, which is what closes all three gaps at once. Same four signals, same reactive-request rule — the difference is entirely in what that loader plugs into.

The mental model

You stop walking your own package to the post office.

A hand-rolled fetch() loader is you, personally, carrying a package to the post office, filling out your own customs form, and finding out it was rejected by prying the box back open yourself. httpResource() drops the same package in the building's internal mailroom instead. Everything that goes through the mailroom automatically clears the building's checkpoints — and you never had to know a single checkpoint's policy to benefit from it.

httpResource() is still shaped for reads, not mutations — it is resource() with a different loader, not a general-purpose replacement for calling HttpClient directly. Keep that in mind; it comes back later on this page.

The mechanism

Nothing is sent until the request factory says so.

A request factory that reads undefined doesn't produce "an empty request" — it produces no request at all. status() stays 'idle', nothing touches the network, and — this matters more than it sounds like it should — no cleanup task is left open for anything waiting on this component to go quiet.

What's actually new

Everything resource() has, plus three HTTP-specific signals.

value, status, error, isLoading, hasValue(), reload() — all of it carries over unchanged from resource-api. What HttpResourceRef adds sits entirely on top:

@for (item of newSignals; track item.heading) { {{ item.body }} }

Beyond a bare URL

When a string isn't enough, the factory returns an object instead.

Everything so far returned a plain URL string. The moment you need query parameters, headers, or a default value while nothing has loaded yet, the factory returns a request object instead — same reactive rule, more to configure.

The anti-pattern

A resource is state kept in sync. A click is a command.

Because the request factory re-runs on any signal it reads changing, it's tempting to reach for httpResource() for a mutation too. Resist it — a resource doesn't know or care why a dependency changed, which is exactly wrong for an action that should fire once, on purpose.

A query signal drives a search resource. Typing changes the signal, the factory reactively re-fires, and the results genuinely should reflect whatever was typed most recently. This is precisely what httpResource() is for — even shaped as a POST with a search body.

A "liked" signal is read inside an httpResource() factory to POST a like. It fires once on the click that flips the signal — and again if anything else that factory reads changes for unrelated reasons, silently re-sending the like. Call http.post() directly from the click handler instead.

Testing

The request goes through HttpClient — so a test can actually catch it.

This is the payoff of "wired to HttpClient" made concrete: HttpTestingController can intercept and flush a request an httpResource() fired, the same way it would for any HttpClient call. A hand-rolled fetch() loader gives a test nothing to grab onto.

That flush() call is the one step neither this page's live demo above nor an un-clicked httpResource() in a mounted-but-untouched lesson ever gets. Which is exactly why the live panel on this page had to stay idle until you clicked it — a request this exact page's own automated smoke test never flushes would simply hang that test forever.

Questions from the back row

Before you go

Four things to remember.

  • httpResource() is resource() with an HttpClient loader already written — same four signals, same reactive-request rule, but interceptors, structured errors and a testable backend come for free.
  • A request factory returning undefined means no request, no pending task — the idle mechanism this page's own live demo depends on to be safely live at all.
  • error() holds a real HttpErrorResponse — read .status and .error, never interpolate the object itself.
  • headers(), statusCode() and progress() are the only genuinely new signals. Everything else is the resource() contract you already know — and it's still shaped for reads, never a substitute for calling HttpClient directly on a click.
