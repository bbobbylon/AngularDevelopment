Every navigation is a small pipeline — recognise the URL, check the guards, run the resolvers, activate the components — and router.events is the play-by-play of that pipeline, emitted live as it happens. This page is about reading that stream: the order things really fire in, the four different ways a navigation can end, and the bug you get for assuming there's only one.

The mental model, in full

router.events is the announcer, not the referee.

Here's the loading-bar problem from the block above, in full. Not a spinner inside one component — a bar across the very top of the page, the kind every big app has, that appears the instant a link is clicked and disappears once the new page is ready. It can't live inside the page being navigated to, because that page doesn't exist yet when the bar needs to appear. It has to sit somewhere that outlives any single route and can see navigations as they happen, from outside — and that "somewhere" is router.events, an Observable on the injected Router that emits one value per meaningful step of every navigation, success or not.

A stadium announcer calls the game as it happens — every fan in the building hears the same call, live. But the announcer does not decide anything. A referee's whistle happens first; the announcer just tells the crowd about it a beat later. Shout at the announcer's booth all you want — the call already stands.

router.events is the announcer. Guards and resolvers are the referees — they are the only things that can actually change what a navigation does. By the time an event reaches your subscriber, that decision has already been made and cannot be unmade from inside a .subscribe().

Events narrate. Guards decide. If you need to allow, block or redirect a navigation, that's a guard. If you only need to react to one — a loading bar, an analytics ping, a scroll reset — that's router.events. Reaching for the wrong one is the single most common mistake on this page's topic.

The mechanism

One navigation, one strict order.

Angular's own EventType enum lists these events in declaration order — NavigationStart, NavigationEnd, NavigationCancel, NavigationError, RoutesRecognized… — which is not the order they actually fire in. Declaration order is alphabetical-ish convenience for the framework's source file. The real order is a strict pipeline, and every event class's own doc comment says exactly where it sits in that pipeline.

Question answered by the demo

Four ways in, exactly one way out — but four different "out"s.

Every navigation resolves to exactly one of these. A UI wired to only the first one is wired to roughly a quarter of reality.

Carries urlAfterRedirects. The only outcome that means the new route is actually live. A guard returned false, a resolver produced nothing, a redirect superseded it, or a newer navigation preempted it. Carries a stable code — use that, not the human-readable reason string, for any branching logic. An unexpected exception during the pipeline. Carries error and, when available, a target snapshot. withNavigationErrorHandler (below) is the centralised place to react to these. The router decided not to navigate at all — most often because the target URL is identical to the current one. Distinct from cancel: nothing here was "aborted," because nothing was ever tried.

Centralising the error case

One handler can quietly change which event fires.

withNavigationErrorHandler is a provideRouter feature: one function, configured once, that runs for every NavigationError in the app instead of a check repeated in every interested subscriber. Its return value matters more than it looks like it should.

Returning a RedirectCommand suppresses the error. The navigation still ends, but as a NavigationCancel with code: Redirect instead of a NavigationError — so any other part of the app watching specifically for NavigationError will not see this one.

Questions from the back row

Before you go

Six things to remember.

  • router.events narrates; it doesn't decide. It's the announcer, not the referee — change a navigation's outcome from a guard or a resolver, never from a subscriber.
  • The EventType enum's declaration order is not emission order. The real order is NavigationStart → (lazy-load, if uncached) → RoutesRecognized → the guard phase → the resolve phase → one terminal event.
  • ChildActivationStart/ActivationStart/ActivationEnd/ChildActivationEnd nest inside the resolve phase, firing after ResolveStart and before ResolveEnd — not after resolution finishes.
  • A navigation ends exactly one of four ways — NavigationEnd, NavigationCancel, NavigationError, NavigationSkipped — never more than one, and a UI that only listens for the first gets stuck on any of the other three.
  • Cancel and error carry a stable code — use it for logic; the reason string is for humans reading a log, not for branching.
  • withNavigationErrorHandler centralises error handling, and returning a RedirectCommand from it replaces the outcome with a redirect-flavoured cancel — the NavigationError it was reacting to never fires.
