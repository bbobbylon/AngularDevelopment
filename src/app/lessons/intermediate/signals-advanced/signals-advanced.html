signal, computed and effect cover most of what you need — until state has to be both derived and overridable, or you need to read a signal without reacting to it. This page is the tool built for the first gap, linkedSignal, plus untracked for the second, and effect cleanup and custom equality along the way.

The problem

What do you do when "derived" also needs to be overridable?

Picture a dropdown whose options come from the server. You want a sensible default selected — say, the first item — but the user should be free to pick something else. And when the list reloads (a refresh, a filter change), the right thing to happen is for the selection to reset, because whatever the user had chosen might no longer make sense at all.

Try to build that with what you already have, and both tools refuse in a different way. A plain signal holds whatever you last wrote — it never resets on its own, so a stale, no-longer-valid selection sits there quietly after a reload. A computed would reset perfectly... except it's read-only: the moment a user clicks a different option, you have nothing to write to. Angular's answer is a signal that does both — writable, and re-derived on demand.

The mental model

linkedSignal is a formula cell you're still allowed to type over.

Signals Basics introduced the spreadsheet: a signal is a cell holding a value, a computed is a cell holding a formula, and an effect is a cell that does something when its inputs change.

linkedSignal is the one that analogy explains best. It's a formula cell you are allowed to type over. Enter something by hand and it keeps your entry — right up until one of the formula's own inputs changes, at which point the formula reasserts itself and your entry is gone. That is not a bug in the metaphor; it is precisely the behaviour, and it is why "selected item" state is the textbook use case.

computed is a formula. linkedSignal is a formula you can type over. If you're writing an effect whose whole body copies one signal into another, you wanted one of those two instead.

The decision

Four tools, one fork in the road: who can overwrite the value?

Every one of these questions collapses to the same fork. Once a value can be derived from other signals, the only thing left to decide is whether a human is also allowed to write to it directly.

Not derived from anything. You write it directly, and it holds whatever you last wrote until the next write. Derives from other signals and can't be written to at all — Angular throws if you try. Correct whenever nothing needs to override the result. Derives from a source like computed — and stays writable like signal. The catch, and the whole point: a source change throws your write away and re-derives. Nothing to read at all — it exists purely to do something (log, save, redraw) when its dependencies change. Reaching for it to copy one signal into another is the mistake this page opens with.

The trap worth naming out loud: reaching for effect to copy one signal into another. That's a second source of truth, one tick behind the first — computed and linkedSignal are synchronous and glitch-free, while an effect runs only after render, adding a change-detection pass for nothing.

The writable derivation

linkedSignal resets on purpose. That's not a bug to work around.

A computed is read-only; a linkedSignal can be written and recomputes when its source changes. The textbook case is exactly the dropdown from the top of this page.

The deliberate blind spot

untracked reads the value. It just won't tell anyone it did.

Inside a computed or an effect, reading a signal subscribes to it — that read is what lets the framework find you again later. Wrap the read in untracked() and you get the value without the subscription.

untracked() removes an edge, not a value. The write still lands — only the notification is skipped, which is why the number sits there visibly wrong until something unrelated forces a recompute.

Side effects

Whatever your effect opens, something has to close it.

An effect's callback can take a second, optional job on top of running: its first parameter, onCleanup, is where you register teardown work for whatever this run just started.

Skip it and every re-run — or every destroy — leaves the previous timer, subscription or listener running invisibly beside the new one. That's a leak that never throws, so nothing tells you it's there until a profiler does.

Equality

Not every difference should count as a change.

By default a signal decides "did this change?" with Object.is — reference equality for anything that isn't a primitive. Pass your own equal function and you get to redefine what "changed" means.

A custom equal works on computed too, not only on writable signals — see the FAQ below for the case where that is genuinely the fix rather than a curiosity.

The advanced form

Give the computation a memory, and it can choose to keep your pick.

The one-argument shorthand from earlier always resets unconditionally — it has no idea what the previous selection was, because nothing ever told it. Angular's object form hands the computation exactly that memory.

Reach for this form specifically when the rule is "keep the selection if it's still valid, otherwise reset" — the plain one-argument form can only ever do the second half.

Under the hood

The graph pulls. Nothing runs until something asks.

Signals form a dependency graph of producers (writable signals) and consumers (computed, effect, views). Read a signal inside a reactive context and Angular records an edge: "this consumer depends on that producer." Dependencies are therefore dynamic — an if branch not taken this run creates no edge, and untracked() deliberately skips recording one on purpose.

Six steps run between a write and the screen. The fifth is the one people forget, and it explains both "why didn't this update?" and its mirror image, "why did everything update?":

  • Pull, not push. Writing a signal doesn't eagerly recompute anything — it just bumps a version number and marks dependents "dirty". A computed only re-runs when someone actually reads it and finds a dependency changed. Untouched computeds cost nothing.
  • Memoized. A computed caches its last value and returns it until a dependency's version changes — so reading it ten times runs the formula at most once.
  • Glitch-free. Because evaluation is synchronous and pull-based, a reader never observes a half-updated graph (an intermediate "glitch") the way a chain of effects copying values can.
  • Equality gates propagation. After recomputing, a signal compares new vs old with its equal fn (reference by default). If equal, dependents are not notified — the ripple stops early.

The traps, collected

Five ways this bites — and the fix for each.

the mistake, and what actually happens
The mistake What actually happens
Using effect to sync one signal to another Prefer computed/linkedSignal — synchronous, glitch-free, no extra CD pass.
Writing to a signal inside a computed Computeds must be pure. Set signals only in event handlers or effects.
Reaching for untracked everywhere It silently breaks reactivity. Use it only to deliberately exclude one dependency.
Forgetting effect cleanup for timers/listeners Return work through onCleanup or it leaks across re-runs and on destroy.
Mutating an object/array in place then set-ing it Default equality is by reference; pass a fresh value (or a custom equal) so readers update.

Questions from the back row

Before you go

Four things to remember.

  • linkedSignal = derived AND writable, and it resets from its source — that reset is the whole point, not an edge case to guard against.
  • untracked() removes an edge, not a value. The write still lands; only the notification is skipped.
  • The onCleanup callback tears down work before the next run and on destroy — a timer or socket that never registers one leaks quietly.
  • A custom equal fn stops needless notifications for data that only looks new — reference equality is the default for a reason, and overriding it is a deliberate trade.
