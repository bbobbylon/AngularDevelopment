Resolvers & Route Data

A resolver fetches data before a route activates, so the component renders with its data already present — no in-component loading flicker, no empty first paint. Static data attaches fixed values to a route. The catch: resolvers block navigation, so they carry rules (complete or hang, keep them fast, handle errors) that this page drills with live simulations.

The problem a resolver solves

Fetch data inside the component and the route activates instantly with nothing to show — you paint a spinner, then swap in the data (a "flicker"). A resolver moves that wait to before activation: the old view stays up while data loads, then the new route appears already populated. Same total time; very different feel. Where resolvers run — the navigation pipeline

Resolvers are not the first thing the router does. A navigation runs a fixed pipeline, and resolvers sit near the end — they only run once every guard has passed, so you never waste a fetch on a route the user isn't allowed to enter: 

{{ pipelineSample }}
All resolve keys on the activated route (and its resolved parents) run in parallel, and navigation waits for all of them. One slow resolver holds up the whole transition — the route is only as fast as its slowest resolver. That is also why guards run first: an unauthorized user should be redirected before you pay for the data.

With provideRouter(routes, withComponentInputBinding()) (enabled in this app), each resolve key, path param and query param is bound straight to a matching component input() — no ActivatedRoute plumbing. The input name must equal the resolve key. Prefer the observable route.data over snapshot.data when the same component instance is reused across param changes (see runGuardsAndResolvers below) — the snapshot is frozen at activation and won't update on re-resolve.

An Observable resolver must complete

This is the number-one resolver bug. The router subscribes to your resolver and waits for it to complete, not just emit. An HttpClient call completes after one value, so it's fine. But a long-lived stream — a Subject, valueChanges, a store select(), interval() — emits and keeps going, so the router waits forever and the navigation silently hangs. Take one value with first() (or take(1)) to force completion:

If a resolver errors (or its Observable errors), the navigation is cancelled and the router emits NavigationError — the user is left on the current page with no route change. Always catch and decide: redirect, return an empty/placeholder value, or rethrow to a global handler.

Re-running: runGuardsAndResolvers

Navigate from /users/7 to /users/9 and Angular reuses the same component instance. By default the resolver does not re-run on a query-param-only change — which is a classic "why is my data stale?" bug. The route's runGuardsAndResolvers controls exactly when:

Value Re-runs guards + resolvers when…
'paramsChange' (default) a matrix/path param changes (:id). Query-only changes do not re-run.
'pathParamsChange' only a path param changes — ignores matrix params like ;view=grid.
'paramsOrQueryParamsChange' any param or query param changes — use when ?page=2 should refetch.
'pathParamsOrQueryParamsChange' path params or query params (ignores matrix params).
'always' every navigation that lands on this route, even same-URL. Combine with onSameUrlNavigation: 'reload' to support a "refresh" click.
a function you return a boolean from (from, to) => boolean for full control.

Resolver, resource(), guard, or component fetch?

Resolvers are not always the answer. Blocking navigation for a big or slow fetch makes the app feel frozen — the user clicks and nothing happens. Match the tool to the data:

Use… When Trade-off
Resolver Small, fast, must-have data the first paint depends on (the user record for a profile page). You'd rather delay the route than flash an empty shell. Blocks navigation; a slow resolver = a frozen click. Keep it fast.
resource() modern Data that can stream in after the route shows. Render the shell immediately, load reactively, drive skeletons off isLoading. Re-fetches when its params signal changes. You design the loading/empty/error states in the template.
Guard (CanActivate) Deciding whether the route may activate (auth, feature flag) — not fetching its content. Returns boolean / UrlTree / RedirectCommand, not data.
Component fetch Secondary or below-the-fold data, or anything where a spinner is acceptable UX. First paint has no data — plan the flicker away with skeletons.
Rule of thumb in the signals era: reach for resource() first for responsiveness, and keep resolvers for the small, critical, must-be-present-on-first-paint data.

Pitfalls that show up in exams & code review

  • Non-completing Observable → hung navigation. The router waits for completion, not the first emission. Pipe first()/take(1) onto any long-lived stream you resolve.
  • Reading snapshot.data when the route is reused. On a param change with runGuardsAndResolvers, the snapshot is stale — subscribe to route.data or bind an input() instead.
  • Query-param changes don't re-resolve by default. Add runGuardsAndResolvers: 'paramsOrQueryParamsChange' when ?page= or ?sort= must refetch.
  • Heavy resolver = frozen app. Users perceive the whole app as hung during a slow resolver because the URL hasn't changed yet. Prefer resource() for anything that can stream in.
  • Unhandled resolver error kills the navigation. It's a NavigationError, not a component-level catch — handle it in the resolver (redirect / EMPTY / fallback value).

Exam corner

Your resolver returns store.select(x) and the page never loads. Why?
The selector is a long-lived Observable — it emits but never completes, so the router waits forever. Add .pipe(first()) so it completes after the first value.
Do guards or resolvers run first?
Guards. CanDeactivate → CanActivate/CanMatch → resolvers → activation. Resolvers run only if every guard passed, so you never fetch data for a route the user can't enter.
Navigating /users/7?tab=posts → ?tab=likes doesn't refetch. Fix?
Only the query param changed, and the default is 'paramsChange'. Set runGuardsAndResolvers: 'paramsOrQueryParamsChange' on the route.
Resolver vs resource() — one line?
Resolver blocks navigation until small, critical data is ready (no flicker, but a slow fetch freezes the click). resource() shows the route now and streams data in reactively (responsive, but you design the loading state).
How do you redirect from a resolver in modern Angular?
Return new RedirectCommand(router.parseUrl('/somewhere')). Pre-17.1 you injected Router, called navigate(), and returned EMPTY to abort the original navigation.

Key takeaways

  • A ResolveFn<T> pre-fetches data before activation, removing the first-paint flicker.
  • Resolvers run after guards, in parallel, and block navigation until all complete.
  • An Observable resolver must complete — pipe first() or the route hangs.
  • Read via bound input()s or route.data; avoid stale snapshot.data on reused routes.
  • runGuardsAndResolvers controls re-fetch on param/query changes; static data and title use the same read path.
  • Prefer resource() for anything that can stream in; keep resolvers for small, must-have data.
