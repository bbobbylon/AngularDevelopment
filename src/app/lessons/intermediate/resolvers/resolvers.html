A resolver fetches data before a route activates, so the component that finally renders never has to fake a loading state — it already has what it needs. Static data attaches fixed values the same way, with no fetch at all. The catch: a resolver blocks the click until its promise keeps one specific word — complete — and this page drills exactly what that word means with two live simulations and the trap that catches almost everyone.

The problem

Your route just changed. Where's the data?

Fetch inside a component and there is a gap — however small — between the moment the route changes and the moment there is anything worth looking at. During that gap the component has already mounted, already run ngOnInit, and has nothing to show: a spinner, an empty shell, a flicker. The URL is already right. The screen is still wrong.

What if, instead, something checked whether the data existed before the router ever handed control to the component at all?

Two identical trips, both about 900ms. One navigates instantly and fetches inside the component. The other holds the OLD page up the entire time and fetches first. Nobody waits any less — the total time is identical either way. Before you scroll: which one do you think feels faster to the person who clicked, and why? The mental model

A resolver is the maître d', not the waiter.

Picture two restaurants, both fully booked. The first seats you the moment you walk in — at a table that hasn't been cleared yet, so the busser works around your elbows while you wait for cutlery. The second makes you stand at the door for the exact same ninety seconds, then walks you straight to a table that is already set, poured, and ready. Nobody waited less. One of them just picked a far better place to spend the wait.

A resolver is the second restaurant's maître d': the host who won't seat you until your table is actually ready. A component that fetches its own data in ngOnInit is the first — technically quicker to seat you, but it seats you into a mess. The router is the door; the resolver is the person standing in it, refusing to open that door until the table — the data — is set.

No ticket, no table. A resolver is the router's way of refusing to seat the next component until its data ticket is actually punched — punched meaning something very specific, which is the whole of the next section.

The mechanism

One resolver is one function that returns a promise to be kept.

No classes, no decorators — a resolver is a plain ResolveFn<T>, the exact same shape as the guards from the previous lesson, just answering a different question: not may this navigation proceed, but what does the next component need before it does.

Resolvers do not run first. They sit near the end of a navigation — every guard on the route has to return true before a single resolver is even asked, so a fetch is never wasted on a user who was never getting in. All resolve keys on the matched route then run in parallel, and navigation waits for every one of them — the route is only as fast as its slowest key.

The rule everyone breaks

An Observable resolver must complete — not just emit.

This is the number-one resolver bug, in this app's own audit and in bug trackers everywhere. The router subscribes to your resolver and waits for it to complete, not merely to produce a value. An HttpClient call completes on its own after one emission, so it's fine. A long-lived stream — a Subject, a store select(), valueChanges, interval() — emits and then keeps going, so the router waits forever, with no error and no timeout of its own.

An Observable resolver must complete, not just emit. Pipe first() (or take(1)) onto any long-lived stream you resolve, or the navigation hangs with nothing in the console to even tell you it's stuck.

Reading the result

Three ways to receive it, three different lifetimes.

With provideRouter(routes, withComponentInputBinding()) (enabled in this app), each resolve key, path param and query param binds straight to a matching component input() — no ActivatedRoute plumbing at all. Prefer the observable route.data over snapshot.data whenever the same component instance can be reused across a param change — the snapshot is frozen at activation and simply won't update on a re-resolve.

Re-running

Navigate from /users/7 to /users/9 — does the resolver fire again?

Angular reuses the same component instance across that navigation. By default the resolver does not re-run on a query-param-only change — a classic "why is my data stale?" bug. The route's runGuardsAndResolvers controls exactly when it does:

Choosing the right tool

Resolver, resource(), guard, or component fetch?

Resolvers are not always the answer — blocking navigation for a big or slow fetch makes the whole app feel frozen. Match the tool to the data:

Small, fast, must-have data the first paint depends on. Delays the route rather than flashing an empty shell — keep it fast, or a slow resolver freezes the whole click. Shows the shell immediately and loads reactively. You design the loading, empty and error states, and it re-fetches whenever its params signal changes. CanActivate / CanMatch decide WHETHER a route may proceed — auth, a feature flag. Never return data from one; return a boolean, a UrlTree, or a RedirectCommand. Fine for secondary or below-the-fold data where a spinner is acceptable UX. First paint always has nothing to show.
Rule of thumb in the signals era: reach for resource() first for responsiveness, and keep resolvers for the small, critical, must-be-present-on-first-paint data.

Pulling it together

Spot the bug: a "fixed" resolver that still hangs.

Five more ways this bites people in real code and in exams:

  • Non-completing Observable → hung navigation. The router waits for completion, not the first emission — pipe first()/take(1) onto any long-lived stream you resolve.
  • Reading snapshot.data when the route is reused. On a param change with the default runGuardsAndResolvers, the snapshot is stale — subscribe to route.data or bind an input() instead.
  • Query-param changes don't re-resolve by default. Add runGuardsAndResolvers: 'paramsOrQueryParamsChange' when a page or sort query must refetch.
  • Heavy resolver = frozen app. Users perceive the whole app as hung during a slow resolver because the URL hasn't even moved yet. Prefer resource() for anything that can stream in.
  • An unhandled resolver error kills the navigation. It's a NavigationError, not a component-level catch — handle it in the resolver itself, with a redirect or a fallback value.

Two layers of catch

catchError inside a resolver is not the only net — and shouldn't be the last one.

Every catchError in this lesson so far lives inside one specific resolver, catching the failures that resolver's author anticipated. That leaves a real gap: a resolver nobody remembered to wrap, a lazy-loaded route's chunk failing to download after a redeploy, or a genuinely unexpected error — all of these still produce a raw, unhandled NavigationError with nothing shown to the user. withNavigationErrorHandler is the app-wide net underneath every per-resolver catch:

The two layers have different jobs. A per-resolver catchError is for expected failures you can redirect meaningfully — a 404 lookup sends the user to /not-found, specifically. withNavigationErrorHandler is for everything unexpected — the resolver nobody wrapped, and any lazy-chunk load failure — a single, generic net rather than a specific answer. Neither replaces the other.

Questions from the back row

Before you go

Six takeaways before you move on.

  • A resolver is the maître d', not the waiter — data is fetched before the route activates, so the component never renders in a loading state at all.
  • Resolvers run only after every guard has passed, and every resolve key on the route runs in parallel — navigation waits for the slowest one.
  • An Observable resolver must complete, not just emit. first()/take(1) is the fix; skipping it hangs navigation with nothing in the console to notice.
  • Emitting immediately is not completing immediately — a cached, synchronous-looking value from a long-lived stream can still hang the navigation exactly the same way.
  • An error is the opposite failure mode: it cancels the navigation instantly with NavigationError, rather than hanging silently forever.
  • Prefer resource() for anything that can stream in after first paint; keep resolvers for the small, must-have data that actually justifies delaying the click.
