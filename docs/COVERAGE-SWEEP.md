# Coverage Sweep — what each concept still needs

**Version:** 1.0  
**Last Updated:** 2026-08-31  
**Status:** Final (findings), Living (the work)

## Overview

A per-lesson list of the sub-concepts, examples, failure modes and exam traps that are
missing or too thin, produced by sweeping all 100 lessons on 2026-08-31. This is the
detail behind [BACKLOG.md](BACKLOG.md) §1.3 — the backlog carries the summary and the
priorities, this file carries every finding.

## Method

Twenty-one agents, one per curriculum slice, each read every `.ts` and `.html` file in
its slice — including the long copy that lives in the TypeScript: quiz option `why` text,
FAQ answers, Compare rows and Predict explanations, not just the visible prose. Every
claimed gap was then handed to a second agent whose stated default was that the claim
was **wrong**, and which had to grep the lesson before confirming it.

The brief was **coverage only**. Nothing here is about styling, layout or retention
formatting — [BACKLOG.md](BACKLOG.md) §1.2 owns that, and mixing the two is how a
presentation pass quietly turns into a rewrite of the whole curriculum.

**These are findings, not a plan.** Several are one sentence of copy; a few are a new
section with a live demo. Read the lesson before acting on a line: the sweep was
thorough, but it is still a machine reading for absence, and absence is the easiest
thing to be wrong about. The adversarial pass dropped 12 of the 413 raw claims
(about 3%), which is a sign the finders were careful, not a guarantee every survivor is real.

## Themes worth acting on as a batch

Several findings repeat across many lessons. Those are cheaper and more coherent to fix
as one pass than lesson by lesson:

1. **Nothing ever fails.** 96 findings are a missing failure mode. The curriculum
   is strong on how an API works and weak on what it looks like when it goes wrong — no
   rejected promise, no NG error code read aloud, no rejected `git push`. A learner who has
   never seen the error message cannot recognise it at 2am.
2. **The Angular 21 surface is ahead of the curriculum.** `httpResource`, Signal Forms,
   `linkedSignal`, `router.events` and `EnvironmentProviders` are named in passing and taught
   nowhere. 26 findings are an API that has moved under a lesson.
3. **The web platform underneath Angular is assumed.** There is no HTML lesson, no CSS
   lesson, and CORS is named as a cause of failure three times without ever being
   explained. The Foundations tier promises "no prior experience assumed" and then
   assumes the two languages every component file is written in.
4. **Delivery stops at `ng build`.** Nothing covers what the output actually is, why a deep
   link 404s without a server rewrite, or how metadata reaches a crawler — in a tier
   literally called Rendering & Delivery.

## Foundations

### `foundations/arrays-objects-basics`

- **No way to iterate an object: Object.keys/values/entries, for...in vs for...of** — _sub-concept, high_  
  Add a section next to the array toolkit: Object.keys(person) → ['name','age','member'], Object.values, and Object.entries(person) with the [key, value] destructuring loop — for (const [key, value] of Object.entries(person)). Contrast for...in (keys of an object, and a trap on arrays because it yields the string indices '0','1','2' plus inherited keys) against for...of (values of an array). Rule of thumb: for...of for arrays, Object.entries for objects.
  <sub>The lesson teaches objects thoroughly by fixed key name but never shows how to walk an object whose keys you don't know at author time — a dictionary, a settings map, an API response keyed by id. Object.entries and for...in appear nowhere in any lesson in the repo, so a learner cannot render or loop a keyed map at all, and cannot understand Angular's keyvalue pipe later.</sub>
- **sort() converts to strings — [10, 9, 1].sort() is [1, 10, 9]** — _exam trap, high_  
  Extend the array toolkit: show [10, 9, 1].sort() → [1, 10, 9] and explain the default string coercion, then the numeric comparator [...nums].sort((a, b) => a - b) with the sign convention (negative = a first) spelled out, then sorting the people array by age and by name with localeCompare. Keep the existing mutation warning attached — copy first, then sort. Add it to Exam corner alongside the existing sort-mutates question.
  <sub>The lesson mentions bare .sort() mutating and shows [...list].sort(), but never that the default sort compares items as text. [10, 9, 1].sort() returning [1, 10, 9] is a genuine shock, a classic interview question, and the comparator function — the only way to sort numbers or sort an array of objects by a field — is never shown even though the very next section is all about arrays of objects.</sub>

### `foundations/async-basics`

- **The event loop is demonstrated but never explained — no stack, queue or Web APIs** — _sub-concept, high_  
  Add a diagrammed section between the A/C/B demo and the callbacks round: the four boxes (call stack, Web APIs, callback queue, event loop) with the setTimeout(fn, 0) callback traced through all four, plus the rule 'the event loop only moves a callback onto the stack when the stack is empty'. This also makes the existing busy-wait Exam corner answer mechanical rather than assertion, and sets up the microtask/macrotask distinction the TS tier builds on. Worth a step-through demo of the same shape as the loop tracer in decisions-loops.
  <sub>The A/C/B demo proves the ordering and the prose says the callback is 'only allowed back into the lane', but the actual machinery is never named: call stack, the browser's timer/network APIs running outside JS, the callback queue, and the event loop moving work back onto the stack when it empties. 'Explain the event loop' is the most-asked JavaScript interview question, and the strings 'call stack' and 'callback queue' appear nowhere in the entire repo (the TS-tier ts-async lesson covers microtask vs macrotask ordering but assumes this model already exists).</sub>
- **Nothing in the lesson ever fails: no reject, no .catch firing, no unhandled rejection** — _failure mode, high_  
  Add a failure path to the existing 1.2s load demo — a 'make it fail' toggle that rejects, so the learner watches the promise go pending → rejected and the catch branch render an error message. Show new Promise((resolve, reject) => ...) once, since the lesson's own source already uses it unexplained. Then the two silent-failure traps: a promise with no .catch produces an unhandled rejection warning and your app just stops mid-flow, and try { loadUser(); } catch {} around a NON-awaited call catches nothing at all because the function returned before the rejection existed.
  <sub>The lesson says 'always handle the failure case too' and shows .catch and try/catch in code listings, but every runnable demo succeeds — the learner never sees a rejection happen, never sees reject() or new Promise's two callbacks, and is never told what an unhandled rejection looks like in the console (Uncaught (in promise) Error). Network failure is the normal case in the very next lesson (json-and-apis) and in every HttpClient lesson afterwards.</sub>
- **await inside forEach does nothing; await inside a loop is accidentally sequential** — _failure mode, high_  
  Add a section after sequential vs parallel: the forEach-with-async version shown running to completion instantly (log 'done' printing before any save resolves) and the explanation that forEach ignores the promise its callback returns. Then the two correct shapes — for...of + await when each step must finish before the next (order matters, rate limits), and await Promise.all(items.map(save)) when they are independent — with the N-requests timing contrast made explicit.
  <sub>Promise.all is taught only for two hardcoded independent calls, which leaves the far more common case uncovered: awaiting over a list. items.forEach(async item => await save(item)) compiles, runs, and returns immediately without waiting for anything — the classic 'my save loop finished before the saves did' bug — while for (const item of items) await save(item) does wait but serialises N requests. Both are routine code-review findings and interview follow-ups to the Promise.all question already in the lesson.</sub>
- **Out-of-order responses: the last request to start is not the last to finish** — _failure mode, medium_  
  Add a short demo or trace: fire request A with a 900ms delay and request B with a 200ms delay, show B's result rendered then clobbered by A's, and name it a race condition. Give the beginner-level defences — track a request id or timestamp and ignore results that are not the newest, or cancel the previous request — and forward-reference that Angular solves this with switchMap and with cancellation in the resource API.

### `foundations/debugging-basics`

- **Compile-time vs runtime errors — the lesson never says errors appear in two different places** — _sub-concept, high_  
  Add a section with three panels — editor squiggle, `ng serve` terminal output, browser console — and the rule for which errors land where: type errors and template errors are caught before the code runs (compile time, terminal + editor, app does not update); TypeErrors/ReferenceErrors happen while running (browser console). Show one real terminal compile error verbatim, e.g. `X [ERROR] TS2339: Property 'nmae' does not exist on type 'User'. [plugin angular-compiler] src/app/user.ts:12:20`, and one template error such as `NG9: Property 'titel' does not exist on type 'AppComponent'`, annotating file:line:column the same way the existing stack-trace anatomy diagram does. Add the takeaway: when the browser doesn't change after a save, look at the terminal before you look anywhere else.
  <sub>Every example in the lesson is a runtime JavaScript error in the browser console. But in an Angular project the majority of a beginner's errors are TypeScript and template compile errors that appear in the _terminal running ng serve_ and as editor squiggles, never reaching the browser at all — the browser just shows a stale page or nothing. A learner who only knows to look in the console will stare at an unchanged page while the answer sits in the terminal behind their editor. This is the single most disorienting moment of week one and the lesson's own 'did it recompile?' Exam corner brushes against it without ever explaining it.</sub>
- **Async stack traces and unhandled promise rejections are absent** — _failure mode, high_  
  Add a fifth entry to the BUG_CASES field guide: an error thrown inside a `setTimeout` / `.then()` callback whose trace shows only the callback plus engine frames, with the reading — the call stack was unwound before the callback ran, so the code that _scheduled_ it is not on it; look at the async work, not the trace. Cover the two practical tools: DevTools' 'Async' stack-trace stitching (the greyed 'Async call' separators in the Call Stack panel), and `Uncaught (in promise) TypeError: …` — a promise that rejected with nobody catching it, which prints once and then goes quiet, so a missing `.catch()`/error callback makes failures _invisible_ rather than loud. Tie it to the existing silent-bug theme: an unhandled rejection is a silent bug with a receipt.
  <sub>The lesson's model of a stack trace is 'reading down tells you the story of how we got here' — which is exactly the model that breaks the first time the error happens inside a setTimeout, a `.then()`, or an HTTP subscribe callback. The trace then starts at some framework internal and contains none of the code that scheduled the work, so a learner applying the taught method finds no suspect at all. The prerequisite async-basics lesson makes this the _expected_ shape of an Angular error (data arrives late), and the lesson's own best Exam corner ('why hadn't items been assigned yet? the data hadn't arrived from the server') describes this bug while never teaching how to trace it.</sub>
- **No Angular-specific errors: NG error codes, angular.dev/errors, or Angular DevTools** — _sub-concept, high_  
  Add a short 'Angular errors have codes' section: show one real message (`ERROR NG0201: No provider found for \`UserService\`. Source: StandaloneInjector.`), point out that the NGxxxx prefix is the searchable identifier and that every code has a page at angular.dev/errors/NG0201, and give a mini table of the four or five codes a beginner will actually meet with a one-line cause each. Add a pointer that the browser DevTools stop at the DOM and JS — for 'which component owns this, what are its inputs, why did it re-render' there is a separate Angular DevTools extension with a component tree, injector tree and profiler (worth its own lesson, but the learner needs to know it exists here).
<sub>This is the debugging lesson of an Angular course and every error it teaches is plain JavaScript. Angular's runtime errors are coded — NG0100 ExpressionChangedAfterItHasBeenCheckedError, NG0200 circular dependency, NG0201 no provider for X, NG0912 duplicate hydration id — and the code is the searchable key that leads straight to an official explanation page. A learner who does not know that `NG0201` is a lookup key will search the full message text with their own class names in it and find nothing. Later lessons (change-detection, di-advanced, hydration) reference these codes as if this foundation had been laid.</sub>
- **Breakpoints are advocated but never actually taught — no debugger statement, conditional breakpoints, watch, or call-stack panel** — _thin example, medium_  
  Expand into a walkthrough of the paused state: the four step controls and what each means (resume / step over / step into / step out), the Scope pane as 'every variable at this instant', Watch expressions for an expression you want re-evaluated at each pause, and the Call Stack pane as the live version of the stack trace already taught — clicking a frame re-inspects the world at that caller's moment. Add `debugger;` as the one-line way to set a breakpoint from code (and the warning to never commit it). Add right-click → 'Add conditional breakpoint' with `id === 42`, and 'Logpoint' as a log that needs no code edit and no recompile. Finish with 'Add script to ignore list' on framework frames so stepping stays inside your own code.
- **console.log of an object shows a live reference, not a snapshot** — _exam trap, medium_  
  Add a predict-then-reveal example: log `user`, then set `user.name = 'changed'` on the next line, and show that the expanded console entry reads 'changed'. Explain the mechanism (the console keeps a reference; primitives are copied, objects are not — the small blue ⓘ 'value below was evaluated just now' badge is DevTools admitting this) and give the three fixes: log a primitive (`console.log(user.name)`), snapshot with `structuredClone`/`JSON.parse(JSON.stringify(x))`, or use a breakpoint, which pauses the world so nothing can change underneath you. This is also a natural on-ramp to the reference-vs-value idea the arrays-objects lesson introduces.
- **Source maps — why a production stack trace is unreadable** — _sub-concept, medium_  
  Add a short before/after pair: the same error as a dev trace and as a production trace, with one sentence on the mechanism — the browser is genuinely running one giant minified file, and a `.map` file is what lets DevTools show you TypeScript that no longer exists at runtime. Note the practical consequences: your TypeScript appearing in the Sources panel is the source map working; `"sourceMap": true` in the production build configuration of angular.json makes deployed traces readable (with the tradeoff of shipping your source); and this is why error-tracking services ask you to upload source maps. One line connects it to the CLI lesson's `ng serve` vs `ng build` distinction.

### `foundations/decisions-loops`

- **switch/case is entirely absent, yet the beginner tier teaches @switch** — _sub-concept, high_  
  Add a section after the if/else-if chain: the same grade or status example written as switch (status) { case 'active': ... break; ... default: }, with an explicit annotated demo of what happens when break is omitted (execution falls through and runs every subsequent case body until it hits one). Cover deliberate fall-through for grouped cases, the default branch as the catch-all, and the guidance that switch compares with === so '1' never matches 1. Add a spot-the-bug Exam corner entry.
  <sub>The lesson covers if / else-if chains and stops there. switch is the other half of branching, it is what the beginner-tier control-flow-switch lesson (Angular's @switch) implicitly assumes, and its failure mode — a missing break causing fall-through into the next case — is a stock exam and interview question that cannot be discovered by reading @switch alone.</sub>
- **Ternary, and && / || as value-producing operators, not just boolean glue** — _sub-concept, high_  
  Add a section 'choosing a value, not a branch': const label = age >= 18 ? 'adult' : 'minor' contrasted with the four-line if/else that assigns the same variable, and the point that a ternary is an expression so it can sit inside interpolation while an if cannot. Then short-circuiting: || returns the first truthy operand (so count || 10 wrongly yields 10 when count is 0 — reuse the discount trap), && returns the first falsy one and is the guard idiom user && user.name. Forward-reference ?? as the fix that only treats null/undefined as missing.
  <sub>The lesson teaches && / || only as ways to combine booleans, and never teaches the ternary at all — yet the ternary is the only conditional that works inside an Angular template expression, this app's own demos are full of cond ? a : b, and `name || 'Guest'` short-circuit defaulting is everywhere in real code. The truthiness section already sets up the discount = 0 trap, which is exactly the trap that || defaulting falls into and ?? fixes.</sub>
- **You cannot break out of forEach, and mutating an array while looping skips items** — _failure mode, high_  
  Add a short 'when to go back to a real loop' block: show a forEach with a return that fails to stop the iteration, then the working alternatives — for...of with break for early exit, some() for 'is there one that...', find() to get the item and stop. Separately show the delete-while-looping bug: for (let i = 0; i < list.length; i++) with a splice inside skipping the next element, and the fix (iterate backwards, or filter into a new array). Both are strong spot-the-bug Exam corner candidates.
  <sub>The lesson promotes array methods over raw loops but never states where that advice stops. Two concrete bugs follow: return inside a forEach callback only ends that one iteration (it does not exit the loop, and it does not return from the enclosing function), and break/continue are syntax errors inside it — so learners who internalise 'always use array methods' get stuck the first time they need early exit. Splicing inside a counting for loop shifting later items past the index is the sibling bug.</sub>
- **reduce: the initial value is not optional in practice, and group-by is its real use** — _exam trap, medium_  
  Expand the reduce bullet into its own annotated walkthrough: table the accumulator's value at each step for [1,2,3] so the two-parameter callback stops being opaque, then show the empty-array crash and why the 0 seed prevents it. Add one non-numeric accumulator — reduce over the people array into a { [name]: age } lookup, or count items per category — and note that map/filter cannot produce a differently-shaped result. Then an Exam corner: what does [].reduce((a,b)=>a+b) do?

### `foundations/dom-and-events`

- **Teaches bubbling as the whole propagation model — capture phase missing entirely** — _sub-concept, high_  
  Extend the existing three-box demo with a capture toggle: with capture on, the log order flips to outer → middle → inner, making the down-then-up journey visible in the same widget. Add a diagram of the two legs, and a short table contrasting stopPropagation (stops the journey) with stopImmediatePropagation (stops the journey AND the other handlers on this same element) with preventDefault (stops the browser's default action, not the journey).
  <sub>The lesson states "an event doesn't fire on just one element. After firing on the target it bubbles up" — which is the model with a third of it removed. Real propagation is capture (document → target) then target then bubble (target → document), and `addEventListener(name, fn, { capture: true })` opts into the downward leg. "Name the phases of event propagation" is one of the most-asked DOM interview questions, and capture is the practical answer for interception patterns (a wrapper that must see a click before a child can stopPropagation it). `stopImmediatePropagation` — which also kills sibling listeners on the same element, unlike `stopPropagation` — appears nowhere in the entire repo.</sub>
- **innerHTML never appears — so the XSS injection vector Angular sanitizes against is never introduced** — _failure mode, high_  
  Add innerHTML to the toolkit block alongside textContent with the difference annotated: textContent sets text (an `<img>` shows as literal characters), innerHTML parses markup (that same string becomes a real element). Then a two-button live demo feeding the same attacker-ish string `<img src=x onerror=alert(1)>` into each, and one line closing the loop: this is exactly why Angular sanitizes `[innerHTML]` and why `{{ }}` interpolation can never inject markup.
  <sub>The manual-toolkit block teaches textContent, classList, createElement and append, but never mentions innerHTML — the property beginners reach for first and the one that parses its input as markup. A learner who never sees `el.innerHTML = userComment` has no mental model for what Angular's sanitizer, `[innerHTML]` binding and `bypassSecurityTrust*` are protecting them from, yet `property-binding.html` (beginner) and `security.html` (expert) both assume it. It is also the cleanest possible demonstration of why "the DOM is a tree of objects, not a string of text" matters.</sub>
- **Attribute vs property never shown, despite the component docstring claiming it** — _sub-concept, medium_  
  Add a live input where typing updates a side-by-side readout of `.value` (changes) and `getAttribute('value')` (frozen at the initial markup). Follow with the `checked`/`disabled` case (attribute presence, not its string, is what counts — hence `disabled="false"` still disables) and the ARIA case (aria-* has no property equivalent at all, so setAttribute is the only route). One closing sentence pointing at `[value]` vs `[attr.value]`.
- **Event delegation taught without the events that don't bubble** — _failure mode, medium_  
  Add a caveat after the delegation paragraph listing the non-bubbling events (focus, blur, load, error, and scroll on elements) with the focusin/focusout replacements. A tiny demo — a wrapper with (focus) that never fires next to one with (focusin) that does — makes the failure visible rather than asserted.

### `foundations/functions-basics`

- **Wrong argument count is silent; default and rest parameters absent** — _failure mode, high_  
  Extend the tip() example: call tip(50) with the percent missing, trace it to percent = undefined → 50 * (undefined/100) → NaN, and contrast with a language that would refuse to compile. Then introduce function tip(bill, percent = 15) as the fix, and ...rest for 'any number of arguments' (sum(1,2,3)) since it is the mirror image of the spread they meet in the next lesson.
  <sub>The lesson says arguments match parameters by position but never says what happens when the counts disagree — and JavaScript does not error: missing arguments become undefined (so tip(50) returns NaN, not a crash), extra arguments are silently dropped. That silent NaN/undefined is one of the most common beginner debugging sessions. Default parameters (b = 1) and rest (...args) are everyday syntax that appear nowhere in the slice.</sub>
- **Closures — a function keeping its outer variables alive after the call returns** — _sub-concept, high_  
  Add a section after Scope: a makeCounter() factory that returns an arrow function reading a local count, called twice to show two independent counters that each remember their own box after makeCounter returned. State the rule as 'a function remembers where it was born, not where it is called'. Then land it on the real payoff already in the lesson — the setTimeout/addEventListener callbacks capture the surrounding variables, which is why they still work seconds later.
  <sub>The scope section teaches one-way outward visibility and then says locals are 'destroyed when the call ends', which is exactly the half-truth closures contradict. Closures are taught nowhere in the entire curriculum (only referenced in passing in http-interceptors and narrowing), yet they are a top-three interview question and are the mechanism behind Angular's functional guards/interceptors capturing injected dependencies, and behind every callback that remembers state.</sub>
- **Declaration vs expression: calling before the definition line** — _exam trap, medium_  
  Add a two-column before/after under the arrow-function section: double(5) placed above 'function double(n)' works, the identical call above 'const double = n => n * 2' throws. Explain that declarations are registered when the file loads, whereas a const only exists from its line onward. Add an Exam corner entry, since the current arrow section presents the two forms as interchangeable.
- **Pure vs side-effecting functions, and the early-return guard clause** — _sub-concept, medium_  
  Contrast two versions of the same job: addTax(price) returning a new number (pure — same input, same output, touches nothing outside) versus a version that mutates a shared cart total (side effect). State the test: could you replace the call with its result and change nothing? Then show the guard-clause shape — function save(user) { if (!user) return; ... } — as the deliberate use of 'return ends the function', preferred over a deeply nested if.
- **Recursion — a function calling itself — appears nowhere in the curriculum** — _sub-concept, low_  
  Add a short final section: countdown(3) or a factorial, drawn as the stack of calls piling up and then unwinding, with the base case highlighted as the thing that stops it, and the missing-base-case failure named (RangeError: Maximum call stack size exceeded — infinite loop's cousin). One practical example — summing quantities in the nested order object — makes the point that recursion is for tree-shaped data.

### `foundations/git-basics`

- **No `git init` / `git clone <url>` / `git remote add` / `git push -u` — the repo is never actually created or connected** — _sub-concept, high_  
  Add a 'day zero' command block with per-line comments covering both entry points: joining an existing project (`git clone https://github.com/org/repo.git` → 'copies history, files AND the origin remote in one step', then `cd repo`, then `npm install` linking back to the npm lesson), and publishing a new one (`git init` → 'creates the hidden .git folder — this is the whole database', `git add .`, `git commit -m …`, `git remote add origin <url>` → 'name a remote; "origin" is just the conventional name', `git push -u origin main` → 'the -u sets the upstream so future pushes are bare `git push`'). Prepend the one-time identity setup `git config --global user.name/user.email` and note that every commit permanently records that email.
  <sub>The lesson simulates add/commit on a repository that already exists and already has a remote. It mentions clone once in prose and never shows a single command that starts a repo or attaches it to GitHub. A learner finishing this lesson can commit but cannot get their project onto GitHub — which is the entire stated payoff ('your GitHub PR history is a portfolio interviewers actually read'). It also omits first-run `git config user.name` / `user.email`, without which the very first commit either fails or is attributed to nobody.</sub>
- **Rejected push (non-fast-forward) is never shown — the most frequent daily Git failure** — _failure mode, high_  
  Show the real output (`! [rejected] main -> main (non-fast-forward)` / `Updates were rejected because the remote contains work that you do not have locally`) and explain the mechanism in one sentence: your branch and origin's branch have diverged, so there is no straight line to fast-forward along. Give the fix ladder: `git pull` (merges, creates a merge commit) or `git pull --rebase` (replays your commits on top — linear history) then push again; and a red-flag note that `--force` makes the error go away by deleting your teammates' commits, which is why teams protect main against it. This pairs naturally with the existing 'shared history is append-only' rule.
  <sub>The lesson presents `git push` and `git pull` as symmetrical uploads/downloads and never shows the case where push is _refused_ because the remote moved on while you worked. `! [rejected] main -> main (fetch first)` is the error every collaborating developer sees weekly, and the panic reaction — `git push --force` — is precisely the shared-history rewrite the lesson elsewhere (correctly) warns against, so leaving the gap actively invites the disaster the lesson tries to prevent.</sub>
- **`git stash` missing — and the lesson never says what happens to uncommitted work when you switch branches** — _failure mode, high_  
  Add a short subsection after branching: show the refusal message verbatim, then `git stash` ('shelve every uncommitted change and give me a clean tree'), `git stash list`, `git stash pop` ('put them back — pop removes it from the shelf, apply keeps a copy'). Name the trap that stash is _silent and easy to forget_ — stashes are invisible in `git status` and `git log`, so a forgotten stash looks like lost work. Extend the existing three-areas simulator with a 'switch branch' button that blocks while files are modified, so the failure is felt rather than described.
  <sub>The lesson's centrepiece branch insight is 'switching branches rewrites your working directory', and its Exam corner drills that. But it never answers the obvious follow-up a learner will hit within a day: what about my half-finished edits? Git either carries them along or refuses with `Your local changes to the following files would be overwritten by checkout`, and the beginner reading that error has no tool to resolve it. Stash is the answer and is completely absent, despite the lesson's own closing rule ('uncommitted work is trivially easy to lose') making it essential.</sub>

## Concepts with no lesson at all

Proposed by the sweep, deduplicated, highest priority first. Each would be a new entry
in `src/app/core/curriculum.ts`. Adding one is a much bigger commitment than closing a gap
above — it is a whole lesson written to the full bar in [CONTRIBUTING.md](CONTRIBUTING.md)
§2, §2A and §2B — so treat this as a menu, not a queue.

### High priority

- **`html-essentials`** — HTML: The Language of Structure  
  The curriculum has no HTML lesson at all. how-the-web-works names HTML as "the structure" in a three-row table and moves on; dom-and-events opens with a `<body><header><h1>` sample it assumes the reader can already read. For a track that explicitly promises "zero prior knowledge", a learner is expected to jump into Angular templates — which are HTML — without ever being taught elements, attributes, nesting, or which tag to reach for. The gap bites hardest in forms: template-driven and reactive forms both assume the reader knows `<form>`, `<input type>`, `<label for>`, `<select>/<option>`, required/name/value, and what submit does by default. It also blocks the expert a11y lesson, whose entire argument ("use the semantic element and get keyboard and screen-reader behaviour free") has no foundation to rest on.
- **`css-essentials`** — CSS: Styling, the Cascade & Layout  
  There is no CSS lesson anywhere, yet every component the learner will write has a .css file, and the beginner class-style-binding lesson already reasons about specificity and the cascade as though they are known. Nothing teaches selectors, the box model, display/position, flexbox and grid, or CSS custom properties — the last of which is the only sanctioned way to style across the component boundary that view-encapsulation teaches. Without this, a learner can make an Angular app work and cannot make it look like anything, and the intermediate view-encapsulation lesson (:host, ::ng-deep, emulated encapsulation via attribute selectors) is unteachable because it is entirely a story about how Angular rewrites CSS selectors.
- **`origins-and-cors`** — Origins, CORS & the Browser's Security Rules  
  CORS is named three times in json-and-apis as a cause of fetch rejection and never once explained, and appears nowhere else except an incidental mention in http-crud. It is the first hard blocker every learner hits the moment they point their dev server at a real API, and the error text ("blocked by CORS policy: No 'Access-Control-Allow-Origin' header") describes a mechanism they have not been taught. The specifically counterintuitive parts need a lesson: the request usually reached the server and succeeded — the browser is refusing to hand the response to your JavaScript — which is why "but it works in Postman/curl" is the universal first reaction; the OPTIONS preflight that fires for non-simple methods and custom headers, so a plain GET works while your PATCH with an Authorization header does not; that only the server can fix it, not the client; that a dev proxy (angular.json's proxyConfig) sidesteps it in development and hides it until deploy; and that credentials/cookies need both withCredentials and an explicit non-wildcard origin. Same-origin policy is standard interview material and it is the missing foundation under the expert security lesson's CSRF section.
- **`strings-and-text`** — Strings & Text: Template Literals and the Methods You Use Daily  
  Strings get one table row in programming-basics ('text in quotes') and one concatenation example, and then nothing in the entire curriculum teaches them. Template literals with ${} — the default way strings are built in every later lesson's source — are taught nowhere (the only hits in the repo are template literal TYPES in the advanced TS tier). split, join, slice, trim, includes, replace, toUpperCase, startsWith and padStart appear in no lesson, yet learners must handle text from every form input and API response: splitting a full name, trimming user input before validation, formatting a display label. String immutability ('abc'.toUpperCase() returns a new string, it does not change the original) is also the cheapest possible place to reinforce the value-vs-reference distinction that arrays-objects-basics builds on. This is a real hole in a zero-to-hero track, not a nicety.
- **`scope-closures-hoisting`** — Scope, Closures & Hoisting  
  functions-basics teaches scope as one-way outward visibility and states that locals are 'destroyed when the call ends' — which is precisely the claim closures contradict. Closures are taught nowhere in the curriculum (only mentioned in passing in http-interceptors, narrowing and decorators, all of which assume the reader already knows), despite being a top-three JavaScript interview question and the actual mechanism behind Angular's functional guards and interceptors capturing injected dependencies, behind every event handler that remembers state, and behind the counter/factory pattern. Hoisting and the temporal dead zone are equally absent as JavaScript concepts (the only 'hoist' hits are about ES module evaluation order and Angular's @let), leaving 'Cannot access X before initialization' and 'why can I call this function above where it is written' unexplained. A single lesson covering global/function/block scope, the scope chain, closures with a makeCounter demo, hoisting vs TDZ, var's function scoping, and the classic for-var-setTimeout puzzle would close all of it and is a certification/interview staple.
- **`angular-devtools`** — Angular DevTools: Inspecting a Running App  
  The curriculum teaches browser DevTools (debugging-basics) and mentions the Angular DevTools profiler exactly once, in passing, inside the expert performance lesson — there is no lesson on the tool itself. - **`template-reference-variables`** — Template Reference Variables (#ref)

- **`http-resource`** — Signal-Based HTTP: httpResource()  
  `httpResource` is taught nowhere in the 100-lesson curriculum — it survives only as a passing name-drop in one sentence of state-management, and matches zero times in every HTTP and Signals lesson. It is the Angular 21 default for fetching data for display: a GET whose URL is a reactive computation, exposing `value()`, `status()`, `isLoading()`, `error()`, `headers()` and `reload()` as signals, with automatic re-fetch and cancellation when a dependency changes. Every alternative in the curriculum is now the older way — http-basics teaches subscribe-and-set-a-signal, resource-api teaches the generic `resource`/`rxResource` loaders. This is the largest single Angular-21 hole in the HTTP slice and an obvious interview topic.
- **`signal-forms`** — Signal Forms (@angular/forms/signals)

- **`form-composition`** — Splitting Forms Across Components (ControlContainer & sub-forms)  
  Any form past one screen gets broken into child components, and Angular has two genuinely different answers with different trade-offs: (a) the child renders a slice of the parent's existing control tree by inheriting the parent's ControlContainer — `viewProviders: [{ provide: ControlContainer, useExisting: FormGroupDirective }]` — so it can use `formGroupName`/`formControlName` with no inputs and no CVA; or (b) the child is an opaque custom control implementing ControlValueAccessor. The curriculum teaches (b) at expert level but (a) exists only as a single passing clause in di-advanced ('how form directives find their surrounding ControlContainer'), and nothing anywhere compares them. 'How do you build a reusable address sub-form?' is a top-tier senior Angular interview question, and the wrong answer (rebuilding a nested group and syncing it by hand, or reaching for CVA when the child should just borrow the parent's tree) is the common one. It is also the natural bridge from this slice's form-arrays lesson to the expert CVA lesson, which currently has no on-ramp: the FormArray row is exactly the case where you want to extract a child component and immediately hit the ControlContainer problem.
- **`form-submission`** — Submitting Forms & Server-Side Errors  
  The slice teaches how to build and validate a form but stops at the moment the user clicks Save, which is where the remaining half of the real work is and where several genuinely uncovered concepts live. Specifically: mapping a 422/400 field-error response back onto individual controls, and why the obvious `ctrl.setErrors({ taken: true })` approach is fragile — form-validation already proves the error is wiped by the next keystroke, but never supplies the working alternative (a serverError signal read by a dedicated validator the control actually owns, cleared on the next edit). Also unowned: preventing double-submit while the request is in flight, `form.disable()` during submission and the fact that disabled controls vanish from `form.value` so you must capture `getRawValue()` first, resetting to the newly-saved state rather than to blank, and optimistic vs pessimistic UI. It ties to CanDeactivate for unsaved changes, which route-guards covers from the routing side with no forms-side counterpart. Some of this can be absorbed as gaps in existing lessons, but the server-error round trip is a distinct concept with no natural home.
- **`router-config`** — Router Configuration: Scrolling, URL Strategy & Route Reuse  
  The `provideRouter` feature functions are scattered one-per-lesson (withPreloading in lazy loading, withComponentInputBinding in route-params, withViewTransitions in its own expert lesson) and the rest are simply absent, even though several fix user-visible bugs a learner will hit in their first routed app. Most importantly scroll position: without `withInMemoryScrolling({ scrollPositionRestoration: 'enabled', anchorScrolling: 'enabled' })` every navigation keeps the previous scroll offset and `#fragment` links do nothing — and route-params teaches fragments without ever mentioning that they need this to work. Scope: withInMemoryScrolling, withHashLocation and when a hash URL is forced on you (static hosts, no server rewrite), withRouterConfig's four options (onSameUrlNavigation, paramsInheritanceStrategy, canceledNavigationResolution, urlUpdateStrategy 'eager' vs 'deferred' and what each does to the address bar during a slow guard), withEnabledBlockingInitialNavigation for SSR, and a custom RouteReuseStrategy for tab/detached-view caching — the natural sequel to the reuse mechanics route-params already explains.
- **`testing-routing`** — Testing Routes, Guards & Resolvers  
  The routing slice repeatedly establishes that guards and resolvers are plain functions that only work inside an injection context, and then never shows how to test one — so a learner who follows the lesson literally will write `authGuard(route, state)` in a spec and get a runtime throw with no idea why. The curriculum has testing-components and testing-services-http lessons but neither covers routing beyond one line recommending the NgModule-era `RouterTestingModule`, which is outdated guidance. `RouterTestingHarness` is a named interview topic (it appears in the app's own interview bank) with no lesson behind it. Scope: `provideRouter([...])` in TestBed, `RouterTestingHarness.create('/users/42')` and asserting on the routed component and DOM, testing a blocked navigation (harness.routeNativeElement is null / the URL did not change), unit-testing a functional guard and resolver via `TestBed.runInInjectionContext`, faking ActivatedRoute vs letting the real router run, and testing components that use withComponentInputBinding by simply setting inputs.
- **`testing-directives-pipes-guards`** — Testing Directives, Pipes, Guards & Resolvers  
  The Testing category covers exactly two shapes — components and services/HTTP — leaving every other testable unit in the curriculum without a home. Custom pipes, attribute and structural directives, host directives, functional guards and resolvers are all taught as concepts (custom-pipes, attribute-directives, structural-directives, host-directives, route-guards, resolvers) and none of them are ever tested. The techniques do not fall out of the two existing lessons: a directive needs a host-component wrapper (@Component with a template that applies the directive, then query By.directive), an impure pipe needs a call-count assertion to prove purity, and a functional guard is invoked directly inside TestBed.runInInjectionContext(() => authGuard(route, state)) with a mocked Router — a pattern that appears nowhere in the app despite route-guards teaching that guards run in an injection context. Certification testing sections and interviews both ask 'how would you test a structural directive / a guard?', and today a learner who has read the whole curriculum has no answer.
- **`typed-templates`** — Typed Templates & Generic Components  
  Nothing in the curriculum covers template type-checking or generic component authoring: `strictTemplates` appears only as an aside in one rxjs-interop answer, `$any()` is used in four project templates and never explained, and `ngTemplateContextGuard` is introduced inside structural-directives with no home for the broader topic. This is the slice's missing capstone — what turns 'I can use components' into 'I can build a reusable, type-safe one' — and it is directly load-bearing for the bring-your-own-row/table patterns the ng-template-outlet lesson teaches and then leaves untyped (`Record<string, unknown>`). Covers: strictTemplates and what each sub-flag checks, `$any()` as the escape hatch and its cost, generic components/directives whose `input.required<T[]>()` infers T at the call site, typed `TemplateRef<Ctx>`, `ngTemplateContextGuard` vs `ngTemplateGuard_*`, and `ngAcceptInputType_*` for coerced inputs — all interview- and certification-relevant.
- **`web-workers`** — Web Workers & Getting Work Off the Main Thread  
  Nothing in the curriculum covers Web Workers (the only 'worker' lesson is the PWA service-worker one, which is a different thing entirely — a distinction that is itself an interview question). It is a supported first-class CLI feature (ng generate web-worker, with the builder emitting the worker bundle) and it is the only real answer to the class of INP problem the performance lesson gestures at but cannot solve: CPU-bound work — parsing a large CSV, diffing, crypto, image processing, big sorts — that no amount of OnPush, signals or zoneless will make faster because change detection was never the bottleneck. A lesson should cover generating and wiring a worker, the postMessage/structured-clone boundary and what cannot cross it (functions, DOM nodes, class identity), transferables for large buffers, wrapping the worker as an injectable service that exposes a signal or Promise, terminating it on destroy, and the honest cost/benefit (serialization overhead means small jobs get slower). It also completes the 'which kind of slow do I have?' framing the performance lesson opens with, which currently has no branch for 'the work itself is expensive'.
- **`cdk-toolkit`** — The Angular CDK: Overlay, Portal, Virtual Scroll & Drag-Drop  
  The CDK appears in exactly one place in the whole curriculum — a five-row table in the a11y lesson listing cdkTrapFocus, LiveAnnouncer, FocusMonitor and ListKeyManager — and nothing else. `cdkVirtualScrollViewport` gets zero hits anywhere, which means the curriculum has no answer to one of the most common Angular interview questions ('you have to render 100,000 rows — what do you do?'), even though the expert Performance lesson is the natural place for that answer and does not give it. Overlay + Portal are likewise absent, so a learner who has finished dynamic-components knows createComponent but not how real modals, tooltips, autocompletes and menus are built (positioning strategies, scroll strategies, backdrop, the top layer, disposal). This is cross-cutting infrastructure that sits between the framework and Angular Material, and it is where a lot of production Angular actually lives. Content: Portal/PortalOutlet and the DomPortalOutlet, OverlayRef with FlexibleConnectedPositionStrategy and scroll strategies, cdkVirtualScrollViewport with fixed and autosize item sizes plus the trap that it needs a bounded-height host, cdkDropList/cdkDrag, and BreakpointObserver for responsive logic in TypeScript.
- **`e2e-testing`** — End-to-End Testing an Angular App  
  The curriculum's Testing category stops at intermediate with testing-components and testing-services-http; there is no e2e lesson and the only mention of Playwright in 100 lessons is one clause in the animations exam corner ('E2E tools (Playwright) can force prefers-reduced-motion'). That leaves a genuine hole for both certification prep and interviews, and several Angular-specific behaviours are only testable here: verifying SSR/hydration actually happened (no NG0500 hydration mismatch in the console, content present before JS loads), asserting a route guard blocks a lazy chunk download, checking that @defer triggers fire on viewport, and confirming a view transition or reduced-motion override behaves. It is also the right home for the Angular-specific waiting story — why the old protractor waitForAngular does not exist any more, and how auto-waiting on web-first assertions replaces it in a zoneless app where there is no zone to be stable. Content: Playwright project setup against ng serve and against a prod build, resilient locators via getByRole (which ties back to the a11y lesson), network mocking with page.route, an axe accessibility assertion in the e2e layer, and where the unit/component/e2e boundary should sit.
- **`app-architecture`** — Application Architecture: Feature Boundaries & Component Roles  
  The expert Architecture category holds state-management, dynamic-components, host-directives and ngmodules-migration — four mechanisms, no lesson on how to lay out an application. The smart/presentational (container/presentational) split exists only as an answer in the interview bank, not as a lesson, and nothing covers feature-folder structure, which layer owns routes vs providers vs stores, dependency direction between features (feature A must not import feature B's internals), the shared/core folder conventions and when they become anti-patterns, barrel files and the circular-import failures they cause, or how lazy-route boundaries should line up with feature boundaries. 'How would you structure a large Angular application?' is close to universal in senior interviews, and after a learner has state-management plus standalone migration they have every ingredient and no recipe.
- **`project-testing-a-feature`** — Project: Testing a Feature End-to-End  
  The repo's own standards call out that the reference implementation's near-zero test coverage is a gap not to copy, and all three projects relegate testing to a 'further extensions' bullet. The testing-components and testing-services-http lessons cover APIs in isolation; what is missing is a walkthrough that tests one whole feature the way a job actually requires — a signal store without TestBed, a component with setInput and the ComponentFixture autoDetect/zoneless story, a functional guard invoked inside runInInjectionContext, an interceptor with HttpTestingController and provideHttpClientTesting, fake timers for a debounced filter and a token refresh, and where an e2e test earns its keep instead. 'How would you test this?' follows every interview whiteboard exercise in this slice.

### Low priority

- **`ci-basics`** — Continuous Integration: What Runs on Your Pull Request  
  git-basics tells the learner that on a PR 'teammates review the diff, comment line by line, and CI runs the tests' — and CI/CD, GitHub Actions and pipelines are mentioned nowhere else in the curriculum. terminal-and-npm likewise says 'your future CI pipeline is just the terminal commands you're learning now, run by a server on every push' and then drops it. A short lesson closing that loop would make three existing lessons pay off: a minimal GitHub Actions workflow that checks out the repo, runs `npm ci` (not `npm install`), then `ng lint`, `ng test --watch=false --browsers=ChromeHeadless` and `ng build`; reading a red check and finding the failing step's log; caching node_modules; and branch protection requiring green checks before merge. It is low priority relative to the others because it is adjacent to Angular rather than part of it, but it is the natural terminus of the Your Dev Toolkit arc and it is currently a dangling promise.
- **`angular-elements`** — Angular Elements & Custom Element Interop  
  Shipping an Angular component into a non-Angular page (`createCustomElement`, `customElements.define`, attribute/property/event mapping, `CUSTOM_ELEMENTS_SCHEMA` for consuming third-party web components) is absent from the entire curriculum. It is the natural terminus of this slice — it depends on ShadowDom encapsulation, `<slot>`-based projection and input transforms, all taught here — and it is a standard senior-interview question ('how would you reuse this component in another framework?'). Lower priority than typed templates because it is not on the certification path and affects fewer day-to-day tasks.
- **`realtime-feed`** — Project: Real-Time Feed — WebSockets, Signals and Zoneless  
  Every project in the slice is request/response. Push-driven state has its own failure modes that no lesson covers: a socket message arriving outside Angular's knowledge (the zoneless case where nothing schedules a refresh unless the value lands in a signal), reconnect with backoff, buffering while disconnected, ordering and de-duplication against the initial REST snapshot, and unbounded list growth. It is a common senior-interview design question and the natural place to make zoneless concrete rather than theoretical. Lower priority than the four above because it is less certification-relevant, but it is the last obvious hole in end-to-end coverage.
